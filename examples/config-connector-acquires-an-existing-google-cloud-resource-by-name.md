# Config Connector acquires an existing Google Cloud resource by name

## Scenario

A team applies a Config Connector manifest for a Google Cloud resource that may or may not already exist. The managing-and-deleting-resources page gives a walkthrough that acquires an empty BigQuery dataset, and it names Spanner instances as another covered resource type. [[sources/research-idempotency]]

## How it works

Create is built to be idempotent. If the resource does not exist, Config Connector creates it. If a resource with the same name already exists in the organization, project, or folder, Config Connector acquires it and starts managing it. A retried create after a crash therefore converges on the same object. Resources whose IDs are generated by the service can be acquired only through the `resourceID` field, because a name cannot identify them. [[sources/research-idempotency]]

## Deletion

By default, deleting the Kubernetes object deletes the cloud resource. The annotation `cnrm.cloud.google.com/deletion-policy: abandon` keeps the cloud resource. [[sources/research-idempotency]]

## Lesson

Same-name-means-same-resource works well when the cloud API accepts caller-chosen names and poorly when it assigns IDs, and it can take over a resource that happened to share a name. See [[findings/adopt-or-create-can-take-over-a-look-alike-resource]] and [[comparisons/ambiguous-create-and-adoption-strategies-across-crossplane-sap-ack-and-config-connector]].
