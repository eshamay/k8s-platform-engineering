# Part 5: Principles of Good Platform Architecture and Operating at Scale

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) and are finishing the tutorial series on controllers, API machinery and platform abstractions.<br>
> **Purpose:** Trace one Flux commit through server-side apply, finalizers and conditions to a Ready status, show that good platform architecture is the disciplined composition of the earlier mechanics, and describe what operating that architecture at scale requires.<br>
> **Status:** Active. The end-to-end trace is assembled from documented pieces, because no single source traces a Flux commit through to a Ready object (see section 12).<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-27<br>
> **Draws on:** [[concepts/universal-control-plane]], [[concepts/gitops-pull-based-delivery]], [[concepts/reconciliation-loop]], [[concepts/server-side-apply-and-field-ownership]], [[concepts/finalizers]], [[concepts/conditions]], [[concepts/scale-and-sharding]], [[concepts/pitfalls-and-case-studies]], [[concepts/tooling-landscape]], and the examples, findings, comparisons and decisions linked inline<br>

## 1. Recap: the layered stack from Parts 1 to 4

The earlier parts of this series built one idea in layers, and this final part puts the layers to work together. It helps to restate them in plain terms before we trace anything.

The foundation is the observation that Kubernetes ships two products in one box. One is a container scheduler. The other is a generic, extensible API machine: an API server that provides authentication, RBAC, admission, validation and watch, backed by etcd, plus a convention that controllers reconcile an object's `spec` (what you want) toward its `status` (what is observed). The second product has no inherent tie to pods, so anything that can be described declaratively and reconciled by a loop can become a custom resource, whether it is a cloud database, a DNS record or a whole cluster. That is the idea behind the [[concepts/universal-control-plane]], and every tool in this part depends on it. Once an outside thing is represented as a Kubernetes object, it inherits authentication, RBAC, audit and a shared tooling ecosystem.

The second layer is the controller itself. A controller runs a [[concepts/reconciliation-loop]]: a function that receives only the namespace and name of an object, never the event that woke it, reads the current state, performs API calls to close the gap, and writes status. Because the function can run many times in any order, it must be [[concepts/idempotency]] safe, and because it works from current state and not from a stream of events, it is level-triggered, meaning a missed event cannot leave the system permanently wrong. Under the loop sits the machinery from [[concepts/informers-reflectors-and-workqueues]]: a reflector lists and then watches the API server, an informer keeps an in-memory cache, and a rate-limited workqueue deduplicates object keys so that one object is never reconciled by two workers at once.

The third layer is the set of API conventions that let many writers share one object. [[concepts/server-side-apply-and-field-ownership]] records which manager owns each field in `metadata.managedFields`. [[concepts/finalizers]] hold an object in the API until its controller has cleaned up whatever lives outside the cluster. [[concepts/owner-references-and-garbage-collection]] let the cluster remove children when a parent goes away. [[concepts/conditions]] give every kind a common, machine-readable way to say whether it is ready.

The fourth layer is the set of abstractions that platform tools build on top. A [[concepts/provider]] teaches the control plane to speak to an external API and exposes [[concepts/managed-resource]] objects, each standing for exactly one outside resource. A [[concepts/composite-resource]] bundles several of those behind a simple API, and a [[concepts/composition]] defines how the bundle expands. On the delivery side, [[concepts/gitops-pull-based-delivery]] uses an in-cluster agent such as Flux to pull desired state from Git and apply it.

The thesis of this part is that none of these pieces is new when you meet it in a platform. A good platform is the disciplined composition of the same mechanics, and a failing platform is nearly always one of those mechanics used carelessly. The fastest way to see this is to follow one commit all the way down and then all the way back out.

## 2. End-to-end lifecycle trace: a Git commit to a Flux Kustomization to server-side apply

A note on evidence before we start. No single source traces a Flux commit step by step through to a Ready object. What follows is therefore an assembly of documented behaviors from the Flux documentation and the concept pages of the earlier parts, and we will mark the places where the documentation is silent. The composition is the point of the exercise, and it is the best test of whether the earlier concepts fit together.

Imagine a platform team that keeps a Git repository describing what should run in a cluster. A developer merges a commit that changes the image tag of a Deployment. Flux is a set of single-purpose controllers that communicate through custom resources, so the first thing to understand is who does what. A source controller watches a `GitRepository` object, fetches the repository on its interval and packages the content as an artifact. A kustomize controller watches a `Kustomization` object that points at that source, builds the manifests and applies them. The notification controller can accept a webhook from the Git host that tells the source to refresh immediately, which is described in [[examples/flux-notification-receivers-start-reconciliation-without-waiting-for-the-poll-interval]]. Without a webhook, the commit waits until the next interval fires, which is a quiet failure mode, because the system looks healthy while changes arrive late.

The handoff between the source controller and the kustomize controller has a few operational details that the Flux source code shows. The source controller serves the artifacts it builds through a small in-process HTTP file server, and it starts that server only after it has won leader election. Leader election means that several replicas of a controller may run but only one holds a lease and does the work. A standby replica reports itself not ready by design, so adding replicas of the source controller buys failover and not extra capacity, as the Flux sharding page itself says. A typical installation keeps the artifacts it builds in scratch storage that disappears when the pod does. A restart therefore most likely empties the artifact store, and every dependent waits while the next reconcile rebuilds it. In practice that means a source controller that is rolled often, or scheduled on nodes that get evicted, produces short windows in which Kustomizations cannot fetch their sources (see [[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]]).

Here is a minimal Kustomization of the kind a platform team would write. It is illustrative, the field names follow the Kustomization API reference, and the bracketed values are placeholders for choices each team makes.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: team-a
spec:
  interval: <how often to re-check>
  retryInterval: <delay after a failure>
  timeout: <time budget for one run>
  sourceRef:
    kind: GitRepository
    name: team-a-repo
  path: ./deploy/production
  prune: true
  wait: true
  serviceAccountName: team-a-deployer
  dependsOn:
    - name: infrastructure
```

Read it as a policy wrapped around the bare reconcile primitive. The `interval` says how often the controller re-fetches, builds, applies and checks for drift. The `retryInterval` is the delay before the next attempt after a failure, and the `timeout` caps the work of a single run. The `prune` field turns on garbage collection, `wait` holds the object until what it applied is healthy, and `dependsOn` makes this Kustomization wait for another one to be Ready. This is the structure described in [[examples/flux-kustomization-interval-and-retry-interval-set-the-loop-timing]]: a cadence, a failure delay, a time budget and a set of switches. The interval is a required field, so the drift-correction latency in Flux is whatever the author writes in the manifest, and it is worth choosing deliberately for each class of object. How often a controller re-checks the outside world is a trade-off between how quickly drift is noticed and how many calls are spent on the API behind it, and each tool and provider picks its own cadence. Changes to the source itself are picked up outside the interval when a webhook fires, so the interval governs mainly drift detection and periodic re-checks.

Now the apply. The kustomize controller does not use the old client-side approach of stamping a `last-applied-configuration` annotation. It uses server-side apply. The controller sends the set of fields it has an opinion about together with a field manager name, and the API server merges that into the live object and updates `managedFields`. In Part 3 we saw that if another manager owns a field with a different value, the API server answers with a conflict instead of silently overwriting. Flux's posture, as [[comparisons/ssa-conflict-policy-across-tools]] records it, is to force-apply its own intent and then offer escape hatches. The Kubernetes documentation recommends that controllers force conflicts on objects they own, while the same maintainers argue that CI/CD systems behave like users and should surface conflicts to humans. This unresolved tension is framed in [[decisions/force-conflicts-or-surface-them-to-humans]]. Other tools in this part sit at different points on that spectrum, as their source code shows. kro applies the resources it templates with server-side apply and forces ownership of them, but a patch node that contributes fields to an object kro does not own is applied under its own manager without force, so it claims only the fields it sets ([[findings/kro-applies-template-resources-with-server-side-apply-and-force-and-applies-patch-contributions-without-force]]). The Cluster API topology controller forces ownership under the manager name `capi-topology` while letting provider controllers co-author the generated objects, although co-authored list slices can reconcile forever when apply cannot remove list items ([[findings/cluster-api-co-authored-list-slices-can-reconcile-forever-and-server-side-apply-can-fail-to-remove-list-items]]). The ACK runtime does not use server-side apply at all: it sends merge patches and sets no field manager ([[findings/the-ack-runtime-sends-merge-patches-and-sets-no-server-side-apply-field-manager]]). Helm is part of the same spectrum, because a release can be applied client-side or server-side, so a cluster can hold releases applied in both ways and the field-ownership records on those objects differ.

Flux runs a server-side apply dry run on every interval to detect drift, which is why a hand edit gets reverted. [[examples/gitops-reverts-a-hand-edited-deployment]] describes the outcome: the revert is not a bug, it is a level-triggered controller doing what it was built to do, and teams that need an emergency change must set `suspend` first, which stops both applying and drift detection.

The same field-ownership machinery explains the most famous way this goes wrong. In [[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]], Flux kept resetting a replica count, a horizontal autoscaler kept lowering it, and the cluster autoscaler added and removed nodes in a loop that a Flux blog describes as two controllers ping-ponging indefinitely. Flux's answer was a `.spec.ignore` list of JSON Pointer paths. A "strip" rule removes the field from Flux's payload when another server-side apply manager owns it, and an "adopt" rule keeps the live value when Flux is the sole owner. The price, recorded in [[findings/ignoring-a-field-in-flux-or-argo-cd-means-git-changes-to-it-are-no-longer-applied]], is that Git changes to an ignored field are no longer applied. A per-object annotation can also choose how Flux applies that one object, including leaving it alone entirely, as shown in [[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]. One more escape hatch matters when a stale field manager wedges the dry run itself. The ordinary takeover moves field ownership from a named legacy manager only after a dry run succeeds, so it cannot rescue an object that fails at dry-run validation. Taking ownership before the dry run solves that, but it is a blunt tool: it transfers every field owned by the named managers, prunes fields missing from the source, is not reverted if the apply then fails, and matches manager names exactly and not by prefix. It is meant only for recovering stuck objects and should be removed once they reconcile again ([[findings/the-flux-pre-dry-run-takeover-transfers-all-fields-of-the-named-managers-and-is-not-reverted-if-the-apply-fails]]). There is one limit that surprises people: lists in custom resources whose CRDs carry no merge markers are treated as atomic, so only one manager can own such a list ([[findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership]]).

The two big GitOps tools word their versions of this escape hatch differently, and each has a trap that the primary documentation describes. A Flux ignore rule can carry an optional `target` selector, and the Kustomization specification says that omitting it makes the rule match every object the Kustomization manages. A rule written with one Deployment's `/spec/replicas` in mind therefore also exempts that path on every other object, and real drift there goes uncorrected without any signal, so the safe habit is to give every rule a target ([[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]]). Argo CD's `ignoreDifferences` is narrower than its name suggests. Ordinarily Argo CD uses it only when computing the diff that drives the sync status, so an ignored field stops showing as OutOfSync, yet the next sync still applies the full manifest from Git and can overwrite the field, which looks exactly like a revert loop with a clean diff. Argo CD can be told to honor the ignore rules during the sync as well, but even then the rules apply only to resources that already exist, so a first create still applies every field ([[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]], [[comparisons/exemption-and-ignore-controls-across-tools]]). Neither tool documents an observe-only mode in the documentation pages for ignore rules and sync options, though that describes those pages and is not a statement from either project.

Secrets are the other writer problem that GitOps meets early, because a repository is a poor place for plaintext. The two projects take opposite stances. Flux decrypts inside the kustomize controller and supports SOPS, an open-source tool that encrypts the values inside a file while leaving the keys readable, as its only encryption provider, with the requirement that `metadata`, `kind` and `apiVersion` stay in plaintext so the controller can read the object before decrypting it ([[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]]). Argo CD's secret-management page strongly recommends the opposite design, in which an operator on the destination cluster (Sealed Secrets, External Secrets Operator, the Secrets Store CSI Driver or Vault Secrets Operator) populates the secret and Git never holds the value. It cautions against plugins that inject secrets while rendering manifests, because Argo CD stores generated manifests in plaintext in its Redis cache, secret updates become coupled to syncs, and the approach conflicts with the rendered-manifests pattern. The page is silent on SOPS and ksops (a Kustomize plugin that decrypts SOPS files), so Argo CD's position on those two tools is not stated, and the sources examined document no failure modes for either approach ([[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]]).

Identity is the last piece of the apply step. Unless the platform team locks it down, a Kustomization applies with the controller's own identity, which is powerful. The reference multi-tenancy repository, described in [[examples/flux-multi-tenancy-repository-isolates-tenants-with-service-account-impersonation]], starts the controllers with cross-namespace references and remote bases disallowed and with a low-privilege default service account for every Kustomization. A Kustomization then reconciles as a ServiceAccount in the tenant's namespace, and ordinary Kubernetes RBAC decides what that tenant's repository may create. A manifest that tries to create a ClusterRole is rejected by the API server. Without that lockdown the trade-off is stated bluntly in [[findings/without-lockdown-flags-a-flux-kustomization-applies-with-the-controllers-own-identity]].

At this point the Deployment's new image tag is in the API server. The Deployment controller, a built-in reconcile loop, creates a new ReplicaSet, which creates pods. Notice that Flux did not roll anything out. It declared intent, and a chain of other controllers carried it forward through owner references. That handoff, intent written once and realized by several loops, is the first architectural principle we will name later.

## 3. Continuing the trace: composite, composition function and managed resources reaching the cloud API

Suppose the same commit also adds a request for a database. The repository does not contain a cloud-specific resource. It contains a small custom object that the platform team designed, for example a composite resource of a kind the platform team calls a PostgreSQL instance. This is the layer where the platform team's opinions live.

In Crossplane, the schema of that small API is declared by a CompositeResourceDefinition, which becomes a CRD. A Composition says how an instance of that API becomes lower-level objects. In current Crossplane, a Composition is a pipeline of composition functions. A function is installed as a package and runs as a pod. On each reconcile, Crossplane calls the steps in order over gRPC, giving each the composite's observed state and the desired state accumulated so far, and each function returns what should exist ([[concepts/composition]]). One hazard here is worth memorizing for every author: a function that omits a resource from its desired state causes that resource to be deleted ([[findings/a-composition-function-that-omits-a-resource-from-its-desired-state-deletes-it]]).

Two points about functions are worth knowing. The name comes from the KRM Functions Specification (KRM, the Kubernetes Resource Model, is the convention that every object is a structured document with `apiVersion`, `kind`, `metadata`, `spec` and `status`). That specification is a client-side standard used by tools such as kpt and Kustomize: a function must be a container that reads a `ResourceList` document on standard input, writes one on standard output and exits non-zero on failure, and the spec is explicitly decoupled from the cluster. kpt and Kustomize can run functions without containers only through opt-in exec extensions that both projects' documentation discourages ([[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]], [[findings/kpt-and-kustomize-run-functions-without-containers-only-through-opt-in-exec-extensions-that-both-docs-discourage]]). Crossplane borrowed the idea and the name but speaks a different contract, a gRPC `RunFunction` call, so the two are not interchangeable ([[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]]). Crossplane's runner works differently from the KRM Functions model. Composition functions are long-running gRPC servers that the package manager deploys as ordinary Deployments behind a headless Service, and Crossplane calls them on every reconcile, rather than starting a container per run. The second point concerns pinning. Pinning a composite to a Composition revision freezes the pipeline definition but not the function code behind each step, because every step follows the active revision of the Function package, so upgrading a Function reaches pinned composites as well. Referencing a function by immutable digest is the way to keep old and new revisions running side by side ([[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]]).

The composite spec carries operational controls as well as user-facing fields. It selects a Composition with `compositionRef` or `compositionSelector`, can pin a composition revision, can be paused with the `crossplane.io/paused` annotation, and can be forced to reconcile with `crossplane.io/reconcile-requested-at` ([[examples/crossplane-xr-spec-pins-composition-and-status-reports-synced-and-ready]]). Version history matters: in Crossplane v1 a namespaced claim fronted a cluster-scoped composite, while in v2 the composite is namespaced and claims are gone for new-style definitions. Older tutorials describing claims and patch-and-transform may no longer match current behavior (see [[entities/crossplane]]).

The functions produce managed resources. A managed resource is a Kubernetes object that represents exactly one external thing, and the Crossplane documentation calls the thing in the cloud the external resource. It has `spec.forProvider`, which is the authoritative desired state, `status.atProvider`, which is what the provider last observed, and an external-name annotation that ties the object to the cloud identifier. A provider controller then runs a Connect, Observe, Create, Update, Delete cycle against the cloud API ([[concepts/managed-resource]], [[concepts/provider]]).

This is where idempotency stops being a theoretical virtue. Creating a cloud resource is not naturally idempotent. If a controller calls a create API and crashes before it records the returned identifier, the next reconcile cannot tell whether the resource exists, and a blind retry could leak the first one. [[concepts/idempotency]] lists four answers that the tools use: deterministic names (Config Connector acquires a same-named resource, ACK adopts by identifier), a persisted external identity (Crossplane's external-name annotation), recording intent before acting (Crossplane writes create-pending annotations and halts for a human if the outcome is unknown), and a server-side client token that lets the cloud recognize a retried request. Two more tools add mechanisms worth knowing. kro records the resources it is about to create in `status.managedResources` before it applies them, so if the controller restarts between applying a child and recording the result, the next reconcile still knows the child exists, and it applies with server-side apply and no force, so a clash with another writer is rejected as a conflict instead of overwriting ([[findings/kro-records-the-resources-it-is-about-to-create-in-status-before-applying-them-and-applies-without-force]]). That protects Kubernetes children and not an external cloud call, and the kro pages examined give no naming rule for children, so names are deterministic only as far as the graph author templates them. The comparison with Crossplane's create-pending annotation is an interpretation, and no source draws it. Cluster API takes a different approach, which is guidance for provider authors and not an algorithm: its best-practices page says not to use a derived infrastructure name as the sole lookup key, and asks for provider-owned tags or labels, plus a deterministic name shortening that keeps a readable prefix and adds a hash. It states no recovery algorithm for a create whose response was lost, so how a given infrastructure provider recovers is left to that provider ([[findings/cluster-api-tells-providers-not-to-use-a-derived-name-as-the-only-lookup-key-and-states-no-lost-create-algorithm]]). No source establishes which of these approaches is safest at scale.

The delete verb needs the same care on this side, and we will return to it in section 5. For now note one more arrow in the trace. The GitOps agent reconciles Git into the Kubernetes API, and the Crossplane controllers reconcile the API into reality. That is the two-loop structure described in [[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]. A green sync in the GitOps agent says only that the custom resource matches Git. It does not say the database exists, and drift in a composed resource may be corrected by the lower loop without the GitOps agent ever seeing a difference.

## 4. Status flowing back: conditions, observedGeneration, readiness and health rollups

Everything in the trace above flowed downward from intent to reality. A platform is only usable if the answer flows back up, and the vehicle is status. The spec-status split from Part 2 reserves `spec` for the user and `status` for the controller, and the standard way to say something useful in status is the condition.

A condition is one entry in `.status.conditions`. It has a `type` such as `Ready`, a `status` of `True`, `False` or `Unknown`, a machine-readable `reason`, a human-readable `message`, a `lastTransitionTime` and an optional `observedGeneration`. Here is how a Flux Kustomization might look partway through a rollout, again as an illustration of the documented fields.

```yaml
status:
  observedGeneration: 7
  conditions:
    - type: Ready
      status: "False"
      reason: DependencyNotReady
      message: dependency 'team-a/infrastructure' is not ready
      observedGeneration: 7
    - type: Reconciling
      status: "True"
      reason: Progressing
      observedGeneration: 7
```

The most important field to read is `observedGeneration`. The API server increments `metadata.generation` whenever the spec changes, and a controller copies the generation it has processed into status. If `generation` is greater than `observedGeneration`, the status describes an older spec and should not be trusted. [[concepts/conditions]] makes the point that under the "abnormal-true" polarity that kstatus describes (kstatus is a library from the Kubernetes SIGs `cli-utils` project that computes whether an object is ready by reading standard status fields such as conditions and `observedGeneration`, so tools can judge readiness without knowing each kind), the absence of problem conditions looks healthy, so a stopped controller looks identical to a healthy one unless you compare generations ([[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]). Leaving out `observedGeneration` is a common operator mistake. Without it on the conditions, a stale `ResourceSynced=True` looks identical to a current one, and consumers are pushed into fragile workarounds such as comparing managed-field timestamps ([[findings/missing-observedgeneration-hides-stale-status]]).

It helps to know exactly how kstatus reads these fields, because a great deal of GitOps tooling inherits its behavior. Reading the library's source, it evaluates an object in a fixed order. It first checks for a deletion timestamp, which reads as Terminating. It then compares `metadata.generation` with the top-level `status.observedGeneration`, and a mismatch reads as in progress. Next it scans the conditions in array order, where `Reconciling=True` means in progress and `Stalled=True` means failed, and the first match wins. Only then does it apply rules for built-in kinds and, for other kinds, fall back to `Ready`, where `True` reads as current and both `False` and `Unknown` read as in progress. Two consequences follow. A `Ready=False` condition on its own never reads as failed, because the library cannot tell a slow object from a doomed one. And a kind with no `Ready` condition at all is assumed to be always reconciled, which is the mechanism behind the premature-readiness problem described below ([[findings/kstatus-checks-deletion-then-generation-then-reconciling-and-stalled-then-ready-so-a-stale-top-level-observedgeneration-overrides-ready-true]], [[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]]). kstatus also reads only the top-level `observedGeneration`, because its condition struct has no per-condition field, so a per-condition value written under the newer `metav1.Condition` convention is never consulted by it ([[findings/kstatus-reads-only-the-top-level-observedgeneration-because-its-condition-struct-has-no-per-condition-field]]). Which polarity condition authors should choose is itself unsettled: kstatus favors the abnormal-true style, while the Kubernetes API conventions say that neither polarity can be recommended as a general rule, so the choice is left to the author, and consumers that assume the other polarity will misread the object ([[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]]).

Flux gives its own objects a clear reading guide, summarized in [[examples/flux-helmrelease-status-records-attempts-and-health]]. `Ready` is the headline, `Reconciling=True` is normal progress, `Stalled` means the release will not advance without a change, and a chain of `DependencyNotReady` conditions points at an upstream problem. The status never restates what the user wanted; it records what happened to that intent, including the last attempted revision and release action. There is one trap to know: a suspended resource keeps its last condition and can look healthy.

Crossplane splits the idea differently, and understanding the split is worth the effort. A managed resource reports `Synced`, which says whether the last reconcile succeeded, and `Ready`, which says the external resource is usable. A composite reports `Ready` only when the function pipeline says every composed resource is ready. While a cloud provisions a database, a user sees `Synced=True` and `Ready=False`, which means the controller is working and the thing is not usable yet ([[examples/crossplane-database-claim-reports-synced-and-ready]]). The platform's two failure stories are the mirror images. `Synced=False` with `Ready=True` is a silent failure: the thing exists and apps keep running, but Crossplane can no longer manage it, so drift is no longer corrected ([[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]]). And a summary condition can stay true while long work runs. In one reported case, an AWS MSK cluster update that took over an hour left `Synced=True` the whole time, and only an `AsyncOperation` condition said `Ongoing` ([[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]]). Providers generated with Upjet (the code generator and shared runtime that builds Crossplane providers from Terraform providers) report a successful reconcile while the asynchronous operation runs. The lesson is that a summary condition can stay true while long asynchronous work is running, so a consumer who cares about in-flight changes has to read the more specific operation condition and not only the summary.

Other stacks use different vocabularies for the same job, compared in [[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]. ACK adds `ACK.ResourceSynced`, `ACK.Terminal` and `ACK.Recoverable` and keeps `Ready` as a roll-up. Config Connector uses a single `Ready` condition whose reasons move through `Updating`, `UpToDate` and, on failure, `UpdateFailed`. Because `Ready=False` covers both an update in flight and an update that failed, the reason is the only way to tell them apart, so a consumer should match on the reason and not on the status alone. kro lets the author of a ResourceGraphDefinition (kro's single object that declares both the new API's schema and the graph of resources behind it) define instance conditions with CEL, the Common Expression Language, a small expression syntax that Kubernetes and its ecosystem use to write conditions over an object's fields. Cluster API moved to the standard condition type and split `Available` from `Ready`. Kubernetes defines a shared `metav1.Condition` type so that conditions look alike across kinds, but adoption is voluntary, so older APIs keep their own forms.

Why does this vocabulary matter so much to a platform? Because conditions are what ordering depends on. In Flux, a Kustomization marks itself Ready only after health checks pass, and that unblocks the Kustomizations that `dependsOn` it. Flux judges compatible custom resources with kstatus and others with CEL health expressions, which are short expressions the user writes to say what "healthy" means for a kind that does not follow the conventions. Argo CD aggregates the worst health among an application's immediate children and needs Lua checks for custom kinds, meaning small scripts in the Lua language that the user supplies to teach Argo CD what ready means for that kind ([[comparisons/health-and-readiness-models-across-tools]]). When a provider's conditions do not follow the convention, the rollup lies. The best-documented case is Cluster API: an object that had `observedGeneration` set but no conditions yet could look ready to kstatus, so Flux might start dependents too early ([[findings/premature-readiness-in-kstatus-based-tools]], [[entities/cluster-api]]). The remedy on the Flux side is a custom CEL health check that also looks at `observedGeneration`. Likewise, Crossplane's guide for running resources under Argo CD prescribes custom Lua health checks, since a generic agent has no idea what "ready" means for a custom kind ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]).

That last claim needs a qualification, because the two agents diverge here. Argo CD ships built-in Lua scripts for whole provider groups: `cnrm.cloud.google.com` (Config Connector), `services.k8s.aws` (ACK), `crossplane.io`, `upbound.io`, `kro.run`, and several `cluster.x-k8s.io` kinds. The scripts show exactly how each condition maps to a health state. The ACK script treats `ACK.Terminal=True` as Degraded, `Ready=False` as Progressing and `Ready=True` as Healthy. The Config Connector script returns Progressing while `observedGeneration` is stale, Healthy on the reason `UpToDate`, and Degraded on `UpdateFailed`. The Crossplane script marks `Synced=False` Degraded and treats a list of kinds that never carry conditions as Healthy, so they do not sit at Progressing forever. The cost of matching a whole group by wildcard is that a script that mishandles one kind blocks sync waves: Argo CD advances a wave only when the current one is synced and healthy, so an unhealthy provider object in an early wave stops everything after it ([[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]]). Flux has no per-provider logic at all. A Kustomization's `healthChecks` accept built-in kinds, Flux kinds and custom resources that are compatible with kstatus, and for the rest the author supplies CEL `healthCheckExprs`, so a provider's own `Ready` condition reaches Flux only through kstatus's generic handling. Flux's CEL cheatsheet lists a Crossplane library but, in the cheatsheet page examined, nothing for Config Connector or ACK, and the sources examined do not say how kstatus treats ACK's abnormal-true `ACK.Terminal` condition, so whether a terminal ACK error reads as failed under Flux is open ([[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]]). The premature-readiness race for kinds that start without a `Ready` condition is avoided by a CEL health expression that also checks `observedGeneration`. For a composite that wraps these objects the same logic applies one level up: Crossplane's `function-auto-ready` treats a non-built-in composed resource as ready only when it carries `Ready=True`, and kro's `readyWhen` expressions make dependents wait, so on paper both ACK and Config Connector objects satisfy them, but no worked example of Crossplane composing ACK or Config Connector objects was found, and that conclusion is an inference ([[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]]).

The lesson of this section is that a rolled-up status is only as honest as its definition of ready. The platform author chooses what the composite promises, and the platform is only trustworthy if that promise is true.

## 5. Deletion trace: prune, finalizers, propagation modes and ordered teardown

Creation is the easy half. Deletion is where platforms lose data and money, so we trace it with equal care.

Start with the commit that removes the database request from Git. With `prune: true`, Flux deletes objects that were applied earlier but are missing from the current source, using the inventory recorded in `.status.inventory` ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). Notice that this is not Kubernetes garbage collection. Flux and Argo CD apply objects they do not own through owner references, so each keeps its own record of what it applied. An object can opt out of pruning with a per-object annotation. The warning in [[findings/unintended-deletion-through-prune]] is that the boundary of "the desired configuration" is easy to misjudge, and a level-based loop deletes whatever it no longer sees in desired state. Argo CD treats pruning as an opt-in action with a guard against pruning everything when the source is empty, while Flux exposes explicit switches for it ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). Both make the destructive step an explicit choice.

The delete now reaches the composite, and this is where finalizers enter. When a client deletes an object that carries finalizers, the API server does not remove it. It sets `metadata.deletionTimestamp`, returns HTTP 202, and leaves the object visible as Terminating. The controller that owns each finalizer sees the timestamp, performs cleanup, and removes its own entry; when the list is empty, the object is deleted ([[concepts/finalizers]]). Here is the pattern in an object, illustrative of a managed resource under deletion.

```yaml
metadata:
  name: orders-db
  deletionTimestamp: "2026-11-25T10:15:00Z"
  finalizers:
    - finalizer.managedresource.crossplane.io
```

The finalizer line is the promise that the cloud database will be removed before the Kubernetes record disappears. The API server enforces rules around that promise: after the deletion timestamp is set, nobody can add a new finalizer, and the only permitted edit is removal. Custom finalizer names must be qualified with a domain. A well-written controller adds its finalizer on the first pass, before creating anything outside, and its cleanup must be idempotent and treat an already-deleted external resource as success.

The three deletion mechanisms divide the work. Owner references handle in-cluster, same-namespace cleanup. Finalizers handle external resources, cross-namespace cleanup and ordered shutdown. Propagation modes decide timing ([[comparisons/background-foreground-and-orphan-propagation-modes]]): background, the default, removes the owner at once and cleans dependents later; foreground puts a finalizer on the owner and waits for dependents that carry `blockOwnerDeletion=true`; orphan leaves the dependents behind.

Ordering is the hard part, because the default is no ordering at all. Crossplane composed resources carry owner references to their composite, and under background propagation the garbage collector marks all children deleted at once. [[examples/crossplane-foreground-and-pipeline-deletion-policies-order-composed-resource-teardown]] describes the options: `Foreground` keeps the parent until the children are gone, and `Pipeline` lets a function remove resources from desired state step by step. A Usage object can additionally block deletion of a used resource, such as a subnet, until its users are gone ([[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]]). An interaction between tools is easy to miss: Argo CD can delete with foreground propagation, and in that case Crossplane ignores the composite deletion policy and emits a warning event, so the ordered-teardown guarantee depends on settings in two tools ([[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]]).

kro takes a different route. It keeps an instance finalizer until every managed resource is gone, finds them through a persisted inventory, and deletes in reverse dependency order in waves, each fully gone before the next begins ([[examples/kro-deletes-instance-resources-in-reverse-dependency-waves]]). kro does this without owner references on the children it creates. kro's documentation says this is intentional, for two reasons: owner-reference garbage collection gives no ordering guarantee, and a namespaced owner cannot own a cluster-scoped child. Each child instead carries labels that identify the instance and an annotation that records its wave in the teardown order. kro finds the children from the instance's persisted inventory and not by re-evaluating the graph, so cleanup can proceed even when something the graph referenced is gone. kro does set an owner reference from the ResourceGraphDefinition to the CRD it generates. A tool that draws hierarchy from owner references will therefore not see the instance as the owner of its children, and kro's FAQ tells Argo CD users to add an owner reference and a tracking-id annotation by hand if they want Argo CD to track them ([[findings/kro-sets-no-owner-references-on-instance-children-and-tracks-them-with-labels-and-an-applyset-inventory]], [[examples/kro-resources-need-owner-references-and-tracking-ids-to-be-tracked-by-argo-cd]]). Crossplane, by contrast, has a gap: a credentials secret without its own finalizer can vanish before managed resources finish cleanup ([[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]]).

Config Connector shows what happens when no tool supplies teardown ordering. When a parent is deleted before its child, the child's reference can no longer be resolved, reconcile reports `DependencyNotFound`, and the child's finalizer is never removed. No Config Connector documentation page or source file among those examined describes a dependency-ordered teardown. One practitioner's case is a BigQuery table whose dataset was deleted first, and the workaround was a periodic job that strips the finalizer from such tables. That is safe only for parent and child pairs where deleting the parent also deletes the child in the cloud, as deleting a dataset does for its tables. The same post says Argo CD has no deletion ordering. The Argo CD documentation says wave order is reversed during pruning, but the sources examined do not say whether a cascading Application delete honors waves, so the two statements may describe different deletes ([[findings/a-config-connector-design-document-says-a-child-whose-parent-was-deleted-first-sticks-on-dependencynotfound-and-no-read-documentation-describes-ordered-teardown]], [[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]], [[examples/a-practitioner-ran-a-cronjob-that-removed-finalizers-from-config-connector-bigquery-tables-whose-dataset-was-deleted-first]]).

The tools also answer a different question, which is whether deleting the Kubernetes object should delete the real thing. Provider controllers such as Crossplane, ACK and Config Connector delete the external resource when the Kubernetes object is deleted, and each offers a per-object way to retain or abandon the real resource instead. Crossplane expresses this as `spec.managementPolicies`, a list of the verbs the controller is permitted to perform: observe-only is a list with only observation, orphan-on-delete is a list that omits delete, and a pause is an empty list. A resource whose permitted verbs omit delete is removed from Kubernetes while its cloud resource stays, and keeps costing money ([[findings/a-managed-resource-without-delete-in-its-management-policies-is-removed-from-kubernetes-but-its-cloud-resource-stays]], [[decisions/choose-management-policies-for-an-imported-resource]]). ACK and Config Connector use policy annotations on the object instead, and the policy must be in place before the delete happens. ACK also lets the policy be set on the namespace or for the whole controller, and the narrowest setting wins. That makes a controller-wide retain the weakest protection, because any chart or manifest that stamps an explicit delete setting on each resource overrides it. One reporter describes the practical consequence: a GitOps prune led to AWS deletion, and a controller-wide retain did not help because every chart-rendered custom resource carried an explicit delete setting. This is a single account without maintainer confirmation, so treat it as a strong warning and not as an audited incident. The design lesson is that protection belongs at the layer that is hardest to override ([[findings/ack-deletion-policy-resolves-from-the-resource-then-the-namespace-then-the-controller-default-and-one-reporter-says-chart-stamped-delete-defeats-a-controller-wide-retain]], [[findings/config-connector-deletion-policy-has-two-source-values-and-only-abandon-changes-the-delete-path-and-the-terraform-based-controller-path-is-unverified]]). The GitOps agents have their own prune opt-outs, which live in the manifests that GitOps manages and which protect only against that agent, whether they apply to one object or to a whole group of objects. Provider-side retention survives any client that deletes the object, including kubectl, but a retained cloud resource keeps costing money. No source recommends one placement over the other ([[decisions/protect-a-provider-managed-object-from-gitops-prune-with-a-provider-retain-policy-or-an-agent-side-prune-opt-out]]). Argo CD cascades an Application delete only if the Application carries a cascade finalizer, and a non-cascading delete either removes that finalizer or never adds it, which is the choice to make when the managed workloads must survive the Application. Pruning during a sync is governed by a separate propagation setting and should not be confused with how an Application delete is propagated. How Argo CD decides which objects it owns, and therefore which it may prune, depends on its resource-tracking method. Tracking by annotation, by label, or by both have different failure modes, since labels are length-limited and can collide with other tools, and a tracking marker that does not reference its own resource keeps that resource out of sync status and out of pruning. The documentation does not state how the tracking methods interact with owner-reference-based discovery of children ([[findings/argo-cd-applications-use-three-cascade-finalizer-names-and-a-non-cascading-delete-removes-the-finalizer]], [[findings/argo-cd-tracks-resources-by-annotation-by-default-and-label-mode-truncates-and-collides-with-other-tools]], [[decisions/choose-an-argo-cd-resource-tracking-method-annotation-annotation-plus-label-or-label]]).

Flux lets a Kustomization choose what happens to the objects it applied when the Kustomization itself is deleted: it can mirror its prune setting, delete them, wait for them to finish terminating, or orphan them. The controller adds a finalizer to the Kustomization before any other work so that a deletion cannot race its registration. When it waits for termination, that covers the finalizers the children carry, but the wait is time-limited. If the wait fails, Flux logs an error, emits an event and removes its own finalizer anyway, so a stuck child finalizer cannot hold the Kustomization forever, and the children are then left to their own finalizers, which means a provider resource may still be finalizing after the Kustomization is gone ([[findings/flux-kustomization-uses-finalizers-fluxcd-io-and-removes-it-even-when-waitfortermination-times-out]]).

Every tool registers its own finalizer and removes it only after cleanup, and kro does the same on its instances once no deletion candidates remain. Config Connector adds a second finalizer that defends against accidental deletion, and when a resource's CRD is being uninstalled it removes both and sets the resource to abandon, so uninstalling a CRD keeps the Google Cloud resources ([[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]], [[findings/config-connector-has-a-second-deletion-defender-finalizer-and-removes-both-finalizers-with-an-abandon-setting-when-its-crd-is-uninstalled]]). Cluster API orders teardown with a drain, volume detachment, hooks and then infrastructure deletion. These are compared in [[comparisons/deletion-policies-across-gitops-and-provider-tools]]; the decision itself is framed in [[decisions/delete-or-retain-the-external-resource-when-the-kubernetes-object-is-deleted]]. Cluster API deliberately chose annotation hooks over finalizers for blocking machine deletion, because a misbehaving controller could remove a finalizer ([[findings/cluster-api-chose-annotation-hooks-over-finalizers-for-machine-deletion-because-a-misbehaving-controller-could-remove-finalizers]]).

The failure modes follow directly. A finalizer only works while its controller runs, so deleting the cluster first, or removing a Crossplane provider before its managed resources, strands the cloud resources, still billing ([[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]], [[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]]). The first of those rests on a single consultancy blog and the second on Crossplane's documentation. Forcing a finalizer off to unstick an object skips the cleanup it guarded ([[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]). Forcing has an in-cluster failure mode too. The official Kubernetes guidance on finalizers warns that finishing a namespace by sending an update to its `finalize` subresource with `spec.finalizers` set to null may delete the namespace and leave orphan objects in a namespace that no longer exists, which it calls a confusing state. It says the namespace can be re-created by hand and that the orphaned objects sometimes reappear under it, which makes manual cleanup possible, though it names no condition for when they reappear and gives no frequency. The same guidance makes a point that explains why stuck objects are common. A finalizer is only a key in a list and does not have to name any code, so a ConfigMap given a finalizer that no controller handles stays in deletion until someone patches `/metadata/finalizers` away ([[findings/forcing-namespace-finalization-can-leave-orphan-objects-in-a-namespace-that-no-longer-exists-and-recreating-the-namespace-may-bring-them-back]], [[examples/a-configmap-with-a-finalizer-no-controller-handles-stays-in-deletion-until-kubectl-patch-removes-the-finalizer-list]]). The practical rule is to uninstall controllers only after their custom resources are deleted.

Public reports from individual users show these mechanisms in practice. They are issue reports and not organization-authored postmortems, and their authors are anonymous or identified only by a handle, so read them as reproductions and not as audited incidents. In one, a GitOps prune removed a custom resource whose controller deleted the cloud resource but did not treat the later not-found answer as success, so the object sat in Terminating until someone patched the finalizer off by hand. That manual patch was safe because the cloud resource was already gone, but the same patch would leak a billing resource if the cloud object still existed ([[examples/an-argo-cd-prune-left-an-ack-wafv2-webacl-terminating-on-its-finalizer-after-the-aws-resource-was-already-gone]]). In a second, a reporter describes a multi-cluster setup with leader election: objects deleted on a standby cluster stay in Terminating because the standby does not process them, and when that cluster becomes leader it runs the stale deletion against cloud resources that another cluster may have re-created under the same name. This is one reporter's account of a scenario ([[findings/config-connector-leader-election-across-clusters-can-run-a-stale-deletion-against-live-google-cloud-resources]]). In a third, an author's own audit of one provider family, not an observed production count, argues that a lost create response either duplicates a cloud resource or wedges the custom resource because the name already exists. Recording the cloud identity immediately after the create call narrows that window but cannot close it, because a crash between the cloud call and the write can still lose the identifier ([[findings/an-ack-audit-found-48-resources-in-22-controllers-where-a-lost-create-response-duplicates-the-resource-or-wedges-the-custom-resource]]). The Kubernetes finalizers documentation and the issue trackers of Kubernetes, Cluster API, Crossplane and ACK contain no quantification of how often forced finalizer removal orphans resources, so the frequency of that mistake remains unknown and should not be stated as a number ([[findings/no-source-quantifies-how-often-forced-finalizer-removal-orphans-guarded-resources]]).

Reporter accounts show the same destructive path from the delivery side, and all are anonymous. In one, a user wiped the namespace holding the delivery agent and reinstalled it, after which it began deleting the applications it had managed, which points to the cascade finalizer on the Application objects, though the maintainers did not confirm the root cause. In another, deleting one generated Application removed the workloads it managed, including namespaces and the agent itself, and no mechanism was established. In a third, replacing an explicit Namespace manifest with the create-namespace sync option caused the sync to delete and recreate the namespace, which deletes everything inside it ([[findings/deleting-or-recreating-an-argo-cd-parent-can-cascade-to-everything-it-managed]]). Taken together with the Skyscanner outage in section 10, they give reporter-level and one named-organization example of an accidental delete, but no named organization has published a postmortem of an accidental prune of provider-managed cloud resources.

## 6. Principles of good platform architecture, drawn from the traced lifecycle

The trace above is long, but a handful of principles recur at every step. Each is a reason the design works, and each has a documented way of failing when ignored.

The first principle is that intent is written once, declaratively, and realized by many small loops. Flux declares a Deployment and lets the built-in controllers produce pods. The platform declares a composite and lets functions and providers produce cloud resources. Each controller owns one aspect, which is the design the Kubernetes documentation favors. This works because the loops are level-triggered and idempotent, so a crash, a missed event or a duplicate run changes nothing about the end state. When the principle is violated, as with logic keyed to specific events, resources get stuck ([[findings/event-specific-logic-in-reconcilers]]).

The second principle is that events are hints and state is truth. Webhooks, watches and notification receivers lower latency, but the interval and the full reread of state are the safety net. Flux's notification receiver speeds a commit along, while the poll interval guarantees it eventually arrives. See [[decisions/events-as-hints-state-as-truth]]. The consequence is that detection latency equals the interval, so you choose intervals per resource class ([[findings/drift-detection-latency-is-the-interval]]).

The third principle is that every writer must be identified, and shared objects must have explicit ownership. Server-side apply makes ownership visible and turns a clash into a conflict. A platform that lets Flux, an autoscaler and cert-manager touch one object without an ownership decision will fight indefinitely. Which conflict policy is the best default is an open question, since forcing hides real disagreement ([[findings/forcing-conflicts-hides-disagreements-between-writers]]).

The fourth principle is that deletion deserves as much design as creation. The delete verb is destructive for external resources, so good platforms make the outcome explicit through finalizers, deletion policies, management policies and ordering controls, and they make the default safe for the data that matters. Argo CD makes destructive actions opt-in while Flux exposes explicit switches for each; neither is "right," but both are explicit.

The fifth principle is honest status. A readiness signal is a contract with other automation. If it says ready too early, dependents start against nothing. If it stays true while work is ongoing, alerts stay silent. Good platforms set conditions on first visit (even as `Unknown`), track `observedGeneration`, separate "controller can reconcile" from "thing is usable," and teach generic agents the health meaning of custom kinds.

The sixth principle is that every loop has a budget, and the budget should be explicit. A workqueue limiter normally protects the API server, but for a provider the same queue is also the budget for someone else's API, because the rate of reconciles is a good proxy for the rate of external API calls ([[examples/crossplane-max-reconcile-rate-turns-reconcile-rate-into-an-api-call-budget]]). A cap on parallel reconciles is not a cap on calls per second: how many calls per second it produces depends on how long each reconcile takes, so a concurrency setting does not state a call budget on its own. Tools that re-check slowly make the same trade of freshness for API cost. Self-healing also needs a brake, and Cluster API shows that the brake is something you must configure. A machine health check can stop automatic remediation when too many machines look unhealthy at once, because that pattern usually points to a shared cause such as a network fault and not to many independent machine failures. Without a threshold, machines are remediated no matter the state of the cluster, and control-plane remediation should likewise carry a retry limit, because an unset limit retries forever ([[findings/the-cluster-api-machine-health-check-short-circuit-is-off-by-default-so-remediation-is-unbounded-until-a-threshold-is-set]], [[findings/remediation-can-amplify-an-outage]]).

The seventh principle is that blast radius should be a design decision. A control plane that manages everything concentrates authority. ACK runs one controller per AWS service with scoped IAM; a single management cluster or shared provider credential enlarges the blast radius; and whoever can create a custom resource inherits the controller's cloud rights ([[findings/blast-radius-and-privilege-centralization]]). RBAC on the platform API is the security boundary, and Flux's per-tenant impersonation is one way to apply that principle.

The eighth principle is to keep abstractions small and honest. A platform API is a contract that users depend on. One practitioner blog advises against mega-Compositions and against APIs that mirror a cloud's own resource names, and Crossplane's own cost admission is that it needs a hosting cluster, Kubernetes skills and platform-team-owned abstractions ([[findings/crossplane-adoption-needs-a-hosting-cluster-kubernetes-skills-and-platform-team-owned-abstractions]]). The expressiveness question, functions versus CEL graphs, is compared in [[comparisons/helm-versus-kro-versus-crossplane-as-platform-abstraction-layers]].

The ninth principle is to stage risky automation. Drift correction, pruning and cluster-wide defaults all amplify a mistake through a loop. Grafana's 2019 outage came from a new cluster-wide default PriorityClass that a ReplicaSet kept reapplying to every recreated pod, preempting every production ingester and causing an outage, with no data lost ([[findings/a-new-cluster-wide-default-must-wait-until-existing-workloads-carry-explicit-values]]). The pattern is to add the explicit value first and change the default second, and to adopt automatic correction in stages ([[decisions/staged-adoption-of-automated-drift-correction]]).

## 7. Scale: informer memory, workqueue rates, API priority and fairness, etcd limits

Scale in this world is a set of separate limits, and the practical method the sources describe is to find which resource saturates first and then either raise it or split the work ([[concepts/scale-and-sharding]]).

At the cluster level, SIG Scalability publishes a tested envelope on the order of thousands of nodes and a hundred thousand or more pods, with a cap of roughly a megabyte and a half on the size of one object. The page says explicitly that these thresholds are not hard limits and that crossing one degrades performance, that they are scoped to built-in resource types and a particular test setup, and that the dimensions interact, so the envelope is not a cube. CRD count is not one of the tested dimensions, which is exactly where platform tools fell in. Operators of many clusters give tighter advice: Gardener says most clusters should stay roughly an order of magnitude below the tested node maximum and that webhooks and object counts need control ([[examples/gardener-advises-keeping-most-clusters-under-about-500-nodes-and-controlling-webhooks-and-object-counts]]). The gap is not a contradiction, because the two answer different questions: a tested maximum versus working advice. Treat the envelope as an upper limit and operator advice as a conservative target ([[findings/tested-scalability-maximums-and-operator-advice-differ-by-an-order-of-magnitude]]).

Underneath is the shared store. Every custom resource lives in etcd, which has a single Raft write leader, a storage size that is meant to stay modest and revision growth that needs compaction. A single request is also capped at a size below the API server's own request limit, so the store's limit binds first, which matches the object-size cap in the SIG Scalability envelope. Mitigations include moving Events to a separate etcd, alternative backends and watch-cache improvements ([[findings/etcd-scale-limits-of-the-shared-store]]). Ant Group's very large cluster reduced apiserver memory substantially by serving list requests from the watch cache, among other changes, which shows that list traffic is a main cost of a large shared control plane ([[examples/ant-group-large-cluster-tuning-of-apiserver-watch-cache-and-etcd]]).

Inside a controller there are four limits, and they are worth understanding separately. First, the informer cache holds every watched object with no eviction, so memory grows with what you watch ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]). Since nothing is evicted, the only way to shrink the cache is to watch less or keep less, and controller-runtime's cache package offers several options, each with a cost its source names ([[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]). Restricting the cache by type, namespace, label or field selector limits what the list-and-watch fetches, at the cost that anything outside the restriction is invisible to the cache, so the selector must match everything the reconciler reads. Transforming objects as they are stored, for example by stripping managed fields, can reduce memory, though that is a vendor statement and not a measurement, and it is unsafe if the reconciler reads those fields from cached objects. Caching only an object's metadata means the full object is unavailable from the cache. Reading a type straight from the API server saves cache memory and costs an API call per read. Skipping the deep copy on cache reads saves CPU but lets a careless caller mutate a shared cached object, and failing on a read of an unplanned type turns a silently started informer into an error. No source gives memory measurements for any of these, so the size of the savings is unquantified. Second, the workqueue never processes one key concurrently, so throughput is set by worker count and reconcile duration and not by the object count; a slow reconcile hogs a worker and deepens the queue. Third, the client-side rate limiter, set by QPS and burst, throttles requests before they leave the process. Fourth, leader election means only one replica reconciles, so extra replicas add failover and not capacity ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

Two throttling layers are easy to confuse. Client-side throttling delays requests inside the process. Server-side API Priority and Fairness classifies requests by FlowSchema into priority levels with their own concurrency shares, queues with shuffle sharding, and rejects with HTTP 429 when a level saturates, so one badly behaved controller need not starve others. The design is more approximate than that summary suggests. Its fair queuing is approximate in how it shares capacity among queues. A LIST costs more than one unit of concurrency, growing with the number of objects returned, and a client that requests big responses and does not finish reading them can hold a large share of capacity for a long time, so one slow reader can still tie up capacity that other flows need ([[findings/apf-fair-queuing-allocates-seats-equally-and-a-slow-reader-can-hold-hand-size-times-ten-seats]]). A controller's own log line saying a request waited because of client-side throttling, not priority and fairness, shows why the distinction matters: raising server capacity would not have helped ([[findings/client-side-throttling-and-server-side-apf-are-separate-layers]]).

Watches have their own failure. When a resource version is too old, the server answers 410 Gone and the client must relist. If many clients lose their watch together they relist together, a storm ([[findings/an-expired-resourceversion-forces-a-relist-and-synchronized-relists-can-storm]]). Bookmarks, the server watch cache and jittered backoff are the mitigations. The default workqueue limiter combines two ideas, and it helps to see them in plain terms. Exponential backoff means that each time the same object fails, the wait before retrying it roughly doubles, so a persistently broken object backs off quickly instead of hammering the API server. A token bucket works like a jar that refills at a steady rate: every reconcile must take a token, so the queue can burst briefly when the jar is full but cannot sustain more than the refill rate over time. Together they keep one failing object and one busy burst from crowding out everything else. The per-object backoff protects the API server from a persistently failing object, while the overall token bucket caps total throughput. Which limiters apply depends on the controller library and its queue type.

The failure that ties this together is described in [[examples/an-openai-outage-shows-many-api-clients-can-overload-the-control-plane]], and OpenAI published its own postmortem for it. In 2024 OpenAI rolled out a new telemetry service, and its postmortem says the service's configuration caused every node in each cluster to run resource-intensive Kubernetes API operations whose cost scaled with the size of the cluster, so the API servers were overwhelmed in most large clusters and services were significantly degraded for hours. The data plane could mostly run on its own, but DNS-based service discovery relied on the control plane, so cached records hid the failure for a while and then, as they expired, services began failing and the expiring caches added load ([[findings/dns-caching-hid-the-control-plane-failure-for-about-twenty-minutes-before-expiring-records-added-load]]). Remediation was slow because removing the telemetry service required control-plane access that the overload had taken away, so teams scaled down clusters, blocked network access to the admin APIs and scaled up the API servers in parallel. Staging did not catch it because the pre-rollout checks looked at CPU and memory and not at API server load. All of these details are self-reported by OpenAI. The postmortem does not say the calls were list or watch calls or that the service was a DaemonSet, so any such claim is an inference, and the link to informers is indirect. Use the incident as an illustration that [[findings/control-plane-overload-blocks-the-remediation-that-would-fix-it]]. A related, widely known principle follows: keep the means of repair off the path that can fail. Fail-closed admission webhooks are the same trap, because an unreachable backend with `failurePolicy: Fail` blocks the writes needed to repair it ([[findings/fail-closed-webhooks-can-block-the-writes-needed-to-repair-them]]); the webhook guidance is backed by one primary postmortem, Jetstack's, described in section 10. No primary postmortem of a CRD deletion cascade or an etcd quota alarm turned up, though many searches returned empty results, so that absence is weak evidence ([[findings/no-primary-postmortem-was-found-for-a-crd-deletion-cascade-or-an-etcd-quota-alarm]]).

Finally, CRD count is itself a scale dimension. Upbound's test of a control plane of about two thousand managed resources showed that every CRD adds cost. Client discovery needed hundreds of HTTP requests, the server spent significant CPU computing OpenAPI schemas, and each CRD added memory, so an API server managed this way can be killed for running out of memory long before the object count looks large. That shows CRD count is a real scale dimension that the built-in test envelope does not cover ([[examples/upbound-tested-a-multi-cloud-control-plane-of-about-2000-managed-resources-and-upstreamed-kubernetes-fixes]]). These are Upbound's own measurements. The description of API Priority and Fairness above rests on the Kubernetes documentation page, and this part makes no claim about portions of its design beyond those cited.

## 8. Sharding and tuning: Flux label sharding, Argo CD cluster sharding, Crossplane provider families, domain-scoped control planes

There are two levers: raise capacity vertically, or split the work along a stable key.

For Flux, the first lever is vertical: give the controllers more worker concurrency, more memory and CPU, and a larger cache for Helm repositories ([[examples/flux-controllers-expose-worker-concurrency-and-helm-cache-size-as-tuning-knobs]]). The sources point toward tuning first and sharding only when one instance reaches its structural limits, because tuning adds no operational moving parts ([[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]]). Morgan Stanley took exactly the tuning route, as we will see.

When tuning is not enough, Flux shards by label. Additional controller deployments run side by side, each watching only the objects that carry its own value of a sharding label, while the default controllers skip labeled objects so nothing is handled twice ([[examples/flux-sharding-splits-reconciliation-across-label-selected-controller-instances]]). The sharp edge is consistency: a HelmRepository, the HelmChart generated from it, and the HelmRelease that uses the chart all need matching labels, or the pieces land on different controllers ([[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]]). A parent Kustomization can bulk-label children, and the Flux Operator can declare shards declaratively. A HelmChart is generated from a HelmRelease and not written by hand, so its shard label is set through the HelmRelease's chart metadata, and the main controllers are told to ignore any labeled object. If a HelmRelease carries the key but its chart does not, a different controller ends up handling the chart than the one that needs its artifact, though the documentation does not spell out the symptom a user would see ([[findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels]]). The sharding page says the notification controller and the source-watcher do not support sharding, and its example recipe deletes the image reflector and image automation Deployments from the shard sets, so the recipe shards the source, kustomize and Helm controllers and leaves image automation to the default instance. Whether the image controllers can be sharded is not stated, so a plan that targets load from notifications or image scanning will not be relieved by adding shards ([[findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded]]). Each shard also elects its own leader, so a shard does not compete with the default instance for a lease. The one named project that automates this is Cozystack, whose operator creates Helm controller shards in proportion to the number of HelmReleases and places tenants greedily. That is the project's documented design intent, with no measured outcome and no independent confirmation of production use ([[examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard]]).

Argo CD shards by destination cluster. Application-controller replicas are told how many replicas exist, and clusters are assigned to replicas by an algorithm or pinned by hand through the cluster's secret. The simplest algorithm distributes clusters by identifier in a non-uniform way, so it can be uneven, while the alternatives balance better and rebalance less, so a team that cares about even distribution should choose its method explicitly and not rely on the simplest one. Like Flux, Argo CD's controller can also be tuned vertically, by giving it more processing capacity and memory as the application count grows ([[examples/argo-cd-application-controller-shards-clusters-and-tunes-processor-counts]], [[findings/argo-cd-legacy-sharding-can-be-uneven-and-the-other-algorithms-were-labelled-experimental]]). Compare the two ideas in [[comparisons/flux-label-sharding-versus-argo-cd-cluster-sharding]]: Flux's key is a label on each object, which is flexible and requires discipline, while Argo CD's key is the destination cluster, which fits hub-and-spoke setups naturally.

Hub-and-spoke deserves one clarification, because "pull-based" is easy to over-read. A central Argo CD instance targets remote clusters that are registered with it, so delivery to a fleet is a push from the hub into each spoke even though every Application pulls its source from Git. A separate project, `argocd-agent` in the `argoproj-labs` organization (a Labs project, not core Argo CD), describes the inverse model in which lightweight agents reach back to a central hub, with Managed and Autonomous agent modes. Flux can also target a remote cluster through a kubeconfig reference on the Kustomization, although the more common Flux layout runs a controller set in each cluster ([[findings/argo-cd-reaches-into-registered-clusters-from-a-hub-and-the-argocd-agent-pull-model-is-a-labs-project-of-unverified-maturity]], [[decisions/reach-spoke-clusters-from-a-central-argo-cd-hub-or-with-argocd-agent-pulling-from-the-spokes]]). On the Argo CD side the fleet is usually generated by an ApplicationSet, which stamps out Applications from generators, and the documentation describes limits on how generators can be composed. Generators that poll an external system also carry their own polling and rate-limit trade-off. The sources examined state no quantified scale limit for ApplicationSets or for hub-and-spoke Argo CD, which means the limit is undocumented and not necessarily nonexistent. The RollingSync strategy for staged rollout across a fleet has costs of its own. It takes over sync control from every generated Application (which also gives up the self-heal and automated prune a team may rely on), it watches only Application health and so depends on how honest that health is, and an Application that no step selects is silently left out of the rollout ([[findings/applicationset-rollingsync-is-beta-forces-autosync-off-and-watches-only-application-health]]). Finally, a head-to-head comparison of Argo CD and Flux behavior is still assembled from each project's own documentation, because no neutral benchmark or CNCF comparison was found ([[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]).

The same split-by-key idea appears outside GitOps. kro funnels the events for all of its instances through one shared, rate-limited queue. Because every ResourceGraphDefinition feeds the same queue, a rate limit on that queue works as a fairness device: a definition with thousands of busy instances, or one stuck in a failure loop, can only consume its share of the worker time and API calls, and cannot starve the others. The caps matter because without them a single misbehaving definition would be limited only by how fast the cluster could answer. The same backoff-and-token-bucket ideas described in section 7 apply, and a retry cap adds a final stop so that an object that never succeeds is eventually left alone instead of being retried forever ([[examples/kro-shared-queue-tunes-throughput]]). kro exposes tuning for this shared queue's retry behavior, parallelism, backoff and request rate. There is no measured throughput data, only an open request for performance testing and a maintainer proposal for weighted queues ([[findings/kro-s-single-shared-queue-can-starve-resources-and-a-maintainer-proposed-weighted-queues]]). Crossplane composite load is arithmetic: every composite is reconciled on a periodic cadence and each function step is a gRPC call, so the number of function calls grows with the number of composites times the number of steps, and large composites can exhaust function memory according to a third-party article whose log excerpts are labelled simulated ([[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]). Providers generated from Terraform sit at a different layer with their own, slower cadence, so a drift latency quoted for Crossplane is meaningful only when it names the component. How often a controller re-checks the outside world is a trade-off between how quickly drift is noticed and how many calls are spent on the external API, and each tool and provider picks its own cadence.

A word on how much to trust kro's scale story, because the sources disagree with each other. The kro documentation FAQ says kro "deploys a dedicated controller" for each ResourceGraphDefinition, while the tuning page and the source describe one dynamic controller with one shared queue and one parent watch per definition. The code and the tuning page agree, so the FAQ wording is the outlier, and a reader who sizes kro as many controllers with separate queues will look for isolation that does not exist ([[findings/the-kro-docs-faq-says-a-dedicated-controller-per-rgd-while-the-tuning-page-and-source-describe-one-shared-queue]]). The scale evidence itself is thin: the sources contain no benchmark, no measured limit, no adopters file and no named production adopter, only open requests for weighted queues and automated performance testing. The tuning documentation warns that a definition that watches a very large number of objects can fail to sync its watch. On governance, kro is a Kubernetes SIG Cloud Provider subproject, and it offers a second, newer way to express graphs on the same engine, so a team can choose between ResourceGraphDefinitions and that graph abstraction while both ride one engine ([[decisions/build-platform-apis-on-resourcegraphdefinitions-or-track-the-alpha-graph-api]]).

kro is also offered as a managed capability on one cloud, Amazon EKS, so customers of that service do not install or scale the controllers themselves, and it integrates with ACK for AWS resources and with Argo CD for deploying kro custom resources across clusters. That is a statement about packaging and not evidence of scale or adoption ([[examples/the-eks-kro-capability-composes-ack-s3-buckets-with-deployments-and-config-maps]]).

For Crossplane the dominant scale problem is CRD count, and the remedy is packaging. The original monolithic AWS provider registered a CRD for every AWS service, hundreds in all, which could leave the API server unresponsive for a long time during scale-up. Provider families split the monolith so an operator installs only the member providers for the services in use, sharing a common configuration provider, at the cost of running more provider pods ([[examples/crossplane-provider-families-let-operators-install-only-the-cloud-services-they-use]], [[findings/splitting-a-provider-into-a-family-trades-fewer-crds-for-more-pods-and-memory]]). A second control is activation policies, which let an operator choose which managed resource definitions become served CRDs, by exact name or by pattern, so the CRD count can be limited without splitting packages ([[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]]). Activation is one-way, so a definition that has become active cannot be deactivated, which makes the choice of what to activate a trade-off between flexibility and CRD load, and providers declare whether their definitions start inactive or active ([[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]]). Crossplane's scaling guidance is scattered across pages and states no numeric limits for composites or composed resources. It relies on the API server's Priority and Fairness for traffic control and offers a circuit breaker on composites as a runaway guard. ACK avoided the problem by shipping one controller per service from the start ([[comparisons/provider-families-versus-per-service-controllers]]), and the choice among families, filtering and lazy loading is framed in [[decisions/split-a-large-provider-into-families-or-filter-or-lazy-load-its-crds]].

Where the cost moved after the CRD problem was attacked is the controller's own cache. Crossplane core strips the OpenAPI schemas, which are most of a CRD's size, from the CRDs it caches and excludes Secrets from its client cache, and the project reports that this substantially reduces memory on clusters with very many CRDs. That is a self-reported claim and not an independent benchmark ([[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]]). The Upjet runtime that produces most large providers has no single execution model: it supports several Terraform execution modes chosen per resource, a fork-based mode that spawns the Terraform CLI and provider process and keeps a workspace per resource, and no-fork modes that call the provider as a Go library. ([[findings/upjet-supports-three-terraform-execution-modes-selected-per-resource-configuration]]). Package installs have their own scaling behavior. Crossplane's resolver builds a dependency graph from the cluster-scoped lock object, never modifies it, and creates only the first missing dependency on each pass, so a chain of unmet dependencies fills in over several reconciles ([[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]]).

Config Connector and ACK are worth stating next to Crossplane because their controller design can be read from source. Config Connector routes each kind to one of three reconciler implementations, a direct controller, a Terraform-based one and one built on Google's declarative client library, and which one a kind uses is chosen in a static table. All three end a successful pass the same way, so the controller kind alone does not change how quickly drift is noticed ([[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]]). There is no separate drift poll: each reconcile reads live state and compares it to the desired state, so drift detection runs at that cadence, and failed reconciles back off exponentially. Config Connector is installed in namespaced mode, the recommended mode, with one context per namespace naming that namespace's Google service account, or in cluster mode, which takes exactly one credential for every resource ([[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]]). Unless a lease policy is set, two objects can manage the same cloud resource. ACK re-checks resources on a periodic resync cycle, and disabling its cross-namespace references is a reference-resolution setting and not a tenant-isolation boundary ([[findings/disabling-ack-cross-namespace-references-is-not-tenant-isolation]]). When these tools are wrapped by a composition, the only first-party example is ACK's kro guide, which composes an S3 bucket, a DynamoDB table and a Deployment, waits for the ACK resources to become ready before creating dependents, and on deletion removes the Deployment first and then the AWS resources following ACK's deletion policy ([[examples/the-ack-docs-kro-guide-composes-an-s3-bucket-a-dynamodb-table-and-a-deployment-and-deletes-the-deployment-before-the-aws-resources]]).

Domain-scoped control planes are the architectural version of the same idea. Two practitioner blogs argue that teams no longer need one monolithic Crossplane instance and propose several small control planes scoped to domains such as networking or data. This is advice and not evidence: neither post names an organization running it or gives numbers ([[examples/domain-scoped-crossplane-control-planes-are-proposed-in-place-of-one-monolithic-instance]], [[decisions/run-one-crossplane-control-plane-or-several-domain-scoped-ones]]). It fits the blast-radius principle, but it also multiplies the clusters you must operate.

The tooling comparison across stacks is in [[comparisons/load-and-fairness-controls-across-controller-runtime-flux-argo-cd-and-kro]], and [[comparisons/concurrency-and-cache-memory-controls-across-flux-argo-cd-and-crossplane]] covers the Flux and Argo CD concurrency and cache controls. For retry behavior, tools differ in whether failures are capped and in how the failure delay is separated from the normal cadence ([[comparisons/retry-and-backoff-controls-across-tools]]). kro caps retries, Argo CD does not re-sync a failed sync of the same commit and parameters unless self-heal is on (its separate automated-sync retry is a configurable exponential backoff), and Flux separates the retry interval from the reconcile interval. The retry storm described in section 10 shows what happens when clients retry a failing call with no cap.

## 9. Industry scale stories: Morgan Stanley, Upbound, Ant Group, Gardener, Cozystack

Real organizations show how these principles bend under load, but the evidence quality varies, and it is worth reading each story with its caveat.

Morgan Stanley described its Flux adoption at a 2025 Flux conference, and the Flux team wrote it up, with a reported footprint of "over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources." Before Flux it used push pipelines, which suffered drift and made cluster rebuilds fragile. Multi-tenancy rested on service account impersonation, and a self-service onboarding platform checked entitlements, registered the service in a configuration management database, primed the namespace with a `GitRepository` and a `Kustomization`, and scaffolded the team's repository. At scale the team raised reconciliation intervals, tuned worker concurrency and resource limits, and moved the source of truth from a self-hosted Git provider to S3 buckets, which the write-up gives as an availability and compliance choice ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]). Sharding, OCI artifacts and Flagger were roadmap items, so there are no production sharding numbers. It is a self-reported conference account, not an independent audit, but it is the clearest evidence that vertical tuning plus per-tenant impersonation holds at several hundred clusters.

Upbound's test, covered in section 7, is the story of what happens when a platform meets API machinery that was never tested for thousands of CRDs, and it points toward packaging as Crossplane's answer. Crossplane's adopters file is self-reported and mostly unquantified. A few entries give object counts, from thousands of managed resources up to a provider orchestrating on the order of a couple hundred thousand; treat these as pointers and not as documented case studies ([[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]]). Built Technologies says that at times it has exceeded ten thousand AWS resources managed by Crossplane, in a developer environment and not production, undated and self-reported ([[examples/built-technologies-reports-peaks-above-10000-aws-resources-managed-by-crossplane-in-a-developer-environment]]). On the ACK side, Adobe is listed for global Kubernetes cluster provisioning and for stateful service infrastructure using multiple ACK controllers, with no object count and no date ([[examples/adobe-lists-ack-for-global-kubernetes-cluster-provisioning-and-stateful-service-infrastructure]]). Argo CD's users file lists self-reported adopters, and Flux's adopters data file names organizations such as Xenit, SortList, Tietoevry, Nexxiot, SoulCycle and Luma Health, again with no write-ups attached ([[examples/the-flux-adopters-data-file-lists-xenit-sortlist-tietoevry-nexxiot-soulcycle-and-luma-health-among-others-with-no-write-ups]]). Searches for further adopter accounts returned nothing, so the absence of further named adopters is weak evidence and not proof. For GitOps outages, one named-organization postmortem exists, Skyscanner's, described in section 10, alongside reporter-level GitHub issues from individuals whose employers are not named. No organization says it runs sharded Flux, since Morgan Stanley lists sharding as future work, and there is no adopters file for kro, Cluster API or Config Connector, so named adopters and measured scale for those remain absent ([[comparisons/flux-scaling-options-intervals-concurrency-sharding-and-source-choice]], [[findings/kro-scale-evidence-is-two-open-issues-and-a-closed-unmerged-pull-request-with-no-benchmark-and-no-named-production-adopter]], [[entities/config-connector]]).

Ant Group's more-than-10,000-node cluster is a reminder that custom resources share storage and watch paths with built-in objects, so general apiserver and etcd tuning applies to them too, though the write-up is not about CRDs. Gardener, an operator of many clusters for many tenants, supplies the conservative numbers from section 7 and the warning that conversion webhooks are especially risky because an outage blocks garbage collection ([[findings/a-down-conversion-webhook-can-stall-garbage-collection]]). Retiring an old version of a custom resource has its own operational step. Kubernetes provides a storage-version migration API and a migrator controller, but migration is not triggered automatically. A team that wants to stop serving an old CRD version creates a cluster-scoped `StorageVersionMigration` object whose immutable `spec.resource` names the resource, and watches its `Running` and `Succeeded` conditions, since progress appears only as text in the `Running` message. After a CRD migration, the stored-versions list in the CRD status should name only the preferred version ([[findings/storage-version-migration-is-not-triggered-automatically-so-a-retired-crd-version-needs-a-user-created-object]], [[concepts/crd-versioning-and-storage-migration]]).

Cozystack is a different kind of story. It packages Talos Linux, Kubernetes, KubeVirt, LINSTOR with DRBD, and Kube-OVN into a PaaS framework for turning commodity servers into a cloud offering Kubernetes clusters, databases and VMs through an API ([[examples/cozystack-turns-commodity-servers-into-a-cloud-with-kubernetes-databases-and-vms]]). No adopter names or measurements for it appear in the sources, so it illustrates the architecture's direction and not its scale. Its repository does contain a Flux shard operator, described in section 8, which is the only automated Flux sharding in the sources, with design targets and no measured result. A related direction is the Kubernetes-as-a-kernel distribution model that Aenix, the company behind Cozystack, describes: no Kubernetes community body or conference talk adopting that model appears in the sources, and the one direct source is Aenix's own post, so it is a vendor position and not a community direction ([[findings/no-sig-charter-or-kep-adopts-a-kubernetes-distribution-model-and-the-only-direct-source-is-aenix-s-own-post]]).

Several other stories show platform composition in practice. JFrog delivers self-service cloud environments through Jenkins, Git, Argo CD and Crossplane ([[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]). VSHN's AppCat sells self-service databases, queues and object storage through composition functions ([[examples/vshn-appcat-sells-self-service-databases-queues-and-object-storage-through-composition-functions]]). A Google Cloud style stack that delivers Config Connector resources from Git with Argo CD or Flux is described in [[concepts/tooling-landscape]]. The control-plane-as-a-platform idea at its far end is kcp hosting node-less API workspaces for multi-tenant SaaS ([[examples/multi-tenant-api-hosting-with-kcp]]) and Cluster API managing fleets of clusters ([[examples/cluster-fleet-lifecycle-with-cluster-api]]). A KubeCon speaker from Accenture says a kcp workspace, an isolated Kubernetes API endpoint with no nodes or pods in which the user is cluster admin, appears in about a second, where a managed cluster takes half an hour to an hour. These are spoken estimates from a short talk, with no measurement, tenant count or adopter named, and the transcript has recognition errors, so they illustrate the pitch and do not fill the scale gap ([[examples/a-kcp-speaker-says-a-workspace-takes-about-a-second-to-create-where-a-managed-cluster-takes-half-an-hour-to-an-hour]], [[comparisons/tenancy-models-namespaces-vcluster-kcp]]). Named production adopters, scale numbers and postmortems remain thin for most of these tools.

## 10. Pitfalls catalog and operational guardrails

The postmortems examined here agree that serious incidents are cascades in which a small change meets a loop, a default or a shared dependency. [[concepts/pitfalls-and-case-studies]] names three mechanisms that recur: finalizers, field ownership and deletion propagation. We have already met all three. This section adds the rest and pairs each pitfall with the guardrail the tools provide.

Retry storms come first. Zalando's 2019 outage began with a timed-out downstream call. Clients retried, which spiked DNS queries; a default resolver search-path setting multiplied each external lookup into many queries; the cluster's DNS pods ran out of memory and were killed together; and monitoring that depended on DNS and ran inside the cluster went blind. Zalando raised the memory limits, adopted a node-local DNS design, and moved alerting outside the cluster ([[examples/zalando-s-2019-coredns-outage-turned-a-retry-storm-into-a-total-dns-failure]], [[findings/monitoring-that-runs-inside-the-cluster-and-depends-on-cluster-dns-goes-blind-in-the-outage-it-should-report]]). The postmortem states the principle: it should not be possible for a single application to take down DNS infrastructure. Within the tools, retries are capped differently, as described in section 8.

Webhook outages are a recurring class in the k8s.af index, a community-maintained catalog of Kubernetes failure stories ([[findings/admission-webhook-outages-are-a-recurring-failure-class]]), and one of those postmortems is Jetstack's 2019 post. A regional GKE cluster shared by many teams was upgrading its control plane through a Terraform pipeline. During the upgrade the API server tried to update a ConfigMap in `kube-system` as part of a post-start hook, and that write was subject to an Open Policy Agent (OPA, a policy engine that Kubernetes admission webhooks can call) validating webhook whose backend was not responding, so it timed out. The post says the operation must complete for a master to pass its health check, so the master crash-looped and the upgrade halted. Intermittent API downtime then stopped kubelets from reporting node health, and GKE node auto-repair began recreating nodes in an endless loop, which caused loss of service for every tenant. Jetstack fixed it by deleting the validating webhook, which worked only because the API server answered intermittently. Its follow-ups were scoping the webhook to the namespaces where policy applies, enabling it only for Ingress and Service resources, adding a liveness probe to OPA, and alerting on API server response times for create and update calls, and it deliberately kept node auto-repair on. The post never mentions `failurePolicy`, so its fixes were not a change of failure policy. The account is self-reported ([[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]]). The second webhook entry in that index is an Airbnb KubeCon talk that exists only as video, so its contents are not described here. The OpenAI incident in section 7 shows the same lesson from the control-plane side, since the tools needed to repair the cluster sat on the path that failed.

Reddit's 2023 Pi-Day postmortem shows the webhook as a symptom and not the cause. During a Kubernetes minor-version upgrade the API server began timing out on writes because of calls to its OPA webhook, and removing the webhook configurations ended the timeouts without recovering the cluster, since the real fault was that the upgrade removed a node label that the cluster's route reflectors selected on ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]]). The official guidance is to scope matches narrowly, exclude system namespaces, keep timeouts short, run multiple replicas and use `Fail` only for security-critical checks ([[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]]). Part of the webhook risk can be avoided by not using a webhook. ValidatingAdmissionPolicy and MutatingAdmissionPolicy evaluate CEL expressions inside the API server, so there is no backend whose outage can block writes. The validating policy is positioned as a replacement for most validating webhooks, but not for mutation or full webhook parity. These policies cannot reach external data and are subject to the CEL cost limits described below, so a check that needs to call another system still needs a webhook ([[comparisons/admission-mechanisms-webhooks-vap-map-and-crd-rules]], [[findings/cel-policies-cannot-reach-external-data-and-have-bounded-cost]]).

Policy engines that run as admission webhooks, Kyverno among them, make a failure-policy choice on your behalf, and an engine that fails closed can block writes to the cluster when its own backend is down, so its availability has to be designed accordingly. Not every tool has a webhook to fail. kro and ACK ship no admission webhook and rely on CRD schema and CEL validation instead (for Argo CD no admission webhook turned up, though only a search of the repository tree was run, which is weaker evidence than reading the manifests) ([[findings/kro-and-ack-ship-no-admission-webhook-and-rely-on-crd-schema-and-cel-validation-and-no-argo-cd-webhook-was-found-in-a-tree-search-only]]). CEL validation has its own limits that bite platform authors: the API server estimates each rule's cost statically and rejects a CRD whose rules are too expensive, a list or string with no declared maximum size makes that estimate too high until the maximum item count and length are declared, and at runtime there are per-call and per-request cost budgets ([[findings/an-unbounded-list-or-string-makes-the-cel-cost-estimate-reject-a-crd-rule-until-maxitems-and-maxlength-are-set]]).

Three named postmortems show what happens when a faithful automation applies the wrong intent, and they are worth reading as a set. Skyscanner's 2021 outage is the clearest GitOps case. An engineer merged a change to the templating system that was meant to change no behavior, but it left out the `{{ }}` template markers, so templating stopped applying and the rarely changed root file that rolled out regional configuration reached every region at once. Argo CD then reconciled the clusters against a configuration that listed no valid namespaces and began deleting every service, across every availability zone and region. Because clusters pull their state, recovery meant restoring correct configuration and letting each cluster reconcile itself, and the site was serving from a single region within hours, with the rest returning over the following two days. The post does not say which Argo CD sync options were set, whether pruning was automated, or why no guard stopped the deletion, so no specific misconfiguration is claimed here ([[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]]). Reddit's 2023 outage lasted hours. A Kubernetes minor-version upgrade removed a control-plane node label that its hand-edited Calico route reflector selectors relied on, routing collapsed, rolling back required restoring an etcd backup because Kubernetes has no supported downgrade, and the restore procedure was old and untested ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]], [[findings/kubernetes-has-no-supported-downgrade-so-a-failed-control-plane-upgrade-forces-a-backup-restore-and-an-untested-restore-procedure-is-the-risk]]). Spotify's talk covers a 2018 console deletion of a production GKE cluster, restored within hours, and a second incident about a month later in which a Terraform review build wrote to a state file shared with production builds, an out-of-order merge deleted the Asia cluster, and widening a service account's permissions while recreating it led Terraform to delete a second cluster. Two of three production clusters were gone for hours, yet the team reports no end-user impact, which it credits to partial migration, service discovery that registered pod IPs, hourly backups and rehearsed restores ([[examples/spotify-deleted-one-production-gke-cluster-by-console-click-and-two-more-through-terraform-with-no-end-user-impact]]). The end-user claim means no reports reached the team. All three accounts are self-reported by the organizations involved. Skyscanner and Spotify share the lesson that destructive operations need guards separate from the tool doing the reconciling.

Ordering and CRDs are the next group. Applying a custom resource before its CRD is established fails with "no matches for kind", reported in Helm, Argo CD and Flux alike ([[findings/custom-resources-applied-before-their-crd-exists]]). Flux's remedy is separate Kustomizations linked by `dependsOn` with health checks; Argo CD users reach for sync waves, where the order is phase, then wave, then kind, then name, and each wave must be Healthy before the next ([[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]]); some Argo CD details are not documented, and the two tools are compared in [[comparisons/missing-crd-handling-flux-versus-argo-cd]]. Helm has no native support for upgrading or deleting CRDs, which Flux works around with its Helm CRD install and upgrade policies ([[findings/helm-does-not-upgrade-or-delete-crds]]). Circular `dependsOn` chains never reconcile ([[findings/circular-dependson-chains-between-flux-resources-never-reconcile]]). The deeper principle, from [[concepts/eventual-consistency-and-convergence]], is that Kubernetes does not promise instant convergence; Flux's `dependsOn` keeps the retry-until-ready behavior but in a controlled order, so transient errors do not arrive as a burst ([[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]).

Automation hazards come from the fact that GitOps tools do exactly what they are told, quickly and repeatedly, so any ambiguity in what they are told becomes an outage. The first hazard is image automation, where a controller watches a container registry and writes new image tags back into Git. If the rule that selects tags is looser than the team realizes, an unintended version is committed and then rolled out by the same loop that normally protects you, and nothing in the pipeline treats it as unusual ([[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]]). Flux's reference repository limits image automation to staging for that reason, so production changes still pass through a human decision. The official image update guide offers three controls and stops there. Production uses semver-selected release tags built by CI while staging uses tags chosen by numerical or alphabetical policies. Pushing to a separate branch from the checkout branch lets CI open a pull request, so that, in the guide's words, you can manually approve the image updates before they are applied. A bad update is undone by narrowing the semver range. No adopter write-up on staging-only or reviewed promotion was found, so the promotion policy that teams actually use remains an open question ([[findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range]], [[decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation]]).

A related hazard is the mutable remote reference. A Kustomization or Helm release can pull a base or a chart from somewhere other than your repository, and if that reference points at a branch or a floating tag, the same commit of your own repository can render different manifests tomorrow than it did today. The deployment looks unchanged in Git while the cluster changes, which defeats the audit trail that made GitOps attractive. Pinning remote Helm and Kustomize references to tags or commit SHAs restores the property that a commit determines what runs ([[findings/mutable-remote-references-change-what-a-commit-renders]]). Rollback has a similar trap in Argo CD. Its rollback action works by deploying an older revision directly, but while automated sync is on, the next sync immediately re-applies whatever Git says, so the rollback is undone or refused. The tool blocks it to protect the principle that Git is the source of truth, which means the working path is a Git revert that the automation then follows ([[findings/rollback-is-blocked-while-automated-sync-is-on]]).

The remaining hazards concern how objects are written. Argo CD's `Replace` and force sync options delete and recreate a resource instead of patching it, which is sometimes needed for immutable fields but briefly removes the object, so a Deployment or a stateful resource can take an outage ([[findings/argo-cd-replace-and-force-sync-options-can-recreate-resources-and-cause-outages]]). Flux's `force` option does the same when an update touches an immutable field, and it should be a temporary measure and not a standing setting. Migrating from client-side apply to server-side apply can leave behind fields that nobody now wants. The old `kubectl apply` ownership is recorded under a manager that no longer runs, and a stale co-owner cannot be forced off a field by the new manager through an ordinary apply, so removing the field from Git does not remove it from the live object ([[examples/flux-migration-from-client-side-apply-strands-removed-fields]]). Finally, an Argo CD app-of-apps, which is an Application whose job is to create other Applications, can show perpetually out of sync when an image updater edits the same fields that the parent also declares. That is the same two-writers field fight from section 2, and the fix is likewise an explicit ownership decision ([[examples/argo-cd-app-of-apps-out-of-sync-from-image-updater]]).

Silent failures are the most dangerous class because nothing alerts. Flux failures can be silent when resources are suspended, when polling lag hides a missing webhook, or when a command-line operation reconciles a Kustomization without also refreshing its source; the evidence there is documentation plus one practitioner blog. The `Synced=False` with `Ready=True` case from section 4 belongs here too.

A short set of operational guardrails follows from all of this, stated as sentences and not a checklist. Keep prune off until the source of truth is trusted, and annotate objects that must never be pruned. Choose an orphan or retain policy for critical external resources before deleting anything, and apply the policy before the delete. Set explicit propagation options when a GitOps tool hosts composites. Alert from outside the cluster on saturation signals. Read both the GitOps tool's sync status and the custom resource's conditions. Keep test environments identical to production and read release notes before upgrades. Review cluster-scoped configuration with the rigor of code. The pitfall evidence rests mostly on 2017 to 2021 incidents, documentation and blogs, although the postmortems above add 2023 (Reddit) and 2024 (OpenAI) accounts, and no named-organization postmortem specific to kro, Config Connector, ACK or Cluster API turned up. What exists for those tools is first-party known-issue lists and release notes, plus individual reporter issues, almost all without maintainer root-cause confirmation. Known-issue lists are useful evidence of upgrade-ordering risk, such as a webhook that is not ready while an upgrade rolls out, but they name no organization and give no incident timeline, so they are not postmortems ([[findings/no-named-organization-postmortem-was-found-for-kro-config-connector-ack-or-cluster-api]]).
## 11. The tooling landscape: delivery, provisioning, platform and portal layers

The landscape is easiest to learn as three layers that solve different problems and are routinely combined, and confusing them is the most common source of bad comparisons ([[concepts/tooling-landscape]], [[comparisons/delivery-versus-provisioning-versus-platform-layers-in-the-kubernetes-tooling-landscape]]). Asking whether Argo CD or Crossplane is better is like asking whether a package manager beats a database, because one moves manifests and the other reconciles cloud resources.

The delivery layer gets desired state from Git, OCI or Helm into a cluster and keeps it there. Flux and Argo CD are the two CNCF projects. Argo CD ships as an integrated application with an API server, a repository server that renders manifests and an application controller that diffs live against target state, polling the source on a periodic cadence with jitter so that many applications do not hit the Git host at once. How often a delivery tool re-checks its source is a trade-off between how quickly changes and drift are noticed and how many calls are spent on the source and the cluster, and each tool picks its own cadence, so a latency quoted for any tool is meaningful only when it names the component. Flux ships as a toolkit of small controllers that each own their own CRDs, so its parts can be used by other automation ([[comparisons/flux-versus-argo-cd-architecture]]). The vendor caution applies here: comparisons often come from vendors such as Akuity (which sells Argo CD), Port and Syntasso (which sells Kratix), with no independent benchmarks ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]], [[comparisons/flux-versus-argo-cd-isolation-ordering-and-interface-according-to-a-vendor-blog]]). The pull-versus-push comparison in [[comparisons/push-versus-pull-delivery]] explains why pull limits credential exposure: a push pipeline holds credentials for every environment, while a pull agent needs only read access to the source but becomes a powerful identity itself. Flux's D2 reference architecture goes further, with clusters pulling signed OCI artifacts so they never connect to a Git host ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]); this is a vendor write-up, and whether Git or OCI should be the source of truth is unresolved (see [[concepts/gitops-pull-based-delivery]]). The signature evidence is lopsided. Flux's OCIRepository can verify Cosign or Notation signatures, supports keyless verification by matching OIDC identities, and can pin a Sigstore trust root, while the Argo CD pages examined document OCI sources (an image with a single layer) and Git commit signature checks with GnuPG keys, and describe no OCI signature verification. That describes the documentation and is not proof that the feature is absent from the code, and no independent evidence that signed OCI beats Git, nor any registry rate-limit documentation, was found for either tool ([[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]], [[decisions/git-versus-oci-as-the-canonical-source]]).

The provisioning layer turns custom resources into calls against an infrastructure API. Config Connector, ACK and Azure Service Operator are single-vendor controllers that expose roughly one CRD per cloud resource ([[comparisons/crossplane-versus-cloud-vendor-add-ons-ack-config-connector-and-aso]]). Crossplane is multi-cloud and adds Compositions so a platform team can publish its own API without writing a controller. The Terraform wrappers, tofu-controller and terraform-operator, run plan and apply in pods ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]]). Both Terraform wrappers are community-maintained: tofu-controller sits under a community organization with several active maintainers, and the Terraform Operator is low-activity and effectively single-maintainer, though no deprecation notice exists in the sources examined, so it is best described as low-activity and not as abandoned ([[comparisons/tofu-controller-versus-terraform-operator-as-terraform-in-cluster-controllers]]). The practical difference between the two execution models is review. Crossplane runs always-on controllers that detect and correct drift on their own, and it applies a change as soon as the desired state changes, without a separate plan step to review. Terraform and OpenTofu run on demand, and a team sees drift only when the next plan runs, but they offer a reviewable plan before apply. That plan is a check and not a guarantee. A 2025 practitioner post reports an anonymous case in which a plan showed an update while the apply recreated the resource and lost data, which it blames on an official provider and for which it names no provider, resource or date. See [[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]] and [[findings/one-practitioner-reports-a-terraform-plan-that-showed-an-update-while-the-apply-recreated-the-resource-and-lost-data]]. Be cautious with the comparisons you will find: no neutral comparison of Crossplane with Terraform or with the single-cloud operators turned up, only vendor, consultancy and lab write-ups, and a search for a neutral Config Connector versus Crossplane study found two vendor positions and nothing else ([[findings/no-neutral-comparison-of-crossplane-with-terraform-or-single-cloud-operators-was-found-and-the-independent-material-is-dated]], [[findings/no-neutral-comparison-of-config-connector-and-crossplane-was-found-so-the-evidence-is-two-vendor-positions]]). Cluster API applies the pattern to Kubernetes clusters themselves. Its abstraction for platform teams is ClusterClass, a reusable class of template references plus a small `topology` on a Cluster that a controller expands into many machine and infrastructure objects, which mirrors the split between a Crossplane definition and its instances. The per-resource controllers do not build a dependency graph, so ordering falls to the delivery tool or a composition layer, and the controller holds the cloud identity, so whoever can create the custom resource inherits its rights.

The platform and portal layer defines what application teams see. Backstage and Port are catalogs and portals with self-service actions, Kratix is an orchestration framework behind a portal where a Promise, Kratix's unit of packaging, bundles a platform API together with the workflows that fulfill requests for it and the rules for scheduling the result onto a fleet of clusters, and Cozystack ships its own substrate ([[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]). A Kratix vendor claims that a portal supplies visibility and not provisioning. Backstage's own documentation fits that reading. Its Kubernetes feature is described as designed for service owners and not cluster admins, and its backend reads standard objects plus the custom resources an operator configures by group, version and plural, matching them to catalog entities through the label `backstage.io/kubernetes-id` or a label selector annotation. A custom resource whose CRD is not installed is silently skipped and only logged at debug level, so a typo shows up as an empty panel and not an error. The Backstage Kubernetes plugin documentation describes no operator pattern, so nothing there supports the idea that templates and the catalog form a platform layer above operators ([[findings/the-backstage-kubernetes-plugin-matches-entities-to-cluster-objects-by-label-and-no-backstage-document-describes-an-operator-pattern]]). The Software Templates documentation settles that question in part: the Scaffolder loads code skeletons, fills in variables and publishes the result to a location such as GitHub or GitLab, and each run is treated as a unique task, which makes it an imperative run-once tool and not a reconcile loop. The nearest operator-style integration is a community plugin, the TeraSky Kubernetes Ingestor, which acts as a sync loop in the Backstage backend from cluster to catalog and ingests Crossplane claims and kro instances, while the upstream community-plugins repository has workspaces for Argo CD and Flux but none for Crossplane or kro. The sources do not cover the built-in Scaffolder actions page, so a built-in action that creates custom resources is not ruled out ([[findings/the-backstage-scaffolder-is-a-one-shot-task-runner-and-the-nearest-operator-style-integration-is-a-third-party-plugin]]).

Kratix's mechanics are documented as follows. It schedules in two stages by label matching. In the first stage a Promise's dependencies go to every Destination by default, or only to Destinations whose labels satisfy the Promise's `destinationSelectors`, and a Destination with `strictMatchLabels: true` accepts only Promises whose selectors match its labels. In the second stage a resource request triggers the `resource.configure` workflow and its output goes to a matching Destination, and when several match, Kratix by default picks one at random. A workflow can add selectors of its own, and on conflict the order of precedence is the Promise selectors, then the Promise workflow file, then the Resource workflow file. Kratix does not apply what it produces. It writes documents to a state store (a Git repository through a GitStateStore, or an S3-compatible bucket through a BucketStateStore) under a `dependencies` directory and a `resources` directory, and the agent on the Destination, typically Flux or Argo CD, reads them from there. The Destination's filepath mode is immutable once created, so changing the layout means creating a new Destination. This account rests on the documentation and the Go types and not on the scheduler or work-creator source, so how matching is implemented is not described ([[findings/kratix-schedules-in-two-stages-by-label-matching-and-picks-a-destination-at-random-when-several-match]], [[findings/a-kratix-destination-writes-dependencies-and-resources-directories-and-its-filepath-mode-is-immutable]]).

Radius and Score are two developer-facing workload abstractions that both live in the CNCF community. They have different maintainer bases: all of Radius's listed maintainers work for one company, while Score's maintainers span several employers. Neither is established as a production default ([[findings/radius-and-score-are-both-cncf-sandbox-projects-per-the-landscape-file-and-both-passed-sandbox-votes]]). One third-party blog review claims that Radius depends on Bicep, and no primary source states that claim.

Abstraction tools overlap with each other. kro merges schema and implementation into one ResourceGraphDefinition, generates the CRD, infers dependency order from CEL references, and deletes in reverse; the Crossplane project's `function-kro` runs kro-style graphs inside a pipeline. It is the same idea on a different engine, and the engine changes failure semantics. When a resource cannot be rendered, the function model returns a fatal result and Crossplane applies nothing, so the composite reports a failed sync, whereas kro keeps the resource and retries. The project's claim of full parity therefore reads best as the same engine with different failure behavior. Independent production reports were not found, and how a standalone kro controller would feed a Crossplane composite is undocumented ([[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]], [[findings/function-kro-approximates-kro-built-in-conditions-from-one-run-and-writes-only-declared-status-paths-to-the-desired-xr]]). Helm and Kustomize are render-time abstractions that produce manifests once and leave correction to a GitOps tool, while composites are live control loops ([[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]], [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]]). Both tools reach the same outcome in the StorageApp comparison, with kro inferring order and Crossplane's Go-template route needing hand-written ordering and deletion guards ([[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]). A worked end-to-end example is [[examples/platform-team-self-service-apis-with-crossplane-and-kro]]. The abstractions themselves are young ([[findings/immature-abstractions-in-the-control-plane-ecosystem]]).

For plain controllers, the contrast is the cost of writing one per platform API, which composition and resource graphs exist to avoid ([[comparisons/hand-written-operator-versus-crossplane-composition-versus-kro]]). Tenancy at the cluster level is compared in [[comparisons/tenancy-models-namespaces-vcluster-kcp]]. If you want a yardstick for how mature a hand-written operator is, the Operator SDK defines five capability levels from Level 1, Basic Install, to Level 5, Auto Pilot, framed around an operator managing a workload. It says operators that do not manage a workload, or that delegate to off-cluster orchestration services, remain at Level 1, and its page never mentions Crossplane, kro or composition, so it offers no rating for those tools ([[findings/operator-sdk-capability-levels-keep-delegating-operators-at-level-1-and-say-nothing-about-composition-tools]]).

## 12. Remaining gaps and what is not yet known

This part would be dishonest if it ended with a tidy conclusion, because many questions remain open, and several touch the heart of the thesis.

The first is the trace itself. No source traces the handoff from the source controller to the kustomize controller in detail, finalizer registration, and status updates, and the available sources cover Flux at the component and API level. What you read in section 2 is a faithful composition of documented behaviors, but it is a composition and not an observation. A worked example on a live cluster would close it.

The second is scale evidence. Named production adopters and object counts are mostly self-reported. There is no sourced data on how cloud provider API limits constrain Crossplane, Config Connector or ACK, no scaling data for kro, ACK, Cluster API or Config Connector controllers, no published numeric capacity limits for Crossplane, no official memory or processor figures for Upjet, and no neutral Argo CD versus Flux benchmark. Flux documents when to shard only in rough terms, Morgan Stanley lists sharding as future work, and Cozystack's sharding is a design intent. No authoritative CRD scale limits are published in the sources examined.

The third is controller mechanics. What an informer resync does is shown by the client-go source: it is a local replay of the informer's cached objects to the handlers and never contacts the API server, as Part 3 explains. What remains unresolved is whether it should be switched on, because sources disagree on whether a periodic resync is a useful defense against reconciler bugs or a common misunderstanding ([[decisions/keep-informer-resync-disabled-or-set-a-periodic-resync]]). A bare requeue result is a rate-limited requeue with per-object exponential backoff, and the failure history is kept, so a reconciler that returns it on every pass waits longer each time. Only a requeue-after result clears the history and schedules the next run after exactly that duration. Some descriptions say a bare requeue happens immediately, but the controller-runtime source shows otherwise ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]]). Reconcile cadence differs per tool and per layer within a tool: some controllers re-check the outside world every few minutes, some only every few hours, and some re-read a cache and never contact the cloud at all, as in Cluster API's sync period. The cadence is a trade-off between how quickly drift is noticed and how many calls are spent on the external API, and each tool and provider picks its own ([[findings/the-cluster-api-sync-period-flag-is-a-cache-resync-and-not-a-poll-of-the-cloud-infrastructure]]). Server-side apply behavior is documented for kro (force for templates, no force for patches), ACK (merge patches, no field manager), Cluster API (forced ownership by the topology controller) and Helm (a release follows the apply method it was created with), as section 2 describes. Config Connector's apply behavior was not found, and the helm-controller's handling of Helm's server-side apply was not settled.

The fourth is the evidence for failure modes. The pitfalls evidence is mostly older, documentation-based and vendor-influenced. No named-company postmortem of a runaway reconcile loop, of an accidental prune that a company reported as its own, or of a kro, Config Connector, ACK or Cluster API pitfall turned up. What exists are public reports from individual operators describing runaway reconcile loops with three recurring mechanisms. The first is a status write on every pass, so the write itself triggers the next reconcile and the loop outlives its original trigger ([[findings/a-status-patch-or-update-on-every-pass-keeps-a-controller-in-a-self-sustaining-reconcile-loop]]). The second is volatile text, such as request identifiers and timestamps copied from an error, in a condition message, which defeats the equality check that would otherwise skip the update ([[findings/volatile-text-in-a-condition-message-defeats-the-equality-check-and-causes-a-reconcile-storm]]). The third is applying one object twice in a single pass with different content while owning that kind with no predicate to ignore the controller's own writes, so each pass changes the resource version and queues another pass ([[findings/applying-one-object-twice-in-a-reconcile-with-owns-and-no-predicate-loops-on-its-own-resource-version]]). The same unconditional status update has also kept reconcile-ordering tests from converging. The control-plane-as-platform class has a primary report from OpenAI (2024), plus Jetstack's 2019 webhook outage, and the section 10 postmortems from Skyscanner, Reddit and Spotify are primary accounts; but no organization postmortem from 2024 to 2026 on Argo CD, Flux, Crossplane, Karpenter or cert-manager surfaced, and the content of the Airbnb webhook talk is not described here. Several questions about the other tools have answers in the sources: Config Connector's per-kind controller routing and cadence, the Radius and Score maintainer bases, the Kratix Destination mechanics, the tofu-controller and Terraform Operator maintenance state and the KRM function specification. These remain open: the Argo CD and Flux comparison that rests on each project's own documentation, any named kro, Config Connector or Cluster API adopter, how Flux treats Cluster API objects and ACK terminal conditions, whether the Terraform-based Config Connector controller honors the abandon setting, and how a controller should detect and recover from a stale informer cache, which is an open design question. Several searches returned nothing, so each absence is weak evidence and not proof.

The fifth is design direction. Where `observedGeneration` should live, the right polarity for new condition types, the best default conflict policy for teams running GitOps beside in-cluster controllers, and whether to place external names in an annotation or a spec field are all framed as open decisions. Crossplane versus kro is still a live debate, and the abstractions themselves are young.

None of these gaps contradicts the thesis, and each sharpens it. The mechanics compose, the principles follow from the composition, and the places where the evidence is thin are the places where a careful platform team should measure its own system instead of trusting a number from a blog.
