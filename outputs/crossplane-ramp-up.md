# Crossplane Ramp-Up: Compositions, Providers and Design Principles for Control-Plane Platforms

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) but have not yet worked with controllers, API machinery or platform abstractions, and platform engineers weighing Crossplane for an internal developer platform.<br>
> **Purpose:** Teach Crossplane from first principles, explain how it behaves in practice, and draw out the design principles that make it a useful model for building platforms.<br>
> **Status:** Active. Where the named sources are thin or disagree with each other, the text says so.<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-27<br>
> **Draws on:** [[entities/crossplane]], [[concepts/managed-resource]], [[concepts/composite-resource]], [[concepts/composition]], [[concepts/provider]], [[sources/research-crossplane-deep-dive]], and the findings, comparisons and decisions listed under Further reading.<br>

## 1. What Crossplane is and who uses it

Crossplane is an extension to Kubernetes that turns a cluster into a control plane for things that are not in the cluster. The Kubernetes API server stores objects and notifies controllers when they change, and a controller is a program that keeps nudging the real world toward whatever those objects say. Kubernetes uses this idea for pods and deployments. Crossplane applies the same idea to a cloud database, a storage bucket, an IAM role or a whole managed Kubernetes cluster. You write a Kubernetes object that describes the cloud thing you want, and a Crossplane controller creates, updates and eventually deletes the real thing to match. The wiki describes this as an instance of the [[concepts/universal-control-plane]], the observation that the API server, etcd and the controller pattern make a general-purpose engine for managing any resource that has an API. [[entities/crossplane]]

The project describes itself as a framework for building control planes, and its documentation says a Composition "composes individual resources together into a larger, reusable, solution." That sentence hints at the two halves of the tool. The lower half is a catalog of providers that expose individual cloud resources as Kubernetes objects. The upper half lets a platform team define its own higher-level APIs, such as a `PostgreSQLInstance` or a `Microservice`, and describe how each one expands into many lower-level objects. Application teams then ask for the simple thing and never see the cloud-specific details. [[concepts/composition]]

Crossplane was created by Upbound and is now a graduated project of the Cloud Native Computing Foundation (CNCF), which signals a mature, vendor-neutral governance model. Its adopters come from a wide range of industries. [[entities/crossplane]]

The adopters list in the project repository is a set of self-reported one-liners and not verified case studies, but it conveys the range. Organizations describe internal developer platforms managing thousands of cloud resources, fleets of control planes built on the Kubernetes resource model, and fully GitOps-driven self-service, and the largest claims run to the hundreds of thousands of managed resources. Some entries describe peaks in non-production environments, and none says how many control planes held those objects or what reconciliation cost, so they show how far people say they have pushed the tool and not how it behaved when they did. Treat them as pointers for research and not as evidence of behavior. [[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]]

## 2. Mental model: external resources as Kubernetes objects and the two reconcile loops

To understand Crossplane you need three ideas from the controller world. The first is declarative intent: the object's `spec` says what you want, and you do not script the steps. The second is the split between `spec` and `status`. Spec is written by users, status is written by the controller, and the controller reports what it observed there. This is the [[concepts/spec-status-split]], and it is why you can read an object and learn both what was asked for and what is true. The third is the reconciliation loop, in which a controller repeatedly observes the real state, compares it to the desired state, and acts to close the gap. The loop is level-triggered, meaning it looks at the current state each time rather than reacting to a one-time event, so a missed event or a restart does not leave the system permanently wrong. See [[concepts/reconciliation-loop]] and [[concepts/operator-pattern]].

The Crossplane documentation uses precise vocabulary here. The Kubernetes object is called a managed resource, and the real thing in the cloud is called an external resource. A provider controller reads the external resource, compares it with the managed resource, and creates, updates or deletes the external resource to close the gap. The shortest framing the wiki offers is a Deployment-style controller loop whose pods are cloud resources. [[concepts/managed-resource]]

Because Crossplane has two layers of abstraction, a typical platform has two reconcile loops stacked on top of each other, and a third if you add a GitOps agent. GitOps means keeping Git as the source of truth for what should run, with an agent inside the cluster that pulls from Git and applies it. Argo CD and Flux are the two best-known agents of this kind: each is a pull-based controller that watches a Git repository and syncs its contents into the Kubernetes API server. At the bottom, provider controllers reconcile each managed resource against the cloud API. Above them, Crossplane's composition machinery reconciles each composite resource against the managed resources it owns. If you deliver the whole thing through Argo CD or Flux, a delivery loop reconciles Git into the Kubernetes API. The wiki's finding on this point is that each loop can report green or drift independently. A green sync in the GitOps agent says only that the custom resource matches Git. It does not say the database is healthy, and a lower loop may correct drift without the upper loop ever noticing a difference. The practical advice is to read both layers, the agent's sync status for "Git versus API" and the custom resource's conditions for "API versus reality." [[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]

A last piece of background is the idea of a finalizer. A finalizer is a string on an object's metadata that tells Kubernetes "do not remove this object yet." When you delete such an object, Kubernetes sets a deletion timestamp and waits for the responsible controller to finish its cleanup and remove the finalizer. Crossplane puts a finalizer on every managed resource so that the cloud resource is really gone before the Kubernetes object disappears. The managed resources documentation adds two warnings about it: deletion hangs if the provider that owns the finalizer is gone, and removing the finalizer by hand orphans the real resource, because the cleanup it exists to protect is skipped. Every tool that manages external resources uses its own finalizer name, which matters when you are staring at a stuck object and trying to work out which controller owes you a cleanup, because the owner of the finalizer is the place to look first. One further rule from the Kubernetes side explains why a late finalizer is useless: once an object has a deletion timestamp, the API server refuses to add new finalizers, so a controller must add its finalizer on the first reconcile, before it creates anything external. This is how deletion of a Kubernetes object becomes deletion of a cloud resource, and it comes back repeatedly in the pitfalls below. [[concepts/finalizers]], [[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]] and [[findings/a-finalizer-added-after-the-delete-request-is-too-late-and-new-ones-are-refused]]

## 3. Providers, ProviderConfigs, credentials and provider families

A provider is a packaged controller plus a set of CustomResourceDefinitions (CRDs, the mechanism that lets you add new object kinds to Kubernetes) that teaches the cluster how to speak to one external API, for example AWS, Azure, GCP or GitHub. The CRDs describe the external resource types as Kubernetes kinds, and the controller watches those kinds and calls the external API. See [[concepts/provider]] and [[concepts/custom-resource-definition]].

In Crossplane a provider is an installable package, an OCI image of the sort you would pull from a container registry. You install one by creating a `Provider` object. Each upgrade creates a `ProviderRevision`, so the cluster can keep an older revision for rollback. A `ProviderConfig` (or a `ClusterProviderConfig` for cluster-wide use) tells the provider which credentials to use, and a `DeploymentRuntimeConfig` customizes the provider's pod. Every provider reuses a shared managed reconciler from crossplane-runtime with the phases Connect, Observe, Create, Update and Delete, and the provider author implements an external client behind that interface. [[concepts/provider]] and [[examples/provider-authors-implement-an-external-client-behind-the-shared-managed-reconciler]]

Writing hundreds of resource types by hand is impractical, so large catalogs are generated. Upjet, a Crossplane code-generation framework, reads Terraform provider schemas at build time and generates Go types and controllers, and the generated controllers reuse Terraform's resource logic at runtime while users see only a Kubernetes API. The Upjet sources say Upjet underpins the official AWS, Azure and GCP providers. Whether the generated runtime calls Terraform as a subprocess or in-process depends on the resource, because Upjet offers three execution modes chosen per resource. In the fork-based mode the controller shells out to the Terraform command-line tool and talks to a Terraform provider process. In the other two modes the Terraform provider is called as an ordinary Go library inside the provider pod, one mode for providers written against the older Terraform plugin SDK and one for those written against the newer plugin framework. Because the mode is a per-resource setting, one provider package can mix forked and in-process paths, and the sources do not say which official providers use which mode, so any claim about a specific official provider's process count or cost has no support. In the fork-based mode each managed resource gets its own Terraform working directory holding state on the provider pod's filesystem, so that state belongs in any capacity and restart review, and a single shared native provider process serves many resources that use the same provider configuration, which means one slow operation can delay the others. Generated providers also carry a real memory and processing cost, because each one embeds the machinery of the system it was generated from, and the project discourages large monolithic provider packages for that reason. Upjet publishes no general per-resource cost baseline, so measure the providers you actually install. The wider consequence is that generated providers share the behavior and quirks of their generator, which matters when you hit an oddity in one provider and find it in all of them. [[entities/upjet]], [[findings/upjet-supports-three-terraform-execution-modes-selected-per-resource-configuration]] and [[findings/generated-provider-catalogs-inherit-the-behavior-and-bugs-of-their-generator]]

Credentials deserve their own attention. A provider controller acts with its own cloud identity, not with yours. The Config Connector documentation states this plainly for Google's equivalent, and the same logic holds for every provider: permission to create the Kubernetes object is effectively permission to change cloud resources with the controller's identity. Kubernetes RBAC on the custom resource therefore becomes your cloud authorization boundary. Crossplane's mitigation is one `ProviderConfig` per account so that different objects use different credentials. See [[findings/anyone-who-can-create-a-provider-managed-object-gets-the-controllers-cloud-permissions]] and the open trade-off in [[decisions/scope-provider-credentials-per-namespace-or-cluster-wide]], where a single identity is simple to operate but needs the union of everyone's permissions, and scoped identities limit damage at the cost of more configuration.

The original provider-aws was a single monolith that registered a CRD for every AWS service, hundreds of them, and that volume could leave the API server slow or unresponsive. The project answered with provider families: scoped providers per service, grouped into a family that shares a common configuration provider so credentials are defined once. An operator installs only the member providers for the services in use, which cuts the number of CRDs the API server must hold by a large factor, at the cost of running more provider pods. The fewer-CRDs-for-more-pods trade is real, and the family idea needed no new user-facing concept, which is why the project chose it over CRD filtering or lazy loading. [[examples/crossplane-provider-families-let-operators-install-only-the-cloud-services-they-use]], [[findings/splitting-a-provider-into-a-family-trades-fewer-crds-for-more-pods-and-memory]] and [[decisions/split-a-large-provider-into-families-or-filter-or-lazy-load-its-crds]]

## 4. Managed resources: forProvider, external names, management policies and deletion policies

A managed resource has a consistent skeleton regardless of which cloud thing it represents. The field `spec.forProvider` holds the desired state and is the source of truth: the Crossplane documentation says Crossplane "considers the `forProvider` field of a managed resource the 'source of truth' for external resources," so a change made in the cloud console is reverted on the next poll. The field `status.atProvider` holds what the provider last observed. The field `spec.initProvider` holds values applied only at creation. The annotation `crossplane.io/external-name` records which cloud resource this object maps to; a VPC called `my-test-vpc` in Kubernetes may have the external name `vpc-01353cfe93950a8ff`, because the cloud assigns its own identifier. Without a stable link like that, the controller could not find the resource again. Where the external name comes from depends on the kind. For resources whose cloud name the user chooses, such as a storage bucket, an IAM role or a Kubernetes cluster, providers give the external resource the same name as the Kubernetes object by default. For kinds where the cloud assigns the identifier, such as a VPC, subnet, security group or encryption key, the external name stays empty until the create call returns and the provider records the identifier the cloud chose. It matters because a name you can predict before the first create lets a retried create find the same resource, whereas a provider-assigned identifier leaves a window in which the resource exists in the cloud but not yet in the annotation, which is the window the create-pending safeguard in sections 8 and 11 exists to cover. [[concepts/managed-resource]], [[sources/research-managed-resource]] and [[findings/crossplane-external-names-default-to-the-object-name-only-for-name-based-kinds-and-upjet-providers-switch-the-default-off-for-provider-assigned-ids]]

The role of `initProvider` is easiest to see with an example. A Crossplane EKS node group declares an initial `desiredSize`, and a cluster autoscaler later changes the size. If the size lived in `forProvider`, Crossplane would reset it on every reconcile and the two controllers would fight forever. Putting the initial size in `initProvider` means Crossplane applies it once and then leaves it alone. The general lesson is that a drift-correcting reconciler is correct only for fields the declaration owns, and a field that another writer manages must be left out of the enforced set. [[examples/crossplane-initprovider-lets-an-autoscaler-own-node-group-size]] A related issue is late initialization: cloud providers fill in default values you never set, and a naive comparison would treat them as drift. Crossplane keeps those fields optional and offers a `LateInitialize` policy so the provider's value is copied into spec deliberately. [[findings/late-initialized-fields-create-false-drift]]

The `spec.managementPolicies` list says which verbs the controller may use: Observe, Create, Update, Delete and LateInitialize, with `*` meaning all. The consequence is that several distinct operational needs become one field. `["Observe"]` gives read-only import or a permanent reference. A list without Delete means "manage this, but leave the cloud resource if the object is deleted." An empty list pauses reconciliation. The `crossplane.io/paused: "true"` annotation also pauses. Management policies replace an older, coarser deletion setting, the `deletionPolicy` field, which offered only Delete and Orphan. On legacy cluster-scoped managed resources both settings still exist and are combined, so the cloud resource is deleted only when both allow it. Namespaced managed resources use management policies alone, so older advice that talks about the deletion setting or an old observe-only mode has to be translated into policy lists.  [[findings/older-observeonly-and-deletionpolicy-advice-needs-translation-to-managementpolicies]] and [[decisions/choose-management-policies-for-an-imported-resource]]

Two guardrails complement these. First, Usages: a `Usage` object marks one resource as in use by another, and deletion of the used resource is blocked until its users are gone. A Usage names the resource being used, the resource using it and, optionally, a reason, and its stated purpose is ordering deletion so a resource is not deleted before its dependents. The `reason` field lets an operator protect a resource from accidental deletion without naming a user. Usages add ordering and protection at the delete verb, while management policies decide whether the delete verb is allowed at all, so the sources present them as complementary. An admission webhook is an HTTPS service that the API server calls before it accepts a create, update or delete, and which can approve or reject the request; a ValidatingWebhookConfiguration is the object that tells the API server which requests to send to which service. The enforcement mechanism is worth knowing. Core installs one validating webhook that fires on deletes of objects marked as in use, and it fails closed, so while the webhook is unreachable such deletes are refused, which is the safe direction for a protection feature. The cost is that a webhook outage can block legitimate deletes, and some managed Kubernetes services restrict how such webhooks may be configured. Crossplane's other admission checks, for definitions and Compositions, do not depend on a webhook pod being up, because the same validation runs inside the API server as CEL rules in the CRD schema. [[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]] and [[findings/crossplane-core-ships-one-fail-closed-usage-webhook-and-replaced-its-xrd-and-composition-webhooks-with-cel]] Second, Crossplane deliberately does not delete and recreate a resource to change an immutable field, which is what Terraform does. A change to such a field in `forProvider` may simply not take effect, which is safer for stateful resources and surprising to people who expect Terraform semantics. [[findings/crossplane-does-not-delete-and-recreate-to-change-immutable-fields]]

## 5. Composite resources, XRDs and claims, and the v2 namespaced model

A managed resource is one-to-one with a cloud thing, which is too low-level to hand to application developers. A composite resource, or XR, represents a set of resources as one Kubernetes object. The Crossplane documentation's own wording is that "a composite resource, or XR, represents a set of Kubernetes resources as a single Kubernetes object." A controller expands the small object into the lower-level ones, keeps them reconciled, wires values from one into another, reports aggregate readiness and tears everything down. This is the ordinary controller pattern applied one level up, because the world being reconciled is a set of other API objects. [[concepts/composite-resource]]

Crossplane splits the idea across two objects. A CompositeResourceDefinition, or XRD, declares the schema of your new API: its `group`, `kind`, `plural`, a list of versions and a `scope`. Crossplane generates a CRD from it, so the platform team authors a brand new Kubernetes kind. The XRD's name must be `<plural>.<group>`, the group and names cannot change after creation, breaking schema changes should ship as a new XRD or through a conversion webhook, and the dossier notes schema edits may need a Crossplane pod restart. The Composition, covered in the next section, says how an instance of that API becomes composed resources. The pairing lets one API have several implementations. [[entities/crossplane]] and [[findings/platform-api-schemas-are-contracts-and-breaking-changes-are-blocked-or-need-conversion]]

Here is a deliberately small, illustrative XRD for a namespaced API. The scope, group, kind and version fields come from Crossplane's documentation, but the field names in this sketch are illustrative, so check them against the live documentation before copying it.

```yaml
apiVersion: apiextensions.crossplane.io/v2
kind: CompositeResourceDefinition
metadata:
  name: storageapps.platform.example.org
spec:
  scope: Namespaced
  group: platform.example.org
  names:
    kind: StorageApp
    plural: storageapps
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: string
                  enum: [small, medium, large]
```

The snippet declares a new kind called `StorageApp` in the group `platform.example.org`, scoped to a namespace, with one field, `size`, restricted to three values. The point of the enum is the platform idea: developers choose a size class, and the platform team decides what "medium" means in cloud terms. JFrog's engineering blog describes exactly this guardrail, with predefined small, medium and large classes preventing over-provisioning, and tags recording an owner and an expiry so forgotten environments can be cleaned up. [[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]

In Crossplane v1, composites were cluster-scoped, so tenants could not own them from their namespaces. The fix was the claim: if the XRD set `claimNames`, an application team could create a claim in its own namespace, and Crossplane created a cluster-scoped XR and linked the two with `spec.resourceRef` on the claim and `spec.claimRef` on the XR. Connection secrets were written to the claim's namespace. Crossplane v2 made XRs namespaced by default, removed the claim and XR split for new-style definitions, let a Composition include any Kubernetes resource and not only Crossplane-managed ones, and removed native patch and transform, the old controller configuration object and the external secret stores. There is no automated migration for v1 cluster-scoped composites, so moving a platform from v1 to v2 means redesigning its APIs and not simply upgrading them. Claims are available only on a v1-style definition, which keeps the older cluster-scoped model alive for teams that still need it. [[comparisons/crossplane-v1-claims-versus-v2-namespaced-composite-resources]], [[examples/a-v1-crossplane-claim-fronts-a-cluster-scoped-composite-resource]] and [[findings/crossplane-v2-removed-features-and-offers-no-automated-migration-for-v1-composites]]

The v2 scope matters for tenancy. A namespaced XR can compose only resources in its own namespace, so the tenant boundary moves onto the XR itself, and `Cluster` exists as the alternative scope. A v2-style definition offers only those two scopes, defaulting to Namespaced, and it rejects claim names. Claims, which let a tenant request a cluster-scoped composite from its own namespace, belong only to the older definition API, so keeping claims means keeping an older-style definition, and legacy cluster-scoped XRs cannot compose namespaced resources. This is why the Crossplane 2.0 announcement can sketch a `Microservice` kind whose one namespaced object creates an RDS instance, security groups, a Deployment, a Service, an Ingress and monitoring dashboards. The dossier stresses this is an illustration from the Crossplane authors and not a named customer. [[examples/a-microservice-xr-creates-a-database-and-its-workload-from-one-namespaced-object]]

An XR carries per-object controls in its spec and annotations. It selects a Composition with `compositionRef` or `compositionSelector`, follows revisions automatically (a CompositionRevision is an immutable snapshot of a Composition, created each time the Composition changes) or pins one with `compositionUpdatePolicy: Manual` and a revision reference, can be paused with `crossplane.io/paused`, can be given its own poll cadence, and can be forced to reconcile with the `crossplane.io/reconcile-requested-at` annotation. [[concepts/composite-resource]]

## 6. Compositions and composition function pipelines, with CEL, Go templating and Python or KCL examples

A Composition holds the platform team's opinions. In current Crossplane, "a Composition is a pipeline of composition functions." A function is installed as a package and runs as a pod. On each reconcile Crossplane calls the steps in order over gRPC (a binary remote-procedure-call protocol, so the function is called like a local method even though it runs in another pod), giving each a request that holds the observed state of the XR and its owned resources, the desired state accumulated by earlier steps, per-function input and shared context. Each function returns the new desired state. The documentation summarizes it as "a function's main job is to update the desired state and return it to Crossplane," and crucially the function never talks to the API server itself; Crossplane applies the result with server-side apply and re-observes on the next loop. Server-side apply is a Kubernetes feature in which the API server itself tracks which manager owns which fields of an object, so several writers can share one object without silently overwriting each other, and a field that a manager stops asking for can be removed. Each manager is identified by a field owner name. Crossplane applies the composite's reference list and status with forced ownership under one fixed owner, and applies composed resources under per-composite owners. "Forced" matters here because an ordinary server-side apply that touches a field owned by someone else is rejected as a conflict, whereas a forced apply takes the field over, so any other controller that writes the same fields will lose them to Crossplane at the next pass. That is the mechanism behind the external-writer caution discussed in section 11. [[examples/a-composition-function-pipeline-turns-observed-state-into-desired-state]], [[concepts/server-side-apply-and-field-ownership]] and [[entities/crossplane]]

The history explains the design. The first authoring model was patch and transform, a static list of base resources plus patches, deliberately not Turing complete. It had no conditionals, no loops and no dynamic lookups, and the design document wanted to "avoid organically growing a new configuration Domain Specific Language." Composition functions were introduced to supply the missing expressiveness, and native patch and transform is now gone in favour of a function that provides the same behavior, so existing compositions can be converted into pipeline form. Imagine Learning's patch-and-transform files for an AWS RDS cluster ran past a thousand lines, with near-duplicate files for different instance counts. They moved to one function that loops over `instanceCount`. VSHN hit the same limits and uses functions to drive Helm charts and share backup logic across service types. [[concepts/composition]], [[examples/imagine-learning-replaces-thousand-line-patch-and-transform-files-with-a-looping-composition-function]] and [[findings/patch-and-transform-cannot-branch-loop-or-patch-between-composed-resources]]

Here is a sketch of a pipeline Composition using Go templating. The wiki names `function-go-templating` and `function-auto-ready` but does not reproduce their schemas, so treat the field names as illustrative and confirm them against each function's own documentation.

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: storageapp-aws
spec:
  compositeTypeRef:
    apiVersion: platform.example.org/v1alpha1
    kind: StorageApp
  mode: Pipeline
  pipeline:
    - step: render-resources
      functionRef:
        name: function-go-templating
      input:
        apiVersion: gotemplating.fn.crossplane.io/v1beta1
        kind: GoTemplate
        source: Inline
        inline:
          template: |
            apiVersion: s3.aws.upbound.io/v1beta1
            kind: Bucket
            metadata:
              annotations:
                gotemplating.fn.crossplane.io/composition-resource-name: bucket
            spec:
              forProvider:
                region: eu-west-1
    - step: mark-ready
      functionRef:
        name: function-auto-ready
```

The Composition says "when a `StorageApp` appears, run these two steps." The first renders a bucket as a composed resource, and the second marks the composite ready once every composed resource reports ready. `compositeTypeRef` is how the Composition is matched to the XRD's group and kind. Because the template is real code you can add conditionals and loops, but the wiki records a cost: a Go-template Composition needs hand-written creation order and guards against deleting resources when a dependency is briefly unavailable. [[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]

Python, KCL and CUE are among the supported authoring languages, alongside Go templating and custom functions written in Go or Python. The Crossplane documentation lists them as supported but gives no code here, and the sources do not describe KCL's features, so a team considering it should read the function's own documentation. A Python function has the same contract as every other function: read the request, add resources to the desired state, return the response. The sketch below is untested pseudocode written to show that contract. It is not taken from the SDK documentation. The real Python SDK may have you subclass a function runner and implement a `RunFunction(self, req, rsp)` method, but the exact class and method names are not given in the sources used here, and the real SDK's names may differ from the ones invented here. Treat every identifier in the sketch as a placeholder, and check the SDK's current API before relying on any of it.

```python
# Untested pseudocode: shows the contract, not the SDK's exact API.
class FunctionRunner:
    def RunFunction(self, req, rsp):
        # Start from the desired resources earlier steps already produced,
        # so nothing they added is dropped from the response.
        for name, res in req.desired.resources.items():
            rsp.desired.resources[name] = res

        size = req.observed.composite.resource["spec"]["size"]
        replicas = {"small": 1, "medium": 2, "large": 3}[size]
        for i in range(replicas):
            rsp.desired.resources[f"node-{i}"].resource.update({
                "apiVersion": "ec2.aws.upbound.io/v1beta1",
                "kind": "Instance",
                "spec": {"forProvider": {"region": "eu-west-1"}},
            })
        return rsp
```

The idea is that a loop does what a thousand duplicated lines used to do. The first loop copies the incoming desired resources into the response, which is the rule described next made visible in code; an SDK may pre-seed the response from the request for you, but no source used here says so, so the sketch does not assume it. Note one rule that applies to every language: the function must carry forward everything already in the desired state, because a resource omitted from the returned desired state is deleted. VSHN discovered this early on ("if an object is not explicitly specified in a request payload, it will be deleted"). The mitigation is to start from the incoming desired state, change only your own parts, and test with `crossplane render` so an accidental omission shows up before it reaches a cluster. [[findings/a-composition-function-that-omits-a-resource-from-its-desired-state-deletes-it]]

CEL, the Common Expression Language, enters through kro. CEL is a small expression language that terminates by design, has no side effects and is type-checked at apply time. kro's ResourceGraphDefinition (RGD), the single object in which a kro user declares an API's schema, resource templates and expressions, uses it inside `${...}` expressions to reference fields across resources, from which kro infers a dependency graph. A function named `function-kro` embeds kro's graph builder and CEL evaluator so that a kro-style `resources` block can run as a Crossplane pipeline step. In the example below, one step calls `function-kro` with a VPC, a Subnet and a SecurityGroup wired together by CEL so that the subnet reads the VPC's identifier, followed by `function-auto-ready`. The schema is invented for illustration:

```yaml
pipeline:
  - step: graph
    functionRef:
      name: function-kro
    input:
      # kro-style resources block; subnet reads the VPC id via CEL
      resources:
        - id: vpc
          template: { kind: VPC }
        - id: subnet
          template:
            kind: Subnet
            spec:
              forProvider:
                vpcId: ${vpc.status.atProvider.id}
  - step: ready
    functionRef:
      name: function-auto-ready
```

The key line is the `${vpc.status.atProvider.id}` expression: the subnet is not created until the VPC's identifier exists, which is the inferred ordering. A topological order is simply an order in which every resource comes after the resources it depends on. The function shares kro's engine but not every behavior of a standalone kro installation, and the differences are worth knowing before you rely on it. When a resource cannot be rendered, the function returns a fatal result and Crossplane applies nothing, so the composite goes unsynced, whereas kro keeps the resource and retries, which means a hard error in one resource fails the whole run. Because Crossplane owns the composite's condition types, the function approximates conditions: it reports readiness from the single run in progress and does not provide kro's four built-in conditions, so an author who relies on those will not find them, and it writes only the status paths the graph declares so that server-side apply ownership stays narrow. A dependent resource is held back until the resources it references are ready, as in kro. The honest reading is that this is the same engine running inside Crossplane's model for applying resources and reporting status, with a short list of documented differences. No documented pattern chains a standalone kro controller into a Crossplane composite, so combining them that way is neither supported nor ruled out. [[entities/function-kro]], [[examples/function-kro-runs-a-kro-resource-graph-as-a-crossplane-pipeline-step]], [[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]] and [[findings/function-kro-approximates-kro-built-in-conditions-from-one-run-and-writes-only-declared-status-paths-to-the-desired-xr]]

Where does the expressiveness limit sit? The wiki's synthesis (the wiki authors' own, since no source compared the two head to head) is that Crossplane fixes the contract and frees the code: any language that serves gRPC works, with no termination guarantee, validation at reconcile time and one pod per function. kro limits the language and frees the runtime: CEL always terminates, definitions are checked when created, and no external function servers exist, but logic beyond CEL cannot be expressed. [[comparisons/where-the-expressiveness-bound-sits-in-crossplane-functions-and-kro-cel]]

Functions run as long-lived pods, and Crossplane reaches them through a headless Service. An ordinary Kubernetes Service gives a set of pods one virtual IP that load-balances across them, whereas a headless Service has no virtual IP and instead lets a client resolve the individual pod addresses directly. That suits gRPC, which keeps long-lived connections and does its own balancing. The connection between Crossplane and a function pod is secured with mTLS, mutual TLS, in which both sides present certificates and verify each other. The effect is that traffic between them is encrypted and each side can confirm the other's identity, which matters because a function receives the observed state of the composite and everything it owns. [[concepts/composition]]

Composition functions are long-running gRPC servers: the package manager deploys each one as an ordinary Kubernetes Deployment, reached through the headless Service and secured with the mTLS described above. That differs from the better-known KRM function standard. A KRM function, as defined by the specification in the Kustomize repository and used by kpt and Kustomize, must be a container that reads a `ResourceList` document from standard input, writes one to standard output and signals failure with a non-zero exit code, so every invocation is a short-lived container. Crossplane's contract is the `RunFunction` call in a protobuf service whose request carries observed state, desired state, required resources and schemas, and whose server stays running. A KRM function therefore cannot be dropped into a Crossplane pipeline without a wrapper, and the reverse is also true. The difference has a practical upside for Crossplane: because its functions run in the cluster, it avoids the container-runtime requirement that makes KRM functions awkward on laptops and in CI. kpt and Kustomize can run functions without containers only through opt-in executable extensions, and their own documentation discourages those because nothing sandboxes them. [[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]], [[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]] and [[findings/kpt-and-kustomize-run-functions-without-containers-only-through-opt-in-exec-extensions-that-both-docs-discourage]]

Composites are re-checked on a regular cadence, and every pass over a composite makes one gRPC call for each step in its pipeline. Call volume therefore grows with the number of composites and the length of their pipelines and not with the amount of change happening, so a large fleet of idle composites still keeps its functions busy. That is why function replicas, the polling cadence and response caching come up as tuning levers in section 12. Composition functions also do not run when a composite is deleted, so Crossplane deletes the composed resources itself. [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]

The local testing loop has three rungs, and it pays to use the cheap ones first. `crossplane render` runs a Composition and its functions on your laptop against a sample composite and prints the desired resources, with no cluster involved, so it catches a mistake such as an omitted resource in seconds. Ordinary unit tests of the function's own code come next. The slow rung is an end-to-end loop that uses Kuttl (a declarative test runner that applies manifests and asserts on the resulting cluster state), a kind cluster (Kubernetes running inside local Docker containers) and Skaffold (a tool that rebuilds and redeploys your function image on each change), and each run takes minutes. That delay matters because it is the cost of every iteration spent debugging against a live cluster, and it is the reason to push as much checking as possible into the fast rungs. [[concepts/composition]]

Finally, functions are packages, and a package can be pinned by its OCI digest, the content hash of the image in a container registry, rather than by a mutable tag. It is tempting to assume that each Composition revision references specific function digests, so that composites pinned to older revisions keep running the old function, but that holds only in an optional mode. By default a pipeline step refers to a function by name, which calls whichever Function revision is currently active, and the Composition revisions documentation says that upgrading a Function affects every CompositionRevision, "including revisions you've pinned XRs to with the `Manual` update policy." Pinning a composite to a Composition revision therefore freezes the pipeline definition but not the function code behind a by-name reference. The optional mode lets a step name a function package by digest, so that several revisions of the same Function can be active at once, and only that mode supports a staged rollout in which a few composites move to a new function build while the rest keep the old one. Without it, a function upgrade reaches every composite at once, whichever update policy they use, so test function changes with `crossplane render` and in a non-production control plane first. Function response caching is a further optional control that reduces repeated calls. [[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]], [[decisions/choose-automatic-or-manual-composition-update-policy]] and [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]

## 7. Status, Synced and Ready conditions, and observing long-running operations

Conditions are the standard way a Kubernetes controller reports state: a list of entries in `status.conditions`, each with a type such as `Ready`, a status of True, False or Unknown, a reason and a message. They let humans and other tools read status without knowing the controller's internals. See [[concepts/conditions]].

Crossplane managed resources use two. `Ready` says whether the external resource is operational, with reasons `Available`, `Creating`, `Unavailable` and `Deleting`. `Synced` says whether the provider's last reconcile succeeded, with reasons `ReconcileSuccess`, `ReconcileError` and `ReconcilePaused`. Read together they diagnose different problems: `Synced=False` points at credentials, configuration or provider trouble, while `Ready=False` with `Synced=True` points at the cloud side, which is the normal state while a database is provisioning for several minutes. A composite resource becomes `Ready` only when its function pipeline reports that every composed resource is ready, and the pipeline contract is precise about what "reports" means. Each desired resource in a function's response carries a ready flag with three values, `READY_UNSPECIFIED`, `READY_TRUE` and `READY_FALSE`, and Crossplane counts a composed resource as ready only when the value is `READY_TRUE`, so an unspecified value is treated the same as false. The composite reconciler then collects every composed resource that is not ready, and sets the XR's `Ready` condition to `Available` when that list is empty and to `Creating` with the message "Unready resources: ..." otherwise, with `Synced` set to `ReconcileError` and an "Unsynced resources: ..." message if any composed resource is not synced. The practical consequence is that a pipeline which composes healthy resources but has no function setting `READY_TRUE` leaves the XR in `Creating` forever, and the cause lies in the pipeline and not the provider. That is why the pipeline in section 6 ends with `function-auto-ready`: it leaves alone any resource that already carries an explicit flag, and for the rest it runs optional CEL queries and built-in health checks for standard Kubernetes resources before falling back to checking that the observed object has a `Ready` condition equal to True. When an XR is stuck, read the "Unready resources" message first, since it names the culprits. This also marks a difference from kro, where the controller computes an instance's `Ready` from the graph and the author does not write a function for it. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]] Crossplane's two-condition split is the clearest attempt in the wiki's survey to separate "the platform is broken" from "the cloud resource is still coming up." [[comparisons/health-and-readiness-models-across-tools]] and [[examples/crossplane-database-claim-reports-synced-and-ready]]

Two failure patterns are worth memorizing. In the first, `Synced=False` with `Ready=True` means the thing exists but Crossplane can no longer manage it, typically because credentials expired or permissions were removed. Applications keep running, so nothing user-visible breaks, but drift is not corrected and spec changes are not applied. Teams that alert only on `Ready=False` will not notice, so alert on persistent `Synced=False` as well. [[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]] In the second, `Synced` stays `True` while a long asynchronous operation runs. A long update to a managed Kafka cluster, for example, can take an hour during which the resource reports itself as up to date, because the framework treats an up-to-date observation as a successful reconcile even though the provider is still working. Providers built with Upjet add an `AsyncOperation` condition that reads `False` with reason `Ongoing`, but it sits outside the usual alert surface, so a team that alerts only on `Ready` and `Synced` will not see it. Composite status can also flap briefly, because a controller that reads from a cache which trails the API server can publish conditions that are a moment out of date. Practically, a single brief `Ready` or `Synced` flip on an XR may be noise, so alert on a condition that persists, and check a live resource to see how a given provider reports in-flight work before writing an alert on it. [[findings/upjet-and-crossplane-runtime-source-still-reports-reconcilesuccess-while-an-async-operation-runs]] and [[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]]

Other stacks draw this line differently. ACK splits terminal from recoverable errors into separate conditions alongside a synced condition. Config Connector packs everything into a single `Ready` condition whose reason says whether an update is in flight, up to date or failed, so a consumer has to read the reason because `Ready=False` covers both an update in progress and a failed one. Flux uses `Ready`, `Reconciling` and `Stalled`, where `Stalled` means no progress without a change. Those names also show the polarity choice that every condition vocabulary makes. `Ready=True` is a positive condition, where true means healthy, whereas `Reconciling` and `Stalled` are abnormal-true conditions, where true means something needs attention. Neither is simply correct: the Kubernetes API conventions leave the choice to the author, a positive `Ready=False` cannot say whether the object is progressing or doomed, and an abnormal-true scheme makes an absent condition look healthy, which hides a dead controller unless you compare `observedGeneration`, a status field recording the spec generation the controller last acted on, so that a value lagging behind the object's current generation shows the controller has not yet seen the latest change. kstatus is the Kubernetes status-interpretation library, used by tools such as kpt and Flux, that decides from an object's conditions whether it is current, in progress or stalled. Its maintainers named the failure state `Stalled` and not `Failed` because, from outside, a slow object and a doomed one are hard to tell apart. kro lets the graph author define conditions with CEL and `readyWhen`, and Cluster API adds `Available` and operation conditions such as `ScalingUp` and `Remediating`. This variety is why Argo CD needs a custom Lua health check per custom resource kind (a small script that tells Argo CD whether an object of an unfamiliar kind is healthy) and Flux needs CEL health checks (the same idea, written as expressions in the Common Expression Language), and why Crossplane's own guide for Argo CD asks for Lua checks over its resource kinds. Argo CD ships built-in scripts for whole provider groups, covering Config Connector, ACK, Crossplane, kro and several Cluster API kinds, so a team should read the shipped script before writing its own. Each script translates one tool's condition vocabulary into Argo CD's health states: a terminal ACK error maps to Degraded, an unready condition to Progressing, a stale `observedGeneration` also reads as Progressing, and kinds that never carry conditions are treated as Healthy so that they do not sit at Progressing forever. Flux takes the opposite approach and has no per-provider logic: a Kustomization's health checks accept kstatus-compatible custom resources, and CEL expressions cover the kinds that are not. Kstatus can read a resource that has no initial `Ready` condition as already ready, which makes a delivery tool report success before the provider has even started. The remedy is for the controller to set `observedGeneration` on its `Ready` condition and for the consumer to require that it equals the object's current generation, which a CEL health expression can express. In Crossplane's case the condition semantics are fixed by the framework, whereas in kro the author defines them. [[decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types]], [[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]], [[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]], [[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]] and [[comparisons/provider-fixed-versus-author-defined-condition-semantics-crossplane-versus-kro]]

## 8. Adoption, import and observe-only workflows

Most organizations start with infrastructure that already exists, so adopting a cloud resource without recreating it is a core need. The Crossplane recipe, from the official import guide, uses a GCP Cloud SQL `DatabaseInstance` as its example. You write a managed resource with `managementPolicies: ["Observe"]` and the `crossplane.io/external-name` annotation set to the existing instance's provider-side name. You pick a Kubernetes object name and, if the same name exists in more than one region, add a disambiguating `forProvider` field such as the region. [[examples/crossplane-import-of-an-existing-gcp-database-observes-first-then-takes-control]]

```yaml
apiVersion: sql.gcp.upbound.io/v1beta1
kind: DatabaseInstance
metadata:
  name: orders-db
  annotations:
    crossplane.io/external-name: orders-db-prod
spec:
  managementPolicies: ["Observe"]
  forProvider:
    region: europe-west1
```

This manifest asks Crossplane to look at an existing instance and change nothing. The guide says Crossplane "imports observe only resources but never changes or deletes the resources." Once applied, the provider fills `status.atProvider` with what it saw. You then copy the values you want to own into `spec.forProvider` by hand and change the policies to `["*"]` so the controller may create, update and delete. The two-phase design is the lesson: a safe read-only phase proves the object maps to the right resource before a second phase grants write authority. The hazards are the manual copy, ambiguous names across regions, relaxed validation during Observe, and disabled late initialization. The recipe depends on the provider supporting management policies. [[findings/observe-based-import-has-manual-copy-steps-ambiguous-names-and-relaxed-validation]]

Observe is also useful permanently. A composition can read a database owned by another team without ever managing it, for example to hand its connection details to a workload. [[examples/an-observe-only-managed-resource-lets-a-composition-read-a-database-owned-by-another-team]]

Other tools answer the same two questions, "how do I adopt this?" and "how do I keep it when the object goes away?", in different styles. Config Connector acquires a resource implicitly whenever a manifest's name matches, which is convenient for migration but can take over something never meant to be managed, and keeping a resource on delete requires an abandon-style annotation set before deletion. Its protection against two objects managing one cloud resource is opt-in, so out of the box nothing stops two objects in different namespaces from acquiring the same Google Cloud resource, which the documentation calls possible but not recommended. When the protection is enabled, Config Connector stores a time-limited lease on the cloud resource itself, renewed while the holder keeps reconciling, and a losing object reports a management conflict. The documentation lists limits: because the lease lives on the resource as labels, it does not work for resources that cannot carry labels, and two objects in the same namespace that name one resource explicitly create conflicts Config Connector cannot manage. ACK splits observation and adoption: a read-only annotation never creates, updates or deletes and errors if the AWS resource is missing, while an adoption feature, with a strict mode and an adopt-or-create mode, gives full management, and a retain deletion policy keeps the cloud resource. Adopt-or-create can take over a look-alike resource and overwrite it to match the spec. Worse, ACK records ownership only in the custom resource's status and not on the AWS resource, so two custom resources can adopt the same resource, rewrite it on every resync and both report healthy, and deleting either one deletes the shared resource out from under the other. Without the adoption annotation ACK stops with a terminal "already exists" error, so the annotation turns off the only guard there is. A natural defence is to record the owner in the cloud resource's tags at creation time so that a controller can refuse resources it did not create. Acquisition has a second hazard even for the intended resource: the declared spec is only a subset of the live settings, so acquiring an existing resource can silently strip a setting that the custom resource definition has no field for, such as an encryption-enforcement setting on a storage bucket, and a diff of exported manifests would not show the change. The sources show no accidental-adoption report for Crossplane, whose Observe-first flow gives a review step that the implicit paths lack, and the cases above show mechanisms and not how often they bite. The SAP BTP provider takes a third path: an explicitly set external name signals that the resource should already exist, and the default initializer is removed so a missing name never becomes accidental adoption. Its design record says plainly that this is not an import mechanism. [[comparisons/observe-only-and-keep-controls-across-crossplane-config-connector-and-ack]], [[findings/adopt-or-create-can-take-over-a-look-alike-resource]], [[findings/ack-adopt-or-create-removes-the-only-guard-against-two-custom-resources-owning-one-aws-resource]], [[findings/acquiring-an-existing-cloud-resource-can-strip-settings-the-custom-resource-definition-does-not-model]], [[decisions/adopt-or-create-or-require-explicit-import]] and [[entities/crossplane-provider-btp]]

The reconcile loop also interacts with idempotency, meaning that doing something twice has the same effect as doing it once. Cloud create calls are not always idempotent. The AWS Builders' Library describes the EC2 `ClientToken`: the caller supplies a unique token, the service stores it atomically with the mutation, and a retry returns an equivalent response instead of launching a second instance. Where an API offers such a token a controller can retry freely. Where it does not, Crossplane writes a durable marker, `crossplane.io/external-create-pending`, before the create call and `external-create-succeeded` or `external-create-failed` afterward. That guards against the case where the create succeeds but the status write fails, which could otherwise leak a billed resource. [[examples/ec2-client-token-makes-a-retried-runinstances-call-safe]] and [[findings/a-create-that-succeeds-while-the-status-write-fails-can-leak-an-external-resource]]

## 9. Use cases: self-service databases and clusters, service catalogs, multi-cloud, and who runs it at scale

The dominant use is self-service. A platform team publishes a small API and application teams consume it without cloud expertise or tickets. The JFrog pattern chains four tools, each doing one job: developers ask through a Jenkins-based interface, the interface writes custom resources into Git, Argo CD syncs them into a cluster, and Crossplane reconciles them into real cloud resources. Argo CD sees the platform-level custom resources and not every cloud resource beneath them. The post is an organizational success story and lists no pitfalls, no scale figures and no detail of the Compositions behind the size classes, so it is a pattern illustration and not proof of operational cost. [[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]

Service catalogs are the second pattern. VSHN, a managed Kubernetes provider that has run Crossplane in production for years, uses composition functions in its Application Catalog (AppCat), a marketplace where customers self-provision databases, message queues and object storage. The wiki calls it the clearest example of composition as a product catalogue, because one provider sells many service types across clouds from one declarative layer, though it is a single self-reported case with no scale numbers. Its operational lessons were that a resource missing from a function's response is deleted, and that mixing patch and transform with functions for the same objects "increases complexity dramatically." [[examples/vshn-appcat-sells-self-service-databases-queues-and-object-storage-through-composition-functions]]

Governance is a third. The Crossplane blog on designing compositions argues that a platform should expose well-understood features behind its own versioned API rather than pass every provider feature through, because native provider features can break proprietary environments or reduce compliance. Inside a Composition the platform team can apply automated tagging to every composed resource, and "multi-tenant access segregation for resource claims is an excellent pattern for proper cloud governance and security." The blog is vendor-authored and predates v2, so claims, external secret stores and native patch and transform appear in it though v2 removed or changed them. [[examples/a-platform-api-hides-provider-features-to-enforce-tagging-and-tenant-segregation]]

Whole-cluster provisioning is a fourth. RTL Nederland reports on the adopters list that it provisions whole Kubernetes clusters on Azure and AWS with Crossplane, which overlaps with Cluster API's home territory. The entry is self-reported and unverified. It shows that the provisioning layer has no hard border: a general framework can create clusters as managed resources, while Cluster API offers cluster-specific kinds such as `MachineHealthCheck`. [[examples/rtl-nederland-provisions-whole-kubernetes-clusters-with-crossplane-which-overlaps-with-cluster-api]]

Multi-cloud follows from the provider model. Upbound tested a multi-cloud control plane of about two thousand managed resources and found that installing thousands of CRDs strained both clients and the API server: client discovery needed hundreds of HTTP requests and hit client-side throttling, OpenAPI computation (the API server building the machine-readable schema document that describes every kind it serves) consumed large amounts of CPU and memory, and hosted control planes ran out of memory. The fixes were made in kubectl and in the Kubernetes API server, and these are Upbound's own self-reported observations and not formal benchmarks. The lesson is that CRD count is a real scaling dimension of any control plane. [[examples/upbound-tested-a-multi-cloud-control-plane-of-about-2000-managed-resources-and-upstreamed-kubernetes-fixes]] Finally, the wiki notes that the same composite-API idea works for application and infrastructure together, as in the `Microservice` example, and that a scalable composition can expose the scale subresource so HPA and KEDA can drive an XR. The scale subresource is a standard Kubernetes endpoint that lets tools read and set an object's replica count without knowing its other fields. HPA, the HorizontalPodAutoscaler, is the built-in controller that adjusts replica counts from metrics, and KEDA is an add-on that scales from event sources such as queue depth, so both can scale a whole composite through that one endpoint. [[examples/a-scalable-composition-lets-hpa-and-keda-drive-an-xr-through-the-scale-subresource]]

## 10. Design principles to take from Crossplane

The reason to study Crossplane even if you never adopt it is that its design encodes several principles that apply to any platform built on a control plane. Each is argued here from the sources cited in the section.

**Separate the platform API from its implementation.** The XRD defines what users can ask for and the Composition defines how it is fulfilled. Because the API is a versioned contract and the implementation is replaceable, a platform team can move from AWS to GCP, or from one database engine to another, without changing a single consumer manifest. The `function-kro` post phrases the same value as "one schema, many implementations." The cost is that the schema becomes a contract with live consumers, so breaking changes need new versions or conversion webhooks. The wiki's decision page on this frames the choice between a conversion webhook and a new XRD. See [[decisions/conversion-webhook-versus-new-xrd-for-breaking-changes]] and [[comparisons/crossplane-xrds-versus-kro-resourcegraphdefinitions-as-crd-generators]].

**Hide provider features to protect users and the organization.** An API that mirrors the cloud provider's own resource model pushes cloud knowledge onto every consumer. The Polarpoint practitioner blog advises modeling APIs by infrastructure domain, designing for the mental model of the people who use them, and starting with small Compositions and not mega-Compositions. This is opinion without incident data, but it agrees with the contract argument above. [[findings/oversized-compositions-and-cloud-shaped-apis-make-platform-apis-hard-to-use]]

**Status honesty.** Crossplane insists that "exists" and "last reconcile succeeded" are different facts, and it publishes both as separate conditions. A platform that reports one green light hides the cases that matter most: a healthy-looking database that nobody can manage, and a "synced" resource in the middle of a slow update. The lesson is to design status so that operators can distinguish the broken platform from a resource that is still coming up, and then to test that your alerts actually watch both. The wiki's own caveat is that the framework-fixed semantics still leave gaps, such as a long-running update that still reads as synced. [[concepts/conditions]]

**Safety by default at the destructive verb.** Deleting the object deletes the cloud resource, so Crossplane layers controls: management policies to omit Delete, Usages to order and protect, a composite deletion policy with Background, Foreground and Pipeline options, and a refusal to delete and recreate for immutable fields. The ambiguous-create behavior follows the same instinct. When Crossplane cannot tell whether a create succeeded, it halts and asks a human rather than risk a duplicate or a leak, and the event reads "cannot determine creation result - remove the crossplane.io/external-create-pending annotation if it is safe to proceed." The wiki's comparison summarizes the spectrum: Crossplane optimizes for never duplicating or leaking and accepts a human step, ACK and Config Connector optimize for convergence and accept the chance of adopting something unintended, and SAP sits between by requiring explicit intent and narrowing recovery with a creation-time window. [[comparisons/ambiguous-create-and-adoption-strategies-across-crossplane-sap-ack-and-config-connector]]

**Modularity of providers.** Provider packages, provider families, activation policies and revisions are all about letting a cluster hold only what it needs. This is a scaling principle as much as a convenience: the unit of installation decides how many CRDs the API server must hold, so packaging is a performance control. [[concepts/scale-and-sharding]]

**Make the expressiveness limit explicit.** Crossplane refused to grow a templating DSL and moved logic into functions behind a fixed gRPC contract, and kro limits the language to CEL. Either way, the design question is where you accept limits so that the system stays understandable. The reasoning is that an unrestricted language invites oversized, hard-to-debug definitions, and a too-small language invites a pile of workarounds. [[comparisons/where-the-expressiveness-bound-sits-in-crossplane-functions-and-kro-cel]]

**Level-triggered correction with a budget.** Reconciliation corrects drift automatically, but every observation of an external resource may cost a cloud API call. Crossplane's design favors a single control over how much reconcile work runs, on the stated reasoning that "reconcile rate in Crossplane is a good proxy for average external API call rate." The lesson is to pick the one control that maps to the scarce resource you are protecting. A control that limits concurrency is not the same as one that limits calls per second, because how many cloud calls a pool of workers produces depends on how long each reconcile takes, so a concurrency limit does not by itself state a call budget. A second kind of guard protects against runaway composites: a circuit breaker built on a token bucket (a counter that refills at a steady rate and lets a burst through until it is empty, after which work must wait for refills) stops reconciling a composite whose reconciles come too fast. Providers add their own controls, so the budget has to be considered at each layer. [[examples/crossplane-max-reconcile-rate-turns-reconcile-rate-into-an-api-call-budget]]

## 11. Pitfalls: ambiguous create, deletion data loss, provider removal, live composition edits, immutable fields, credential blast radius

**Ambiguous create.** If a provider restarts between writing `external-create-pending` and recording the result, the next reconcile finds the marker with no outcome and halts, and the resource stays stuck until a person intervenes. A maintainer explains that many cloud APIs return generated IDs, so with a lost response there is nothing to look up, and a second create could leak the first resource. Looking up by tags needs per-resource code and fails where tagging is unsupported. Letting resources with deterministic names skip the safeguard is safe where a retried create finds the same resource, but a provider must opt in. Failing safe does not scale, since every ambiguity needs a person. SAP's alternative searches by a business key within a creation-time window, only when the pending marker is present. [[findings/an-ambiguous-create-result-halts-reconciliation-until-a-human-intervenes]] and [[examples/provider-restart-blocks-a-crossplane-resource-on-external-create-pending]]

The opt-out helps only where a provider sets it, so a provider that does not can still leave resources whose names the user chooses, such as bucket sub-resources and IAM policies, wedged after a transient error. Where a provider restart lands inside a long create, the external name can be lost and the retry then fails because the cloud answers that the resource already exists, since the first create actually succeeded. That case is a stuck retry loop and not a duplicate resource, though a stuck resource can still incur cost. The same hazard appears one layer up whenever a reconciler reads from a stale cache and creates something twice. The mechanism is common to the operators for single clouds too: ACK records the AWS identifier in status only after the create call returns, so a controller that stops before that write leaves an AWS resource its custom resource does not know about, and when a create response is lost ACK either creates a second resource or fails on every later reconcile because the name is already taken. Writing the identifier immediately after the create call narrows that window and does not close it, since a crash between the cloud call and the write can still lose the identifier. These are accounts from individual reporters and not organization-authored postmortems, and no named postmortem of a leaked or duplicated cloud resource from Crossplane, ACK or Config Connector appears in the sources used here, so the mechanism is well documented and the production frequency is unknown. [[findings/no-named-postmortem-or-production-comparison-was-found-for-leaked-resources-or-adopt-or-create-versus-explicit-import]]

**External writers on a composite.** Because Crossplane applies composite status and composed resources with server-side apply under fixed field owners, and applies some of them with forced ownership, a second controller that writes to the same fields of an XR can lose its changes to Crossplane at the next pass. (`managedFields` is the metadata list in which the API server records which manager owns which field of an object, and it is what lets server-side apply tell a legitimate write from a conflicting one.) A user report describes a field applied to an XR by an external controller disappearing within one reconcile, but nobody has reproduced it, and a reading of the source shows no path that would prune a field owned by another manager, so treat it as a caution and not an established fact. The safe pattern is for other writers to stay out of the fields Crossplane owns, and if you need a second controller to write to an XR, inspect the object's managed fields on your own cluster first so you can see who owns what.

**Deletion and data loss.** The default of Delete means a mistaken manifest removal, a namespace deletion or a GitOps prune can delete a production database along with its data. Config Connector's documentation names `SpannerInstance` and `BigtableTable` as types where deletion can lose data, and the same logic applies to Crossplane. Set `Orphan` or a policy list without Delete before any operation that removes the Kubernetes object. The wiki's decision page records that the sources document the defaults and opt-outs but recommend no single setting. It helps to know how the Kubernetes garbage collector and the management policies interact when a composite is deleted, because the two are easy to conflate. A namespaced XR can compose only resources in its own namespace, and its composed resources carry a controller owner reference with `blockOwnerDeletion: true`. Deleting the XR defaults to background propagation, so Crossplane stops managing it and the garbage collector removes the composed objects, while a foreground or orphaning delete request from kubectl, and Argo CD's foreground propagation, make Crossplane ignore the composite deletion policy and emit a warning event. What happens to the cloud resource, though, is decided by `managementPolicies` and not by the owner reference: in the managed reconciler source the external resource is deleted only when it exists and the policy allows Delete, and otherwise the reconciler unpublishes connection details and removes the finalizer. A composed resource whose policies omit Delete therefore disappears from Kubernetes with its XR and leaves the cloud resource running, which is the intended behavior for a retained database and a leak for everything else. [[findings/deleting-stateful-resources-through-a-provider-can-lose-data]] and [[findings/a-managed-resource-without-delete-in-its-management-policies-is-removed-from-kubernetes-but-its-cloud-resource-stays]] and [[decisions/delete-or-retain-the-external-resource-when-the-kubernetes-object-is-deleted]]

Related ordering problems: a credentials Secret with no finalizer can vanish before managed resources finish cleanup, leaving them stuck Terminating. When a namespace is deleted its objects go in arbitrary order, so the Secret that holds the credentials can vanish while managed resources still need it to call the cloud API, and those resources then cannot authenticate and stay Terminating. Crossplane protects the provider configuration object while managed resources terminate, but the Secret behind it is not covered, so a platform team must order teardown itself, for example by keeping credentials outside the namespaces being deleted, or by adding a dependency-protection controller or provider-side credential caching. A further namespace-deletion failure can occur even with the provider running: if the managed reconciler connects before it checks whether the resource is being deleted, it may try to create a usage-tracking object in a namespace that is terminating, the API server rejects the create, and deletion is blocked. Namespace deletion while the provider itself is absent is not documented in any source used here, so any claim about it is inference. A paused resource cannot be deleted until it is unpaused, because the pause also stops the reconcile that runs deletion. [[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]], [[findings/crossplane-protects-providerconfigs-while-managed-resources-terminate-but-the-credentials-secret-behind-them-is-still-unprotected]] and [[findings/a-paused-crossplane-resource-cannot-be-deleted-until-it-is-unpaused]]

When a managed resource is stuck Terminating, the temptation is to patch its finalizer list empty, and the sources treat that as a last resort. For some stuck states the only way out is to remove finalizers by hand, which orphans the external resources. A finalizer is usually the only record that something outside the object still needs releasing, so removing it makes the object disappear without running the cleanup, and the cloud resource can keep billing. The 2021 Kubernetes blog post on finalizers shows the same trap at the namespace level: forcing a namespace out through its finalize subresource can leave orphan objects in a namespace that no longer exists, and recreating the namespace may bring them back so they can be cleaned up. The sources agree on the order of preference, which is to find the owning controller, read its logs and repair the cause, and to clean up the external resource by hand if force is unavoidable. They do not agree on a threshold for forcing, and none quantifies how often forced removal orphans resources. One practitioner automated the forced path for Config Connector BigQuery tables with a CronJob that strips finalizers only when the parent dataset is already gone, arguing that this is safe because deleting a dataset in Google Cloud also deletes its tables. That argument is the author's own and holds only where the parent's deletion removes the child in the cloud. [[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]

**Provider removal and cluster deletion.** The documentation states that "removing a Provider without first removing the Provider's managed resources may abandon the resources." The CRDs and controller vanish, finalizers can no longer run, and the real resources keep running and billing. The same mechanism applies if you delete the whole cluster first, which a single consultancy article reports for Config Connector on GKE. Remove managed resources first and wait; Crossplane has a provider-deletion-protection feature that blocks provider removal while managed resources exist. [[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]] and [[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]]

**Live composition edits.** An XR defaults to the Automatic update policy and so follows the latest CompositionRevision, which means an edit to a shared Composition rolls out to every composite at once. The v2 upgrade guide warns that editing a live Composition could disrupt or replace resources. Manual pinning with `compositionRevisionRef` or a label selector shifts risk to consumers, who must then track which composite is on which revision. The wiki's decision page lists a mix as an option, Automatic in non-production and Manual in production, without claiming anyone's practice. Be careful about what Manual protects, since it freezes the pipeline definition and not the function code: a pipeline step that uses `functionRef` follows the active Function revision for every CompositionRevision, pinned ones included, so a function upgrade reaches Manual composites too, as section 6 describes. Revisions also accumulate, one for every edit of a Composition. A garbage collector for unused revisions, which deletes revisions beyond a configurable history limit, is worth enabling on platforms whose Compositions change often. [[findings/editing-a-live-composition-can-disrupt-or-replace-existing-composed-resources]], [[decisions/choose-automatic-or-manual-composition-update-policy]], [[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]] and [[comparisons/composition-revisions-versus-graph-revisions-for-rolling-out-platform-api-changes]]

**Immutable fields.** A change to an immutable field in `forProvider` may silently not apply. Treat such fields as part of the resource's identity, decide them before the first apply, and watch `Synced` after any edit. [[findings/crossplane-does-not-delete-and-recreate-to-change-immutable-fields]]

**Credential blast radius.** Anyone who can create a provider-managed object borrows the controller's identity. Scope credentials with per-account `ProviderConfig` objects, scope who can create composites with RBAC, and remember that a hosting cluster that holds broad cloud permissions is a high-value target. The wiki's general finding is that centralizing privilege in a control plane makes the control plane the blast radius. [[findings/blast-radius-and-privilege-centralization]]

**Functions as moving parts.** Every function in a pipeline is a pod, and a composite cannot reconcile while a function it depends on is unhealthy. Errors in a function's logic also tend to appear only at reconcile time, when Crossplane actually calls it, and not when you apply the Composition. Plan to monitor function pods the way you monitor any other production service. [[findings/composition-functions-add-moving-parts-that-must-be-healthy]]

**Old provider revisions.** Each provider upgrade creates a new `ProviderRevision`, and older ones are kept so that you can roll back. Automatic downgrades are not performed, because moving to an older provider could remove the CRDs or controller behavior that existing managed resources rely on and risk orphaning them, so rolling back is a deliberate manual act and not something the system does for you. Only one revision of a package is active at a time, and activation can be automatic or manual, where manual means a new revision is not activated on its own. Dependencies between packages are handled by a resolver that watches the revision objects, builds a graph from the cluster-scoped `Lock` object (the "lock file" is that object and not a file), rejects cycles and, when dependencies are implied but missing, creates the missing ones one step at a time, so a chain of missing dependencies fills in over several reconciles and a Configuration can briefly report unmet dependencies while it installs. The resolver never rewrites the Lock. Moving an already installed dependency to another version is opt-in, and a downgrade can orphan managed resources, lose data or change storage versions, so without opting in a needed downgrade ends in an error that asks for manual intervention. A Configuration can also be told to skip dependency resolution entirely, in which case Crossplane ignores its dependencies altogether. [[findings/provider-upgrades-leave-old-revisions-and-block-automatic-downgrades]], [[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]] and [[decisions/let-crossplane-resolve-package-dependencies-or-pin-versions-and-skip-resolution]]

**Hosting and skills cost.** Adopting Crossplane requires a hosting cluster, Kubernetes skills on the team that runs it, and a platform team willing to own the abstractions. The critics and the project agree on this point, which is why it is worth stating plainly. Troubleshooting also spans several layers, from the delivery agent to the composite to the provider to the cloud API, which raises the skill needed to debug a platform. Be aware too that older blog posts describing claims, native patch and transform or external secret stores no longer match current Crossplane. [[findings/crossplane-adoption-needs-a-hosting-cluster-kubernetes-skills-and-platform-team-owned-abstractions]] and [[findings/older-claims-and-patch-and-transform-material-no-longer-matches-current-crossplane]]

**GitOps resource tracking.** Crossplane's guide for Argo CD asks for several settings, and each one answers a specific problem. Argo CD normally records which objects belong to an application with a label; the guide asks for annotation-based resource tracking instead, because the guide says that label-based tracking collides with the labels Crossplane itself places on the composed resources it creates, whereas an annotation does not. The guide also asks for custom Lua health checks, because without them Argo CD has no idea whether a `crossplane.io` or `upbound.io` object is healthy and may report it as healthy or progressing indefinitely. Argo CD ships built-in scripts for these kinds, as section 7 describes, so check the shipped script first, and remember that a wildcard script that mishandles one kind can hold up every later sync wave, because Argo CD advances waves only when the current wave is synced and healthy. [[examples/crossplane-resources-hosted-by-argo-cd]]

**GitOps load and noise.** The guide asks you to exclude `ProviderConfigUsage` objects, which Crossplane creates to record which managed resources use a given `ProviderConfig`. They are bookkeeping that nobody authored in Git. The guide describes them as noisy and asks for them to be excluded because end users of Crossplane do not need to interact with them, so Argo CD has no reason to display or sync them. The guide also asks that Argo CD be allowed to make more calls to the Kubernetes API server, because a Crossplane installation has many more kinds and objects to watch than a typical application, so an ordinary client budget can throttle Argo CD. [[examples/crossplane-resources-hosted-by-argo-cd]]

**Foreground deletion.** Argo CD can delete with foreground propagation, and commonly does. In foreground deletion the parent object stays present, marked as deleting, until all of its dependents have been removed, whereas background deletion removes the parent immediately and lets cleanup happen afterward. Crossplane's composite deletion policy offers Background, Foreground and Pipeline behaviors for ordered teardown, but when the delete request itself arrives as a foreground deletion, Crossplane ignores that policy and emits a warning event. The fix is to configure the sync to use background propagation. The danger is that a team can choose Pipeline deletion for ordered teardown and silently lose it, because another tool's setting takes precedence. [[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]]

**Named incidents in the layers around Crossplane.** No organization-authored postmortem is recorded in which Crossplane itself leaked or duplicated a cloud resource, but several named, first-party accounts exist from the layers a Crossplane platform sits among, and they teach the same lessons. Skyscanner's 2021 outage is the clearest GitOps case. An engineer merged a change to the templating system that generates Skyscanner's cluster configuration. The change was meant to alter no behavior, but it left out the `{{ }}` template markers, so templating stopped applying to the root file that every region used and the namespaces defined by it were corrupted. Argo CD then reconciled the clusters against a configuration that listed no valid namespaces and began deleting every service, hundreds in all, across every availability zone and region. Because the clusters pull their state, recovery meant restoring correct configuration and letting each cluster reconcile itself, and the team had the site serving from a single region within hours, with the other regions and non-critical services returning over the following days. The post's own summary is that Argo CD did this "ultimately because we told it to." The lesson for Crossplane users is that a reconciler enforces a bad desired state faithfully, so the guards against deleting stateful resources in this section matter most exactly when the desired state itself is wrong. Spotify's two sets of cluster deletions in late 2018, told at KubeCon in 2019, make the same point about infrastructure as code: an operator deleted a production GKE cluster by console click in November 2018, and about a month later a Terraform review build that imported the Asia cluster into a state file shared with production builds, followed by an out-of-order merge, deleted that cluster. When the team widened a service account's permissions to recreate it, Terraform saw the other clusters with different properties and deleted a second one, so two of three production clusters were gone for a night, and the account says users did not notice. Jetstack's 2019 post is the webhook case, and it bears on the fail-closed Usage webhook described in section 4. A GKE master upgrade stalled because the API server's own post-start write to a ConfigMap was subject to an OPA validating webhook whose backend was not responding, the master failed its health check, and node auto-repair then recreated nodes in an endless loop, which the fix of deleting the webhook resource resolved only because the API server answered intermittently. All three accounts are self-reported, and none involves Crossplane. Closer to provider-managed resources, the same hazards recur in single-reporter accounts and not in postmortems. When a custom resource is pruned from Git, the cloud resource goes with it irreversibly, which is the documented behavior of the AWS controllers unless the object is told to retain its cloud resource. A delivery tool that waits for deletion but gives up after a time limit can let the Kustomization be deleted while a slow cloud delete is still in progress, so the failure outlives the object that was supposed to show it; that is an inference from documented behavior and not an observed event. A multi-cluster setup with leader election can leave deletions pending on a standby cluster and then run the stale deletion against live Google Cloud resources when that cluster becomes leader again. And deleting or recreating a GitOps parent object, or removing a manifest that owns a namespace, can cascade to everything it managed. Several of these reproductions ran on local test clusters with mock cloud services, so treat them as mechanisms and not as frequencies. [[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]], [[examples/spotify-deleted-one-production-gke-cluster-by-console-click-and-two-more-through-terraform-with-no-end-user-impact]], [[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]], [[findings/config-connector-leader-election-across-clusters-can-run-a-stale-deletion-against-live-google-cloud-resources]] and [[findings/deleting-or-recreating-an-argo-cd-parent-can-cascade-to-everything-it-managed]]

## 12. Scaling Crossplane: reconcile rate, provider families, activation policies, domain-scoped control planes

Scaling a Crossplane control plane has several separable pressures. The first is object and CRD count. Each external resource type is its own CRD, so multi-cloud provider sets imply thousands of CRDs that strain API server discovery and OpenAPI computation. Provider families (described in section 3) cut the count by letting you install only the services you use. Crossplane adds a second control: each managed resource type is described by a `ManagedResourceDefinition`, and a `ManagedResourceActivationPolicy` lists exact names or prefix-wildcard patterns so that only matching definitions are activated and turned into served CRDs, with providers that support on-demand activation able to start only what is needed. The trade is completeness for a smaller API surface, so a platform team must know which types it uses. Two details change how you apply this. Unless activation is restricted, every managed resource is activated, so the CRD count does not shrink until you list only the groups you need. And activation is one-way, since a definition that has become active cannot be deactivated, and a provider without on-demand activation starts everything active regardless. [[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]], [[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]] and [[findings/one-crd-per-external-resource-type-overloads-api-server-discovery-and-openapi-computation]]

The second pressure is reconcile load. Each reconcile of a managed resource may call a cloud API that has its own quota, so how often a controller re-checks the outside world is a trade-off between how quickly drift is noticed and how many calls are spent on the external API. Crossplane has no single cadence: the shared runtime, the composition machinery and each provider pick their own, and providers generated from Terraform schemas typically re-check more slowly than hand-written ones because each check is more expensive, so a drift-detection latency quoted for "Crossplane" means little unless it names the provider. Other tools make the same trade differently. Some controllers re-read the cloud on a long periodic resync, some replay cached state to their handlers without re-reading the cloud at all, which is a different mechanism from a real re-read, and the delivery tools check Git and the cluster on cadences of their own, which an author can usually tune per object or switch off. Config Connector jitters its requeue so that resources do not all hit the cloud at the same moment, and lets the cadence be tuned or drift correction disabled outright. Longer intervals save API quota but lengthen drift-detection latency, which is the trade the wiki's decision page on choosing a drift-check interval frames. Concurrency works alongside cadence: a pool of workers limits how many reconciles run at once, and API Priority and Fairness (the API server's mechanism for queuing and rate-limiting requests by priority so that one noisy client cannot starve the others) protects the API server from any one controller. Crossplane has no single scaling page and no published numeric limits for composites or composed resources, and no independent benchmark exists. [[comparisons/drift-detection-mechanisms-across-tools]] and [[decisions/choosing-a-drift-check-interval-for-external-resources]]

The third pressure is function load: composites are re-checked on a regular cadence, and function calls scale with composite count. The design document lists the levers as the polling cadence, function replicas and response caching. A third-party article argues large composites can exhaust function memory, though its log excerpts are labelled simulated, so that claim is plausible guidance and not an incident report. Imagine Learning chose one monolithic function to reduce idle pods, trading isolation for fewer processes. [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]

Informer caches add a fourth, general Kubernetes pressure: a controller that watches many objects holds every watched object in memory, so memory grows with cluster size. Crossplane core takes some steps against this. It strips the OpenAPI schemas, which are most of the size of each CustomResourceDefinition, from the copies it caches, it reads Secrets directly from the API server without caching them. Providers can shrink their footprint in a similar way, and providers that support on-demand activation can leave idle runtime pods scaled down until a resource type is first needed. The effect is that the family-split trade of fewer CRDs for more pods is being offset from the other side, as per-provider memory shrinks. The project reports sizeable memory reductions from this work, all self-reported and tied to particular cluster sizes, and none an independent benchmark. For Upjet-based providers specifically, no official memory or CPU figures exist, as section 3 notes. No Crossplane performance or sharding guide exists in the sources, and no documentation describes informer sharding. After a provider restart all of its managed resources are re-queued as the cache is rebuilt, so a long polling cadence reduces drift checks but does not spare that initial burst. The wiki's general treatment lives in [[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]] and [[concepts/informers-reflectors-and-workqueues]], and for the other tools in [[findings/flux-controllers-keep-separate-caches-narrowed-by-a-watch-label-selector-and-leave-secrets-and-configmaps-uncached-by-default]] and [[examples/argo-cd-application-controller-shards-clusters-and-tunes-processor-counts]]. The shared store also has limits of its own, covered in [[findings/etcd-scale-limits-of-the-shared-store]]. Tested scalability envelopes and operator advice also differ by roughly an order of magnitude, and neither lists CRD count as a tested dimension. [[findings/tested-scalability-maximums-and-operator-advice-differ-by-an-order-of-magnitude]]

Finally there is the question of how many control planes to run. A practitioner blog from Polarpoint argues that "teams no longer need a single monolithic Crossplane instance," and proposes several small control planes each scoped to a domain such as networking or data. The wiki marks this as prescriptive advice from two blogs, not evidence of deployments, with no object counts or operating costs. The trade-off, which the decision page leaves open, is smaller blast radius and clearer ownership against more clusters to operate. The same worry appears for Cluster API, where centralizing authority in a management cluster makes that cluster a single point of failure. [[findings/blast-radius-and-privilege-centralization]], [[examples/domain-scoped-crossplane-control-planes-are-proposed-in-place-of-one-monolithic-instance]] and [[decisions/run-one-crossplane-control-plane-or-several-domain-scoped-ones]]

## 13. How Crossplane compares with kro, Terraform and tofu-controller, ACK, Config Connector, ASO, Cluster API and Kratix

**kro.** kro (kube-resource-orchestrator) was created by Google together with AWS and Microsoft and is governed as a Kubernetes SIG Cloud Provider subproject. It expands one end-user CRD into a graph of resources through a single ResourceGraphDefinition that holds schema, templates and CEL expressions. Where Crossplane separates XRD from Composition and runs external function pods, kro puts everything in one object and evaluates CEL inside its own controller. kro infers dependency order from references and creates in topological order, deleting in reverse; Crossplane leaves ordering to the functions and eventual reconciliation. kro validates at creation time, Crossplane often at reconcile time. kro is a younger project than Crossplane with a shorter track record, whereas Crossplane is CNCF graduated. Amazon's EKS documentation describes a fully managed kro capability, so customers do not install, maintain or scale the kro controllers, and it names ACK (for composing AWS resources) and Argo CD (for deploying kro custom resources across clusters) as its integrations with other managed capabilities. That page is vendor documentation and names no scale limit and no production adopter. [[entities/kro]] On scale, the evidence is thin. kro runs its instances through one shared work queue with a single dynamic controller, which means one busy resource type can starve others, and a maintainer has proposed weighted queues as a remedy. There is no published benchmark, no measured limit and no named production adopter, and a third-party article that lists production failure patterns cites no customer and no data, so it is low reliability. [[findings/kro-s-single-shared-queue-can-starve-resources-and-a-maintainer-proposed-weighted-queues]] An engineer's rule of thumb from a comparison blog is to use kro when the building blocks are already Kubernetes resources and Crossplane when the platform must drive cloud APIs directly, and `function-kro` lets you combine them. A tutorial that built the same `StorageApp` API both ways found equivalent outcomes and noted that the Go-template Composition needed hand-written creation order and deletion guards. It is a single tutorial and not a production report. Rollout differs too: Crossplane has CompositionRevisions pinnable per XR, while kro has immutable graph revisions with no fallback when a revision fails compilation. [[comparisons/crossplane-composition-functions-versus-kro-resource-graph-execution-models]], [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]], [[examples/build-the-same-storageapp-api-with-kro-and-with-a-crossplane-go-templating-composition]] and [[findings/a-kro-graph-revision-that-fails-compilation-stops-all-instances-with-no-fallback]]

**Terraform and tofu-controller.** The Crossplane blog's one-liner is that "Crossplane is a control plane, where Terraform is a command-line tool, an interface to control planes." Crossplane controllers reconcile continuously and correct drift without anyone running a command, with each resource an independent API object under Kubernetes RBAC. Terraform plans against a state file when a person or CI job invokes it, and drift shows up at the next plan, with a reviewable plan before apply. Crossplane needs a running Kubernetes cluster and Kubernetes expertise, and the Crossplane blog itself concedes Terraform is simpler and more familiar. The comparison sources mostly come from vendors, so this contrast is a statement of design and not a neutral benchmark. Crossplane has no equivalent plan preview for what a provider will change in the cloud, although rendering a Composition previews what it will produce, and fields that would force recreation in Terraform may be ignored while the provider reports in sync. A plan is also only as accurate as the provider that produces it, since an anonymous report describes a plan that showed an update while the apply recreated the resource and lost its data, so plan review is a check and not a guarantee. Disaster recovery of the cluster that runs the controllers is a further open question: an object's external-name annotation is the link to the cloud resource and ownership records live in the cluster, so a restore into a new cluster has to preserve that link, and a restored copy could give one cloud resource two owners. Terraform also enters Crossplane through Upjet. Two controllers run Terraform inside a cluster. tofu-controller, a community project under the flux-iac organization, runs plan and apply in runner pods, stores state as Kubernetes Secrets, and does manual approval by putting the plan identifier in the manifest through Git; it also offers a drift-detection-only mode. It is tied to particular Terraform and Flux releases, so upgrades have to be coordinated. Terraform Operator, a community project that starts Terraform workflow pods when its manifest changes, is a low-activity project that depends on a single main author. Neither controller removes the need to write Terraform. [[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]], [[findings/terraform-in-cluster-controllers-keep-state-in-secrets-gate-apply-on-git-approval-and-couple-to-specific-versions]], [[comparisons/tofu-controller-versus-terraform-operator-as-terraform-in-cluster-controllers]] and [[findings/no-neutral-comparison-of-crossplane-with-terraform-or-single-cloud-operators-was-found-and-the-independent-material-is-dated]]

**ACK, Config Connector and ASO.** These cloud-vendor add-ons expose one cloud's resources close to one-to-one, with no built-in composition layer. ACK runs one controller per AWS service with scoped IAM permissions, uses `IAMRoleSelector` to map namespaces to roles and is generated from AWS API models. Config Connector covers Google Cloud with three kinds of controller, a direct controller and two generated from Terraform and from Google's declarative library, and reports a single `Ready` condition. Which of the three controllers handles a given kind is an implementation detail that can change, so treat the behavior of each kind as something to check on your own cluster and not as a fixed mapping, and note that all three share the single `Ready` condition. Namespaced mode scopes credentials per namespace, while cluster mode uses one credential for everything. One practitioner's account, from a single author and not reproduced, adds an ordering cost. Config Connector does not order creation by dependency the way Terraform's graph does, so a BigQuery table that points at its dataset cannot be created until the dataset exists, and the author orders them with Argo CD sync waves. On deletion Argo CD gives no ordering, so removing the dataset first leaves the table object in a failed deletion state. The same author lists multi-cloud support as Crossplane's one advantage over Config Connector, without any measurement. This is the pattern in which a per-resource provisioning controller pushes ordering onto the delivery tool, whereas a Crossplane Composition or a kro graph keeps ordering inside one abstraction. On the comparison with Crossplane, the sources include no neutral comparison, only a Crossplane maintainer's positioning and an unanswered question. Azure Service Operator is similar in style, with CRDs generated from Azure Resource Manager schemas, though the sources do not cover its credential scoping, deletion policy or drift cadence, and the comparison source is a project maintainer, so it is positioning and not neutral analysis. The EKS kro capability composes ACK S3 buckets with Deployments and ConfigMaps, which shows the add-ons paired with a separate abstraction layer. [[examples/the-eks-kro-capability-composes-ack-s3-buckets-with-deployments-and-config-maps]] The ACK documentation has its own first-party guide, "Using ACK with kro", whose ResourceGraphDefinition composes an S3 bucket, a DynamoDB table and a Deployment: kro waits for the ACK resources to become ready before creating dependents, does not create dependents if an ACK resource fails, and on deletion removes the Deployment first and then the AWS resources, following ACK's deletion policy. The sources contain no Crossplane equivalent: no worked example of Crossplane composing ACK or Config Connector objects, and no first-party test of the interplay. On paper both satisfy `function-auto-ready`, which treats a composed resource of an unknown kind as ready when it carries a `Ready` condition with status True, and ACK defines a `Ready` condition that its runtime source calls equivalent to `ResourceSynced` while Config Connector reports `Ready` when a resource is up to date, but that is an inference from documented conditions, and whether composite deletion honors their deletion ordering is unsettled. ACK's deletion policy resolves from the resource, then the namespace, then the controller default, and one reporter says a chart-stamped Delete defeats a controller-wide Retain, which is a single-reporter claim. ACK's per-service controllers avoided the many-CRD problem from the start, whereas Crossplane needed families. [[comparisons/crossplane-versus-cloud-vendor-add-ons-ack-config-connector-and-aso]], [[comparisons/provider-families-versus-per-service-controllers]], [[examples/the-ack-docs-kro-guide-composes-an-s3-bucket-a-dynamodb-table-and-a-deployment-and-deletes-the-deployment-before-the-aws-resources]], [[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]], [[findings/ack-deletion-policy-resolves-from-the-resource-then-the-namespace-then-the-controller-default-and-one-reporter-says-chart-stamped-delete-defeats-a-controller-wide-retain]], [[findings/config-connector-routes-a-kind-to-its-controller-by-namespace-override-then-static-default-and-a-live-crd-label-shows-which-one-runs]], [[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]] and [[findings/no-neutral-comparison-of-config-connector-and-crossplane-was-found-so-the-evidence-is-two-vendor-positions]]

**Cluster API.** Cluster API means something different by "provider": an implementation of a contract so a generic core can build whole clusters, split into infrastructure, bootstrap and control-plane providers, with a small interface. A Crossplane provider is a wide catalog of resource types. Cluster API's Machines are immutable, with changes replacing machines like a Deployment replacing pods, and it offers `MachineHealthCheck` for remediation. [[comparisons/crossplane-providers-versus-cluster-api-providers]]

**Kratix, Backstage and Port.** Kratix, from Syntasso, is an orchestration framework whose central object is the Promise, bundling a self-service API, workflows and fleet scheduling, and its documentation expects a portal such as Backstage in front. Backstage is an open-source portal framework (originally from Spotify) with a software catalog and templates, and Port is a commercial SaaS portal. Portals provide visibility; a Syntasso blog argues a portal alone leaves ticket queues in place, though that is a vendor claim and the only comparison with Port is Port's own. Kratix and Crossplane both define platform APIs, but no source compares them head to head, so this document makes no claim about which is better. Kratix's reference pages document the mechanics that distinguish it, as follows. A Destination is a cluster-scoped representation of a system that Kratix can write documents to, such as a Kubernetes cluster with Flux or Argo CD pulling manifests, Terraform, Ansible, or even a Backstage catalog filled from a Git repository. Kratix does not apply those documents itself. It writes them to a state store, either a Git repository (GitStateStore) or an S3-compatible bucket (BucketStateStore), and the agent on the Destination reads them, so Kratix leans on a delivery tool for the last step in the way a Crossplane platform leans on Flux or Argo CD. Under the store path Kratix writes one directory for Promise-level items such as CRDs and another for each Resource request, and the directory layout is fixed when a Destination is created, so changing it means creating a new Destination. Scheduling happens in two stages. In the first, a Promise's dependencies go to every Destination, or only to those whose labels satisfy the Promise's selectors, and a Destination can be set to accept only Promises whose selectors match its labels. In the second, a Resource request triggers its configure workflow and the outputs go to a matching Destination, and when several match Kratix selects one at random, which is a surprise for anyone expecting a deterministic spread. The sources cover the documentation and the Go types and do not cover the scheduler source. The Score and Radius projects sit higher still, closer to the developer's workload description. Both are CNCF Sandbox projects, which is the entry tier and says nothing about production readiness. All of Radius's listed maintainers work at one company, whereas Score's maintainers span several employers. Score separates a specification from its implementations, such as score-k8s and score-compose. Backstage, finally, is a read-oriented portal over what operators produce. Its Kubernetes plugin matches catalog entities to cluster objects through the `backstage.io/kubernetes-id` label or a label-selector annotation and silently skips a custom resource whose CRD is not installed, and its Scaffolder is a one-shot task runner and not a reconcile loop. The nearest operator-style integration is a community plugin, the TeraSky Kubernetes Ingestor, which syncs from cluster to catalog and ingests Crossplane claims and kro instances. [[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]], [[findings/a-kratix-destination-writes-dependencies-and-resources-directories-and-its-filepath-mode-is-immutable]], [[findings/kratix-schedules-in-two-stages-by-label-matching-and-picks-a-destination-at-random-when-several-match]],  [[comparisons/score-versus-radius-as-developer-facing-workload-abstractions]], [[findings/the-backstage-kubernetes-plugin-matches-entities-to-cluster-objects-by-label-and-no-backstage-document-describes-an-operator-pattern]], [[findings/the-backstage-scaffolder-is-a-one-shot-task-runner-and-the-nearest-operator-style-integration-is-a-third-party-plugin]] and [[examples/the-terasky-kubernetes-ingestor-ingests-crossplane-claims-and-kro-instances-into-the-backstage-catalog]]

**Render-time tools and KRM functions.** Helm, Kustomize, kpt and Score belong to a different family from Crossplane and kro. They produce manifests once, on a laptop or in CI, and something else, usually a GitOps agent, must keep the result correct afterward, whereas a controller-driven abstraction such as Crossplane, kro or Radius is a live API whose controller keeps reconciling children, writes status back to the parent and handles deletion order. Moving Kustomize or Helm inflation into KRM functions brings the container requirement discussed in section 6, which laptops, CI runners and Argo CD often lack, and kpt and Kustomize offer only opt-in exec extensions as the way around it. [[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]] and [[findings/moving-kustomize-helm-inflation-to-krm-functions-needs-a-container-runtime-that-laptops-ci-and-argo-cd-often-lack]]

**Flux and Argo CD.** These deliver rather than provision. Flux orders whole objects with `dependsOn` between Kustomizations, and Argo CD orders within a sync with phases and wave numbers, while kro and Crossplane order resources inside one abstraction. Flux can run `prune` and can also be told to orphan objects and so keep them; Argo CD prunes only when asked. The guards at both layers need to agree, since a Git removal with `prune: true` deletes the object and the provider then deletes the cloud resource unless Delete is excluded. A good mental stack is delivery (Flux or Argo CD), then abstraction (Crossplane or kro), then provisioning (providers, ACK, Config Connector), with a portal on top. [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]], [[comparisons/deletion-policies-across-gitops-and-provider-tools]] and [[comparisons/delivery-versus-provisioning-versus-platform-layers-in-the-kubernetes-tooling-landscape]]

**Flux versus Argo CD behavior, side by side.** Since the choice of delivery agent changes how a Crossplane platform behaves, the design differences are worth having next to each other, with the caveat that no neutral benchmark or CNCF comparison of the two exists and everything here rests on each project's own documentation. For drift, Flux checks the live object against Git on every reconcile and reverts manual changes unless the object is suspended, whereas Argo CD compares Git with live state and marks the application out of sync, and reverts only when self-heal is turned on. Pruning is an explicit decision in both tools: Flux prunes per object with an opt-out annotation, Argo CD prunes only when asked, and both offer ways to keep an object when its manifest leaves Git. The ignore controls differ in a way that has bitten users: Argo CD's ignore rules affect only the diff unless it is told to respect them when applying, and then only for resources that already exist, while a Flux ignore rule without a target selector matches every object the Kustomization manages. Neither tool offers a true observe-only mode, which is a negative finding from the documentation pages in the sources, so Crossplane's `Observe` management policy remains the way to look without touching. For multi-cluster delivery, a central Argo CD instance reaches into registered clusters from a hub, so delivery to a fleet is a push even though each application pulls from Git, while the more common Flux layout runs a controller set in every cluster, though a Flux Kustomization can also target a remote cluster. Large organizations report running Flux across hundreds of clusters with self-service onboarding. ApplicationSets generate many Applications from one template and have documented limits on how generators can be combined. Their staged rollout strategy watches only Application health, so it is only as good as the health scripts discussed in section 7, and an Application that no step selects is silently excluded. No quantified scale limit for ApplicationSets or hub-and-spoke Argo CD was found. [[comparisons/exemption-and-ignore-controls-across-tools]], [[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]], [[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]] and [[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]]

**Secrets and OCI sources in GitOps.** A Crossplane platform needs credentials for providers, so how the delivery agent handles secrets matters. Argo CD's secret-management page "strongly" recommends populating secrets on the destination cluster through an operator, naming Sealed Secrets and External Secrets Operator (in-cluster operators that turn encrypted or externally stored secrets into ordinary Kubernetes Secrets), the Secrets Store CSI Driver (which mounts secrets from an external store into pods) and Vault Secrets Operator (which does the same for HashiCorp Vault), and it cautions against plugins that inject secret values while rendering manifests, because Argo CD stores generated manifests in plaintext in its Redis cache, secret updates become coupled to syncs, and the approach is incompatible with the "Rendered Manifests" pattern, which means committing the fully rendered manifests to Git so that reviewers can see exactly what will be applied. The page does not mention SOPS (a tool that encrypts the values inside a YAML file so the file can safely sit in Git) or ksops (a Kustomize plugin that decrypts SOPS files during rendering) at all, which is a statement about the page and not a position of the project. Flux takes the opposite stance for SOPS: the Kustomization specification says "The only supported encryption provider is SOPS", decryption runs inside kustomize-controller, and encrypted files must leave `metadata`, `kind` and `apiVersion` in plaintext. Flux also publishes a Sealed Secrets guide, and the sources describe no failure modes for either approach. On sources, Flux's OCIRepository can verify Cosign or Notation signatures (both are tools that sign and verify container and OCI artifacts) through `.spec.verify`, including keyless identity matching, while the Argo CD pages in the sources document OCI images as an application source but no OCI signature verification, covering only Git commit signatures with GnuPG. Again that describes only the pages in the sources and is not proof of absence from the code, and no independent evidence that signed OCI beats Git, and no registry rate-limit documentation, was found. [[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]], [[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]] and [[decisions/git-versus-oci-as-the-canonical-source]]

**Flux internals worth knowing.** A few design ideas from Flux explain behavior a Crossplane operator may see when Flux delivers the platform. Running extra replicas of a Flux controller gives failover and not extra capacity, because only the replica that holds leadership does the work and the standbys wait. When controllers are sharded to spread load, each shard elects its leader independently, so the shards fail over on their own. Production evidence for sharded Flux is thin, and no organization in the sources says it runs sharded Flux. For composites, Flux records what it applied in an inventory, so resources that Crossplane or kro create from a composite sit outside it. The inference that Flux therefore needs no owner reference or tracking annotation on them, unlike Argo CD, is unverified because no Flux page states it. [[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]] and [[findings/flux-tracks-composite-resources-through-its-inventory-and-kstatus-or-cel-health-checks-and-documents-no-owner-reference-recipe-or-kro-guidance]]

**Plain controllers.** Writing your own operator with Kubebuilder gives full control and costs a controller per API. The wiki frames Composition as a way to express a custom API "without hand-writing a controller," and its decision page weighs building a custom operator against composing existing resources. Hand-written operators duplicate what composition could express, though a hand-written provider has its own traps, such as treating not-found as an error and breaking the create flow. ## 14. Getting started checklist and remaining unknowns

A sensible path for a first week looks like this, and each step ties to a pitfall above. First, decide whether you already operate Kubernetes; if not, the hosting cluster is your first cost. Second, start with the current namespaced model and read the upgrade guide as a map of what changed, since many online posts describe claims and patch and transform. Third, install only the provider family members you need and decide your credential scope before creating any resource. Fourth, create one managed resource by hand and watch both `Synced` and `Ready` as it provisions, so you internalize the two-condition model. Fifth, set deletion safety early: management policies without Delete, or `Orphan`, for anything stateful, and Usages for dependency ordering. Sixth, try an import with Observe before promoting to `["*"]`. Seventh, author a small XRD and a one-step Composition, test it with `crossplane render`, and make sure every function passes through the incoming desired state. Eighth, decide whether Compositions update automatically or by pinned revision before you have consumers. Ninth, if you use Argo CD, apply the documented tracking, health-check and propagation settings. Tenth, alert on persistent `Synced=False` and read `AsyncOperation` for Upjet-based providers.

The following open questions affect real decisions. Crossplane's managed-resources documentation states no poll interval for providers, so how quickly a given provider notices drift has to be read from that provider's own configuration. Operations, the type for running pipelines to completion for day-two tasks, is the least settled feature: an Operation cannot delete resources, it applies with forced ownership and it sets no owner references. Legacy cluster-scoped composites with claims exist only on the older definition API, and the async `Synced` behavior described in section 7 remains something to alert around.

What is still open is narrower. Several details of Crossplane's current behavior rest on older documentation, third-party blogs or a reading of reconciler source, namely condition semantics, how namespaced managed resources behave when a provider is down, and how management policies interact with garbage collection when a namespace is deleted; the garbage-collection interaction is consistent with the documented policy table but is stated by no documentation page. Function-pipeline status propagation is partly documented: how a function's per-resource ready flag becomes the XR's `Ready` condition is clear, and for `function-kro` the way conditions are approximated is described, but where `function-kro` marks each desired composed resource ready is not, and no documentation of a standalone kro controller feeding a composite exists. Whether external writers on an XR lose fields depends on which fields the writers share, and nobody has shown it either way. Package dependency resolution is documented, as section 11 describes, but the activation policy and history limit for Function packages are not stated. Whether the Upjet runtime runs Terraform as a subprocess depends on a per-resource execution mode, as section 3 describes, and which official providers use which mode, along with the memory and CPU cost of any of them, is not established. The sources describe no Crossplane-specific performance or sharding guide and do not say what happens to a namespaced managed resource when its namespace is deleted while the provider is down. Elsewhere in the landscape, the thin spots are the ones that need a neutral third party or a measurement: no independent Argo CD versus Flux benchmark, no neutral comparison of Crossplane with Terraform or of Config Connector with Crossplane, no kro benchmark or named kro adopter, no first-party Flux postmortem, no measured Flux shard outcomes and no measured Config Connector drift latency. These are absences in the evidence and not proof that nothing exists. Adopter claims remain self-reported, and no named Crossplane case study with scale and incident data exists in the sources used here, and neither does an organization-authored postmortem of a leaked or duplicated cloud resource. The named incident accounts in section 11 (Skyscanner, Spotify and Jetstack) concern Argo CD, Terraform and an admission webhook and not Crossplane, but they teach the same lessons about reconcilers enforcing a bad desired state.
