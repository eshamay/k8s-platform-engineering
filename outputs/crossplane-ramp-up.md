# Crossplane Ramp-Up: Compositions, Providers and Design Principles for Control-Plane Platforms

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) but have not yet worked with controllers, API machinery or platform abstractions, and platform engineers weighing Crossplane for an internal developer platform.<br>
> **Purpose:** Teach Crossplane from first principles, explain how it behaves in practice, and draw out the design principles that make it a useful model for building platforms.<br>
> **Status:** Active. Facts come from the k8s-platform-engineering wiki; where the wiki is thin or its sources disagree, the text says so.<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** [[entities/crossplane]], [[concepts/managed-resource]], [[concepts/composite-resource]], [[concepts/composition]], [[concepts/provider]], [[sources/research-crossplane-deep-dive]], and the findings, comparisons and decisions listed under Further reading.

## 1. What Crossplane is and who uses it

Crossplane is an extension to Kubernetes that turns a cluster into a control plane for things that are not in the cluster. The Kubernetes API server stores objects and notifies controllers when they change, and a controller is a program that keeps nudging the real world toward whatever those objects say. Kubernetes uses this idea for pods and deployments. Crossplane applies the same idea to a cloud database, a storage bucket, an IAM role or a whole managed Kubernetes cluster. You write a Kubernetes object that describes the cloud thing you want, and a Crossplane controller creates, updates and eventually deletes the real thing to match. The wiki describes this as an instance of the [[concepts/universal-control-plane]], the observation that the API server, etcd and the controller pattern make a general-purpose engine for managing any resource that has an API. [[entities/crossplane]]

The project describes itself as a framework for building control planes, and its documentation says a Composition "composes individual resources together into a larger, reusable, solution." That sentence hints at the two halves of the tool. The lower half is a catalog of providers that expose individual cloud resources as Kubernetes objects. The upper half lets a platform team define its own higher-level APIs, such as a `PostgreSQLInstance` or a `Microservice`, and describe how each one expands into many lower-level objects. Application teams then ask for the simple thing and never see the cloud-specific details. [[concepts/composition]]

Crossplane was created by Upbound, entered the CNCF Sandbox in 2020, and graduated in the CNCF in late 2025 according to the project's own announcement and InfoQ. The project reports 70 or more public adopters, and the contributing-company counts differ between sources (480 or more in the project's post, 450 in InfoQ), all self-reported. One engineer's July 2026 blog still calls it CNCF Incubating, which conflicts with the graduation record, and the wiki treats that label as a likely stale claim. [[entities/crossplane]]

The adopters list in the project repository is a set of self-reported one-liners and not verified case studies, but it conveys the range. Nike describes an internal developer platform managing thousands of resources, SAP reports 100 or more control planes built on the Kubernetes resource model as of February 2024, Deutsche Kreditbank reports 10 or more EKS clusters with thousands of resources, DB Systel (Deutsche Bahn) describes fully GitOps-driven self-service, and Akamai reports a provider that orchestrates up to 200,000 managed resources. The wiki is explicit that these entries are pointers for research and not evidence of behavior. [[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]]

A fresh read of the adopters file on 2026-11-26 counted 87 linked rows, with the file last changed on 2026-10-27, and found numeric claims for only about eight organizations. Three more are worth naming because their entries carry a number and a context. Built Technologies says its developer environment has "at times" exceeded 10,000 AWS resources managed by Crossplane, which is a peak in a non-production setting with no statement of how many Crossplane instances held those objects or what reconciliation cost. Consensys says it is managing more than 1,000 resources and links a KubeCon talk that the wiki has not yet watched, so nothing beyond the one-liner is recorded. SpareBank 1 Utvikling describes a self-service migration of over a thousand production microservices, databases and caches to EKS and AWS managed services, which counts workloads moved and not managed-resource objects. None of these entries is dated, and all of them are self-reported, so they show how far people say they have pushed the tool and not how it behaved when they did. [[examples/built-technologies-reports-peaks-above-10000-aws-resources-managed-by-crossplane-in-a-developer-environment]], [[examples/consensys-reports-managing-more-than-1000-resources-with-crossplane]] and [[examples/sparebank-1-utvikling-reports-a-self-service-migration-of-over-a-thousand-production-microservices-with-crossplane]]

## 2. Mental model: external resources as Kubernetes objects and the two reconcile loops

To understand Crossplane you need three ideas from the controller world. The first is declarative intent: the object's `spec` says what you want, and you do not script the steps. The second is the split between `spec` and `status`. Spec is written by users, status is written by the controller, and the controller reports what it observed there. This is the [[concepts/spec-status-split]], and it is why you can read an object and learn both what was asked for and what is true. The third is the reconciliation loop, in which a controller repeatedly observes the real state, compares it to the desired state, and acts to close the gap. The loop is level-triggered, meaning it looks at the current state each time rather than reacting to a one-time event, so a missed event or a restart does not leave the system permanently wrong. See [[concepts/reconciliation-loop]] and [[concepts/operator-pattern]].

The Crossplane documentation uses precise vocabulary here. The Kubernetes object is called a managed resource, and the real thing in the cloud is called an external resource. A provider controller reads the external resource, compares it with the managed resource, and creates, updates or deletes the external resource to close the gap. The shortest framing the wiki offers is a Deployment-style controller loop whose pods are cloud resources. [[concepts/managed-resource]]

Because Crossplane has two layers of abstraction, a typical platform has two reconcile loops stacked on top of each other, and a third if you add a GitOps agent. GitOps means keeping Git as the source of truth for what should run, with an agent inside the cluster that pulls from Git and applies it. Argo CD and Flux are the two best-known agents of this kind: each is a pull-based controller that watches a Git repository and syncs its contents into the Kubernetes API server. At the bottom, provider controllers reconcile each managed resource against the cloud API. Above them, Crossplane's composition machinery reconciles each composite resource against the managed resources it owns. If you deliver the whole thing through Argo CD or Flux, a delivery loop reconciles Git into the Kubernetes API. The wiki's finding on this point is that each loop can report green or drift independently. A green sync in the GitOps agent says only that the custom resource matches Git. It does not say the database is healthy, and a lower loop may correct drift without the upper loop ever noticing a difference. The practical advice is to read both layers, the agent's sync status for "Git versus API" and the custom resource's conditions for "API versus reality." [[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]

A last piece of background is the idea of a finalizer. A finalizer is a string on an object's metadata that tells Kubernetes "do not remove this object yet." When you delete such an object, Kubernetes sets a deletion timestamp and waits for the responsible controller to finish its cleanup and remove the finalizer. Crossplane puts a finalizer on every managed resource so that the cloud resource is really gone before the Kubernetes object disappears. The documented name of that finalizer is `finalizer.managedresource.crossplane.io`, and the managed resources documentation adds two warnings about it: deletion hangs if the provider that owns the finalizer is gone, and removing the finalizer by hand orphans the real resource, because the cleanup it exists to protect is skipped. Finalizer names are not uniform across tools, which matters when you are staring at a stuck object and trying to work out which controller owes you a cleanup. ACK derives a name of the form `finalizers.<apiGroup>/<Kind>` for each generated controller, Config Connector uses `cnrm.cloud.google.com/finalizer` plus a second `cnrm.cloud.google.com/deletion-defender`, and kro uses `kro.run/finalizer`. The wiki read the ACK, Config Connector and kro names from source, since none of those projects' documentation pages explains them, and for ACK it read only the template form and not the literal string of any one service controller. One further rule from the Kubernetes side explains why a late finalizer is useless: once an object has a deletion timestamp, the API server refuses to add new finalizers, so a controller must add its finalizer on the first reconcile, before it creates anything external. This is how deletion of a Kubernetes object becomes deletion of a cloud resource, and it comes back repeatedly in the pitfalls below. [[concepts/finalizers]], [[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]] and [[findings/a-finalizer-added-after-the-delete-request-is-too-late-and-new-ones-are-refused]]

## 3. Providers, ProviderConfigs, credentials and provider families

A provider is a packaged controller plus a set of CustomResourceDefinitions (CRDs, the mechanism that lets you add new object kinds to Kubernetes) that teaches the cluster how to speak to one external API, for example AWS, Azure, GCP or GitHub. The CRDs describe the external resource types as Kubernetes kinds, and the controller watches those kinds and calls the external API. See [[concepts/provider]] and [[concepts/custom-resource-definition]].

In Crossplane a provider is an installable package, an OCI image of the sort you would pull from a container registry. You install one by creating a `Provider` object. Each upgrade creates a `ProviderRevision`, so the cluster can keep an older revision for rollback. A `ProviderConfig` (or, in Crossplane v2, a `ClusterProviderConfig`) tells the provider which credentials to use, and a `DeploymentRuntimeConfig` customizes the provider's pod. Every provider reuses a shared managed reconciler from crossplane-runtime with the phases Connect, Observe, Create, Update and Delete, and the provider author implements an external client behind that interface. [[concepts/provider]] and [[examples/provider-authors-implement-an-external-client-behind-the-shared-managed-reconciler]]

Writing hundreds of resource types by hand is impractical, so large catalogs are generated. Upjet, a Crossplane code-generation framework, reads Terraform provider schemas at build time and generates Go types and controllers, and the generated controllers reuse Terraform's resource logic at runtime while users see only a Kubernetes API. The wiki's dossier says Upjet underpins the official AWS, Azure and GCP providers. Whether the generated runtime calls Terraform as a subprocess or in-process turns out not to have a single answer, because Upjet offers three execution modes that are chosen per resource in the resource's configuration. The first is the traditional fork-based mode, in which the controller shells out to the Terraform command-line tool and talks to a Terraform provider process. The second calls the Terraform Plugin SDK v2 provider as an ordinary Go library inside the provider pod, with no forked process. The third does the same for providers written against the newer Terraform Plugin Framework, talking to them over the protov6 protocol. Because the mode is a per-resource setting, one provider package can mix a forked path for some kinds and in-process paths for others, and the wiki did not establish which of the official AWS, Azure and GCP providers use which mode, so any claim about a specific official provider's process count or cost is unsupported. In the fork-based mode each managed resource gets its own Terraform working directory holding a `terraform.tfstate` file, which means state lives on the provider pod's filesystem and belongs in a capacity and restart review. The Terraform provider process itself is not forked on every reconcile. One native provider process is shared between all resources that yield the same provider configuration and is replaced once its invocation count reaches a time-to-live and it is idle, which counts invocations and not elapsed time, so a long synchronous Terraform operation can delay the replacement. Upjet issue 263 is a report of exactly that kind of stuck shared provider, and issue 754 reports the Plugin Framework connector re-running provider configuration on every reconcile. For measurement, Upjet exposes metrics for CLI duration, active CLI invocations, running processes and time to readiness, and its monitoring page calls the process count a best-effort figure. What does not exist is a published baseline: no official per-resource or per-provider memory or CPU numbers were found, and the one first-party cost thread, issue 151 on capturing the provider memory footprint, was closed as outdated once provider families arrived, with a collaborator adding that the large monolithic provider packages are discouraged. That absence of figures means only that none were found. The consequence is that generated providers share the behavior and bugs of their generator, which matters when you hit a quirk in one provider and find it in all of them. [[entities/upjet]], [[findings/upjet-supports-three-terraform-execution-modes-selected-per-resource-configuration]], [[findings/upjet-cli-mode-keeps-a-terraform-workspace-per-resource-and-shares-a-forked-provider-process-until-an-invocation-ttl]], [[findings/no-official-upjet-memory-or-cpu-figures-exist-and-the-memory-footprint-issue-was-closed-as-outdated-by-provider-families]], [[examples/upjet-issue-263-reports-a-shared-terraform-provider-stuck-at-its-invocation-limit]], [[examples/upjet-issue-754-reports-the-plugin-framework-connector-re-running-provider-configure-on-every-reconcile]] and [[findings/generated-provider-catalogs-inherit-the-behavior-and-bugs-of-their-generator]]

Credentials deserve their own attention. A provider controller acts with its own cloud identity, not with yours. The Config Connector documentation states this plainly for Google's equivalent, and the same logic holds for every provider: permission to create the Kubernetes object is effectively permission to change cloud resources with the controller's identity. Kubernetes RBAC on the custom resource therefore becomes your cloud authorization boundary. Crossplane's mitigation is one `ProviderConfig` per account so that different objects use different credentials. See [[findings/anyone-who-can-create-a-provider-managed-object-gets-the-controllers-cloud-permissions]] and the open trade-off in [[decisions/scope-provider-credentials-per-namespace-or-cluster-wide]], where a single identity is simple to operate but needs the union of everyone's permissions, and scoped identities limit damage at the cost of more configuration.

The original provider-aws was a single monolith that registered a CRD for every AWS service, passing 900 CRDs, and the Crossplane blog reports it could leave the API server unresponsive for up to an hour. The project answered with provider families: scoped providers per service, grouped into a family that shares a common configuration provider so credentials are defined once. An operator installs only the member providers for the services in use, and the dossier reports this cuts a typical user from more than 900 CRDs to about 176, at the cost of about 9 provider pods instead of 2. The fewer-CRDs-for-more-pods trade is real, and the family idea needed no new user-facing concept, which is why the project chose it over CRD filtering or lazy loading. [[examples/crossplane-provider-families-let-operators-install-only-the-cloud-services-they-use]], [[findings/splitting-a-provider-into-a-family-trades-fewer-crds-for-more-pods-and-memory]] and [[decisions/split-a-large-provider-into-families-or-filter-or-lazy-load-its-crds]]

## 4. Managed resources: forProvider, external names, management policies and deletion policies

A managed resource has a consistent skeleton regardless of which cloud thing it represents. The field `spec.forProvider` holds the desired state and is the source of truth: the Crossplane documentation says Crossplane "considers the `forProvider` field of a managed resource the 'source of truth' for external resources," so a change made in the cloud console is reverted on the next poll. The field `status.atProvider` holds what the provider last observed. The field `spec.initProvider` holds values applied only at creation. The annotation `crossplane.io/external-name` records which cloud resource this object maps to; a VPC called `my-test-vpc` in Kubernetes may have the external name `vpc-01353cfe93950a8ff`, because the cloud assigns its own identifier. Without a stable link like that, the controller could not find the resource again. Where the external name comes from depends on the kind. The managed resources page says providers give external resources the same name as the Kubernetes object by default, and that is true for kinds whose cloud name the user chooses, such as an S3 bucket, an IAM role or an EKS cluster. Upjet-based providers implement it with a name initializer that sets the external name to `metadata.name` when none is given, and each resource's configuration can switch that off. For kinds where the cloud assigns the identifier, such as an AWS VPC, subnet, security group, instance or KMS key, the configuration uses `IdentifierFromProvider`, so the external name stays empty until the create call returns and the provider records the identifier the cloud chose. The wiki read this from provider source on main and sampled only some kinds, so it is a mechanism with examples and not a complete per-kind table. It matters because a name you can predict before the first create lets a retried create find the same resource, whereas a provider-assigned identifier leaves a window in which the resource exists in the cloud but not yet in the annotation, which is the window the create-pending safeguard in sections 8 and 11 exists to cover. [[concepts/managed-resource]], [[sources/research-managed-resource]] and [[findings/crossplane-external-names-default-to-the-object-name-only-for-name-based-kinds-and-upjet-providers-switch-the-default-off-for-provider-assigned-ids]]

The role of `initProvider` is easiest to see with an example. A Crossplane EKS node group declares an initial `desiredSize`, and a cluster autoscaler later changes the size. If the size lived in `forProvider`, Crossplane would reset it on every reconcile and the two controllers would fight forever. Putting the initial size in `initProvider` means Crossplane applies it once and then leaves it alone. The general lesson is that a drift-correcting reconciler is correct only for fields the declaration owns, and a field that another writer manages must be left out of the enforced set. [[examples/crossplane-initprovider-lets-an-autoscaler-own-node-group-size]] A related issue is late initialization: cloud providers fill in default values you never set, and a naive comparison would treat them as drift. Crossplane keeps those fields optional and offers a `LateInitialize` policy so the provider's value is copied into spec deliberately. [[findings/late-initialized-fields-create-false-drift]]

The `spec.managementPolicies` list says which verbs the controller may use: Observe, Create, Update, Delete and LateInitialize, with `*` meaning all and being the default. The consequence is that several distinct operational needs become one field. `["Observe"]` gives read-only import or a permanent reference. A list without Delete means "manage this, but leave the cloud resource if the object is deleted." An empty list pauses reconciliation. The `crossplane.io/paused: "true"` annotation also pauses. The feature started as a three-value enum (FullControl, OrphanOnDelete, ObserveOnly) in a design document and shipped as a list, and the feature is labelled beta in the v2.5 documentation as well as in the import guide. No single official table maps the old enum values onto the new list, so the mapping above is assembled by the wiki from three sources. The older `deletionPolicy` field, with values Delete (default) and Orphan, still exists on the cluster-scoped managed resources that carry over from v1, and on those legacy resources a deprecated resolver in crossplane-runtime combines the two fields, so the cloud resource is deleted only when both the deletion policy and the management policies allow it. Crossplane issue 5283, "Deprecate DeletionPolicy", was opened on 2024-01-25 and was still open on 2026-11-26. A contributor wrote there that the project "never actually deprecated it, just added a note that we plan to deprecate", and a maintainer agreed that formal deprecation is a first step toward graduating management policies. Meanwhile Crossplane v2.0.0, released in August 2025, removed `deletionPolicy` from the new namespaced managed resources, and the v2.5 managed resources page never mentions it. The field is therefore gone from the docs and from new API types but was never formally deprecated on legacy managed resources, so older advice has to be translated. [[examples/crossplane-issue-5283-has-left-deletionpolicy-deprecation-open-since-2024]] [[findings/older-observeonly-and-deletionpolicy-advice-needs-translation-to-managementpolicies]] and [[decisions/choose-management-policies-for-an-imported-resource]]

Two guardrails complement these. First, Usages: a `Usage` object marks one resource as in use by another, and deletion of the used resource is blocked until its users are gone. The documentation lists the fields `of`, `by`, `reason` and `replayDeletion`, and the stated purpose is ordering deletion so a resource is not deleted before its dependents. The `reason` field lets an operator protect a resource from accidental deletion without naming a user. Usages add ordering and protection at the delete verb, while management policies decide whether the delete verb is allowed at all, so the sources present them as complementary. An admission webhook is an HTTPS service that the API server calls before it accepts a create, update or delete, and which can approve or reject the request; a ValidatingWebhookConfiguration is the object that tells the API server which requests to send to which service. The enforcement mechanism is worth knowing, because it is Crossplane's only remaining admission webhook. Core installs one ValidatingWebhookConfiguration named `crossplane-no-usages` that fires on DELETE for any object carrying the label `crossplane.io/in-use=true`, and its failure policy is `Fail`, so while the webhook is unreachable such deletes are refused, which is the safe direction for a protection feature. The Helm chart lets operators set it to `Ignore` for managed Kubernetes services that reject `Fail`-policy webhooks with wildcard rules, and its comment names an AKS cluster stop as the case. Older Crossplane served validating webhooks for CompositeResourceDefinitions and Compositions too, but the init code now removes them with the comment that Crossplane "now uses CEL validation", meaning the same checks run inside the API server as rules in the CRD schema and no longer depend on a webhook pod being up. The files were read on the default branch, which can run ahead of the v2.5.0 tag. [[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]], [[examples/crossplane-no-usages-webhook-blocks-deletes-of-resources-labelled-in-use]] and [[findings/crossplane-core-ships-one-fail-closed-usage-webhook-and-replaced-its-xrd-and-composition-webhooks-with-cel]] Second, Crossplane deliberately does not delete and recreate a resource to change an immutable field, which is what Terraform does. A change to such a field in `forProvider` may simply not take effect, which is safer for stateful resources and surprising to people who expect Terraform semantics. [[findings/crossplane-does-not-delete-and-recreate-to-change-immutable-fields]]

## 5. Composite resources, XRDs and claims, and the v2 namespaced model

A managed resource is one-to-one with a cloud thing, which is too low-level to hand to application developers. A composite resource, or XR, represents a set of resources as one Kubernetes object. The Crossplane documentation's own wording is that "a composite resource, or XR, represents a set of Kubernetes resources as a single Kubernetes object." A controller expands the small object into the lower-level ones, keeps them reconciled, wires values from one into another, reports aggregate readiness and tears everything down. This is the ordinary controller pattern applied one level up, because the world being reconciled is a set of other API objects. [[concepts/composite-resource]]

Crossplane splits the idea across two objects. A CompositeResourceDefinition, or XRD, declares the schema of your new API: its `group`, `kind`, `plural`, a list of versions and a `scope`. Crossplane generates a CRD from it, so the platform team authors a brand new Kubernetes kind. The XRD's name must be `<plural>.<group>`, the group and names cannot change after creation, breaking schema changes should ship as a new XRD or through a conversion webhook, and the dossier notes schema edits may need a Crossplane pod restart. The Composition, covered in the next section, says how an instance of that API becomes composed resources. The pairing lets one API have several implementations. [[entities/crossplane]] and [[findings/platform-api-schemas-are-contracts-and-breaking-changes-are-blocked-or-need-conversion]]

Here is a deliberately small, illustrative XRD for a Crossplane v2 style namespaced API. The wiki records the v2 default scope and the group, kind and version fields, but the dossier read the XRD page only through summaries, so check field names against the live documentation before copying it.

```yaml
apiVersion: apiextensions.crossplane.io/v2
kind: CompositeResourceDefinition
metadata:
  name: storageapps.platform.example.org
spec:
  scope: Namespaced
  group: platform.example.org
  names:
    kind: StorageApp
    plural: storageapps
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: string
                  enum: [small, medium, large]
```

The snippet declares a new kind called `StorageApp` in the group `platform.example.org`, scoped to a namespace, with one field, `size`, restricted to three values. The point of the enum is the platform idea: developers choose a size class, and the platform team decides what "medium" means in cloud terms. JFrog's engineering blog describes exactly this guardrail, with predefined small, medium and large classes preventing over-provisioning, and tags recording an owner and an expiry so forgotten environments can be cleaned up. [[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]

In Crossplane v1, composites were cluster-scoped, so tenants could not own them from their namespaces. The fix was the claim: if the XRD set `claimNames`, an application team could create a claim in its own namespace, and Crossplane created a cluster-scoped XR and linked the two with `spec.resourceRef` on the claim and `spec.claimRef` on the XR. Connection secrets were written to the claim's namespace. Version 2.0 (released in mid-August 2025; the wiki records 12 August on one page and 14 August on others) made XRs namespaced by default, removed the claim and XR split for new-style XRDs, let a Composition include any Kubernetes resource and not only Crossplane-managed ones, removed native patch-and-transform, `ControllerConfig` and the alpha external secret stores, and has no automated migration for v1 cluster-scoped composites. Upgrades must start from v1.20. One caution from the wiki: the claim rows come from v1.20 pages, and an earlier draft of the v2 picture rested partly on a third-party blog. The later read of the shipped v2 XRD, described a few paragraphs below, settled the main question: claims are not available on a v2 XRD at all, and keeping them means keeping a v1 XRD, which is deprecated but still served. [[comparisons/crossplane-v1-claims-versus-v2-namespaced-composite-resources]], [[examples/a-v1-crossplane-claim-fronts-a-cluster-scoped-composite-resource]] and [[findings/crossplane-v2-removed-features-and-offers-no-automated-migration-for-v1-composites]]

The v2 scope matters for tenancy. A namespaced XR can compose only resources in its own namespace, with `Cluster` as the alternative scope, and the tenant boundary moves onto the XR itself. A word of caution about a third value you may see: the v2.5 documentation table lists `LegacyCluster` ("cluster-scoped with support for claims, v1 compatibility mode") right beside `Namespaced` and `Cluster`, which makes it look like a choice a v2 XRD can make. The shipped CRD says otherwise. The v2 version of the XRD API (`apiextensions.crossplane.io/v2`) enumerates only `Namespaced` and `Cluster`, defaults to `Namespaced`, and rejects `claimNames` with a validation rule. `LegacyCluster` exists only on the v1 XRD API, whose scope defaults to it and which alone may offer claims. Keeping claims therefore means keeping a v1 XRD, which is deprecated in its own CRD but still served, and no removal date was found. Claims are still maintained: v2.4.0 strips XR machinery fields when syncing a claim to its XR, and v2.5.0 makes a claim fail reconciliation if its XRD lookup fails. Legacy cluster-scoped XRs cannot compose namespaced resources. [[findings/the-crossplane-xrd-docs-list-legacycluster-beside-v2-scopes-although-it-exists-only-on-the-v1-xrd-api]] This is why the Crossplane 2.0 announcement can sketch a `Microservice` kind whose one namespaced object creates an RDS instance, security groups, a Deployment, a Service, an Ingress and monitoring dashboards. The dossier stresses this is an illustration from the Crossplane authors and not a named customer. [[examples/a-microservice-xr-creates-a-database-and-its-workload-from-one-namespaced-object]]

An XR carries per-object controls in its spec and annotations. It selects a Composition with `compositionRef` or `compositionSelector`, follows revisions automatically (a CompositionRevision is an immutable snapshot of a Composition, created each time the Composition changes) or pins one with `compositionUpdatePolicy: Manual` and a revision reference, can be paused with `crossplane.io/paused`, takes a per-XR poll interval, and can be forced to reconcile with the `crossplane.io/reconcile-requested-at` annotation. [[concepts/composite-resource]]

## 6. Compositions and composition function pipelines, with CEL, Go templating and Python or KCL examples

A Composition holds the platform team's opinions. In current Crossplane, "a Composition is a pipeline of composition functions." A function is installed as a package and runs as a pod. On each reconcile Crossplane calls the steps in order over gRPC (a binary remote-procedure-call protocol, so the function is called like a local method even though it runs in another pod), giving each a request that holds the observed state of the XR and its owned resources, the desired state accumulated by earlier steps, per-function input and shared context. Each function returns the new desired state. The documentation summarizes it as "a function's main job is to update the desired state and return it to Crossplane," and crucially the function never talks to the API server itself; Crossplane applies the result with server-side apply and re-observes on the next loop. Server-side apply is a Kubernetes feature in which the API server itself tracks which manager owns which fields of an object, so several writers can share one object without silently overwriting each other, and a field that a manager stops asking for can be removed. Each manager is identified by a field owner name, and the wiki's source reading gives the names Crossplane uses: on the main branch the composite reconciler applies `resourceRefs` and status with forced ownership under the field owner `apiextensions.crossplane.io/composite`, while composed resources are applied under per-composite owners with the prefix `apiextensions.crossplane.io/composed`. "Forced" matters here because an ordinary server-side apply that touches a field owned by someone else is rejected as a conflict, whereas a forced apply takes the field over, so any other controller that writes the same fields will lose them to Crossplane at the next pass. That is the mechanism behind the external-writer report discussed in section 11. The v1.20 server-side apply concept page has no v2.5 successor, so the details here come from source and not from current documentation. [[examples/a-composition-function-pipeline-turns-observed-state-into-desired-state]], [[concepts/server-side-apply-and-field-ownership]] and [[entities/crossplane]]

The history explains the design. The first authoring model was patch and transform, a static list of base resources plus patches, deliberately not Turing complete. It had no conditionals, no loops and no dynamic lookups, and the design document wanted to "avoid organically growing a new configuration Domain Specific Language." Composition functions arrived as alpha in v1.11 and beta in v1.14, and native patch and transform (`mode: Resources`) was deprecated in v1.17 and removed in v2, with `function-patch-and-transform` and a `crossplane beta convert pipeline-composition` command as the migration path. Imagine Learning's patch-and-transform files for an AWS RDS cluster ran past 1,000 lines, around 1,250 for a two-instance cluster, with near-duplicate files for different instance counts. They moved to one function that loops over `instanceCount`. VSHN hit the same limits and uses functions to drive Helm charts and share backup logic across service types. [[concepts/composition]], [[examples/imagine-learning-replaces-thousand-line-patch-and-transform-files-with-a-looping-composition-function]] and [[findings/patch-and-transform-cannot-branch-loop-or-patch-between-composed-resources]]

Here is a sketch of a pipeline Composition using Go templating. The wiki names `function-go-templating` and `function-auto-ready` but does not reproduce their schemas, so treat the field names as illustrative and confirm them against each function's own documentation.

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: storageapp-aws
spec:
  compositeTypeRef:
    apiVersion: platform.example.org/v1alpha1
    kind: StorageApp
  mode: Pipeline
  pipeline:
    - step: render-resources
      functionRef:
        name: function-go-templating
      input:
        apiVersion: gotemplating.fn.crossplane.io/v1beta1
        kind: GoTemplate
        source: Inline
        inline:
          template: |
            apiVersion: s3.aws.upbound.io/v1beta1
            kind: Bucket
            metadata:
              annotations:
                gotemplating.fn.crossplane.io/composition-resource-name: bucket
            spec:
              forProvider:
                region: eu-west-1
    - step: mark-ready
      functionRef:
        name: function-auto-ready
```

The Composition says "when a `StorageApp` appears, run these two steps." The first renders a bucket as a composed resource, and the second marks the composite ready once every composed resource reports ready. `compositeTypeRef` is how the Composition is matched to the XRD's group and kind. Because the template is real code you can add conditionals and loops, but the wiki records a cost: a Go-template Composition needs hand-written creation order and guards against deleting resources when a dependency is briefly unavailable. [[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]

Python and KCL are supported authoring languages, along with CUE and custom functions in Go or Python, and the dossiers confirm the list but give no code. KCL is a typed configuration language: it looks like a configuration file but has schemas, type checking, conditionals and loops, so a team that wants stronger guarantees than a text template provides, without writing a full program, might choose it. A Python function has the same contract as every other function: read the request, add resources to the desired state, return the response. The sketch below is untested pseudocode written to show that contract. It is not drawn from the wiki, and the wiki has not verified it against the function-sdk-python documentation. The real Python SDK may have you subclass a function runner and implement a `RunFunction(self, req, rsp)` method, but the wiki has not confirmed the exact class and method names, and the real SDK's names may differ from the ones invented here. Treat every identifier in the sketch as a placeholder, and check the SDK's current API before relying on any of it.

```python
# Untested pseudocode: shows the contract, not the SDK's exact API.
class FunctionRunner:
    def RunFunction(self, req, rsp):
        # Start from the desired resources earlier steps already produced,
        # so nothing they added is dropped from the response.
        for name, res in req.desired.resources.items():
            rsp.desired.resources[name] = res

        size = req.observed.composite.resource["spec"]["size"]
        replicas = {"small": 1, "medium": 2, "large": 3}[size]
        for i in range(replicas):
            rsp.desired.resources[f"node-{i}"].resource.update({
                "apiVersion": "ec2.aws.upbound.io/v1beta1",
                "kind": "Instance",
                "spec": {"forProvider": {"region": "eu-west-1"}},
            })
        return rsp
```

The idea is that a loop does what a thousand duplicated lines used to do. The first loop copies the incoming desired resources into the response, which is the rule described next made visible in code; an SDK may pre-seed the response from the request for you, but the wiki could not confirm that, so the sketch does not assume it. Note one rule that applies to every language: the function must carry forward everything already in the desired state, because a resource omitted from the returned desired state is deleted. VSHN discovered this in the alpha ("if an object is not explicitly specified in a request payload, it will be deleted"). The mitigation is to start from the incoming desired state, change only your own parts, and test with `crossplane render` so an accidental omission shows up before it reaches a cluster. [[findings/a-composition-function-that-omits-a-resource-from-its-desired-state-deletes-it]]

CEL, the Common Expression Language, enters through kro. CEL is a small expression language that terminates by design, has no side effects and is type-checked at apply time. kro's ResourceGraphDefinition (RGD), the single object in which a kro user declares an API's schema, resource templates and expressions, uses it inside `${...}` expressions to reference fields across resources, from which kro infers a dependency graph. The wiki has no source on a Crossplane-native CEL function, so this document does not describe one. What it does record is `function-kro`, announced by Upbound on 2026-03-19, which embeds kro's graph builder and CEL evaluator so a kro-style `resources` block can run as a Crossplane pipeline step. The announcement's example is a `NetworkingStack` API where one step calls `function-kro` with a VPC, a Subnet and a SecurityGroup wired by CEL so that the subnet reads the VPC's identifier, followed by `function-auto-ready`. The example below is an illustration of the idea with an invented schema, not a copy of the announcement, and the exact schema is left to the project's post:

```yaml
pipeline:
  - step: graph
    functionRef:
      name: function-kro
    input:
      # kro-style resources block; subnet reads the VPC id via CEL
      resources:
        - id: vpc
          template: { kind: VPC }
        - id: subnet
          template:
            kind: Subnet
            spec:
              forProvider:
                vpcId: ${vpc.status.atProvider.id}
  - step: ready
    functionRef:
      name: function-auto-ready
```

The key line is the `${vpc.status.atProvider.id}` expression: the subnet is not created until the VPC's identifier exists, which is the inferred ordering. A topological order is simply an order in which every resource comes after the resources it depends on. The project's README says the function embeds kro's graph builder, CEL evaluator and runtime "with full feature parity", and that claim is the project's own, not independently verified. The repository itself qualifies it, though. A file in the repository, `patches/UPSTREAM_DIFFERENCES.md`, opens by listing "where a ResourceGraph behaves differently than the same RGD would in kro". The differences are concrete and worth knowing before you rely on the function. When an existing resource cannot be rendered, the function returns a fatal result and Crossplane applies nothing, so the composite goes `Synced=False`, whereas upstream kro keeps the resource and retries. A hard error in one resource fails the whole run. A resource that is still waiting on its dependencies can still receive template updates. Dependents see rendered values one function pass before they see values the server has set. The composite's status fields are not checked against the XRD, resource scope is inferred and not asked of the API server, Crossplane-owned condition types cannot be set by authors, and creation-time validation of the graph is skipped because, in the file's words, it "requires upstream code that isn't public". Conditions are approximated as well. The function computes `GraphResolved` as always true, sets `ResourcesReady` and `Ready` to whether every resource in this one run was ready, and omits `InstanceManaged`, so an author who relies on kro's four built-in conditions will not find them, and the function writes only the status paths the graph declares to the desired composite so that server-side apply ownership stays narrow. Release v0.4.0, published on 2026-11-26, changed the engine underneath: it imports kro v0.10.0 as a Go module and runs kro's own graph engine, so a resource is now held back until every resource it references is ready, "matching upstream kro". The honest reading is therefore "same engine with a documented list of gaps", not identical behavior. Two further cautions apply. OWNERS.md names a single maintainer, so the bus factor on paper is one, and the wiki found no independent production report of the function. It also found no documentation of a standalone kro controller feeding a Crossplane composite, so chaining the two that way is neither supported nor ruled out by anything read. The wiki did not confirm whether the server-side apply ownership problem described in the repository was fixed in v0.4.0, and it did not map kro's GraphRevisions onto Crossplane's CompositionRevisions. [[entities/function-kro]], [[examples/function-kro-runs-a-kro-resource-graph-as-a-crossplane-pipeline-step]], [[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]], [[examples/function-kro-v0-4-0-moved-onto-the-kro-v0-10-0-graph-engine-on-2026-11-26-with-one-listed-maintainer]], [[findings/function-kro-approximates-kro-built-in-conditions-from-one-run-and-writes-only-declared-status-paths-to-the-desired-xr]] and [[findings/no-documentation-was-found-of-a-standalone-kro-controller-feeding-a-crossplane-composite-and-function-kro-s-readiness-link-is-unlocated]]

Where does the expressiveness limit sit? The wiki's synthesis (the wiki authors' own, since no source compared the two head to head) is that Crossplane fixes the contract and frees the code: any language that serves gRPC works, with no termination guarantee, validation at reconcile time and one pod per function. kro limits the language and frees the runtime: CEL always terminates, definitions are checked when created, and no external function servers exist, but logic beyond CEL cannot be expressed. [[comparisons/where-the-expressiveness-bound-sits-in-crossplane-functions-and-kro-cel]]

Functions run as long-lived pods, and Crossplane reaches them through a headless Service. An ordinary Kubernetes Service gives a set of pods one virtual IP that load-balances across them, whereas a headless Service has no virtual IP and instead lets a client resolve the individual pod addresses directly. That suits gRPC, which keeps long-lived connections and does its own balancing. The connection between Crossplane and a function pod is secured with mTLS, mutual TLS, in which both sides present certificates and verify each other. The effect is that traffic between them is encrypted and each side can confirm the other's identity, which matters because a function receives the observed state of the composite and everything it owns. [[concepts/composition]]

It helps to know that this runner design is the second one Crossplane tried, because older posts describe the first. In alpha, from Crossplane v1.11.0 (published 2023-01-31), a function was a run-to-completion container started by an `xfn` sidecar inside the Crossplane pod, which ran each function in a rootless container, and the design document records that no alternative runners appeared. The beta design in v1.14.0 (published 2023-11-01) turned a function into a long-running gRPC server that the package manager deploys as an ordinary Kubernetes Deployment, reached through the headless Service and secured with mTLS, and the release notes state plainly that the new implementation "is incompatible with existing `v1alpha1` functions", so an alpha adopter had to rebuild functions as gRPC servers distributed as packages before upgrading. Functions graduated to v1 in v1.17.0 (2024-08-29), and native patch and transform was removed in v2.0.0. The wiki read release notes and source and no named adopter's migration, so it does not claim any adopter's experience, and whether any `xfn`-style wrapper that runs a container per Deployment is still maintained was not confirmed. The contract also differs from the better-known KRM function standard. A KRM function, as defined by the specification in the Kustomize repository and used by kpt and Kustomize, must be a container that reads a `ResourceList` document from standard input, writes one to standard output and signals failure with a non-zero exit code, so every invocation is a short-lived container. Crossplane's contract is the `RunFunction` call in a protobuf service whose request carries observed state, desired state, required resources and schemas, and whose server stays running. A KRM function therefore cannot be dropped into a Crossplane pipeline without a wrapper, and the reverse is also true. The difference has a practical upside for Crossplane: because its functions run in the cluster, it avoids the container-runtime requirement that makes KRM functions awkward on laptops and in CI, and kpt and Kustomize run functions without containers only through opt-in exec extensions (`--allow-exec` for kpt, `--enable-alpha-plugins --enable-exec` for Kustomize) whose own documentation discourages them because there is no sandbox. [[findings/crossplane-moved-composition-functions-from-an-xfn-sidecar-in-v1-11-to-package-manager-deployments-in-v1-14]], [[examples/crossplane-v1-14-0-shipped-beta-functions-on-2023-11-01-and-broke-compatibility-with-alpha-functions]], [[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]], [[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]] and [[findings/kpt-and-kustomize-run-functions-without-containers-only-through-opt-in-exec-extensions-that-both-docs-discourage]]

Composites are polled every 60 seconds by default, which is the figure the composition dossier reports for composite resources, and every poll of a composite makes one gRPC call for each step in its pipeline. Call volume therefore grows with the number of composites and not with the amount of change happening. A hundred composites with a single step make about a hundred calls a minute even when nothing is changing, and a larger fleet or a longer pipeline multiplies that, which is why function replicas, the poll interval and response caching come up as tuning levers in section 12. Composition functions also do not run when a composite is deleted, so Crossplane deletes the composed resources itself. [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]

The local testing loop has three rungs, and it pays to use the cheap ones first. `crossplane render` runs a Composition and its functions on your laptop against a sample composite and prints the desired resources, with no cluster involved, so it catches a mistake such as an omitted resource in seconds. Ordinary unit tests of the function's own code come next. The slow rung is an end-to-end loop that uses Kuttl (a declarative test runner that applies manifests and asserts on the resulting cluster state), a kind cluster (Kubernetes running inside local Docker containers) and Skaffold (a tool that rebuilds and redeploys your function image on each change), where each run takes 2 to 5 minutes. That delay matters because it is the cost of every iteration spent debugging against a live cluster, and it is the reason to push as much checking as possible into the fast rungs. [[concepts/composition]]

Finally, functions are packages, and a package can be pinned by its OCI digest, the content hash of the image in a container registry, rather than by a mutable tag. It is tempting to assume that each Composition revision references specific function digests, so that composites pinned to older revisions keep running the old function, but that holds only for one alpha feature. In the ordinary case a pipeline step uses `functionRef`, which calls whichever Function revision is currently active, and the Composition revisions documentation says that upgrading a Function affects every CompositionRevision, "including revisions you've pinned XRs to with the `Manual` update policy." Pinning a composite to a Composition revision therefore freezes the pipeline definition but not the function code behind a `functionRef` step. Only the alpha feature enabled with `--enable-pipeline-oci-references` lets a step name a function package by digest in its `function` field. With it on, Crossplane creates external FunctionRevisions owned by the CompositionRevision, several external revisions of the same Function can be active at once, and they are listed in the Function's `status.externalRevisionRefs`. Only that mode supports a staged rollout in which a few composites move to a new function build while the rest keep the old one. Without it, a function upgrade reaches every composite at once, whichever update policy they use, so test function changes with `crossplane render` and in a non-production control plane first. Two related alpha controls are worth knowing: function response caching, enabled with `--enable-function-response-cache` since v1.20.0, and a `credentials` field on pipeline steps since v1.16.0. The wiki saw but did not read a one-page design note on controlled rollout of function changes added in the v1.20.0 notes. [[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]], [[decisions/choose-automatic-or-manual-composition-update-policy]] and [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]

## 7. Status, Synced and Ready conditions, and observing long-running operations

Conditions are the standard way a Kubernetes controller reports state: a list of entries in `status.conditions`, each with a type such as `Ready`, a status of True, False or Unknown, a reason and a message. They let humans and other tools read status without knowing the controller's internals. See [[concepts/conditions]].

Crossplane managed resources use two. `Ready` says whether the external resource is operational, with reasons `Available`, `Creating`, `Unavailable` and `Deleting`. `Synced` says whether the provider's last reconcile succeeded, with reasons `ReconcileSuccess`, `ReconcileError` and `ReconcilePaused`. Read together they diagnose different problems: `Synced=False` points at credentials, configuration or provider trouble, while `Ready=False` with `Synced=True` points at the cloud side, which is the normal state while a database is provisioning for several minutes. A composite resource becomes `Ready` only when its function pipeline reports that every composed resource is ready, and the v2.5.0 source says precisely what "reports" means. Each desired resource in a function's response carries a ready flag with three values, `READY_UNSPECIFIED`, `READY_TRUE` and `READY_FALSE`, and Crossplane counts a composed resource as ready only when the value is `READY_TRUE`, so an unspecified value is treated the same as false. The composite reconciler then collects every composed resource that is not ready, and sets the XR's `Ready` condition to `Available` when that list is empty and to `Creating` with the message "Unready resources: ..." otherwise, with `Synced` set to `ReconcileError` and an "Unsynced resources: ..." message if any composed resource is not synced. The practical consequence is that a pipeline which composes healthy resources but has no function setting `READY_TRUE` leaves the XR in `Creating` forever, and the cause lies in the pipeline and not the provider. That is why the pipeline in section 6 ends with `function-auto-ready`: it leaves alone any resource that already carries an explicit flag, and for the rest it runs optional CEL queries and built-in health checks for standard Kubernetes resources before falling back to checking that the observed object has a `Ready` condition equal to True. A TODO comment in the source asks whether an unspecified value should derive readiness from the resource's own condition, so this behavior may change. When an XR is stuck, read the "Unready resources" message first, since it names the culprits. This also marks a difference from kro, where the controller computes an instance's `Ready` from the graph and the author does not write a function for it. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]] Crossplane's two-condition split is the clearest attempt in the wiki's survey to separate "the platform is broken" from "the cloud resource is still coming up." [[comparisons/health-and-readiness-models-across-tools]] and [[examples/crossplane-database-claim-reports-synced-and-ready]]

Two failure patterns are worth memorizing. In the first, `Synced=False` with `Ready=True` means the thing exists but Crossplane can no longer manage it, typically because credentials expired or permissions were removed. Applications keep running, so nothing user-visible breaks, but drift is not corrected and spec changes are not applied. Teams that alert only on `Ready=False` will not notice, so alert on persistent `Synced=False` as well. [[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]] In the second, `Synced` stays `True` while a long asynchronous operation runs. Provider-aws issue 2287 reports an MSK (Kafka) update that took over an hour during which the resource said "up to date" and crossplane-runtime overwrote the pending state with `ReconcileSuccess`. Upjet-based providers add an `AsyncOperation` condition that reads `False` with reason `Ongoing`, but it sits outside the usual alert surface. A later check found no fix. The issue was opened on 2026-03-11, marked stale on 2026-06-10 and closed on 2026-06-25 by the stale bot with no maintainer comment and no linked change, so its closure does not mean the behavior was repaired. Reading the source on 2026-11-26 explains why: Upjet's async client reports the resource as existing and up to date while an operation is ongoing, and crossplane-runtime's managed reconciler, on an up-to-date observation, takes the branch that records `ReconcileSuccess`. The latest releases read were Upjet v2.5.1 and crossplane-runtime v2.5.0, and a search of Upjet, crossplane-runtime and provider-aws found no change that sets `Synced=False` or otherwise surfaces in-flight async work. An open pull request, 8080 (opened 2026-11-20), has now been read in full, and it does not address this case. It guards the composite's status write with a resource version so that a lagging cache cannot replay old conditions. That is a separate bug in which v2.5.0 writes an XR's status twice per pass, a server-side apply patch built from the cached copy and then a status update, so a cache that trails the API server publishes stale conditions that the second write corrects. Open issues 7062 and 8033 describe the resulting flapping and the extra watch events, the reporter sees it back to 2.1.x, and the fix is not merged and not in v2.5.0, which was released on 2026-11-24. Practically, a single brief `Ready` or `Synced` flip on an XR may be noise, so alert on a condition that persists. The v2.5 docs list `AsyncOperation` and `LastAsyncOperation` as provider-specific detail and not as an alerting recommendation, and docs and code disagree on the status value `AsyncOperation` carries, so check a live resource before writing an alert on it. [[findings/upjet-and-crossplane-runtime-source-still-reports-reconcilesuccess-while-an-async-operation-runs]], [[findings/crossplane-v2-5-0-writes-xr-status-twice-so-a-lagging-cache-can-replay-old-conditions]], [[examples/crossplane-pull-request-8080-guards-the-xr-status-write-with-a-resource-version-to-stop-stale-condition-replay]] and [[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]]

Other stacks draw this line differently. ACK splits terminal from recoverable errors into separate conditions, `ACK.Terminal` and `ACK.Recoverable`, plus `ACK.ResourceSynced`. Config Connector packs everything into a single `Ready` with reasons `Updating`, `UpToDate` and `UpdateFailed`. A caution on that last name: Config Connector's design document proposes `UpdateFailure`, but the code at release v1.162.0 (2026-11-23) ships `UpdateFailed`, and Argo CD's own health script for Config Connector matches `UpdateFailed`, which corroborates the shipped spelling. The same read found no trace of the design document's first-field-path failure message or its `Updating:<operation-id>` reason, so anything built from the design alone would match the wrong strings, and because `Ready=False` covers both an update in flight and a failed one, a consumer has to read the reason. Flux uses `Ready`, `Reconciling` and `Stalled`, where `Stalled` means no progress without a change. Those names also show the polarity choice that every condition vocabulary makes. `Ready=True` is a positive condition, where true means healthy, whereas `Reconciling` and `Stalled` are abnormal-true conditions, where true means something needs attention. Neither is simply correct: the Kubernetes API conventions leave the choice to the author, a positive `Ready=False` cannot say whether the object is progressing or doomed, and an abnormal-true scheme makes an absent condition look healthy, which hides a dead controller unless you compare `observedGeneration`, a status field recording the spec generation the controller last acted on, so that a value lagging behind the object's current generation shows the controller has not yet seen the latest change. kstatus is the Kubernetes status-interpretation library, used by tools such as kpt and Flux, that decides from an object's conditions whether it is current, in progress or stalled. A kstatus maintainer explained in cli-utils issue 167 why kstatus names its failure state `Stalled` and not `Failed`: from outside, a slow object and a doomed one are hard to tell apart. [[decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types]], [[examples/cli-utils-issue-167-a-kstatus-maintainer-said-stalled-is-not-named-failed-because-slow-and-doomed-are-hard-to-tell-apart]] and [[findings/config-connector-shipped-updatefailed-with-a-single-ready-condition-and-the-first-field-path-message-and-operation-id-reason-are-not-in-code]]. kro lets the graph author define conditions with CEL and `readyWhen`. Cluster API adds `Available` and operation conditions such as `ScalingUp` and `Remediating`. The wiki's observation is that this variety is why Argo CD needs a custom Lua health check per custom resource kind (a small script that tells Argo CD whether an object of an unfamiliar kind is healthy) and Flux needs CEL health checks (the same idea, written as expressions in the Common Expression Language), and why Crossplane's own guide for Argo CD asks for Lua checks over `crossplane.io` and `upbound.io` resources. That advice has partly been overtaken. On 2026-11-26 the `resource_customizations` tree of Argo CD (v3.6.3) ships built-in scripts for whole provider groups, with wildcard directories for `cnrm.cloud.google.com` (Config Connector), `services.k8s.aws` (ACK), `crossplane.io` and `upbound.io`, plus directories for `kro.run` and five Cluster API kinds, so a team on a recent Argo CD should read the shipped script before writing its own. The scripts show how each tool's vocabulary is translated. The ACK script maps `ACK.Terminal=True` to Degraded, `Ready=False` to Progressing and `Ready=True` to Healthy. The Config Connector script returns Progressing while `observedGeneration` is stale, Healthy on reason `UpToDate` and Degraded on `UpdateFailed`. The Crossplane script marks `Synced=False` or `LastAsyncOperation=False` Degraded, and it treats a list of kinds that never carry conditions as Healthy so that they do not sit at Progressing forever. The wiki read that script only through its first Healthy branch. Flux takes the opposite approach and has no per-provider logic: a Kustomization's `healthChecks` accept kstatus-compatible custom resources, and `healthCheckExprs` supply CEL expressions for kinds that are not, with the Flux CEL cheatsheet listing Crossplane but, as far as the page text showed, neither Config Connector nor ACK. The Flux approach has no wildcard-script risk and no provider-aware help either, and kstatus can read a Crossplane resource that has no initial `Ready` condition as already ready. Flux issue 5855, closed on 2026-04-21, reports exactly that race, and the maintainers answered that controllers should set `observedGeneration` on the `Ready` condition and recommended a CEL expression requiring `e.observedGeneration == metadata.generation`, which the reporter said works although they wanted Flux to handle it. The wiki did not read how kstatus treats ACK's abnormal-true `ACK.Terminal` condition, so whether a terminal ACK error looks failed or ready to Flux is open. In Crossplane's case the condition semantics are fixed by the framework, whereas in kro the author defines them. [[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]], [[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]] and [[examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression]] [[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]] and [[comparisons/provider-fixed-versus-author-defined-condition-semantics-crossplane-versus-kro]]

## 8. Adoption, import and observe-only workflows

Most organizations start with infrastructure that already exists, so adopting a cloud resource without recreating it is a core need. The Crossplane recipe, from the official import guide, uses a GCP Cloud SQL `DatabaseInstance` as its example. You write a managed resource with `managementPolicies: ["Observe"]` and the `crossplane.io/external-name` annotation set to the existing instance's provider-side name. You pick a Kubernetes object name and, if the same name exists in more than one region, add a disambiguating `forProvider` field such as the region. [[examples/crossplane-import-of-an-existing-gcp-database-observes-first-then-takes-control]]

```yaml
apiVersion: sql.gcp.upbound.io/v1beta1
kind: DatabaseInstance
metadata:
  name: orders-db
  annotations:
    crossplane.io/external-name: orders-db-prod
spec:
  managementPolicies: ["Observe"]
  forProvider:
    region: europe-west1
```

This manifest asks Crossplane to look at an existing instance and change nothing. The guide says Crossplane "imports observe only resources but never changes or deletes the resources." Once applied, the provider fills `status.atProvider` with what it saw. You then copy the values you want to own into `spec.forProvider` by hand and change the policies to `["*"]` so the controller may create, update and delete. The two-phase design is the lesson: a safe read-only phase proves the object maps to the right resource before a second phase grants write authority. The hazards are the manual copy, ambiguous names across regions, relaxed validation during Observe, and disabled late initialization. The guide labels management policies a beta feature that providers must support, so the recipe depends on provider support. [[findings/observe-based-import-has-manual-copy-steps-ambiguous-names-and-relaxed-validation]]

Observe is also useful permanently. A composition can read a database owned by another team without ever managing it, for example to hand its connection details to a workload. [[examples/an-observe-only-managed-resource-lets-a-composition-read-a-database-owned-by-another-team]]

Other tools answer the same two questions, "how do I adopt this?" and "how do I keep it when the object goes away?", in different styles. Config Connector acquires a resource implicitly whenever a manifest's name matches, which is convenient for migration but can take over something never meant to be managed, and keeping a resource requires the `cnrm.cloud.google.com/deletion-policy: abandon` annotation set before deletion. Its protection against two objects managing one cloud resource is opt-in. The annotation `cnrm.cloud.google.com/management-conflict-prevention-policy` takes `resource` or `none`, and the documented default is `none`, so out of the box nothing stops two objects in different namespaces from acquiring the same Google Cloud resource, which the documentation calls possible but not recommended. With `resource`, Config Connector stores a lease on the cloud resource as two labels, `cnrm-lease-holder-id` and `cnrm-lease-expiration`, a lease lasts 40 minutes and is renewed while the holder keeps reconciling, and a loser reports `ManagementConflict`. The page lists limits: because the lease lives in labels it does not work for resources that cannot carry labels, two objects in the same namespace that use `resourceID` to name one resource create conflicts Config Connector cannot manage, and resources with service-generated IDs can be acquired only through `resourceID`. The wiki read this from documentation without testing it. ACK splits observation and adoption: an annotation `services.k8s.aws/read-only: "true"` never creates, updates or deletes and errors if the AWS resource is missing, while an adoption feature, with `adopt` (strict) and `adopt-or-create`, gives full management, and `deletionPolicy: Retain` keeps the cloud resource. The wiki's finding on adopt-or-create is that it can take over a look-alike resource and overwrite it to match the spec, and it can now point to reproduced cases and not only the general warning. In ACK issue 3149, run against moto with iam-controller v1.11.3 and so not against real AWS, two custom resources adopted one IAM role, rewrote it on every resync and flipped its trust policy while both reported `Synced` and `Ready`, and deleting either one deleted the role in a few milliseconds before the survivor created a replacement with a new role ID. The reporter's reading is that the annotation "turns off the only guard there is", because without it ACK stops with a terminal "Resource already exists". An open proposal, ACK issue 3143, would record the owner in AWS tags at creation time so the controller could refuse foreign resources, and neither it nor an older tag-check pull request has shipped. In Config Connector issue 14236, open and a reporter's claim with no maintainer confirmation read, acquiring an existing storage bucket removed its CSEK `FullyRestricted` enforcement setting because the CRD has no field for it, and the setting was absent from bulk export, so a diff of exported manifests would not show the change. That case is a risk even for the intended resource, because the declared spec is only a subset of the live settings. The wiki found no accidental-adoption report for Crossplane, but also no production comparison of the three tools' policies, and most of the late-2026 ACK reports come from one reporter, so these cases show the mechanism and not how often it bites. Crossplane's Observe-first flow gives a review step that the implicit paths lack. The SAP BTP provider takes a third path: an explicitly set external name signals the resource should already exist, and the default initializer is removed so a missing name never becomes accidental adoption. The ADR says plainly that this is not an import mechanism. [[comparisons/observe-only-and-keep-controls-across-crossplane-config-connector-and-ack]], [[findings/adopt-or-create-can-take-over-a-look-alike-resource]], [[findings/ack-adopt-or-create-removes-the-only-guard-against-two-custom-resources-owning-one-aws-resource]], [[findings/acquiring-an-existing-cloud-resource-can-strip-settings-the-custom-resource-definition-does-not-model]], [[findings/config-connector-conflict-prevention-defaults-to-none-so-two-objects-can-manage-one-cloud-resource-unless-a-lease-policy-is-set]], [[decisions/adopt-or-create-or-require-explicit-import]] and [[entities/crossplane-provider-btp]]

The reconcile loop also interacts with idempotency, meaning that doing something twice has the same effect as doing it once. Cloud create calls are not always idempotent. The AWS Builders' Library describes the EC2 `ClientToken`: the caller supplies a unique token, the service stores it atomically with the mutation, and a retry returns an equivalent response instead of launching a second instance. Where an API offers such a token a controller can retry freely. Where it does not, Crossplane writes a durable marker, `crossplane.io/external-create-pending`, before the create call and `external-create-succeeded` or `external-create-failed` afterward. That guards against the case where the create succeeds but the status write fails, which could otherwise leak a billed resource. [[examples/ec2-client-token-makes-a-retried-runinstances-call-safe]] and [[findings/a-create-that-succeeds-while-the-status-write-fails-can-leak-an-external-resource]]

## 9. Use cases: self-service databases and clusters, service catalogs, multi-cloud, and who runs it at scale

The dominant use is self-service. A platform team publishes a small API and application teams consume it without cloud expertise or tickets. The JFrog pattern chains four tools, each doing one job: developers ask through a Jenkins-based interface, the interface writes custom resources into Git, Argo CD syncs them into a cluster, and Crossplane reconciles them into real cloud resources. Argo CD sees the platform-level custom resources and not every cloud resource beneath them. The post is an organizational success story and lists no pitfalls, no scale figures and no detail of the Compositions behind the size classes, so it is a pattern illustration and not proof of operational cost. [[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]

Service catalogs are the second pattern. VSHN, a Swiss managed Kubernetes provider that has run Crossplane in production for roughly three years, uses composition functions in its Application Catalog (AppCat), a marketplace where customers self-provision databases, message queues and object storage. The wiki calls it the clearest example of composition as a product catalogue, because one provider sells many service types across clouds from one declarative layer, though it is a single self-reported case with no scale numbers. Its alpha-era lessons were operational: OpenShift's crun runtime initially could not run functions, resources missing from a function response were deleted, and mixing patch and transform with functions for the same objects "increases complexity dramatically." [[examples/vshn-appcat-sells-self-service-databases-queues-and-object-storage-through-composition-functions]]

Governance is a third. The Crossplane blog on designing compositions argues that a platform should expose well-understood features behind its own versioned API rather than pass every provider feature through, because native provider features can break proprietary environments or reduce compliance. Inside a Composition the platform team can apply automated tagging to every composed resource, and "multi-tenant access segregation for resource claims is an excellent pattern for proper cloud governance and security." The blog is vendor-authored and predates v2, so claims, external secret stores and native patch and transform appear in it though v2 removed or changed them. [[examples/a-platform-api-hides-provider-features-to-enforce-tagging-and-tenant-segregation]]

Whole-cluster provisioning is a fourth. RTL Nederland reports on the adopters list that it provisions whole Kubernetes clusters on Azure and AWS with Crossplane, which overlaps with Cluster API's home territory. The entry is self-reported and unverified. It shows that the provisioning layer has no hard border: a general framework can create clusters as managed resources, while Cluster API offers cluster-specific kinds such as `MachineHealthCheck`. [[examples/rtl-nederland-provisions-whole-kubernetes-clusters-with-crossplane-which-overlaps-with-cluster-api]]

Multi-cloud follows from the provider model. Upbound tested a multi-cloud control plane of about 2,000 managed resources and found that installing thousands of CRDs broke both clients and the API server: discovery needed around 300 HTTP requests and hit client-side throttling, OpenAPI computation (the API server building the machine-readable schema document that describes every kind it serves) burned CPU and memory, and hosted control planes hit out-of-memory kills. The fixes included higher kubectl discovery limits, checksum-based caching, lazy OpenAPI computation in Kubernetes 1.23 and shared loggers, and the numbers came through a digest and need checking. [[examples/upbound-tested-a-multi-cloud-control-plane-of-about-2000-managed-resources-and-upstreamed-kubernetes-fixes]] Finally, the wiki notes that the same composite-API idea works for application and infrastructure together, as in the `Microservice` example, and that a scalable composition can expose the scale subresource so HPA and KEDA can drive an XR. The scale subresource is a standard Kubernetes endpoint that lets tools read and set an object's replica count without knowing its other fields. HPA, the HorizontalPodAutoscaler, is the built-in controller that adjusts replica counts from metrics, and KEDA is an add-on that scales from event sources such as queue depth, so both can scale a whole composite through that one endpoint. [[examples/a-scalable-composition-lets-hpa-and-keda-drive-an-xr-through-the-scale-subresource]]

## 10. Design principles to take from Crossplane

The reason to study Crossplane even if you never adopt it is that its design encodes several principles that apply to any platform built on a control plane. Each is argued here from the wiki's evidence.

**Separate the platform API from its implementation.** The XRD defines what users can ask for and the Composition defines how it is fulfilled. Because the API is a versioned contract and the implementation is replaceable, a platform team can move from AWS to GCP, or from one database engine to another, without changing a single consumer manifest. The `function-kro` post phrases the same value as "one schema, many implementations." The cost is that the schema becomes a contract with live consumers, so breaking changes need new versions or conversion webhooks. The wiki's decision page on this frames the choice between a conversion webhook and a new XRD. See [[decisions/conversion-webhook-versus-new-xrd-for-breaking-changes]] and [[comparisons/crossplane-xrds-versus-kro-resourcegraphdefinitions-as-crd-generators]].

**Hide provider features to protect users and the organization.** An API that mirrors the cloud provider's own resource model pushes cloud knowledge onto every consumer. The Polarpoint practitioner blog advises modeling APIs by infrastructure domain, designing for the mental model of the people who use them, and starting with small Compositions and not mega-Compositions. This is opinion without incident data, but it agrees with the contract argument above. [[findings/oversized-compositions-and-cloud-shaped-apis-make-platform-apis-hard-to-use]]

**Status honesty.** Crossplane insists that "exists" and "last reconcile succeeded" are different facts, and it publishes both as separate conditions. A platform that reports one green light hides the cases that matter most: a healthy-looking database that nobody can manage, and a "synced" resource in the middle of a slow update. The lesson is to design status so that operators can distinguish the broken platform from a resource that is still coming up, and then to test that your alerts actually watch both. The wiki's own caveat is that the framework-fixed semantics still leave gaps, such as the MSK case. [[concepts/conditions]]

**Safety by default at the destructive verb.** Deleting the object deletes the cloud resource, so Crossplane layers controls: management policies to omit Delete, Usages to order and protect, a composite deletion policy with Background, Foreground and Pipeline options, and a refusal to delete and recreate for immutable fields. The ambiguous-create behavior follows the same instinct. When Crossplane cannot tell whether a create succeeded, it halts and asks a human rather than risk a duplicate or a leak, and the event reads "cannot determine creation result - remove the crossplane.io/external-create-pending annotation if it is safe to proceed." The wiki's comparison summarizes the spectrum: Crossplane optimizes for never duplicating or leaking and accepts a human step, ACK and Config Connector optimize for convergence and accept the chance of adopting something unintended, and SAP sits between by requiring explicit intent and narrowing recovery with a creation-time window. [[comparisons/ambiguous-create-and-adoption-strategies-across-crossplane-sap-ack-and-config-connector]]

**Modularity of providers.** Provider packages, provider families, activation policies and revisions are all about letting a cluster hold only what it needs. This is a scaling principle as much as a convenience: the unit of installation decides how many CRDs the API server must hold, so packaging is a performance control. [[concepts/scale-and-sharding]]

**Make the expressiveness limit explicit.** Crossplane refused to grow a templating DSL and moved logic into functions behind a fixed gRPC contract, and kro limits the language to CEL. Either way, the design question is where you accept limits so that the system stays understandable. The reasoning is that an unrestricted language invites oversized, hard-to-debug definitions, and a too-small language invites a pile of workarounds. [[comparisons/where-the-expressiveness-bound-sits-in-crossplane-functions-and-kro-cel]]

**Level-triggered correction with a budget.** Reconciliation corrects drift automatically, but every observation of an external resource may cost a cloud API call. Crossplane's `--max-reconcile-rate` flag, from issue 2595 and merged for Crossplane 1.6, replaced scattered knobs (`QPS`, `PollInterval`, `MaxConcurrentReconciles`, `RateLimiter`) with one control whose stated reasoning is that "reconcile rate in Crossplane is a good proxy for average external API call rate." The lesson is to pick the one control that maps to the scarce resource you are protecting. The control has also changed meaning since that 1.6-era design, which is a lesson of its own. Crossplane v2.1.0 renamed the flag to `--max-concurrent-reconciles`, and the v2.5.0 source describes it as "the maximum number of concurrent reconcile operations (worker pool size)" with a default of 100 and `max-reconcile-rate` kept as an alias. The v2.5 Pods guide in the docs repository still says the flag sets the rate, in times per second, at which Crossplane reconciles resources, so the docs and the source disagree. A pool of 100 workers is not a ceiling of 100 reconciles per second: how many cloud calls per second it produces depends on how long each reconcile takes, so the flag no longer states a call budget by itself. A second guard exists for runaway composites, an XR circuit breaker described in the v2.1.0 notes that stops reconciling an XR whose reconciles exceed a token-bucket threshold (a token bucket is a counter that refills at a steady rate and lets a burst through until it is empty, after which work must wait for refills). The v2.1.0 notes give a burst of 50 with one token every two seconds sustained, the v2.5.0 source sets a burst of 100 refilled at 1.0 per second with a five-minute cooldown, and the release in which the default changed was not traced, so quote the version with any number. Providers define their own flags separately, and the docs note that most providers use their own `--max-reconcile-rate`. [[examples/crossplane-max-reconcile-rate-turns-reconcile-rate-into-an-api-call-budget]], [[findings/the-crossplane-v2-5-docs-describe-max-reconcile-rate-as-a-rate-but-source-treats-it-as-a-worker-pool-size-alias]] and [[findings/the-crossplane-xr-circuit-breaker-default-is-burst-100-in-v2-5-0-source-while-the-v2-1-0-notes-say-burst-50]]

## 11. Pitfalls: ambiguous create, deletion data loss, provider removal, live composition edits, immutable fields, credential blast radius

**Ambiguous create.** Crossplane issue 3037 reports managed resources that stop reconciling after a provider restart, including an SQS queue on provider-aws. If the provider restarts between writing `external-create-pending` and recording the result, the next reconcile finds the marker with no outcome and halts. A maintainer explains that many cloud APIs return generated IDs, so with a lost response there is nothing to look up, and a second create could leak the first resource. Looking up by tags needs per-resource code and fails where tagging is unsupported. The issue proposed letting resources with deterministic identifiers opt out, and earlier wiki notes record it as closed as not planned, a wording a later dossier did not restate and that is worth rechecking before you repeat it. The related issue 1863 was closed without a decision. Failing safe does not scale, since every ambiguity needs a person. SAP's alternative searches by a business key within a creation-time window, only when the pending marker is present. [[findings/an-ambiguous-create-result-halts-reconciliation-until-a-human-intervenes]] and [[examples/provider-restart-blocks-a-crossplane-resource-on-external-create-pending]]

The opt-out proposed in that issue did later ship, though not every provider uses it. crossplane-runtime now has a `WithDeterministicExternalName` option: when it is false the reconciler stops with "cannot determine creation result" after an incomplete create, and when it is true the safeguard is skipped because it is safe to re-queue a deterministically named resource. Issue 2251 on provider-upjet-aws, opened on 2026-09-25 and still open when read, reports that the Upjet-generated AWS controllers do not set it, so resources with names the user chooses, such as S3 bucket sub-resources and IAM policies, still wedge. The reporter's trigger was a dropped HTTP/2 connection to the Kubernetes API server while about 500 S3 and IAM resources across 10 environments were created in parallel, which is the reporter's own account, and the wiki did not read the Upjet controller template to confirm it. A related report, provider-upjet-aws issue 2199 from 2026-08-18, describes a provider-aws-eks restart landing inside the 30 to 60 second create window of a `PodIdentityAssociation`. The external name was lost, the next create returned `409 ResourceInUseException` because the first had actually succeeded, and the provider retried three to four times a minute. That case is a stuck retry loop and not a duplicate resource, and the reporter estimated about 155 dollars of GuardDuty analysis cost over 15 days across seven stuck resources on two clusters, an unconfirmed figure. A one-layer-up version of the same stale-read hazard appears in Crossplane issue 6260, opened 2025-02-01, where Crossplane 1.17's cached reads let the composite reconciler create composed Kubernetes objects twice. These are named issues from individual reporters and not organization-authored postmortems, and the wiki found no named postmortem of a leaked or duplicated cloud resource from Crossplane, ACK or Config Connector, so the honest summary is that the mechanism is well documented and the production frequency is unknown. The nearest quantified neighbor is from ACK, the AWS operator discussed in section 13. ACK community issue 3177, opened on 2026-11-13 by one reporter, is that reporter's own audit of ACK code and documentation, not an observed production count, and it states that when a create response is lost, 48 resources in 22 controllers either create a second AWS resource (28) or fail on every following reconcile because the name is already taken (20). The mechanism is the same one Crossplane guards with its pending marker: ACK records the AWS identifier in status only after the create call returns, so a controller that stops before that write leaves an AWS resource its custom resource does not know about. ACK runtime pull request 292, merged on 2026-11-20, moves the status patch to immediately after the create, which narrows the window and does not close it, since a crash between the AWS call and the patch can still lose the identifier. [[findings/provider-upjet-aws-controllers-do-not-set-withdeterministicexternalname-so-deterministically-named-resources-stay-stuck-after-a-transient-error]], [[examples/provider-upjet-aws-issue-2199-a-lost-external-name-after-a-provider-restart-became-a-409-retry-loop-reported-at-about-155-dollars-over-15-days]], [[examples/crossplane-issue-6260-unstructured-caching-in-1-17-let-the-composite-reconciler-leak-composed-resources]] [[findings/an-ack-audit-found-48-resources-in-22-controllers-where-a-lost-create-response-duplicates-the-resource-or-wedges-the-custom-resource]] and [[findings/no-named-postmortem-or-production-comparison-was-found-for-leaked-resources-or-adopt-or-create-versus-explicit-import]]

**External writers on a composite.** Because Crossplane applies XR status and composed resources with server-side apply under fixed field owners, a second controller that writes to an XR can in principle collide with it. Crossplane issue 7453, opened on 2026-05-31 against v2.3.1 with function-go-templating, reports exactly that: a field applied to an XR by an external controller with `--force-conflicts` disappeared within one reconcile, and `managedFields` looked empty afterward. (`managedFields` is the metadata list in which the API server records which manager owns which field of an object, and it is what lets server-side apply tell a legitimate write from a conflicting one.) The only maintainer comment, on 2026-08-27, says the behavior could not be reproduced on v2.3.1 for either a namespaced XR or a legacy claim, and suggests that `kubectl get -o yaml` hides `managedFields` unless `--show-managed-fields` is passed. The issue was still open and labelled stale on 2026-11-26, and two community pull requests that assert a root cause remain unmerged. Pull request 7787 ("preserve managedFields in SSA patches") has no discussion, and 7783 is labelled stale with a changes-requested review, so neither has been accepted by a maintainer. Both say the function pipeline's `FromStruct()` call replaces the whole XR object map and so loses `managedFields`, which would break ownership tracking. A later read of the v2.5.0 source is inconclusive and not a refutation. It does find that the XR status apply replaces the XR content with the function's desired composite and then resets identity fields, with a comment that Crossplane needs "to pass in only our fully specified intent". But that apply goes through the status subresource and sends only status, conditions and deletion policy, and the resource-reference patch touches only `resourceRefs`, so the reading found no path that prunes a `spec` field owned by another manager, and therefore does not explain the reported loss of `spec.externalRef`. The finalizer-update and claim-propagation write paths were not traced, no cluster was run, and no one has reproduced the report, so whether the bug is real is unverified. The two competing pull requests show that contributors suspect the `FromStruct` path, which is evidence about their belief and not about behavior. Treat this as a reported and unreproduced case: it does not show that Crossplane drops external writers, and it does not show that it is safe for them either, and no v2.5 docs page describes server-side apply behavior for XRs. If you need a second controller to write to an XR, test with `--show-managed-fields` on your own version first. [[examples/crossplane-issue-7453-reports-an-external-ssa-writer-losing-a-field-on-a-composite-resource]] and [[examples/crossplane-pull-requests-7783-and-7787-say-fromstruct-drops-managedfields-on-the-composite-resource]]

**Deletion and data loss.** The default of Delete means a mistaken manifest removal, a namespace deletion or a GitOps prune can delete a production database along with its data. Config Connector's documentation names `SpannerInstance` and `BigtableTable` as types where deletion can lose data, and the same logic applies to Crossplane. Set `Orphan` or a policy list without Delete before any operation that removes the Kubernetes object. The wiki's decision page records that the sources document the defaults and opt-outs but recommend no single setting. It helps to know how the Kubernetes garbage collector and the management policies interact when a composite is deleted, because the two are easy to conflate. A namespaced XR can compose only resources in its own namespace, and its composed resources carry a controller owner reference with `blockOwnerDeletion: true`. Deleting the XR defaults to background propagation, so Crossplane stops managing it and the garbage collector removes the composed objects, while `kubectl delete --cascade=foreground` or `--cascade=orphan`, and Argo CD's foreground propagation, make Crossplane ignore the composite deletion policy and emit a warning event. What happens to the cloud resource, though, is decided by `managementPolicies` and not by the owner reference: in the managed reconciler source the external resource is deleted only when it exists and the policy allows Delete, and otherwise the reconciler unpublishes connection details and removes the finalizer. A composed resource whose policies omit Delete therefore disappears from Kubernetes with its XR and leaves the cloud resource running, which is the intended behavior for a retained database and a leak for everything else. Version 2.4.0 restricted the XR garbage collector to delete only resources whose controller reference points back to the XR, and v2.5.0 stops a function from making a namespaced XR compose a cluster-scoped object by setting `metadata.namespace`. No v2 documentation page connects these rules, so this account is derived from source and consistent with the docs policy table, and what happens when a namespace is deleted while the provider is down is not covered. [[findings/deleting-stateful-resources-through-a-provider-can-lose-data]] and [[findings/a-managed-resource-without-delete-in-its-management-policies-is-removed-from-kubernetes-but-its-cloud-resource-stays]] and [[decisions/delete-or-retain-the-external-resource-when-the-kubernetes-object-is-deleted]]

Related ordering problems: a credentials Secret with no finalizer can vanish before managed resources finish cleanup, leaving them stuck Terminating, as described in issue 7801, opened on 2026-09-02. When a namespace is deleted its objects go in arbitrary order, so the Secret that holds the credentials can vanish while managed resources still need it to call the cloud API, and those resources then cannot authenticate and stay Terminating. As of 2026-11-26 the issue is open, labelled `enhancement`, with two comments and no maintainer reply or linked fix. Its body lists three directions and says none is decided: a Usage-style or generic dependency-protection controller, provider-side credential caching, and ordered namespace teardown. Part of the neighboring problem has been fixed. On 2026-09-08 crossplane-runtime pull request 1113, "Protect ProviderConfigs while managed resources terminate", merged together with a design one-pager (Crossplane pull request 7594) and the closing of issue 4661, so a ProviderConfig is now protected while managed resources terminate. The Secret behind the ProviderConfig is not covered, and the one-pager treats Secret protection as out of scope. A second open report, crossplane-runtime issue 1150 (a reporter on v2.3.3, and read only in part), traces another namespace-deletion failure with the provider running: the managed reconciler runs `Connect()` before checking whether the resource is being deleted, tries to create a `ProviderConfigUsage` object, and the API server rejects the create with a 403 `NamespaceTerminating`, which blocks deletion for hours. Namespace deletion while the provider itself is absent is not documented anywhere the wiki searched, so any claim about it is inference. A paused resource cannot be deleted until it is unpaused, because the pause also stops the reconcile that runs deletion, which the wiki read on a v1.20 page and flags for re-checking. **Provider removal and cluster deletion.** The documentation states that "removing a Provider without first removing the Provider's managed resources may abandon the resources." The CRDs and controller vanish, finalizers can no longer run, and the real resources keep running and billing. The same mechanism applies if you delete the whole cluster first, which a single consultancy article reports for Config Connector on GKE. Remove managed resources first and wait; Crossplane has an alpha provider-deletion-protection feature that blocks provider removal while managed resources exist. [[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]] and [[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]]

**Live composition edits.** An XR defaults to the Automatic update policy and so follows the latest CompositionRevision, which means an edit to a shared Composition rolls out to every composite at once. The v2 upgrade guide warns that editing a live Composition could disrupt or replace resources. Manual pinning with `compositionRevisionRef` or a label selector shifts risk to consumers, who must then track which composite is on which revision. The wiki's decision page lists a mix as an option, Automatic in non-production and Manual in production, without claiming anyone's practice. Be careful about what Manual protects, since it freezes the pipeline definition and not the function code: a pipeline step that uses `functionRef` follows the active Function revision for every CompositionRevision, pinned ones included, so a function upgrade reaches Manual composites too, as section 6 describes. Revisions also accumulate, one for every edit of a Composition. Crossplane v2.5.0, released on 2026-11-24, added an alpha garbage collector that deletes unused revisions beyond a new `spec.unusedRevisionHistoryLimit` field on the Composition, with a default of 1, so the feature needs enabling and its default is not a recommendation. [[findings/editing-a-live-composition-can-disrupt-or-replace-existing-composed-resources]], [[decisions/choose-automatic-or-manual-composition-update-policy]], [[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]], [[examples/crossplane-v2-5-0-released-2026-11-24-with-alpha-compositionrevision-garbage-collection-and-an-upgrade-ownership-fix]] and [[comparisons/composition-revisions-versus-graph-revisions-for-rolling-out-platform-api-changes]]

**Immutable fields.** A change to an immutable field in `forProvider` may silently not apply. Treat such fields as part of the resource's identity, decide them before the first apply, and watch `Synced` after any edit. [[findings/crossplane-does-not-delete-and-recreate-to-change-immutable-fields]]

**Credential blast radius.** Anyone who can create a provider-managed object borrows the controller's identity. Scope credentials with per-account `ProviderConfig` objects, scope who can create composites with RBAC, and remember that a hosting cluster that holds broad cloud permissions is a high-value target. The wiki's general finding is that centralizing privilege in a control plane makes the control plane the blast radius. [[findings/blast-radius-and-privilege-centralization]]

**Functions as moving parts.** Every function in a pipeline is a pod, and a composite cannot reconcile while a function it depends on is unhealthy. Errors in a function's logic also tend to appear only at reconcile time, when Crossplane actually calls it, and not when you apply the Composition. Plan to monitor function pods the way you monitor any other production service. [[findings/composition-functions-add-moving-parts-that-must-be-healthy]]

**Old provider revisions.** Each provider upgrade creates a new `ProviderRevision`, and older ones are kept so that you can roll back. The `revisionHistoryLimit` setting controls how many inactive revisions are retained, and the default is one. Automatic downgrades are switched off, because moving to an older provider could remove the CRDs or controller behavior that existing managed resources rely on and risk orphaning them. The practical effect is that rolling back is a deliberate manual act and not something the system does for you. The package documentation fills in the surrounding rules. Only one revision of a package is active at a time, the most recently installed one by default, and `revisionActivationPolicy` can be `Automatic` (the default) or `Manual`, where Manual means a new revision is not activated on its own. Setting `revisionHistoryLimit` to 0 disables keeping inactive revisions. Those defaults are documented for Providers and Configurations, but a keyword scan of the Functions page found none of them, so applying the Provider rules to Function packages is an inference, even though FunctionRevisions plainly exist. Dependencies between packages are handled by a resolver that watches the revision objects, builds a graph from the cluster-scoped `Lock` object (the "lock file" is that object, named `lock`, and not a file), rejects cycles and, when dependencies are implied but missing, creates only the first missing one per pass, so a chain of missing dependencies fills in over several reconciles and a Configuration can briefly report unmet dependencies while it installs. The resolver never rewrites the Lock. Moving an already installed dependency is opt-in and alpha: `--enable-dependency-version-upgrades` lets the resolver pick the minimum version that satisfies every constraint, and automatic downgrades need that flag plus a second one, and the documentation warns that a downgrade can orphan managed resources, lose data or change storage versions. Without them, a needed downgrade ends in an error saying manual intervention is required, and setting `skipDependencyResolution: true` on a Configuration makes Crossplane ignore its dependencies altogether. Crossplane v2.5.0 also fixed a case in which a new package revision did not reliably take ownership of its objects during an upgrade, though the release notes do not describe how the bug showed up in practice. [[findings/provider-upgrades-leave-old-revisions-and-block-automatic-downgrades]], [[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]], [[findings/crossplane-dependency-version-upgrades-and-downgrades-are-alpha-and-downgrades-need-both-feature-flags]], [[findings/crossplane-activation-policy-and-history-defaults-are-documented-for-providers-and-configurations-and-were-not-found-for-functions]] and [[decisions/let-crossplane-resolve-package-dependencies-or-pin-versions-and-skip-resolution]]

**Hosting and skills cost.** Adopting Crossplane requires a hosting cluster, Kubernetes skills on the team that runs it, and a platform team willing to own the abstractions. The critics and the project agree on this point, which is why it is worth stating plainly. Early evaluations (SuperOrbital in 2022) reported sparse documentation, alpha APIs and hard troubleshooting across several layers, which is historical but explains the project's reputation. Be aware too that older blog posts describing claims, native patch and transform or external secret stores no longer match current Crossplane. [[findings/crossplane-adoption-needs-a-hosting-cluster-kubernetes-skills-and-platform-team-owned-abstractions]] and [[findings/older-claims-and-patch-and-transform-material-no-longer-matches-current-crossplane]]

**GitOps resource tracking.** Crossplane's guide for Argo CD asks for several settings, and each one answers a specific problem. Argo CD normally records which objects belong to an application with a label; the guide asks for annotation-based resource tracking instead, which keeps Argo CD's ownership marker from colliding with labels that Crossplane and its providers propagate onto composed resources, a collision that I infer from the guide's advice and did not confirm in the sources. The guide also asks for custom Lua health checks, because without them Argo CD has no idea whether a `crossplane.io` or `upbound.io` object is healthy and may report it as healthy or progressing indefinitely. That advice predates the built-in scripts described in section 7, so on a recent Argo CD check the shipped script first, and remember that a wildcard script that mishandles one kind can hold up every later sync wave, because Argo CD advances waves only when the current wave is synced and healthy. [[examples/crossplane-resources-hosted-by-argo-cd]]

**GitOps load and noise.** The guide asks you to exclude `ProviderConfigUsage` objects, which Crossplane creates to record which managed resources use a given `ProviderConfig`. They are bookkeeping that nobody authored in Git, and the wiki does not record the guide's stated reason, so treat them as noise Argo CD should not try to sync. The guide also raises the client QPS to 300, from a default of 50. QPS is queries per second, the rate at which Argo CD's Kubernetes client is allowed to call the API server, and a Crossplane installation has many more kinds and objects to watch than a typical application, so the default rate can throttle Argo CD. [[examples/crossplane-resources-hosted-by-argo-cd]]

**Foreground deletion.** Argo CD deletes with foreground propagation by default. In foreground deletion the parent object stays present, marked as deleting, until all of its dependents have been removed, whereas background deletion removes the parent immediately and lets cleanup happen afterward. Crossplane's alpha composite deletion policy offers Background, Foreground and Pipeline behaviors for ordered teardown, but when the delete request itself arrives as a foreground deletion, Crossplane ignores that policy and emits a warning event. The fix is the `PrunePropagationPolicy=background` sync option. The danger is that a team can choose Pipeline deletion for ordered teardown and silently lose it, because another tool's setting takes precedence. [[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]]

**Named incidents in the layers around Crossplane.** The wiki still holds no organization-authored postmortem in which Crossplane itself leaked or duplicated a cloud resource, but it now holds several named, first-party accounts from the layers a Crossplane platform sits among, and they teach the same lessons. Skyscanner's 2021 outage is the clearest GitOps case. On 25 August 2021, at about 1530 GMT, an engineer merged a change to the templating system that generates Skyscanner's cluster configuration. The change was meant to alter no behavior, but it left out the `{{ }}` template markers, so templating stopped applying to the root file that every region used and the namespaces defined by it were corrupted. At 1600 GMT Argo CD reconciled the clusters against a configuration that listed no valid namespaces and began deleting every service, 478 in all, across every availability zone and region. Because the clusters pull their state, recovery meant restoring correct configuration and letting each cluster reconcile itself, and the team had the site serving from a single region by about 2030 GMT, with the other regions and non-critical services returning over the following two days. The post's own summary is that Argo CD did this "ultimately because we told it to", and it does not say which sync options were set or whether pruning was automated, so the wiki claims no specific Argo CD misconfiguration. The lesson for Crossplane users is that a reconciler enforces a bad desired state faithfully, so the guards against deleting stateful resources in this section matter most exactly when the desired state itself is wrong. Spotify's 2018 and 2019 cluster deletions, told at KubeCon, make the same point about infrastructure as code: an operator deleted a production GKE cluster by console click in November 2018, and about a month later a Terraform review build that imported the Asia cluster into a state file shared with production builds, followed by an out-of-order merge, deleted that cluster. When the team widened a service account's permissions to recreate it, Terraform saw the other clusters with different properties and deleted a second one, so two of three production clusters were gone for a night, and the account says users did not notice. Jetstack's 2019 post is the webhook case, and it bears on the fail-closed Usage webhook described in section 4. A GKE master upgrade stalled because the API server's own post-start write to a ConfigMap was subject to an OPA validating webhook whose backend was not responding, the master failed its health check, and node auto-repair then recreated nodes in an endless loop, which the fix of deleting the webhook resource resolved only because the API server answered intermittently. All three accounts are self-reported, and none involves Crossplane. Closer to provider-managed resources, issues rather than postmortems document the same hazards. ACK issue 3153, opened on 2026-11-09, says that when a custom resource is pruned from Git the AWS resource goes with it irreversibly, and the issue accepts that this is ACK's documented default. A Flux Kustomization whose `deletionPolicy` is `WaitForTermination` gives up at `spec.timeout`, logs an error and lets the Kustomization be deleted, so a slow cloud delete can outlive the object that was supposed to show its failure, which is an inference from the documented timeout and finalizer order and not an observed event. Config Connector issue 16444, opened on 2026-11-25, describes a multi-cluster setup with leader election in which deleting objects on a standby cluster leaves them Terminating and then runs the stale deletion against live Google Cloud resources when that cluster becomes leader again, and it was still open on 2026-11-26. Three anonymous Argo CD issues add that deleting or recreating an Argo CD parent object, or removing a manifest that owns a namespace, can cascade to everything it managed. The ACK and Config Connector reproductions ran on kind with a mock AWS service or are single-reporter claims, so treat them as mechanisms and not as frequencies. ## 12. Scaling Crossplane: reconcile rate, provider families, activation policies, domain-scoped control planes

Scaling a Crossplane control plane has three separable pressures. The first is object and CRD count. Each external resource type is its own CRD, so multi-cloud provider sets imply thousands of CRDs that strain API server discovery and OpenAPI computation. Provider families (described in section 3) cut the count by letting you install only the services you use. Crossplane v2 adds a second control: each managed resource type is a `ManagedResourceDefinition`, and a `ManagedResourceActivationPolicy` lists exact names or prefix-wildcard patterns so that only matching definitions are activated and turned into served CRDs, with providers that implement "safe-start" able to activate on demand. The trade is completeness for a smaller API surface, so a platform team must know which types it uses. Two details change how you apply this. The stock Helm chart creates a `default` activation policy that activates `"*"`, so a plain install activates every managed resource and the CRD count does not shrink until you turn that default off with `--set provider.defaultActivations={}` and list the groups you need. And the feature's maturity is described inconsistently: the documentation labels both the definitions and the activation policies alpha, while the code lists the conversion flag under beta features, so call it alpha-to-beta and check the flag before relying on it. Activation is also one-way, since a definition that has become Active cannot be deactivated, and a provider without the `safe-start` capability starts everything Active regardless. The docs estimate about 3 MiB of API server memory per CRD, which is an estimate, and no measurement with and without activation policies was found. [[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]] [[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]] and [[findings/one-crd-per-external-resource-type-overloads-api-server-discovery-and-openapi-computation]]

The second pressure is reconcile load. Each reconcile of a managed resource may call a cloud API with its own quota, which is why `--max-reconcile-rate` exists, and why poll interval matters. To be precise about which number is which, the 60-second poll figure used elsewhere in this document applies to composite resources, as reported by the composition dossier. A note on the flag that governs concurrency, since older advice misstates it: `--max-reconcile-rate` is no longer a per-second rate. v2.1.0 renamed it `--max-concurrent-reconciles`, and in v2.5.0 source it is a worker pool size with a default of 100, so the number says how many reconciles may run at once and not how many may start each second, while the XR circuit breaker described in section 10 is the guard against a runaway composite. The same source gives a sync interval of one hour, a minimum per-resource poll interval of one second and ten concurrent package establishers. The managed-resource poll interval is now verified from source, and it differs by layer. crossplane-runtime's managed reconciler defaults to one minute, and Crossplane core exposes a `--poll-interval` flag that also defaults to one minute with a one-second minimum for per-resource overrides set through the `crossplane.io/poll-interval` annotation. Providers built on Upjet override the value: the provider-upjet-aws S3 provider defaults to a 10-minute poll, a one-hour sync and a `--max-reconcile-rate` of 100, with jitter of 5 percent of the poll interval. A drift-detection latency quoted for "Crossplane" is therefore wrong unless it names the provider, about one minute for providers that keep the runtime default and about ten minutes for the Upjet-generated catalogs. The design one-pager for the per-resource annotation still says "Draft" although the feature is implemented. These values come from source files, because the docs.crossplane.io managed-resources page was read in full and states no poll interval default, so it cannot be cited for the numbers, and the wiki found no single Crossplane v2 scaling page and no documented numeric limits for XRs or composed resources, only guidance scattered across the Pods guide (poll and sync intervals), the worker-pool flag, notes on API Priority and Fairness (the API server's mechanism for queuing and rate-limiting requests by priority so that one noisy client cannot starve the others) and the activation-policy pages, with no independent benchmark. For comparison, ACK resyncs about every 10 hours by default after `ResourceSynced` (tunable per kind) and kro does a 10-hour full resync (which the wiki reads as a replay of the informer's cached state to the handlers and not a fresh read of the cloud, so it is a different mechanism from ACK's real re-read), while Flux Kustomizations reconcile on a required, author-chosen interval with a recommended minimum of 60 seconds that the API type does not enforce (the Flux concepts page says five minutes by default, but the Kustomization and HelmRelease references require the interval and set no default), and Argo CD polls Git every 180 seconds through v2.14 and every 120 seconds plus up to 60 seconds of jitter from v3.0, although some documentation still says three minutes. Config Connector reconciles each resource about every 10 minutes on average, jittered between 0.5 and 1.5 times that, and the controller kind does not change the cadence: the direct, Terraform-based and DCL-based reconcilers share one jittered requeue, and the source shows no separate drift poll. Per-kind intervals exist only as five Terraform service-mapping overrides, two set to 0 and three set to 3600 seconds, while 262 of 267 reference pages show 600 seconds. The interval can be tuned by annotation, and "0" disables drift correction, which the documentation calls irreversible. A failure-backoff annotation works only for direct controllers from release 1.160.0. [[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]], [[findings/config-connector-per-kind-reconcile-intervals-exist-only-as-five-terraform-service-mapping-overrides-and-262-of-267-reference-pages-show-600-seconds]], [[findings/config-connector-has-no-separate-drift-poll-and-the-failure-backoff-annotation-works-only-for-direct-controllers-from-1-160-0]], [[findings/argo-cd-changed-its-default-polling-from-a-flat-180-seconds-to-120-seconds-plus-60-seconds-of-jitter-in-v3-0-and-some-docs-still-say-three-minutes]], [[findings/the-flux-concepts-page-says-five-minutes-by-default-but-the-kustomization-and-helmrelease-references-require-the-interval-and-set-no-default]] and [[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]] Longer intervals save API quota but lengthen drift-detection latency, which is the trade the wiki's decision page on choosing a drift-check interval frames. [[comparisons/reconcile-cadence-and-off-switches-across-tools]], [[comparisons/drift-detection-mechanisms-across-tools]] and [[decisions/choosing-a-drift-check-interval-for-external-resources]]

The third pressure is function load: composites are polled every 60 seconds by default and function calls scale with composite count. The design document lists the levers as the poll interval, function replicas and response caching by TTL. A third-party article argues large composites can exhaust function memory, though its log excerpts are labelled simulated, so that claim is plausible guidance and not an incident report. Imagine Learning chose one monolithic function to reduce idle pods, trading isolation for fewer processes. [[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]] and [[findings/crossplane-poll-interval-defaults-differ-by-layer-with-one-minute-in-core-and-runtime-and-ten-minutes-in-upjet-providers]]

Informer caches add a fourth, general Kubernetes pressure: a controller that watches many objects holds every watched object in memory, so memory grows with cluster size. Crossplane core takes some steps against this that are visible in its source on the main branch. It builds a dedicated cache for the API-extensions kinds with a transform whose comment reads "Strip the OpenAPI schemas (most of CRDs' size) from typed CRDs in this cache", which removes most of the bytes of each CustomResourceDefinition held in memory. It lists Secret among the kinds its client reads straight from the API server without caching, and it sets the cache's resync period from the sync-interval flag. The project reports measured results from this work, all self-reported and tied to particular cluster sizes, and none an independent benchmark. The Crossplane v2.5.0 release notes (2026-11-24) say that after core stopped caching all CRD OpenAPI schemas, heap usage fell from 338 MiB to 190 MiB and resident memory from 415 MiB to 250 MiB on a cluster with 791 CRDs. A Crossplane blog post dated 2026-10-08 reports that provider memory drops by roughly 80 to 95 percent depending on the provider, on a cluster of about 2,000 CRDs, using crossplane-runtime v2.4 with schema stripping and an optional Secret cache, and v2.4.0 (2026-08-20) creates the runtime Deployment of a safe-start provider with zero replicas until its first managed resource definition is active. The effect is that the family-split trade of fewer CRDs for more pods is now being offset from the other side, as per-provider memory and idle providers shrink, and no measurement of API server memory with and without activation policies was found. For Upjet-based providers specifically, no official memory or CPU figures exist, as section 3 notes. The closest official guidance is the Pods guide, which gives a one-minute polling default and a one-hour sync interval, and says most providers use their own `--max-reconcile-rate`. No Crossplane performance or sharding guide was found: a guessed `guides/performance` URL returned an empty body, the docs repository has no such file, and a search for "perform", "scal" and "tuning" turned up only the Pods guide, the scale-subresource page and the troubleshooting page, so that absence means only that none was found, and no documentation describes informer sharding. One vendor knowledge-base article, which is secondary evidence because it does not come from the project, says all managed resources are re-queued immediately after a provider restart because the cache is rebuilt, and that a poll interval of 30 minutes or an hour cuts drift checks by three or six times. The wiki's general treatment lives in [[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]] and [[concepts/informers-reflectors-and-workqueues]], with the Crossplane specifics in [[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]] and the cross-tool options in [[comparisons/concurrency-and-cache-memory-controls-across-flux-argo-cd-and-crossplane]]. The memory figures are in [[examples/crossplane-v2-4-and-v2-5-cut-memory-on-clusters-with-hundreds-to-two-thousand-crds]]. The shared store also has limits of its own, covered in [[findings/etcd-scale-limits-of-the-shared-store]]. The wiki also notes that tested envelopes and operator advice differ by an order of magnitude (SIG Scalability's 5,000 nodes versus Gardener's advice to stay under 500 for most clusters), and that neither lists CRD count as a tested dimension. [[findings/tested-scalability-maximums-and-operator-advice-differ-by-an-order-of-magnitude]]

Finally there is the question of how many control planes to run. A practitioner blog from Polarpoint argues that "teams no longer need a single monolithic Crossplane instance," and proposes several small control planes each scoped to a domain such as networking or data. The wiki marks this as prescriptive advice from two blogs, not evidence of deployments, with no object counts or operating costs. The trade-off, which the decision page leaves open, is smaller blast radius and clearer ownership against more clusters to operate. The same worry appears for Cluster API, where centralizing authority in a management cluster makes that cluster a single point of failure. ## 13. How Crossplane compares with kro, Terraform and tofu-controller, ACK, Config Connector, ASO, Cluster API and Kratix

**kro.** kro (kube-resource-orchestrator), announced by Google on 2025-01-30 with AWS and Microsoft, expands one end-user CRD into a graph of resources through a single ResourceGraphDefinition that holds schema, templates and CEL expressions. Where Crossplane separates XRD from Composition and runs external function pods, kro puts everything in one object and evaluates CEL inside its own controller. kro infers dependency order from references and creates in topological order, deleting in reverse; Crossplane leaves ordering to the functions and eventual reconciliation. kro validates at creation time, Crossplane often at reconcile time. kro is `v1alpha1`, the docs read showed version 0.10.0, and Google said at launch it was not ready for production, while Crossplane is CNCF graduated. kro has no ADOPTERS file at the repository root, and the wiki found no named production adopter with a reported scale. A third-party blog (2026-07-29) says a CNCF and SlashData platform-engineering radar placed kro in "Adopt" and that AWS ships a kro concepts page in its EKS documentation, but those are secondary claims and the radar was not read. [[entities/kro]] Four first-party sources confirm that kro is governed as a Kubernetes SIG Cloud Provider subproject, and v0.10.0, published on 2026-11-10, is the latest release. It also carries an alpha Graph API, off by default behind a feature gate, that is additive to the ResourceGraphDefinition, and both run on one engine, so engine changes reach RGD users as well. The in-repo roadmap is marked last updated 2026-04-03 and predicted v0.10 for mid-May, about six months before it shipped, and it gives no promotion timeline for Graph, so a team cannot plan from it. The wiki did not check whether kro appears on the CNCF project list. On scale, the evidence is thin and worth stating exactly. **Terraform and tofu-controller.** The Crossplane blog's one-liner is that "Crossplane is a control plane, where Terraform is a command-line tool, an interface to control planes." Crossplane controllers reconcile continuously and correct drift without anyone running a command, with each resource an independent API object under Kubernetes RBAC. Terraform plans against a state file when a person or CI job invokes it, and drift shows up at the next plan, with a reviewable plan before apply. Crossplane needs a running Kubernetes cluster and Kubernetes expertise, and the Crossplane blog itself concedes Terraform is simpler and more familiar. The wiki flags that both main sources are partisan (the Crossplane blog is advocacy, the Encore article comes from a competing vendor) and no neutral comparison was read. A later search confirmed the gap: the results were vendor pages (Spacelift, Loft, Stategraph, Encore and the Crossplane blog), five pages were read, and the most independent item, a SuperOrbital consultancy evaluation from 2022, predates Crossplane v2 and function-based composition, so it must not be treated as current. That evaluation is also where the plan-preview claim comes from, namely that Crossplane "has no equivalent to a dry run mode, like `terraform plan`" and that fields which would force recreation in Terraform may be ignored while the provider reports in sync. That claim rests on a dated 2022 source, and `crossplane render` now previews what a Composition produces, though that is not a preview of what a provider will change in the cloud. Two Medium comparisons returned empty pages, so they were not read. Terraform also enters Crossplane through Upjet. Two controllers run Terraform inside a cluster. tofu-controller, a flux-iac project, runs plan and apply in runner pods, stores state as Kubernetes Secrets, and does manual approval by putting the plan ID in `.spec.approvePlan` through Git; its README also describes a drift-detection-only mode. Its maintenance question, left open after Weaveworks' wind-down, is now answered from release and commit history on 2026-11-26. The project is community maintained under flux-iac, previously known as Weave TF-Controller, with five active maintainers listed, a last push on 2026-11-25 and a roughly monthly to bimonthly release cadence. Release v0.17.0 (2026-11-16) removed the `v1alpha1` API, so only `v1alpha2` remains and manifests still on the old version need migration before the upgrade, and the version-coupling figure that 0.16 pairs with Terraform 1.5.7 and Flux 2.6.x now describes a release line one minor version behind. **ACK, Config Connector and ASO.** These cloud-vendor add-ons expose one cloud's resources close to one-to-one, with no built-in composition layer. ACK runs one controller per AWS service with scoped IAM permissions, uses `IAMRoleSelector` to map namespaces to roles and is generated from AWS API models. Config Connector covers Google Cloud with direct, Terraform-based and DCL-based controllers, namespaced or cluster mode, and one `Ready` condition. Which controller a given kind uses is answered by a Go table named `ControllerConfigStatic` in the Config Connector source. At master commit 5cce7c7e (2026-11-26, latest release v1.162.0) it maps 814 kinds, and the dossier author's own tally has direct as the default for 539 of them, Terraform-based for 206, DCL-based for 65 and four IAM-specific kinds, with some kinds supporting more than one controller. The controller-types page says new resources use the direct controller by default and existing ones are migrated regularly, so cite the commit or tag and do not hard-code those counts. The routing order is a namespace override in the ConfigConnectorContext first and otherwise the build-time default, and the labels on the live CRD show which controller runs: `cnrm.cloud.google.com/tf2crd: "true"` means Terraform-based, `dcl2crd: "true"` means DCL-based, and no label means direct. Namespaced mode is the CRD default and needs one ConfigConnectorContext per namespace, while cluster mode takes exactly one credential, and the deletion policy has two values of which only `abandon` changes the delete path, with the Terraform-based controller's handling of `abandon` not located. Google's known-issues page records a webhook TLS race before 1.134.1 that could leave the API server rejecting creates, and direct-reconciler regressions in 1.132.0 and 1.134.0. On the comparison with Crossplane, the wiki found no neutral source, only a Crossplane maintainer's 2021 to 2022 positions and an unanswered 2024 question. ASO v2 manages 150 or more Azure resources with CRDs generated from Azure Resource Manager schemas, and the dossier does not cover its credential scoping, deletion policy or drift cadence. The comparison source is a project maintainer, so it is positioning and not neutral analysis. The EKS kro capability composes ACK S3 buckets with Deployments and ConfigMaps, which shows the add-ons paired with a separate abstraction layer. [[examples/the-eks-kro-capability-composes-ack-s3-buckets-with-deployments-and-config-maps]] The ACK documentation has its own first-party guide, "Using ACK with kro", whose ResourceGraphDefinition composes an S3 bucket, a DynamoDB table and a Deployment: kro waits for the ACK resources to become ready before creating dependents, does not create dependents if an ACK resource fails, and on deletion removes the Deployment first and then the AWS resources, following ACK's deletion policy. What the wiki did not find is the Crossplane equivalent: no worked example of Crossplane composing ACK or Config Connector objects, and no first-party test of the interplay. On paper both satisfy `function-auto-ready`, which treats a composed resource of an unknown kind as ready when it carries a `Ready` condition with status True, and ACK defines a `Ready` condition that its runtime source calls equivalent to `ResourceSynced` while Config Connector reports `Ready` with reason `UpToDate`, but that is an inference from documented conditions, and whether composite deletion honors their deletion ordering is unsettled. ACK's deletion policy resolves from the resource, then the namespace, then the controller default, and one reporter says a chart-stamped Delete defeats a controller-wide Retain, which is a single-reporter claim. ACK's per-service controllers avoided the many-CRD problem from the start, whereas Crossplane needed families. **Kratix, Backstage and Port.** Kratix, from Syntasso, is an orchestration framework whose central object is the Promise, bundling a self-service API, workflows and fleet scheduling, and its documentation expects a portal such as Backstage in front. Backstage is an open-source portal framework (CNCF incubating, from Spotify) with a software catalog and templates, and Port is a commercial SaaS portal. Portals provide visibility; a Syntasso blog argues a portal alone leaves ticket queues in place, though that is a vendor claim and the only comparison with Port is Port's own. Kratix and Crossplane both define platform APIs, but the wiki has no head-to-head source, so this document makes no claim about which is better. The mechanics that distinguish Kratix are now documented from its reference pages. A Destination is a cluster-scoped representation of a system that Kratix can write documents to, such as a Kubernetes cluster with Flux or Argo CD pulling manifests, Terraform, Ansible, or even a Backstage catalog filled from a Git repository. Kratix does not apply those documents itself. It writes them to a state store, either a Git repository (GitStateStore) or an S3-compatible bucket (BucketStateStore), and the agent on the Destination reads them, so Kratix leans on a delivery tool for the last step in the way a Crossplane platform leans on Flux or Argo CD. Under the store path Kratix writes a `dependencies` directory for Promise-level items such as CRDs and a `resources` directory for each Resource request, the `filepath.mode` is `nestedByMetadata` by default, and the documentation says that mode "is immutable once the Destination is created", so changing the layout means creating a new Destination. Scheduling happens in two stages. In the first, a Promise's dependencies go to every Destination, or only to those whose labels satisfy the Promise's `destinationSelectors`, and a Destination with `strictMatchLabels: true` accepts only Promises whose selectors match its labels. In the second, a Resource request triggers its configure workflow and the outputs go to a matching Destination, and when several match Kratix by default selects one at random, which is a surprise for anyone expecting a deterministic spread. Only the documentation and the Go types were read, and the scheduler source was not. The Score and Radius projects sit higher still, closer to the developer's workload description. Both are CNCF Sandbox projects according to the CNCF landscape file, which lists Radius as accepted on 2024-04-16 and Score on 2024-07-08, and both passed their sandbox votes. Sandbox is the entry tier and says nothing about production readiness. All four Radius maintainers listed are Microsoft employees, only the newest minor release channel (0.62 when read) is supported with older lines deprecated, and its changelog still lists breaking changes, whereas Score's maintainers span four employers and its sandbox application names Humanitec as the sponsoring company, though no document read says in words that Humanitec created Score. Score's specification releases slowly while its implementations, such as score-k8s and score-compose, release often. Backstage, finally, is a read-oriented portal over what operators produce. Its Kubernetes plugin matches catalog entities to cluster objects through the `backstage.io/kubernetes-id` label or a label-selector annotation and silently skips a custom resource whose CRD is not installed, and its Scaffolder is a one-shot task runner and not a reconcile loop. The nearest operator-style integration is a community plugin, the TeraSky Kubernetes Ingestor, which syncs from cluster to catalog and ingests Crossplane claims and kro instances. **Render-time tools and KRM functions.** Helm, Kustomize, kpt and Score belong to a different family from Crossplane and kro. They produce manifests once, on a laptop or in CI, and something else, usually a GitOps agent, must keep the result correct afterward, whereas a controller-driven abstraction such as Crossplane, kro or Radius is a live API whose controller keeps reconciling children, writes status back to the parent and handles deletion order. Moving Kustomize or Helm inflation into KRM functions brings the container requirement discussed in section 6, which laptops, CI runners and Argo CD often lack, and kpt and Kustomize offer only opt-in exec extensions as the way around it. **Flux and Argo CD.** These deliver rather than provision. Flux orders whole objects with `dependsOn` between Kustomizations, and Argo CD orders within a sync with phases and wave numbers, while kro and Crossplane order resources inside one abstraction. Flux can run `prune` and, with `deletionPolicy: Orphan`, keep objects; Argo CD does not prune by default. The guards at both layers need to agree, since a Git removal with `prune: true` deletes the object and the provider then deletes the cloud resource unless Delete is excluded. A good mental stack is delivery (Flux or Argo CD), then abstraction (Crossplane or kro), then provisioning (providers, ACK, Config Connector), with a portal on top. **Flux versus Argo CD behavior, side by side.** Since the choice of delivery agent changes how a Crossplane platform behaves, the documented defaults are worth having next to each other, with the caveat that no neutral benchmark or CNCF comparison of the two was found and everything here rests on each project's own documentation, read on the main branch and not a pinned release. For drift, Flux runs a server-side apply dry run each interval and reverts manual changes on reconcile unless the object is suspended, whereas Argo CD compares Git with live state and marks the application OutOfSync, and reverts only when self-heal is on, which it is not by default. Prune is controlled by Flux's `prune` setting with a per-object opt-out annotation, and Argo CD does not prune by default. Flux offers a `deletionPolicy` with `MirrorPrune` (the default), `Delete`, `WaitForTermination` and `Orphan`. The ignore controls differ in a way that has bitten users: Argo CD's `ignoreDifferences` affects only the diff unless `RespectIgnoreDifferences` is set, and then only for resources that already exist, while a Flux ignore rule without a target selector matches every object the Kustomization manages. Neither tool offers a true observe-only mode, which is a negative finding from the pages read, so Crossplane's `Observe` management policy remains the way to look without touching. For multi-cluster delivery, a central Argo CD instance reaches into registered clusters from a hub, so delivery to a fleet is a push even though each application pulls from Git. The separate argocd-agent project in `argoproj-labs` inverts that, with lightweight agents reaching back to the hub, and its maturity is unverified because its README states none. A Flux Kustomization can target a remote cluster through `.spec.kubeConfig`, though the more common Flux layout runs a controller set in every cluster, and Morgan Stanley is a named adopter that reports running Flux across more than 500 clusters with self-service onboarding, listing sharding as future work. ApplicationSets generate many Applications from one template, and their documented limits are concrete: the matrix generator combines only two child generators, combination generators can be nested only once, the Pull Request generator polls every 30 minutes by default and makes anonymous, lower-rate-limit requests without a token, and the OCI generator polls every 3 minutes. The RollingSync strategy for staged fleet rollout is beta since v3.3.0, forces autosync off for the generated Applications and watches only Application health, so it is only as good as the health scripts discussed in section 7, and an Application no step selects is silently excluded. No quantified scale limit for ApplicationSets or hub-and-spoke Argo CD was found. **Secrets and OCI sources in GitOps.** A Crossplane platform needs credentials for providers, so how the delivery agent handles secrets matters. Argo CD's secret-management page "strongly" recommends populating secrets on the destination cluster through an operator, naming Sealed Secrets and External Secrets Operator (in-cluster operators that turn encrypted or externally stored secrets into ordinary Kubernetes Secrets), the Secrets Store CSI Driver (which mounts secrets from an external store into pods) and Vault Secrets Operator (which does the same for HashiCorp Vault), and it cautions against plugins that inject secret values while rendering manifests, because Argo CD stores generated manifests in plaintext in its Redis cache, secret updates become coupled to syncs, and the approach is incompatible with the "Rendered Manifests" pattern, which means committing the fully rendered manifests to Git so that reviewers can see exactly what will be applied. The page does not mention SOPS (a tool that encrypts the values inside a YAML file so the file can safely sit in Git) or ksops (a Kustomize plugin that decrypts SOPS files during rendering) at all, which is a statement about the page and not a position of the project. Flux takes the opposite stance for SOPS: the Kustomization specification says "The only supported encryption provider is SOPS", decryption runs inside kustomize-controller, and encrypted files must leave `metadata`, `kind` and `apiVersion` in plaintext. Flux also publishes a Sealed Secrets guide, and the wiki collected no failure modes for either approach. On sources, Flux's OCIRepository can verify Cosign or Notation signatures (both are tools that sign and verify container and OCI artifacts) through `.spec.verify`, including keyless identity matching, while the Argo CD pages read document OCI images as an application source but no OCI signature verification, covering only Git commit signatures with GnuPG. Again that is a statement about the pages read and not proof of absence from the code, and no independent evidence that signed OCI beats Git, and no registry rate-limit documentation, was found. **Flux internals worth knowing.** A few mechanics from Flux's source explain behavior a Crossplane operator may see when Flux delivers the platform. Source-controller serves the artifacts it builds from an in-process HTTP file server that starts only after the manager wins leader election, and standby replicas fail a `leader-election` readiness check by design, so extra replicas give failover and no extra capacity. The stock manifest runs one replica with the `Recreate` strategy, keeps the default one-minute artifact retention and mounts `emptyDir` volumes, so a restart probably rebuilds artifacts, which is an inference because the mapping of the storage path to the volume was not verified, and the lease durations and the behavior of dependent controllers during a restart were not found. When sharding with a watch label selector, each shard elects its leader independently. A HelmChart generated from a HelmRelease takes its shard label from the HelmRelease's `.spec.chart.metadata.labels`, and a mismatch sends the chart to a different controller than the one that needs its artifact, though the documentation does not state the failure symptom. Production evidence is thin: one Cozystack README targets roughly 100 HelmReleases per shard, which is design intent and not a measured outcome, and no organization says it runs sharded Flux. Flux image automation kinds are `image.toolkit.fluxcd.io/v1` on the current spec pages, with older versions still in the API directory, and the release at which they graduated was not found. The official image update guide offers semver-selected release tags for production, a separate push branch so that changes can be reviewed before they apply, and reverting by narrowing the semver range, and no adopter write-up on reviewed promotion was found. For composites, Flux records what it applied in an inventory, so resources that Crossplane or kro create from a composite sit outside it, and the inference that Flux therefore needs no ownerReference or tracking annotation on them, unlike Argo CD, is unverified because no Flux page states it. Hand-written operators duplicate what composition could express, though a hand-written provider has its own traps, such as treating not-found as an error and breaking the create flow. ## 14. Getting started checklist and remaining unknowns

A sensible path for a first week looks like this, and each step ties to a pitfall above. First, decide whether you already operate Kubernetes; if not, the hosting cluster is your first cost. Second, start on v2 and read the upgrade guide as a map of what changed, since many online posts describe v1 claims and patch and transform. Third, install only the provider family members you need and decide your credential scope before creating any resource. Fourth, create one managed resource by hand and watch both `Synced` and `Ready` as it provisions, so you internalize the two-condition model. Fifth, set deletion safety early: management policies without Delete, or `Orphan`, for anything stateful, and Usages for dependency ordering. Sixth, try an import with Observe before promoting to `["*"]`. Seventh, author a small XRD and a one-step Composition, test it with `crossplane render`, and make sure every function passes through the incoming desired state. Eighth, decide whether Compositions update automatically or by pinned revision before you have consumers. Ninth, if you use Argo CD, apply the documented tracking, health-check and propagation settings. Tenth, alert on persistent `Synced=False` and read `AsyncOperation` for Upjet-based providers.

The wiki is honest about what it does not know, and the following unknowns affect real decisions. Several items that used to be unknown are now settled, and it helps to know which. The managed-resource poll interval is verified from source (one minute in crossplane-runtime and core, ten minutes in Upjet-based providers). The Pods guide in the docs does state a one-minute polling default for Crossplane, which agrees with the source, but the docs page that covers the provider poll interval states no default and so cannot be cited for the ten-minute figure, which rests on the provider's source. Backoff values were not verified. If you follow older Crossplane links, note that the pre-v2 `https://docs.crossplane.io/latest/concepts/...` pages return HTTP 404 with no redirect as of 2026-11-26, because the v2 reorganization moved that section into `composition/` and `managed-resources/` and the site's redirect rules cover only end-of-life versions, and several explicit rules in the redirect file point at targets that no longer exist. Use the `v1.20/concepts/` path for v1 behavior, which still answers, or the `/latest/composition/` and `/latest/managed-resources/` paths for v2, and expect search engines to surface dead pages for older questions. [[findings/the-old-crossplane-latest-concepts-urls-return-404-and-the-docs-redirect-rules-only-cover-end-of-life-versions]] Management policies are beta in v2.5, and activation policies and managed resource definitions are labelled alpha in the docs while the code says beta, with the Helm chart activating everything by default. Operations, the v2 type for running pipelines to completion for day-two tasks, are alpha: the CRDs ship only as `v1alpha1` behind the `--enable-operations` flag, the docs say alpha features may be removed or changed without notice, an Operation cannot delete resources, and it applies with forced ownership and no owner references. No tracking issue or schedule for graduating Operations to beta was found. The `LegacyCluster` scope exists only on the v1 XRD API, and the async `Synced` behavior remains unfixed as described in section 7. [[findings/crossplane-operations-are-alpha-and-cannot-delete-resources-or-set-owner-references]]

What is still open is narrower. Crossplane v2 behavior for several details (condition semantics, namespaced managed resource behavior when a provider is down, and how management policies interact with garbage collection when a namespace is deleted) rests on v1.20 pages, third-party blogs or the wiki's reading of reconciler source, and the garbage-collection interaction is consistent with the docs policy table but is stated by no docs page. Function-pipeline status propagation is better covered than before but not closed. The v2.5.0 source settles how a function's per-resource ready flag becomes the XR's `Ready` condition, and for `function-kro` the source shows how conditions are approximated from one run and which status paths reach the desired composite, but where `function-kro` marks each desired composed resource ready was not located, and no documentation of a standalone kro controller feeding a composite exists. Whether external writers on an XR lose fields (issue 7453) is open and unreproduced. Package dependency resolution is now covered for Providers and Configurations from the docs and the resolver source, as section 11 describes: the resolver never rewrites the Lock and creates only the first missing dependency, and version upgrades and downgrades are alpha. What remains open is the activation policy and history limit for Function packages, which the docs do not state, and the exact activation constants, which were in a source file the wiki could not read. Whether the Upjet runtime runs Terraform as a subprocess is also settled, as section 3 describes: it depends on a per-resource execution mode, although which official providers use which mode, and the memory and CPU cost of any of them, are not established. The redirect behavior of old concepts URLs is settled as described above. No source covered cloud API rate limits, a single Crossplane-specific performance or sharding guide, or what happens to a namespaced managed resource when its namespace is deleted while the provider is down. Elsewhere in the landscape, the thin spots are the ones that need a neutral third party or a measurement: no independent Argo CD versus Flux benchmark, no neutral comparison of Crossplane with Terraform or of Config Connector with Crossplane, no kro benchmark or named kro adopter, no first-party Flux postmortem, no measured Flux shard outcomes, no measured Config Connector drift latency, and a web search that returned nothing for several long queries, so those absences are unverified negatives and not proof. Crossplane's own admission webhooks are now covered: one fail-closed Usage webhook remains, and the XRD and Composition checks moved to CEL, though that was read on the main branch and not the v2.5.0 tag. Adopter claims remain self-reported, and although the wiki now has a handful of named adopters with numbers (Built Technologies, Consensys, SpareBank 1 Utvikling, SAP, Akamai), it still lacks a named, verified Crossplane case study with scale and incident data, and no organization-authored postmortem of a leaked or duplicated cloud resource. The named incident accounts it does hold (Skyscanner, Spotify and Jetstack, in section 11) concern Argo CD, Terraform and an admission webhook and not Crossplane, and no organization says it runs sharded Flux or has had an API Priority and Fairness incident tied to Flux. Check [[open-knowledge-gaps]] for the live list.
