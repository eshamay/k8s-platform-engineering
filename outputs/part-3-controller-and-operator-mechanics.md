# Part 3: Inside Controllers and Operators

> [!NOTE]
> **Audience:** Engineers with real Kubernetes operating experience (pods, deployments, services, RBAC, kubectl) who have not yet worked inside controllers, API machinery, or platform abstractions.<br>
> **Purpose:** Teach the handful of mechanics that every controller-based platform tool depends on, show how real tools implement them differently, and explain why most production failures are violations of those mechanics.<br>
> **Status:** Draft, part 3 of the tutorial series.<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** [[concepts/operator-pattern]], [[concepts/reconciliation-loop]], [[concepts/idempotency]], [[concepts/informers-reflectors-and-workqueues]], [[concepts/finalizers]], [[concepts/owner-references-and-garbage-collection]], [[concepts/conditions]], [[concepts/level-triggered-vs-edge-triggered]], [[concepts/pitfalls-and-case-studies]], and the example, finding, comparison, and decision pages linked inline.

## Why this part exists

If you have operated Kubernetes for a while, you already trust a quiet miracle. You delete a pod that belongs to a Deployment and a new one appears. You scale a Deployment from three replicas to five and two more pods show up. You never wrote a script to make that happen, and nothing you did resembles a command that runs once and finishes. A small program inside the cluster noticed that reality and your stated wish had drifted apart, and it kept acting until they matched.

That small program is a controller, and this tutorial's argument is that nearly everything interesting in the platform-engineering world is a controller wearing a different name. Flux, Crossplane, Argo CD, Cluster API, the AWS and Google Cloud service controllers, kro, and the operator that runs your team's database are all sets of controllers. Their quality depends on a short list of mechanics: reconcile loops that are safe to run any number of times, informer caches and rate-limited workqueues that feed those loops, finalizers that protect cleanup, owner references that tie children to parents, and status conditions that tell the truth about progress. The thesis of this part is that when one of these platforms fails in production, the failure is almost always a violation of one of those mechanics, and the fixes tools have added over the years are almost always guard rails around the same few ideas.

We will build the ideas from the ground up, because each depends on the one before it. We start with what a controller is, then the operator pattern that packages controllers for a domain, then the loop itself and the discipline of idempotency. After that comes the plumbing that feeds the loop, the rules for requeueing and errors, and the two deletion mechanisms, finalizers and owner references. We then turn to conditions, look at some real use cases, catalogue the pitfalls, compare how six tool stacks implement the mechanics, and finish with design principles. Earlier parts of the series introduced the universal control plane idea and the resource model; this part opens the box and looks at the machinery inside.

## 1. What a controller actually is

The Kubernetes documentation describes controllers with a thermostat. You set a temperature, which is your desired state. The thermostat measures the room, which is the current state. When the two differ it turns the heat on or off, and it keeps doing this forever. It does not complete a task and exit. In the documentation's words, controllers are control loops that watch cluster state and make changes where needed, moving current state closer to desired state. A cluster never has to reach a final stable state, and a controller keeps correcting failures indefinitely. The design also favors many small controllers that each own one aspect of the system, instead of one large controller that knows everything ([[concepts/reconciliation-loop]]).

The built-in Job controller is the simplest worked example. It watches Job objects. When it sees one that needs work, it creates pods by asking the API server to create them, and when the work finishes it removes the pods and reports status on the Job. It never starts a container itself. Kubernetes documentation contrasts this with controllers that touch an outside system directly, using the cluster autoscaler as the example, because adding a node means calling something outside the API server ([[examples/job-controller-acts-through-the-api-server-while-the-cluster-autoscaler-acts-directly]]). That contrast matters for the rest of this tutorial, because a database operator, a cloud-resource controller, and a GitOps controller are all of the second kind: they talk to some external system and record what they did.

Every controller has the same four parts. It has a source of desired state, which is the `spec` section of an object that users and tools write. It has a way to observe current state, either by reading other Kubernetes objects or by calling an external API. It has a function that computes the difference and acts to close it. And it has a place to write what it learned, which is the `status` section of the same object. The split between `spec` (intent, owned by users) and `status` (observation, owned by the controller) is enforced by a separate `/status` subresource with its own permissions, so a GitOps tool that re-applies a manifest cannot accidentally overwrite what a controller observed ([[concepts/spec-status-split]]).

There is one more property to absorb before going further: a controller is level-triggered. The terms come from electronics. An edge-triggered circuit reacts to a transition, such as the signal going high. A level-triggered circuit reacts to the current value, such as the signal being high. A level-triggered controller does not ask what just happened; it asks what is true now and what should be true, and it acts on the difference. The Kubernetes design archive says controllers are level-based to maximize fault tolerance, and the API conventions say the system's behavior is level-based and not edge-based ([[concepts/level-triggered-vs-edge-triggered]]).

The classic demonstration is a Deployment whose replica count is changed quickly from 1 to 5 and then to 2. A handler that applies each change as a delta can end at the wrong number if an event is lost or reordered, and in the HackerNoon example it can land at zero. A level-triggered controller compares the final desired value of 2 against what exists and acts on the gap, so it ends at 2 however many intermediate values it saw ([[examples/deployment-replica-changes-converge-to-the-final-count]]). The practical consequence for anyone who edits resources is that a rapid sequence of edits behaves like one edit to the last value. Convergence, the wiki's term for this, does not promise that every intermediate state is processed. It promises that the last declared state wins ([[concepts/eventual-consistency-and-convergence]]).

Kubernetes is a hybrid in practice, and this is worth stating carefully. Watches deliver events with low latency, and that is an edge-triggered optimization. But the event is treated only as a hint to look at an object, and the controller then reads the full state and enforces all of it. The design archive says watches restore the latency benefits of edge triggering without making correctness depend on them ([[decisions/events-as-hints-state-as-truth]]). Keep that sentence in mind, because the informer machinery in section 4 exists to deliver those hints cheaply.

## 2. The operator pattern: encoding runbooks as reconcilers

A controller for built-in kinds such as Jobs and ReplicaSets ships with Kubernetes. The operator pattern asks what happens when you apply the same idea to your own domain. The research dossier defines an operator as a controller that understands two domains: Kubernetes and something else, such as a database, a cloud API, or cluster lifecycle. The pattern pairs a custom resource definition, which adds a new kind to the API server, with a controller that watches instances of that kind and drives the world toward the declared spec. The runbook knowledge a human operator carries, how to install, upgrade, back up, and fail over, becomes code that runs continuously. The Kubernetes documentation puts it as software extensions that use custom resources to manage applications and their components, and describes operators as clients of the Kubernetes API that act as controllers for a custom resource ([[concepts/operator-pattern]]).

Here is the minimal picture. A team wants to offer a database without making every application team learn how to assemble it. They register a kind, say `PostgresCluster`, and an application team writes a small object stating the replica count and version they want. Once the definition exists, the API server serves the new kind like any built-in type: it is listed, watched, validated, covered by RBAC, written to the audit log, and stored in etcd. The definition supplies only the data model and the endpoint. All behavior lives in the controller, which watches these objects and reconciles each into child objects such as StatefulSets, Services, and Secrets, then reports progress in `status` ([[examples/postgrescluster-custom-resource-reconciled-into-child-objects]]).

```yaml
apiVersion: db.example.com/v1alpha1
kind: PostgresCluster
metadata:
  name: orders-db
  namespace: team-orders
spec:
  version: "16"
  replicas: 3
  backup:
    schedule: "0 2 * * *"
```

The object above is the entire interface the application team sees. Behind it, the operator creates the storage, the pods, the services, and the backup job, and it keeps them correct. The platform's quality now depends on the controller following the conventions for `spec`, `status`, and conditions, because the definition enforces none of that on its own. The Kubernetes documentation uses a hypothetical SampleDB resource to make the same point: a user edits a custom resource, and the operator creates the volume claims, StatefulSets, and Jobs needed to realize it. Runbook steps become reconcile logic instead of commands a human types ([[examples/database-operator-encodes-runbooks]]).

Frameworks exist so that nobody writes the plumbing by hand. Kubebuilder and the Operator SDK, both built on the controller-runtime library, scaffold Go projects, and equivalents exist for Python, Java, Rust, and .NET. The Operator SDK's capability model grades operators from Level 1 (basic install) through seamless upgrades, full lifecycle, and deep insights to Level 5 (auto pilot), which gives teams a shared vocabulary for maturity ([[entities/operator-sdk]], [[entities/kubebuilder]], [[entities/controller-runtime]]). The wiki notes that it is unclear how strictly those levels apply to composition-based operators, and that no source gives criteria for choosing a language or framework.

Platform tools are this same pattern specialized to a domain. Flux applies it to GitOps delivery, Crossplane to cloud-resource composition, Cluster API to cluster lifecycle, ACK to AWS resources, and kro to runtime-generated APIs. A Crossplane provider is described in the wiki as an operator whose domain is an external API ([[concepts/provider]]). That is why the mechanics in this tutorial carry across so much of the ecosystem, and why a failure mode learned in a hand-written Go operator tends to reappear in a commercial platform.

One piece of guidance is worth stating early. Not every automation deserves a custom resource, and the wiki's decision page records the trade: a hand-written operator gives full control and suits domain logic such as backup, failover, and schema migration, while composition-based tools suit work that is mostly assembling existing resources ([[decisions/build-a-custom-operator-or-compose-existing-resources]], [[comparisons/hand-written-operator-versus-crossplane-composition-versus-kro]]).

## 3. The reconcile loop and why it must be idempotent

At the heart of every controller is a function. In controller-runtime it is `Reconcile(ctx, req)`. It receives a request that contains only a namespace and a name, never an event type. It must read whatever state it needs, compare it to the spec, act through idempotent calls, update status, and return a result and an error ([[concepts/reconciliation-loop]]). That the request carries no event type is deliberate. The framework removes the temptation to write "if this was a create, do X; if it was an update, do Y," and that logic is the first thing a new operator author is tempted to write. The controller-runtime FAQ answers the question flatly: you should not, because reconcile functions should be idempotent and should always read all the state they need before writing updates ([[findings/event-specific-logic-in-reconcilers]]).

Idempotency means that running the same operation twice leaves the system in the same end state as running it once. A level-triggered loop can run at any time, any number of times, after a crash, with coalesced events, or twice in a row because a cache was slightly behind. If the reconcile function is not idempotent, the second run creates a duplicate or fails. The Kubernetes controllers page says controllers can fail and that Kubernetes is designed to allow for that, which is why the loop has to be a convergence process and not a script of one-shot commands ([[concepts/idempotency]]).

The wiki's idempotency dossier finds the property at three layers, and it helps to treat them separately because the difficulty rises with each.

The first layer is the loop itself: read everything you need, compute, then write. The second is the Kubernetes API. Deterministic object names turn the API server's optimistic locking (a scheme in which a write carrying a stale resourceVersion is rejected) and its name-uniqueness rule into a free duplicate check, because a second create of the same name fails loudly. The StatefulSet controller appends an ordinal to each pod name, so a second attempt to create `web-0` is rejected. The Deployment controller hashes the pod template into the ReplicaSet name, so the same template always maps to the same name. The ReplicaSet controller creates pods with generated names, so the name cannot reject a duplicate, and it instead records the creations it has requested and requeues until its cache catches up. That bookkeeping is called expectations: a per-object count of creates and deletes the controller has issued but not yet seen in its cache, so that it skips acting until the cache catches up ([[examples/built-in-controllers-use-deterministic-names-to-avoid-duplicate-children]], [[examples/how-core-controllers-handle-cache-lag]]). Server-side apply, covered in an earlier part, adds safe repeated writes and turns a clash with another writer into an explicit conflict ([[concepts/server-side-apply-and-field-ownership]]).

The third layer is the hard one: external cloud APIs. Creating a cloud resource is not naturally idempotent. If a controller calls a create API and crashes before it records the returned identifier, the next reconcile cannot tell whether the resource exists, and a blind retry can leak the first one. The wiki's dossier describes four answers, and they appear in different tools.

The first answer is to use deterministic or caller-chosen names, so that the same request always names the same resource. Config Connector acquires a same-named resource, and ACK adopts by identifier. This works only if the cloud API rejects a duplicate name or hands back the existing resource, and many cloud APIs generate their own identifiers or tolerate duplicate names, in which case a deterministic name protects nothing. The second answer is a persisted external identity, such as Crossplane's `crossplane.io/external-name` annotation, which the controller then uses for observe, update, and delete. It is reliable once written, but it is useless in exactly the failure that matters most: if the controller crashes after the cloud create succeeds and before it writes the annotation, the identity was never saved and the next pass has nothing to look up.

The third answer is to record intent before acting and to fail safe when the result is unknown. Crossplane writes `external-create-pending` before the create call and stops for a human if it later finds the marker with no recorded outcome. This prevents leaked duplicates, but the price is that every ambiguous case needs a person. The fourth answer is a server-side client token that lets the cloud itself recognize a retry, such as the `ClientToken` on the EC2 `RunInstances` call. It is the most robust option because the cloud does the deduplication, but it exists only where the provider built it, and the token must stay stable across retries of the same logical request.

The EC2 case is instructive. The caller supplies a unique token, the service stores the token atomically with the new resource, and a retry with the same token returns an equivalent response instead of an error. The AWS Builders' Library article that explains this rejects detecting duplicates by hashing the request, because two identical requests may be intentional, such as launching two identical instances. Only the caller can say that a request is a retry ([[examples/ec2-client-token-makes-a-retried-runinstances-call-safe]]). The wiki is careful to say that deriving such a token from a Kubernetes object's UID is an inference and not something a source shows a controller doing.

The Crossplane case shows the cost of the safe-failure option. Issue 3037 reports managed resources that stop reconciling after a provider restart. The provider writes the pending marker before the cloud create and a success or failure marker afterward. If it restarts between those writes, the next pass finds a pending marker with no outcome and blocks, with an event telling a person to remove the annotation if it is safe to proceed. A maintainer explained the reasoning: many cloud APIs return a generated ID, so if the response is lost there is nothing to look up, and a second create could leak the first resource. Failing safe prevents duplicates and leaked cost, but it does not scale, because every ambiguity needs a human ([[examples/provider-restart-blocks-a-crossplane-resource-on-external-create-pending]], [[findings/an-ambiguous-create-result-halts-reconciliation-until-a-human-intervenes]]).

SAP's BTP provider takes a middle road, and its design is worth reading as a pattern. Recovery runs only when the pending marker is present, which proves the provider itself started a create. It then searches by a business key such as a subdomain, requires the candidate's creation time to fall inside a window around the pending timestamp, and on a match writes the external name back and requeues. A candidate outside the window produces a warning and is not adopted ([[examples/sap-btp-provider-recovers-lost-ids-by-business-key-and-creation-window]]). The wiki frames the three approaches, halt, search, or tag, as an open decision with no verdict ([[decisions/recover-from-an-ambiguous-create-by-halting-searching-or-tagging]]).

A related failure needs no crash at all. A reconciler makes a successful create call and then fails to write the result into status, perhaps because of a conflict. The next pass sees no record and creates again. Crossplane's create-tracking annotations exist for exactly this case ([[findings/a-create-that-succeeds-while-the-status-write-fails-can-leak-an-external-resource]]). Retries compound the issue: blind retry is safe only when the target API is idempotent, which is why retry storms and idempotency are linked ([[findings/blind-retries-duplicate-side-effects-when-the-cloud-api-is-not-idempotent]]).

Idempotency also reaches into deletion and observation code. The Crossplane provider-development guide states the rule sharply: delete implementations must not return an error when asked to delete a non-existent external resource, and an observe call must report a missing resource as "does not exist" instead of as an error, because the shared reconciler uses that answer to decide whether to call create. A hand-written provider that returns not-found as an error never creates anything ([[examples/provider-authors-implement-an-external-client-behind-the-shared-managed-reconciler]], [[findings/hand-written-providers-that-treat-not-found-as-an-error-break-the-create-flow]]).

Idempotency is also what makes a simple availability story possible. The kube-rs guide observes that most controllers can run as a single replica: they are queue consumers, their watches reinitialize with current state on boot, and idempotent reconcilers make repeated work harmless, so a short outage delays convergence without breaking it ([[decisions/single-replica-versus-leader-election]]).

## 4. Informers, reflectors, caches and workqueues

Where do the requests that arrive at `Reconcile` come from? Imagine the naive design: every controller polls the API server asking for all objects of its kind. With thousands of objects and dozens of controllers, that would crush the API server and etcd behind it. The machinery in client-go, the Go client library, solves this by watching once and caching locally ([[concepts/informers-reflectors-and-workqueues]]).

The pipeline has named stages, and it is easiest to follow in order. A reflector performs an initial LIST to obtain a consistent snapshot, then opens a WATCH on the same resource, which is a long-lived HTTP stream of changes. Each change goes into a DeltaFIFO, a queue that keeps an ordered list of deltas per key and drops duplicate consecutive delete deltas. The informer's processing loop pops deltas, writes the object into a thread-safe local cache called the indexer (keyed by namespace and name, with optional secondary indexes by label, owner, or any custom field), and then calls any registered event handlers. Controller code reads through read-only listers that query the cache and never the API server.

```mermaid
flowchart LR
  A[API server] -->|LIST then WATCH| R[Reflector]
  R --> D[DeltaFIFO]
  D --> I[Informer loop]
  I --> X[Indexer cache]
  I --> H[Event handlers]
  H -->|key| Q[Rate-limited workqueue]
  Q --> W[Worker: reconcile]
  W -->|read| X
  W -->|write| A
```

The diagram follows one change from the API server to a reconcile. The two arrows leaving the worker matter most: reads come from the local cache, which is cheap, while writes go straight to the API server. The event handlers are meant to do almost nothing, because the client-go architecture document states that handlers only add an object's key to the work queue. A worker then takes a key, reads the current object from the cache, and reconciles it. The secondary explainer in the wiki's dossier compresses the design into one watch per resource type, one cache per process, one reconcile per key, and one rate limiter per workqueue.

In controller-runtime you rarely build any of this by hand. Declaring that a controller `Owns()` a child type registers an informer on that type and maps each child event back to its owner's key, so a change to a Job triggers a reconcile of the CronJob that created it. A field indexer on the owner reference lets the reconciler list a CronJob's Jobs from the cache without scanning every Job ([[examples/kubebuilder-owns-and-a-field-indexer-wire-child-changes-to-the-owner]]). The Kubebuilder CronJob tutorial, which the dossier calls the best first hands-on exercise, walks through the whole path from API types to a tested controller ([[examples/kubebuilder-cronjob-tutorial-shows-the-end-to-end-shape-of-a-go-operator]]).

The workqueue deserves its own paragraph, because its guarantees are what make the loop safe. It offers a base queue, a delaying queue (`AddAfter`), and a rate-limiting queue (`AddRateLimited`, `Forget`), and it gives three guarantees: items are served in fair order, items added before they are processed are deduplicated, and one item is never processed concurrently. Many events for the same object collapse into one key, and a reconciler never races with itself on that key. The default limiter combines per-item exponential backoff with an overall token bucket (a limiter that refills a fixed number of permits per second), and the wiki's dossier extracted numbers of 5 milliseconds base, a 1000 second cap, 10 per second, and a burst of 100. A later recheck against controller-runtime v0.25.3 (published 2026-11-16) adds a detail that is easy to miss: the framework's `UsePriorityQueue` option defaults to true, and with that queue the default limiter is the per-item exponential limiter alone, with the same 5 millisecond base and 1000 second cap but no overall token bucket. The 10 per second and burst of 100 bucket applies when the priority queue is switched off and client-go's default controller rate limiter is used, and that bucket figure was read from client-go's main branch and not from a pinned release tag, so check your own version before quoting it ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]]). Authors using the raw queue must call `Done()` and `Forget()`, or items stay stuck or keep their accumulated backoff, though frameworks like controller-runtime make those calls for you ([[findings/skipping-done-or-forget-on-the-workqueue-leaves-items-stuck-or-retrying]]).

Two more details complete the picture. The first is how a watch recovers. The resource version is the cursor that lets a watch resume. When the cursor is too old, the API server answers 410 Gone and the client must relist. If many clients lose their watches at the same moment, they all relist at once, which is expensive for the API server and etcd. Watch bookmarks refresh the cursor during quiet periods, the server's watch cache lets clients resume from recent versions, and jittered backoff spreads relists out ([[findings/an-expired-resourceversion-forces-a-relist-and-synchronized-relists-can-storm]]).

The second detail is cache lag, which is the root of one of the most common bugs. Because the cache is updated from the watch stream, it can trail the controller's own writes. If a controller creates a pod and reconciles again before the cache shows it, the gap still appears to exist and the controller may create a second pod. A simulation in one source shows a regulator that cannot see its own recent writes overshooting its target. The fix in the built-in controllers is the pair of techniques from section 3: deterministic names, or expectations, which are per-object counters of the creates and deletes the controller has issued but not yet seen in its cache, so the loop skips acting until the cache catches up and confirms its own writes. Mature controllers are therefore level-based logic plus bookkeeping about in-flight actions ([[findings/stale-cache-and-double-action]]).

Kubernetes v1.36 added a built-in mitigation that moves part of this bookkeeping into the informer layer, tracked by KEP 5647 (Stale Controller Handling). The DaemonSet, StatefulSet, ReplicaSet, and Job controllers inside kube-controller-manager now record the resource version of each write they make, and before syncing an object they check whether their cache has reached that version. If the cache is behind, the controller takes no action on that object and retries it later, so the skip is keyed on resource version and is not a sleep or a timer.

The mechanism has three layers. A feature gate is an on/off switch for a Kubernetes feature, which lets a new behavior ship disabled or enabled and be toggled without changing the binary. In client-go, the `AtomicFIFO` feature gate (Beta, on by default from 1.36) makes the informer queue apply list and relist batches atomically, and a store can report the latest resource version it has seen. Each of the four controllers then has its own `StaleControllerConsistency<API type>` gate, also Beta and on by default from 1.36, which depends on `AtomicFIFO` and can be switched off individually. A client-go helper named `ConsistencyStore` is described for authors of other informer-based controllers.

When a DaemonSet or Job sync is deferred, the controller increments a skip counter, `daemonset_controller_stale_sync_skips_total` or `job_controller_stale_sync_skips_total` according to the changelog, and the gauge `informer_store_resource_version` shows how far the cache has progressed. The v1.36 release blog uses shorter names for both metrics, so a dashboard built from the blog will match nothing, and the wiki found no changelog names for the ReplicaSet and StatefulSet counters ([[examples/kubernetes-v1-36-daemonset-statefulset-replicaset-and-job-controllers-skip-a-sync-until-the-cache-catches-up-with-their-own-write]], [[findings/the-kubernetes-v1-36-staleness-blog-names-metrics-differently-from-the-changelog-and-source]]). This generalizes the expectations idea rather than replacing it, and the wiki did not find a controller-runtime implementation of the same behavior, so a controller built on that library still needs its own protection. Controller-runtime's cache-backed client reads from the cache while writes and status updates go directly to the API server, so an authoritative read needs an explicit uncached reader.

There is a cost to all this caching. The cache holds every watched object with no eviction, so memory grows with the number of objects watched, and the practical advice from tools reflects it: Argo CD recommends sharding and setting `GOMEMLIMIT`, and Flux exposes Helm cache flags and warns that in-memory artifact storage counts against pod memory ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]). Resync, a periodic replay of cached objects to handlers, is usually disabled. Sources disagree on whether it is a useful defense against reconciler bugs or a common misunderstanding, and the wiki records that no source explains whether it replays the cache or refetches from the server ([[decisions/keep-informer-resync-disabled-or-set-a-periodic-resync]]).

## 5. Requeue, error handling, backoff and terminal errors

At the end of every pass, the reconciler tells the workqueue what to do next, and the choices are a frequent source of confusion. The wiki's convergence dossier maps return values this way: an empty result and a nil error mean the object has converged and nothing more is needed until the next watch event. A `RequeueAfter` delay means the object is healthy but waiting, for example for a dependency. A non-nil error means this attempt failed, and the item returns to the queue with exponential backoff. Controller-runtime also offers a `TerminalError`, which is logged and counted but not retried, and it marks the older `Requeue: true` as deprecated ([[decisions/choose-error-requeueafter-or-terminalerror-in-a-reconciler]]).

```go
func (r *DBReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var db dbv1.PostgresCluster
    if err := r.Get(ctx, req.NamespacedName, &db); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)   // gone: nothing to do
    }
    if !specIsValid(&db) {
        return ctrl.Result{}, reconcile.TerminalError(errors.New("invalid spec"))
    }
    ready, err := r.ensureChildren(ctx, &db)
    if err != nil {
        return ctrl.Result{}, err                          // failed: backoff applies
    }
    if !ready {
        return ctrl.Result{RequeueAfter: 30 * time.Second}, nil // waiting, not failing
    }
    return ctrl.Result{}, r.updateStatus(ctx, &db)
}
```

The sketch is illustrative and compresses a real controller, but it shows the four exits. A missing object is not an error, because the object may simply have been deleted. An invalid spec is a permanent problem that retrying will not fix, so it is marked terminal. A real failure returns the error and lets the queue back off. A healthy but unready situation returns a delay with no error. A common mistake is to collapse the last two. A third-party guide the wiki cites puts the rule well: errors should mean the reconcile attempt failed, not "come back in thirty seconds." Returning an error for a waiting state triggers backoff and generates noisy failure signals even though nothing failed ([[findings/errors-used-as-timers-in-reconcilers]]).

Sources once disagreed about `Result{Requeue: true}`, and a later check of controller-runtime v0.25.3 settles the question. The package reference said it produces a rate-limited requeue, while a summary of controller-runtime issue 808 read it as an immediate requeue without backoff. The source code sides with the package reference: the handler adds the request with `RateLimited: true`, so the controller's rate limiter chooses the delay, and the per-item failure counter is not reset on that path. A reconciler that returns `Requeue: true` on every pass therefore waits longer each time. Only `RequeueAfter` calls `Forget` first, which clears the failure history and then waits exactly the duration you asked for, and it takes precedence over `Requeue` when both are set. The `reconcile_total` metric labels these paths `error`, `requeue_after`, `requeue`, and `success`, so you can tell them apart in monitoring. The wiki could not locate where the older "immediate" reading came from, because the body of issue 808 only says it is unclear which returns force a requeue with or without backoff and the comment thread was not read. The field is also marked deprecated in favor of `RequeueAfter`, so an author who uses it for planned polling accumulates backoff and never gets a steady cadence, and new code should prefer an error or `RequeueAfter` ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]], [[findings/the-requeue-true-result-is-deprecated-and-described-inconsistently]]).

Why does any of this matter beyond tidiness? Because a level-triggered loop has no built-in notion of giving up. A reconcile that always fails retries forever. The controllers the wiki surveys limit that behavior in different ways, which is where the tools start to diverge ([[findings/failure-retry-loops-and-backoff]]). Flux has a `retryInterval` separate from its success `interval`. Argo CD does not re-sync the same commit and parameters after a failed automated sync unless self-heal is enabled, although a retry policy with exponential backoff can also be configured. The wiki pages word the condition slightly differently, so check the Argo CD documentation for your version. Config Connector caps its exponential backoff at two minutes. kro combines exponential backoff from 200 milliseconds to 1000 seconds with a token bucket of 10 events per second and a burst of 100, and drops an item after 20 retries. Those values were first read from kro's unreleased "next" documentation and are now confirmed on the released v0.10.0 tuning page (v0.10.0 shipped on 2026-11-10), which also gives the instance requeue interval as 3 seconds, doubling with backoff up to five minutes and resetting on progress. The wiki's comparison table lays these out side by side and notes that values come from fetched pages and may change by version ([[comparisons/retry-and-backoff-controls-across-tools]], [[comparisons/reconcile-cadence-and-off-switches-across-tools]]). Permanent errors such as an invalid spec should stop consuming reconciles, while transient errors should retry with backoff so a recovering dependency is not overwhelmed.

Two further rules protect the whole queue. First, never block inside a reconcile. A worker that sleeps, polls, or waits for something occupies one of a limited number of workers, and because a key is never processed concurrently, a slow object delays unrelated objects. The Google Cloud guidance advises asynchronous sync loops that do not block on errors; the standard alternative is to return a requeue and let the worker move on ([[findings/blocking-on-errors-inside-the-sync-loop-stalls-every-other-object]]). The Cluster API Machine controller is a good example of waiting done correctly: it sets owner references, waits for infrastructure and bootstrap data to be ready, and matches nodes to provider IDs, with the waiting expressed through state read on each pass and not through a held-open operation ([[examples/cluster-api-machine-controller-waits-for-infrastructure-and-bootstrap-data]]).

Second, do not wake yourself up. A controller can generate the events that trigger it: status writes that retrigger reconciles, accidental changes to the spec, noisy child objects watched through `Owns()`, an aggressive `RequeueAfter`, or logic that depends on individual events. The result is a hot loop that burns CPU and API capacity while changing nothing of substance ([[findings/self-triggered-reconcile-loops-generate-their-own-events]]). The most common instance is writing status through the main resource. Without the status subresource, a status write is a write to the whole object, which bumps `metadata.generation`, fires the controller's own watch, and starts another pass. With the subresource enabled, a status patch updates only status and leaves the generation alone ([[findings/status-writes-through-the-main-resource-retrigger-reconcile-loops]]). The mitigations are a generation-changed predicate on watches, the status client, patches in place of full updates, and jitter on requeues.

## 6. Finalizers: guarding external cleanup

Everything so far concerns creating and maintaining things. Deletion is where controllers face a new problem. When you delete an object, the API server removes it from etcd immediately, and a controller watching it sees only that it is gone, with nothing left to read. If that object represented an RDS instance, the controller has just lost the record of what to delete. Finalizers solve this ([[concepts/finalizers]]).

A finalizer is a string in `metadata.finalizers`. While the list is non-empty, Kubernetes will not remove the object. When a client deletes an object that carries finalizers, the API server sets `metadata.deletionTimestamp`, returns HTTP 202, and leaves the object visible in a Terminating state. Controllers that watch the object see the timestamp, do their cleanup, and remove their own entry from the list. When the list is empty, the object is deleted. A delete becomes a mark followed by a removal, and the controller sees the delete as an update. The simplest built-in case is `kubernetes.io/pv-protection`, which keeps a PersistentVolume that a pod is using from vanishing. The object is only a record, and the real asset is the disk ([[examples/pv-protection-finalizer-keeps-an-in-use-volume-from-vanishing]]).

The API server enforces a few rules that determine how controllers must be written. Once `deletionTimestamp` is set, no one can add a new finalizer, and the only permitted edit is removal. Custom finalizer names must be qualified, such as `example.com/cleanup`. The consequence for controller design, stated bluntly by one tutorial, is that the finalizer must be on the resource before the delete request arrives ([[findings/a-finalizer-added-after-the-delete-request-is-too-late-and-new-ones-are-refused]]).

The standard Kubebuilder reconcile pattern therefore reads the object and branches on `deletionTimestamp`. The Kubebuilder book calls finalizers asynchronous pre-delete hooks.

```go
if db.DeletionTimestamp.IsZero() {
    // Not being deleted: make sure our finalizer is present BEFORE creating anything external.
    if !controllerutil.ContainsFinalizer(&db, finalizerName) {
        controllerutil.AddFinalizer(&db, finalizerName)
        if err := r.Update(ctx, &db); err != nil { return ctrl.Result{}, err }
    }
    // ...create or update the external resource...
} else if controllerutil.ContainsFinalizer(&db, finalizerName) {
    // Being deleted: clean up first, then release the object.
    if err := r.deleteExternal(ctx, &db); err != nil { return ctrl.Result{}, err }
    controllerutil.RemoveFinalizer(&db, finalizerName)
    return ctrl.Result{}, r.Update(ctx, &db)
}
```

The first branch adds the finalizer on the first pass, before any external work, so the guard is in place before there is anything to guard. The second branch runs only when deletion has begun: it deletes the external resource, and only on success removes the finalizer so the API server can finish the delete. Three details from the wiki's sources keep this safe. The cleanup must itself be idempotent, because the loop may run it more than once. It must treat an already-deleted external resource as success. And the controller needs RBAC permission to update the `finalizers` subresource ([[examples/kubebuilder-reconcile-adds-a-finalizer-before-external-work-and-removes-it-after-cleanup]]). Authors recommend finalizers for external resources, cross-namespace management, and audit logging, and not for in-cluster cleanup that garbage collection already handles.

The same mechanism, applied by platform tools, produces their deletion behavior. Crossplane keeps a finalizer on a managed resource until the external resource is fully gone, and its default `deletionPolicy` is Delete, with Orphan to keep the cloud resource. ACK deletes the AWS resource and then the Kubernetes object by default, and a `deletion-policy: retain` annotation keeps the AWS resource, which the ACK guide recommends for migrating between clusters and for protecting buckets and databases. Config Connector deletes the Google Cloud resource by default, and a `deletion-policy: abandon` annotation keeps it ([[examples/crossplane-ack-and-config-connector-delete-the-cloud-resource-before-the-kubernetes-object]]). The wiki records that the ACK, Config Connector, and kro pages do not say how their finalizers are named or removed, so a detailed comparison would need live objects or source code.

Argo CD uses the finalizer as an ownership switch. The `resources-finalizer.argocd.argoproj.io` finalizer on an Application makes deleting the Application also delete the resources it deployed. Deleting an ApplicationSet with `--cascade=orphan` leaves the Applications in place, but each still carries the finalizer, so removing one of them later still deletes its workloads. Setting `preserveResourcesOnDeletion` stops the finalizer from being added in the first place ([[examples/argo-cd-resources-finalizer-cascades-an-application-delete-to-its-workloads]]). The lesson for platform teams is that orphaning the parent does not remove its responsibility for the children; the policy must be changed before anything is deleted.

Finalizers are also the most familiar source of operational pain. A finalizer works only while its controller runs. When the controller is missing or failing, the object stays Terminating forever ([[findings/finalizers-strand-objects-in-terminating-when-the-controller-is-missing-or-failing]]). Several variations appear in the wiki's evidence. A cleanup that always errors, or that fails when the external resource is already gone, strands the object ([[findings/cleanup-that-always-errors-or-assumes-the-external-resource-exists-strands-the-object]]). Deleting a cluster that hosts Config Connector stops the controller, leaving the Google Cloud resources it managed behind and still billing, according to one consultancy article that the wiki flags as limited evidence ([[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]]). Crossplane's documentation warns that removing a provider before its managed resources may abandon the cloud resources ([[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]]). And a credentials Secret without a finalizer can disappear during namespace deletion, because objects in a deleted namespace go in arbitrary order, leaving managed resources unable to authenticate to the cloud API they must call to finish deleting ([[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]]). The remedy that issue weighs, finalizer protection on the Secret, credential caching, or ordered teardown, is itself an open decision ([[decisions/protect-shared-credentials-with-finalizers-caching-or-ordered-teardown]]).

When you face a stuck object, the wiki's guidance is an order of operations. Read `metadata.finalizers` on the object and its dependents, check owner references, find the controller that owns each finalizer, and read its logs. Forcing a finalizer off, by patching the list empty, or for a namespace by editing the `finalize` subresource, is the last resort, because it skips the cleanup the finalizer guarded and can leak billing resources or corrupt data ([[examples/diagnosing-a-pod-stuck-terminating-from-finalizer-to-force-delete]], [[examples/stuck-terminating-namespace-fixed-through-the-finalize-subresource]], [[findings/forcing-a-finalizer-off-skips-cleanup-and-can-leak-billing-resources-or-corrupt-data]]). The wiki frames whether to force or repair as an open judgment call where sources agree on the preference order but not on a threshold ([[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]). A practical rule from the pitfalls dossier is to uninstall controllers only after their custom resources are deleted.

## 7. Owner references and garbage collection, and the inventory alternative

Finalizers handle things outside Kubernetes. For child objects inside the cluster, Kubernetes has a lighter mechanism. Each object can carry `metadata.ownerReferences`, entries that name an owner by API version, kind, name, and UID. Delete the owner and the garbage collector deletes the dependents ([[concepts/owner-references-and-garbage-collection]]).

```yaml
metadata:
  name: orders-db-statefulset
  ownerReferences:
    - apiVersion: db.example.com/v1alpha1
      kind: PostgresCluster
      name: orders-db
      uid: 3f1c9a52-8a1e-4b9f-9d0f-0c2b7e5f1a11
      controller: true
      blockOwnerDeletion: true
```

The snippet shows the reference a controller writes on a child it creates. The UID identifies one specific incarnation of the owner, not just its name. `controller: true` marks the single managing owner, since a dependent may have many owners but only one controller owner. `blockOwnerDeletion: true` lets this dependent hold up foreground deletion of its owner. In controller-runtime, `controllerutil.SetControllerReference` writes this entry, and the same reference lets an `Owns()` watch map child events back to the owner, so one call provides both cleanup and event routing. Kubernetes sets these references itself for ReplicaSets, DaemonSets, Deployments, Jobs, CronJobs, and ReplicationControllers ([[examples/controller-runtime-sets-a-controller-reference-so-deleting-the-custom-resource-tears-down-its-children]]).

The everyday example is deleting a Deployment. A Deployment owns its ReplicaSets, and each ReplicaSet owns its pods. In the default background mode, the API server removes the Deployment at once, and the garbage collector then finds ReplicaSets whose owner is gone and deletes them, which leaves the pods ownerless so they are collected too. Nothing in your delete call named a ReplicaSet or pod ([[examples/built-in-workload-controllers-cascade-a-deployment-delete-through-replicasets-to-pods]]). The garbage collector is itself a controller. A graph builder watches all resources through monitors and keeps a dependency graph, feeds queues for deletion and orphaning, remembers owners already confirmed gone, and classifies each reference as dangling, waiting on dependent deletion, or solid ([[examples/the-garbage-collector-builds-a-dependency-graph-from-watch-events-and-sorts-references-into-three-classes]]). It is level-based and cache-driven like every other controller here.

The propagation mode on a delete decides the ordering. Background, the default, deletes the owner immediately and cleans dependents later. Foreground sets a `foregroundDeletion` finalizer on the owner and removes it only after dependents with `blockOwnerDeletion=true` are gone. Orphan uses the `orphan` finalizer to strip references and leave dependents behind ([[comparisons/background-foreground-and-orphan-propagation-modes]], [[examples/kubectl-cascade-modes-compared-in-a-hands-on-lab]]). Notice that two of the three modes are implemented with finalizers, which is why the two mechanisms are best learned together. The pitfalls follow from the modes. Background deletion gives no ordering between dependents, so a child that must go before its sibling needs foreground deletion ([[findings/background-deletion-gives-no-teardown-ordering-between-dependents]]). Foreground waits only for dependents with `blockOwnerDeletion` set to true ([[findings/foreground-deletion-waits-only-for-dependents-with-blockownerdeletion-true]]). Some client libraries default to a different propagation policy than kubectl, so a delete from code can orphan dependents that the same delete from kubectl would have removed ([[findings/api-client-default-propagation-policy-can-differ-from-kubectl-and-orphan-dependents]]). Orphaned dependents then keep running with empty owner references until someone deletes them by hand ([[findings/orphaned-dependents-keep-running-with-empty-owner-references-until-someone-deletes-them]]).

Namespace rules cause a particularly quiet failure. A namespaced dependent may have a cluster-scoped owner or an owner in its own namespace, and a cluster-scoped dependent may only have a cluster-scoped owner. The documentation says cross-namespace owner references are disallowed by design; one that points to a namespaced owner in a different namespace is treated as absent, since Kubernetes v1.20 the API emits `OwnerRefInvalidNamespace` events, and, as the wiki's finding puts it, a dependent whose owner is treated as absent can be collected ([[findings/cross-namespace-owner-references-are-treated-as-absent-and-the-dependent-can-be-collected]]). Controllers that need to relate objects across namespaces should use labels plus finalizer-based cleanup. Two other traps involve identity: recreating an owner under the same name gives it a new UID, so old dependents are not adopted ([[findings/recreating-an-owner-with-the-same-name-gives-a-new-uid-and-strands-its-old-dependents]]), and backup and restore tools can strip references, so controllers must be prepared to re-reconcile them. The Cluster API book says explicitly that owner references should be re-reconciled if they are lost ([[findings/backup-and-restore-tools-can-strip-owner-references-so-controllers-must-re-reconcile-them]]). Disputed detail also exists: the Kubernetes documentation says an admission controller restricts who can set `blockOwnerDeletion` based on delete permission on the owner, while one tutorial claims the controller needs update permission on the owner's `finalizers` subresource, a claim the wiki flags as unverified ([[findings/blockownerdeletion-needs-permission-on-the-owner-and-the-failure-mode-is-disputed]]).

Owner references have a natural limit: they cover in-cluster, same-namespace parent-child cleanup. Cloud resources, cross-namespace relationships, and ordered shutdown fall to finalizers. That is why GitOps tools mostly avoid owner references and use an inventory instead. Flux records what it applied in `.status.inventory` of each Kustomization. With `prune` enabled, objects present in an earlier inventory but missing from the current source revision are removed. A per-object annotation exempts an object from pruning, and a `deletionPolicy` (MirrorPrune by default, Delete, WaitForTermination, or Orphan) decides what happens to the managed objects when the Kustomization itself is deleted. Argo CD identifies its managed objects through tracking and cascades an Application delete only when the Application carries its resources finalizer ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). The wiki notes that it could not confirm whether Flux ever sets owner references. The comparison shows why: the GitOps tools own sets of objects that Kubernetes does not know are related, so they bring their own list ([[comparisons/how-tools-garbage-collect-owner-references-inventory-and-finalizers]]). An inventory, however, introduces the danger that a loop with prune permission deletes whatever it no longer sees in desired state ([[findings/a-level-based-loop-deletes-what-it-no-longer-sees-in-desired-state]]).

Cluster API treats ownership as a core contract. The chain is Cluster, MachineDeployment, MachineSet, Machine, with infrastructure and bootstrap objects owned by the Machine. Owner references drive cluster deletion, and `clusterctl move` uses them to relocate objects to another management cluster in dependency order ([[examples/cluster-api-owner-reference-chain-drives-cluster-deletion-and-clusterctl-move]]).

## 8. Conditions: status as an API for humans and machines

A controller that does everything right but tells no one is nearly useless, so the last mechanic is reporting. A condition is one entry in `.status.conditions`. It has a `type` (a PascalCase name such as `Ready`), a `status` of `True`, `False`, or `Unknown`, a machine-readable `reason`, a human-readable `message`, a `lastTransitionTime`, and ideally an `observedGeneration`. The list behaves like a map keyed by type, and a missing condition is equivalent to `Unknown` ([[concepts/conditions]]).

```yaml
status:
  observedGeneration: 7
  conditions:
    - type: Ready
      status: "False"
      reason: DatabaseProvisioning
      message: "Waiting for primary to accept connections"
      lastTransitionTime: "2026-11-25T09:14:03Z"
      observedGeneration: 7
```

This is what a healthy-but-not-yet-ready object looks like. The `reason` is a short CamelCase token for programs to match on, the `message` is for humans, and the `observedGeneration` records which spec generation this statement was made about. That last field is the most important and the most commonly forgotten. `metadata.generation` increases whenever the spec changes. If a controller copies the generation it has processed into status, a reader can compare the two numbers: if `generation` is greater than `observedGeneration`, the status describes an older spec and should not be trusted. Without it, a stale `Ready=True` looks identical to a current one ([[findings/missing-observedgeneration-hides-stale-status]]). ACK issue 1583 is the wiki's clearest example, where conditions without `observedGeneration` left Argo CD maintainers comparing managed-field timestamps, which they called fragile ([[decisions/publish-synced-false-at-reconcile-start]]).

Many tools read conditions, so slips in convention are not private. Flux, Argo CD, kstatus (a library from the cli-utils project that infers readiness from standard status fields), Cluster API, and Crossplane all use them to decide readiness, which is why free text in a `reason` breaks consumers ([[findings/free-text-in-a-condition-reason-breaks-consumers]]). Everyday consumers are mundane: `kubectl rollout status` reads the Deployment's `Progressing` condition and fails when the controller sets it to `False` with reason `ProgressDeadlineExceeded`, which happens when a rollout makes no progress for the `progressDeadlineSeconds` period that defaults to 600 ([[examples/deployment-progress-deadline-sets-progressing-false-for-a-stalled-rollout]]). A Deployment's conditions describe state over time, not just binary health: a rollout can be `Available` and still `Progressing`, and a stall is an explicit condition with a reason and not merely an absence. The shared `metav1.Condition` type, created through KEP-1623 (a Kubernetes Enhancement Proposal, the project's design-document process), standardizes the structure, but adoption is voluntary, so older APIs keep their own forms ([[examples/deployment-status-reports-ready-replicas-against-spec-replicas]]).

The vocabularies differ by stack, and these differences are worth knowing before you build automation on top of any of them ([[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]):

- Crossplane separates `Synced` (the provider could reconcile) from `Ready` (the external resource is usable). During a slow provision you see `Synced=True` and `Ready=False`, which means the controller is working and the thing is not yet usable ([[examples/crossplane-database-claim-reports-synced-and-ready]]).
- ACK adds `ACK.ResourceSynced`, `ACK.Terminal`, and `ACK.Recoverable`, keeping `Ready` as the roll-up. Separating terminal from recoverable errors lets automation decide between waiting and paging a human, which a single `Ready=False` cannot support ([[examples/ack-splits-terminal-and-recoverable-errors-into-separate-conditions]]).
- Config Connector uses one `Ready` condition whose reason carries the phase: `Updating`, `UpToDate`, or `UpdateFailure`. That is simple for consumers, but `Ready=False` means both working and failed, so readers must inspect the reason ([[examples/config-connector-ready-condition-moves-through-updating-uptodate-and-updatefailure]]).
- Flux uses `Ready` with `Reconciling` and `Stalled`. A HelmRelease also records attempts, failure counters, and the last attempted revision, so status serves as an audit trail for people and as health for tools ([[examples/flux-helmrelease-status-records-attempts-and-health]]).
- kro lets the author of a ResourceGraphDefinition (kro's custom resource that declares a group of related resources as one new API) define instance conditions with CEL expressions (the Common Expression Language Kubernetes uses for inline expressions), including a `readyWhen` per resource; if omitted, a resource counts as ready as soon as it exists, a weak default for slow cloud resources ([[examples/kro-rgd-authors-define-instance-conditions-with-cel-and-readywhen]]).
- Cluster API moved to `metav1.Condition`, split `Available` from `Ready`, and added operation conditions such as `ScalingUp` and `Remediating`, because one mandatory summary `Ready` could not distinguish a broken cluster from a healthy one that was mid-upgrade ([[examples/cluster-api-adds-available-and-operation-conditions-beside-ready]]).

Each design trades something away, and the pitfalls cluster around the trade-offs. A summary condition can stay true while long asynchronous work is running. In provider-aws issue 2287, a team changed an AWS MSK cluster configuration that took more than an hour to apply. The controller reported the resource as up to date, `Synced` stayed `True` for the whole hour, and an `AsyncOperation` condition that did read `Ongoing` sat outside the alert surface the team watched ([[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]], [[findings/a-summary-condition-can-stay-true-while-a-long-async-operation-is-running]]). The inverse is also dangerous: `Synced=False` with `Ready=True` means the thing exists but the controller can no longer manage it, so drift is not corrected, a silent failure whose typical causes are expired credentials or removed permissions ([[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]]).

Polarity is a more subtle trap. The kstatus library favors an abnormal-true pattern, where conditions appear only when something needs attention, but then a missing condition looks healthy and a stopped or lagging controller is indistinguishable from a working one unless generations are compared. The API conventions and the Cluster API proposal lean toward positive names such as `Ready` and `Available`. The wiki records the disagreement without picking a winner ([[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]], [[decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types]]). Related hazards include premature readiness, where kstatus treats a new object with no conditions as reconciled and Flux can move to dependents too early ([[findings/premature-readiness-in-kstatus-based-tools]]), and the habit of bumping `lastTransitionTime` on every loop, which turns a transition timestamp into a heartbeat ([[findings/updating-lasttransitiontime-on-every-reconcile-turns-a-condition-into-a-heartbeat]]). A generic agent also cannot know what ready means for a custom resource, which is why Crossplane's Argo CD guide prescribes custom Lua health checks, small scripts that Argo CD runs to decide whether a resource is healthy ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]).

The remedies are cheap compared with the failures. Write an initial `Unknown` condition on first visit so that a started controller is visible. Always set `observedGeneration`. Put long-running progress in a place consumers will read. And if you are building on top of another tool's status, learn which condition that tool considers authoritative. The wiki also records that operators publishing no standard status or metrics leave their state opaque, which is the failure of not doing any of this ([[findings/operators-that-publish-no-standard-status-or-metrics-leave-their-state-opaque]]).

## 9. Use cases: kubebuilder operators, database operators, cluster add-ons, Cluster API

Mechanics become easier to remember when you see them working together, so here are four families of real use. The wiki is candid that several of these come from documentation and explainers and not from named adopters' postmortems.

The first family is the custom operator you write yourself. The Kubebuilder CronJob tutorial rebuilds the CronJob controller and shows the full pattern. The reconciler fetches the primary object, lists the children it owns through a field index, updates status, prunes old children, and returns `RequeueAfter` for the next scheduled run. Child objects carry controller references so that deleting the parent cascades. Status is written through the status subresource. The tutorial itself notes that if something else changes in between, the controller may reconcile again sooner, which shows that a requeue time is a hint and not a guarantee. Every mechanic in sections 3 through 8 appears in this one small controller. The Kubebuilder book also shows applying status through server-side apply with a named field owner, recommended when several controllers or users manage one resource, while for a sole-owner controller it says traditional updates are simpler and sufficient ([[examples/kubebuilder-controller-applies-status-with-a-field-owner]]).

The second family is database and stateful-data operators, the classic case because a database needs human operational knowledge a Deployment cannot express: provisioning, high availability, version upgrades, backups, and schema migrations. The CNCF explainer names Postgres operators and the Elastic operator as well-known examples that automate provisioning, upgrades, and backups ([[examples/stateful-data-services-run-on-postgres-and-elastic-operators]]). The wiki's caveat applies here: the dossier named these operators without reading their documentation, so their object counts, failure behavior, and adopters are unknown. What the evidence does support is the nature of the problem. The stakes of deletion are high, so finalizers and clear retain-or-delete policies matter most here, and the wiki records that deleting stateful resources through a provider can lose data, with Config Connector's best practices naming Spanner instances and Bigtable tables as examples ([[findings/deleting-stateful-resources-through-a-provider-can-lose-data]]).

The third family is cluster add-ons. Installing and upgrading monitoring, certificate management, and a service mesh were once manual runbooks. The CNCF explainer names the Prometheus Operator for monitoring, cert-manager for certificate issuance and renewal, and the Istio operator for mesh install and upgrade. Each exposes custom resources, so an administrator declares what is wanted and the operator performs install and day-2 work continuously ([[examples/cluster-add-on-operators-turn-install-and-day-2-work-into-objects]], [[entities/prometheus-operator]], [[entities/cert-manager]]).

The fourth family is Cluster API, which treats cluster lifecycle as the operator domain. A management cluster holds Cluster API resources and runs controllers for them, and pluggable infrastructure providers implement the backend-specific work, so the core controllers stay generic across AWS, GCP, vSphere, and others ([[examples/cluster-api-keeps-core-controllers-generic-with-provider-controllers]]). Its machine deletion is a model of finalizer-like discipline. A `deletionTimestamp` on a Machine starts a multi-phase teardown: pre-drain hooks, node drain, waiting for volumes to detach, pre-terminate hooks, deletion of infrastructure and bootstrap objects, and finally the node. The hooks are implemented as annotations that behave like finalizers, and each phase can block with a documented cause. PodDisruptionBudgets, still-attached volumes, and failing hooks are the common ones, with `exclude-node-draining` and `nodeDrainTimeout` as controlled escape hatches ([[examples/cluster-api-machine-deletion-drains-detaches-and-runs-hooks-before-removing-the-node]], [[findings/machine-deletion-stalls-on-disruption-budgets-attached-volumes-and-failing-hooks]]). A MachineHealthCheck evaluates node conditions against timeouts and replaces failed machines, with a `maxUnhealthy` setting that skips remediation when too many machines look unhealthy at once so a wide problem does not trigger a wholesale replacement. The wiki cautions that its source for this is an older book version, so current behavior may differ ([[examples/cluster-api-machine-health-check-replaces-failed-nodes]]).

## 10. Pitfalls: stale caches, self-triggered loops, stuck finalizers, cross-namespace owners, retry storms

By now most of the pitfalls will look familiar, which is the point. They are the same mechanics, violated. This section gathers them, adds the ones we have not discussed, and shows what real incidents look like. The wiki's pitfalls hub notes that serious incidents are usually cascades, in which a small change meets a controller loop, a default, or a shared dependency and the loop amplifies it ([[concepts/pitfalls-and-case-studies]]).

Stale caches and double action come first. A level-triggered controller that reads from a lagging cache can act twice on one gap. The cure is deterministic names, expectations, or an authoritative uncached read. A neighboring mistake is mutating an object returned from a shared informer cache, which changes what every other consumer of that cache sees, or acting before a cache has synced and deciding from incomplete data. The controller guidelines state the cures plainly: copy objects before modifying them and wait for caches to sync before starting workers. Both mistakes are silent, because the controller keeps running and simply reasons from wrong input ([[findings/mutating-objects-from-a-shared-cache-or-reading-an-unsynced-cache-corrupts-reconcile-input]]).

Self-triggered loops come next, as section 5 described. The cheapest of them to create is writing status through the main resource, and the hardest to find because each pass looks like a normal reconcile. A related status pitfall is implementation error. A Kubebuilder walkthrough lists four recurring ones: using the normal client instead of the status client, forgetting RBAC on the `/status` subresource, not retrying on resource-version conflicts, and not setting `observedGeneration`. They produce controllers that appear fine in a test cluster with broad permissions and fail under least-privilege RBAC ([[findings/status-client-rbac-and-conflict-mistakes]]).

Stuck finalizers are the pitfall every operator meets. Section 6 covered the causes. The case worth remembering is a namespace stuck in Terminating, reporting the condition `NamespaceFinalizersRemaining`, where the culprit in a Red Hat walk-through was a custom resource finalizer whose controller was no longer removing it. The usual cause is a controller or CRD that was uninstalled first or is failing ([[concepts/finalizers]]). A paused Crossplane resource also cannot be deleted until it is unpaused ([[findings/a-paused-crossplane-resource-cannot-be-deleted-until-it-is-unpaused]]).

Cross-namespace owners were introduced in section 7, and they deserve a concrete scenario because the failure is silent. Suppose a controller running for an object in namespace A creates a child ConfigMap in namespace B and sets an owner reference pointing back at the parent. Owner references are only valid within one namespace, so the garbage collector cannot find the owner where it looks, treats it as absent, and may delete the child as an orphan, which looks to the user like a resource that vanishes for no reason. You can spot the problem by looking for `OwnerRefInvalidNamespace` events on the child. The fix is either to keep the parent and child in the same namespace, or to drop the owner reference and instead label the child with its parent's identity and add a finalizer to the parent, so that the controller itself finds and cleans up the labeled children when the parent is deleted.

Retry storms are the pitfall that turns a local fault into a global one. When retries lack backoff, a recovering dependency receives a flood. Zalando's 2019 outage is the wiki's case study. A downstream call timed out and clients retried, which spiked DNS queries. The CoreDNS pods had a 100Mi memory limit and were OOM-killed together, and a series of defaults multiplied the problem: the `ndots:5` setting meant about ten DNS queries per external lookup, Node.js did not cache DNS, connections were short-lived, CoreDNS had no vertical autoscaler, and monitoring that depended on DNS ran inside the cluster. Product pages returned errors for over an hour. Zalando raised the memory limits, adopted a node-local design, and moved alerting outside the cluster ([[examples/zalando-s-2019-coredns-outage-turned-a-retry-storm-into-a-total-dns-failure]], [[findings/retry-storms-and-unbounded-retries]]). That incident was a retry storm among ordinary clients, not an operator, but the lesson transfers directly to controllers that hammer a cloud API. The wiki separates two throttling layers that people confuse: the client-side rate limiter configured by QPS and burst, and the server's API Priority and Fairness, which queues or rejects requests with HTTP 429 when a priority level is saturated. A log line saying a request waited due to client-side throttling means that raising server capacity would not have helped ([[findings/client-side-throttling-and-server-side-apf-are-separate-layers]]).

Several further failures deserve names. Heavy handlers and expensive reconciles waste API calls: handlers should only enqueue keys, and a reconciler that makes needless calls multiplies load every time any of its event sources changes ([[findings/heavy-event-handlers-and-expensive-reconciles-waste-api-calls]]). Duplicate work follows from running two replicas without leader election, since each replica consumes the same stream of keys ([[findings/duplicate-work-from-replicas-without-leader-election]]). Multi-kind controllers, three independent sources say, break encapsulation and scale poorly, which is the reason for the single-responsibility advice ([[findings/multi-kind-controllers-break-encapsulation-and-scale-poorly]]). Constant reconciliation costs reads and external calls, and a continuous loop reverts intentional manual changes ([[findings/cost-of-constant-reconciliation]]). With two loops stacked, a GitOps agent above kro or Crossplane, status and drift can be reported at two layers, and a team has to know which one to read ([[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]).

Honesty about the evidence belongs here, and it is less bleak than it was when this part was first drafted. A later research pass found named projects with root-caused runaway reconcile loops, though none is a formal organization-authored postmortem and every rate is the reporter's own measurement. In Cluster API provider RKE2 (Rancher), issue 905, filed on 2026-05-18, an unconditional status patch with no equality check held the control-plane controller at about 10 reconciles per second from v0.22.0, kept looping after the external trigger was removed, and spread to neighboring controllers that watch the same objects ([[examples/cluster-api-provider-rke2-issue-905-an-unconditional-status-patch-held-the-controller-at-about-ten-reconciles-per-second]]). In Longhorn v1.10.1, issue 13831 (2026-08-24), a backup-store error containing S3 request IDs and timestamps was copied into a condition message, so the equality check never matched and the object reconciled about 6 times per second ([[examples/longhorn-issue-13831-volatile-text-in-a-condition-message-drove-about-six-reconciles-per-second]]). Longhorn issue 14121 (2026-09-28) reports `longhorn-manager` memory growing about 25-fold during a backup-target outage until it was killed at about 5.5 GiB, with the reporter diagnosing retries that had no backoff or health gate ([[examples/longhorn-issue-14121-a-backup-target-outage-grew-longhorn-manager-memory-about-25-fold]]). In Konflux's kube-shard operator, issue 121 (2026-09-07), two server-side applies of one ConfigMap with different labels bumped the resource version twice per pass, and with an `Owns()` watch and no predicate the controller looped at about 13 reconciles per second ([[examples/konflux-kube-shard-issue-121-two-server-side-applies-of-one-configmap-looped-at-about-13-reconciles-per-second]]). In Crossplane, issue 7221 (filed 2026-03-19, closed 2026-05-13) showed the CompositionRevision and composite reconcilers calling `Status().Update()` on every pass, so reconcile-ordering tests never converged, while in production the rate limiter turned the loop into slow churn ([[examples/crossplane-issue-7221-an-unconditional-status-update-kept-reconcile-ordering-tests-from-converging]]). Two recurring causes emerge, an unconditional status write and volatile text defeating an equality check ([[findings/a-status-patch-or-update-on-every-pass-keeps-a-controller-in-a-self-sustaining-reconcile-loop]], [[findings/volatile-text-in-a-condition-message-defeats-the-equality-check-and-causes-a-reconcile-storm]]).

The lost-event failure that section 1 describes in theory also has a named case. Kubernetes issue 115658, opened on 2023-02-09, showed that a client-go informer could miss the DELETE event for a short-lived object when a relist raced a queued create. Reporters saw production controllers drift out of sync, with queues over 1000 elements and resync disabled, until a later relist. The fix, pull request 115620, merged on 2023-02-17, and a maintainer said a second change resolved it for 1.27. It is a bug in the layer that produces the hint, and it hurts most for code that keeps its own state keyed on events ([[examples/kubernetes-issue-115658-a-client-go-relist-could-drop-the-delete-event-for-a-short-lived-object]]).

Limits remain. The wiki found no formal organization-authored operator postmortem, the search tooling returned empty results for many queries so that absence is weak evidence, and stuck-finalizer data loss still has no named-company account ([[findings/no-formal-organization-authored-postmortem-of-an-operator-failure-was-found]]). The older case studies in this section, such as the Zalando outage, lean toward 2017 to 2021, and the newer reports are single-reporter issues, so pitfall coverage for kro, Config Connector, ACK, and Cluster API still rests on open issues, many from a single reporter, without maintainer confirmation ([[findings/no-named-organization-postmortem-was-found-for-kro-config-connector-ack-or-cluster-api]]).

## 11. How Flux, Crossplane, ACK, Config Connector, Cluster API and kro implement the mechanics differently

The same mechanics, implemented by different teams with different priorities, produce different trade-offs. This section reads the tools against the mechanics rather than describing each in isolation, and it relies on the wiki's comparison pages, which record the version each value was read at.

**How they split controllers.** All of them follow the single-responsibility guidance, but along different axes. Flux splits by concern: source, kustomize, helm, notification, and image automation, as parts of the GitOps Toolkit ([[examples/flux-splits-gitops-into-single-purpose-controllers]]). ACK ships one controller image per AWS service, which scopes permissions and releases per service ([[examples/ack-ships-one-controller-per-aws-service]]). Cluster API separates generic core controllers from provider controllers, for portability. The wiki's comparison states that it has no performance or operability data comparing these approaches ([[comparisons/how-flux-ack-and-cluster-api-split-controllers]]). Crossplane gives every managed resource the same shared reconciler, which walks connect, observe, create, update, and delete, with provider authors implementing only the external calls, so all providers inherit the same `Synced` and `Ready` semantics and finalizer behavior ([[concepts/managed-resource]]). kro handles all instances of all its generated APIs through one shared dynamic controller with a single rate-limited queue, stated to ensure no single ResourceGraphDefinition overwhelms the system ([[examples/kro-shared-queue-tunes-throughput]]).

**How they time the loop.** Flux requires `spec.interval` on each Kustomization and HelmRelease and supplies no controller default, so a manifest that omits it is rejected. The figure of 60 seconds is a recommended minimum written as "should" in the reference and not enforced by the type, and the `flux create` command's own `--interval` flag defaults to one minute when it generates a manifest. The Flux concepts page says reconciliation runs every five minutes by default, which contradicts the reference pages and likely reflects the 5m used in most example manifests, though the wiki did not trace the origin of that wording. Flux also has a separate `retryInterval` for failures. Argo CD's polling default depends on the version: a flat 180 seconds through v2.14, and from v3.0 a base of 120 seconds plus up to 60 seconds of random jitter, so a poll lands somewhere between 120 and 180 seconds. Some documentation still says three minutes, and the v3.0 FAQ restates the old figure as a ceiling, which is why the two numbers get confused. The wiki did not find why the default changed. A pull request merged in July 2026 is titled as treating `timeout.reconciliation=0` as disabled, which suggests that value turns polling off, but the wiki read only the title and not the change itself, so confirm the behavior on your version. Git webhooks bypass the poll in either version. ACK reconciles resources again roughly every 10 hours after they reach their desired state, to limit AWS API cost and throttling, with Helm values to tune the period per kind. Stateful resources are the example the ACK page gives of kinds worth a shorter period ([[examples/ack-resync-period-tuning-for-stateful-resources]]). kro's tuning page, confirmed for the released v0.10.0, lists a full resync every 10 hours as well. Config Connector reconciles periodically once a resource is up to date, tunable by annotation. The table in the wiki is the most efficient way to see off switches: Flux has `suspend`, Argo CD has toggles for self-heal and automated sync, Crossplane has the pause annotation and management policies, and Config Connector accepts an interval of "0" ([[comparisons/reconcile-cadence-and-off-switches-across-tools]]). The shared trade-off is freshness against API cost, because each observation of an external resource is a call to a rate-limited cloud API.

**How they handle ambiguous creates and existing resources.** Crossplane halts on ambiguity and defaults the external name to the object name for many kinds or an ID the cloud assigns. ACK offers `adopt` and `adopt-or-create` annotations, the latter making a retried create converge on an existing resource. Config Connector acquires a same-named resource automatically. SAP's BTP provider searches inside a creation window. Each choice trades a risk for another: Crossplane needs a human, ACK's adopt-or-create can take over a look-alike, Config Connector can take over a same-named resource ([[comparisons/ambiguous-create-and-adoption-strategies-across-crossplane-sap-ack-and-config-connector]], [[examples/ack-adopt-or-create-brings-existing-aws-resources-under-management]], [[findings/adopt-or-create-can-take-over-a-look-alike-resource]]).

**How they tear down.** The wiki comparison of finalizer-held teardown is the best summary. Argo CD holds deletion with a finalizer on the Application. Flux handles deletion through Kustomization garbage collection and `deletionPolicy`. kro holds an instance finalizer until all managed resources are gone, deleting in reverse-dependency waves from an inventory, and its documented fix for a stuck instance is to clear finalizers on children in the active wave. Cluster API uses the Machine `deletionTimestamp` with annotation hooks. Crossplane composites use owner references from composed resources to the composite, with composite deletion policies of Background, Foreground, or Pipeline ([[comparisons/finalizer-gated-teardown-across-argo-cd-flux-kro-and-cluster-api]], [[comparisons/deletion-policies-across-gitops-and-provider-tools]]).

**How they report status.** The conditions section covered the vocabularies. The consumer-side differences are equally important. Flux's kustomize-controller waits for health before marking a Kustomization `Ready`, using kstatus for compatible resources and CEL `healthCheckExprs` for others. Argo CD aggregates the worst health of an application's immediate children and needs Lua checks for custom resources. The Cluster API change broke kstatus-based readiness, so Flux added CEL health checks for Cluster API resources, and the wiki quotes the closing comment on that issue: given the Ready condition is replaced with Available, Flux cannot rely on kstatus for Cluster API anymore ([[comparisons/health-and-readiness-models-across-tools]], [[findings/premature-readiness-in-kstatus-based-tools]]). The point to take away is that conditions are a contract between tools, and changing one tool's vocabulary can break another tool's automation.

**How they handle load.** Flux exposes worker concurrency and Helm cache flags directly and documents label-based sharding of its source, kustomize, and helm controllers. Argo CD shards application controllers by destination cluster. Crossplane reduces load by splitting providers into families so users install only the CRDs and controllers they need, and it exposes a maximum reconcile rate. kro tunes its shared queue. All of these are knobs on the same machinery from section 4 ([[comparisons/concurrency-and-cache-memory-controls-across-flux-argo-cd-and-crossplane]], [[comparisons/load-and-fairness-controls-across-controller-runtime-flux-argo-cd-and-kro]], [[concepts/scale-and-sharding]]). One finding to carry forward is that extra replicas of a Flux controller add failover and not capacity, because only the leader reconciles ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

The wiki's own gaps limit how far these comparisons go. It could not read how Flux, ACK, Config Connector, and kro name and remove their finalizers, has no scaling data for kro, ACK, Cluster API, or Config Connector controllers, and found kro's idempotency and Cluster API's idempotency uncovered by any readable source.

## 12. Design principles for writing controllers that scale and behave

The failures in this tutorial were not random. They cluster around a few ideas, and the principles below are the ideas stated as rules, each with its reasoning. They are assembled from the wiki's sources and are meant as guidance, not as a standard any one project publishes.

**Treat events as hints and state as the truth.** Derive every action from observed state and the spec, never from the event that woke you. This is why a restarted, lagging, or event-missing controller still converges, and it is the single design decision that makes the rest of the model workable. A controller that branches on create, update, or delete has rebuilt the fragility that level-triggering removed ([[decisions/events-as-hints-state-as-truth]]).

**Make every step safe to repeat.** The loop will run extra times, so every action must be idempotent: deterministic child names, a persisted external identity, tolerance for already-exists and not-found, and a recorded intent before any external create that cannot be recognized on retry. The reason is that the alternative is not a crash but a quiet duplicate, and duplicates of cloud resources cost money.

**Keep the cache honest.** Read from the cache, write to the API server, copy before mutating, wait for sync before starting workers, and track your own recent writes so a lagging cache does not make you act twice. Keep handlers trivial so the queue's deduplication and rate limiting still apply.

**Say what a pass meant.** Return nil when converged, `RequeueAfter` when waiting, an error when failed, and `TerminalError` when retrying cannot help. Never block a worker. Keep requeue behavior from generating its own events by using the status subresource and generation-aware predicates. The reasoning is that the return value is the only language the controller shares with the queue, and an ambiguous pass produces a hot loop or a stalled object.

**Put the guard in place before the thing exists.** Add the finalizer before creating any external resource, because it cannot be added after deletion starts. Make cleanup idempotent and treat a missing external resource as success. Decide the delete-or-retain policy explicitly for stateful resources, and give users a documented escape hatch so that forced removal is rare. Protect credentials that cleanup depends on, and uninstall controllers only after their custom resources are gone.

**Use ownership for what Kubernetes can see, and inventory or finalizers for what it cannot.** Set controller references on in-cluster, same-namespace children and let garbage collection do the work. Use finalizers or an inventory for external resources, cross-namespace relationships, and ordered teardown. Ask for foreground deletion when order matters, and expect that owner references can be lost and must be re-reconciled.

**Report honestly and in the shared language.** Publish standard conditions with `observedGeneration`, write an initial `Unknown` on first visit, keep `lastTransitionTime` meaningful, and distinguish "working" from "usable" from "failed" so that terminal and recoverable errors can be told apart. The reason is that other tools, not only people, consume your status, and a status that lies produces automation that moves on too early or never alerts. Choose polarity deliberately and document which condition a generic consumer should read.

**Give each controller one job, and give each tool the right size.** One controller per kind keeps the failure domain small and the code understandable, which is why Flux, ACK, and Cluster API each split theirs, along different axes. Choose a hand-written operator when domain logic is the point, and composition when you are mostly assembling existing resources ([[decisions/one-controller-per-kind-or-one-multi-kind-controller]], [[decisions/build-a-custom-operator-or-compose-existing-resources]]).

**Spend external API calls on purpose.** Make freshness a decision, not an accident: pick a resync or poll interval per kind based on how stale you can tolerate, limit concurrency, and respect server back-pressure. Run a single replica unless faster failover justifies leader election, and remember that replicas add availability, not throughput. The wiki's scale page adds that worker count and reconcile duration, not object count, set throughput, because a key is never processed concurrently ([[concepts/scale-and-sharding]]).

If a single sentence has to carry this part, it is this: a controller is only as trustworthy as its idempotency, its cache discipline, its deletion handling, and its status, and a platform built from controllers inherits whichever of those it neglected.
