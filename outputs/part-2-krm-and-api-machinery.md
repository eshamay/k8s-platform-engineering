# Part 2: The Kubernetes Resource Model and API Machinery

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes day to day (pods, deployments, services, RBAC, kubectl) but have not yet studied controllers, API machinery, or platform abstractions.<br>
> **Purpose:** Teach the shared substrate that Flux, Crossplane, kro and their neighbors all build on, so that platform failures and design choices can be explained from first principles.<br>
> **Status:** Active. Part 2 of the series on Kubernetes platform engineering.<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** The wiki's concept, example, finding, comparison, decision and entity pages on GVK and GVR, CRDs, the spec and status split, server-side apply and admission, plus the research dossiers listed under Further reading.

## 1. Why the resource model is the real platform

When people first meet Flux, Crossplane or kro, the natural question is which one to pick. A more useful question comes before it: what do these tools have in common, and why can they run side by side in one cluster without a shared codebase or a shared vendor? The answer is that none of them ships its own database, its own authentication system, its own API server, or its own way of describing desired state. They all lean on the same substrate, which this tutorial calls the Kubernetes Resource Model, usually shortened to KRM, together with the API machinery that serves it.

The idea behind this is what the wiki calls the [[concepts/universal-control-plane]]. Kubernetes ships two things bundled together. One is a container scheduler. The other is a generic, extensible API server backed by etcd (the cluster's key-value store), with authentication, RBAC, admission, validation and a watch mechanism, plus a convention for controllers that reconcile what a user declared toward what actually exists. The second part has no inherent tie to pods. Anything that can be described declaratively and reconciled by a loop can be modeled as an object in the API, whether that is a cloud database, a DNS record, a whole cluster, or an application bundle. Once an external thing is represented as a Kubernetes object, it inherits authentication, authorization, audit, watch and a uniform client experience without anyone writing those features again.

This is why the resource model, and not any single tool, is the real platform. Flux fetches manifests from Git and writes objects into the API server. Crossplane defines new object types for infrastructure and runs controllers that act on them. kro lets a platform team publish a new object type that expands into a graph of other objects. Argo CD, Kyverno, cert-manager, Cluster API and the cloud add-ons (Config Connector, ACK, Azure Service Operator) all read and write the same kinds of objects through the same HTTP API. They coexist because they agree on a small set of contracts: how a type is named, how its schema is declared and evolved, who owns which half of an object, who owns which individual field, and how writes are checked before they are stored.

The thesis of this part is that those contracts explain most platform failures and most good design choices. When a Flux reconcile fails with "no matches for kind," when an Argo CD application sits permanently out of sync, when a webhook outage stops a cluster from being repaired, or when a Crossplane upgrade quietly changes who owns a field, the cause is almost always a contract in this substrate behaving exactly as designed while an operator or tool assumed something else. Learning the contracts first makes the tools far easier to reason about later. The tutorial walks from the structure of a single object up through naming, schemas, versioning, ownership and admission, then looks at pitfalls, at how individual tools use the machinery, and finally at principles for building APIs that platforms can sit on.

## 2. Anatomy of a Kubernetes resource: apiVersion, kind, metadata, spec, status

Every object you have ever applied with kubectl has the same skeleton. Before looking at the machinery, it is worth reading that skeleton slowly, because each part exists for a reason that later sections depend on.

Consider a small Deployment as it might look when read back from a cluster, trimmed for clarity.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
  generation: 4
  resourceVersion: "812345"
  labels:
    app: web
  ownerReferences: []
  finalizers: []
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: example/web:1.4.2
status:
  observedGeneration: 4
  readyReplicas: 3
  conditions:
    - type: Available
      status: "True"
```

The first two fields, `apiVersion` and `kind`, say what type of thing this is. Together they form what the next section calls a GVK, and they let the API server pick the right schema, the right storage format and the right endpoint. The `metadata` block holds identity and bookkeeping that is common to every object: the name, the namespace, labels, and several fields that platform tooling relies on heavily. The `generation` counter increases whenever the desired state changes. The `resourceVersion` is an opaque token that supports optimistic concurrency, meaning that a write based on a stale copy is rejected with an HTTP 409 conflict instead of silently overwriting a newer change. The `ownerReferences` field links a child object to its parent so that deleting the parent cascades to the child, a behavior covered in [[concepts/owner-references-and-garbage-collection]]. The `finalizers` field lists tokens that stop the object from being removed from storage until a controller has finished cleanup, as described in [[concepts/finalizers]]. Finalizers are the reason an object can sit in `Terminating` for a long time when its controller is missing or failing, and they are the main way a controller makes deletion safe for things that live outside the cluster, such as a cloud database.

Finalizers are plain strings, and each tool picks its own, which is useful to know because the string is what you search for on a stuck object. Flux's Kustomization controller uses `finalizers.fluxcd.io`, Config Connector uses `cnrm.cloud.google.com/finalizer` and a second `cnrm.cloud.google.com/deletion-defender`, kro uses `kro.run/finalizer` on instances, and ACK generates a name of the form `finalizers.<apiGroup>/<Kind>` for each service controller (the wiki read the template and not the rendered string for a specific service). Argo CD Applications use three cascade-related names. One rule governs when a controller may add its finalizer: once a delete request has set `deletionTimestamp`, no new finalizer can be added, so a controller has to register its finalizer on the first reconcile, before it creates anything outside the cluster. Otherwise a delete that lands between the create and the registration leaves the external resource with no cleanup hook. See [[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]], [[findings/flux-kustomization-uses-finalizers-fluxcd-io-and-removes-it-even-when-waitfortermination-times-out]], [[findings/argo-cd-applications-use-three-cascade-finalizer-names-and-a-non-cascading-delete-removes-the-finalizer]] and [[findings/a-finalizer-added-after-the-delete-request-is-too-late-and-new-ones-are-refused]].

The last two top-level blocks, `spec` and `status`, are the heart of the model. The `spec` records intent: what somebody wants to be true. The `status` records observation: what a controller has actually found. This separation is explained in section 6, and it is what makes Kubernetes declarative. A person or a tool states intent once, and independent control loops work to make reality match it and report progress without rewriting the intent. The wiki's page on [[concepts/declarative-vs-imperative]] draws the contrast with imperative commands like `kubectl scale`, which act on a live object once and leave no record of why.

A controller is simply a program that watches objects of some type and acts to reduce the gap between spec and observed reality. Because a controller can crash, restart, miss an event, or run twice, the loop has to be written so that running it again does no harm. That property is [[concepts/idempotency]], and it is why controllers are written as "look at the current world and compute what should change" rather than as scripts of one-shot commands. Keep this picture of a control loop in mind, because every contract discussed below exists to make many such loops, written by different teams, safe to run against the same API.

Two further pieces of the skeleton deserve a name now. `status.conditions` is a standardized list of entries, each with a type, a status, a reason, a message and an `observedGeneration`, which gives tools a common language for readiness. The wiki covers it in [[concepts/conditions]]. And the `generation` and `observedGeneration` pair gives anyone reading an object a cheap way to ask whether the status still describes the latest spec.

## 3. GVK versus GVR, discovery and the RESTMapper

Kubernetes names things in two different ways, and confusing them is a common stumbling block for people who start writing tooling. A GVK, short for GroupVersionKind, names a type: the schema of an object, such as `apps/v1` with `Kind=Deployment`. A GVR, short for GroupVersionResource, names an HTTP endpoint collection: the lowercase plural that appears in a URL, such as `apps/v1` with `Resource=deployments`. The Kubernetes API concepts page puts the split in one sentence: a resource type is the name used in the URL, and every resource type has a concrete representation, its object schema, which is called a kind. The wiki's seed vocabulary gives a provider example, where `s3.aws.upbound.io/v1beta1` with `Kind=Bucket` is the GVK and `buckets` is the resource. See [[concepts/gvk-and-gvr]] and the side-by-side table in [[comparisons/gvk-versus-gvr]].

Manifests and wire payloads speak GVK through their `apiVersion` and `kind` fields. REST URLs speak GVR, in the form `/apis/<group>/<version>/<plural>`, with the core group served under `/api/v1`. In the great majority of cases the mapping is one to one and the resource is the lowercased plural of the kind, but that is a convention and not a guarantee. The classic exception is the `Scale` kind. Many resources expose a subresource that returns the same `Scale` kind, for instance `deployments/scale` and `replicasets/scale`, and this is how the HorizontalPodAutoscaler adjusts replica counts on very different workloads without knowing any of their schemas. One GVK is served at many GVR endpoints there. A custom resource definition, by contrast, gives each kind exactly one resource. [[examples/hpa-scales-any-workload-through-the-scale-subresource]] walks through the HPA case, and [[examples/a-scalable-composition-lets-hpa-and-keda-drive-an-xr-through-the-scale-subresource]] shows the same trick applied to a Crossplane composite resource, where the composition author must patch the desired replica count down into the Deployment and write the observed count back up to the composite's status.

Why does the distinction matter in practice? Because different parts of the system speak different dialects. Humans and Git repositories speak GVK. RBAC rules, audit logs and URLs speak GVR. A generic tool that is handed a manifest and has to send it to the server must translate from one to the other, and it does so using API discovery. The API server publishes a catalog of what it serves, in two forms: the Discovery API, which lists group-versions and their resources, and OpenAPI, which describes schemas. Discovery historically required one request per group-version after fetching the `/api` and `/apis` roots. Aggregated discovery, stable in Kubernetes 1.30, serves everything in one request when the client asks for it with the right Accept header, so modern clients make far fewer startup calls. OpenAPI v3 has been stable since 1.27 and is preferred over v2. The reason aggregated discovery exists is now documented in its enhancement proposal, KEP-3352, which the wiki read after an earlier pass had reported that none could be found. The proposal says that serving discovery as many small per-group-version documents "causes a storm of requests for clusters and is a source of latency and throttling", and the research dossier reports that a client could need up to 80 requests to learn the whole API surface. The proposal also notes that kubectl keeps a six-hour timer during which it does not refresh discovery, which is a freshness trade-off made precisely to limit that traffic. Its metadata records alpha in 1.26, beta in 1.27 and stable in 1.30, behind the `AggregatedDiscovery` feature gate. See [[findings/aggregated-discovery-exists-because-per-group-version-discovery-caused-a-request-storm]] and [[concepts/api-discovery-and-restmapper]].

Clients feed discovery output into a component called the RESTMapper, which translates a kind into the resource that appears in a URL. In client-go, the Go client library that most controllers use, the restmapper package builds one from discovery, prefers the preferred version of each group, and can add shortcut names such as `po` for pods. A separate registry called the Scheme maps GVKs to Go types so that typed clients can decode JSON, while dynamic and unstructured clients skip the Scheme and take a GVR directly. See [[entities/client-go]].

The key operational fact is that discovery is a snapshot. A mapper built once at startup reflects the cluster at that moment. If a CRD is installed later, the mapper does not know about it, and any lookup fails with the familiar "no matches for kind X in version Y" error. The wiki records this in [[findings/stale-restmapper-hides-newly-installed-crds]]: controller-runtime issue 321 reported exactly this, with workarounds that reloaded the mapper on a miss or recreated the client, and the eventual fix was a dynamic, rate-limited mapper that invalidates itself when a lookup fails. That the dynamic mapper became the controller-runtime default in v0.3.0 is now confirmed from primary sources and no longer rests on a summarized issue thread. The v0.3.0 release notes, published 2019-10-10, list "DynamicRESTMapper that reloads on REST cache miss (#554)" under new features, and pull request 554, merged the same day, says reloads are rate-limited by a token bucket and return an `ErrRateLimited` error when the limit is hit. The release notes do not use the word "default", but the `pkg/manager/manager.go` file at the v0.3.0 tag returns `apiutil.NewDynamicRESTMapper(c)` as the manager's default mapper, which settles the claim from source. A later change, pull request 2296 merged on 2023-05-04, replaced the pieces with a single dynamic mapper that holds an aggregated-discovery client and loads groups lazily. Which controller-runtime release first adopted aggregated discovery was not established, and KEP-3352 does not mention controller-runtime, so the idea that cheaper discovery makes a reload-on-miss mapper cheaper is the wiki's inference from the two sources and not a statement in either. See [[findings/the-dynamic-restmapper-is-confirmed-as-the-controller-runtime-default-at-v0-3-0-from-the-release-notes-and-tag-source]]. [[comparisons/restmapper-strategies-static-deferred-and-dynamic]] contrasts the three strategies: a static mapper that fails until rebuilt, a deferred mapper that lazily rebuilds, and a dynamic mapper that heals on demand.

The same failure shows up at the delivery layer in a very ordinary form. A Helm chart or GitOps application includes a Prometheus Operator `ServiceMonitor`, and the CRD for it is absent or not yet established when the manifest is applied. The dossier calls this the most common everyday GVK-missing scenario, and [[examples/servicemonitor-no-matches-for-kind-in-helm-and-argo-cd]] collects the causes, which include the CRD not existing yet, a wrong apiVersion, and version skew between an operator and its CRDs. The mitigations the sources describe are ordering (Flux `dependsOn`, Argo CD sync waves), mapper invalidation, and not depending on the CRD being present at all. [[comparisons/missing-crd-handling-flux-versus-argo-cd]] sets the two tools side by side, though the wiki is candid that the Argo CD column is thin because the Argo-specific posts did not resolve, so it should not be treated as a settled comparison. See also [[findings/custom-resources-applied-before-their-crd-exists]].

One more wrinkle is that GVK is not always a unique key. A scaffolding tool that composes external APIs can meet two external types that share the same group, version and kind under different domains. Kubebuilder issue 5872 proposes that the tool error on such an ambiguity and accept an explicit `--domain` flag. The wiki notes that the issue was still open in late October 2026, so whether it lands is unknown. See [[examples/kubebuilder-domain-flag-for-ambiguous-external-gvks]].

## 4. Custom resource definitions: schemas, scope, structural schemas and pruning

A CustomResourceDefinition, or CRD, is the extension point that makes the universal control plane practical. It is itself a Kubernetes object, and creating one registers a brand new resource type with the API server at runtime. Once the CRD exists, the built-in kube-apiserver serves a REST endpoint for the new kind with the same machinery it uses for built-in types: list and watch, RBAC, audit logging, schema validation, and storage in etcd. No new server is needed, and the official documentation observes that custom resources can appear and disappear in a running cluster through dynamic registration. See [[concepts/custom-resource-definition]].

A CRD by itself only stores data. The usual pattern pairs a custom resource with a custom controller that reconciles the declared `spec` and reports progress in `status`, which is the operator pattern. The wiki's decision page [[decisions/crd-versus-aggregated-api]] records the alternative: an aggregated API server, a separate server behind the API aggregation layer that gives more control over storage and REST behavior at a higher operational cost. The guidance is to choose a CRD unless the kind needs storage other than etcd or unusual REST semantics, because a CRD inherits storage, authentication, authorization, versioning and watch from the API server with almost no code.

Here is a small CRD for a hypothetical `Database` type that a platform team might publish.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.platform.example.com
spec:
  group: platform.example.com
  scope: Namespaced
  names:
    kind: Database
    plural: databases
    singular: database
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                storageGB:
                  type: integer
                  minimum: 10
                minReplicas:
                  type: integer
                maxReplicas:
                  type: integer
              x-kubernetes-validations:
                - rule: "!has(self.minReplicas) || !has(self.maxReplicas) || self.minReplicas <= self.maxReplicas"
                  message: "minReplicas must not exceed maxReplicas"
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true
```

The CRD's name must be `<plural>.<group>`, and the group and plural names are what clients and RBAC rules will use forever, which section 10 returns to. The `scope` says whether instances live inside a namespace or are cluster-wide. The `versions` list declares which versions exist, which are served over the API, and which one is the storage version, the form actually persisted in etcd. The `schema` is a structural OpenAPI v3 schema. The `subresources.status` entry turns on the separate status endpoint discussed in section 6. The `x-kubernetes-validations` entry carries a CEL rule, which section 8 covers. Notice that the rule begins with two `has()` checks. Neither `minReplicas` nor `maxReplicas` is required in this schema, and in CEL, reading a field that is absent from the object is an error ("no such key") and not a quiet null. A bare `self.minReplicas <= self.maxReplicas` would therefore reject perfectly valid objects that simply leave one of the two fields out. The alternative is to list both fields under `required` in the spec schema, which is the right choice when they must always be present; the `has()` form is the right choice when they are truly optional and the comparison should apply only when both are set.

CEL rules also carry a cost budget, and it affects schema design more than most authors expect. When a CRD is created, the API server estimates the worst-case cost of every rule, and for a list, map or string with no declared size it assumes the worst. The Kubernetes documentation's own example, `self.all(x, x.contains('a string'))` on an array of strings with no limits, is rejected on validation-budget grounds, and the same rule is accepted once the schema sets `maxItems` to 25 and `maxLength` to 10. Nested lists multiply, so the estimate grows quickly. The numbers, read from Kubernetes source on the default branch (not pinned to a release tag, so a given cluster can differ), are a static estimate limit of 10 million per expression and 100 million for all the rules of one CRD, and at request time a limit of 1 million per call, roughly a tenth of a second, and 10 million per request or custom resource, roughly one second. The static per-expression check is suppressed for a schema that has not changed, so tightening estimates does not break CRDs that already exist. This failure appears at CRD creation and not at request time, which is why authors of generated CRDs, such as authors of a Crossplane XRD (a CompositeResourceDefinition, the object a platform team writes to declare a new platform API that Crossplane turns into a CRD) or of a kro ResourceGraphDefinition (kro's equivalent, which describes a new API together with the graph of objects behind it; a later section of this part returns to both), meet it when they add iterating rules to schemas that declare no size limits. See [[findings/an-unbounded-list-or-string-makes-the-cel-cost-estimate-reject-a-crd-rule-until-maxitems-and-maxlength-are-set]] and [[findings/cel-cost-limits-are-10-million-per-expression-and-100-million-per-crd-statically-and-1-million-per-call-and-10-million-per-request-at-runtime]].

The word structural deserves attention, because it explains a behavior that routinely surprises authors. Plain OpenAPI describes what must be present but not what is forbidden, so a possibly incomplete spec used to let unknown fields leak into storage. Structural schemas, introduced to make validation, pruning and defaulting reliable, are a constrained subset of OpenAPI v3. Under a structural schema, the API server drops any field the schema does not declare, unless the author sets `x-kubernetes-preserve-unknown-fields`. The effect is that someone who forgets to declare a field sees the value vanish from stored objects without any error. [[findings/unknown-fields-are-silently-pruned-under-structural-schemas]] records the behavior and its rationale. When a custom resource seems to ignore a field you set, pruning is the first thing to check, and the fix is nearly always to declare the field in the schema.

CRDs are cheap to add but they are not free. Each one adds API surface, etcd data, possibly webhook dependencies, and upgrade-ordering concerns. Two operational facts are worth knowing early. First, deleting a CRD deletes every custom resource of that kind. The wiki marks this as standard behavior that the dossier reported secondhand and did not see stated verbatim in the pages it read, so treat it as unverified against a primary page, but it is consistent with the caution that delivery tools show around CRD deletion. A targeted search for a primary postmortem of a CRD deletion cascade, or of an etcd quota alarm outage, found none, though the search tool returned empty results for many queries, so the absence itself is unverified; treat any claim that this behavior caused a named outage as unsupported. See [[findings/deleting-a-crd-deletes-every-custom-resource-of-that-kind]] and [[findings/no-primary-postmortem-was-found-for-a-crd-deletion-cascade-or-an-etcd-quota-alarm]]. Second, Helm has no native support for upgrading or deleting CRDs, which the Flux documentation attributes to the danger of unintentional data loss. A chart upgrade leaves the old definition in place, and removing a chart leaves its CRDs behind. Flux works around this with `spec.install.crds` and `spec.upgrade.crds`, whose policies are Skip, Create (the default) and CreateReplace, and CreateReplace updates existing CRDs but does not delete ones removed from the chart. See [[findings/helm-does-not-upgrade-or-delete-crds]].

Scale is the third cost. Crossplane's model gives every external resource type its own CRD, so a multi-cloud provider set implies thousands of them. Upbound's estimate, recorded in [[findings/one-crd-per-external-resource-type-overloads-api-server-discovery-and-openapi-computation]], is roughly two thousand CRDs for AWS, Azure and GCP together, with more than 4 MiB of API server memory per CRD and about 300 API group-versions needing discovery requests. A GitHub issue reports that installing providers with over a hundred Terrajet-based CRDs made (Terrajet and its successor Upjet are Crossplane's Terraform-based provider generators, which section 9 describes further) API servers slow, with causes in OpenAPI recomputation each time a CRD is registered and in client discovery rate limits. Custom resources share the same storage and watch paths as built-in objects, which is why an unrelated write-up of large-cluster tuning, [[examples/ant-group-large-cluster-tuning-of-apiserver-watch-cache-and-etcd]], is relevant here: serving list requests from the watch cache cut one team's memory use from roughly 400 GB to 100 GB at more than 10,000 nodes.

It is worth being clear about how firm the numbers in this area are. No official limit exists for the number of CRDs per cluster, the number of custom resources per type, or the API server memory a CRD costs, and the SIG Scalability thresholds document covers built-in resource types only. What exists is reporter measurements in issues: one reports a CPU spike in OpenAPI publishing when just over 700 CRDs were posted at once, another reports about 8 GiB of API server memory near 1,900 CRDs, and a third notes that the API server creates one etcd client per CRD and is still open. Those are individual environments and not benchmarks, so read them as orders of magnitude. Two storage limits do come from primary documentation. The etcd limits page says the default maximum request size is 1.5 MiB and the default storage quota is 2 GiB, with 8 GiB a suggested maximum and not the default, and because the kube-apiserver's own default request body limit is 3 MiB, the etcd limit is the one that bites first unless etcd is reconfigured. One explainer the wiki used earlier described an 8 GB default cap, and the etcd documentation corrects that. See [[findings/crd-scale-evidence-is-issue-reports-of-a-cpu-spike-near-700-crds-and-about-8-gib-of-apiserver-memory-near-1900-crds-with-no-official-limit]] and [[findings/etcd-limits-requests-to-1-5-mib-and-storage-to-2-gib-by-default-and-8-gib-is-a-suggested-maximum-not-the-default]].

## 5. Versioning, storage versions and conversion for CRDs

An API that is useful lives long enough to need change, and a CRD supports that by listing several versions of the same kind. Exactly one version is the storage version, which is how objects are written to etcd. Any number of versions can be marked `served`, meaning the API server answers requests for them. When a client asks for a version other than the stored one, the API server converts the object on the fly. See [[concepts/crd-versioning-and-storage-migration]].

The conversion strategy is either `None` or `Webhook`. With `None`, the server rewrites only the `apiVersion` field, so it is safe only when the two versions have compatible schemas. With `Webhook`, the server calls a service that performs the translation, configured with `conversionReviewVersions` and a `caBundle`. When a project has several versions, the Kubebuilder book recommends a hub-and-spoke arrangement: one version is the hub, every other version (a spoke) converts only to and from the hub, and a request for any version converts through the hub. That keeps the number of conversion functions near 2(N-1) for N versions instead of one for every pair, as shown in [[examples/kubebuilder-hub-and-spoke-conversion-for-multi-version-crds]]. [[comparisons/crd-conversion-strategies-none-webhook-and-hub-and-spoke]] lays the three options out in a table. The guidance in the sources is to prefer `None` when schemas are compatible, because it removes a runtime dependency.

Retiring a version has a documented sequence that is easy to get wrong. Add the new version, migrate clients to it, set the old version to `served: false`, upgrade the stored objects so that none remain in the old storage form, and only then remove the old version from the CRD. The task page tells authors to check `status.storedVersions` before dropping a version. Skipping the migration step strands objects that the API server can no longer decode, which [[findings/crd-version-removal-without-migration-strands-stored-objects]] describes. The upgrade step uses a StorageVersionMigration object, a small API object whose creation asks the cluster to read every stored object of a given resource and write it back in the current storage version. The stage is settled by primary sources. The `storagemigration.k8s.io/v1` API and its controller reached GA and are enabled by default in Kubernetes 1.37, which the release blog, the 1.37 changelog and the feature-gate table at the 1.37 release tag all agree on; the same gate was beta and off by default in 1.36, and the enhancement proposal (KEP 4192) records alpha in 1.30, beta in 1.35 and stable in 1.37. One trap is worth knowing: the task page on kubernetes.io still carried a stale "Beta since v1.35; disabled by default" header at the time it was read, even though its body described the feature as enabled, so cite the feature-gate table and the changelog for the stage and not that header.

The more important point is that "enabled by default" describes the API and the controller, not an automatic trigger. The enhancement proposal says the creation of the migration resource is deferred to the user, and the GA announcement says a migration starts when a person or a tool creates a StorageVersionMigration object. The older out-of-tree trigger, which scanned for resources every ten minutes and created migration objects on its own, was not moved into the core, so retiring a CRD version still needs an explicit step in your runbook: create the object, wait for its Succeeded condition, confirm that `status.storedVersions` on the CRD lists only the preferred version, and only then remove the old version.

Waiting on the right signal matters, because the object does not report progress as a number. Read from the v1.37.0 source, the `storagemigration.k8s.io/v1` type has an immutable `spec.resource` and a `status` holding standard conditions of type `Running`, `Succeeded` and `Failed`, and no numeric progress field. Progress appears only as text in the message of the `Running` condition, which starts with "The migration is running", then adds ", N/M objects not yet migrated" while objects remain (or ", M objects verified migrated" when none do), and appends "; transient error: ..." when a transient error occurred. When the pass finishes, `Running` flips to False with the message "Migration completed", and the controller sets `Succeeded` to True or, on failure, `Failed` to True. For a CRD target the controller also sets a `StorageMigrating` condition on the CRD, and pull request 135297 (merged 2026-03-11) removes the old versions from the CRD's `status.storedVersions` after migration, which is the step that leaves only the preferred version there. A script should therefore wait for the `Succeeded` condition and treat the `Running` message as human-readable text whose wording can change, never as a value to parse. The layout comes from source alone, because the GA blog post and the KEP text on progress were not read. See [[findings/storageversionmigration-reports-progress-as-text-in-the-running-condition-message-and-has-no-numeric-progress-field]].

Several caveats apply to that runbook. Migration needs an integer resource version, so it fails for resources that lack one, such as those served by aggregated APIs. If `storedVersions` still shows an old entry afterwards, the CRD changed while the migration was running, and the migration should be retried. The 1.37 changelog also records a kube-controller-manager panic when the target resource was missing from the RESTMapper, fixed in a later pull request, so check your patch level. No incident report caused by skipping this step turned up in the sources, so the consequence described above is inferred from the documented sequence and not from an observed outage. See [[findings/storage-version-migration-is-not-triggered-automatically-so-a-retired-crd-version-needs-a-user-created-object]] and [[findings/kubernetes-docs-pages-disagree-with-the-code-on-mutating-admission-policy-and-storage-version-migration-stage]]. Before the built-in API existed, operators wrote their own migrators.

The risk with webhook conversion is that it puts a network service in the path of reads. A bug report in the Kubernetes repository, summarized in [[findings/a-down-conversion-webhook-can-stall-garbage-collection]], describes the garbage collector in kube-controller-manager failing to sync its cache when a conversion webhook behind a CRD was unavailable. Cascading deletes stopped, so a deleted Deployment left its ReplicaSets and pods behind. That stall has since been fixed upstream. Pull request 125796, "garbagecollector: controller should not be blocking on failed cache sync", merged on 2024-09-25 in the 1.32 milestone, and the long-standing issue 101078 was closed as completed at the same moment. The 1.32 changelog says the collector can now continue when a resource cannot be listed or watched, and it logs "not all resource monitors could be synced, proceeding anyways". The release note carries an important caveat: any objects of the unsynced type that carry owner references with `blockOwnerDeletion: true` are not known to the garbage collector. So the fix narrows the damage without removing it. A down webhook still leaves that one resource type unwatched by the collector, the error is counted by the `GarbageCollectorResourcesSyncError` metric, and cascading deletes for owners and dependents of that type are not handled until the webhook recovers. No source read measures how long dependents linger, and no further partial-sync work beyond this pull request was found, so those two points stay unverified. The workaround that the old issue suggested, deleting the converter webhook while the controller is down, predates the fix. See [[findings/since-kubernetes-1-32-the-garbage-collector-proceeds-after-a-failed-cache-sync-but-cannot-see-block-owner-deletion-owners-of-the-unsynced-type]]. For readers new to the term, an informer is a client-side cache of objects that a controller keeps current by holding a watch open against the API server, so a controller can read from memory instead of querying the server on every decision. Before the fix, one webhook for one CRD thus damaged behavior for unrelated built-in resources.

For platform teams, versioning is where product management meets API machinery. Crossplane recommends Kubernetes-style alpha, beta and stable versions for XRDs, and says that breaking schema changes should ship as new XRDs or through conversion webhooks, because an XRD's group and names cannot change. [[decisions/conversion-webhook-versus-new-xrd-for-breaking-changes]] records the trade: a webhook keeps one type and one name but adds a service to run, while a new XRD avoids conversion machinery but forks the API so that consumers must migrate. The wiki does not rank the two.

Upstream Kubernetes treats its own beta types the same way. It removes beta GVKs on a published schedule: PodSecurityPolicy under `policy/v1beta1` was removed in 1.25, and the HPA's `autoscaling/v2beta2` and `flowcontrol.apiserver.k8s.io/v1beta1` went in 1.26. Manifests, charts and clients pinned to those GVKs break once the cluster upgrades. [[examples/cluster-upgrades-remove-beta-gvks-in-1-25-and-1-26]] tells that story, and section 10 explains the mechanism and how to check ahead of time. Deprecation scanners such as pluto and kubent appeared in search results, but the wiki did not read them, so their behavior is not established here. See [[findings/removed-beta-gvks-break-pinned-manifests-and-clients]].

## 6. The spec and status split and the status subresource

Section 2 introduced spec as intent and status as observation. The Kubernetes API conventions describe spec as the complete description of desired state, including defaults and modifications by ecosystem components, and status as a summary of current state, usually written by automated processes. The split is more than a naming convention. It is a division of ownership: users and GitOps tools own `.spec`, and controllers own `.status`. See [[concepts/spec-status-split]].

Why does that matter? Consider a GitOps tool that re-applies a manifest every few minutes. If the object's status lived in the same writable space as its spec, every re-apply could overwrite what a controller observed. With the split, the tool applies only intent, and the controller reports observations in a separate place. The split also gives the reconcile loop a clean input (spec) and a clean output (status).

The split is enforced through the `/status` subresource, which a CRD opts into with `subresources.status: {}`. Once enabled, a PUT or PATCH on the main resource ignores changes to status, a PUT or PATCH on `/status` ignores everything except status, and only changes to the main resource bump `metadata.generation`. The subresource has its own authorization scope, so you can give users write access to spec while giving controllers write access to status. That is a security property as much as a convenience.

The generation counter gives controllers a cheap staleness check. A controller copies the generation it acted on into a field called `observedGeneration`, so that any consumer can compare the two numbers. Flux exposes the comparison directly: an `observedGeneration` below `metadata.generation` means a spec change is pending. Where the field lives is the part that took a source-level reading to settle, and three placements coexist in practice. The Kubernetes API conventions describe both a top-level `status.observedGeneration` and a per-condition `observedGeneration` (the field on the standard `metav1.Condition` type, which says the condition is out of date relative to the current spec), without ranking them. The generic readiness library kstatus parses a condition struct that has no per-condition field at all, so it consults only the top-level value, and Argo CD's health-check documentation likewise tells authors to use `status.observedGeneration`. Flux's condition setter stamps the current generation on every condition it sets and also keeps a top-level field, so that both kinds of reader work. Config Connector's direct controllers write only the top-level value. The practical advice that follows from the evidence is to publish both placements when generic consumers matter, though no source states a rule for choosing and the wiki's decision page deliberately makes no recommendation. See [[decisions/place-observedgeneration-at-the-top-level-on-each-condition-or-both]], [[findings/kstatus-reads-only-the-top-level-observedgeneration-because-its-condition-struct-has-no-per-condition-field]], [[examples/flux-stamps-the-current-generation-on-every-condition-and-also-keeps-a-top-level-observedgeneration]] and [[comparisons/observedgeneration-top-level-versus-per-condition]].

The kstatus evaluation order shows why the top-level field is so valuable to generic tools. Read from its source in the cli-utils repository, kstatus checks in a fixed sequence: first whether a deletion timestamp is set (Terminating), then whether `metadata.generation` differs from the top-level `status.observedGeneration` (InProgress, with the synthetic reason `LatestGenerationNotObserved`), then the conditions in array order, where `Reconciling=True` means InProgress and `Stalled=True` means Failed and the first match wins, and only then type-specific rules and a `Ready` fallback, where True means Current and both False and Unknown mean InProgress. Because the generation check runs before the `Ready` check, a stale top-level field overrides a `Ready=True` beside it. That consequence is an inference from code order and not a documented rule. The opposite case is the dangerous one: for a custom resource whose controller never writes the top-level field, the generation check is skipped, and if no `Reconciling`, `Stalled` or `Ready` condition has been written yet the final default reports Current, so the resource can read as reconciled before its controller has done anything. See [[findings/kstatus-checks-deletion-then-generation-then-reconciling-and-stalled-then-ready-so-a-stale-top-level-observedgeneration-overrides-ready-true]] and [[findings/a-kstatus-resource-whose-controller-never-writes-status-observedgeneration-skips-the-generation-check-and-can-read-current-early]].

Skipping the subresource has a concrete cost. Without it, a status write is a write to the whole object, so it bumps `generation`, which fires the controller's own watch, which reconciles again, which can write status again. A tutorial quoted in [[findings/status-writes-through-the-main-resource-retrigger-reconcile-loops]] puts it simply: keeping them separate is how you avoid infinite reconcile loops. With the subresource enabled, a Kubebuilder controller's `r.Status().Patch()` updates only status and leaves generation alone.

Missing `observedGeneration` has a different cost. ACK issue 1583 is the clearest example in the wiki: without the field on its conditions, a stale `ResourceSynced=True` looks exactly like a current one. Argo CD maintainers described working around the gap by comparing managed-field timestamps, which they called fragile. The proposed mitigation is to publish `ResourceSynced=False` at the start of each reconcile. At fetch time the issue was open and frozen. See [[findings/missing-observedgeneration-hides-stale-status]].

Three 2026 reports show the same missing field causing a consumer to see Ready too early. All three are open issues from individual reporters, with timings that the reporters measured themselves, so none is a formal postmortem. On 2026-09-01 a reporter filed CloudNativePG issue 11390 against version 1.30.0 on a Kubernetes 1.36 kind cluster: after patching `spec.instances`, `kubectl wait --for=condition=Ready` returned immediately on a Ready condition produced before the change, because the Cluster status has no field saying which generation the condition describes, and the reporter saw intermittent CI failures ([[examples/cloudnativepg-issue-11390-kubectl-wait-for-ready-can-return-on-a-condition-produced-before-the-spec-change]]).

On 2026-10-12 a reporter filed restate-operator issue 216 against version 3.1.0: a RestateCluster reported Ready before its StatefulSet rollout finished, and Flux with `wait: true` marked the release healthy about 37 seconds before the last pod was Ready ([[examples/restate-operator-issue-216-ready-true-before-a-statefulset-rollout-finished-let-flux-mark-the-release-healthy]]).

On 2026-10-23 a reporter filed Argo CD issue 30373 about the built-in ACK health check added in v3.6.0-rc1: with iam-controller v1.10.1 on EKS 1.35, the check reported Healthy about two seconds before the ACK controller re-stamped its conditions after a spec change, because ACK resources carry no `observedGeneration` ([[examples/argo-cd-issue-30373-the-built-in-ack-health-check-reports-healthy-before-the-controller-observes-a-spec-change]]). The reporter adds that the ACK issue has been open since 2022, a claim the wiki did not verify independently. Together they show the cost on three consumer paths: scripts, delivery tools and health checks. No fix is recorded for any of them. See [[findings/ready-can-be-reported-for-a-spec-generation-the-controller-has-not-yet-observed]].

Not every CRD should get a status. [[decisions/which-crds-get-a-status-subresource]] records Prometheus Operator's answer. Its `Prometheus`, `Alertmanager`, `PrometheusAgent` and `ThanosRuler` CRDs run as pods and have a single owning reconciler, so they gained replica and availability counts plus `Available` and `Reconciled` conditions. `ServiceMonitor`, `PodMonitor` and `PrometheusRule` stayed without status, because they are configuration read by more than one reconciler and a single status block would collect conflicting data from several writers ([[findings/config-style-crds-with-several-reconcilers-get-no-status]]). The decision also carries a warning for retrofits: enabling the subresource on an existing CRD changes write semantics, since writes to the main resource then ignore status. See [[examples/prometheus-operator-retrofits-status-onto-workload-crds]].

Status is also an integration surface. Flux, Argo CD, kstatus (a Kubernetes SIGs library that computes a generic ready or not-ready verdict for any object from its status conditions), Cluster API and Crossplane all read conditions to decide whether something is ready. Where conventions are followed, generic tooling works. Where they are not, every consumer needs custom code. The wiki gives ACK's missing `observedGeneration` as one example and notes that Cluster API moving from `Ready` to `Available` is unresolved for generic tools. Crossplane's split of `Synced` (is the controller able to reconcile this object) from `Ready` (is the resource usable) keeps two different meanings from sharing one signal.

Condition polarity, meaning whether a condition is true when things are fine or true when something is abnormal, is a place where the published guidance really does conflict, and the wiki records the conflict instead of choosing a side. kstatus favors abnormal-true conditions, `Reconciling` and `Stalled`, which are present only when true. The Kubernetes API conventions once recommended abnormal-true, reversed to positive in February 2020, and since June 2020 say that neither polarity can be recommended as a general rule, and Cluster API's 2024 proposal quotes that same text. The conventions add that a negative condition can be easier for people to read but that `Failed=False` invites double-negative confusion. An author who follows one source therefore produces conditions the other source's tooling reads poorly. Flux publishes both styles together, a positive `Ready` plus `Reconciling` and `Stalled`, and that pairing, together with `observedGeneration`, is the mitigation the wiki records. One hazard of abnormal-true is that a stopped controller writes nothing, so nothing looks wrong. See [[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]], [[findings/the-kubernetes-api-conventions-recommended-abnormal-true-then-positive-polarity-and-since-june-2020-recommend-neither]] and [[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]. See also [[concepts/conditions]] and [[entities/kstatus]].

Composition tools repeat the split one level up. A platform author defines a spec schema for users and a status schema that surfaces rolled-up readiness or selected fields from composed resources. A Crossplane composite resource ([[concepts/composite-resource]]) puts composition selection in its spec and reports `Synced` and `Ready` in its status, while kro uses CEL expressions that reference the status of underlying resources. See [[concepts/composition]].

## 7. Server-side apply, managed fields and field ownership

So far the contracts have concerned naming, schemas and the two halves of an object. This section covers the contract that lets several writers share one object, which is the hardest problem in a platform with many controllers.

Start with what was wrong before. Client-side apply, the original `kubectl apply`, performs a three-way merge in the client between the new manifest, a copy of the last applied manifest stored in the `kubectl.kubernetes.io/last-applied-configuration` annotation, and the live object. The wiki's [[comparisons/client-side-apply-versus-server-side-apply]] lists its problems, drawn from the design proposal KEP-555: surprises after a `kubectl edit`, last writer wins silently, dependence on client version and on a strategic merge patch format (the older kubectl patch format, which relies on per-list merge keys that are hard-coded for built-in types) that grew organically, and an annotation capped at 262,144 bytes in total.

Server-side apply, abbreviated SSA, moves the merge into the API server. A client sends a partial object, its intent, along with a `fieldManager` name. The server merges the intent into the live object and records, for every field, which manager owns it. The records live in `metadata.managedFields`, where each entry names a manager, an operation of `Apply` or `Update`, and the set of fields owned. SSA reached GA in Kubernetes 1.22. A sketch of how ownership looks in practice follows.

```yaml
metadata:
  managedFields:
    - manager: kustomize-controller
      operation: Apply
      fieldsV1:
        f:spec:
          f:template:
            f:spec:
              f:containers:
                k:{"name":"web"}:
                  f:image: {}
                  f:name: {}
    - manager: kube-controller-manager
      operation: Update
      fieldsV1:
        f:spec:
          f:replicas: {}
```

The snippet shows a Deployment where Flux's kustomize controller owns the container image and another writer owns the replica count. The replicas owner appears as `kube-controller-manager` because the HorizontalPodAutoscaler scales through the scale subresource, and the write is recorded under the manager that performs it, not under a separate autoscaler manager. The sketch is trimmed: real output also carries an `apiVersion`, a `fieldsType: FieldsV1` and a `time` on every entry. The `k:{"name":"web"}` key shows that lists can be tracked per entry when the schema declares a key, and the entry records the key field itself (`f:name`) next to `f:image`. That key exists because the container list is declared as a map-type list keyed by `name`, which the next paragraphs explain. Because each manager owns only the fields it set, Flux can re-apply its manifest every few minutes without touching the replica count, and an autoscaler can change replicas without Flux reverting it. By default `kubectl get -o yaml` hides this block unless you pass `--show-managed-fields`, which is why people debugging ownership from default output may wrongly conclude it is empty. [[findings/managedfields-are-hidden-from-kubectl-output-by-default]] notes that Crossplane issue 7453 may have been exactly that confusion, though the issue was marked stale and unresolved, so the underlying claim is unverified.

When two managers set a field to different values, the later apply gets a conflict error instead of silently overwriting. The applier has three choices: force the write and become the sole owner, drop the field from its request and give up the claim, or set the same value and become a co-owner. If two managers set the same value they share ownership, and a later change by either conflicts with the other. The standard illustration is [[examples/hpa-and-git-both-set-replicas-surface-an-ssa-conflict]]: Git says three replicas, the autoscaler has moved to ten, and a CD system applying Git's manifest now sees a conflict instead of resetting to three. The Kubernetes maintainer blog uses this case to argue that conflicts are information, and that a tool that resets silently is hiding a real disagreement.

How lists and maps merge depends on schema markers. Two vocabularies are in play here, and it helps to keep them apart. CRD authors who write Go with Kubebuilder add comment markers (`+listType=map`, `+listMapKey=name`, `+mapType=granular|atomic` and `+structType`), and the generator turns them into the schema extensions `x-kubernetes-list-type`, `x-kubernetes-list-map-keys` and `x-kubernetes-map-type` that a reader actually sees in a CRD or OpenAPI document; `structType` has no CRD YAML field of its own. The `k:{"name":"web"}` key in the sketch above exists because the container list is declared as `listType=map` with the key `name`. A CRD with no markers is treated as unstructured, with atomic lists, so only one manager can own such a list. Flux documents that atomic lists such as `.spec.tolerations` cannot be shared under its `Merge` policy, and Crossplane's SSA page says complex-field merging works only when provider CRD schemas carry the markers. This is why CRD authors should add them. See [[findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership]].

Three pitfalls follow from the ownership model. First, a controller that reads an object and applies the whole thing back claims every field in it, including fields set by users and other controllers. The recommended patterns are extract-modify-apply, where the controller extracts only its own fields, and building the desired fields from scratch. The Kubebuilder book shows its controllers applying status with a named owner and `ForceOwnership`, as in [[examples/kubebuilder-controller-applies-status-with-a-field-owner]]. See [[findings/applying-a-whole-read-back-object-claims-every-field]]. Second, migrating from client-side apply leaves old managers (`kubectl` with operation `Update`, and `before-first-apply`) co-owning fields, so removing a field from the manifest leaves it in the cluster because someone else still owns it and force cannot take a field that is no longer in the applied object. Flux hit this moving from 0.17 to 0.18, and Crossplane hit it moving composed resources to composition functions, where a four-step managed-fields migration clears the old manager before applying under a new one. See [[findings/client-side-to-server-side-migration-leaves-stale-co-owners]], [[examples/flux-migration-from-client-side-apply-strands-removed-fields]] and [[examples/crossplane-clears-managed-fields-when-migrating-to-composition-functions]]. Third, a stale manager that owns a list entry key can leave an invalid half-removed object, as in Flux issue 1722, where a legacy controller co-owned a container entry's key but not its required `image` field, and the dry-run then failed on every reconcile (a server-side dry-run asks the API server to run the full request path, including admission, without persisting anything, which makes it a cheap way to find out whether an apply would succeed) ([[findings/a-stale-manager-owning-a-list-entry-key-breaks-the-dry-run-after-removal]]).

The question of who should force is a design decision that tools answer differently. The Kubernetes documentation strongly recommends that controllers always force conflicts on objects they own, since a controller usually cannot resolve a disagreement about fields it manages. The same maintainers argue that CI/CD systems are controllers that behave like users, and should surface conflicts to humans. In practice Argo CD (opt-in SSA with `--force-conflicts`) and Flux (force-applying its own intent) both force, then add escape hatches. Kluctl decides per field, treating changes by known interactive managers like kubectl and k9s as temporary and leaving alone fields that other controllers set. The record is in [[decisions/force-conflicts-or-surface-them-to-humans]], [[comparisons/ssa-conflict-policy-across-tools]], [[findings/forcing-conflicts-hides-disagreements-between-writers]] and [[examples/kluctl-decides-field-level-conflicts-with-known-manager-heuristics]]. Helm 4 adds a useful data point. Its release notes (2025-11-12) say server-side apply is now supported, and on the main branch `helm install` defaults to server-side apply, `helm upgrade` takes true, false or auto (default auto, which follows the previous release's method), and the `--force-conflicts` flag defaults to false. The manager name is normally `helm`, taken from the binary's name. helm-controller is the opposite: its source sets force-conflicts equal to server-side apply with the comment "We always force conflicts on server-side apply." So a person running Helm 4 gets a conflict error by default, while the same chart under Flux takes the fields. The wiki read main only, so whether the v4.0.0 tag itself made install default to server-side apply is unverified from source, although Helm's own overview says it does. See [[findings/helm-4-install-defaults-to-server-side-apply-names-its-manager-after-the-binary-and-forces-conflicts-only-when-asked]]. The wiki is explicit that the sources do not settle the best default for platform teams that run GitOps alongside in-cluster controllers.

## 8. Admission: mutating and validating webhooks, validating admission policy and CEL

Admission control is the stage of the API server's request path that runs after authentication and authorization and before an object is persisted. Its job is to rewrite defaults or to validate rules so that an object is accepted, rejected or modified no matter which client or tool sent it. For a platform this is the enforcement point that does not depend on any particular tool behaving well. See [[concepts/admission-webhooks-and-cel]].

Built-in admission plugins run inside the API server. Dynamic admission control adds two extension routes. The first is the admission webhook: an HTTPS callout in which the API server sends an AdmissionReview request and expects an AdmissionReview response. Mutating webhooks run first and may return patches. The object then passes schema validation, and validating webhooks run and may only allow or deny. A webhook configuration says which requests match, using `rules`, `namespaceSelector`, `objectSelector`, `matchPolicy` and CEL `matchConditions`, and how to behave on trouble: `failurePolicy` defaults to `Fail` for `v1`, `timeoutSeconds` defaults to 10 seconds, `sideEffects` declares whether dry-run requests are safe, and `reinvocationPolicy` lets a mutating webhook be called again after later mutations.

The second route is in-process CEL, the Common Expression Language, a small typed expression language that is not Turing-complete. ValidatingAdmissionPolicy, stable since 1.30, splits the work into a policy holding the CEL `validations`, a binding that sets scope and `validationActions` (`Deny`, `Warn`, `Audit`), and an optional parameter resource that supplies configuration. MutatingAdmissionPolicy extends the same structure to mutation using `ApplyConfiguration` or `JSONPatch`. Its stage is settled: it is GA and enabled by default since Kubernetes 1.36, which the docs page, the 1.36 changelog and the feature-gate table at the 1.36.0 tag all state. The gate table also shows the earlier history as alpha in 1.32 and beta in 1.34, both off by default. The live docs page says the feature was first available in 1.30, which looks like a conflict with the gate table, and the source history now explains both. Pull request 123425 merged in February 2024 under the 1.30 milestone and registered a `MutatingAdmissionPolicy` feature gate as Alpha and off by default, with nothing usable behind it, so it was an inert placeholder that stayed Alpha at 1.31. The first release with a usable API was 1.32, whose changelog says "Introduced `v1alpha1` API for mutating admission policies", which needs both the gate and a `--runtime-config` setting for `admissionregistration.k8s.io/v1alpha1`. So cite 1.32 for "first usable", and read the docs page's 1.30 as the gate registration. How the docs sentence is generated was inferred from the page source and not confirmed, so that explanation is secondary ([[findings/the-mutating-admission-policy-gate-was-registered-in-v1-30-as-an-inert-alpha-placeholder-and-the-usable-api-arrived-in-v1-32]] and [[findings/kubernetes-docs-pages-disagree-with-the-code-on-mutating-admission-policy-and-storage-version-migration-stage]]). CRD validation rules (`x-kubernetes-validations`) put CEL directly inside the schema, with `self` and `oldSelf` for transition rules. The wiki's [[comparisons/admission-mechanisms-webhooks-vap-map-and-crd-rules]] gives the four-way table.

A concrete CEL case is the minimum-replicas example from section 4. A plain OpenAPI schema can check each field alone but cannot compare two, so before CEL the usual answer was a validating webhook. The rule `self.minReplicas <= self.maxReplicas`, guarded by `has()` checks as section 4 explained because the fields are optional, solves it with no external service, as [[examples/cel-rule-replaces-a-validating-webhook-for-cross-field-checks]] explains. Transition rules reach further. The Kubernetes immutability post shows `self == oldSelf` making a field immutable, and `self.all(x, x in oldSelf)` making a list append-only, which is how a platform can forbid changing a claim's region after creation without writing any code ([[examples/cel-transition-rules-enforce-crd-immutability]]).

Policy that spans many types uses ValidatingAdmissionPolicy. The Kubernetes tutorial builds a policy requiring Deployments to have at least two replicas, binds it to a scope, then exercises the three actions. A parameter resource lets different environments carry different minimums without copying the policy, which [[examples/vap-minimum-replicas-policy-with-per-environment-parameters]] describes. This is the pattern that replaced many guardrails that used to be webhooks with their own service and certificates.

Webhooks remain the general escape hatch. Controller frameworks scaffold them, as in [[examples/kubebuilder-operator-scaffolds-defaulting-and-validating-webhooks]], where the author implements `Default()` and the validation methods and markers generate the manifests. cert-manager is the best documented operator that uses all three roles (validation, defaulting and conversion) for its own CRDs, and it solves the bootstrapping problem every webhook owner faces with a self-signed CA and automatic renewal ([[examples/cert-manager-runs-validation-defaulting-and-conversion-webhooks]]). The decision page [[decisions/validate-with-cel-rules-or-a-validating-webhook]] summarizes the guidance: use CEL where it can express the check, since that removes a failure point, and reserve webhooks for logic that needs external data or arbitrary code. CEL has real limits. Rule cost is capped to protect the API server, so schemas with unlimited lists or strings can be rejected unless iterating rules set `maxItems` and `maxLength`, and CEL cannot call out to registries or signature services. The cost numbers behind the first limit are given in section 4, and they include a per-request runtime budget of 10 million units and a separate 2.5 million for `matchConditions`. See [[comparisons/cel-validation-rules-versus-validating-webhooks]] and [[findings/cel-policies-cannot-reach-external-data-and-have-bounded-cost]].

Policy engines sit on top. Kyverno began as a webhook-based engine, and its ValidatingPolicy is a CEL-first policy type described as a superset of ValidatingAdmissionPolicy that adds background scanning of existing objects, policy exceptions, PolicyReports and an evaluation mode for non-Kubernetes JSON such as Terraform plans. A ValidatingPolicy can generate native ValidatingAdmissionPolicy objects, so enforcement runs in the API server instead of Kyverno's webhook. The two are related and not rivals. See [[entities/kyverno]], [[examples/kyverno-validatingpolicy-generates-native-vap-objects]] and [[comparisons/kyverno-versus-native-validating-admission-policy]]. Kyverno's own webhook failure behavior is now documented from its website (read 2026-11-26, against release v1.20.0). The failure policy is set per policy with `spec.failurePolicy` and defaults to `Fail`, which rejects the request when the call times out or errors. The webhook timeout is `spec.webhookConfiguration.timeoutSeconds`, default 10 seconds with an allowed range of 1 to 30. Kyverno's own namespace and `kube-system` are excluded by default, and when automatic webhook updating is turned off Kyverno creates catch-all webhooks with failure policy `Ignore`. For availability, the high-availability guide says the admission controller does not use leader election for requests and that "the minimum supported replica count for a highly-available admission controller deployment is three", and the troubleshooting page warns that policies matching wildcards send every action on every resource to Kyverno, so expect its resource needs to double, triple or more. The documented failure mode is the familiar deadlock: if all Kyverno pods are down and policies are fail-closed on Pods, API requests time out, usually only when the Kyverno namespace has not been excluded, and the recovery is to delete the `kyverno-resource-validating-webhook-cfg` and `kyverno-resource-mutating-webhook-cfg` configurations, which Kyverno recreates. No measured availability figures were found, and no page read compares the resilience of generated native ValidatingAdmissionPolicy objects with webhook mode, so that benefit is plausible but unquantified. See [[findings/kyverno-defaults-to-failure-policy-fail-with-a-10-second-timeout-and-needs-three-admission-replicas-for-high-availability]] and [[findings/kyverno-fail-closed-policies-time-out-api-requests-when-all-kyverno-pods-are-down-unless-the-kyverno-namespace-is-excluded]].

Gatekeeper, the other widely used policy engine, takes the opposite default, and the wiki now has primary sources for it. Its Helm values (v3.23.1 era) set the validating and mutating webhook failure policies to `Ignore`, with a 3 second validating timeout, a 1 second mutating timeout and 3 replicas, and its `failing-closed` documentation states that Gatekeeper defaults to `failurePolicy: Ignore` and describes an admission deadlock risk when failing closed, which "can normally be mitigated by deleting the `ValidatingWebhookConfiguration`". It keeps a separate check-ignore webhook at `Fail`, excludes namespaces labeled `admission.gatekeeper.sh/ignore`, and relies on its audit process as the backstop for requests that passed while the webhook was failing open. It also integrates with ValidatingAdmissionPolicy, stable from v3.18 per its documentation. The choice between the two defaults remains a decision for the cluster owner, recorded as options in [[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]]. See [[findings/gatekeeper-defaults-its-webhooks-to-fail-open-and-documents-a-fail-closed-deadlock-with-an-emergency-delete-of-the-webhook-configuration]].

## 9. Use cases: platform API schemas as contracts, CRD-generating tools, policy at admission

With the contracts in view, three recurring use cases make the machinery concrete.

The first is the platform API as a contract. Crossplane and kro let a platform team declare a type, and the tool generates the CRD that application teams consume. A Crossplane CompositeResourceDefinition declares `group`, `kind`, `plural`, a list of versions and a `scope`, and the XRD's name must be `<plural>.<group>`. A kro ResourceGraphDefinition takes a simple schema plus a resource graph with CEL expressions, and registers a CRD with the API server. In both cases the GVK becomes the platform's public contract, so naming and versioning decisions are product decisions. [[examples/xrd-and-rgd-declare-platform-gvks]] and [[comparisons/crossplane-xrds-versus-kro-resourcegraphdefinitions-as-crd-generators]] describe the mechanics. Both tools treat the schema as a contract with live consumers. For Crossplane, group and names cannot change without deleting the XRD, and at v1.20 a schema change required restarting the Crossplane pod. For kro, a breaking schema change on an RGD is blocked unless the `kro.run/allow-breaking-changes` annotation is set, where breaking means removing a field, changing a type, adding a required field without a default, or changing an enum or pattern, and kro warns that forcing a change can invalidate existing instances. See [[findings/platform-api-schemas-are-contracts-and-breaking-changes-are-blocked-or-need-conversion]]. The wiki notes the kro column of the comparison is thin on versions and scope, and that kro is pre-1.0.

The second use case is generating CRDs from some other authority. Azure Service Operator v2 generates CRDs from Azure Resource Manager schemas, so supported resources and fields track what Azure publishes, and the documentation says it manages 150 or more resources ([[examples/azure-service-operator-generates-crds-from-azure-resource-manager-schemas]]). Upjet, the successor to Terrajet, is Crossplane's Terraform-based provider generator and creates Crossplane providers from Terraform providers: it reads Terraform schemas at build time and produces Go types and controllers, so users see only a Kubernetes API while the runtime reuses Terraform's resource logic ([[examples/upjet-generates-crossplane-providers-from-terraform-providers]]). Generated providers inherit shared behavior and shared bugs, and their CRD counts feed directly into the scale problem from section 4.

The third use case is policy at admission. A platform team that wants "no Deployment below two replicas in production" or "no change to a claim's region after creation" can put that in CEL, scoped by binding and parameterized per environment, so it holds regardless of whether a request came from Flux, Argo CD or a person with kubectl. This is where admission matters most for GitOps: the tools are not admission systems, but their server-side dry-runs pass through admission, so webhook configuration is a GitOps concern too.

## 10. Pitfalls: client-side apply limits, conflicts, webhook outages, removed beta APIs, permanent names

Most of the failures already mentioned are instances of a few patterns. This section collects them with the evidence the wiki has.

**Client-side apply limits.** A very large generated CRD can exceed the annotation cap and fail with "metadata.annotations may not be more than 262144 bytes." The reported case is the Argo CD ApplicationSets CRD, installed through its Helm chart with client-side apply. The issue lists `ServerSideApply=true` as the mitigation, and `ClientSideApplyMigration=false` for Kustomize. Kluctl moved to direct SSA for the same reason after hitting it with Prometheus operator CRDs. See [[findings/large-crds-exceed-the-client-side-apply-annotation-limit]] and [[examples/argo-cd-applicationsets-crd-too-large-for-client-side-apply]].

**Conflicts and false drift.** SSA changes how drift fights look. In the Flux community case, an edited Service port made the helm-controller dry-run fail with duplicate port names, so the controller stopped at "unable to determine cluster state" and never corrected anything, and `driftDetection.ignore` did not help because ignores apply after the dry-run ([[findings/field-ownership-blocks-drift-correction]]). The upstream cause is Kubernetes issue 130292, filed 2025-02-19 and still open with a comment in September 2026 reading "Still an issue." A Service's `spec.ports` is a list keyed by port and protocol, so a hand-edited port number turns the edited entry into a different key, and the API server rejected even a forced apply that tried to correct it. Argo CD issue 17717 reports the same duplicate port name error. This shows the limit of forcing: choosing force or yield does not settle a conflict when the forced apply itself fails ([[examples/kubernetes-issue-130292-a-forced-server-side-apply-could-not-revert-an-edited-service-port]]). The order of operations in the Flux controllers matters here. kustomize-controller's `--override-manager` flag reclaims the named managers' fields only after a successful server-side dry-run, so it cannot rescue an object whose dry-run keeps failing, and Flux added `--override-manager-before-dry-run` (kustomize-controller v1.10.0, Flux v2.10.0) for that case. helm-controller is the reverse by source order: its diff patches `managedFields` to remove the disallowed managers before it runs the dry-run, so it can clear a stale manager such as `kubectl-edit` that wedges the dry-run, though how a dry-run error then surfaces for a stuck HelmRelease was not traced, and no documented recovery exists. Forcing also cannot fix a dry-run failure caused by validation of the merged object, which is not a conflict at all ([[findings/helm-controller-takes-over-override-manager-fields-before-its-dry-run-diff-the-reverse-of-kustomize-controller]] and [[findings/the-flux-override-manager-flag-takes-over-only-after-a-successful-dry-run-so-it-cannot-recover-an-object-stuck-at-dry-run-validation]]). Argo CD with `ServerSideApply=true` can stay OutOfSync because its default diff compares Git-rendered manifests with live state in its own process, so server defaults such as `volumeMode` in a StatefulSet's `volumeClaimTemplates` appear as differences until Server-Side Diff is used ([[examples/argo-cd-server-side-diff-ends-false-out-of-sync-from-server-defaults]]). Argo CD's diff-strategies page labels Server-Side Diff "Stable (Since v3.1.0)", runs a dry-run server-side apply per resource, uses it automatically for Applications that enable the Server-Side Apply sync option, lets you turn it off with `ServerSideDiff=false`, and says the older Structured-Merge Diff strategy has been discontinued in its favor. That label is a documentation label and not a promise that the bugs are closed: a tracker search found 20 or more open issues mentioning Server-Side Diff, including stale `managedFields` causing a permanent phantom OutOfSync (issue 28861, 2026-07-22), a failure to detect spec changes to a custom resource (25533), and a revert of target changes for CRDs with `x-kubernetes-preserve-unknown-fields` (27625). Only the titles of most were read, and no maintainer statement reconciling the label with the open bugs was found, so whether "stable" means issue-free is unverified ([[findings/argo-cd-documents-server-side-diff-as-stable-since-v3-1-0-while-the-issue-tracker-holds-many-open-bugs]]). Flux offers `ssa` annotations (`Override`, `Merge`, `IfNotPresent`, `Ignore`) and ignore rules for fields that other controllers legitimately change ([[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]). The tools' answers are compared in [[comparisons/flux-ignore-rules-versus-argo-cd-ignoredifferences-and-force-conflicts-for-drift-fights]]. External providers add a related problem: they fill in defaults the user never set, and a naive comparison sees a difference. Crossplane's `LateInitialize` management policy lets the controller copy the provider's value into spec without treating it as drift ([[findings/late-initialized-fields-create-false-drift]]). Mixing management techniques on one object is the older form of the same trouble ([[findings/mixing-management-techniques-on-one-object]]).

**Webhook outages.** Because the API server calls webhooks synchronously, an unreachable backend with `failurePolicy: Fail` blocks every matching write, including writes needed to repair the webhook, such as the Deployment that runs it. The clearest named case is Jetstack's 2019 outage, which the wiki has now read through a Wayback capture of the Venafi-hosted copy of their post (self-reported by Jetstack, dated 2019-09-05). During a GKE master upgrade, the API server's `ca-registration` post-start hook had to update the ConfigMap `extension-apiserver-authentication` in `kube-system`. An OPA validating webhook matched that write and its backend was not responding, so the write timed out. The post states that this operation must complete for a master to pass a health check, so the master crash-looped and the upgrade halted, and node auto-repair then recreated nodes in a loop. Recovery was possible only because the API server answered intermittently, which let the webhook configuration be deleted. This is the repair-deadlock described above in a concrete form: the write the webhook blocked was one the cluster needed to fix itself. Jetstack reduced the exposure by scoping the webhook to the namespaces where policy applies, enabling it only for Ingress and Service resources, adding a liveness probe to OPA, and updating the OPA documentation, and it noted that alerting on API server latency for CREATE and UPDATE requests could have caught the problem earlier. The k8s.af failure-story index turns out to be thinner than earlier wording suggested. Of its 78 entries only two are tagged as webhook stories, Jetstack's post and an Airbnb KubeCon NA 2020 talk that cites a mutating admission webhook in outages, and the Airbnb talk is video-only and has not been read, so it adds no detail here. See [[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]], [[findings/an-unresponsive-validating-webhook-can-block-the-api-server-s-own-startup-write-and-crash-loop-a-master-upgrade]] and [[findings/intermittent-api-server-downtime-can-send-node-auto-repair-into-an-endless-recreate-loop]]. Official guidance is to scope matches narrowly, exclude system namespaces, keep timeouts short, run multiple replicas, and use `Fail` only for security-critical checks. See [[findings/admission-webhook-outages-are-a-recurring-failure-class]], [[findings/fail-closed-webhooks-can-block-the-writes-needed-to-repair-them]] and [[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]]. Related hazards include certificate and network bootstrap windows (cert-manager documents connectivity trouble on GKE private clusters and EKS with custom CNIs, and an unready period after install; see [[findings/webhook-tls-and-network-bootstrap-leaves-an-unready-window]]), webhooks that omit `sideEffects` and so break dry-run clients with "admission webhook does not support dry run" ([[findings/webhooks-without-sideeffects-declared-break-dry-run-clients]], [[examples/flux-dry-run-fails-against-webhooks-without-dry-run-support]]), mutating webhooks that can run repeatedly in no guaranteed order ([[findings/mutating-webhooks-can-run-repeatedly-and-in-no-guaranteed-order]]), and webhooks built against older APIs that silently drop fields they do not know, with the sidecar containers added to Pods in 1.29 as the example ([[findings/api-evolution-breaks-webhooks-that-drop-unknown-fields]]).

**Removed beta APIs.** The trap here is that nothing is wrong today. A manifest that pins `policy/v1beta1` or `autoscaling/v2beta2` applies cleanly on a cluster that still serves that version, so tests and dry-runs pass right up until the control plane upgrade. Once the API server stops serving a removed version, any manifest, Helm chart template or client that names it is rejected with the same "no matches for kind" style of error described in section 3, and Helm can also fail on releases whose stored release metadata still references the removed version. Objects already in the cluster are usually not lost, because they were persisted in the storage version and the API server can still read and serve them under a newer GVK; the breakage lands on the tooling and the manifests that write them. To check ahead of an upgrade, the API server exposes an `apiserver_requested_deprecated_apis` metric that shows which deprecated versions clients are still calling, and scanners such as pluto and kubent can inspect manifests, charts and live objects for removed versions, with the caveat from section 5 that the wiki did not read those tools and so cannot vouch for what they do or miss. The advice is to move to GA versions before upgrading ([[findings/removed-beta-gvks-break-pinned-manifests-and-clients]]).

**Permanent names.** Crossplane refuses to change an XRD's group or names after creation, and a practitioner post says that changing them for a CRD controller is "quite the challenge, to say the least." The post is a single practitioner's view, but it matches the mechanics, since group and plural appear in URLs, RBAC rules and every stored reference. See [[findings/group-and-plural-names-are-effectively-permanent]].

**Missing ordering.** Custom resources applied before their CRDs fail, because the API server has no endpoint for a kind it has not yet been told about, and a bulk apply submits everything at once without waiting for the CRD to become established. Flux and Argo CD address that with different ordering tools, as section 3 described. Flux's `dependsOn` makes one Kustomization or HelmRelease wait until another is ready, so the one that installs the CRDs finishes first. Argo CD's sync waves split a sync into numbered stages and advance to the next stage only when the previous one is healthy. Both work by turning a single simultaneous apply into a sequence in which each step can rely on the previous one, and both are far more dependable than hoping a retry will eventually succeed.

## 11. How Flux, Crossplane, kro, Argo CD, Kyverno and cloud add-ons use or differ on the machinery

It helps to read the tools against the contracts rather than against each other.

**Flux** is a set of single-purpose controllers that communicate through CRDs, and it is both a heavy user and a heavy victim of the machinery. It applies with SSA after a server-side dry run every interval, so admission behavior surfaces directly as reconcile failures. It offers `dependsOn`, health checks and `wait` to order CRDs before custom resources, per-resource `ssa` annotations, ignore rules, and `--override-manager` to reclaim legacy field owners. It surfaces webhook trouble but does not prevent it. See [[entities/flux]].

**Argo CD** treats SSA as an opt-in sync option and separately offers Server-Side Diff, and it runs with `--force-conflicts` when SSA is on. It orders by phase, wave, kind and name, advancing only when a wave is healthy, so it addresses missing CRDs with sync waves. Its health model rolls up child status, which makes the status conventions of section 6 matter directly. It also tracks which objects belong to an Application with a mechanism that differs from owner references: by default an annotation, `argocd.argoproj.io/tracking-id`, chosen with `application.resourceTrackingMethod` in `argocd-cm`. The `annotation+label` method also writes the `app.kubernetes.io/instance` label without using it for tracking, and the `label` method uses that label as the key, which truncates values at 63 characters, can collide with other tools writing the same label, and interferes across several Argo CD instances on one cluster unless an installation ID is set. A tracking annotation that does not reference the object it sits on, as with namespace copies made by the Hierarchical Namespace Controller, makes the object invisible to sync status and pruning instead of reported as drift. Pruned objects use foreground deletion by default, and the docs were read from the master branch, with v3.6.3 the latest release at the time. See [[findings/argo-cd-tracks-resources-by-annotation-by-default-and-label-mode-truncates-and-collides-with-other-tools]] and [[entities/argo-cd]].

**Crossplane** uses the machinery as a code generator and a field-ownership user. XRDs generate CRDs for composite resources, providers ship one CRD per external type, and SSA propagates claims to composites to composed resources under a manager prefix of `apiextensions.crossplane.io/composed/`. Composition functions are small programs that a composition calls to compute which resources to create; they run as pods that Crossplane talks to over gRPC (a binary remote-procedure-call protocol) and that receive observed and desired state. Crossplane applies composed resources with its own service account, so RBAC on the composite API is the main guardrail. Its `Synced` and `Ready` split and its `forProvider` versus `atProvider` separation are applications of the spec and status contract ([[entities/crossplane]]).

**kro** also generates CRDs, from a simpler schema plus CEL expressions that reference fields across resources, and it infers dependency order and catches errors at definition time. It guards schema contracts with the breaking-change annotation described earlier. It is pre-1.0 and its announcement described it as not production-ready ([[entities/kro]]). The wiki did not read kro's status schema at primary-source depth.

**Kyverno** sits on the admission contract. It began as a webhook engine, in which every matching request is sent to Kyverno's own service for a decision, and that design carries the availability and `failurePolicy` risks described in section 10. Its newer ValidatingPolicy type is CEL-first and can generate native ValidatingAdmissionPolicy objects, so enforcement can move into the API server and the Kyverno webhook leaves the request path for those checks. What it adds beyond the native feature is background scanning, policy exceptions, reports and evaluation of non-Kubernetes JSON. The contrast with Gatekeeper is now documented from both projects' own pages. Kyverno defaults to failure policy `Fail` with a 10 second timeout and wants three admission replicas, so an outage can block matching requests, while Gatekeeper defaults its webhooks to `Ignore` with 3 second and 1 second timeouts and relies on audit to catch what slipped through. Each trades a different risk: Kyverno risks blocking the cluster when it is down, and Gatekeeper risks admitting a bad object during an outage. The two failure-policy defaults are laid out side by side in [[comparisons/admission-webhooks-and-failure-policies-across-crossplane-kro-argo-cd-config-connector-ack-cluster-api-gatekeeper-and-kyverno]], and section 8 gives the details ([[entities/kyverno]]).

**cert-manager** is a different kind of example, a plain operator and not a policy engine. It does not decide anything about other teams' objects. It runs validation, defaulting and conversion webhooks for its own CRDs, and it solves its own certificate bootstrapping with a self-signed CA, so it shows what an ordinary controller needs from the admission and conversion machinery ([[entities/cert-manager]]).

**Cloud add-ons** expose cloud resources close to one to one. [[entities/config-connector]] reconciles level-triggered (it reacts to the current state of the object and the cloud resource, not to individual change events) against the Google Cloud API, deletes the cloud resource by default when the object is deleted, and acquires an existing cloud resource when the manifest name matches. [[entities/ack]] runs one controller per AWS service with scoped permissions, a periodic resync of ten hours by default (verified against ACK's drift-recovery page, which says controllers attempt to detect drift once every ten hours, and against the default resync constant in the runtime source; Helm values let you shorten it for all kinds or per kind, as in [[examples/ack-resync-period-tuning-for-stateful-resources]]), and a deletion-policy annotation, and it lacks `observedGeneration` on conditions. [[entities/azure-service-operator]] generates CRDs from ARM schemas and uses owner references to model lifecycle relationships. All three rely on [[concepts/finalizers]] to make external deletion safe, and none ships a composition layer, which is the gap kro and Crossplane fill.

**Cluster API** shows the contracts at the opposite end from GitOps. Its topology controller added an SSA helper in pull request 6495, stated as a way to "leverage on the API server for handling controllers co-authoring the same object," because the ClusterClass controller and the infrastructure and control plane providers all write to the same generated objects ([[examples/cluster-api-topology-controller-uses-ssa-for-co-authored-objects]], [[entities/cluster-api]]). Its machines are immutable by design, a deliberate rollout model akin to Pod versus Deployment.

**Plain controllers** built with [[entities/kubebuilder]] and [[entities/controller-runtime]] get most of the contracts by convention. The Kubebuilder book teaches rebuilding status from the observed world rather than from prior status, setting owner references on children, writing status through the subresource, and applying with a named field owner. Two practical details from the controller-runtime source are worth knowing. First, its cache can be narrowed to save memory, and each option has a cost the source names: restricting by namespace, label selector or field selector makes objects outside the restriction invisible to the cache, a transform such as `TransformStripManagedFields` is documented as able to "lead to a significant reduction in memory usage" (a vendor statement, not a measurement) but removes the stripped fields from every cached read, metadata-only informers give only metadata, `DisableFor` makes every read of a type a live API call, and skipping the deep copy on reads lets a caller mutate shared cache objects. Unstructured reads bypass the cache unless it is told otherwise. No memory measurement exists for any of these options. See [[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]. Second, choosing an operator framework has no documented selection criteria: the wiki found only each project's self-description, so any advice about Kubebuilder versus the alternatives would be opinion, and the comparison page says so ([[comparisons/operator-frameworks-by-self-description-kubebuilder-operator-sdk-java-operator-sdk-kopf-shell-operator-and-metacontroller]]).

Admission, which this tutorial left as a gap, is now read for most of the tools above, from their source on default branches as of 2026-11-26. Crossplane core (v2.5.0) ships one webhook, `crossplane-no-usages`, which blocks deletes of resources labelled `crossplane.io/in-use=true` with failure policy `Fail` by default (a Helm value can set `Ignore` for managed Kubernetes services that reject wildcard `Fail` webhooks), and it removed its XRD and Composition webhooks in favor of CEL validation. kro (v0.10.0) and the ACK s3 controller ship no admission webhook in the files read and rely on the generated CRD schema and CEL. Config Connector (v1.162.0) ships ten handlers in a separate webhook-manager and Cluster API (v1.14.4) ships many mutating, validating and conversion webhooks, and every entry in both uses failure policy `Fail`. Argo CD showed no webhook, but only in a search of tree paths, so that absence is unverified, and namespace exclusions in the Cluster API and Config Connector manifests were not searched exhaustively. See [[comparisons/admission-webhooks-and-failure-policies-across-crossplane-kro-argo-cd-config-connector-ack-cluster-api-gatekeeper-and-kyverno]] and [[findings/crossplane-core-ships-one-fail-closed-usage-webhook-and-replaced-its-xrd-and-composition-webhooks-with-cel]].

## 12. Design principles for APIs that platforms can build on

The contracts above also suggest what a good platform API looks like. The following principles are drawn from the wiki's findings, each with its reasoning.

**Treat the GVK as a product, and choose group and plural names as if they were permanent.** Group and plural names are baked into URLs, RBAC, stored references and every client, and the wiki found no tool that makes renaming easy. Crossplane forbids it outright. Evolve through versions, and take the Kubernetes alpha, beta, stable ladder seriously, because upstream removes betas on a published schedule and your consumers will treat yours the same way.

**Declare complete, structural schemas and decide on pruning deliberately.** If a field is not declared, it vanishes silently. A schema is also where CEL rules, defaults, list markers and printer columns live, so a complete schema makes the type self-describing to every tool that reads OpenAPI.

**Prefer conversion that cannot go down.** Use `None` when schemas are compatible. When a webhook is unavoidable, treat it as critical infrastructure, because its outage can stall reads and even garbage collection. When a change is breaking enough, a new type may be safer than a conversion, as the Crossplane guidance allows.

**Separate intent from observation, and publish observation in the standard form.** Enable the status subresource when a single reconciler owns the object, record `observedGeneration`, and use the conventional conditions structure so generic tools can read readiness. Where several reconcilers read one configuration object, consider leaving it statusless, as Prometheus Operator did, rather than merging conflicting writers into one block.

**Mark lists and maps so that ownership can be shared.** Add the Go markers `+listType=map`, `+listMapKey=name`, `+mapType=granular|atomic` and `+structType` where they apply; they generate the schema extensions `x-kubernetes-list-type`, `x-kubernetes-list-map-keys` and `x-kubernetes-map-type` that the API server reads, and that is why a keyed list shows up in `managedFields` as per-entry `k:{"name":"web"}` keys. Without them, a CRD behaves as atomic, and every tool that wants to co-own a list will conflict. Controllers should apply only the fields they own and name their field manager.

**Make conflicts visible, and decide force policy per actor.** Controllers should force fields they own. CD systems that act on behalf of humans should prefer to surface disagreement or, at least, offer per-field ignore rules. The wiki records that the sources do not settle the best default for combined GitOps and controller environments, so the principle is to make the choice explicit and observable instead of inheriting a tool's default by accident.

**Push validation into the schema and in-process policy first, and keep webhooks for what only webhooks can do.** CEL rules travel with the CRD, need no service, and cannot take the cluster down. Reserve webhooks for external data or arbitrary code, and when you use them, scope narrowly, declare `sideEffects`, run replicas, exclude system namespaces, keep mutations idempotent, and choose `failurePolicy` deliberately.

**Keep the surface small.** CRDs share etcd, discovery and OpenAPI computation. A design that generates thousands of CRDs pays for it in API server memory and discovery latency, so group types sensibly and avoid per-field CRDs.

**Design for deletion and for retrofits.** Use finalizers and owner references so that cleanup is safe, document deletion policies for external resources, and remember that enabling a subresource or a stricter validation on an existing type changes what existing clients experience.

The unifying reasoning is that a shared control plane works only as long as every participant keeps the contracts simple enough to be checked by generic machinery. Names that never change, schemas that are explicit, ownership that is recorded per field, and validation that runs inside the server are all ways of making the cluster, rather than any one tool, the arbiter of what is true. That is why Flux, Crossplane and kro can coexist, and why most of their failures turn out to be contract violations. The next part builds on this by looking at what happens inside the controllers that read and write these objects.
