# Resource Graphs and Ordering: Dependencies, Readiness and Convergence

> **Audience:** An engineer fluent in Kubernetes who needs depth on how platforms order dependent resources and decide when one is ready.<br>
> **Purpose:** Teach the principles behind dependency ordering, readiness signals, convergence and teardown in Flux, Argo CD, kro and Crossplane, so the reader can reason about new situations without a product manual.<br>
> **Status:** Draft<br>
> **Created:** 2026-11-27<br>
> **As of:** 2026-11-27<br>
> **Draws on:** the wiki pages listed under Further reading, which rest on the research dossiers, practitioner write-ups and project documentation recorded in the wiki sources.<br>

Platform stacks that turn Git, a pipeline or a platform API into running infrastructure all answer the same question: in what order do dependent resources come into being, and how does anything know an upstream resource is done? This document explains how Kubernetes leaves ordering to convergence by retry, and how Flux, Argo CD, kro and Crossplane each add an ordering layer on top, whether as dependencies between objects, waves inside a sync, references inside a graph, or logic inside a function pipeline. It follows the readiness signals those layers depend on, the failure modes that follow from each design, teardown ordering, and the places where the stacks choose differently. It is written for engineers who operate Kubernetes and build or run platforms on it, and who want to reason about dependencies, readiness and convergence in new situations without a product manual.

## 1. Why ordering is the platform's problem, not the cluster's

Most real systems are made of parts that depend on one another. A database must exist before the application that connects to it, a network must exist before the subnet inside it, and a custom resource definition (a CRD, the object that teaches the API server about a new kind of resource) must be established before anyone can create an instance of that kind. When engineers write these things down as manifests, they naturally imagine that the cluster will understand the dependencies and build things in a sensible order. It does not. Kubernetes gives no ordering between dependent resources: the API server accepts each object on its own merits, and nothing in the substrate says that one object must wait for another. [[findings/ordering-and-dependency-failures]]

The reason is not an oversight. Kubernetes is built around controllers, which are programs that watch the declared state of some resources and keep working to make the real world match it. Each controller runs a reconcile loop, a function that reads the desired state, looks at the actual state, and takes whatever idempotent action (an action that is safe to repeat) moves the two closer together. The loop is non-terminating, so a controller never "finishes" and goes home; it keeps correcting failures indefinitely. [[concepts/reconciliation-loop]] The design favors many small controllers that each own one aspect of the system, and none of them is in charge of a global schedule.

What replaces a schedule is convergence by retry. The substrate accepts that complex systems do not update instantaneously, so instead of building a strict dependency graph up front, resources are applied concurrently, fail where their dependencies are missing, and retry until those dependencies exist and the system settles on the desired state. [[concepts/eventual-consistency-and-convergence]] This works because controllers are level-triggered: each pass recomputes the whole difference between desired and actual state from what is currently true, instead of reacting to a particular event. A missed or reordered event therefore delays the correct end state without preventing it, and a failing reconcile is retried with exponential backoff, meaning that the wait between attempts grows. [[concepts/reconciliation-loop]] [[concepts/eventual-consistency-and-convergence]] The practical consequence is familiar to anyone who has applied a large set of manifests to a fresh cluster: the first pass shows transient errors that resolve on their own, and a platform that leans on retries and status conditions does not need strict ordering to get there in the end. [[concepts/eventual-consistency-and-convergence]]

Retry is a baseline, not a guarantee of comfort. Some failures are not transient in the sense that a human or a pipeline would call it so. Applying a custom resource before its CRD is established fails with a "no matches for kind" error in Helm, Argo CD and Flux alike, and whether that failure heals itself depends on whether the tool retries or stops and marks the whole operation failed. [[findings/ordering-and-dependency-failures]] The same finding notes that tools built around waves or hooks can halt a sync where a plain retrying controller would eventually succeed. Its source is a research summary of how the main stacks behave, so the claim is best read as a pattern, not a specification.

That is why ordering becomes the platform's problem. Any platform that composes resources has to decide where order comes from. It can lean entirely on retry and accept noisy first passes. It can add explicit dependency declarations with health checks, as Flux does between Kustomizations, or phases and waves, as Argo CD does. It can derive order from references between resources, as kro does within a graph, or let Crossplane's composition functions withhold dependent resources until what they depend on is ready. [[findings/ordering-and-dependency-failures]] Each answer has its own failure mode, and the choice largely determines how the platform fails: quietly and eventually, loudly and immediately, or stuck waiting on a signal that is lying. The rest of this document is about making that choice deliberately, starting with the mental model that underlies all of these answers.

## 2. The mental model: convergence, readiness gates and two axes of status

The previous section ended with a decision every composing platform has to make: since the cluster gives dependent resources no order, someone must say where order comes from. Before comparing the answers, it helps to understand what the cluster does offer instead, because every ordering mechanism in this document is built on top of it. The thesis of this section is that ordering is an optional layer over a level-triggered, retrying substrate, and that any gate in that layer is only as honest as the status signal it reads. That signal has to separate "the controller is working" from "the thing is usable," and "this status is current" from "this status describes an older spec."

Kubernetes does not promise that the gap between desired and actual state closes instantly, nor that a controller sees every intermediate change. It promises that the system keeps working toward the most recently declared state, and convergence is the observable result: once disruptions stop, actual state settles on desired state. This is usually called eventual consistency. In practice it means you can apply a large set of manifests in any order, watch a few transient errors appear, and then watch them disappear as the things they were waiting for come into existence. [[concepts/eventual-consistency-and-convergence]]

The mechanism that makes this safe is level-triggered reconciliation. A level-triggered controller does not react to the news that something changed. Each time it runs, it receives only the name of an object, reads the current state of the world, and recomputes the whole difference between what is wanted and what exists. An edge-triggered system, by contrast, acts on events, and a single missed or reordered event can leave it permanently wrong. Because the level-triggered controller recomputes from scratch, a lost event merely delays the correct outcome. A reconcile that fails returns an error and is retried with increasing delay, and a reconcile that is healthy but waiting for something can ask to be revisited after a period of time. [[concepts/reconciliation-loop]] [[concepts/eventual-consistency-and-convergence]]

Put these together and you get the axiom that the rest of the document leans on. In the substrate, "wait for my dependency" does not need to be written anywhere. A resource that needs a network that does not yet exist fails, backs off, retries, and eventually succeeds. Explicit ordering is therefore a refinement, not a requirement, and it is worth asking what it buys. It buys fewer noisy failures, less wasted retrying against external systems, and a deliberate sequence where a wrong order is dangerous rather than merely untidy. It costs a dependency model the platform must define, execute and keep honest.

In this document a readiness gate means something broader than the Pod field of the same name: it is the point in an ordering layer where a dependent is allowed to proceed only after something it depends on is reported ready. Every ordering mechanism you will meet in the following sections has one, whether it is called a dependency, a wave, a readiness expression or a health check. The gate itself is trivial: it reads a field and compares it to a value. All of its trustworthiness therefore lives in the field it reads.

That field is usually a condition. A condition is one entry in a resource's `status.conditions` list, with a type such as `Ready`, a status of `True`, `False` or `Unknown`, a machine-readable reason, a human-readable message, and a record of when it last changed. Conditions are the common language that lets a GitOps tool wait for health, lets a composite resource aggregate the state of its children, and lets a person debug. They live in the status half of the spec and status split, where users and delivery tools own the spec, which records intent, and controllers own the status, which records what has been observed. [[concepts/conditions]] [[concepts/spec-status-split]]

The first question a status signal must answer is whether the controller is functioning or the thing is usable. These are different facts. Crossplane, a platform that represents cloud resources as Kubernetes objects, draws this line explicitly. Each cloud resource is represented by a managed resource, an object that a provider controller reconciles against the cloud API. A managed resource reports `Synced`, which says whether the provider's reconcile against the external system succeeded, and `Ready`, which says whether the external resource is actually available. Read together, `Synced` false points toward credentials, configuration or provider trouble, while `Ready` false with `Synced` true points toward the cloud side still doing its work. A gate that read only a merged signal could not tell a broken platform from a resource that is still coming up. [[entities/crossplane]] [[concepts/conditions]]

The second question is whether the status is current or stale. Every object carries `metadata.generation`, a counter that increases whenever the spec changes. A controller records the generation it has processed in `observedGeneration`, either at the top of the status, on each condition, or both, and sources do not rank those placements. If `generation` is greater than `observedGeneration`, the status describes an older spec, and whatever it says about readiness is a statement about the past. Because convergence takes time, there is always a window in which the spec has changed and the status has not caught up, so a gate that skips this comparison is trusting a record that may predate the change it is meant to protect. [[concepts/spec-status-split]] [[findings/misleading-readiness-and-stale-status]]

Two failures recur in the sections that follow, and section 9 treats them formally. Premature readiness is a gate opening before the thing is done, and stale readiness is a status that describes an older spec. In both cases the ordering layer behaves exactly as designed and still produces the wrong outcome, because it was handed an answer to a question nobody asked it. The evidence is mostly user reports and tool documentation, not postmortems from named organisations, so the claim is about the design weakness and not about how often it bites. [[findings/misleading-readiness-and-stale-status]] [[concepts/conditions]]

One more principle belongs in the model, because ordering and drift correction both depend on it. A controller that talks to an external system has to decide how often to re-check that system. The worst-case time to notice drift is the length of the re-check cycle, so a long cycle is slow to correct, while a short one spends calls on an external API that may be slow, rate limited or billed. Each tool and each provider chooses its own cadence for its own reasons, and the choice is a trade-off to be made per class of resource, not a constant to be copied. [[findings/drift-detection-latency-is-the-interval]]

With that model in hand, the useful question about any platform is not whether it orders things but where its order comes from and how truthful its readiness signal is. Flux gives the first clean answer: it makes ordering a relationship between independently reconciled objects and insists that "ready" means healthy, not merely applied.

## 3. Flux: ordering between objects, with health-defined readiness

Flux is built from several single-purpose controllers that talk to each other only through custom resources, and its Kustomization object is the unit that applies a set of manifests from a source. Each Kustomization is reconciled independently, on its own schedule, by the same retrying, level-triggered machinery described in the previous section. Nothing in that machinery knows that one Kustomization should wait for another. Ordering is therefore something Flux layers on top, and it does so as a relationship between whole objects rather than as a sequence of steps inside one operation. [[entities/flux]]

The mechanism is a field called `dependsOn`, which lists other Kustomizations (or HelmReleases) that must be Ready before this one is applied. If a named dependency is not Ready, the dependent simply does not proceed, and it is reconsidered on a later pass. Because every object is already retried until it converges, waiting costs nothing special: the dependent declines to act until the dependency's status says Ready. Flux does not give up eventual consistency to get ordering. It adds dependencies so that retrying happens in a controlled order instead of as a burst of transient errors. [[examples/flux-dependson-and-health-checks-gate-rollout]]

Everything in this arrangement depends on what "Ready" means. If Ready meant only that the apply call returned without error, a dependent could start while the objects it relies on were still pulling images or waiting for a controller to wake up, and the ordering would be a formality. Flux therefore lets a Kustomization define a **health check**, which is a declared list of applied objects whose condition Flux must observe as healthy before it marks the Kustomization itself Ready. A `wait` option extends the same idea to everything the Kustomization applied. The result is that Ready means the applied objects are healthy, not merely applied, and a dependent's start is tied to the health of what it depends on. [[examples/flux-dependson-and-health-checks-gate-rollout]] [[entities/flux]]

The next question is how Flux judges health for kinds it has never heard of, and the answer is **kstatus**. kstatus is a Go library from the Kubernetes SIGs that computes a generic status for any resource that follows the common status conventions: it looks at whether the controller has observed the latest generation of the spec, whether the conditions `Reconciling` and `Stalled`, which are set to true only while something is in flight or wrong, are present, and whether a `Ready` condition is true, and from those it reports values such as in progress, current or failed. Because it needs no per-kind logic, Flux can hold back a dependent until a custom resource it was never taught about is healthy, provided that resource's controller speaks the convention. [[entities/kstatus]] For kinds that do not follow the convention, Flux accepts custom health expressions written in CEL, the small expression language Kubernetes also uses for admission rules, so the author can state which fields mean healthy for that kind. [[entities/flux]]

This reliance on a convention is the central design point of the section, and it has a sharp edge. Generic readiness checking is only as good as the status every provider writes. kstatus falls back, for an unknown kind with no `Ready` condition, to assuming the object is always reconciled, and it reads `observedGeneration` only at the top level of status. A resource whose controller never writes that field, or one that reports health under a different condition name, can therefore look healthy before it is. The failure is silent: the dependent starts, nothing errors, and the ordering the author thought they had does not exist. Cluster API, the project that models whole clusters and their machines as Kubernetes resources, is the clearest illustration of drift from the convention, because its resources report an availability condition in place of `Ready`. The CEL option exists precisely as the escape hatch. Which provider objects Flux can judge generically, and which need per-kind expressions, is a question the document returns to in section 9; the point to hold here is that a convention shared across independent authors is a dependency like any other. [[entities/kstatus]] [[entities/flux]]

The same relationship between objects solves a problem that is easy to mistake for a different one: a custom resource cannot be created before its CustomResourceDefinition exists. The familiar error says no matches exist for the kind, and it appears in Helm, Argo CD and Flux alike. The cause is API discovery, the mechanism by which a client asks the API server which resource kinds it serves and maps a kind to an endpoint. Until the CRD is registered and established, discovery does not list the kind, so the apply cannot even resolve what it is being asked to create. [[findings/custom-resources-applied-before-their-crd-exists]]

Flux's answer is not a special rule for CRDs. It is the ordinary one: split the work into two Kustomizations, one that installs the controller and its CRDs and another that holds the custom resources, and make the second depend on the first. Because the first becomes Ready only once its health checks pass, the second is applied only after the CRDs exist. The same discovery dependency appears inside health checks, since they reference objects by apiVersion and kind. What looks like a special case is an ordinary instance of "this unit may start when that unit is healthy". [[findings/custom-resources-applied-before-their-crd-exists]] [[entities/flux]]

The trade-off is granularity. Ordering lives between objects, so you set the order by deciding how to divide manifests into Kustomizations, and a dependency is a statement about whole sets, not individual resources. In return the mechanism is simple, visible in status, and consistent with the rest of the system. Flux orders between objects that a pipeline delivers, while other designs order inside a single operation or inside one abstraction. [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]] The next section looks at the first of those alternatives, Argo CD, which orders work inside one sync operation instead.

## 4. Argo CD: phases, waves and hooks inside one sync

The previous section described ordering as a relationship between objects that are reconciled independently, where a dependent starts only when its dependency reports healthy. Argo CD answers the same question from the opposite direction. Instead of many controllers each watching a few objects, a single operation, the sync, takes a whole set of manifests from Git and applies them to a cluster. Because one operation owns the entire batch, it can impose an order on the batch directly, and the author declares that order with annotations on the manifests rather than with edges between separate objects. This section looks at how that ordering works, how health decides when the operation may advance, and what the design costs.

Argo CD sorts the work in a sync by a fixed sequence of keys. The first key is the sync phase, which is a named stage of the operation: resources and hooks marked for the PreSync phase run before the main body of the sync, the Sync phase is the main body, and the PostSync phase runs after everything has succeeded. Within a phase the second key is the wave, an integer written in an annotation on each resource. Lower numbers apply first, and resources that carry no annotation sit in an implicit middle group, so an author can place something ahead of the rest by giving it a lower number than the others. Argo CD also breaks ties between resources in the same phase and wave with fixed secondary rules, so the order is deterministic even where the author said nothing. [[entities/argo-cd]] [[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]]

The most useful property of this scheme is that a wave does not merely start before the next one. Argo CD advances to the next wave only after every resource in the current wave has been applied and has become healthy. That makes waves a way to express things Kubernetes itself does not order: a custom resource definition before the operator that serves it, an operator before the workloads it manages, a dataset before the table inside it. The documented example places CRDs, then operators, then workloads in successive waves, and a practitioner's account of Config Connector, Google's set of Kubernetes controllers that turn Google Cloud objects into custom resources, uses an earlier wave for a BigQuery dataset than for the table inside it, because the table cannot be created until the dataset exists. Pruning is Argo CD's removal of live resources that Git no longer declares. In that account, waves solved creation but did nothing for deletion order, a point section 8 takes up. [[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]] [[findings/ordering-and-dependency-failures]]

Everything depends on what "healthy" means, and Argo CD derives it from the status of each live object. A health check is a small piece of logic that reads an object's status and returns one of a handful of verdicts, such as Healthy, Progressing, Degraded or Suspended. For the built-in Kubernetes types the logic is compiled in. For custom resources it cannot be, because, as Argo CD's own documentation puts it, custom resource definitions do not follow a consistent or standardized status format. The extension point is the Lua health script: a short script, written in the Lua language and attached to a kind, which receives the object and inspects its status fields and conditions to decide which verdict to return. Argo CD ships scripts for whole groups of provider kinds, including Config Connector, ACK (the AWS Controllers for Kubernetes), Crossplane and Upbound resources, kro's resource graph definitions and several Cluster API kinds, and a team hosting other custom kinds writes its own. [[entities/argo-cd]] [[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]]

This is where the design shows its sharpest edge. Flux, as the previous section showed, leans on a shared readiness convention for most objects. Argo CD instead judges each kind with its own script, so the quality of every wave boundary is the quality of a script someone wrote. A provider object whose status the script mishandles never turns Healthy, and Argo CD's documentation warns that an unhealthy resource in an early wave means the application can never get to healthy. Every later wave is then blocked behind it. There is also a structural limit that no script can repair: where a provider's conditions carry no record of which generation of the spec they describe, a script can report Healthy before the controller has even noticed a spec change. The evidence here is the project's documentation and shipped scripts, not an independent benchmark. [[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]]

The second tool for ordering is the hook. A hook is a resource, usually a Job, that Argo CD runs at a particular phase of the sync instead of treating it as part of the application. A typical use is a database migration before a new version rolls out. A hook brings imperative work into a declarative system: it says "run this", not "this should exist". Because Argo CD runs hooks as part of every sync, a hook has to be idempotent: running it twice must leave the system as running it once would. A migration that fails halfway and is run again, or a sync that is retried, must not corrupt anything. Hooks also carry an ordering hazard. A PreSync hook runs before the main sync, so a migration Job placed there can start before the ConfigMaps or Secrets it reads have been applied, and it fails until the author moves those resources into an earlier phase. [[concepts/idempotency]] [[findings/ordering-and-dependency-failures]]

Now consider what happens when something goes wrong. A failed PreSync hook stops the sync and marks it failed, and the same is true if any resource in a wave fails. Nothing later runs. This is the fundamental contrast with the model in the previous section. Independently reconciled objects tolerate a missing dependency by retrying until it appears, so many ordering mistakes resolve themselves. A wave-based sync is a single transaction-like operation that prefers to stop and report rather than push on with later waves against a broken earlier one. That makes a rollout easy to read, since the failed step is exactly where the sync halted, but a single bad resource halts the whole operation. Retrying a whole sync is a coarser tool than a dependent object quietly waiting for its dependency. [[findings/ordering-and-dependency-failures]]

Hooks also sit outside desired state, and that carries a design lesson. A hook is an event attached to a particular kind of operation, not a fact about what should exist, so any reconcile path that is not a full sync may legitimately skip it. One practitioner reports that when Argo CD self-heals drift, meaning it automatically syncs to pull a hand-edited cluster back to Git, the corrective run can be a partial sync that does not execute hooks. Argo CD's documentation describes hooks as running during a sync without saying whether such a run triggers them, so that claim is one author's reading and not settled behavior. The principle holds either way: anything that must always happen belongs in desired state, where reconciliation can see it, and not in an event that only some paths fire. [[findings/argo-cd-self-heal-runs-a-partial-sync-that-skips-hooks-according-to-one-author-so-a-migration-hook-can-be-missed]]

The pattern across this section is that Argo CD declares order by annotation, enforces it by health, and accepts that one failure stops everything. The next section turns to kro, which removes the annotations altogether. Rather than asking an author to number the waves, it treats every reference from one resource to another as a dependency and derives the order, the parallelism and even the teardown from the graph those references form.

## 5. kro: ordering inferred from references in a resource graph

Argo CD asks an author to declare order: phases and wave numbers are written onto resources, and the controller enforces them by watching health. kro starts from the opposite premise. If a platform author already has to write down which resource uses a value from which other resource, then the order is sitting in the definition, and nobody should have to say it a second time. kro is a controller that turns one custom API into a group of Kubernetes resources, and the way it decides what to create first is the clearest example of ordering that is derived and not declared. [[entities/kro]]

Some vocabulary first. A resource graph is the set of resource templates in one definition together with the references that connect them. In kro the definition is called a ResourceGraphDefinition, and it holds a schema for the new API plus a list of templates. Any field value inside a template may be an expression written in CEL (the Common Expression Language met in the Flux section), which has no open-ended loops and no side effects, so an expression always finishes and can be type-checked before anything runs. A template might say that a Deployment's environment variable takes its value from the status of a bucket declared elsewhere in the same definition. That reference is the whole ordering mechanism. [[entities/kro]]

Every such reference becomes an edge, an arrow meaning "this resource needs a value from that one." The resources and arrows form a directed acyclic graph: directed because each arrow points one way, and acyclic because following the arrows never leads back to the start. From that graph kro computes a topological order, a sequence in which every resource appears after everything it depends on, creates resources in that order, and publishes the order in the definition's status so an operator can read it. A circular reference has no valid order, so kro rejects it when the definition is applied, not when an instance is half built. [[entities/kro]] [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]

Once order is a property of a graph and not a list, other behaviors arrive without anyone writing them. Resources that reference only the user's input have no edges between them, so they are created in parallel. Teardown is the same graph read backwards: dependents are removed before what they depend on, and each wave is fully gone before the next begins, so a database is not deleted out from under the application still using it. And nobody maintains a numbered sequence that drifts out of date when a resource is added. The price is that only data dependencies can be expressed. If one resource must follow another for a reason that no value flows through, the author has to invent a reference to carry it. [[entities/kro]]

Ordering by references answers one precise question: can this template be filled in yet? A template that mentions a bucket's address cannot be rendered until that address exists, so kro waits for the field. That is field availability, and it is different from asking whether the upstream resource is healthy. A cloud database may publish its endpoint long before it accepts connections, so if "the field exists" were the only rule, a dependent could be applied while its upstream was still coming up. [[findings/kro-readywhen-gates-dependents-in-a-resource-graph-definition-but-only-reports-health-in-the-alpha-graph-api]]

kro therefore offers a second mechanism, readyWhen: a list of CEL conditions, evaluated against the resource itself, that define when that one resource counts as ready. Without it, a resource is ready once it has been created and its references resolve. With it, an author can say a database is ready only when a particular status condition is true, and dependents wait for that condition before they are applied. The expressions may refer only to the resource they describe, which keeps them local and easy to debug but means a condition that spans two resources must be written another way. [[findings/kro-readywhen-gates-dependents-in-a-resource-graph-definition-but-only-reports-health-in-the-alpha-graph-api]]

The design point to carry away is that these two mechanisms are separable, and a builder of a graph engine has to keep them distinct. An engine can order by field availability and also hold dependents on readiness, or it can order by field availability alone and treat readiness as information for humans and status. Both are coherent, and the same field name can mean different things in each. For a platform author the consequence is practical: before relying on "wait until the upstream is healthy," confirm that the engine in use actually holds dependents on readiness. Where it does not, the working technique is to make the dependent reference a field that exists only once the upstream is healthy, which turns a health condition back into a field-availability condition. The support for this comes from kro's product documentation, with no independent measurement of the behavior. [[findings/kro-readywhen-gates-dependents-in-a-resource-graph-definition-but-only-reports-health-in-the-alpha-graph-api]] [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]

A third question, whether a resource should exist at all, is a different axis again. kro answers it with includeWhen, a list of CEL conditions that decide whether a template is instantiated. If a resource is skipped, everything that depends on it is skipped too, because their references can never resolve. Existence is neither readiness nor order: an absent resource has not failed to become healthy, and a slow resource has not stopped existing. Conflating the three is how definitions go wrong. [[findings/a-kro-includewhen-on-a-volatile-upstream-status-field-makes-resources-flip-flop]]

The failure is easy to describe. Suppose an author includes a resource only when an upstream status field, such as a count or a transient phase, has a certain value. That field moves as the real world changes. The controller creates the resource when the condition holds, deletes it when the condition stops holding, and does the same to every dependent, so with cloud infrastructure the result is repeated creation and deletion of real things that nobody intended. The principle is that inclusion should depend on stable inputs, meaning values the instance author set in the spec, and not on observations that fluctuate. Readiness is the safe way to wait for health because holding a dependent back deletes nothing. Section 10 returns to this among the failure modes that come from a controller faithfully acting on an unstable signal. [[findings/a-kro-includewhen-on-a-volatile-upstream-status-field-makes-resources-flip-flop]]

## 6. Crossplane: ordering as logic in a function pipeline

kro answers the ordering question by reading references out of a declared graph, so the graph itself is the plan. Crossplane answers it from the opposite direction. A Crossplane composition does not describe a graph at all. It describes a program that runs on every reconcile, and ordering is whatever that program does.

A few terms first. A composite resource is the high-level object a platform team invents and users create, such as a "database" that stands for a cloud instance, a subnet group and a credentials secret. A composition is the recipe that says which lower-level resources a composite resource should own. In Crossplane the recipe is a pipeline: an ordered list of steps, each naming a composition function. A composition function is a small program, packaged and installed like any other Crossplane component, that runs as a long-lived gRPC server in a pod, so the pipeline is code the platform team versions and ships like any other service. On each reconcile Crossplane calls the steps in order, and each call carries two pieces of state. Observed state is what Crossplane currently sees in the cluster: the composite resource and the composed resources it already owns, with their statuses. Desired state is what the pipeline wants to exist, accumulated as the steps run, with each step receiving what earlier steps produced and returning a revised version. [[concepts/composition]] [[examples/a-composition-function-pipeline-turns-observed-state-into-desired-state]]

This is the level-based loop every controller runs, applied to a bundle: look at what is, compute what should be, and let the platform converge the difference. The consequence for ordering is easy to miss. In kro, order falls out of structure, because a reference is an edge and the engine sorts the edges. In a pipeline there are no edges for the engine to read, and the only ordering it provides is the order of the steps, which governs how the desired state is assembled and not the order in which cloud resources come to exist. If a database must not be requested until its network has an identifier, the function author expresses that by inspecting observed state: when the network's status does not yet carry the identifier, the function leaves the database out of the desired state, and on a later pass, once the observation has changed, it includes it. Ordering is a conditional written in code, re-evaluated on every pass, and it converges because the loop keeps running, not because anything was scheduled. [[concepts/composition]]

That freedom has a price. A pipeline built on a general-purpose templating or scripting function needs hand-written creation order, and it needs hand-written guards against deleting resources when a dependency is briefly unavailable, where a graph engine would infer the first and wait on the second. The omission rule sharpens the danger: a resource that a function stops returning is deleted. A function that leaves the database out because the network is not ready yet has, if it is careless about observed state, asked for the database to go away the moment the network briefly looks unready. Ordering guards and deletion guards are the same logic seen from two sides, and the expressiveness that makes pipelines powerful is what makes them easy to make complicated. [[concepts/composition]]

Readiness follows the same pattern. In kro, as the previous section described, the controller computes whether an instance is ready from the graph. In Crossplane the controller computes almost nothing of the kind. Each desired resource a function returns carries a readiness marker with three values: explicitly ready, explicitly not ready, or unspecified. Crossplane counts a composed resource as ready only when the function marked it explicitly ready, so "not ready" and "unspecified" both count as not ready. The composite resource then reports itself available only when no composed resource remains on the not-ready list, and otherwise reports that it is still being created, with a message naming the resources it is waiting for. A function may also set readiness on the composite as a whole, and that explicit value takes precedence over the derived one. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]]

The practical result is a trap unrelated to the cloud. A pipeline that composes perfectly healthy resources, but contains no function declaring any of them ready, leaves the composite resource reporting "creating" indefinitely. Nothing is broken; the author forgot to say so. Composite readiness is a declaration, not a measurement, and the pipeline author owns it, which is why a pipeline is normally ended with a function whose only job is to fill that gap. The evidence for this behavior is Crossplane's own source code and not its user documentation. The design consequence is that the safe default is conservative: a resource the author has said nothing about is treated as not ready, which protects dependents at the cost of requiring the author to declare readiness. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]]

That gap-filling function judges resources in layers. It leaves alone anything already carrying an explicit marker, applies resource-specific health checks to standard Kubernetes kinds, and for any other kind falls back to a convention: a resource is ready when its status carries a condition of type Ready with the value True. This is the shared-convention half of a wider pattern in which a provider's objects are judged either by a condition every provider agrees to publish or by a per-kind script someone writes for each kind. Crossplane's own managed resources publish that condition, and so do the cloud-vendor controllers from AWS (ACK) and Google (Config Connector), so on paper both satisfy the convention. The support for that last point is thin. It consists of the function's documentation and the vendors' documented condition definitions, and no worked example or first-party test of Crossplane composing ACK or Config Connector objects appears in the sources, so the compatibility is an inference from documented conditions and not an observed result. [[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]]

One distinction keeps the readiness story honest. Synced says whether the last reconcile succeeded and Ready says whether the thing is operational, but for composites the two come from different places. Synced is derived by the controller from whether every composed resource is itself synced, so an error in any one surfaces on the composite. Ready is the function-authored summary. A composite can be Synced and stuck in creating because nobody declared readiness, or Ready by declaration while a composed resource underneath has stopped syncing. Read Synced as the platform's report and Ready as the author's claim. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]]

All of this concerns bringing things up. Functions do not run when a composite resource is deleted; Crossplane removes the composed resources itself. The careful sequencing a function author wrote for creation therefore has no automatic counterpart on the way down, and that asymmetry is where the next section begins. [[concepts/composition]]

## 7. Teardown: reverse order, owner references and finalizers

The previous section ended with composition as code, where ordering is whatever the author writes. Deletion is the half of that story that authors forget to write, because nothing in creation order carries over to it automatically. A platform that creates a network, then a database, then an application has described a dependency graph only implicitly, and the cluster does not remember that graph when the whole thing is removed. Unless some layer builds a teardown order on purpose, the order is accidental, and ordered teardown, once a layer does build it, trades liveness for safety.

Start with what Kubernetes provides by default. An owner reference is a field on a child object that names its parent, and the garbage collector is the controller that watches those links and deletes children whose parent has gone. In its default background mode the parent is removed immediately and the collector cleans up dependents afterward, with no regard for which sibling should disappear first. If a database must go before the network it lives in, background deletion does not honor that, because the collector may mark the whole tree for deletion at once. Foreground deletion is the alternative mode: the parent stays visible, held by a special finalizer, until its dependents are gone. A finalizer is a token in an object's metadata that keeps the API server from removing the object until the controller that owns the token has finished its cleanup and removed the token. Foreground deletion makes the owner wait only for dependents that have explicitly declared that they block their owner's deletion. The sources describe it as holding the parent until those children are gone, and they say nothing that orders one child before another, so the order between a database and the network it lives in is left to the tool above. [[findings/background-deletion-gives-no-teardown-ordering-between-dependents]] [[concepts/finalizers]]

The consequence is practical. Cloud APIs enforce their own order and refuse to delete a network that still has a database in it, so parallel deletion shows up as failures and retries, and sometimes as leaked resources. A team that composes resources under one parent and trusts owner references to unwind them gets a race, not a sequence.

Because of this, the tools that care about teardown build their own mechanism, and they differ in instructive ways. kro avoids owner references on the children of an instance for two stated reasons: they delete out of order, and they cannot link a namespaced object to a cluster-scoped one. Instead it records the children in an ApplySet, which is an inventory object that lists every resource an apply operation created so that a later operation can find and prune them as a group. With the inventory persisted, kro does not need to rediscover the graph at deletion time. It deletes in reverse dependency order, in waves, and each wave must disappear completely before the next one starts. The instance's own finalizer stays until nothing remains. This evidence is project documentation describing design intent, not a measured failure, and no incident report describes it. [[findings/default-owner-references-delete-out-of-order-and-cannot-link-namespaced-to-cluster-scoped-objects-so-kro-uses-applysets]] [[examples/kro-deletes-instance-resources-in-reverse-dependency-waves]]

Crossplane keeps owner references and layers policy on top. A composite can be deleted in the background, in the foreground so that children go before the composite is released, or through a pipeline mode in which a composition function removes resources from desired state step by step, which makes the function the author of the teardown order. The foreground and pipeline modes are the tool-level answer to the gap above, and a user who needs ordering has to ask for it. Crossplane also offers claims, namespaced objects through which an application team requests a composite resource without touching the composite itself. Deleting a claim appears to order teardown only because the claim controller deletes the composite using its own policy, not because the collector does. A delivery tool can also override the choice: when Argo CD deletes with foreground propagation, Crossplane ignores its own composite policy. [[examples/crossplane-foreground-and-pipeline-deletion-policies-order-composed-resource-teardown]] [[entities/argo-cd]]

Argo CD works through a different channel again. An Application carries a finalizer, and deleting the Application cascades to the resources it deployed. During a sync, pruning reverses wave order, so resources created last are removed first. Flux uses a finalizer on its Kustomization with a deletion policy chosen between cascading, waiting for termination, and orphaning, and Cluster API orders machine teardown with annotation hooks instead of finalizers. The comparison between them is one of choosing a policy versus choosing an order. [[comparisons/finalizer-gated-teardown-across-argo-cd-flux-kro-and-cluster-api]]

The evidence on Argo CD and ordering is not settled. Argo CD's documentation states that pruning during a sync runs the waves in reverse, but does not say whether cascading deletion of a whole Application honors waves. One practitioner's account, a single secondary source covered in the next section, says Argo CD deletes Config Connector children without ordering. The two statements may describe different operations, but the practitioner does not say which he means, so the question is open. [[entities/argo-cd]] [[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]]

The cost of ordered teardown follows directly from how it works. Waiting for each wave to disappear completely means that one child with a finalizer whose controller is missing or failing holds its wave, and every later wave waits behind it. kro's documented diagnosis for a stuck instance is to look for finalizers on children in the active wave. The same property that protects a dependency from vanishing before its dependents finish cleanup also lets a single broken controller freeze the rest of the teardown. Unordered deletion fails noisily and recovers by retrying, while ordered deletion fails by stopping. A platform chooses safety, and pays for it with a procedure for stuck finalizers and a temptation to force them off, which skips the cleanup the finalizer was protecting. [[concepts/finalizers]]

This is also why the provider layer matters. A provider controller that models no graph of its own leaves teardown to whoever sits above it, and the next section looks at how practitioners have coped with that gap.

## 8. Lessons from practitioners: creation order is easier than deletion order

The previous section ended on the point that a delivery layer does not get deletion order for free from creation order, and that someone has to build it. A practitioner's account from 2023 shows what that looks like in a real cluster. The account comes from a single author writing on a blogging platform, so it is best read as one engineer's experience rather than as a survey of the field, but the lesson it carries is architectural and holds up well against the mechanisms covered so far.

The author delivered Google Cloud resources through Config Connector, a set of controllers that turn Google Cloud objects such as a BigQuery dataset and a table inside it into Kubernetes resources, with Argo CD applying the manifests from Git. The table refers to its dataset by name, so the table cannot be created until the dataset exists. Config Connector did not impose that order itself, and the author describes it as lacking the kind of dependency graph that a tool like Terraform builds before it acts. The fix lived in the delivery tool. Argo CD offers sync waves, which are numeric annotations on resources that tell it to apply the lower-numbered group first and wait for it to become healthy before moving on. Giving the dataset an earlier wave than the table made creation reliable. [[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]] [[examples/a-practitioner-ran-a-cronjob-that-removed-finalizers-from-config-connector-bigquery-tables-whose-dataset-was-deleted-first]]

Deletion was another matter. The author reports that Argo CD offered no matching order for removal, so when the dataset object was deleted first, the table object could no longer be cleaned up and stayed in a failed deletion state, held in place by the finalizer its controller had put on it. His remedy was a scheduled job that looked for such tables, checked that the dataset object was gone, and stripped the finalizers so Kubernetes could finish the delete. He judged this safe only because deleting a dataset in Google Cloud also removes its tables, so nothing was left behind in the cloud. Forcing a finalizer off skips cleanup, so it can leak real resources whenever that argument does not hold. Only the creation half of his account is well supported; the deletion claim stands on his word alone. [[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]]

The lesson is about where ordering lives. A provisioning controller that reconciles each resource on its own, with no graph connecting resources to one another, has nowhere to record that one thing must precede or follow another. That knowledge has to come from somewhere, and the delivery tool is the nearest candidate, so the provider's missing dependency model becomes the operator's task. Because creation is the direction people test first, delivery tools tend to serve it better, and the deletion direction is discovered later, usually during an incident. [[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]]

A related design lesson concerns readiness. A sync wave can only wait for a resource to become healthy if the tool can tell what healthy means. A generic delivery tool cannot understand every provider's resources, so it relies on every provider reporting readiness through the same convention in its status. When one provider reports it differently, or too early, every ordering built on that signal quietly inherits the flaw. The next section examines how that signal fails.

## 9. Failure modes of the readiness signal

This section asks what happens when the readiness signal is wrong. The answer is consistent across the evidence. Every gate fails the way its signal fails: early when the status is premature or describes a generation the controller never observed, silently when a summary hides in-flight work, and falsely healthy when the signal is built from conditions that only appear when something is wrong. In each case the gate worked exactly as designed, which is why these failures are hard to notice.

Premature readiness is the first family, and it builds on the observedGeneration idea from section 2. A freshly created resource has an empty or partial status because its controller has not run yet. A consumer that infers health from the absence of problems reads that emptiness as success. The kstatus library, which Flux and other tools use to judge arbitrary custom resources, behaves this way by design: when the status carries no observedGeneration, the generic generation check is skipped, and when no Ready, Reconciling or Stalled condition has been written, the default answer is that the resource is current. A resource no controller has touched therefore looks finished, and its dependents start against a provider that has not acted. Cluster API resources show the pattern: a status that carries no record of the generation it describes lets a generic reader treat a resource that no controller has touched as already reconciled. The status conventions do not define what a default observed generation should be for an untouched resource, so a generic reader has no shared meaning to give it. The practical repair is a per-kind health check written by the consumer, which means the consumer, not the provider, takes on the work of keeping the signal honest. [[findings/premature-readiness-in-kstatus-based-tools]]

The same failure appears when a condition is present but old. A resource that was Ready for its previous spec stays Ready after the user edits it, until the controller notices and rewrites the status. In that window a script that waits for Ready, a delivery tool that waits for health, or a GitOps health check can all succeed on a condition produced before the change. Any consumer that does not compare observedGeneration with generation can be released by such a stale condition. The evidence for this is self-reported by users, so it supports the existence of the failure and not any precise window. [[findings/ready-can-be-reported-for-a-spec-generation-the-controller-has-not-yet-observed]] The defense has two ends: the controller records the generation it has processed, and the consumer compares it with the current generation before trusting any condition. A Ready with a lagging observed generation is a statement about the past, and under eventual consistency there is always some time in which that is the case. [[findings/misleading-readiness-and-stale-status]]

The second family comes from compression. A summary condition is a single condition, such as Ready or Synced, that stands in for a much larger state so that an alert rule or a delivery tool has one place to look. Compression can lose the most important fact, which is that work is still happening. The failure is easiest to see with a long-running external operation. A summary condition is only as honest as the code that writes it, so if the controller reports success for the reconcile call while a long cloud-side update is still running, the summary stays True and the resource looks finished. Nothing flips to False, which is why the failure is silent: automation that polls the summary sees convergence that has not happened. Controllers should therefore record an in-progress condition when a long call starts and not let a later success path overwrite it, and consumers who care should watch the operation-specific condition and observedGeneration as well as the summary. [[findings/a-summary-condition-can-stay-true-while-a-long-async-operation-is-running]]

The third family is a matter of polarity, meaning which value of a condition is the good news. A positive condition such as Ready is healthy when True. An abnormal-true condition is present and True only when something is wrong or in flight. The kstatus library defines two of these: Reconciling is True while a controller is working on a change and has not converged, and Stalled is True when the controller has stopped making progress and will not resume without outside change. The weakness follows directly. If healthy means the absence of Reconciling and Stalled, then a controller that is not running writes neither and the resource looks the same as a healthy one. The kstatus documentation says so itself: with the controller not running, the resource will look like it is in a good state when it is not. A controller that has not yet written any condition is treated as reconciled, which is the premature case seen from the other side. [[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]

Positive conditions avoid part of this, but they trade it for another ambiguity, since a False Ready cannot say whether the object is progressing or doomed. That is why kstatus pairs the two styles. The Kubernetes API conventions recommend neither polarity as a general rule, so a builder adding a condition type has to choose deliberately. The generation comparison covers either choice, because a stopped controller stops advancing the observed generation, but only when the controller writes that field at all. [[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]] [[concepts/conditions]]

All three failures share a premise: that a generic consumer can read many kinds of resource with one set of rules. That premise is what makes dependency gating workable across countless custom resource types, and it is also the weakest point, because the conventions for conditions are voluntary. Crossplane, ACK, Config Connector, Flux, kro and Cluster API publish different vocabularies, and Ready means different things in each. [[concepts/conditions]] When a provider changes its vocabulary or omits a condition, nothing announces the break. A generic reader that looks for Ready on a kind that publishes a different summary finds none and, under the kstatus default, may conclude the resource is reconciled. In the Cluster API case, where the summary is an availability condition and not Ready, the conclusion was that Flux cannot rely on kstatus for that kind. Sources state the exact result for a naive reader as an inference from kstatus defaults and the type definition, not as a tested outcome. [[findings/premature-readiness-in-kstatus-based-tools]] Generic readiness therefore quietly becomes per-kind readiness: CEL health expressions for Flux, Lua checks for Argo CD, and readiness expressions in kro definitions, each encoding what a provider's author meant. That is a sound response, but it moves the burden of keeping the signal honest to the platform team and turns every provider upgrade into a possible silent change to ordering. [[concepts/conditions]]

These failures all concern the signal and appear even when the graph is drawn correctly. The next section turns to the graph and its definition, and to the ways the ordering mechanisms themselves break through missing prerequisites, destructive diffs, oscillating existence, platform-wide blast radius and the seams between layers.

## 10. Failure modes of the graph and its definition

The previous section followed the readiness signal through its failures: a status that arrives early, a summary that hides work in flight, a condition that reads healthy because nothing abnormal was reported. Those are failures of the question "is this resource ready?" This section turns to failures of the structure that asks the question. Ordering mechanisms are written by people or inferred from their expressions, and they fail in five recurring ways: a prerequisite is missing when something needs it, an absent dependency is read as an instruction to delete, a resource's existence depends on a value that will not hold still, a single bad definition stops every instance built from it, and the layer that creates resources hides them from the layer that is supposed to track them.

The most familiar failure is the custom resource that arrives before its definition. A custom resource can only be created once the cluster knows its kind, and the cluster learns a kind from a CustomResourceDefinition (CRD). Registering a CRD is not instantaneous. The API server must accept the definition, add the new endpoints, and report the definition as established, which is the point at which the kind can actually be served. We will call that moment CRD establishment. A client that submits a custom resource before establishment, or when the CRD was never installed, receives the error "no matches for kind", which means that the client's discovery of what the cluster serves has no entry for that group, version and kind. The everyday example is a chart or GitOps application that ships a monitoring operator's service-monitor object alongside the operator that defines its kind. Practitioner write-ups report the same error across Helm, Argo CD and Flux, and the sources name other causes too, such as a wrong API version or a mismatch between an operator and its CRDs. The lesson is that discovery is a snapshot of what the cluster knows at one moment, so the failure belongs to no single tool. [[findings/custom-resources-applied-before-their-crd-exists]] [[examples/servicemonitor-no-matches-for-kind-in-helm-and-argo-cd]]

The remedies are design statements about ordering. One is to split the work into dependency-ordered units, so that the unit providing CRDs and their controllers must be ready before the unit holding the custom resources is applied; Flux's documentation describes exactly this arrangement. The other is to install a pinned, compatible CRD set first and wait for establishment before anything depends on it. Flux's own health checks refer to resources by API version and kind, so they too depend on discovery. Argo CD users describe remedies of their own, but the sources for that side are brief post titles and snippets that do not set out the mechanism, so this document does not state what Argo CD does as settled. [[comparisons/missing-crd-handling-flux-versus-argo-cd]]

The second failure appears when ordering is written by hand in a system where omission means deletion. A composition function returns the desired state, and any resource it leaves out of that output is removed. A template that skips a resource because a dependency it observed is momentarily absent therefore asks the platform to delete something that should have stayed. The guard against that, and the logic for creation order, must be written and tested by the composition author for every dependency. A hands-on tutorial that built the same API both ways reports that kro's expression-inferred ordering, which waits for referenced values to resolve and deletes in reverse dependency order, covers both concerns without hand-written guards. That evidence is a single tutorial about the template approach, so treat it as a plausible illustration rather than a measured result. The same source adds the opposite trade-off: the function pipeline is more expressive, and so easier to make complicated. [[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]

The third failure is oscillating existence, the inclusion problem described in the kro section. When a condition that decides whether a resource exists reads a field that changes from one reconcile to the next, the resource and everything depending on it are created and deleted in turn, which for cloud resources means real infrastructure repeatedly appearing and vanishing. Static checks cannot catch it, because the expression is well formed; its value is simply unstable. The remedy is the one already given: existence on stable inputs, waiting on a readiness condition. [[findings/a-kro-includewhen-on-a-volatile-upstream-status-field-makes-resources-flip-flop]]

The fourth failure is a matter of blast radius. kro snapshots each edit to a graph definition, and the documentation states that when the latest snapshot fails to compile, instances stop progressing and kro does not fall back to an older snapshot. That is a deliberate trade-off. Static validation moves many mistakes, including schema errors, unknown kinds, expression type errors and cycles, to definition time, long before any instance is touched. The price is that one definition is shared by every instance of its API, so a bad edit that passes no check reaches all of them at once. Crossplane lets a composite stay on a pinned composition revision, so a bad revision reaches only the composites that follow the latest; the sources give no equivalent rollback for kro, which makes edits to a shared definition high-risk changes. [[findings/a-kro-graph-revision-that-fails-compilation-stops-all-instances-with-no-fallback]]

The fifth failure lives in the seam between layers. Kubernetes owner references have two limits that matter here: the garbage collector deletes dependents without regard to ordering among siblings, and a cluster-scoped object cannot be owned by a namespaced one. kro therefore avoids owner references on instance children, tracks them with labels and an inventory, and deletes in reverse dependency order. The cost lands at the delivery agent. A GitOps agent such as Argo CD needs to know which live objects belong to an application so that it can show their health and prune them, and it often works that out from owner references or from a tracking annotation it places on each object. Because kro's children carry neither by default, the agent cannot see them as part of the application. The kro documentation tells Argo CD users to add an owner reference and a tracking annotation to each templated resource, while warning that doing so brings back out-of-order collection and rejects cross-namespace or cluster-scoped children. The documentation describes design intent rather than a measured incident. [[findings/default-owner-references-delete-out-of-order-and-cannot-link-namespaced-to-cluster-scoped-objects-so-kro-uses-applysets]] [[examples/kro-resources-need-owner-references-and-tracking-ids-to-be-tracked-by-argo-cd]]

These five failures share a cause. Each is a place where one layer's picture of the world, whether discovery, observed status, or ownership metadata, differs from another layer's. How each stack chooses to place and compute ordering decides which of these failures it is exposed to, which is the subject of the next section.

## 11. How the stacks choose differently

The previous section described how ordering mechanisms fail. Those failures look different from one stack to the next because the stacks answer three design questions differently: where ordering lives, whether it is inferred or written by hand, and who computes readiness. Each answer buys one property and pays for it with another. A checkable definition costs flexibility, and a system that keeps trying until it converges costs some legibility about why it has not yet. Seen from a distance, the choices also turn out to be compatible, because every layer reduces to desired state handed to a reconciler, and a reconciler does not care whether its desired state was written by a person or produced by another layer.

The first question is where ordering lives. Flux and Argo CD order objects that a pipeline or a Git repository delivers. Flux expresses order between its own objects, so one Kustomization declares that it depends on another and waits until that dependency reports Ready, with health checks deciding what Ready means. Argo CD expresses order inside a single sync, by phase and then by wave number, and the next wave starts only when the current one is healthy. In both, the ordering belongs to the delivery layer, and the resources being delivered know nothing about it. kro and Crossplane place ordering inside an abstraction instead: one custom resource stands for a bundle of resources, and the abstraction decides the sequence in which the bundle comes into existence. [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]] The practical consequence is that a delivery-layer ordering is visible to whoever reads the pipeline but must be repeated for every stack that needs it, while an abstraction-layer ordering is written once by the platform author and inherited by every consumer of the abstraction. The same pile of CRDs, controllers and custom resources is therefore modeled differently depending on the layer you ask.

The second question is whether order is inferred or written. kro infers it. Every reference from one resource to another's fields is an edge in a graph, creation follows a topological order, deletion runs in reverse, and a cycle is rejected when the definition is created, not when an instance first reconciles. [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]] Crossplane leaves ordering to composition functions: small programs, run as services, that receive the observed state and return the desired state, and that can withhold a dependent resource until its prerequisite shows up in the observed state. Because a function is ordinary code, it can express any ordering rule, but the order exists only in the function's logic and the loop's repeated re-observation, so a mistake tends to appear at reconcile time. [[comparisons/crossplane-composition-functions-versus-kro-resource-graph-execution-models]] The trade is checkability against flexibility. kro restricts authors to a small expression language that terminates and has no side effects, which is what allows validation up front, and Crossplane constrains only the contract between the function and the controller, which frees the code but removes the guarantee. [[comparisons/where-the-expressiveness-bound-sits-in-crossplane-functions-and-kro-cel]] Functions also add running parts that must be healthy before any composite can reconcile, which is an operational price that an in-controller language does not charge. [[findings/composition-functions-add-moving-parts-that-must-be-healthy]]

The third question, who computes readiness, matters because ordering is only as good as the signal that releases the next step. In Crossplane the author of the pipeline defines it. A composed resource counts as ready only when a function says so explicitly, and a resource whose readiness is left unspecified counts as not ready. The composite's Ready condition is therefore a summary that the pipeline writes. A pipeline that composes healthy resources but never marks any of them ready leaves the composite in a Creating state indefinitely, and the cause lies in the pipeline and not in the provider. The usual remedy is a closing step that derives readiness from each resource's own signals. [[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]] In kro the controller derives instance readiness from the state of the graph, and the definition's author can add per-resource readiness expressions that hold back dependents. [[comparisons/provider-fixed-versus-author-defined-condition-semantics-crossplane-versus-kro]] The first approach lets a team express any definition of ready at the cost of having to remember to write one, and the second gives a consistent baseline at the cost of tying readiness to the controller's model. Both can fail the same way when an author writes a lax condition, because a dependent will then start before its prerequisite is usable.

Beyond those three questions, two further observations complete the picture. The first is that the layers compose. A reconciler compares desired and observed state, and it does not care whether the desired state was written by a person or produced by another layer, so any layer that emits desired state can sit beneath another layer that consumes it. function-kro, a Crossplane composition function that embeds kro's graph builder and expression evaluator, shows this directly: a kro-style graph runs as one step of a Crossplane pipeline, followed by a step that marks readiness. From Crossplane the combination gains pinned composition revisions, so a bad change reaches only the composites that follow the latest revision, and the option to add other steps to the same pipeline. [[entities/function-kro]] [[examples/function-kro-runs-a-kro-resource-graph-as-a-crossplane-pipeline-step]] The combination inherits both sets of trade-offs, including one more running function that must stay healthy. Its documented behavior differs in places from standalone kro, so inferred order inside a Crossplane pipeline is the same idea and not the same machinery. [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]]

The second observation is what happens when a step fails. Argo CD's wave model stops the sync when a wave fails, so the failure is loud and the later waves never run. A reconcile-driven abstraction instead retries until the world converges, which hides transient failures and keeps liveness high, but a permanent failure can look like slow progress. The lack of ordering at the other end is also real. The Config Connector account in section 8 is the clearest example of the opposite gap: a provider with no ordering of its own pushed the work onto the delivery tool, and teardown was the half that went unhandled. [[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]] Taken together, the stacks do not disagree about whether order matters. They disagree about who writes it down, who proves it, and how loudly it fails, and that is the set of choices the next section turns into design principles.

## 12. Design principles to carry forward

The preceding sections compared how the stacks choose, and the comparison leaves a practical question for anyone building on them: which of those choices should you copy, and which should you treat as hazards? Four habits cover most of the ground. Treat order as a layer you choose, readiness as a contract you verify, existence as a function of stable inputs, and teardown as a design problem separate from creation.

The first habit concerns how much ordering to ask for at all. Kubernetes itself orders nothing: resources are applied concurrently, the ones whose dependencies are missing fail, and retries carry the system to convergence once the dependencies appear. [[concepts/eventual-consistency-and-convergence]] That is a perfectly sound default, and it costs you only transient errors on a first apply. Explicit ordering is something you add on top when those transient errors are unacceptable, for instance when a custom resource must not be submitted before its definition is served, or when a dependent would create expensive external infrastructure against a half-built foundation. Flux, Argo CD, kro, and Crossplane each add ordering at a different layer, between delivered objects, within a sync, or inside one abstraction. [[comparisons/ordering-models-flux-argo-cd-kro-crossplane]] The principle is to choose that layer deliberately and to ask for the weakest ordering that removes the failures you actually have. Every extra edge in a graph is a place where one stuck resource can stall everything behind it.

The second habit is the one the first quietly depends on. An ordering rule is only as trustworthy as the readiness signal behind it, because the rule says "wait until the upstream is ready" and the signal decides what ready means. Readiness is easy to confuse with "the controller is working," and a status can describe an older spec than the one the user just wrote. [[findings/misleading-readiness-and-stale-status]] A condition that says Ready while its recorded generation lags the object's current generation is a statement about the past, and a dependent released by it starts too early. So verify the contract before building on it. Check that the controller you wait on records which generation its status describes, and that it distinguishes a resource that is being reconciled from one that is usable. Crossplane's separation of a synced condition from a ready condition is the pattern to look for, since it keeps "the controller is working" apart from "the thing is usable." [[entities/crossplane]] [[concepts/conditions]] When the upstream's signal is weak, supply a stronger check of your own rather than trusting the weak one.

The third habit is about conditional inclusion. In kro, a condition on a resource decides whether that resource exists at all, and everything depending on it is skipped when it is false. Basing that condition on a volatile upstream status field, such as a readiness count or a transient phase, turns the creation decision into a loop: the resource is created when the expression is true, deleted when it turns false, and the dependents follow, which for cloud resources means repeatedly creating and destroying real infrastructure. [[findings/a-kro-includewhen-on-a-volatile-upstream-status-field-makes-resources-flip-flop]] The remedy is to let existence depend only on stable inputs, which in practice means fields the instance author sets, and to express "wait until healthy" as a readiness hold, which delays a dependent without deleting anything. The same reasoning applies in any tool: a decision to delete should never hang from a signal that is allowed to move.

The fourth habit is to design teardown on its own terms, because the order that is safe for creation is not automatically safe in reverse. kro deletes in reverse dependency waves and holds its finalizer until every managed resource is gone. A stuck finalizer on one child therefore pauses the whole deletion. [[examples/kro-deletes-instance-resources-in-reverse-dependency-waves]] Argo CD and Flux mostly choose between cascading the delete to children and orphaning them, so their control is a policy rather than an order. [[comparisons/finalizer-gated-teardown-across-argo-cd-flux-kro-and-cluster-api]] Crossplane gives reverse ordering only when the user asks for foreground or pipeline deletion. Namespace deletion shows the cost of not asking. Each managed resource holds a finalizer because its cloud object must be deleted through the cloud API, and that call needs the credentials stored in a Secret. If the whole namespace is deleted, its objects go in arbitrary order, and a credentials Secret that carries no finalizer of its own can disappear first. The managed resources can then no longer authenticate, so they stay Terminating. The finalizers protect each resource but cannot protect the object they depend on. [[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]] The guidance is to decide, for every dependency you create, what must outlive what at deletion, and which tool will enforce it.

A closing caution applies to choosing between the tools. The sources offer a rule of thumb, not outcome data: kro when the building blocks are already Kubernetes resources, Crossplane when the platform must drive cloud APIs directly. [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]] Whichever you pick, the four habits above are what keep it predictable.
