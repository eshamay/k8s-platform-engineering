# Part 4: Platform Abstractions from Managed Resources to Resource Graphs

> [!NOTE]
> **Audience:** Engineers with real Kubernetes operating experience (pods, deployments, services, RBAC, kubectl) who have not yet worked with controllers, API machinery, or platform abstractions in depth.<br>
> **Purpose:** Teach how platform teams publish simple, owned APIs over complex infrastructure, and how Crossplane, kro, and the surrounding tools trade flexibility, operability, and expressiveness against one another.<br>
> **Status:** Active, part 4 of the tutorial series.<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** The concept, example, finding, comparison, decision, and entity pages of this wiki listed under Further reading, which in turn rest on the research dossiers in `sources/`.

## 1. Why platforms need abstractions: the cognitive-load problem

Imagine you are an application developer who needs a PostgreSQL database for a new service. Without a platform, you must learn what the cloud calls its database offering, which subnet group it belongs to, which security group rules let your pods reach it, how the encryption key is chosen, what backup retention your company requires, which tags finance expects on every billable object, and how to wire the resulting endpoint and password into your Deployment. None of that knowledge is about your product. All of it is cognitive load, and it multiplies across every team in the company. The usual response is a platform team, a group whose job is to absorb that complexity once and let everyone else ask for what they want in a few words.

Kubernetes gives the platform team an unusually good place to do this. Earlier parts of this series explained that Kubernetes is more than a container scheduler. Its API server, with etcd behind it, is a general database and orchestration engine, and any kind of object can be registered with it through a custom resource definition, as Part 2 of this series covers in detail. Once a kind exists, it automatically gets the machinery you already trust: authentication, RBAC, audit logging, schema validation, list and watch, and `kubectl`. A controller then watches objects of that kind and drives the real world toward what the object declares, which is the reconcile loop that Part 3 of this series describes, and it is the idea behind every tool in this tutorial. This tutorial is about what happens when a platform team uses that machinery on purpose to build a product: a small, stable, versioned API that hides a large pile of infrastructure behind it.

The wiki's vocabulary note names the layers of that idea, and this tutorial follows them in order. At the bottom is the managed resource, a one-to-one Kubernetes object for one external thing such as a single VPC or IAM role. Delivered by a provider (a package that installs the controllers and custom resource definitions for one cloud or service), these objects teach the cluster to speak to a cloud API. Above them sits the composite resource, a higher-level, opinionated object such as a `PostgreSQLInstance` or `WebApp` that bundles many lower-level ones. The mapping from the high-level object to the low-level ones is a composition. Crossplane implements all four layers. kro, a newer project, collapses the top two into a single definition that describes a graph of resources. The tutorial then widens out to Helm, Kustomize, hand-written operators, Score, Radius, and Kratix, which attack the same cognitive-load problem from different directions and pay different prices for it.

One caution about evidence runs through the whole article. The wiki is built from public documentation, vendor and consultancy blogs, and adopter lists, with very few independent measurements or postmortems. Where a claim rests on one blog or a vendor's own announcement, the text below says so. Both Crossplane and kro are moving quickly, so the wiki's own pages carry a 180-day staleness window and you should check version-specific details against current documentation.

## 2. Managed resources: one Kubernetes object per external resource

The simplest abstraction is almost no abstraction at all. A managed resource is a Kubernetes object that stands for exactly one thing outside the cluster. The Crossplane documentation puts it this way: "Crossplane calls the object inside Kubernetes a managed resource and the external object inside the Provider an external resource." A provider's controller reads the real thing, compares it with what the object asks for, and creates, updates, or deletes the real thing to close the gap. The shortest mental model is a Deployment-style controller loop whose pods happen to be cloud resources.

Here is an illustrative managed resource for an AWS bucket. Field names follow the pattern the wiki describes, though exact API groups and versions vary by provider and release, so treat it as a sketch and not a copy-paste manifest.

```yaml
apiVersion: s3.aws.upbound.io/v1beta1
kind: Bucket
metadata:
  name: team-a-reports
  annotations:
    crossplane.io/external-name: team-a-reports-prod
spec:
  forProvider:
    region: eu-west-1
  managementPolicies: ["*"]
status:
  atProvider:
    arn: arn:aws:s3:::team-a-reports-prod
  conditions:
    - type: Ready
      status: "True"
    - type: Synced
      status: "True"
```

Read the snippet from the top. The `spec.forProvider` block is the authoritative desired state, and the Crossplane documentation calls it the "source of truth" for the external resource, which means that someone editing the bucket in the cloud console will see the edit reverted on the next poll. The `crossplane.io/external-name` annotation says which real bucket this object maps to. The `status.atProvider` block is what the provider last observed, and it is written by the controller and not by you. Two conditions, explained in , diagnose different failures: `Synced` says whether the last reconcile succeeded, while `Ready` says whether the external thing is usable. A resource can be `Ready=True` and `Synced=False`, a quiet state in which the bucket exists but drift correction has stopped.

The word "next poll" deserves a number, and the wiki found that no single number exists. The managed reconciler in crossplane-runtime, the shared Go library on which every provider's reconciler is built, defaults to a one-minute poll interval, Crossplane core exposes a `--poll-interval` flag that also defaults to one minute, and providers generated by Upjet, the code generator that turns Terraform providers into Crossplane providers (Section 3 returns to it), default to ten minutes, so how quickly a console edit is reverted depends on which layer set the interval for the provider you run ([[findings/crossplane-poll-interval-defaults-differ-by-layer-with-one-minute-in-core-and-runtime-and-ten-minutes-in-upjet-providers]]). The `Synced` condition also has a documented blind spot with a real report behind it. In provider-aws issue 2287, a team changed the configuration of an Amazon MSK (managed Kafka) cluster, AWS took more than an hour to apply the update, and `Synced` stayed `True` for the whole hour because crossplane-runtime overwrote the pending state with `ReconcileSuccess`. An `AsyncOperation` condition exists and reads `Ongoing` while the work runs, but it sits outside the conditions most alerts watch, and the wiki's source reading of Upjet and crossplane-runtime found that the behavior is still present. The Crossplane documentation and the Upjet code also disagree about whether that condition's status is `True` or `False` while the operation is ongoing, so a monitor should be written against the live object and not against the documentation example ([[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]], [[findings/upjet-and-crossplane-runtime-source-still-reports-reconcilesuccess-while-an-async-operation-runs]], [[findings/crossplane-v2-5-docs-and-source-disagree-on-stage-labels-condition-status-and-group-suffixes]]). The lesson for a platform author is that a green `Synced` means the last reconcile call returned without error, not that a long cloud operation has finished.

The `managementPolicies` list is the main safety lever. A value of `*` means every verb and is the default. `["Observe"]` gives read-only import or a permanent reference. A list that omits `Delete` means "manage this, but leave the real resource behind if the object is removed," and an empty list pauses reconciliation. The same feature began life as a three-value enum in a design document and shipped as a list, and the v2.5 documentation and import guide still label it beta. Older advice about `deletionPolicy: Orphan` therefore needs translating, and the translation is mechanical once you know it: `ObserveOnly` becomes `["Observe"]`, an empty list is a pause, and orphan-on-delete becomes a list that leaves out `Delete`. No single official page tabulates that mapping, so the wiki assembled it from the release notes, the documentation, and the runtime code. The interaction with Kubernetes garbage collection is worth stating because no v2 documentation page does. When a cascade deletes a managed resource object, whether the cloud resource goes too is decided by `managementPolicies` and not by the owner reference: in the crossplane-runtime source the managed reconciler deletes the external resource only when it exists and the policy set allows `Delete`, and otherwise it unpublishes connection details and removes its finalizer. A composition that gives its composed resources a policy list without `Delete`, for instance observe-only references to a database another team owns, will therefore lose the Kubernetes objects when the composite is deleted while the cloud resources keep running. That is the intended behavior for a retained database and a leak for everything else. This reading comes from source and the documentation's statement that the external resource is not deleted, because the wiki found no page that connects the two, and it did not cover what happens when a namespace is deleted while the provider is down ([[findings/a-managed-resource-without-delete-in-its-management-policies-is-removed-from-kubernetes-but-its-cloud-resource-stays]], [[decisions/choose-management-policies-for-an-imported-resource]]). The old field has not vanished everywhere. Crossplane v2.0.0 removed `deletionPolicy` from the namespaced managed resources, but the older cluster-scoped managed resources keep it, a deprecated resolver in the runtime combines the two fields so that the real resource is deleted only when both allow it, and the upstream issue to deprecate the field formally is still open, so there is no formal deprecation yet. An earlier statement that management policies simply take precedence over `deletionPolicy` is therefore too coarse for legacy resources. A related field, `spec.initProvider`, holds values applied only at creation, which lets another system own a field afterward; one documented use is letting an autoscaler own the size of a node group.

Deletion deserves its own paragraph because it is where managed resources differ most from ordinary Kubernetes objects. Deleting a Deployment removes pods you can recreate. Deleting a managed resource, by default, deletes the real database. The mechanism that makes this safe in the other direction is the finalizer, a string in `metadata.finalizers` that tells the API server not to remove the object until a controller has finished cleaning up. When you delete such an object, the API server only sets a `deletionTimestamp`; the controller sees that, deletes the external resource, removes its finalizer, and only then does the object disappear. The price is that a missing or failing controller strands objects in `Terminating`, and forcing a finalizer off skips the cleanup it guarded, which can leave billable resources running. Crossplane, ACK (AWS Controllers for Kubernetes, Amazon's per-service controllers for AWS resources), and Config Connector (Google's equivalent for Google Cloud) all default to deleting the cloud resource, and each offers an opt-out under a different name. The finalizer strings themselves differ, and they are what you search for on a stuck object. ACK renders `finalizers.<apiGroup>/<Kind>` for each generated controller and removes it only after the AWS resource is cleaned up, with asynchronous deletes requeuing so the finalizer stays until the deletion completes. Config Connector uses `cnrm.cloud.google.com/finalizer` plus a second `cnrm.cloud.google.com/deletion-defender`. kro uses `kro.run/finalizer` on instances, definitions and revisions, and `kro.run/graph-finalizer` on the alpha Graph objects, removing it with a merge patch so that field-manager ownership cannot block the removal. None of the three projects documents these names, so they were read from source, and the literal string for a specific ACK service controller was not read, only the template form ([[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]]). A related hazard concerns credentials. Crossplane issue 7801 describes a namespace deletion in which a credentials Secret without a finalizer can disappear before the managed resources that need it have finished cleanup, leaving them stuck in `Terminating` because they can no longer authenticate. As of the wiki's reading the issue was open with no maintainer reply, and a merged change protects `ProviderConfig` objects while managed resources terminate but not the Secret behind them ([[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]], [[findings/crossplane-protects-providerconfigs-while-managed-resources-terminate-but-the-credentials-secret-behind-them-is-still-unprotected]]).

Managed resources also handle two awkward real-world problems. The first is importing something that already exists: set the external-name annotation to the real identifier, apply with `Observe` only, read `status.atProvider`, copy the needed values into `forProvider`, and then widen the policy. The recipe has sharp edges, including the manual copying, names that are ambiguous across regions, and relaxed validation while observing. The second is a create call whose response is lost. Crossplane writes a create-pending annotation before calling the cloud and a succeeded or failed annotation afterward, so a provider that restarts in between cannot tell whether a resource exists and blocks until a person decides. That conservative stop prevents duplicate or leaked resources at the cost of manual intervention. The opposite design choice has a measured cost in at least one project. An audit filed as ACK community issue 3177 on 2026-11-13 states that when a create response is lost, 48 resources across 22 ACK controllers either create a second AWS resource (28 of them) or fail on every following reconcile because the name is already taken (20 of them), with 12 more depending on undocumented behavior. The mechanism is that the controller records the AWS identifier in status only after the create call returns, so a stop in between leaves an AWS resource the custom resource does not know about. The count is the issue author's own reading of code and documentation, not a tally of production incidents, and the wiki did not re-run it ([[findings/an-ack-audit-found-48-resources-in-22-controllers-where-a-lost-create-response-duplicates-the-resource-or-wedges-the-custom-resource]], [[findings/a-create-that-succeeds-while-the-status-write-fails-can-leak-an-external-resource]]).

## 3. Providers: generated and hand-written, families versus per-service controllers

A provider is a packaged controller plus a set of CRDs that teaches a cluster to speak to a specific external API. In Crossplane it is an installable OCI package, meaning a container-registry artifact in the same format as an image, which the cluster pulls and unpacks. A `Provider` object installs it, each upgrade creates a `ProviderRevision`, a `ProviderConfig` selects credentials, and a `DeploymentRuntimeConfig` customizes the pod. Every provider reuses the same shared managed reconciler, which walks the phases Connect, Observe, Create, Update, and Delete. A provider author implements a small external-client interface for those phases and must make create and delete idempotent, meaning safe to repeat with the same result; the contributing guide's sharpest rule is that delete must not return an error when asked to delete something that is already gone.

Writing hundreds of such clients by hand would be impractical, so most large catalogs are generated. Upjet generates Crossplane providers from Terraform providers, so that the generated controllers reuse Terraform's resource logic at runtime while users see only a Kubernetes API. ACK generates its controllers from AWS API models, and Azure Service Operator v2 generates its CRDs from Azure Resource Manager schemas, with the documentation citing 150 or more resources. Generation explains why catalogs grow quickly, and it also explains a recurring drawback: a generated catalog inherits the behavior and the bugs of whatever generated it. Hand-written providers have their own pitfalls, such as treating "not found" as an error and breaking the create flow.

The most instructive operational story in this area is about counts. Because each external resource type is its own CRD, a provider for a big cloud implies hundreds of CRDs, and a multi-cloud set implies thousands. Crossplane's own blog reports that the original monolithic provider-aws passed 900 CRDs and could leave the API server unresponsive, sometimes for up to an hour during scale-up. Upbound's tests of a control plane with about 2,000 CRDs (the title of the wiki's example page says managed resources, so the pages differ on the unit, but the finding and the recheck dossier both count CRDs) found that discovery needed around 300 HTTP requests and hit client-side throttling, while server-side OpenAPI computation consumed CPU and a little over 4 MiB of resident memory per CRD, measured at 780 CRDs, a figure the wiki's recheck against the raw post tightened from an earlier "several MiB". Several upstream fixes followed, including higher kubectl discovery limits and lazy OpenAPI computation in Kubernetes 1.23, but code-generated providers outgrew them. The figures came through digests of the posts, so check them against the originals before quoting, although the follow-up recheck compared every figure with raw text and found no number that needed correcting, only the wording changes described here. Kubernetes' own tested scalability envelope does not include CRD count as a dimension, which is why platform tools fell into this gap.

Two packaging answers emerged. Crossplane split the monolith into provider families, scoped providers grouped under a family that share one configuration provider, so an operator installs only S3 and RDS and gets only those CRDs. The cost is more pods and memory, a trade the wiki documents in its provider-packaging notes. A caution on the memory side: the figures in the smaller-providers design document, about 600 MB for the Crossplane provider process and about 300 MB for each Terraform provider process, are goals the authors hoped to reach and not measurements, and the document is a draft whose last commit was in April 2023. Its CRD counts (872 for provider-aws, 692 for provider-azure, 325 for provider-gcp) did reproduce, and its statement that trouble starts "very approximately" above 500 CRDs is a rough threshold and not a tested limit. ACK took the opposite starting point and has always shipped one controller image per AWS service. The two converge on the same benefit, installing only what you use, from opposite directions. Crossplane v2 adds a finer tool: each managed resource type is represented by a ManagedResourceDefinition, and a ManagedResourceActivationPolicy lists exact names or prefix patterns so that only matching types become served CRDs. Two cautions keep that tool from being oversold. First, it is alpha: the documentation labels managed resource definitions and activation policies alpha, although the Crossplane source lists the flag that converts a provider's CRDs into definitions under its beta features with a default of true, so the docs and the code give different answers about the stage ([[findings/crossplane-v2-5-docs-and-source-disagree-on-stage-labels-condition-status-and-group-suffixes]]). Second, the default Helm install creates an activation policy named `default` that activates `"*"`, so a stock install activates every type and the CRD count does not fall until you turn that default off with `--set provider.defaultActivations={}` and list the groups you need. Patterns match exact names or prefixes only, not regular expressions, policies are additive, a definition's move to Active is one-way, and a definition starts Inactive only when the provider declares the `safe-start` capability; the MRAP documentation's examples use a `*.m.crossplane.io` suffix while the upgrade guide uses `.m.upbound.io`, so a pattern copied from the wrong page may activate nothing ([[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]]). Project-reported numbers show the pressure easing from the other side: the Crossplane v2.5.0 release notes say that stopping core from caching every CRD's OpenAPI schema cut heap from 338 MiB to 190 MiB and resident memory from 415 MiB to 250 MiB on a cluster with 791 CRDs, and a Crossplane blog post of 2026-10-08 reports provider memory falling by roughly 80 to 95 percent on a cluster of about 2,000 CRDs with crossplane-runtime v2.4. These are self-reported, the v2.5 documentation's own estimate of about 3 MiB of API server memory per CRD is an estimate and not a benchmark, and the wiki found no measurement of API server memory with and without activation policies ([[examples/crossplane-v2-4-and-v2-5-cut-memory-on-clusters-with-hundreds-to-two-thousand-crds]], [[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]]). When picking a strategy,  frames the options.

A note on vocabulary will save confusion later. Cluster API also uses the word provider, but there it means an implementation of a narrow contract that lets the core controllers build whole clusters on AWS, Azure, or vSphere, not a catalog of external resources. When someone says "provider," ask which family of tools they mean.

## 4. Composite resources, XRDs, claims and the v2 namespaced model

A managed resource is faithful to the cloud, and that is precisely its problem as a user-facing API. The application developer asked for a database, not for a subnet group, a parameter group, a security group, and an instance. The composite resource, abbreviated XR, is the answer. The Crossplane documentation defines it plainly: "A composite resource, or XR, represents a set of Kubernetes resources as a single Kubernetes object." A controller expands the small object into the lower-level objects it represents, keeps them reconciled, wires values from one child into another, reports aggregate readiness, and tears the whole set down in a sensible order. It is the ordinary controller pattern applied one level up, where the world being reconciled is a set of other API objects.

To publish such a kind, Crossplane asks the platform team to write a CompositeResourceDefinition, or XRD. It declares the group, kind, plural name, versions, scope, and a schema, and Crossplane generates a CRD from it, so the platform team never hand-writes the CRD. Here is a sketch of a small database API.

```yaml
apiVersion: apiextensions.crossplane.io/v2
kind: CompositeResourceDefinition
metadata:
  name: databases.platform.example.org
spec:
  group: platform.example.org
  names:
    kind: Database
    plural: databases
  scope: Namespaced
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                size:
                  type: string
                  enum: [small, medium, large]
                engineVersion:
                  type: string
```

The snippet shows the central design move. The developer sees a `size` of small, medium, or large and an engine version, and nothing about instance classes or storage types. The XRD name must be `<plural>.<group>`, and group and names are immutable after creation, so changing them means deleting and recreating the XRD. That is why the group and kind are product decisions: they become the public contract, and the wiki's decision notes on API naming record the consequence. Treat the example's API version string as indicative, since the XRD API changed between Crossplane major versions.

The scope field leads to the v1 and v2 difference that confuses many readers of older blog posts. In Crossplane v1, a composite resource was cluster-scoped, which is awkward for tenants who work inside namespaces. The fix was the claim: the platform team set `claimNames` in the XRD, a developer created a namespaced claim, and Crossplane created a cluster-scoped XR and linked the two through `spec.resourceRef` and `spec.claimRef`. In v2, XRs are namespaced by default, claims are not available for new-style XRDs, and the tenant boundary moves onto the XR itself. v2 also removed native patch-and-transform composition, offers namespaced managed resources under `.m.` API groups, and, importantly, offers no automated tool to move v1 cluster-scoped XRs and managed resources to the new model. The scope question now has a firmer answer than earlier drafts could give. The v2.5 XRD documentation lists three scope values in one table, `Namespaced` (the v2 default), `Cluster`, and `LegacyCluster`, which can mislead a reader into thinking a v2 XRD may choose `LegacyCluster` to keep claims. The shipped CRD says otherwise. The `apiextensions.crossplane.io/v2` XRD enumerates only `Namespaced` and `Cluster` and rejects `claimNames` with the message that claims are not supported in that API version, while `LegacyCluster` exists only on the v1 XRD API, whose scope defaults to it and which alone may offer claims. So `LegacyCluster` is a v1 XRD scope, and keeping claims means keeping a v1 XRD ([[findings/the-crossplane-xrd-docs-list-legacycluster-beside-v2-scopes-although-it-exists-only-on-the-v1-xrd-api]]). That v1 XRD is marked deprecated in its own CRD and still served, but the wiki found no removal date, and claims are still being maintained: v2.4.0 strips composite machinery fields during claim-to-composite sync, and v2.5.0 makes a claim fail reconciliation if its XRD lookup fails so that it cannot bypass an enforced Composition reference. Legacy cluster-scoped composites also cannot compose namespaced resources. The wiki did not check whether old concepts-section URLs redirect to the new composition and managed-resources pages. Because so much online content predates v2, the wiki's comparison of v1 claims with v2 namespaced composite resources is worth reading before you follow a tutorial. The upgrade path itself is to reach v1.20, fix deprecations with the conversion command, upgrade the core, optionally set activation policies, and then upgrade providers.

A composite resource also carries per-object controls. It can pick a Composition with `compositionRef` or `compositionSelector`, follow revisions automatically or pin one, be paused with the `crossplane.io/paused` annotation, and be forced to reconcile with `crossplane.io/reconcile-requested-at`. Its `Ready` condition becomes true only when the pipeline reports that all composed resources are ready. The mechanism is more literal than that sentence suggests. In Crossplane v2.5.0 each desired resource that a function returns carries a ready value that is `READY_TRUE`, `READY_FALSE`, or `READY_UNSPECIFIED`, and the composer counts a resource as ready only for `READY_TRUE`, so an unspecified value is treated as not ready. The XR then reports `Ready` as `Available` when no composed resource is unready and as `Creating` with an "Unready resources" message that names the offenders otherwise, while `Synced` turns to `ReconcileError` with an "Unsynced resources" message if a composed resource is not synced. A pipeline that composes resources but never sets `READY_TRUE` therefore leaves the XR in `Creating` indefinitely even though every child is healthy, which is why most pipelines end with `function-auto-ready`: it leaves alone any resource that already carries explicit readiness, applies optional CEL queries and built-in health checks for standard Kubernetes kinds, and falls back to the observed `Ready` condition equal to `True` last. A source comment in the composer asks whether an unspecified value should derive readiness from the resource's own condition, so this behavior could change ([[findings/a-crossplane-composed-resource-counts-as-ready-only-when-the-function-sets-ready-true-so-unspecified-readiness-leaves-the-xr-creating]]). An alpha deletion policy chooses Background, Foreground, or Pipeline teardown, which Section 9 returns to.

Governance is the usual motive for all this. A Crossplane blog on designing compositions for organizational needs argues that the platform team should expose well understood features behind its own versioned API and not pass every provider feature through, since native provider features can break proprietary environments or weaken compliance. Inside the Composition, tags can be applied to every composed resource automatically, and namespaced tenant segregation becomes an access-control pattern. The post is advocacy and not a named deployment, but the pattern is clear.

## 5. Compositions and composition functions: pipelines that turn observed state into desired state

A Composition says how an instance of the XRD's API becomes composed resources. It is matched to an XR by `compositeTypeRef`, which names the XRD's group and kind. In current Crossplane, the Crossplane documentation says, "A Composition is a pipeline of composition functions." A function is installed as a package and runs as a pod. On each reconcile, Crossplane calls the steps in order over gRPC, a binary remote-call protocol. Each call carries the XR's current state, the observed state of the resources it owns, the desired state accumulated by earlier steps, per-function input, and shared context. The function returns what should exist, and the output of one step feeds the next.

A minimal pipeline looks like this.

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: database-aws
spec:
  compositeTypeRef:
    apiVersion: platform.example.org/v1alpha1
    kind: Database
  mode: Pipeline
  pipeline:
    - step: render-resources
      functionRef:
        name: function-go-templating
      input:
        apiVersion: gotemplating.fn.crossplane.io/v1beta1
        kind: GoTemplate
        source: Inline
        inline:
          template: |
            # templates that emit an RDS instance, subnet group, and so on
    - step: mark-ready
      functionRef:
        name: function-auto-ready
```

The first step renders the composed resources from the developer's `size` and `engineVersion`, and the second, `function-auto-ready`, reports readiness once the composed resources are ready. The input details are elided because they depend on the function chosen, and function names and API versions should be checked against the version you run. What matters is the contract: a function's main job is to update the desired state and hand it back, and Crossplane, not the function, talks to the API server and applies the result. Functions do not run on deletion, so Crossplane itself deletes composed resources.

Why a pipeline of external programs and not a richer template language? The design document says the maintainers wanted to "avoid organically growing a new configuration Domain Specific Language." The earlier model, native patch-and-transform, was a static list of base resources plus patches. It was deliberately not Turing complete, meaning it could not express arbitrary loops or programs, and it could not branch, loop, or patch between composed resources. Imagine Learning's experience shows the cost: its patch-and-transform files for AWS RDS clusters ran past 1,000 lines, about 1,250 for a two-instance cluster, with near-duplicate files for different instance counts. After moving to a function with a loop over `instanceCount`, the duplication disappeared. VSHN, a Swiss provider that sells self-service databases, queues, and object storage through its AppCat marketplace, reached the same conclusion after hitting the lack of conditionals and dynamic lookups. Patch-and-transform survives as `function-patch-and-transform`, and the legacy `mode: Resources` was deprecated in v1.17 and removed in v2.

Functions bring their own failure modes. The sharpest is that a function returns the complete desired state, not an incremental patch, so a resource it omits is deleted. VSHN learned this during the alpha: "if an object is not explicitly specified in a request payload, it will be deleted." The discipline is to start from the incoming desired state, change only your own parts, and pass everything else through. Functions are also extra moving parts that must be healthy for a composite to reconcile, and mistakes appear at reconcile time and not at definition time. Load scales with composite count: composites are polled every 60 seconds by default and each function step is a gRPC call, so 100 XRs with one step make 100 calls per minute. A third-party article argues that large composites can exhaust function memory, though its log excerpts are labelled as simulated, so treat that as plausible guidance and not an incident. Go templating adds a further burden: in a tutorial that built the same API two ways, the template-based Composition needed hand-written logic for creation order and for avoiding deletion of a resource when a dependency was briefly unavailable.

The recommended mitigation for most of this is testing before rollout: `crossplane render` runs a Composition locally, functions can be unit tested, and the Crossplane blog describes a loop using kind, Kuttl, and Skaffold in which each Kuttl run takes two to five minutes.

## 6. kro: ResourceGraphDefinitions, CEL and readiness checks

kro, short for kube-resource-orchestrator, was announced by Google on 2025-01-30 as a joint effort with AWS and Microsoft. It takes a different position on the same problem: put the schema and the implementation in one object and keep logic in a restricted expression language. Its announcement describes "a Kubernetes-native framework that lets you create reusable APIs to deploy multiple resources as a single unit." The wiki's reading of the project site shows version 0.10.0 and a `v1alpha1` API, and Google said at launch that kro was not production-ready, so kro is pre-1.0.

A ResourceGraphDefinition, or RGD, has a `schema` block that declares the new kind in a lightweight "SimpleSchema" and a `resources` list of templates. kro converts the schema to OpenAPI v3 (the standard schema format the Kubernetes API server uses to validate custom resources), generates a CRD named `<plural>.<group>` (the group defaults to `kro.run`), registers a dynamic controller for it, and reconciles instances. The following sketch follows the pattern in the AWS documentation's WebApplication examples, simplified and illustrative.

```yaml
apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata:
  name: web-app
spec:
  schema:
    apiVersion: v1alpha1
    kind: WebApp
    spec:
      name: string
      image: string
      replicas: integer | default=2
  resources:
    - id: bucket
      template:
        apiVersion: s3.services.k8s.aws/v1alpha1
        kind: Bucket
        metadata:
          name: ${schema.spec.name}-assets
        spec:
          name: ${schema.spec.name}-assets
    - id: deployment
      template:
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: ${schema.spec.name}
        spec:
          replicas: ${schema.spec.replicas}
          selector:
            matchLabels: { app: "${schema.spec.name}" }
          template:
            metadata:
              labels: { app: "${schema.spec.name}" }
            spec:
              containers:
                - name: app
                  image: ${schema.spec.image}
                  env:
                    - name: BUCKET_ARN
                      value: ${bucket.status.ackResourceMetadata.arn}
```

The expressions in `${...}` are CEL, the Common Expression Language. CEL is typed, has no side effects, and always terminates, which is why the wiki describes it as deliberately not Turing complete, in other words unable to express arbitrary loops or programs. The snippet shows the key mechanism: the Deployment's environment variable refers to `bucket.status.ackResourceMetadata.arn`, and from that reference kro infers that the bucket must exist first. It builds a dependency graph, creates independent resources in parallel, waits on status values that do not exist yet, and deletes in reverse order. The AWS guide stresses that "kro validates ResourceGraphDefinitions at creation time, not at runtime," so a mistyped field, a missing kind, a type error, or a cycle is rejected when the platform engineer applies the RGD, before any application team creates an instance. The same idea applies to Google's own example, in which a few parameters (a name, node pool, maximum node count, and location) produce a GKE cluster through Config Connector objects.

Ordering and readiness are two separate mechanisms, and the way kro reports readiness has stable and unstable parts. Dependency order comes from references. Readiness comes from `readyWhen`, a list of CEL expressions per resource that defines when it counts as ready. In an RGD, dependents wait until their dependencies are ready; if `readyWhen` is omitted, kro treats a resource as ready as soon as it exists, which is a weak default for slow cloud resources. In the newer alpha `Graph` API, which is disabled by default, `readyWhen` only reports health and a dependent applies as soon as the fields it references exist, so a team moving from an RGD to a Graph could lose a safeguard it relied on. The released v0.10.0 documentation confirms both halves: for an RGD, everything that depends on a resource waits until it is ready, while a Graph node explicitly "does not wait for the upstream node's `readyWhen` conditions". The documented workaround in a Graph is to reference a status field that exists only once the upstream resource is healthy. The Graph API was introduced in v0.10.0, released 2026-11-10, and is alpha, off by default behind the `GraphKind` gate, with no compatibility guarantee and no published promotion timeline. Authors can also define their own instance conditions with `runtime.newCondition()`; when they do, kro hides its built-in conditions, so the author must compose a summary `Ready` condition or generic tools have nothing to read. A caution applies to the conditions kro supplies for itself. At v0.10.0 an instance carries four built-in conditions: `InstanceManaged`, `GraphResolved`, `ResourcesReady`, and the root `Ready`, which is true when the other three are. The kro documentation tells readers to depend only on `Ready` and says the project reserves the right to add, remove, or modify the sub-conditions without breaking compatibility, so a health rule in Argo CD, Flux, or an alert that reads `ResourcesReady` directly may break on a kro upgrade with no breaking-change notice. The sub-conditions remain useful for a person diagnosing a stuck instance. The ResourceGraphDefinition itself reports five conditions: `Ready`, `GraphRevisionsResolved`, `GraphAccepted`, `KindReady`, and `ControllerReady`, and its `status.state` is `Active` only when the last three are true. The kro documentation pages disagreed about whether an instance `status.state` of `FAILED` exists, with the Instances page listing ACTIVE, IN_PROGRESS, DELETING and ERROR and the Schema page adding FAILED. Reading the Go source settled it: at v0.10.0 the state file defines only IN_PROGRESS, ACTIVE, DELETING and ERROR, and the `FAILED` constant that v0.9.4 still carried is marked deprecated as a legacy value and, in the three files searched, never set. A dashboard that switches on `state` needs no `FAILED` branch at v0.10.0, but should still treat ERROR and anything other than ACTIVE as unhealthy, because kro reserves the field and a platform author cannot redefine it ([[findings/the-kro-docs-disagree-on-whether-an-instance-state-of-failed-exists]]). Compare this with the Crossplane side described in Section 4, where the XR's `Ready` is a summary authored by the pipeline's functions through the `READY_TRUE` signal, while kro's controller computes the instance `Ready` itself from the graph. That contrast matters when you debug: a stuck Crossplane XR points you at the pipeline's readiness logic, and a stuck kro instance points you at the `readyWhen` expressions and the sub-conditions. kro readiness also has a flip-flop pitfall. The kro conditional-creation documentation warns that an `includeWhen` expression based on a volatile upstream status field makes the graph "flip-flop": the resource, and everything that depends on it, is created when the expression is true and deleted when it turns false, which for cloud resources means repeated creation and deletion of real infrastructure. A v0.10.0 fix rejects an expression that can never resolve, but it does not detect one that resolves differently from one reconcile to the next, so base the expression on fields that change in one direction ([[findings/a-kro-includewhen-on-a-volatile-upstream-status-field-makes-resources-flip-flop]]). Crossplane's conditions are fixed by the provider, while kro's are authored, a contrast drawn in .

Deletion is where kro made a deliberate departure. Default Kubernetes owner references, handled by the garbage collector described in Part 2, delete dependents without honoring order among siblings, and a cluster-scoped object cannot be owned by a namespaced one. kro therefore tracks children with an ApplySet, a labeled inventory of everything applied together, keeps its instance finalizer until all children are gone, and deletes in reverse dependency waves, each fully gone before the next begins. The v0.10.0 Instances page says kro "does not set Kubernetes owner references on managed resources by default", and it gives the two reasons above. Ownership is instead written as labels. Each child carries `kro.run/owned`, `kro.run/kro-version`, instance identity labels (`kro.run/instance-id`, `-name`, `-group`, `-version`, `-kind`), `kro.run/node-id`, `app.kubernetes.io/managed-by: kro`, and `applyset.kubernetes.io/part-of`; a namespaced instance adds an instance-namespace label, and items produced by a `forEach` collection add an index and a size. Long names are hashed into label values with an `h-` prefix and the full value kept in an annotation. Each child's dependency wave is stored in an `internal.kro.run/apply-order` annotation, and kro finds children to delete from the instance's persisted ApplySet inventory and not by re-evaluating the graph, so cleanup can proceed when an external reference is already gone. Children without a valid annotation, such as those created before an upgrade, go in a final unordered wave. kro does use owner references in two places: it stamps a `ResourceGraphDefinition` owner reference on the CRD it generates and on GraphRevision objects, and it re-adopts orphaned revisions by stamping the reference again, while the alpha Graph API sets none and cleans up from `status.managedResources` and its own finalizer ([[findings/kro-sets-no-owner-references-on-instance-children-and-tracks-them-with-labels-and-an-applyset-inventory]], [[findings/a-kro-graph-has-no-revision-history-and-sets-no-owner-references-on-the-resources-it-creates]]). The cost appears where GitOps tools meet it: Argo CD decides what it owns from tracking metadata, so the kro FAQ tells Argo CD users to add an owner reference and a tracking-id annotation to each templated resource. The FAQ example sets `controller: false` and `blockOwnerDeletion: true`, and the documentation warns that hand-added references mean resources "may be garbage collected out of order", that cross-namespace or cluster-scoped children fail validation, and that timing can conflict with kro's own reconciliation ([[decisions/give-kro-children-manual-owner-references-or-leave-them-to-applyset-labels]]). Two deletion reports are worth knowing. Kro issue 1171, filed in March 2026 against v0.8.4 by a fault-injection tool and not from production, reports that a controller crash in the middle of an instance deletion can leave the finalizer and the children behind because the controller "doesn't checkpoint progress", and the reporter also claims the CRD was deleted despite `allowCRDDeletion=false`; it was open with no maintainer confirmation when read ([[findings/a-kro-controller-crash-during-instance-deletion-can-leave-the-finalizer-and-children-according-to-a-fault-injection-report]]). And the kro collections documentation itself says that a `forEach` collection above the default limit of 1,000 resources (the `config.rgd.maxCollectionSize` setting) gets stuck during deletion, so a list in the instance spec that grows past the limit can be created and updated yet never finish teardown ([[findings/a-kro-foreach-collection-above-the-1000-item-default-limit-gets-stuck-during-deletion]]). The first is a tool-generated report and the second is documented behavior, and neither is a named organization's postmortem.

Rollout and maturity matter too. Each change to an RGD becomes an immutable GraphRevision, and the documentation states that if the latest revision fails compilation, instances stop progressing with no fallback to an older revision. Breaking schema changes, such as removing a field or adding a required one without a default, are blocked unless the `kro.run/allow-breaking-changes` annotation is set. This check arrived in kro v0.8.0, and two open user reports show its rough edges. In issue 1395, filed 2026-09-04, a user on a live cluster found that the block error did not name the override annotation, wrote that operators "reasonably conclude the only way forward is to delete and recreate the RGD", and could not do so safely because the definition drove per-availability-zone network configuration for running instances. In issue 1391, filed 2026-09-03, the reporter says that adding an `enum` or CEL validation marker to an existing field is accepted and the definition reports Ready, yet kro never patches the live CRD's schema, so the CRD keeps accepting values the definition now forbids. Both are single-reporter claims that were open when the wiki read them, and neither is a production outage, but the practical lesson is that a Ready RGD does not prove the generated CRD matches it. A related shared-failure report, issue 886 from 2025-12-05, says one misconfigured RGD blocked updates to every other RGD until it was deleted and the controller pod restarted. It too is one reporter's unreproduced account, it predates v0.10.0 by about eleven months, and the wiki does not know whether the release changed the behavior. A fourth report concerns load.

Kro issue 1464, opened 2026-09-30 and since closed, says that a hard apply failure on a Graph discarded the watches and then hot-looped without backoff, and that on a large collection "each rebuild re-issues a full WatchList, which drives apiserver memory up"; it was made against kro main and v0.10.0-rc0 on Kubernetes 1.35, it is a reporter observation and not a measurement, and the wiki did not read the fix, so the current behavior is unknown ([[findings/a-kro-hard-apply-failure-discarded-watches-and-hot-looped-while-large-collections-re-listed-against-the-apiserver]]).

Still, no named organization has published a postmortem for kro, so these reports are the best evidence available.

Several mechanics explain how kro behaves under those conditions. kro ships no admission webhook of its own and relies on the generated CRD's schema and CEL validation rules, which removes the fail-closed outage class that webhook-heavy tools such as Config Connector and Cluster API carry, at the price of being limited to what a CRD schema can express ([[comparisons/admission-webhooks-and-failure-policies-across-crossplane-kro-argo-cd-config-connector-ack-cluster-api-gatekeeper-and-kyverno]]). Those CEL rules have a cost budget: the API server estimates the worst-case cost of each rule at CRD admission, and a rule over a list or string with no `maxItems` or `maxLength` is rejected on budget grounds, so schemas that generate CRDs from user input need those limits set; the static limits are 10 million per expression and 100 million per CRD ([[findings/an-unbounded-list-or-string-makes-the-cel-cost-estimate-reject-a-crd-rule-until-maxitems-and-maxlength-are-set]], [[findings/cel-cost-limits-are-10-million-per-expression-and-100-million-per-crd-statically-and-1-million-per-call-and-10-million-per-request-at-runtime]]). On writes, kro applies template resources with server-side apply, a mode in which the API server records which writer (called the field manager) owns each field and rejects or, when the writer asks, overrides conflicting writes from others (Section 11 returns to this). kro forces ownership under the manager `kro.run/applyset`, writes instance status under `kro-instance-status`, and applies patch contributions to objects it does not own without force so that a patch claims only the fields it sets; an opt-in conflict detection for the standalone Graph controller refuses to take a field from another Graph's manager, though the source says external drift from kubectl or other controllers is still reclaimed by a forced re-apply ([[findings/kro-applies-template-resources-with-server-side-apply-and-force-and-applies-patch-contributions-without-force]]). On reads, kro keeps one shared metadata-only informer (a controller's in-memory cache of objects, kept current by a watch on the API server) per watched resource type, with a resync period of 36,000 seconds, so its cache memory scales with the number of watched types and objects and not with the size of each object ([[comparisons/informer-and-cache-choices-across-kro-config-connector-ack-and-cluster-api]]).

On the operational side, kro handles all instances from one shared queue with one worker by default and a ten-hour full resync, per the v0.10.0 controller tuning documentation. That documentation, released 2026-11-10, describes the single worker, the backoff range, the token bucket, the client limits, the ten-hour resync and the twenty-retry cap. A drift-reconciliation issue was also reported closed as a duplicate, and the wiki did not confirm whether the original issue it duplicated was checked, so check your version before relying on self-healing.

The wiki also notes that the Crossplane project's `function-kro`, announced 2026-03-19, embeds kro's graph builder in a Crossplane pipeline step, which the announcement says brings revision pinning, extra pipeline steps, and `crossplane render` to kro-style graphs; its feature-parity claim is the project's own and unverified.

## 7. Other models: Helm and Kustomize render-time, hand-written operators, Score, Radius, Kratix

Crossplane and kro are not the only way to hide complexity, and a fair tutorial has to place them among their alternatives. The wiki's dossier sorts all approaches into two families. In the render-time family, a tool produces manifests once and something else, typically a GitOps tool such as Flux or Argo CD, must keep them correct afterward. In the controller-driven family, the abstraction is itself a Kubernetes API, and a live control loop reconciles children, writes status to the parent, and handles deletion order.

Helm is the best-known render-time tool. A chart is a collection of files describing a related set of Kubernetes resources, rendered with Go templates and values and installed as one tracked release. The abstraction surface is the values file, which is free-form and is not a real API schema unless the chart author adds a values schema. Nothing reconciles after install, and Helm has no native support for upgrading or deleting CRDs, so Flux's HelmRelease adds CRD policies to compensate. Kustomize takes the opposite approach: a base of ordinary manifests plus overlays and patches, with no templates and no parameter surface at all. Its project encourages fork, modify, and rebase. Consumers of an overlay still read and reason about the underlying manifests. The wiki states the consequence directly: an abstraction is useful when its user can ignore what is below it, and Helm values and Kustomize patches expose the manifests underneath, so users still need to understand Kubernetes. That finding is the dossier author's analytical observation supported by documentation, with no incident behind it. kpt and KRM functions run containerized programs over packages of objects and sit in the same render-time family; moving Kustomize's built-in Helm inflation to KRM functions drew user objections because they need a container runtime that laptops, CI, and Argo CD often lack.

A hand-written operator, the pattern in , sits at the other extreme of flexibility. You write a CRD and a controller in Go or another language, typically scaffolded with Kubebuilder or the Operator SDK, and the controller can do anything. That is the right tool when the runbook needs arbitrary logic such as database failover, backup, or schema migration; the wiki's example is the family of stateful data-service operators for Postgres and Elastic. The cost is that you own all the code, including its testing, upgrades, informer caches, finalizers, and RBAC. The wiki's guidance is that when a custom API is mostly a composition of existing resources, a Crossplane Composition or a kro RGD can stand in for a bespoke controller. That guidance is documentation-based, with no measurement of maintenance saved. Choosing the framework or language for a hand-written operator is a separate question, and here the evidence is thin in an instructive way. The wiki searched the project READMEs and the Kubebuilder book for selection criteria and found only self-descriptions, so no source states a rule for choosing among Kubebuilder, the Operator SDK, Java Operator SDK, Kopf, shell-operator, Metacontroller, or composition, and a claim that a CNCF white paper favors Go was not verified. The Operator SDK's capability-level model, which runs from Level 1 Basic Install to Level 5 Auto Pilot, is framed around an operator managing a workload, and it says that an operator which does not manage a workload or that delegates to off-cluster orchestration services remains at Level 1, which matters here because a Crossplane or kro composition is exactly that kind of delegation. The page says nothing about composition tools, so it neither endorses nor ranks them ([[decisions/choose-an-operator-framework-or-language-from-kubebuilder-operator-sdk-josdk-kopf-shell-operator-metacontroller-or-composition]], [[findings/operator-sdk-capability-levels-keep-delegating-operators-at-level-1-and-say-nothing-about-composition-tools]]). If you do write the controller yourself, controller-runtime offers several ways to narrow its cache, namely label or field selectors, transforms that strip fields, metadata-only informers, and a `DisableFor` list that sends reads of chosen types straight to the API server, and each has a cost such as extra API calls or a stale-read tradeoff ([[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]).

Score and Radius move the abstraction higher, from a platform-defined kind to the developer's own view of a workload. With Score, a developer writes one `score.yaml` declaring containers, ports, and abstract resources such as `type: postgres`, and implementation CLIs (`score-compose`, `score-k8s`) generate Docker Compose files or Kubernetes manifests. It generates output and runs no controller, so it belongs with the render-time tools. The only adopter evidence in the dossier is testimonials on the project's own site. Radius is server-side. Developers describe an application with containers, databases, and connections, and platform engineers supply Recipes that decide what a "Redis cache" becomes in each environment. Everything the wiki knows about Radius comes from one third-party review, because the primary documentation could not be read, so its CNCF status, Azure lean, Bicep dependency, and early maturity are all unverified claims.

Kratix, from the vendor Syntasso, is an orchestration framework that sits behind a portal. Its central object is the Promise, which bundles a self-service API, embedded workflows, and fleet scheduling across Destinations. Syntasso's illustration schedules one request across a standard cluster, a PCI DSS cluster, and a Terraform destination so the requester does not choose the target. That is a vendor example and not an independent case study, and the wiki did not retrieve details of how Destinations work. The same vendor argues that a portal such as Backstage gives visibility but not provisioning, so ticket queues persist; read that as an attributed claim from a company with a stake.

These tools combine more often than they compete. A consultancy post argues that mature platforms layer three: Helm installs components, Crossplane provisions cloud resources, and kro composes developer-facing APIs. The wiki's dossier says this is described as typical and is not tied to named companies.

## 8. Industry use cases: self-service databases, cluster provisioning, service catalogs, multi-cloud

Self-service infrastructure is the dominant use case the wiki found for composite resources. The Crossplane adopters list, which is self-reported and unaudited, shows organizations that put composite resources between application teams and raw cloud resources. Renault lists XRDs and compositions as an abstraction layer. Wellhub, Wildlife Studios, Splash, and Millennium bcp offer self-service provisioning to engineers. Grafana Labs and Consensys run internal developer platforms. Deutsche Kreditbank reports more than ten EKS clusters, and Continental provides self-service ephemeral vclusters, lightweight virtual clusters that run inside a host cluster, to developers. The entries show what organizations are building and not how it performed.

The self-service database is the classic case. VSHN's AppCat is a marketplace in which customers provision databases, message queues, and object storage by creating one small object, while the platform team owns the expansion logic, backups, and maintenance, and generalizes them across service types. This is the "each composite kind is a product" pattern: the platform team publishes a catalog of kinds and other teams consume them. JFrog describes a chain of four tools for self-service cloud environments: developers ask through a Jenkins-based interface, which writes custom resources into Git; Argo CD syncs them into a cluster; and Crossplane reconciles them into cloud resources. Predefined small, medium, and large size classes prevent over-provisioning, and owner and expiry tags support cost cleanup of forgotten environments. Notice that the guardrails in that story are exactly the "few safe knobs, hide the rest" idea from Section 4.

Crossplane v2's Composition can include any Kubernetes resource, so one object can create infrastructure and application together. The Crossplane 2.0 announcement sketches a `Microservice` kind whose single namespaced object creates an RDS instance, security groups, a Deployment, a Service, an Ingress, and monitoring dashboards. The wiki notes that this is an illustration from the Crossplane authors and not a named customer. A related guide shows that an XRD can expose the `scale` subresource, so `kubectl scale`, the Horizontal Pod Autoscaler, and KEDA (an event-driven autoscaler) can scale the XR without knowing its schema, although the composition author must wire the scaling logic.

Cluster provisioning is a second major use case, and it shows that the layers overlap. Cluster API applies the same expansion idea to clusters: its ClusterClass is a reusable definition of what a cluster looks like, and a small `topology` on a Cluster object supplies the variable parts, which a controller expands into machine and infrastructure objects the framework already reconciles. The maturity label depends on the release you read. The v1.14.4 documentation still heads the page "Experimental Feature: ClusterClass (alpha)", but the v1.15.0-rc.0 release, published 2026-11-24, lists "ClusterTopology to beta and enabled per default", and its guide says the `ClusterTopology` feature flag is enabled by default and Beta since v1.15. That is a release-candidate claim, since v1.15.0 final had not shipped on the date of this revision, and Beta is not general availability, so recheck at the final release. A further check read both the rc.0 tag and the `main` branch: they agree, with the `ClusterTopology` gate defined as default true and pre-release Beta, code comments reading "alpha: v0.4" and "beta: v1.15", and a new alpha gate, `ClusterTopologyWorkerVersionPinning`, that requires `ClusterTopology`. The newest stable release on 2026-11-26 was v1.14.4, published 2026-11-03, and no source read calls ClusterClass generally available, so quote the release number with any v1.15 statement and name v1.14.4 when giving production guidance ([[findings/cluster-api-v1-15-0-final-was-not-released-on-2026-11-26-so-every-v1-15-statement-is-a-release-candidate-claim]], [[findings/cluster-api-clusterclass-maturity-labels-disagree-across-doc-versions-and-the-original-proposal-still-says-provisional]]). Because a ClusterClass topology is applied by a controller that shares objects with other writers, one more mechanic matters: the Cluster API topology controller writes with server-side apply under the manager `capi-topology` and forces ownership, and a list field co-authored by the topology controller and another writer can reconcile forever or fail to remove items ([[findings/cluster-api-co-authored-list-slices-can-reconcile-forever-and-server-side-apply-can-fail-to-remove-list-items]]). The original ClusterClass proposal from 2021 still carries `status: provisional` in its frontmatter even though its history records later additions, so it is a poor guide to maturity. Meanwhile the Crossplane adopters list says RTL Nederland provisions whole Kubernetes clusters on Azure and AWS with Crossplane, a self-reported entry showing that a general framework can create clusters as managed resources. Cozystack goes further and brings its own substrate, packaging Talos Linux (an operating system built only to run Kubernetes), Kubernetes, KubeVirt, and storage and network components into a PaaS for building a cloud on commodity hardware, with no adopter names in the dossier.

Scale and multi-cloud complete the picture. Adopters report counts from thousands of managed resources to, for Akamai's provider-ceph, up to 200,000, and SAP reports 100-plus KRM control planes as of February 2024. Built Technologies, for instance, writes that "at times it has exceeded over 10,000 AWS resources managed by Crossplane", though the entry is undated, describes a developer environment and not production, and is self-reported. Adobe lists ACK for global Kubernetes cluster provisioning and stateful service infrastructure, again self-reported. Only about eight of the 87 Crossplane entries give numbers, and the wiki found no adopters file for kro, Cluster API, or Config Connector, so no named production kro adopter is known. These are self-reported one-liners and not verified case studies. They explain why per-type CRDs and per-resource polling matter. Domain-scoped control planes, several small Crossplane instances each owning networking or data, are proposed by one practitioner blog as an alternative to a single monolithic instance, but the dossier says explicitly that this is advice and not evidence of deployments.

## 9. Pitfalls: oversized compositions, leaky abstractions, live-edit disruption, deletion ordering, credential blast radius

The wiki's pitfalls hub makes a general point worth remembering: serious platform failures are usually cascades in which a small change meets a controller loop, a default, or a shared dependency, and the loop amplifies it. Three mechanisms recur, namely finalizers, field ownership, and deletion propagation, and platform abstractions inherit all three. Below are the pitfalls most specific to this part.

Oversized compositions and poorly modeled APIs come first. A Polarpoint practitioner blog lists two mistakes: the "mega-Composition" that tries to compose a whole environment in one blueprint, and an API that mirrors a particular cloud's own resource names. Its advice is to start with small Compositions, model APIs by infrastructure domain, and design for the mental model of the people who will use them. A larger Composition also means more functions that must stay healthy and a bigger blast radius for any edit. The source is opinion, citing no incident or measurement, so verify it in practice. Leaky abstractions are the same problem seen from the other end, and Section 7 covered how Helm values and Kustomize patches expose what they were meant to hide.

Editing a live Composition is the most dangerous routine operation. The Crossplane v2 upgrade guide warns that doing so could disrupt or replace resources used by existing XRs. Crossplane tracks each change as a CompositionRevision, and an XR defaults to the Automatic update policy, which adopts the latest revision, so an edit to a shared Composition propagates to every follower and each composite then reconciles toward the new desired state. Mitigations are `compositionUpdatePolicy: Manual` with a pinned revision ref or label selector, referencing functions by OCI digest, and testing with `crossplane render`. kro's model differs. The latest GraphRevision applies to all instances and a failed compile stops them all, so rollout is a single decision and not a per-instance choice. Schema changes are a related contract problem. Crossplane relies on versioning and conversion webhooks, kro blocks breaking changes by default, and a down conversion webhook can stall garbage collection.

Deletion ordering is where abstractions meet finalizers and the garbage collector. Background deletion, the default, removes the owner immediately and cleans dependents later with no ordering, so a database and its network may be deleted together. In Crossplane v2 the composed resources of a namespaced XR carry a controller owner reference with `blockOwnerDeletion: true`, and Kubernetes only makes a foreground deletion wait for dependents that set that field to true ([[findings/foreground-deletion-waits-only-for-dependents-with-blockownerdeletion-true]]). Release v2.4.0 also restricted the composite garbage collector so that it deletes only resources whose controller reference points back to the XR, and v2.5.0 stops a function from making a namespaced XR compose a cluster-scoped resource by setting `metadata.namespace`. The composition `deletionPolicy` that selects Background, Foreground or Pipeline is alpha and sits behind the `--enable-function-controlled-deletion` flag, new in v2.5.0, and composition functions do not run on composite deletion, which is why the Pipeline policy works by removing resources from desired state ([[findings/a-managed-resource-without-delete-in-its-management-policies-is-removed-from-kubernetes-but-its-cloud-resource-stays]]). Crossplane offers three composite deletion policies: `Background`; `Foreground`, which keeps the parent until children are gone; and `Pipeline`, in which a function removes resources from desired state step by step. It also offers Usage objects, which block deletion of a used resource until its users are gone and can protect a resource from accidental removal. Stateful data adds stakes, since deleting a database through a provider can lose data. Removing a Crossplane provider before its managed resources abandons the real resources, because the controller that would run their finalizers is gone; Crossplane has an alpha protection feature that blocks provider removal while managed resources exist. And a paused resource cannot be deleted until it is unpaused. Through a GitOps tool, deletion can bypass the policy you chose; for example, Argo CD foreground deletion makes Crossplane ignore the composite deletion policy. Immutable fields have their own behavior: Crossplane does not delete and recreate, unlike Terraform, so an edit may quietly not apply.

Credential blast radius is the security pitfall. Reconciliation runs as the controller's cloud identity, not as the human who applied the manifest, so permission to create the Kubernetes object is effectively permission to change cloud resources with the controller's rights. Kubernetes RBAC on the platform API therefore becomes the cloud authorization boundary. The tools offer different mitigations, covered in Section 11. A subtler variant is ACK's cross-namespace references: disabling them is not tenant isolation. Adoption brings its own risks, since an adopt-or-create policy can take over a look-alike resource.

Finally, two operational costs apply to the whole approach. Crossplane needs a hosting cluster and Kubernetes skills, and the platform team must own the abstractions, observability, and cross-layer troubleshooting, a conclusion that appears in a competitor's article, in the project's own Terraform comparison, and in a 2022 evaluation. And stacking a GitOps agent over a controller-driven abstraction creates two reconcile loops that can hide status and drift at two layers, with generic agents unable to judge custom-resource health unless given checks.

## 10. Tradeoffs across abstraction models: a decision framework

The tools in this part differ along four axes, and naming them makes the choice less mysterious. The first axis is where the abstraction surface sits. Helm values and Kustomize patches sit close to manifests and leak them. Score and Radius sit high, at the workload, and pay with a translation or control-plane layer. Crossplane and kro sit in the middle, with a typed API the platform team designs. The second axis is whether anything keeps running. Render-time tools produce output once, and continuous correction is a GitOps tool's job. Controller-driven tools reconcile forever, which gives drift correction and ordered deletion and also makes the control plane a production dependency. The third axis is where logic runs and how it can fail. Crossplane runs functions in-cluster as gRPC services, so any language works but errors may surface at reconcile time. kro runs CEL in-process, which terminates and is type-checked at apply time but cannot express logic beyond CEL. The fourth axis is maturity and governance. Crossplane is a CNCF graduated project with versioned XRDs; kro is `v1alpha1`; Radius is described as early-stage by a single blog.

| Model | Surface the user sees | Logic | Keeps reconciling | Best fit |
|---|---|---|---|---|
| Helm | Free-form values | Go templates | No, needs GitOps | Packaging components |
| Kustomize | Plain YAML plus overlays | Template-free patching | No, needs GitOps | Per-environment variants |
| Hand-written operator | Any CRD you design | Any code | Yes | Domain logic such as failover and backup |
| Crossplane | Platform-defined kind from an XRD | Function pipeline | Yes, including cloud APIs | Owning cloud resources behind a platform API |
| kro | Platform-defined kind from an RGD | CEL with inferred order | Yes, Kubernetes objects | Composing resources already on the cluster |
| Score | One workload spec | CLI translation | No, output only | Developer-facing workload description |
| Radius | Application with connections | Recipes per environment | Yes, own control plane | Developer-facing apps, maturity unverified |
| Kratix | Promise API | Pipelines and Destinations | Yes | Orchestration behind a portal |

The table is the wiki's synthesis of several single-source claims, and the Radius and Score rows rest on one third-party review and the project's own site respectively. Within it, the Crossplane versus kro comparison is the one most teams must make. Crossplane separates schema (XRD) from implementation (Composition) and runs logic as external functions. kro puts both in one definition and evaluates CEL inside its own controller. Crossplane reports its readiness through pipeline steps such as `function-auto-ready`, kro through `readyWhen`. Crossplane's rollout is per-instance through revisions, and kro's is global with no fallback. The execution-model difference is flexibility against checkability. One tutorial built the same `StorageApp` API both ways, an application plus an S3 bucket plus an IAM role, and found equivalent outcomes, with kro's reference model handling creation order and dependency-missing cases more naturally. That is a single tutorial and not production evidence.

A practical decision rule, from the consultancy post and echoed in the wiki's decision page, is to use kro when the building blocks are already Kubernetes resources, including ACK, ASO, or Config Connector objects, and Crossplane when the platform must drive cloud APIs directly. The third option is both, as separate layers or through `function-kro`. The wiki labels this an open question framed by the sources and not an outcome-tested rule, since no source gives scale numbers or incident data, so test capacity yourself. Before any of this, ask whether you need a controller at all: if the API is not declarative, or the automation does not need a custom resource, a script or a Helm chart may be enough, a point the Kubernetes documentation itself makes. Finally, ordering between whole manifest sets is a different problem again. Flux `dependsOn` and Argo CD sync waves order objects that a pipeline delivers without defining a new API, so they sit beside composition and not inside it.

## 11. How cloud-vendor add-ons, Cluster API and Terraform controllers approach the same problem

The cloud vendors ship their own provisioning controllers, and they make a revealing contrast. Config Connector for Google Cloud, ACK for AWS, and Azure Service Operator for Azure each expose roughly one CRD per cloud resource. They give a direct, close-to-one-to-one view of the cloud and leave abstraction to other tools; the EKS documentation points to kro for composing ACK objects, and Google's kro announcement composes Config Connector objects. The comparison comes from a Crossplane maintainer's blog, so it is positioning and not neutral analysis. Crossplane is the multi-cloud option that adds Compositions and XRDs.

Each add-on handles the shared problems in its own way. For credentials, Crossplane uses a `ProviderConfig` per account, ACK uses `IAMRoleSelector` objects to map namespaces to AWS roles for cross-account management, and Config Connector's namespaced mode binds each namespace to its own Google service account and project, which also spreads API quota. The wiki's decision page frames the underlying choice. For adoption, ACK offers `adopt-or-create` and strict `adopt` through annotations, Config Connector acquires an existing resource by name and requires `resourceID` when the service generates IDs, and Crossplane uses `Observe` plus the external-name annotation. SAP's BTP provider, where identifiers are assigned by the platform, recovers a lost ID by business key and creation window to avoid blindly adopting look-alikes. For deletion, ACK deletes the AWS resource unless the `services.k8s.aws/deletion-policy: retain` annotation is set on the object or its namespace, or the controller is started with a retain flag, and Config Connector offers an `abandon` deletion policy set by annotation. The wiki's sources spell these options inconsistently, and one dossier uses a looser `deletionPolicy` wording that matches Crossplane's older field name more than ACK's real mechanism, so check the current ACK and Config Connector documentation before relying on an exact spelling. Ordering is a known gap in the per-resource model: Config Connector has no Terraform-style dependency graph, and Argo CD deletes children without ordering. That is exactly the hole a composition layer fills. A typical Google Cloud shop delivers Config Connector resources from Git with Argo CD or Flux while the controller's own identity makes the cloud calls, and single-cloud teams choose between ACK per service and ASO v2.

The add-ons also differ in how they write to the objects they manage, which decides what happens when a GitOps tool or a human edits the same fields. Server-side apply records which writer owns each field, and a tool that applies with it must decide what to do when another writer owns a field it wants to set. Cluster API's topology controller applies under the manager `capi-topology` and forces ownership. kro forces ownership for the templates it owns and does not force for patch contributions. The ACK runtime sends merge patches and sets no field manager at all, although that conclusion rests on absence of the calls in the runtime repository, and the individual service controllers were not read. Config Connector writes with `Update` under the field owner `cnrm-controller-manager` and reads fields set by other managers as user intent, which is why a field set by a GitOps tool is not reverted the way a console edit would be. Crossplane uses server-side apply to propagate a claim to a composite and to composed resources, under a manager prefixed `apiextensions.crossplane.io/composed/`, and an external server-side writer losing a field on a composite is reported in issue 7453, which was open and not reproduced by a maintainer when the wiki read it, with two pull requests claiming that a conversion drops `managedFields` also open ([[comparisons/ssa-conflict-policy-across-tools]], [[findings/the-ack-runtime-sends-merge-patches-and-sets-no-server-side-apply-field-manager]], [[findings/config-connector-writes-with-update-under-cnrm-controller-manager-and-reads-other-managers-fields-as-user-intent]], [[examples/crossplane-issue-7453-reports-an-external-ssa-writer-losing-a-field-on-a-composite-resource]]). The Kubernetes maintainers' guidance is that controllers should force the fields they own and delivery tools should surface conflicts, yet Argo CD and Flux both force by default and then add exemptions, and the wiki records the best default as an open decision with no adopter evidence ([[decisions/force-conflicts-or-surface-them-to-humans]]). Config Connector adds one more guard worth knowing: its management conflict prevention defaults to `none`, so two Config Connector objects can manage one cloud resource unless a lease policy is set ([[findings/config-connector-conflict-prevention-defaults-to-none-so-two-objects-can-manage-one-cloud-resource-unless-a-lease-policy-is-set]]). The caches differ too. kro keeps one shared metadata-only informer per resource type, Config Connector caches only its own configuration kinds and CRDs by default, ACK controllers narrow by watched namespaces and label selector and trigger on generation changes unless drift ignoring is enabled, and Cluster API caches only cluster-labelled Secrets and gives each workload cluster its own cache; none of the four has a published memory figure ([[comparisons/informer-and-cache-choices-across-kro-config-connector-ack-and-cluster-api]]). Admission is the other axis of difference: Config Connector and Cluster API ship many webhooks, every one with failure policy Fail, Crossplane core ships a single fail-closed webhook that protects resources labelled in use and has replaced its XRD and Composition webhooks with CEL, and kro and the ACK service controller read ship none, so an outage of the first two can block writes that the others would accept ([[findings/config-connector-and-cluster-api-register-many-webhooks-and-every-one-uses-failure-policy-fail]], [[findings/crossplane-core-ships-one-fail-closed-usage-webhook-and-replaced-its-xrd-and-composition-webhooks-with-cel]]).

Cluster API applies the same idea to Kubernetes clusters. A management cluster reconciles Cluster and Machine objects into workload clusters through infrastructure, bootstrap, and control-plane providers, and its core controllers stay generic by relying on an agreed contract. Its teardown uses owner references and stops on disruption budgets, attached volumes, and failing hooks. Centralizing authority in a management cluster also makes it a single point of failure.

Terraform in a cluster is the pragmatic route for teams with large existing estates. tofu-controller, from the Flux family, and Terraform Operator wrap existing Terraform code in a CRD and run plan and apply in pods, so neither removes the need to write Terraform. The wiki records that tofu-controller keeps state in Kubernetes Secrets, can require approval through a plan ID set via Git, and couples to specific Terraform and Flux versions, with its maintenance status after Weaveworks' wind-down unchecked; the Terraform Operator side of the comparison is mostly blank because the dossier read only a short README. tofu-controller also supports a detection-only mode, which suits infrastructure where an automatic apply could be destructive. Compared with Crossplane, the core contrast is where the loop runs. The Crossplane blog says "Crossplane is a control plane, where Terraform is a command-line tool." Crossplane corrects drift automatically and gives each resource an independent API object with Kubernetes RBAC, but it has no built-in plan preview and requires Kubernetes expertise. Terraform shows drift at the next plan and offers a reviewable plan, but it needs state locking. Both main sources are partisan, and the wiki records the lack of a neutral comparison. Upjet bridges the two worlds by generating Crossplane providers from Terraform providers.

GitOps tools sit above all of these. Flux and Argo CD deliver desired state and keep it in place, and they judge health differently: Flux's kustomize-controller waits for health before marking a Kustomization ready, while Argo CD aggregates the health of children and needs Lua checks for CRDs, small scripts that tell it how to read health from a custom resource it does not understand natively. Crossplane's own Argo CD guide requires annotation-based resource tracking, Lua health checks, exclusion of `ProviderConfigUsage` objects, and a higher client rate limit because of the many CRDs. The generic health logic these tools share has a documented blind spot. kstatus, the status library in cli-utils, checks a resource in a fixed order: deletion first, then whether the top-level `status.observedGeneration` matches `metadata.generation`, then the `Reconciling` and `Stalled` conditions with the first match winning, then type-specific rules, and only then a `Ready` condition. For a kind it has no rule for and that carries no `Ready` condition, its README says to "assume they are always reconciled", so a custom resource whose controller never writes `observedGeneration` or `Ready` can read as current early. The order has a useful consequence: a stale top-level `observedGeneration` overrides `Ready=True`, which is the protection a platform author gets by publishing the field. The abnormal-true pattern that kstatus favors, where a condition is present only when something is wrong, makes a stopped controller look healthy, and the Kubernetes API conventions have gone from recommending abnormal-true, to recommending positive polarity in February 2020, to saying since June 2020 that neither can be recommended, so there is no single right answer for new condition types. The v1beta2 Cluster API Cluster type, read at v1.15.0-rc.0, exposes `Available` and no `Ready` condition, and whether a kstatus-style tool reads such a Cluster as reconciled is an inference the wiki left caveated ([[findings/kstatus-checks-deletion-then-generation-then-reconciling-and-stalled-then-ready-so-a-stale-top-level-observedgeneration-overrides-ready-true]], [[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]], [[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]], [[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]). Config Connector's shipped status matches that advice only in part: its design document proposed a single `Ready` condition with reasons `Updating`, `UpToDate` and `UpdateFailure`, and at v1.162.0 the code ships one `Ready` condition, the `Updating` and `UpToDate` reasons, `UpdateFailed` as the failure reason, and a top-level `observedGeneration` on every status update, while the first-field-path failure message and operation IDs in the reason are not in the code ([[findings/config-connector-shipped-updatefailed-with-a-single-ready-condition-and-the-first-field-path-message-and-operation-id-reason-are-not-in-code]]). Flux and Argo CD also prune what Git no longer contains, which turns a deleted manifest into a deleted cloud resource unless guarded. The wiki's landscape page adds a warning about sources: several comparisons of Argo CD, Flux, Port, and Kratix come from vendors with no independent benchmarks.

## 12. Design principles for good platform APIs

The preceding sections suggest a set of principles. Each is stated with its reasoning, and where the wiki's evidence is thin the text says so.

First, design the API for the consumer's mental model, not the provider's. A platform API is a product, and its group, kind, and schema become a public contract that cannot be changed lightly: XRD group and names are immutable, and kro blocks breaking schema changes unless forced. An API that mirrors a cloud's own resource names forces every user to learn the cloud, which defeats the purpose of Section 1. Expose a few safe knobs, such as size classes, and hide the rest, as JFrog's small, medium, and large classes do.

Second, keep abstractions small and composable. A mega-Composition concentrates risk and multiplies the functions that must be healthy. Smaller compositions are easier to test, review, and roll out. The wiki's evidence here is practitioner advice and not measurement, but it follows from the blast-radius argument in Section 9.

Third, make safety defaults explicit and visible. Deletion of a real resource should be a deliberate choice, expressed through `managementPolicies`, retain or abandon policies, Usages, and deletion policies, and not an accident of defaults. Where ordering matters, encode it, whether through kro's inferred reverse waves, Crossplane's Foreground or Pipeline policies, or Usages, because background deletion promises no order.

Fourth, report status truthfully. Conditions are the common language that lets GitOps tools wait, composites aggregate, and humans debug. Include `observedGeneration` so a stale status cannot look healthy, define readiness precisely instead of treating "exists" as "ready," and keep a summary `Ready` condition even when you author custom ones. The reasoning comes from how consumers read status: a generic tool checks the generation match before it believes `Ready=True`, treats a kind with no `Ready` condition as always reconciled, and cannot tell a stopped controller from a healthy one if your only signals are conditions that appear when something is wrong. Choose one polarity deliberately, because the Kubernetes conventions no longer recommend either, and do not let a long cloud operation sit under a `Synced` or `Ready` that stays true, as the sixty-minute MSK report shows ([[decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types]], [[decisions/publish-synced-false-at-reconcile-start]]).

Fifth, treat RBAC on the platform API as the security boundary, and scope the identity behind it. Because controllers act with their own cloud identity, anyone who can create the object inherits those rights. Map namespaces to separate roles or accounts where the tool allows it, and keep trusted repositories as the source of manifests.

Sixth, choose the least expressive tool that does the job. A restricted language like CEL can be checked at apply time and always terminates, while a function in a general-purpose language can do anything and fail late. Neither is better in the abstract: the trade is checkability against flexibility, and a hand-written operator is warranted only when the runbook needs logic composition cannot express.

Seventh, make change safe. Version the schema, pin revisions where the tool allows it, test with `crossplane render` or its equivalent before changing shared definitions, and treat edits to a shared Composition or RGD as high risk, since both tools can propagate a bad change to every consumer.

Eighth, plan for scale from the beginning. Count CRDs, function calls, and reconciles. Install only the provider families or resource types you use, and remember that the stock Crossplane Helm install activates every type until you turn the default activation off. Know which poll interval applies (one minute in Crossplane core and runtime, ten minutes in Upjet providers), and note that Crossplane's `--max-reconcile-rate` is, in source, an alias for the worker pool size and not a rate, even though the v2.5 documentation describes it as a rate, while the v2.5.0 circuit breaker default is a burst of 100 against 50 in the v2.1.0 notes ([[findings/the-crossplane-v2-5-docs-describe-max-reconcile-rate-as-a-rate-but-source-treats-it-as-a-worker-pool-size-alias]], [[findings/the-crossplane-xr-circuit-breaker-default-is-burst-100-in-v2-5-0-source-while-the-v2-1-0-notes-say-burst-50]]). Narrow controller caches where you write controllers, and remember that cloud API rate limits are invisible to Kubernetes, and note that the wiki has no sourced data on how those limits constrain these controllers.

Ninth, design the seam with GitOps deliberately. A controller-driven abstraction runs a second loop beneath the delivery tool's loop, so decide who owns which fields, how health is judged, and what deletion does at each layer before you go to production.

Finally, accept that this field is young. kro is pre-1.0, Crossplane v2 removed features without an automated migration path, and much online content is stale. Pin versions, read release notes, and prefer designs that can survive replacing a tool underneath a stable API. That last point is the strongest argument for the whole approach: a good platform API outlives the implementation behind it.
