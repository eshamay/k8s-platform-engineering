## 1. Who this series is for and how to read it

This series is written for people who already run Kubernetes. You know what a Pod is, you have written a Deployment, you have fought with a Service selector, and you have granted or denied access with RBAC. What you may not have studied is the machinery underneath those objects: the controllers that make a Deployment produce Pods, the API conventions that make every object look alike, and the abstractions that tools like Flux and Crossplane build on top. That machinery is the subject of the series, and this first part supplies the foundation for everything after it.

The thesis of this part is simple to state. Kubernetes generalizes beyond containers because a small set of principles compose into a control plane that can manage any resource. Those principles are declarative intent, level-triggered reconciliation, eventual consistency, continuous drift correction, and pull-based delivery. Each one is useful alone. The reason the design works is that they reinforce one another, and the reason good platforms built on Kubernetes tend to behave well is that they inherit all five at once. Platforms that quietly break one of the five tend to be the ones that surprise their operators.

Here is how to read this part. Section 2 frames Kubernetes as a general control plane, and sections 3 through 7 introduce the five principles one at a time, starting from first principles and ending with a practical use case. Section 8 steps back and asks which design rules fall out of the model, using Flux and Crossplane as worked implementations. Section 9 collects industry use cases. Section 10 covers the pitfalls that appear in practice, and section 11 compares how Argo CD, Terraform, Cluster API, and others differ on these principles. Section 12 says where the series goes next. A short list of further reading closes the document.

A word about evidence. This part rests on a research wiki whose sources are mostly tool documentation, design documents, practitioner blog posts, and a small number of public postmortems. Where the wiki has only a vendor claim, a single practitioner account, or a default value that may have changed between versions, the prose says so. A targeted fact-check pass on 2026-11-26 read controller source files and versioned manifests for several of the defaults that matter most here, so the polling intervals, the Requeue behavior, and the Cluster API field names in this part now name the version they were verified against ([[findings/evidence-and-fact-check-pass-gap-dispositions]]). A later pass on the same day read the documentation and source for the tools around that core, namely Argo CD and its ApplicationSets, Flux internals, Config Connector, ACK, kro, Kratix, Radius, Score, Backstage, tofu-controller, KRM functions, and Crossplane packaging, and where it changes a claim in this part the prose says so and links the finding ([[findings/other-tool-coverage-pass-gap-dispositions]]). Many of those readings were taken from documentation on a project's default branch and not from a pinned release, and the prose keeps that caveat. Even so, treat numeric defaults as accurate for the versions that were read, and verify them against the version you run.

A short vocabulary note will save time later. A **controller** is a program that watches objects in the Kubernetes API and works to make the world match what those objects say. A **custom resource** is an object type that you or a tool adds to the API, and a **CRD** (CustomResourceDefinition) is the registration that teaches the API server about it; see [[concepts/custom-resource-definition]]. The **spec** of an object holds the intent a user wrote, and the **status** holds what controllers observed; see [[concepts/spec-status-split]]. Each term will be explained again where it matters.

## 2. From container scheduler to universal control plane

Most of us first meet Kubernetes as a way to run containers. You hand it a Deployment, and Pods appear on nodes. That experience hides the fact that Kubernetes ships two separable things together. One is a container scheduler. The other is a general, extensible API machine: an API server that handles authentication, RBAC, admission, validation, and watch, backed by etcd for storage, plus a convention for controllers that reconcile an object's `spec` toward reality and report back in `status`. The research behind this wiki makes the separation explicit: the second part has no inherent tie to Pods, so anything that can be described declaratively and reconciled by a loop can be modeled as a custom resource, whether that is a cloud database, a whole cluster, a firewall rule, or an application bundle ([[concepts/universal-control-plane]]).

Consider what you get for free when you represent an external thing as a Kubernetes object. The object inherits authentication, RBAC, audit logging, watch semantics, and a large ecosystem of tooling. The API conventions fix `spec` and `status`, conditions, `resourceVersion`, and finalizers for every kind. A condition is a named true, false, or unknown flag in `status` that reports one aspect of an object's health. The `resourceVersion` is an opaque marker the API server stamps on each object so that a writer holding an out-of-date copy can be detected and rejected. A finalizer is a marker on an object that blocks its deletion until the responsible controller has finished its cleanup work, such as removing a cloud resource. Because these conventions are shared, generic tools such as GitOps engines, policy engines, and user interfaces work across all kinds without knowing anything about the particular one. That uniform contract is the real product. A team that wants a managed database to follow the same review, access control, and delivery workflow as its Deployments can get that by making the database an object.

The wiki describes the resulting ecosystem as four layers ([[concepts/universal-control-plane]], [[concepts/tooling-landscape]]). The bottom layer is the primitives: controllers as control loops, CRDs stored in etcd, and the operator pattern, which packages operational knowledge into a controller paired with a custom resource ([[concepts/operator-pattern]]). Above that sit provider controllers that project an external API into Kubernetes. AWS Controllers for Kubernetes (ACK), Google's Config Connector, Azure Service Operator, and Cluster API are the examples; they follow what the Kubernetes controller documentation calls direct control, where a controller acts on an external system instead of creating Pods ([[entities/ack]], [[entities/config-connector]], [[entities/cluster-api]]). Above those are composition layers such as Crossplane and kro, which let a platform team publish a small API that expands into many resources ([[entities/crossplane]], [[entities/kro]]). At the top are delivery layers, Flux and Argo CD, which reconcile Git into the API server ([[entities/flux]], [[entities/argo-cd]]).

The same sources note a consequence worth pausing on. A delivery tool and a provisioning tool are not rivals, because one moves manifests into the API and the other turns objects in the API into cloud calls. Asking whether Argo CD or Crossplane is better confuses the layers, and most production stacks pick one tool from each ([[concepts/tooling-landscape]], [[comparisons/delivery-versus-provisioning-versus-platform-layers-in-the-kubernetes-tooling-landscape]]). The wiki flags that the layers are a learning aid and not a hard taxonomy: Crossplane reaches into the platform layer through its composition API, and Kratix reaches into provisioning through pipelines.

At the far edge of the idea is a project like kcp, a CNCF Sandbox project that hosts many isolated, node-less API workspaces so a SaaS provider can serve a Kubernetes-style API to tenants without giving each one a cluster ([[entities/kcp]], [[examples/multi-tenant-api-hosting-with-kcp]]). Its tenant counts come from vendors and its larger scale numbers are stated goals, not measurements. Ænix, a company that argues for purpose-built distributions that are not container platforms, makes the most explicit version of the claim in an October 2026 opinion post: the API server and controller convention are the product, and the container scheduler is optional ([[examples/non-container-appliances-on-the-kubernetes-api]]). The wiki records that vision as having limited production evidence, and Ænix lists its own risks, including a small maintaining team and limited production testing.

So the claim of this part is not that Kubernetes is magically suited to everything. It is that a specific set of design decisions, taken together, produce a substrate that is unusually good at holding intent and driving the world toward it. The next five sections take those decisions one at a time.

## 3. Declarative versus imperative: intent as the contract

The first principle is declarative intent. To manage something declaratively means to describe the end state you want, usually as YAML in an object's `spec`, instead of writing the sequence of commands that would produce it. The Kubernetes documentation calls an object a record of intent: you store what you want, and the control plane works to make the observed `status` match the `spec`. Imperative management is the opposite. You tell the system what action to take now, as with `kubectl create`, `kubectl scale`, or a shell script ([[concepts/declarative-vs-imperative]]).

The distinction matters more than it first appears, because a declared end state gives a controller something to compare against reality. An imperative script has no standing definition of correct that it can return to. If a script runs once and the world later changes, nothing in the script notices. A declared spec is a persistent statement that the system can evaluate over and over, which is what makes reconciliation, drift correction, and GitOps possible at all.

The official kubectl documentation treats the choice as a spectrum, not a binary ([[comparisons/kubectl-object-management-techniques]], [[decisions/choosing-an-object-management-technique]]). Imperative commands have the lowest learning curve but leave no review or audit trail, so they suit development. Imperative object configuration, such as `kubectl replace -f`, keeps files but still issues explicit verbs, which suits a single writer in production. Declarative object configuration, `kubectl apply -f dir/`, suits multiple writers and gives reviewable files, but it is harder to debug because of the merge and patch logic underneath. The page also warns against mixing techniques on the same object, a hazard the wiki collects under [[findings/mixing-management-techniques-on-one-object]].

Here is a small declarative example, a Deployment you have seen many times, read with fresh eyes.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
```

Notice that the manifest says `replicas: 3`, not "start three pods." The Deployment controller is the machine that notices when the number of ready Pods differs from three and acts. If a node dies and takes a Pod with it, no one runs a command; the next comparison finds two Pods where three were declared and creates another. The API conventions add that fields should express desired outcomes and not actions, which is what keeps a spec declarative ([[concepts/declarative-vs-imperative]]).

The model repeats at every layer. Flux and Argo CD treat Git as the declared state and reconcile the cluster to it. Crossplane, Config Connector, ACK, and Cluster API extend the idea to cloud resources and whole clusters. kro and Crossplane compositions let platform teams define new declarative APIs that expand into many resources. Each layer is the same bet: write down what you want, and let a loop pursue it.

The honest caveat is that pure declarative management is not absolute in practice. Kubernetes keeps imperative commands for development and one-off tasks, and tools expose escape hatches such as Flux suspend, retain or orphan deletion policies, force, and abandon. The wiki's view is that those escape hatches exist because declarative reconciliation is dangerous when ownership, deletion, or drift semantics are misunderstood. The sources also note that ordering, one-shot operations, and data migrations remain weak spots for a purely declarative model, and that the sources read so far do not explain how tools work around them beyond hooks and sync waves.

## 4. Level-triggered versus edge-triggered: why state beats events

The second principle answers a question that sounds technical and turns out to be fundamental: what should a controller react to? There are two answers, borrowed from electronics. An edge-triggered system reacts to a transition, such as a signal going high or a Pod being deleted. A level-triggered system reacts to the current value, such as the signal being high or three replicas being desired while two exist ([[concepts/level-triggered-vs-edge-triggered]]).

The difference is easiest to see when something goes wrong. Imagine an autoscaler that receives events. The replica count changes from 1 to 5 and then from 5 to 2. An edge-triggered handler applies each event as a delta: add four, then remove three. If it misses or reorders events, it can act on the wrong deltas, and the 2018 level-triggering article the wiki relies on shows it terminating more replicas than exist and ending at zero, a state the source of truth never held ([[examples/an-edge-triggered-scaler-ends-at-zero-replicas-where-a-level-triggered-one-converges]]). A level-triggered controller compares the declared count of 2 with the observed count each time it runs, so it ends at 2 regardless of which intermediate events it saw ([[examples/deployment-replica-changes-converge-to-the-final-count]]). Joe Beda is quoted in the source explainer as saying that if you are edge triggered you run the risk of compromising your state and never being able to re-create it. An online book sums up the trade: edge-triggered systems require reliable event delivery, while level-triggered systems only require eventual state observation.

This is why the Kubernetes reconcile function receives only a namespace and a name. It is not told whether the object was created, updated, or deleted. The controller-runtime documentation says reconciliation is driven by actual cluster state, read from the API server or a local cache, and not by individual events ([[concepts/reconciliation-loop]]). A sketch of the structure of such a function makes the point.

```go
func (r *WebReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // Read everything needed from observed state; never branch on "what event woke me".
    var web examplev1.Web
    if err := r.Get(ctx, req.NamespacedName, &web); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    // Compare web.Spec with the child objects that exist, then create, update, or delete to close the gap.
    // Write what was observed back to web.Status.
    return ctrl.Result{}, nil
}
```

Read the comments rather than the Go. The function is handed a key, fetches the current object, compares desired with actual, and writes the result into status. Returning an empty result with a nil error means the object has converged. Returning an error asks the work queue to retry with exponential backoff, meaning progressively longer waits between attempts. The work queue is the deduplicating list of object keys waiting for reconciliation, so ten events for one object collapse into one pending key. A `RequeueAfter` value means the object is healthy but waiting, and it is the supported way to poll on a schedule. The fact-check pass settled an older disagreement about `Requeue: true`. Reading controller-runtime v0.25.3 (published 2026-11-16), the handler treats a nil error with `Requeue: true` as a rate-limited requeue: the controller's rate limiter chooses the delay, and the per-item failure counter is not reset, so a reconciler that returns `Requeue: true` on every pass waits exponentially longer each time. The one path that clears that history is `RequeueAfter`, which calls `Forget` on the item before scheduling the next visit, and it takes precedence over `Requeue` when both are set. An earlier version of this wiki had recorded that an issue thread described the requeue as immediate. The dossier read only the body of that issue (number 808), which says it is not clear which return values force a requeue with or without backoff, so where the immediate reading came from was not located, and the source code and the package documentation agree with each other. `Result.Requeue` is deprecated in current controller-runtime, so prefer returning an error for failures that should back off and `RequeueAfter` for planned polling, and never use `Requeue: true` as a poll timer, because the growing delay will keep you from ever getting a steady cadence ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]], [[concepts/reconciliation-loop]]).

It would be a mistake to conclude that Kubernetes ignores events. In practice it is a hybrid. A watch is a long-lived request that streams changes from the API server, and an informer is a client-side cache that a watch keeps up to date and that notifies the controller when something changes. Together they deliver events with low latency, which is an edge-triggered optimization, but each event is only a hint to enqueue an object key. The reconciler then reads full state and enforces all of it. The Kubernetes design archive says controllers are level-based to maximize fault tolerance and that watches restore the latency benefits of edge triggering without making correctness depend on them ([[decisions/events-as-hints-state-as-truth]]). Tim Hockin's slides are cited for the shorter version: state is more useful than events. Edge triggering is not always wrong, either, since it transmits only changes and can be made safe with periodic full resync or ordered, versioned events.

Level triggering also pays off when a controller is simply offline. The sig-api-machinery guide warns that your controller may be off for an indeterminate time before running again. A controller that keys its behavior on remembered events, such as a Pod having been deleted, will miss whatever happened during the outage and then act on a stale picture. A level-driven controller starts, reads the world, and repairs it ([[findings/a-controller-that-relies-on-seeing-every-event-misses-changes-made-while-it-is-down]]). Because a level-triggered loop may run at any time and any number of times, its logic must also be idempotent, meaning that running it again leaves the system in the same end state as running it once ([[concepts/idempotency]]).

The cost is real and the wiki lists it. A cache read can lag the controller's own writes, so a controller can act twice on one gap; core controllers handle this with deterministic names or with expectations that remember in-flight actions ([[findings/stale-cache-and-double-action]]). Constant re-checking costs reads and external API calls, covered in section 6. A pattern, not just a Kubernetes detail, emerges: the ApeiroRA reference architecture recommends the same controller idiom for digital-twin systems far outside container scheduling, framing level triggering as favoring resilience over efficiency ([[examples/controller-pattern-for-digital-twins]]).

## 5. Eventual consistency and convergence: what "done" means

The third principle changes what we mean by finished. In a system with many independent controllers, nothing happens instantly, and nothing is applied in a strict global order. The Kubernetes answer is to accept that. Instead of building a dependency graph up front, resources are applied concurrently, and anything whose prerequisites are missing fails and retries until those prerequisites exist ([[concepts/eventual-consistency-and-convergence]]).

The convergence research states the guarantee precisely. Kubernetes does not promise that the gap between desired and actual state closes instantly, or that every intermediate change is seen. It promises that the system keeps working toward the latest declared state, and convergence is the observable result: actual state settles on desired state once disruptions stop. The API conventions say the system drives toward the most recent spec regardless of previous versions. The practical lesson is the one from the replica example: if you edit a value five times quickly, treat it as one edit to the final value, because the last declared state wins.

You have probably seen this when applying a large set of manifests for the first time. A custom resource may be rejected because its CRD has not been established yet, or a workload may fail because a ConfigMap has not appeared, and then everything settles on a later pass. That is not a bug in your manifests. It is the design working as intended, and it explains why platform tools lean on retries and status conditions instead of strict ordering ([[concepts/conditions]]).

Status is how users learn where convergence stands. Conditions and `observedGeneration` tell you whether a given generation of the spec has been acted on. The API server increments an object's `metadata.generation` every time its spec changes, and a controller copies the value it last processed into `status.observedGeneration`, so a mismatch between the two means the controller has not yet caught up with your latest edit. Crossplane offers a clear illustration with two separate conditions on each managed resource: `Synced` says the provider can reconcile the resource, and `Ready` says the external thing is available. While a cloud database provisions, a user sees `Synced` true and `Ready` false, which means the controller is working and the thing is not usable yet. Reading only one of the two gives the wrong answer ([[examples/crossplane-database-claim-reports-synced-and-ready]]). Generic tooling that must decide "is this done?" for any kind uses a convention called kstatus, and the wiki's reading of it shows why the `observedGeneration` check matters. It checks deletion first, then generation, then the Reconciling and Stalled conditions, and only then Ready, and it reads only the top-level `status.observedGeneration` because the condition struct has no per-condition field. A stale top-level value therefore overrides a `Ready: True` condition, and a kind with no Ready condition at all is treated as always reconciled ([[findings/kstatus-checks-deletion-then-generation-then-reconciling-and-stalled-then-ready-so-a-stale-top-level-observedgeneration-overrides-ready-true]], [[findings/kstatus-reads-only-the-top-level-observedgeneration-because-its-condition-struct-has-no-per-condition-field]], [[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]]). Note the polarity as well: Reconciling and Stalled are abnormal-true conditions, where true means something needs attention, while Ready is normal-true, so a naive "any condition false is bad" rule misreads them.

Convergence has costs, and the wiki lists them with mitigations. Informer caches lag the API server, so reads can be stale; optimistic concurrency turns a stale write into a retried conflict. Retries can amplify load when there is no backoff or no limit on the number of attempts. Multiple replicas without leader election, the mechanism by which replicas of a controller agree that exactly one of them acts at a time, duplicate work. Kubernetes does not order dependent resources, so Flux, Argo CD, and Crossplane add health-based ordering. And drift correction is slow when the check interval is long. The ordering point deserves a concrete example, because the ordering tools show where a purely concurrent model is stretched. Flux provides `dependsOn` between Kustomizations plus health checks, so a dependent waits for the thing it needs to be Ready. Argo CD orders a sync by phase, then wave number, then kind and name, and it advances to the next wave only when the current wave is healthy ([[entities/flux]], [[entities/argo-cd]]).

## 6. Self-healing and drift detection, and the cost of constant reconciliation

The fourth principle is the one operators notice first. Self-healing is the continuous process by which a controller compares declared state with observed state and acts to close the gap, automatically reverting out-of-band changes such as a manual `kubectl edit` or a cloud console change. Drift is the gap itself: someone or something changed a live object or external resource away from what the source of truth says ([[concepts/self-healing-and-drift-detection]]). The mechanism is the same non-terminating control loop from section 4. Nothing new is added; the loop simply never stops, so the declared spec becomes an enforced contract instead of a suggestion.

There are two layers of drift, and the wiki separates them. For in-cluster objects, Flux and Argo CD detect drift by comparing desired manifests with live objects. Flux runs a server-side apply dry run on each interval (server-side apply is the mode in which the API server itself merges a submitted manifest into the live object and records which writer owns each field, and a dry run asks it to compute the result without saving it), and Argo CD marks the application OutOfSync and, if `selfHeal` is on, syncs again. For external infrastructure such as databases, buckets, and IAM, the same loop calls a provider API. Crossplane treats the `forProvider` field of a managed resource as the source of truth, so an edit made in a cloud console is reverted on the next poll ([[examples/cloud-console-changes-reverted-by-provider-controllers]]). Cluster API extends the idea to machines, where a MachineHealthCheck replaces unhealthy Machines ([[examples/cluster-api-machine-health-check-replaces-failed-nodes]]).

The scenario is easy to reproduce. Someone hand-edits a Deployment in production. With Flux, the next reconcile re-applies the manifest from Git, and with Argo CD self-heal on, the same happens after a short delay. The edit is not lost through a bug. It is lost because the system is doing exactly what a level-triggered controller does, and teams that need emergency changes must pause reconciliation first ([[examples/gitops-reverts-a-hand-edited-deployment]]).

The cost side is where design judgment enters. Observing the world is not free, and detection latency equals the check interval ([[findings/drift-detection-latency-is-the-interval]]). In-cluster tools read the Kubernetes API and are cheap to run often, so their cadences are seconds to minutes. Controllers that talk to cloud APIs pay for every observation, so their cadences are hours. The table below summarizes values the wiki recorded from documentation pages, manifests, and controller source; several differ by version or by layer, and the cells say so. Two of the cells mention jitter, which is a small random offset added to each interval so that many objects do not all poll at the same instant.

| Tool | What is compared | Cadence recorded in the wiki |
|---|---|---|
| Flux Kustomization | Server-side apply dry run against live objects | `interval` is a required field with no controller default; 60 seconds is a recommended minimum, and the `flux create` CLI defaults to 1 minute |
| Flux HelmRelease | Dry-run apply of the stored Helm manifest | Off by default (`disabled`); `warn` emits events; `enabled` corrects |
| Argo CD | Target manifests versus live state | 180 seconds flat through v2.14; 120 seconds plus up to 60 seconds of jitter from v3.0; a Git webhook bypasses polling; reverts only with self-heal |
| Crossplane | `forProvider` versus external state | 1 minute in core and crossplane-runtime; 10 minutes (with 5 percent jitter) in Upjet-generated providers such as provider-upjet-aws; per-resource override with the `crossplane.io/poll-interval` annotation |
| Config Connector | Spec versus Google Cloud state | 10 minutes on average, jittered between 0.5 and 1.5 times that, and the same for the direct, Terraform-based, and DCL-based controllers; five Terraform-mapped kinds override it (two at 0, three at 3600 seconds); a value of "0" disables it and the docs call that irreversible |
| ACK | Spec versus AWS state | About 10 hours after sync, tunable per kind |
| kro | Instance graph versus live resources | 10-hour resync (36000 seconds, v0.10.0 defaults), read as a replay of cached instances through the handlers and not a fresh list from the API server |
| Cluster API | Cache resync of its own objects | 10-minute `--sync-period`, which replays the controller cache and is not a poll of the cloud infrastructure |

The cadences differ for a reason that follows from the cost argument above. In-cluster tools such as Flux and Argo CD compare against the Kubernetes API, which is cheap to read, so they poll in seconds to minutes. ACK and kro sit on top of cloud APIs or large resource graphs where every full check spends rate-limit quota and time, so they use hours. Three details in the table deserve a plain explanation. First, Crossplane has no single poll interval. Core and the shared crossplane-runtime library default to one minute, but a provider generated with Upjet (the tool that turns Terraform providers into Crossplane providers, and the source of most of the large cloud catalogs) overrides it to ten minutes, so a drift latency quoted for "Crossplane" is wrong unless it names the provider. Second, Argo CD changed its default between major versions, and some documentation still carries the old figure: the v3 FAQ restates "3 minutes" as a ceiling of 120 seconds plus 60 seconds of jitter, so a v3 polling pass lands somewhere between two and three minutes, while v2 polled at a flat three. The change is attributed to pull request 22342, merged 2025-03-13, whose one-sentence body does not say why jitter was added, so the motive is unverified.

Third, Config Connector's reconciliation page states no number and points to a per-kind reference row, so the figure comes from the source. All three of its reconcilers (direct, Terraform-based, and DCL-based) end a successful pass by requeuing through one shared jitter function, which applies the `cnrm.cloud.google.com/reconcile-interval-in-seconds` annotation first and otherwise falls back to a ten-minute mean, so the controller kind alone does not change the cadence. The only per-kind differences are five overrides in the Terraform service mappings: ComputeSSLCertificate and ServiceIdentity are set to 0, because a resource that cannot be read back would otherwise be created repeatedly, and ServiceUsage `Service`, BigtableInstance, and BigtableTable are set to 3600 seconds. In the generated reference pages that the dossier tallied, 262 of 267 show 600 seconds. What happens when a kind has both a Terraform mapping and a direct controller was not tested, so that overlap is unverified, and no cadence was measured on a live cluster ([[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]], [[findings/config-connector-per-kind-reconcile-intervals-exist-only-as-five-terraform-service-mapping-overrides-and-262-of-267-reference-pages-show-600-seconds]]).

A fourth detail is that the word "resync" names three different mechanisms, so two rows that both say ten hours do different work. In client-go and controller-runtime, a resync delivers an update notification for every object in the informer's local cache to the event handlers, and the client-go interface comment states that it adds no interaction with the authoritative storage; controller-runtime's `SyncPeriod` is built on that replay, defaults to ten hours with jitter, and produces an artificial update event whose old and new objects are identical, so a predicate such as `GenerationChangedPredicate` filters it out ([[findings/a-resync-replays-the-informers-local-cache-to-the-handlers-and-never-contacts-the-api-server]]). kro's `dynamic-controller-default-resync-period` flag defaults to 36000 seconds and its help text says it will "re list" resources, but the dossier reads the mechanism as the resync argument of the metadata informer kro builds for each resource type, so the help text describes a replay of cached state and not a fresh LIST; the flag text is verified and the mechanism is the dossier's reading. ACK's ten hours is something else entirely: after a successful reconcile the runtime returns a `RequeueAfter` of ten hours, which causes a real re-read of the AWS resource on each pass. So ACK's interval sets the longest time an out-of-band AWS change can go unnoticed, whereas kro's and Cluster API's intervals give handlers another chance to enqueue keys they may have dropped and cannot notice a change the informer never received ([[findings/the-word-resync-names-three-different-mechanisms-in-client-go-kro-and-ack]]). The Cluster API row exists mostly to head off a misreading: its sync period refreshes a cache and does not poll the cloud, so Cluster API's drift handling beyond that flag was not confirmed. The Crossplane documentation page on managed resources was read in full and states no poll interval default, so it cannot be cited for these numbers, and the values come from source files on the default branch as of 2026-11-26. The one official page that does mention a figure, the Crossplane Pods guide, gives a one-minute polling rate and a one-hour sync interval, which agrees with the source for core but says nothing about the ten-minute Upjet default.

The source for the table is [[comparisons/drift-detection-mechanisms-across-tools]], and the broader cadence and off-switch comparison is [[comparisons/reconcile-cadence-and-off-switches-across-tools]]. The wiki notes that it is not stated whether ACK's and kro's ten-hour figures describe comparable mechanisms. The consequence of a ten-hour default is that a console change to an AWS resource may sit uncorrected for hours, whereas a Crossplane resource using the runtime default would be rechecked within about a minute, at the price of an API call per resource per poll ([[decisions/choosing-a-drift-check-interval-for-external-resources]]). Shorter intervals correct faster and cost more quota, and the guidance in the sources is to choose intervals per resource class, with short ones where drift is costly ([[findings/cost-of-constant-reconciliation]]). Argo CD adds jitter to its v3 default so that many applications do not poll at once, and Crossplane's Upjet providers do the same at 5 percent of the poll interval.

A second cost is that a continuous loop reverts intentional changes along with accidental ones. The wiki calls this the main operational lesson for platform teams: decide who owns each field ([[findings/continuous-loops-override-intentional-changes]]). Every tool ships an off-switch, which suggests the problem is common. Flux has `suspend`, Argo CD has a self-heal toggle, Crossplane has a pause annotation and management policies such as Observe-only, and Config Connector accepts a reconcile interval of "0" to disable periodic reconciliation. A short Flux example shows several of these knobs together.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: 10m          # periodic full reconcile; drift is detected at this cadence
  retryInterval: 2m      # separate schedule when a reconcile fails
  path: ./apps/production
  prune: true            # delete objects removed from Git
  wait: true             # treat readiness of applied objects as part of success
  suspend: false         # set to true during incident work to stop applying and drift detection
  sourceRef:
    kind: GitRepository
    name: fleet
```

Read it as a set of decisions. The `interval` is how stale the cluster can be relative to Git. The `retryInterval` keeps a failing object from sharing the healthy cadence. `prune` decides whether a missing manifest means deletion, which section 10 returns to. `suspend` is the deliberate pause an operator uses during an incident. Flux's own documentation contradicts itself on this point, and the contradiction is not a version difference. The concepts page says reconciliation runs every five minutes by default, but the Kustomization reference calls `.spec.interval` a required field and says the value should be at least 60 seconds. The source settles it: the Kustomization type marks `interval` as required with no default, so a manifest without one is rejected and nothing ever falls back to five minutes. The 60-second figure is a recommendation written as "should" in prose, which the type does not enforce, and the only built-in default the dossier found is the `flux create` command's one-minute `--interval` flag, which applies only when the CLI generates a manifest. The five-minute number may circulate because most example manifests use `5m`, but that is an inference. The wiki did trace the concepts-page sentence to a documentation commit on 2022-08-10 that changed it from "every one minute by default" to "every five minutes by default" with no stated reason, and no controller change accompanied the edit, so the reason remains unknown. The practical advice is to set `interval` explicitly on every object ([[findings/the-flux-concepts-page-says-five-minutes-by-default-but-the-kustomization-and-helmrelease-references-require-the-interval-and-set-no-default]]).

## 7. GitOps pull: Git as desired state and push versus pull delivery

The fifth principle applies the first four to the problem of delivery. GitOps is a way of operating a system in which the whole desired state is written declaratively, stored in a versioned and immutable store (usually Git, increasingly an OCI registry, meaning a container registry used to store OCI artifacts such as manifests and charts, not only images), and applied by software agents instead of by humans or pipelines running commands. The OpenGitOps working group under the CNCF reduces it to four principles: the state is declarative; it is stored versioned and immutable with full history; agents automatically pull it; and agents continuously observe actual state and try to apply the desired state ([[concepts/gitops-pull-based-delivery]]).

The last two principles are what separate GitOps from CI/CD that happens to read YAML from Git. A pipeline that pushes once and never looks again does not qualify, because it has no continuous loop. This is exactly the declarative-intent, level-triggered, self-healing machinery from the earlier sections, pointed at a source of truth that lives in Git.

Push and pull differ in where the actor runs and what it holds. A push pipeline runs outside the target on a CI server and needs credentials for every environment it deploys to, so a compromise of that server exposes all of them. A pull agent runs in or next to the target, fetches desired state with read access to the source, and writes with in-cluster identity ([[comparisons/push-versus-pull-delivery]]). INNOQ makes the security case in an article the wiki cites, and also argues that the pattern does not require Kubernetes: a custom operator running inside a virtual machine fleet or cloud environment could read desired state from Git and reconcile it, though INNOQ warns that the hard part is continuous reconciliation and not fetching YAML ([[examples/gitops-agent-on-non-kubernetes-targets]]). The wiki found no named production deployment of that design.

Pull is not a free lunch. The agent becomes a powerful identity itself, so tools add counters. Flux impersonates a per-tenant service account when applying, so a team's Kustomization can only create what that account may create ([[findings/blast-radius-and-privilege-centralization]]). ControlPlane's Flux D2 reference architecture goes further for regulated fleets: CI builds and signs artifacts and pushes them to an OCI registry, and clusters pull the signed artifacts so they never connect to the Git host ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]). That is a vendor write-up, and whether Git or OCI should be the source of record is left open by the sources. Morgan Stanley's reported setup used S3 buckets as a source for another reason, which the write-up gives as availability and compliance.

The word pull also hides a distinction that matters once you run many clusters. Argo CD pulls from Git, but a single central Argo CD instance reaches into each registered remote cluster to apply changes, so delivery to a fleet is still a push from a hub even though every Application pulls its source. A separate project in the argoproj-labs organization, argocd-agent, describes the inverse, in which lightweight agents in each cluster reach back to a central hub; the dossier found no maturity statement in its README, so its readiness is unverified. Flux more commonly runs a set of controllers inside every cluster, although a Kustomization can also target a remote cluster through `.spec.kubeConfig`, which the specification recommends configuring without a stored secret ([[findings/argo-cd-reaches-into-registered-clusters-from-a-hub-and-the-argocd-agent-pull-model-is-a-labs-project-of-unverified-maturity]], [[decisions/reach-spoke-clusters-from-a-central-argo-cd-hub-or-with-argocd-agent-pulling-from-the-spokes]]). On the Argo CD side, an ApplicationSet is a controller that stamps out many Applications from generators, such as a list of registered clusters or a set of pull requests. Its documentation lists limits worth knowing: the matrix generator combines only two child generators, combination generators can be nested only once, and the pull request generator polls every 30 minutes by default and makes anonymous, lower-rate-limit requests unless a token is set. The RollingSync strategy for staged rollouts is marked Beta from v3.3.0, forces autosync off on the generated Applications, and watches only Application health. The dossier found no quantified scale limit for ApplicationSets or hub-and-spoke Argo CD, which is a statement about what was found and not a claim that none exists ([[findings/applicationset-generators-have-documented-limits-matrix-takes-two-children-nesting-is-once-and-pull-request-polling-defaults-to-30-minutes]], [[findings/applicationset-rollingsync-is-beta-forces-autosync-off-and-watches-only-application-health]]).

Secrets are the other place where pull-based delivery meets a hard question, because a repository that holds the whole desired state must not hold secrets in the clear. Argo CD's secret-management page says it strongly recommends populating secrets on the destination cluster with an operator such as Sealed Secrets, External Secrets Operator, the Secrets Store CSI Driver, or Vault Secrets Operator. It cautions against plugins that inject secret values while Argo CD renders manifests, because Argo CD stores generated manifests in plaintext in its Redis cache, secret updates become coupled to syncs, and the approach is incompatible with the Rendered Manifests pattern. The page never mentions SOPS, so Argo CD's documented position on it is unverified. Flux takes the opposite stance: its kustomize-controller decrypts SOPS-encrypted files itself, and requires that `metadata`, `kind`, and `apiVersion` stay in plaintext ([[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]]). The same split shows up for OCI sources. Flux's OCIRepository, which pulls OCI artifacts (the container-registry packaging format that also carries manifests and charts), can verify Cosign or Notation signatures (Cosign and Notation are two tools for signing and verifying such artifacts), including keyless identity matching, whereas the Argo CD pages that were read describe OCI sources and a Git-commit GPG check and document no OCI signature verification; that is a statement about the pages read and not proof the feature is absent from the code ([[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]], [[decisions/git-versus-oci-as-the-canonical-source]]).

A useful way to hold the whole picture is the two-layer loop. GitOps controllers reconcile Git into the Kubernetes API, and domain controllers such as Crossplane or Cluster API reconcile the API into reality. Each layer is level-triggered, and the pitfalls mostly occur at the seams: custom-resource health, pruning, drift against controllers that mutate fields, and credentials.

## 8. Design principles that fall out of the model, with Flux and Crossplane as worked implementations

Once the five principles are on the table, a set of design rules follows from them. This section states the rules with their reasoning and then shows Flux and Crossplane obeying them.

**Make intent the only input.** If the contract is a spec, then every behavior should be derivable from the spec and observed state. Anything that depends on a remembered event or an unrecorded action breaks level triggering. This is why the Kubebuilder good-practices page requires an idempotent reconcile and warns that logic keyed to specific events can leave resources stuck ([[findings/event-specific-logic-in-reconcilers]]).

**Make every action safe to repeat.** A loop that runs forever will run the same operation twice, and sometimes in a crash window where it does not know whether the first attempt succeeded. The wiki describes idempotency at three layers: the controller loop, the Kubernetes API (deterministic names and server-side apply), and external cloud APIs. The third is hardest, because creating a cloud resource is not naturally idempotent. If a controller calls a create API and crashes before recording the returned ID, a blind retry can leak the first resource. The documented answers include caller-chosen names, a persisted external identity such as Crossplane's `crossplane.io/external-name` annotation, recording intent before acting and halting when the result is unknown, and server-side client tokens ([[concepts/idempotency]]).

**Split work into many small controllers that coordinate through shared objects.** The Kubernetes controller documentation favors many controllers that each own one aspect. A DevOps Toolkit walkthrough shows three controllers, for ingress, certificates, and DNS, all reacting to one Ingress object with no controller calling another, each converging on its own concern ([[examples/ingress-cert-manager-and-dns-controllers-react-to-one-object]]). Reconciliation composes without orchestration code.

**Give every writer an explicit identity and every field an owner.** When humans, a GitOps tool, an autoscaler, and other controllers all write to one object, someone will overwrite someone. Server-side apply tracks which manager owns each field and raises a conflict when another manager owns a differing field ([[concepts/server-side-apply-and-field-ownership]], [[findings/multiple-writers-on-one-object]]).

**Ship a brake with every accelerator.** Self-healing needs a way to stop. Cluster API's MachineHealthCheck short-circuit stops remediation when too many machines look unhealthy at once, because the cause is probably shared. In the v1beta2 API (introduced in v1.11.0) that setting is named `remediation.triggerIf.unhealthyLessThanOrEqualTo`, and the older `maxUnhealthy` name is deprecated, though most public writing still uses it. The brake matters only if you set it: the guide read at v1.15.0-rc.0 says the short-circuit is disabled by default, because the default threshold is 100 percent and machines are then remediated no matter the state of the cluster ([[findings/remediation-can-amplify-an-outage]], [[findings/the-cluster-api-machine-health-check-short-circuit-is-off-by-default-so-remediation-is-unbounded-until-a-threshold-is-set]], [[findings/cluster-api-v1beta1-maxunhealthy-and-unhealthyrange-are-deprecated-and-older-material-uses-the-old-names]]). Argo CD ships with prune and self-heal off, and Flux offers a `warn` drift mode before `enabled`.

**Report state honestly.** Conditions, `observedGeneration`, and separations like `Synced` versus `Ready` let people and other tools tell the difference between a controller that is working and a thing that is usable.

Now the two worked implementations. Flux is a set of single-purpose controllers for sources, Kustomize, Helm, notifications, and image automation, and they communicate through CRDs that users or other automation can also write, which makes the control plane an integration bus ([[entities/flux]]). The source controller pulls Git, OCI, Helm, and bucket content into artifacts. The kustomize and helm controllers apply them. The notification controller accepts webhooks that start a reconcile immediately, so events are a latency optimization on top of the polling interval. Image automation writes new tags back to Git, so Git remains the audit record. Notice how each rule appears: intent is in Git, the loop is level-triggered with an interval as the safety net, ordering uses `dependsOn` and health checks, and tenancy uses service-account impersonation.

The internals of Flux show two more of these rules at work, and they matter when you size an installation. First, extra replicas of a Flux controller add failover and not capacity: only the elected leader reconciles, so scaling from one replica to three does not triple throughput. Capacity grows by raising `--concurrent` and resource limits on the active instance, or by sharding, which runs separately named controllers that each watch a disjoint set of objects selected by a label. The sharding page advises it when Flux manages tens of thousands of applications, and it says the notification controller and source-watcher do not support sharding. Its example recipe also removes the image-reflector and image-automation Deployments from the shard sets, so the documented recipe leaves image automation on the default instance, though whether those controllers could be sharded was not established. A dependent object must carry the same shard label as its parent, and a HelmChart generated from a HelmRelease takes its shard label from `spec.chart.metadata.labels` ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]], [[findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded]], [[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]], [[findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels]], [[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]]). Second, the source controller is the one place where state is kept outside the API. It starts its artifact server only after it wins leader election, so standby replicas fail readiness, and the stock manifest runs one replica with `emptyDir` volumes and a one-minute artifact retention. The dossier infers, without confirming it, that artifacts do not survive a pod restart and are rebuilt on the next reconcile, so a platform that restarts the source controller often should expect dependents to wait ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]], [[findings/the-stock-flux-source-controller-keeps-artifacts-in-an-emptydir-with-one-minute-retention-so-a-restart-rebuilds-them]]). Image automation, finally, is the piece that writes back to Git: its kinds are served at `image.toolkit.fluxcd.io/v1`, and the official guide offers semver ranges for production, a separate push branch so that a person or CI can open a pull request and approve updates, and reverting a bad update by narrowing the range. The multi-tenancy reference repository restricts automation to staging, and a loose regex or an over-wide range can promote a release nobody reviewed. No adopter write-up on which promotion policy teams actually use was found ([[findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range]], [[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]], [[decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation]]).

Crossplane is the provisioning-side example. Providers expose cloud resources as managed resources, each with a `spec.forProvider` block that is the source of truth for the external resource. Here is a trimmed sketch, with field names as documented for Crossplane managed resources.

```yaml
apiVersion: s3.aws.upbound.io/v1beta1
kind: Bucket
metadata:
  name: team-artifacts
  annotations:
    crossplane.io/external-name: team-artifacts-prod   # persisted external identity
spec:
  forProvider:
    region: us-east-1                                   # edits made in the console are reverted
  managementPolicies: ["*"]                             # narrow to ["Observe"] to import without modifying
  deletionPolicy: Orphan                                # keep the real bucket if this object is deleted
```

The snippet shows three guard rails in a few lines. The external-name annotation ties the Kubernetes object to a cloud identifier so retries do not create duplicates. `managementPolicies` limits what the controller may do, so an existing resource can be observed without being changed. `deletionPolicy` decides whether deleting the Kubernetes object deletes the real bucket. The wiki notes that older advice about `deletionPolicy` and observe-only behavior needs translation to `managementPolicies`, and that the Crossplane documentation read for pitfalls was an older version, so check your release ([[findings/the-pitfalls-dossier-rests-on-index-summaries-an-older-crossplane-version-and-few-primary-incident-reports]]). Above managed resources, a Crossplane composition lets a platform team publish a small API of its own. The documentation describes a pipeline of functions that accumulate desired state, which Crossplane applies and re-observes on each reconcile, moving composition logic out of templating and into code with feedback ([[entities/crossplane]]). Two details about those functions help explain why Crossplane behaves as it does. They began in alpha (v1.11.0, January 2023) as run-to-completion containers launched by an `xfn` sidecar in the Crossplane pod, and v1.14.0 (2023-11-01) moved them to long-running Deployments managed by the package manager, a change that was incompatible with alpha functions; v1.17.0 graduated them to v1. A function speaks a gRPC `RunFunction` contract, which is a different wire format from the `ResourceList`-over-stdio contract of the KRM Functions specification that kpt and Kustomize use ([[findings/crossplane-moved-composition-functions-from-an-xfn-sidecar-in-v1-11-to-package-manager-deployments-in-v1-14]], [[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]]). Packages also have their own machinery. Crossplane resolves package dependencies in a controller that builds a graph from the cluster-scoped `Lock` object, never modifies the Lock, and creates only the first missing dependency on each pass, so a chain of missing dependencies fills in over several reconciles. Automatic dependency version upgrades are alpha and off by default, and downgrades need a second alpha flag because they can orphan resources. Each provider upgrade leaves a ProviderRevision behind, one inactive revision is kept by default, and upgrading a function changes every composition revision that references it through `functionRef`, even a manually pinned one ([[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]], [[findings/crossplane-dependency-version-upgrades-and-downgrades-are-alpha-and-downgrades-need-both-feature-flags]], [[findings/provider-upgrades-leave-old-revisions-and-block-automatic-downgrades]], [[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]], [[decisions/let-crossplane-resolve-package-dependencies-or-pin-versions-and-skip-resolution]]). On scale, no Crossplane performance or sharding guide was found. The core process strips CRD schemas from its cache and defaults its worker pool to 100, the closest official guidance gives a one-minute poll and a one-hour sync interval, and the only measurement is a maintainer-reported drop in heap from 338 MiB to 190 MiB on a cluster with 791 CRDs in the v2.5.0 notes of 2026-11-24 ([[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]], [[examples/crossplane-v2-5-0-released-2026-11-24-with-alpha-compositionrevision-garbage-collection-and-an-upgrade-ownership-fix]]).

Together the two tools show why the principles compose. Flux uses the control plane to deliver intent, Crossplane uses it to realize intent against external systems, and both rely on the same loop, the same status conventions, and the same ownership model.

## 9. Industry use cases: GitOps fleets, cloud services as Kubernetes objects, non-container appliances

The strongest adopter evidence in the wiki concerns GitOps fleets. Morgan Stanley described its Flux adoption in a FluxCon NA 2025 talk, which the Flux team wrote up in March 2026. The reported footprint is over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources, up from push pipelines that suffered from drift and made cluster rebuilds fragile. Multi-tenancy rests on service-account impersonation with Kubernetes RBAC. A self-service onboarding platform checks entitlements, registers the service, primes a namespace with a source and a Kustomization, and scaffolds a repository. At scale the platform team raised reconciliation intervals, tuned the `--concurrent` flag and resource limits, and moved the source of truth from a self-hosted Git provider to S3 buckets. The wiki is careful to call this a self-reported conference account and not an audit, and sharding and OCI artifacts were still on the roadmap, so no production sharding numbers exist ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]).

Beyond that single detailed case, the adopter lists show breadth without depth. Argo CD's `USERS.md` file, which organizations add themselves to by pull request, held 452 numbered entries when the dossier counted on 2026-11-26 (a later count of its lines gave 461) and names Adobe, IBM, Intuit, Red Hat, and Tesla among others. Flux's adopters data file lists more than 200 organizations, including Xenit, Sortlist, Tietoevry, Nexxiot, SoulCycle, and Luma Health. Both lists are self-reported and unaudited, none of the entries is tied to an incident, and no migration story or measurement was read for any of the Flux names, so what those organizations do and how well it works is unverified. A press repost of a CNCF survey says nearly 60 percent of Kubernetes clusters managed by respondents rely on Argo CD, but the original was not read and the survey year could not be reproduced, so treat that figure as secondary only ([[examples/the-argo-cd-users-file-lists-452-self-reported-adopters]], [[examples/the-flux-adopters-data-file-lists-xenit-sortlist-tietoevry-nexxiot-soulcycle-and-luma-health-among-others-with-no-write-ups]]). On the sharding side, Cozystack, a project that turns commodity servers into a Kubernetes-based cloud, ships a `flux-shard-operator` that creates helm-controller shards at roughly 100 HelmReleases per shard, up to 16, using the label `sharding.fluxcd.io/key`. Those numbers are the project's own design targets, and no measured production outcome was found ([[examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard]]).

Intuit is the other named organization. In a Red Hat interview, Intuit said it built Argo CD to manage deployment complexity in a controlled and auditable way, with Git history as the audit trail and the cluster continuously pulled toward what Git says ([[examples/intuit-argo-cd-gitops-origin]]). The wiki notes it is a podcast-style account and not an engineering postmortem. For teams adopting GitOps, the sources describe a staged pattern: stateless applications run with automated sync and self-heal, while risky production workloads stay on manual sync so Argo CD reports drift without applying it. That example comes from a vendor blog, so it is illustrative and not benchmarked ([[examples/incremental-gitops-adoption-with-manual-sync-and-self-heal]]).

For cloud services as Kubernetes objects, the scenario is a team that already uses Kubernetes and wants S3 buckets, databases, and IAM roles to follow the same RBAC, audit, and GitOps workflow as Deployments. ACK on AWS and Config Connector on Google Cloud expose these services as custom resources. ACK scopes one controller and its IAM permissions per AWS service, and both tools offer adoption of existing resources and a deletion policy ([[examples/cloud-services-as-kubernetes-objects]]). A platform team can go a step further and hide the details. Google's kro announcement, dated 2025-01-30, describes a self-service GKE cluster API where a user supplies a name, a node pool, a maximum node count, and a location, while the cluster, IAM, and policies stay behind those few parameters ([[examples/self-service-gke-cluster-with-kro]]). That source is a vendor announcement, and it said kro was not production-ready. Adoption evidence for these provisioning layers is thin but no longer empty. Built Technologies lists itself in the Crossplane ADOPTERS file and says that at times it has exceeded 10,000 AWS resources managed by Crossplane, though the entry is undated, self-reported, and describes a developer environment and not production ([[examples/built-technologies-reports-peaks-above-10000-aws-resources-managed-by-crossplane-in-a-developer-environment]]). Adobe appears in the ACK community's self-reported adopters file for global Kubernetes cluster provisioning and stateful service infrastructure using several ACK controllers, again with no object counts and no date ([[examples/adobe-lists-ack-for-global-kubernetes-cluster-provisioning-and-stateful-service-infrastructure]]). Crossplane's file has 87 entries but only about eight give numbers, and no adopters file was found for kro, Cluster API, or Config Connector, so named production evidence for kro in particular is still missing ([[findings/evidence-and-fact-check-pass-gap-dispositions]]). The later pass confirmed that gap and found no kro benchmark, ADOPTERS file, or named production adopter either. The nearest evidence of productization is that AWS documents kro as a managed capability of Amazon EKS and walks through composing ACK S3 Buckets with Deployments and ConfigMaps, where kro infers the creation order from a reference to the bucket's `status.ackResourceMetadata` and validates the graph when it is created, not at runtime; that shows a hyperscaler offering the pairing and does not settle maturity, because the project still reports a `v1alpha1` API ([[examples/the-eks-kro-capability-composes-ack-s3-buckets-with-deployments-and-config-maps]], [[findings/kro-scale-evidence-is-two-open-issues-and-a-closed-unmerged-pull-request-with-no-benchmark-and-no-named-production-adopter]]). Two further cautions come from that pass. Google states that the GKE Config Connector add-on can lag the latest release by 12 months or more and, in a 2023 blog post, discouraged using it in production because of the lag ([[findings/the-gke-config-connector-add-on-can-lag-the-latest-release-by-12-months-or-more-and-google-discourages-it-for-production]]). And the two ACK documentation sites disagree on whether annotation-based adoption is alpha or Beta, an ACK contributor called the older site deprecated, and for controller versions released on or after 2026-10-08 cross-namespace references are blocked unless `--enable-cross-namespace` is turned on ([[findings/the-ack-old-and-new-documentation-sites-disagree-on-adoption-maturity-and-cross-namespace-references-default-to-blocked-from-2026-10-08-releases]]).

For clusters themselves, Cluster API designates a management cluster that runs its controllers and the provider controllers for AWS, vSphere, and other infrastructure. Operators describe workload clusters as Cluster, Machine, MachineDeployment, and MachineHealthCheck resources, and Machines are treated as immutable, replaced by rollout in the way Deployments replace Pods ([[examples/cluster-fleet-lifecycle-with-cluster-api]]).

The third group stretches the idea furthest. Ænix's examples include a router and firewall appliance, a KVM hypervisor, an industrial controller, and an IoT gateway speaking Modbus and MQTT, none of which exist to run containers ([[examples/non-container-appliances-on-the-kubernetes-api]]). The ApeiroRA recommendation of controllers for digital twins is a related, though differently motivated, endorsement ([[examples/controller-pattern-for-digital-twins]]). The wiki is open that this group is mostly vision with limited production evidence.

## 10. Pitfalls: stale caches, revert loops, retry storms, and control-plane overload

The wiki's pitfalls hub makes a point that is easy to miss: serious failures are usually cascades in which a small change meets a controller loop, a default, or a shared dependency, and the loop amplifies it ([[concepts/pitfalls-and-case-studies]]). Several of the failure modes below are the cost side of the five principles, which is why they recur.

**Stale caches and double action.** A level-triggered controller reads from an informer cache, and that cache can lag the controller's own writes. If it creates a Pod and reconciles again before the cache shows it, the gap still appears to exist and it may create a second Pod. Core controllers avoid this with deterministic names, as StatefulSet and Deployment do, or with expectations that track the controller's own unseen writes, as ReplicaSet does ([[findings/stale-cache-and-double-action]]). The lesson is that pure level triggering is not enough, and mature controllers add bookkeeping about in-flight actions.

**Revert loops and controllers fighting over fields.** When a mutating webhook (an admission hook that rewrites objects as they are submitted), an HPA (the HorizontalPodAutoscaler, which changes a workload's replica count based on observed load), or an image updater rewrites a field that a GitOps tool also manages, the result is endless OutOfSync status or a revert loop. A Flux blog post from 2026 recounts a SEV2 in which Flux kept resetting replicas to a high value while the HPA kept lowering it, and the cluster autoscaler added and removed nodes in a loop; in the author's words, the two controllers ping-pong indefinitely ([[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]]). The Kubernetes maintainers use the same scenario to explain server-side apply: because the autoscaler owns `replicas`, a CD system's apply conflicts instead of silently resetting the field ([[examples/hpa-and-git-both-set-replicas-surface-an-ssa-conflict]]). The mitigation is to decide who owns the field and tell the other tool to leave it alone, which has its own cost, since Git changes to an ignored field are no longer applied ([[findings/controllers-fighting-over-fields-cause-revert-loops]]).

A quieter variant is false drift. Servers and clouds fill in defaults, so a tool that compares its own rendering with the live object can see a difference that is not real. Config Connector documented this concretely: its legacy Merge mode copied unspecified fields into the spec and produced endless reconcile loops, and Absent mode, the default from version 1.123.1, fixed it ([[findings/defaulting-and-drift-reconcile-loops]]). Argo CD's default diff has a related symptom with server-defaulted fields in StatefulSet volume claim templates, and its Server-Side Diff option addresses it. Argo CD's diff-strategies page labels Server-Side Diff stable since v3.1.0, but that is a documentation label and not a promise that the bugs are closed, since the wiki's tracker search found 20 or more open issues that mention it, and the practitioner blog that first described the fix made stability claims the wiki did not verify ([[findings/diff-is-not-apply-server-defaults-look-like-drift]]).

**Unintended deletion.** A reconciler that compares full desired state with observed state treats anything observed but not desired as surplus. With prune permission, an accidental omission from the source becomes a deletion ([[findings/a-level-based-loop-deletes-what-it-no-longer-sees-in-desired-state]]). With provider controllers, the deletion can reach real cloud resources ([[findings/destructive-deletion-of-external-resources]]). The opposite risk also exists: with prune off, Flux leaves removed manifests running as orphans, which breaks the claim that Git is the source of truth ([[findings/without-prune-flux-leaves-removed-manifests-running-as-orphans]]). The largest named case is Skyscanner's outage of 25 August 2021. An engineer merged a templating change that was meant to alter no behavior, but it omitted the `{{ }}` template markers, so templating stopped applying to a file at the root of the cells configuration, which rolled out to every region at once. By about 1600 GMT Argo CD was reconciling clusters against a configuration that listed no valid namespaces and began deleting every service, 478 in all, across every availability zone and region. Because the clusters pull their state, recovery meant putting correct configuration back and letting each cluster reconcile itself. skyscanner.net was serving travelers from a single region by about 2030 GMT, and the remaining regions and non-critical services returned over the following two days. The post gives two durations for the outage, four and four and a half hours, and does not say which Argo CD sync options were set or whether pruning was automated, so the wiki records the deletion as documented behavior and does not claim a specific misconfiguration ([[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]]). Spotify's account is a cousin that involves Terraform and not a GitOps controller: in November 2018 an operator deleted a production GKE cluster in the console by clicking the wrong browser tab, and about a month later a Terraform review build wrote to a shared state file and an out-of-order merge deleted the Asia cluster, and after the team widened a service account's permissions to recreate it, Terraform deleted a second cluster, so two of the three production clusters were gone at once (the console deletion a month earlier had been restored), with no reported end-user impact because teams ran only part of each service on Kubernetes and service discovery used pod IPs ([[examples/spotify-deleted-one-production-gke-cluster-by-console-click-and-two-more-through-terraform-with-no-end-user-impact]]). The dates are the speaker's, and the talk is self-reported.

Smaller reports show the same mechanism at the scale of a single object. In Argo CD issue 15441 (2023-09-11), an anonymous reporter wrote that replacing an explicit Namespace manifest with the `CreateNamespace=true` sync option "actually deletes the namespace and recreates it during the Sync", which destroys everything inside the namespace; the Argo CD version was not recorded ([[examples/argo-cd-issue-15441-removing-a-namespace-manifest-under-createnamespace-deleted-and-recreated-the-namespace]]). In ACK issue 2911 (opened 2026-06-04), an Argo CD prune of a WAFv2 WebACL custom resource deleted the AWS resource, but the controller did not map the "not found" error on the next pass, so the custom resource sat in `Terminating` until someone patched its finalizer off by hand. A finalizer is the deletion-blocking marker described in section 2, and here nothing was left to clean up in AWS, so removing it was safe; the same patch would skip real cleanup if the cloud resource still existed ([[examples/an-argo-cd-prune-left-an-ack-wafv2-webacl-terminating-on-its-finalizer-after-the-aws-resource-was-already-gone]], [[findings/finalizers-strand-objects-in-terminating-when-the-controller-is-missing-or-failing]]). A related incident involves self-heal and not prune: a CNCF Ambassador post of 2026-11-20 retells an unnamed customer's release pushed during a deny sync window, after which two of five regional Applications skipped the database migration hook for 36 to 44 minutes because, in the author's reading of the source, self-heal runs a partial sync and a partial sync skips hooks ([[examples/argo-cd-self-heal-after-a-deny-sync-window-closed-skipped-the-migration-hook-on-two-of-five-regional-applications]]). That explanation is one author's, and the customer and Argo CD version are unstated. Most of these are single-reporter accounts. The ACK issue 2911 cause was confirmed by a maintainer, but the Argo CD issue 15441 report and the Ambassador retelling are unconfirmed, so the general severity assessment still rests partly on documentation warnings ([[findings/unintended-deletion-through-prune]]).

**Rollback friction.** Argo CD blocks rollback while automated sync is on, because a rollback would put live state out of line with Git and the controller would re-sync it at once. The path is a Git revert, which surprises teams used to fast imperative rollbacks ([[findings/rollback-is-blocked-while-automated-sync-is-on]]).

**Provider-managed objects under a GitOps agent.** The two layers of the loop meet most awkwardly when a delivery tool must judge and order objects that another controller owns. A generic agent cannot read a custom resource's health without help, because custom resources do not share a status format, so Argo CD ships Lua health scripts. On master (Argo CD v3.6.3, read 2026-11-26) those cover whole provider groups: `cnrm.cloud.google.com`, `services.k8s.aws`, `crossplane.io`, `upbound.io`, `kro.run`, and five Cluster API kinds. The scripts map conditions to health states, for example ACK's `ACK.Terminal=True` to Degraded and Config Connector's reason `UpToDate` to Healthy. Because Argo CD advances sync waves only when the current wave is healthy, a script that mishandles one kind blocks every later wave, and the dated cases are Argo CD issue 30164, where Config Connector kinds stayed Progressing because the script did not handle a `status.healthy` field, and issue 30373, where the built-in ACK check reports Healthy before the controller observes a spec change, since ACK conditions carry no `observedGeneration`. Both are reporter claims, not maintainer-confirmed root causes. Flux has no per-provider logic at all: it judges these kinds through kstatus or through health-check expressions you write in CEL, the Common Expression Language, a small expression syntax also used for validation rules and field references, its CEL cheatsheet lists Crossplane but not Config Connector or ACK, and how kstatus treats ACK's abnormal-true `ACK.Terminal` condition was not read. Flux issue 5855 shows the premature-ready race for Crossplane kinds that have no initial Ready condition, where maintainers recommended an `observedGeneration` CEL expression ([[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]], [[examples/argo-cd-issue-30164-config-connector-customize-kinds-stayed-progressing-because-the-health-script-did-not-handle-status-healthy]], [[examples/argo-cd-issue-30373-the-built-in-ack-health-check-reports-healthy-before-the-controller-observes-a-spec-change]], [[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]], [[examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression]]).

Field ownership gives a second seam. ACK resolves its `*Ref` fields and writes the resolved value back into the custom resource, and ACK issue 2361 (opened 2025-02-26, still open) reports that Flux server-side apply then restores the Git value, so the controller sees changed desired state and, at its ten-hour requeue, redeployed ECS services needlessly; the reporter's workaround was the `kustomize.toolkit.fluxcd.io/ssa: merge` annotation. No maintainer has confirmed it ([[findings/flux-server-side-apply-reverts-ack-reference-fields-that-the-controller-rewrote-according-to-issue-2361]]).

Ordering and deletion are a third seam: a single practitioner reports that Config Connector has no Terraform-style dependency graph and that Argo CD deletes children without ordering, leaving some in DeleteFailed, and a Config Connector design document says a child whose parent was deleted first sticks on `DependencyNotFound` with no documented ordered teardown ([[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]], [[findings/a-config-connector-design-document-says-a-child-whose-parent-was-deleted-first-sticks-on-dependencynotfound-and-no-read-documentation-describes-ordered-teardown]]). On deletion policy, ACK resolves it from the resource, then the namespace, then the controller default, and issue 3154 reports that the namespace-level retain annotation is ignored in single-namespace installs, so a team should confirm a per-resource retain ([[findings/pruning-an-ack-custom-resource-deletes-the-aws-resource-and-the-namespace-retain-annotation-is-ignored-in-single-namespace-installs]], [[decisions/protect-a-provider-managed-object-from-gitops-prune-with-a-provider-retain-policy-or-an-agent-side-prune-opt-out]]).

The widest reported blast radius sits in the Argo CD layer itself: in issue 20440, an anonymous reporter on Argo CD v2.6.6 saw an ApplicationSet-generated Application deleted together with everything it deployed, including namespaces and Argo CD itself, with no root cause found. The ApplicationSet `create-only` policy would not have stopped it, because the documentation says it does not prevent deletion through owner references ([[examples/argo-cd-issue-20440-an-applicationset-generated-application-was-deleted-with-its-namespaces-and-argo-cd-itself]], [[findings/the-applicationset-create-only-policy-does-not-stop-owner-reference-deletion-of-applications]]).

**Retry storms.** When a controller retries a failing write against an overloaded dependency, the retries can keep it overloaded. The tools bound retries differently. kro combines exponential backoff, a token bucket, and a documented cap of 20 retries (see the kro paragraph in the next section for what is and is not established about that cap); Argo CD uses configurable backoff and does not repeat an automated sync of the same commit and parameters unless self-heal is active; Flux separates `retryInterval` from `interval` ([[findings/retry-storms-and-unbounded-retries]]). The most complete case in the wiki is Zalando's January 2019 outage. A downstream call timed out, clients retried, and DNS queries spiked. The `ndots:5` default (a resolver setting that makes any name with fewer than five dots be tried against each search domain first, multiplying DNS lookups) meant about ten queries for each external lookup, Node.js did not cache DNS, and CoreDNS pods with a 100Mi memory limit were OOM-killed, meaning killed by the kernel for exceeding their memory limit, together. Monitoring ran inside the cluster and depended on DNS, so it went blind. Zalando raised memory limits to 2000Mi, adopted a node-local design, and moved alerting outside the cluster ([[examples/zalando-s-2019-coredns-outage-turned-a-retry-storm-into-a-total-dns-failure]], [[findings/monitoring-that-runs-inside-the-cluster-and-depends-on-cluster-dns-goes-blind-in-the-outage-it-should-report]]). The postmortem is a first-party 2019 account, so the defaults it names may have changed.

**Control-plane overload.** The shared store and API server are a single point of contention. Every custom resource lives in etcd, which has a single write leader, a storage limit that defaults to 2 GiB, with 8 GiB documented as a suggested maximum for normal environments and not as the default, a default maximum request size of 1.5 MiB (which binds before the kube-apiserver's own 3 MiB request body default, so an oversized custom resource is rejected by etcd first), and revision growth that needs compaction. The etcd limits page read for this pass was the v3.7 breadcrumb, and one secondary explainer the wiki used earlier wrongly called 8 GB the default ([[findings/etcd-limits-requests-to-1-5-mib-and-storage-to-2-gib-by-default-and-8-gib-is-a-suggested-maximum-not-the-default]], [[findings/etcd-scale-limits-of-the-shared-store]]). The clearest primary account is OpenAI's own status-page postmortem for 2024-12-11. A newly deployed telemetry service was configured so that every node in each cluster executed resource-intensive Kubernetes API operations whose cost scaled with cluster size. OpenAI operates hundreds of clusters, and all of its services were significantly degraded between 3:16 PM and 7:38 PM PST. The API servers were overwhelmed, and removing the telemetry service needed control-plane access that the load had taken away, which is why recovery was slow. Cached DNS records hid the failure for about twenty minutes while the rollout continued, and expiring caches then added load. Staging missed it because the failure scaled with cluster size and the pre-rollout checks covered CPU and memory and not API server load. An earlier version of this wiki leaned on a blogger's commentary that described the calls as list and watch calls from every node; the primary text does not say that, so treat that detail as unsupported. The root cause was telemetry load and not an informer bug, and the figures are self-reported by OpenAI ([[examples/an-openai-outage-shows-many-api-clients-can-overload-the-control-plane]], [[findings/control-plane-overload-blocks-the-remediation-that-would-fix-it]], [[findings/dns-caching-hid-the-control-plane-failure-for-about-twenty-minutes-before-expiring-records-added-load]]). Two more named incidents round out the control-plane picture. Jetstack's post of 2019-09-05 describes a regional GKE master upgrade that stalled because the API server's own startup write to a `kube-system` ConfigMap was subject to an OPA validating webhook whose backend was not responding; the master failed its health check, crash-looped, and GKE node auto-repair then recreated nodes in a loop that took down every tenant of the shared dev cluster. The fix was to delete the webhook, and the follow-ups were to scope it, add a liveness probe, and alert on API latency; the post never mentions `failurePolicy` ([[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]]). Neon's postmortem of 2025-05-21 covers two incidents on 2025-05-16 and 2025-05-19, 5.5 hours in total, in which a slow query on Neon's own control-plane database stopped idle pods from being suspended, pod count rose to about 8,000 against 6,000 planned, and two of three subnets ran out of IP addresses; restoring an emergency AWS CNI setting then triggered a second outage. That failure was in a platform layered on Kubernetes, not in the Kubernetes API ([[examples/neon-s-may-2025-delayed-start-incidents-exhausted-subnet-ips-after-a-slow-control-plane-database-query]]). Both are self-reported primary accounts. The server-side protection is API Priority and Fairness, and platform tools face their own scale dimensions, such as the number of CRDs installed by large providers ([[concepts/scale-and-sharding]]).

**Privilege centralization.** A control plane that manages everything concentrates authority. ACK limits this with one controller and scoped IAM per AWS service. A Cluster API management cluster, by contrast, becomes a single point of failure for the fleet, and Crossplane applies composed resources with its own service account, so RBAC on the composite API is the main guard rail ([[findings/blast-radius-and-privilege-centralization]]).

Finally, an honest note on the evidence. The original pitfalls dossier read only three first-party postmortems in full, and much of the failure index dates from 2017 to 2021 ([[findings/the-pitfalls-dossier-rests-on-index-summaries-an-older-crossplane-version-and-few-primary-incident-reports]]). The targeted pass added the OpenAI, Jetstack, and Neon primaries described above, and it also found first-party pitfall reports for the four tools the first pass could not cover, though all of them are individual reporter issues and not organization postmortems. For ACK, issue 3122 reports a controller restart during a rollout that created a second VPC endpoint and blocked subnet deletion for about two hours. Issue 3153 reports that pruning a custom resource from Git deletes the AWS resource irreversibly. A separate batch of issues filed on 2026-11-09 by one reporter was summarized in an audit as 48 resources in 22 controllers where a lost create response can duplicate the cloud resource or wedge the custom resource, which is a related mechanism to the second VPC endpoint in issue 3122 ([[examples/ack-issue-3122-a-controller-restart-during-a-rollout-created-a-second-vpc-endpoint-and-blocked-subnet-deletion-for-about-two-hours]], [[examples/ack-issue-3153-pruning-a-custom-resource-from-git-deletes-the-aws-resource-irreversibly]]). For Config Connector, issue 16444 (2026-11-25) describes a multi-cluster leader-election sequence in which a former leader runs a stale deletion against live Google Cloud resources, with no maintainer response yet ([[findings/config-connector-leader-election-across-clusters-can-run-a-stale-deletion-against-live-google-cloud-resources]]). For kro, user reports 1395, 1391, and 886 and a fault-injection report, issue 1171, cover breaking-change errors and a hard apply failure that discarded watches. For Cluster API, issue 10522 describes cert-manager rotation making webhooks unreachable for up to 90 seconds during an upgrade test, and issue 8172 describes deleting parents before the controller adds its finalizer, which orphans their resources ([[findings/no-named-organization-postmortem-was-found-for-kro-config-connector-ack-or-cluster-api]]). Almost all of these issues were open with no maintainer root-cause confirmation, and no named-organization postmortem exists for any of those four tools, so treat those cases as reproductions and leads and not as established evidence.

The picture for the delivery layer is better than that note suggests, because the Skyscanner, Reddit, and Spotify incidents were read from primary sources. Skyscanner's deletion of 478 services is described in the unintended-deletion paragraph above. Reddit's Pi-Day outage of 14 March 2023 lasted 314 minutes and began about two minutes after the team started upgrading a large legacy cluster from Kubernetes 1.23 to 1.24. Reddit's route reflectors in Calico selected nodes by the label `node-role.kubernetes.io/master`, Kubernetes 1.24 removed that label from running clusters, the selectors matched nothing, and routing collapsed. Responders lost all metrics, fixed forward for about two hours because Kubernetes has no supported downgrade and the backup restore was untested against production, and removed the Open Policy Agent webhook configurations after noticing API server write timeouts that came from admission calls. That removal ended the timeouts but did not recover the cluster, because the webhook was a symptom and not the cause. Recovery then meant restoring etcd by a procedure written for an older Kubernetes, and bringing traffic back in stages from 1 percent to 100 percent ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]]). A secondary retelling of the Reddit outage added a reconstructed timeline and a user count that Reddit's own post does not contain, and this part does not use them. The three incidents are self-reported by the organizations involved, and none of them was a failure of the Kubernetes reconcile model itself: they were failures of rollout process, configuration drift between hand-built clusters, and the permissions and state handling of the automation.

## 11. How Argo CD, Terraform, Cluster API and others differ on these principles

Comparing tools is easier once the principles are a checklist. For each tool, ask five questions. Does it take declared intent? Does it act on state or on events? How does it handle the gap between apply and ready? Does it correct drift continuously, and how fast? Does it pull or push? The answers below come from documentation pages and practitioner sources recorded in the wiki, and several comparisons are vendor-authored, as the wiki flags ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]]).

**Flux versus Argo CD.** Both are CNCF GitOps tools, and both run reconcile loops. The architectural contrast is that Argo CD ships as an integrated application with an API server, a repository server that renders manifests, and an application controller, while Flux is a toolkit of small controllers that each own custom resources, described in the dossier as controllers all the way down ([[comparisons/flux-versus-argo-cd-architecture]]). On drift, Flux reverts manual changes on each interval unless suspended, while Argo CD marks the application OutOfSync and reverts only when self-heal is enabled, which is off by default. On prune, Argo CD defaults to off and adds an allow-empty guard, while Flux prunes when enabled and offers a per-object opt-out annotation and a deletion policy ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). The wiki cautions that this table merges separate documentation pages and is not a head-to-head test. A minimal Argo CD sketch shows the same decisions in its vocabulary.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/fleet.git
    path: apps/web
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: web
  syncPolicy:
    automated:
      prune: false        # off by default; turn on only once the source is trusted
      selfHeal: true      # revert live drift back to Git
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas  # leave replicas to the autoscaler
```

The `automated` block turns on continuous correction, `prune: false` keeps the deletion brake engaged, and `ignoreDifferences` declares a field that another controller owns on purpose. There is a catch in that last rule that surprises people. By default Argo CD uses `ignoreDifferences` only when it computes the diff that decides whether an application is OutOfSync, so the ignored field stops showing as a difference, yet the next sync still applies the whole manifest from Git and can overwrite the field. Adding the sync option `RespectIgnoreDifferences=true` makes the sync honor the rule, but the documentation says that option is effective only when the resource already exists in the cluster, so a first create still writes every field. A team that silences a false OutOfSync with an ignore rule can therefore still see the field reset on every sync, which looks like a revert loop even though the diff is clean ([[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]]). These readings come from the documentation on the default branch, not from a pinned release. Flux expresses the same ideas through `driftDetection.ignore`, the `ssa` annotation, and, since 2026 according to the Flux blog the wiki cites, field-level `.spec.ignore` rules in Kustomizations that act directly during drift detection and correction. Those rules carry their own trap in the opposite direction: the kustomize-controller specification says that omitting the `target` selector makes a rule match every object the Kustomization manages, so a rule written for one Deployment's `/spec/replicas` would quietly exempt that path on every other object too, and real drift there would go uncorrected without any signal. The safe reading of the documentation is to give every rule a target ([[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]], [[comparisons/flux-ignore-rules-versus-argo-cd-ignoredifferences-and-force-conflicts-for-drift-fights]]).

**Crossplane versus Terraform.** The Crossplane project's own framing is that Crossplane is a control plane, where Terraform is a command-line tool, an interface to control planes. Crossplane runs controllers that reconcile continuously, so drift is corrected without anyone running a command. Terraform and OpenTofu compute a plan and apply it when a person or CI job invokes them, so drift shows up at the next plan, and a plan is a reviewable preview that Crossplane lacks. Terraform is simpler and more familiar, as the Crossplane blog itself concedes, and it needs no running cluster. The wiki labels both main sources partisan and records that no neutral comparison was read ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]], [[entities/terraform]]). The two meet in places: Crossplane can reuse the Terraform provider ecosystem through generated providers, and tofu-controller runs Terraform inside a reconcile loop with a detection-only drift model.

**Provider controllers.** ACK, Config Connector, and Azure Service Operator expose roughly one CRD per cloud resource and are single-vendor, while Crossplane is multi-cloud and adds compositions so a platform team can publish its own API without writing a controller ([[concepts/tooling-landscape]]). They differ on cadence and deletion. ACK defaults to about ten hours after a resource syncs and exposes Helm values for per-kind overrides ([[examples/ack-resync-period-tuning-for-stateful-resources]]). Config Connector corrects drift periodically once a resource is UpToDate (about every ten minutes on average, with jitter), retries failures with exponential backoff capped at two minutes, and lets you disable the interval with a value of zero, which its documentation describes as irreversible ([[findings/setting-a-config-connector-reconcile-interval-to-zero-switches-off-drift-correction-and-the-docs-call-it-irreversible]]). Config Connector also has more than one controller behind its kinds: its static configuration table lists 814 kinds and sets the direct controller as the default for 539 of them, a kind is routed by a namespace override and then the static default, and a live CRD label shows which controller runs. Its namespaced mode, the CRD default, needs one `ConfigConnectorContext` per namespace and maps namespaces to projects and service accounts, whereas cluster mode takes exactly one credential ([[findings/config-connector-s-static-config-table-lists-814-kinds-and-sets-direct-as-the-default-for-539-of-them]], [[findings/config-connector-routes-a-kind-to-its-controller-by-namespace-override-then-static-default-and-a-live-crd-label-shows-which-one-runs]], [[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]]). Its `deletion-policy` has two source values, only `abandon` changes the delete path, and the Terraform-based controller path was not verified ([[findings/config-connector-deletion-policy-has-two-source-values-and-only-abandon-changes-the-delete-path-and-the-terraform-based-controller-path-is-unverified]]). Teams weighing Config Connector against Crossplane should know that no neutral comparison was found: the evidence is two vendor positions, and a Crossplane maintainer wrote in provider-gcp issue 283 that Config Connector through the Kubernetes provider is not a replacement for a provider ([[findings/no-neutral-comparison-of-config-connector-and-crossplane-was-found-so-the-evidence-is-two-vendor-positions]], [[decisions/use-config-connector-directly-wrap-it-in-crossplane-through-the-kubernetes-provider-or-use-a-crossplane-gcp-provider]]). Both delete the real cloud resource by default when the Kubernetes object is deleted, and both offer a retain or abandon policy ([[comparisons/deletion-policies-across-gitops-and-provider-tools]]). Per-resource controllers do not build a Terraform-style dependency graph, so ordering falls to the delivery tool or a composition layer.

**kro.** kro expands one end-user CRD into a graph of resources through a ResourceGraphDefinition, infers dependency order from CEL expressions, and calls itself pre-1.0; the announcement said it was not production-ready ([[entities/kro]], [[findings/immature-abstractions-in-the-control-plane-ecosystem]]). It handles all instances from one shared rate-limited queue with a ten-hour resync (a replay of cached instances through its metadata informers, as the cadence table notes) and a documented cap of 20 retries (what happens to an item after the cap was not established), plus, at v0.10.0, per-instance exponential backoff capped at five minutes for an unready instance ([[findings/kro-v0-10-0-requeues-an-unready-instance-with-per-instance-exponential-backoff-capped-at-five-minutes-while-v0-9-4-has-no-backoff-package]]). Earlier wiki text, and the kro FAQ, describe a dedicated controller per ResourceGraphDefinition, but the tuning page and the v0.10.0 source agree on one dynamic controller with one worker by default, a token bucket of 10 events per second with burst 100, and one parent watch per definition, so the FAQ wording is the outlier. The consequence is that one busy definition can starve others, and a maintainer proposed weighted queues in issue 198 (open since 2025-01-11) while issue 610 asks for performance testing automation and has posted no results. A pull request that described added deletion latency at large scale was closed unmerged on 2026-08-11. No benchmark and no measured scaling limit exist, so capacity has to be tested, and a Perun Engineering article that lists production failure patterns cites no customer or data and uses outdated names, so it is low reliability ([[findings/the-kro-docs-faq-says-a-dedicated-controller-per-rgd-while-the-tuning-page-and-source-describe-one-shared-queue]], [[findings/kro-s-single-shared-queue-can-starve-resources-and-a-maintainer-proposed-weighted-queues]], [[findings/kro-scale-evidence-is-two-open-issues-and-a-closed-unmerged-pull-request-with-no-benchmark-and-no-named-production-adopter]]). On governance, v0.10.0 (2026-11-10) fixed graph cleanup after partial apply failures and rejects duplicate definition identities before adopting objects, and a pull request merged on 2026-10-29 adds an alpha per-resource `deletionPolicy` of `Delete` or `Orphaned` behind a feature gate that is off by default, so kro's default is still to delete children. Release notes do not say whether any fix came from a production incident ([[findings/kro-v0-10-0-fixes-partial-apply-cleanup-and-duplicate-rgd-identities-and-pull-request-1445-adds-an-alpha-deletion-policy-behind-an-off-by-default-gate]]). The wiki also records that kro's graph engine can run as a Crossplane pipeline step through function-kro, which approximates kro's built-in conditions from a single run and lists documented differences from upstream, so its full-parity claim reads as the same engine with gaps ([[examples/function-kro-runs-a-kro-resource-graph-as-a-crossplane-pipeline-step]], [[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]], [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]]). A reported kro bug about drift not being reconciled after creation was closed as completed on 2025-11-04, and the wiki marks that history as unverified.

**Cluster API.** Cluster API applies the same loop to clusters, with infrastructure, bootstrap, and control-plane providers behind one API. Its self-healing is replacement: a MachineHealthCheck evaluates Node conditions against timeouts and remediates unhealthy Machines, with the short-circuit threshold as a brake. In the current v1beta2 API that field is `remediation.triggerIf.unhealthyLessThanOrEqualTo` (or `unhealthyInRange`), and `maxUnhealthy` is the deprecated v1beta1 name that appears in older books, including the v0.4 book this wiki first read; v1beta1 is tentatively slated for removal in April 2027. The default threshold is 100 percent, which leaves the guard off until you set a lower value, and the verified guide is from the v1.15.0-rc.0 tag, so recheck it when v1.15.0 final ships ([[entities/cluster-api]], [[findings/the-cluster-api-machine-health-check-short-circuit-is-off-by-default-so-remediation-is-unbounded-until-a-threshold-is-set]]).

**Plain controllers.** A hand-written operator built with Kubebuilder or controller-runtime follows all five principles by default, because the framework supplies informers, a work queue, and a reconcile signature that receives only a key. The cost is that the author must supply idempotency, status conventions, and finalizer discipline, and the wiki observes that hand-written operators sometimes duplicate what a composition could express ([[concepts/operator-pattern]], [[findings/hand-written-operators-duplicate-what-composition-could-express]]).

**Platform frameworks, portals, and developer-facing abstractions.** Several tools in the wider landscape sit above or beside the reconcile loop, and asking the five questions of them shows where they stop short of the model. Kratix, from Syntasso, packages a platform API as a Promise and schedules its output to Destinations in two stages: dependencies go to every Destination, or only those whose labels match the Promise's `destinationSelectors`, and a second stage picks a Destination at random when several match. A Destination with `strictMatchLabels: true` accepts only Promises whose selectors match, and a workflow can add selectors, with a fixed order of precedence among them. Only the documentation and type files were read, not the scheduler code, and Syntasso's PCI-segmentation illustration is a vendor example that does not say whether it relied on strict matching ([[findings/kratix-schedules-in-two-stages-by-label-matching-and-picks-a-destination-at-random-when-several-match]], [[examples/kratix-promises-scatter-workloads-across-standard-pci-and-terraform-destinations]]).

Backstage is a portal and not a controller: its Scaffolder runs each template as a unique task and is an imperative run-once tool, its Kubernetes plugin matches entities to cluster objects by label, and no Backstage document that was read describes an operator pattern. The nearest thing is the community TeraSky Kubernetes Ingestor, a sync loop in the Backstage backend that ingests Crossplane claims and kro instances into the catalog ([[findings/the-backstage-scaffolder-is-a-one-shot-task-runner-and-the-nearest-operator-style-integration-is-a-third-party-plugin]], [[examples/the-terasky-kubernetes-ingestor-ingests-crossplane-claims-and-kro-instances-into-the-backstage-catalog]], [[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]).

Score and Radius let a developer describe a workload and abstract backing resources such as a database, leaving the implementation to a platform team, and they differ in whether anything keeps running afterward. Both are CNCF Sandbox projects (Radius accepted 2024-04-16, Score 2024-07-08), which confirms membership in the foundation and says nothing about production readiness. Radius is pre-1.0, its changelog still lists breaking changes, its four listed maintainers are all Microsoft employees, and only its newest minor channel (0.62 as of 2026-10-27) is supported; Score's maintainers span four employers and its sandbox application names Humanitec as sponsoring company. The Radius and Score documentation sites were not read, so what each does rests on repository files and one third-party review ([[findings/radius-and-score-are-both-cncf-sandbox-projects-per-the-landscape-file-and-both-passed-sandbox-votes]], [[findings/all-four-radius-maintainers-are-microsoft-employees-and-only-the-newest-minor-channel-is-supported]], [[findings/score-maintainers-span-four-employers-and-the-sandbox-application-names-humanitec-as-sponsoring-company]], [[comparisons/score-versus-radius-as-developer-facing-workload-abstractions]]).

Teams with large Terraform estates have a way to join this model without rewriting: tofu-controller, a community project under `flux-iac` that was previously the Weave TF-Controller, runs Terraform and OpenTofu inside a reconcile loop, keeps state in Secrets, and makes apply wait on Git approval. As of 2026-11-26 it was actively released, with v0.17.0 (2026-11-16) removing the `v1alpha1` API, whereas the alternative terraform-operator has had no release since May 2024 and is effectively single-maintainer, though the dossier found no deprecation notice ([[findings/tofu-controller-is-community-maintained-under-flux-iac-and-v0-17-0-removed-the-v1alpha1-api]], [[findings/terraform-operator-has-had-no-release-since-may-2024-and-is-effectively-single-maintainer]], [[decisions/run-existing-terraform-in-the-cluster-with-tofu-controller-or-terraform-operator-or-model-resources-natively-in-crossplane]]).

KRM functions deserve a note because they are the other way platforms generate resources. The KRM Functions specification in the Kustomize repository says a function must be implemented as a container that reads a `ResourceList` on stdin and writes one on stdout, and a non-zero exit code signals failure. It is a client-side standard decoupled from the cluster. kpt and Kustomize can run functions without containers only through opt-in exec extensions (`--allow-exec` for kpt, and `--enable-alpha-plugins` with `--enable-exec` for Kustomize) that both projects' documentation discourages as insecure, and kpt containers get no network and no host filesystem by default. The container requirement is why moving Helm inflation into functions needs a container runtime that laptops, CI, and Argo CD often lack. The dossier did not examine WebAssembly runtimes, so their absence is not established ([[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]], [[findings/kpt-and-kustomize-run-functions-without-containers-only-through-opt-in-exec-extensions-that-both-docs-discourage]], [[findings/kpt-containers-get-no-network-and-no-host-filesystem-by-default]], [[decisions/run-a-krm-function-as-a-container-or-as-an-exec-binary]], [[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]]).

What do the differences add up to? Tools agree on the principles and differ on defaults and escape hatches. In-cluster delivery tools check often and correct quickly. External-API controllers check rarely because observation costs money. Argo CD ships with destructive actions off, Flux exposes explicit switches, and Crossplane scopes behavior with policies. Any of them can be configured into the failure modes of section 10, and any of them can be adopted safely in stages: observe first, correct selectively, and enforce broadly with documented ignore rules ([[decisions/staged-adoption-of-automated-drift-correction]]).

## 12. Where the series goes next and what to carry forward

This part gave you the five principles and the design rules that follow from them. The later parts in the series build on them. The next parts move down into the Kubernetes Resource Model and API machinery, which is the shared substrate that makes the uniform contract possible: type and endpoint coordinates, CRDs, the split between spec and status, server-side apply, and admission. After that, the series opens the controller itself, covering informers, work queues, finalizers, owner references, and conditions, which are the mechanics behind most of the failures in section 10. Later parts cover abstraction layers, such as managed resources, composite resources, compositions, and kro resource graphs, and give Flux and Crossplane their own ramp-ups.

Here is what to carry forward. First, treat the spec as the contract and anything outside it as unmanaged. Second, remember that events are hints and state is truth, so any logic that depends on seeing every event is a bug waiting for a restart. Third, expect convergence and not instant completion, and read status conditions to tell working from ready. Fourth, remember that continuous correction is a policy: every drift-correcting tool needs an owner for each field, a pause for incidents, a deliberate answer on deletion, and an interval chosen for the cost of the thing it checks. Fifth, remember that pull-based delivery moves credentials and trust, and does not remove them; the agent is a powerful identity that deserves the same scrutiny as the pipeline it replaced.

Finally, hold the wiki's own caveats in mind. Adoption evidence for the provisioning and composition layers is thin and self-reported, the most detailed fleet evidence is a single self-reported Flux account, the Argo CD and Flux adopter lists name organizations without write-ups, no organization says it runs sharded Flux (Cozystack publishes sharding design targets and no measurements), kro has no benchmark or named production adopter, much of the other-tool evidence is documentation read on a default branch and not a pinned release, Radius and Score rest on sandbox listings and partial reading, and the pitfalls rest on a growing but still small set of first-party postmortems (Skyscanner, Reddit, Spotify, OpenAI, Jetstack, Neon, Zalando), all self-reported, plus individual issue reports. The defaults that the 2026-11-26 pass verified now carry version labels, but the Cluster API items were read at a release candidate and should be rechecked at v1.15.0 final. The principles are well established, and the specific numbers still need checking against the versions you run.
