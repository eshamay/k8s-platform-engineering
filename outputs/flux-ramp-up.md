# Flux Ramp-Up: GitOps Toolkit Architecture, Operation and Design Principles

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) but have not yet worked with controllers, API machinery or GitOps agents in depth<br>
> **Purpose:** Teach how Flux works from first principles, where it fails in practice, how it compares with neighboring tools, and which of its design choices are worth copying<br>
> **Status:** Active<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** [[entities/flux]], [[concepts/gitops-pull-based-delivery]], [[sources/research-flux-deep-dive]], [[concepts/scale-and-sharding]], [[comparisons/flux-versus-argo-cd-architecture]] and the other wiki pages listed under Further reading<br>

## 1. What Flux is and who uses it

Flux is a GitOps tool that runs inside a Kubernetes cluster. You tell it where a set of manifests lives, in a Git repository, an OCI registry (a registry that stores artifacts in the Open Container Initiative artifact format, the same registry format container images use), a Helm repository or an object-storage bucket, and it keeps the cluster matching what it finds there. It does this continuously. If someone edits a live object by hand, Flux notices on its next pass and puts the object back. If someone deletes a manifest from the source, Flux can remove the corresponding object from the cluster. The definition of the underlying idea, set out in [[concepts/gitops-pull-based-delivery]], is that the whole desired state is written down declaratively, stored in a versioned and immutable place, and applied by software agents instead of by people or pipelines running commands.

Two words in that definition carry most of the weight, so it is worth unpacking them now. "Declarative" means you describe the end state you want, such as "this Deployment has three replicas and runs this image", and you leave the steps to the system. The alternative, "imperative", means you issue actions, such as `kubectl scale` or a shell script that runs `helm upgrade`. [[concepts/declarative-vs-imperative]] covers the spectrum. "Pull" means the agent lives inside the target cluster and fetches desired state, instead of an outside CI server pushing changes in. The OpenGitOps working group states four principles: the desired state is declarative, it is stored versioned and immutable, agents pull it automatically, and agents continuously observe the real state and try to apply the desired one. The last two principles are what separate GitOps from a CI pipeline that happens to read YAML from Git. A pipeline that pushes once and never looks again does not qualify.

Who uses Flux? The Flux project's adopters page lists organizations that include Cisco, SAP, Kong, Grafana Labs, Sonatype, Maersk, Volvo Cars and Axel Springer, though it gives no per-entry detail. Some secondary descriptions say the page lists "more than 200 organizations", but that number does not match the source: the data file behind the page contains 127 `name:` lines, a few of which may not be companies, and the page itself describes the list as a selection of organizations that self-identified as using any of the Flux projects in production. Read the count as roughly a hundred and a quarter self-reported adopters, not as a measured market share ([[sources/research-flux-deep-dive]], [[entities/flux]]). The data file does let you name some entries, for example Xenit, Sortlist, Tietoevry, Nexxiot, SoulCycle and Luma Health, but the data file carries no migration story, incident report or measurement for any of them, so what those organizations do with Flux and how well it works is not documented ([[examples/the-flux-adopters-data-file-lists-xenit-sortlist-tietoevry-nexxiot-soulcycle-and-luma-health-among-others-with-no-write-ups]]). Argo CD keeps an equivalent self-reported file, `USERS.md`, which holds 452 numbered entries (the file runs to 461 lines, probably because of header lines), naming Adobe, IBM, Intuit, Red Hat and Tesla among others. The two lists are the same kind of evidence, a roll call that organizations add themselves to, and neither gives outage information, so the larger Argo CD list says something about visibility and nothing about reliability ([[examples/the-argo-cd-users-file-lists-452-self-reported-adopters]]).

The one adopter with a detailed public account in the sources is Morgan Stanley. A write-up by the Flux team, based on a FluxCon talk, reports "over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources", and says the firm moved to Flux from push pipelines that suffered from drift and made cluster rebuilds fragile ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]). Because that account was written about the adopter by the project and recounts the adopter's own talk, it is self-reported evidence, not an independent audit. No independent postmortem of a Flux outage and no neutral benchmark against Argo CD appear in the sources behind this document, and the caveat recurs wherever it matters. The Flux, Argo CD, Config Connector and ACK issue trackers and release notes contain individual reporter issues and reproductions, but no named organization with a date and an outage impact ([[findings/the-o3-pass-found-no-flux-postmortem-and-no-new-named-gitops-outage-and-the-ack-3152-and-3153-reproductions-ran-on-kind-with-moto]], [[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]). Web searches for such reports returned little, so the absence is weak evidence and does not prove that no such incident has happened.

The absence is specific to Flux, though, because a primary, organization-written postmortem exists for a pull-based GitOps outage on the neighboring tool. Skyscanner, a travel search company, published an account of 25 August 2021, when an engineer merged a templating change that was meant to alter no behavior, the change reached every region at once, and Argo CD reconciled each cluster against a configuration that listed no valid namespaces and deleted all 478 of its services within about half an hour. Skyscanner had skyscanner.net serving from a single region by roughly 20:30 GMT and restored the rest over the next two days, and the post's own summary is that Argo CD did this "ultimately because we told it to" ([[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]]). Flux was not involved, and the post does not say which Argo CD sync options were set, so it is evidence about what a faithful pull-based reconciler does with a bad desired state, and not evidence about Flux's defaults. Section 11 returns to it.

The thesis of this ramp-up is that Flux is a set of single-purpose, level-triggered Kubernetes controllers that pull desired state from Git, OCI or Helm sources and converge clusters with server-side apply, and that its design choices (composable controllers, pull delivery, inventory-based pruning, and explicit health and ordering) form a model worth borrowing when you design platforms of your own. The rest of the document earns that claim one layer at a time.

## 2. Mental model: Flux as Kubernetes controllers over KRM objects

To understand Flux you need three ideas that are not specific to Flux: the Kubernetes Resource Model, controllers, and the level-triggered reconcile loop.

The Kubernetes Resource Model, usually shortened to KRM, is the convention that everything in Kubernetes is an object with an identity, a `spec` and a `status`. The `spec` records what a user wants. The `status` records what a controller observed. The wiki's page on the [[concepts/spec-status-split]] explains that users and GitOps tools own `spec`, while controllers own `status`, and the API server enforces the split through a `/status` subresource. This sounds like bookkeeping, but it is the reason a GitOps tool can write a HelmRelease and then read back, from the same object, whether the release succeeded.

A controller is a program that watches objects through the API server and acts to make reality match their `spec`. The Kubernetes documentation calls controllers non-terminating control loops that move current state closer to desired state ([[concepts/reconciliation-loop]]). A Deployment controller makes ReplicaSets match a Deployment. Flux's controllers do the same trick on a higher level, except that the "reality" they converge is the contents of other objects in the cluster, and the "desired state" comes from outside the cluster. Because the cluster's API server, its storage (etcd) and its controller convention have no inherent tie to Pods, the same machinery can manage any declaratively described thing. [[concepts/universal-control-plane]] names this idea, and Flux is an example of using it for delivery.

The third idea is level-triggered reconciliation. An edge-triggered system reacts to an event, such as "a Pod was deleted". A level-triggered system reacts to the current state, such as "three replicas are desired, two exist". If a level-triggered controller misses an event, the next pass still converges, because it recomputes what to do from the state it can see ([[concepts/level-triggered-vs-edge-triggered]]). The wiki records the Kubernetes design stance as "Controllers are level-based to maximize fault tolerance", with watch events used as hints that make the loop faster, never as the source of correctness ([[decisions/events-as-hints-state-as-truth]]). Flux applies this literally. A Kustomization is re-checked on a timer, and events such as a new source revision are an optimization that skips the wait.

Level triggering has three consequences that recur through this document. First, reconcilers must be idempotent, meaning that running them twice leaves the system in the same state as running them once ([[concepts/idempotency]]). Second, the system is eventually consistent. Kubernetes does not promise that the gap between desired and actual state closes instantly, only that it keeps working toward the latest declared state ([[concepts/eventual-consistency-and-convergence]]). Third, the loop is relentless. It will revert intentional manual changes as readily as accidental ones, which [[findings/continuous-loops-override-intentional-changes]] calls the main operational lesson for platform teams.

Finally, Flux sits in the delivery layer of the tooling landscape. The wiki's landscape page ([[concepts/tooling-landscape]]) sorts tools into delivery (get manifests into a cluster and keep them there), provisioning (turn custom resources into cloud API calls) and platform or portal layers (what developers see). Flux and Argo CD are delivery tools. Crossplane, Config Connector, ACK and Cluster API are provisioning tools. Many comparisons go wrong by pitting a delivery tool against a provisioning tool, and section 13 returns to this.

## 3. The GitOps Toolkit: source, kustomize, helm, notification and image controllers

Flux is built from the GitOps Toolkit, which the Flux documentation describes as "a set of specialized tools and Flux Controllers; composable APIs; reusable Go packages for GitOps" ([[examples/flux-splits-gitops-into-single-purpose-controllers]]). Instead of one large operator, Flux ships several small controllers, each of which reconciles its own custom resource definitions (CRDs, the objects that extend the Kubernetes API with new kinds). The controllers communicate only through those custom resources.

The source controller fetches content from outside the cluster. It handles the kinds GitRepository, OCIRepository, HelmRepository, HelmChart and Bucket, fetches "on-demand and on-a-schedule", and packages the result as an archive (tar.gz or yaml) that other controllers read from inside the cluster. The consequence is that downstream controllers never talk to Git themselves. If you decide to move from Git to an OCI registry, you change the source object and leave the delivery objects alone ([[sources/research-flux-deep-dive]]).

The way the source controller serves those archives explains several behaviors that otherwise look odd. It runs an in-process HTTP file server, and its `main.go` starts that server only after the manager has won leader election, with a source comment that reads "Start the artifact server if running as leader". A readiness check named `leader-election` returns "manager is not the leader" on every replica that has not won the lease, so a standby never becomes ready, and the sharding page says so directly: "Standby source-controller replicas stay not ready by design, because only the leader serves artifacts." The stock manifest runs a single replica with the Recreate strategy, passes `--enable-leader-election` and `--storage-path=/data`, and declares both of its volumes as `emptyDir`. The artifact defaults in the shared runtime package are a one-minute retention time and two records kept after garbage collection. No source states where `/data` maps, but the stock manifest declares only `emptyDir` volumes, which suggests it maps to one of them. That would mean artifacts do not survive a pod restart and are rebuilt on the next reconcile. If that holds, a source-controller restart is a window with no artifact server and probably an empty store, and a platform that rolls the controller often or runs it on evictable nodes should expect dependents to wait. The GitRepository specification supports the general point by saying an artifact can "disappear from the storage due to e.g. the source-controller Pod being evicted". The sources consulted do not say how dependent controllers behave in that window or what the default lease durations are. Flux's vertical-scaling page does recommend persistent volumes in place of `emptyDir` for artifact storage so that artifacts survive restarts, which is the documented way to avoid the empty store after a restart ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]], [[findings/the-stock-flux-source-controller-keeps-artifacts-in-an-emptydir-with-one-minute-retention-so-a-restart-rebuilds-them]], [[decisions/single-replica-versus-leader-election]]).

The kustomize controller reads an artifact from a source, builds it with Kustomize (a template-free tool that customizes plain YAML with overlays and patches, described in [[entities/kustomize]]), and applies the result to the cluster. It also handles decryption of secrets with SOPS (a tool that encrypts the values in a file) using age, OpenPGP or cloud KMS keys, post-build variable substitution, health assessment, ordering, garbage collection and ServiceAccount impersonation. The helm controller does similar work for Helm releases. Helm, the Kubernetes package manager ([[entities/helm]]), normally runs as a command on a laptop or CI runner. Flux's helm controller instead uses the Helm SDK directly, so there is no in-cluster Helm server of the kind Helm 2 required (it was called Tiller), and a HelmRelease object declares what you want the SDK to do.

The notification controller works in two directions. Providers push events to chat systems and other endpoints, Alerts choose which events to send by severity and by involved object, and Receivers accept webhooks from Git hosts, registries and CI so that reconciliation starts at once instead of waiting for the next poll ([[examples/flux-notification-receivers-start-reconciliation-without-waiting-for-the-poll-interval]]). The image automation controllers scan registries for new tags and write the chosen tag back into Git, which section 9 covers.

The API types are published as Go packages, including `github.com/fluxcd/pkg/apis/meta`, and the controllers are ordinary controller-runtime programs, so anyone can read Flux objects with a standard client. That is a quiet but important property. A toolkit whose objects are plain Kubernetes objects can be observed with kubectl, queried by dashboards, composed by other controllers, and tested the way any other API is tested.

There is one more piece worth naming. The Flux Operator, a ControlPlane project, installs and manages Flux through a FluxInstance resource, so the Flux controllers themselves become declaratively managed objects, and it can also declare shards ([[entities/flux-operator]]). Separately, `flux bootstrap` installs Flux and commits its own manifests to the repository so that Flux manages itself from then on ([[concepts/gitops-pull-based-delivery]]).

## 4. Sources and artifacts: Git, OCI, Helm and Bucket, and choosing Git versus OCI

A source object tells the source controller where to fetch from and how often. Here is a minimal GitRepository, followed by the Kustomization that consumes it. The pair is the smallest useful Flux configuration.

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: platform-config
  namespace: flux-system
spec:
  interval: 5m
  url: https://git.example.com/platform/config
  ref:
    branch: main
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: platform-config
  path: ./apps/production
  prune: true
```

The first object asks the source controller to check the repository every five minutes and publish an artifact whenever the branch tip changes. The second asks the kustomize controller to take the `./apps/production` directory from that artifact, build it, apply it, and re-check the result every ten minutes. The two objects are decoupled. The Kustomization does not know that the artifact came from Git, only that a source named `platform-config` produced one. This is what the Flux deep dive means when it says a team can change where manifests come from without changing how they are applied. The URL, names and intervals above are illustrative.

The four source kinds fit different situations. Git is the familiar choice: review happens in pull requests, history is the audit trail, and every engineer already knows the workflow. OCI registries store the same manifests as immutable, optionally signed artifacts. Helm repositories serve packaged charts. Buckets, meaning S3-style object storage, serve a directory of manifests. Morgan Stanley moved its source of truth from a self-hosted Git provider to S3 buckets, which the write-up gives as an availability and compliance choice, and it lists OCI artifacts as roadmap work ([[decisions/git-versus-oci-as-the-canonical-source]]).

The choice between Git and OCI is open in the wiki's sources, and the decision page frames it without resolving it. Pulling directly from Git gives the simplest mental model and a review workflow people already use. But each cluster then needs network access and credentials to the Git host, and branches and remote references are mutable. Pulling signed OCI artifacts decouples source control from deployment control. CI builds and signs the artifacts, pushes them to a registry, and clusters pull only what they can verify. The cost is an extra build step and registry infrastructure. ControlPlane's D2 reference architecture takes this path for regulated, multi-tenant fleets: three repositories (fleet, infrastructure and applications) are built and signed by CI, each cluster runs a FluxInstance, and ResourceSet templates generate per-tenant resources. ControlPlane summarizes the effect as having "decoupled source control from deployment control, while improving auditability and reducing risk" ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]). The claim is the vendor's own and no independent source corroborates it, so treat it as a design rationale, not a measured result.

The signature story is one place where the two main tools differ on documented features. The OCIRepository specification says a new artifact is archived "When the current OCIRepository digest differs from the latest fetched digest", and its `.spec.verify` field can "enable the verification of Cosign or Notation signatures". Cosign and Notation are two signing tools for OCI artifacts. Keyless verification, which proves who signed an artifact through a short-lived identity from an OpenID Connect provider and not through a long-lived key you must guard, matches identities with `.matchOIDCIdentity`, and a Sigstore trust root can be pinned with `.spec.verify.trustedRootSecretRef`. The Flux OCI cheatsheet adds a useful rule of thumb: "Using OCI instead of Git is particularly useful when the Git repository doesn't contain the final Kubernetes manifests." Argo CD also accepts OCI images as an application source. Its page expects an image with a single layer, and an OCI ApplicationSet generator polls every 3 minutes by default. The Argo CD documentation, however, describes no signature verification for OCI sources. Its source-integrity page covers Git commit signatures made with GnuPG keys, and the OCI page contains no mention of signing, cosign or verification. That is a statement about the documentation, not proof the feature is absent from the code, and it comes from documentation on the main branch rather than a pinned release. No independent security review or measured benefit of signed OCI over Git exists for either tool in the sources, and neither project's documentation gives registry rate-limit guidance, so the case for OCI rests on the design argument above ([[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]]).

A related hazard applies whichever source you choose. If a manifest points at a moving remote reference, such as a Helm chart tag that can be re-pushed or a Kustomize remote base at `HEAD`, the same commit can render differently over time. The OpenGitOps requirement that desired state be versioned and immutable assumes that a revision identifies exactly one desired state, and a floating reference quietly breaks that assumption ([[findings/mutable-remote-references-change-what-a-commit-renders]]). Pin remote references to tags or digests, and change them through reviewed commits.

## 5. Kustomization and HelmRelease: the reconcile loop, intervals, retries and server-side apply

The Kustomization and the HelmRelease are where the work happens, so their timing and apply behavior deserve careful attention.

Every `spec.interval` (a field the Kustomization and HelmRelease references both mark as required, with a recommended minimum of 60 seconds, as the note below explains), the kustomize controller fetches the artifact, builds the manifests, applies them with server-side apply and detects drift. If a run fails, `spec.retryInterval` sets the delay before the next attempt, defaulting to the value of `interval`. `spec.timeout` limits the time spent on build, apply and health checks in one run. Jitter, which is a small random offset added to each timer so many objects do not fire at the same instant, spreads many Kustomizations so they do not all hit the API server together. It is on by default: the shared Flux runtime package perturbs every requeue by up to plus or minus 5 percent, set with `--interval-jitter-percentage` on kustomize-controller and helm-controller, so a ten-minute interval actually fires somewhere between 9.5 and 10.5 minutes, and a value of 0 or of 100 or more turns the jitter off ([[findings/flux-controllers-jitter-reconcile-intervals-by-plus-or-minus-5-percent-by-default]]). `spec.suspend` pauses both reconciliation and drift correction, and an annotation can request a manual reconcile ([[examples/flux-kustomization-interval-and-retry-interval-set-the-loop-timing]]). Reconciliation also starts at once when the source revision or relevant metadata changes, so the interval is a safety net and a change is picked up sooner.

A note on defaults, because Flux's own documentation is inconsistent here. The Flux concepts page says reconciliation "runs every five minutes by default", but the Kustomization reference calls `.spec.interval` "a required field" and says the minimum value should be 60 seconds, and the HelmRelease reference also calls it required. In the kustomize-controller source, the Kustomization custom resource type marks the field required, with only a duration-format pattern and no default value. A required field has no controller-side default, so a manifest that omits `interval` is rejected and never quietly falls back to five minutes. The 60 seconds is a recommendation phrased as "should" in the prose, and nothing in the type enforces it. The only default is on the `flux create` command, whose global `--interval` flag defaults to one minute and applies only when the command generates a manifest for you. The history of the five-minute sentence is partly recoverable. In the Flux website repository the concepts page read "every one minute by default" in February 2022, and a documentation commit by Stefan Prodan on 2022-08-10, titled "Add OCIRepository docs", replaced it with "every five minutes by default". The commit message carries only a sign-off, no linked issue or pull request explains the change, and no controller change accompanied it, so the reason is unknown. A code comment in the jitter package uses "requeue every 5 minutes" as a worked example, which could be the origin of the figure, but no source says so. The practical consequence is that the drift-correction latency you get is whatever you wrote in the manifest, give or take the jitter, so set an interval explicitly on every object ([[findings/the-flux-concepts-page-five-minute-sentence-replaced-one-minute-in-an-august-2022-docs-commit-with-no-stated-reason]], [[findings/the-flux-concepts-page-says-five-minutes-by-default-but-the-kustomization-and-helmrelease-references-require-the-interval-and-set-no-default]], [[entities/flux]]).

Here is a fuller Kustomization showing the common operational fields.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: team-a-apps
  namespace: team-a
spec:
  interval: 10m
  retryInterval: 2m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: team-a-repo
  path: ./production
  prune: true
  wait: true
  serviceAccountName: team-a-reconciler
```

Reading it from the top: re-check every ten minutes; after a failure, try again after two minutes instead of waiting for the full interval; give each run five minutes; use the `production` directory from the team's repository; delete objects that have disappeared from the source; wait for the applied objects to become healthy before reporting Ready; and perform every write as the named ServiceAccount. The last line matters more than it looks, and section 8 explains why.

Why does Flux apply with server-side apply (SSA)? In the older client-side apply, the kubectl client computes a three-way merge using a `last-applied-configuration` annotation on the object. In server-side apply the API server merges a partial object into the live one and records, for each field, which manager owns it in `metadata.managedFields` ([[concepts/server-side-apply-and-field-ownership]]). The comparison page ([[comparisons/client-side-apply-versus-server-side-apply]]) lists the benefits: no annotation size cap that large CRDs exceed, conflicts that are detected instead of silently lost, and merge behavior defined by schema markers. SSA reached general availability in Kubernetes 1.22. For a GitOps agent the key benefit is that it can co-manage an object with other actors. Flux owns the fields it sets, an autoscaler can own `replicas`, and the API server knows who is who.

Flux uses SSA in two ways. It applies with SSA, and it runs an SSA dry run on each interval to detect drift: the server computes what would change if the manifest were applied, and a non-empty answer means the live object has diverged. This is elegant, because the diff is computed by the same server logic as a real apply, so server defaults are not mistaken for drift. [[findings/diff-is-not-apply-server-defaults-look-like-drift]] shows the contrary case in Argo CD, whose default diff compares inside its own process and therefore reports server-defaulted fields as differences until Server-Side Diff is enabled.

The HelmRelease adds Helm's own lifecycle. It covers `dependsOn`, install and upgrade remediation (retry, roll back or uninstall on failure), optional Helm tests, `valuesFrom` to pull values from ConfigMaps and Secrets, `chartRef` to an OCIRepository or HelmChart, CEL health checks, and a CRD policy ([[sources/research-flux-deep-dive]]). Its status records an audit trail alongside machine-readable health. The conditions are `Ready`, `Reconciling`, `Stalled`, `Released` and `TestSuccess`, and fields such as `observedGeneration`, failure counters, `lastAttemptedRevision` and `lastHandledReconcileAt` say what the controller tried ([[examples/flux-helmrelease-status-records-attempts-and-health]]). The reading rules are simple. `Ready` is the headline. `Reconciling=True` is normal progress. `Stalled` means the release will not advance without a change. And an `observedGeneration` lower than `metadata.generation` means a spec change is still waiting to be processed ([[concepts/conditions]]). Remember that a suspended resource keeps its last condition and can look healthy while doing nothing.

Helm drift detection is off by default. A HelmRelease has `spec.driftDetection.mode` with `disabled` (the default), `warn` (emit events only) and `enabled` (correct the drift). Flux's older drift-detection configuration page, which serves only as a pointer, says that drift detection became a per-HelmRelease option in Flux v2.2.0 and stopped being a controller-wide feature gate. The sources include no release note for that change, so treat the version number as the pointer page's statement and not as a figure taken from the release itself. This three-step ladder is a model for staged adoption, which section 10 returns to.

## 6. Ordering, health checks and dependsOn

Kubernetes applies objects concurrently and lets failures retry until dependencies appear. For many cases that is fine. But some orderings are not self-healing in a pleasant way: a custom resource applied before its CRD exists fails with "no matches for kind", and an application started before its database operator exists may log errors for minutes. The wiki treats CRD ordering as a recurring theme ([[findings/custom-resources-applied-before-their-crd-exists]], [[examples/servicemonitor-no-matches-for-kind-in-helm-and-argo-cd]]).

Flux handles ordering with three tools. `dependsOn` makes one Kustomization (or HelmRelease) wait until the objects it names are Ready. `wait` and `healthChecks` define what Ready means, so readiness covers the applied objects actually becoming healthy, and not only the apply call returning. Optional CEL expressions (a small expression language, the same one the API server uses for validation) allow custom readiness conditions. The documented pattern for CRDs is to put the CRD-providing controllers in one Kustomization and the custom resources in a second that depends on the first ([[examples/flux-dependson-and-health-checks-gate-rollout]]):

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: monitoring-config
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: platform-config
  path: ./monitoring/config
  dependsOn:
    - name: monitoring-operator
  prune: true
```

This Kustomization applies the monitoring custom resources, but only after the Kustomization named `monitoring-operator` reports Ready. If that first Kustomization uses `wait: true` or health checks, "Ready" means the operator Deployment is actually available, so the CRDs and their controller exist. The practitioner blog summarized in the wiki's example page on `dependsOn` and health checks recommends layering infrastructure, platform and applications this way. The important insight, stated in the wiki's example page, is that Flux does not abandon eventual consistency to get ordering. It adds health-checked dependencies so that the retry-until-ready behavior happens in a controlled sequence instead of as a burst of transient errors.

Health judgment is a harder problem than it looks, because Flux has to decide whether arbitrary custom resources are healthy. It relies on kstatus, a Go package in `sigs.k8s.io/cli-utils` that computes a generic status for any resource that follows the status conventions, using `observedGeneration` and the `Ready`, `Reconciling` and `Stalled` conditions ([[entities/kstatus]]). The weakness is that kstatus only works where conventions are followed. It evaluates a resource in a fixed order: deletion first, then a comparison of the top-level `status.observedGeneration` with `metadata.generation`, then the `Reconciling` and `Stalled` conditions, then type-specific rules for built-in kinds, then a fallback that looks for a `Ready` condition. A kind it has no rule for and that publishes no `Ready` condition falls to the unknown-resource strategy, which the kstatus README states as "assume they are always reconciled" ([[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]]). Notice also that `Reconciling` and `Stalled` are abnormal-true conditions, present and `True` only when something is in flight or wrong, so a controller that is not running at all looks the same as a healthy one, and the README says as much ([[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]).

The wider ecosystem has not settled which polarity authors should choose. The Kubernetes API conventions recommended abnormal-true at one time, switched to positive in February 2020, and since June 2020 say that neither can be recommended as a general rule, while kstatus's README still describes the abnormal-true pair. Flux sidesteps the argument by publishing `Ready` together with `Reconciling` and `Stalled` ([[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]]). Cluster API issue 9299 shows the failure: a new object with `observedGeneration` set but no conditions yet can look ready, so Flux can start dependents too early. The proposed fix of defaulting `observedGeneration` to `-1` was closed as not planned in May 2025, partly because Cluster API is moving from `Ready` to `Available` and partly because Flux added CEL health checks for Cluster API ([[findings/premature-readiness-in-kstatus-based-tools]], [[examples/cluster-api-readiness-gates-flux-dependents]]).

The unknown-kind fallback raises a further worry that the sources leave open. The v1beta2 Cluster type, read at v1.15.0-rc.0, defines an `Available` condition and no `Ready` constant, and a search found no `Reconciling` or `Stalled` condition on it, so by the rules above a kstatus-style tool might treat a Cluster with `Available=False` as reconciled. That conclusion follows from two documented facts, the missing `Ready` condition and the kstatus fallback rule, but no source states it. No source shows kstatus run against a v1beta2 Cluster, and the result also depends on whether the Cluster controller writes a top-level `observedGeneration`, which no source documents. The lesson is general: generic readiness depends on every provider following one convention, and when a project changes its vocabulary, consumers need explicit per-kind checks again.

Argo CD faces the same problem and answers it differently. It orders a sync by phase (PreSync, Sync, PostSync), then wave number, then kind and name, and advances only when the current wave is healthy, and for custom resources it runs Lua scripts (small programs in the Lua scripting language that Argo CD embeds) over `status`, noting that "CRDs do not follow a consistent or standardized status format" ([[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]], [[examples/argo-cd-rolls-up-child-health-with-lua-checks]]). kro derives ordering from references between resources inside one graph, and Crossplane lets composition functions withhold dependents until observed state allows them ([[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]). The distinction is that Flux and Argo CD order objects that a pipeline or Git delivers, while kro and Crossplane order resources inside one abstraction.

The two delivery tools differ visibly in how they judge kinds that cloud-provider controllers publish. Flux has no per-provider health logic at all. A Kustomization's `healthChecks` accept built-in kinds, Flux kinds and "custom resources that are compatible with kstatus", `wait: true` checks everything the Kustomization applied, and for kinds that do not follow the conventions `healthCheckExprs` supply CEL expressions named `current`, `inProgress` and `failed`, while `dependsOn[].readyExpr` can replace the readiness test for a dependency with a CEL expression. A provider's own `Ready` condition therefore reaches Flux through kstatus's generic handling. The Flux CEL cheatsheet carries examples for Crossplane kinds, but a search of the page for Config Connector's `cnrm` group and for ACK's `services.k8s.aws` group found nothing, so a team delivering those kinds writes its own expressions.

Argo CD went the other direction. Its `resource_customizations` tree ships Lua scripts for whole provider groups: `cnrm.cloud.google.com`, `services.k8s.aws`, `crossplane.io`, `upbound.io`, `kro.run` and five `cluster.x-k8s.io` kinds, read at Argo CD v3.6.3. The ACK script maps `ACK.Terminal=True` to Degraded, `Ready=False` to Progressing and `Ready=True` to Healthy. The Config Connector script returns Progressing while `observedGeneration` is stale, Healthy on reason `UpToDate`, and Degraded on `UpdateFailed` or `DependencyNotFound`. Provider awareness has a cost, because Argo CD advances sync waves only when the current wave is healthy, so a provider object whose status a wildcard script mishandles blocks every later wave. Issue 30164 is the dated example, in which Config Connector kinds stayed Progressing because the script did not handle `status.healthy`, and issue 30373 shows the structural limit, since ACK conditions carry no `observedGeneration` and the built-in script can report Healthy before the controller has observed a spec change ([[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]], [[examples/argo-cd-issue-30164-config-connector-customize-kinds-stayed-progressing-because-the-health-script-did-not-handle-status-healthy]], [[examples/argo-cd-issue-30373-the-built-in-ack-health-check-reports-healthy-before-the-controller-observes-a-spec-change]]).

No source describes what Flux's kstatus does with ACK's abnormal-true `ACK.Terminal` condition, so whether a terminally failed ACK object looks failed or ready to Flux is open ([[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]], [[comparisons/health-and-readiness-models-across-tools]]). Flux issue 5855 shows the kstatus race on the Crossplane side: resources with no initial `Ready` condition read as ready, and the maintainers recommended a CEL expression on `observedGeneration` ([[examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression]]).

## 7. Drift, pruning, ignore rules and deletion policies

Drift is the gap between what the source says and what the cluster holds. It arises when a human edits a live object, when another controller rewrites a field, or when the API server fills in defaults. Flux's detection mechanism is the SSA dry run on each interval, so, as [[findings/drift-detection-latency-is-the-interval]] puts it, the worst-case detection latency equals the interval. Webhook Receivers shorten the time to notice new commits but do not change how often live drift is checked.

Pruning is the other half of convergence. With `prune: true`, objects that were applied earlier but are missing from the current source revision are removed. Flux knows which objects it applied through an inventory recorded in the Kustomization's `.status.inventory`, not through Kubernetes owner references ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). The distinction matters. Owner references link a child object to a parent in the same namespace so that deleting the parent cascades ([[concepts/owner-references-and-garbage-collection]]). A GitOps agent applies objects it did not create through a parent object, so it needs its own inventory plus a finalizer (a token in `metadata.finalizers` that holds an object in a deleting state until a controller finishes cleanup, see [[concepts/finalizers]]) on its own top-level object. The wiki's comparison of garbage collection mechanisms makes the same point for Argo CD, Crossplane and Cluster API ([[comparisons/how-tools-garbage-collect-owner-references-inventory-and-finalizers]]).

Prune is a double-edged switch. Without it, "Git is the only source of truth. Without prune, deleted manifests leave orphaned resources", in the practitioner blog's words, which quietly breaks the claim that Git describes the cluster ([[findings/without-prune-flux-leaves-removed-manifests-running-as-orphans]]). With it, a bad edit to Git can delete real objects, and for provider-managed resources a prune followed by a provider delete can remove cloud infrastructure ([[findings/unintended-deletion-through-prune]]). Flux's controls are an annotation, `kustomize.toolkit.fluxcd.io/prune: disabled`, that exempts a single object, and a deletion policy for the case where the Kustomization itself is deleted.

The `spec.deletionPolicy` takes four values. MirrorPrune, the default, follows the `prune` setting. Delete removes the deployed objects. WaitForTermination removes them and waits for the children to leave etcd, so while it waits it is held up by any finalizer its children carry. Orphan leaves them running, the GitOps equivalent of `kubectl delete --cascade=orphan` ([[examples/flux-kustomization-deletion-policy-chooses-between-mirror-prune-delete-wait-and-orphan]]).

It helps to know the three propagation modes that Kubernetes itself offers for deleting an owner. In the background mode, which kubectl has used by default since v1.20, the owner is deleted at once and the garbage collector removes dependents afterward in no guaranteed order. In the foreground mode the owner stays visible with a deletion timestamp until every dependent that sets `blockOwnerDeletion=true` is gone, so an owner can hang if such a dependent cannot be deleted. In the orphan mode the dependents lose their owner references and keep running unmanaged until someone deletes them. Argo CD prunes with foreground deletion by default and accepts all three modes through `PrunePropagationPolicy`, so the two tools differ in what a prune waits for as well as in what they delete ([[comparisons/background-foreground-and-orphan-propagation-modes]]).

The mechanics behind these four values come from the kustomize-controller source. Flux's own finalizer is named `finalizers.fluxcd.io`, and the reconciler adds it before doing any other work, because a finalizer can only be added while the object has no deletion timestamp, so adding it first avoids a race with deletion. When the Kustomization is deleted, the controller prunes its inventory only if a decision function says to. A suspended Kustomization or one with an empty inventory never deletes anything. MirrorPrune follows `spec.prune`, Delete and WaitForTermination always prune, and Orphan never does. The wait in WaitForTermination polls every 2 seconds and is limited by the Kustomization's own `spec.timeout`. If the wait fails, the controller logs an error, emits an event and removes its finalizer anyway, so a stuck child cannot hold the Kustomization forever, although the child stays behind under its own finalizers.

What to do about such a child matters, because the quickest fix is also the riskiest. A finalizer is usually the only record that something outside the object still needs releasing, so patching `metadata.finalizers` to empty makes the object vanish without performing the cleanup the finalizer guarded. Practitioner write-ups list the results as cloud storage that keeps billing, StatefulSets on shared storage at risk of corruption, and pods that keep running after their API object is gone, and the Kubernetes documentation advises against manual removal unless you understand the finalizer's purpose and have met it another way. The Kubernetes finalizers blog adds that forcing a namespace through its `finalize` subresource can leave orphan objects in a namespace that no longer exists, and that re-creating the namespace may bring them back. The safer order is to find the blocking finalizer, read the owning controller's logs or source, and repair the condition that keeps it from finishing, and to clean up the external resource by hand if you must force removal ([[findings/forcing-a-finalizer-off-skips-cleanup-and-can-leak-billing-resources-or-corrupt-data]], [[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]).

The controller does the same if the impersonated ServiceAccount has already been deleted: it logs the stale objects and finishes finalization. Because the wait stops at the Kustomization's timeout, it does not hold the Kustomization for every child finalizer indefinitely. This behavior is documented for the v1 API on the main branch, and the sources say nothing about older beta API versions ([[findings/flux-kustomization-uses-finalizers-fluxcd-io-and-removes-it-even-when-waitfortermination-times-out]], [[comparisons/finalizer-gated-teardown-across-argo-cd-flux-kro-and-cluster-api]]).

Ignore rules address the most common drift problem, which is a second writer that legitimately owns a field. A team runs Flux against workloads scaled by a HorizontalPodAutoscaler (HPA), and against CRDs whose `caBundle` is injected by cert-manager's cainjector (the cert-manager component that writes certificate authority bundles into CRDs). Flux reverts both. The Flux project's own blog tells of a SEV2 (a second-highest-severity production incident in the blog author's incident scale) in which Flux kept resetting replicas to a high value, the HPA kept lowering it, and the cluster autoscaler added and removed nodes in a loop, with "the two controllers ping-pong indefinitely" ([[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]]). According to that blog post, Flux then added a Kustomization `.spec.ignore` list of JSON Pointer paths with an optional target selector. The kustomize-controller specification documents the same two policies, so the behavior does not rest on the blog post alone. If another server-side-apply manager of the Apply type owns the field, Flux strips it from its own apply payload ("Strip"), which the specification describes as relinquishing the controller's ownership and leaves the field with the other manager. If Flux is the sole Apply-type owner, it copies the live value ("Adopt"), which the specification says "preserves the current value without reverting changes made by Update-type operations", so edits made with `kubectl patch` or `kubectl edit` survive. The specification also says "Changes to ignored fields alone do not trigger a reconciliation". The blog also says `flux diff` honours the rules, a claim that only the blog makes. The distinction between Apply-type and Update-type managers matters for choosing a policy, because a controller that writes with plain updates, such as Config Connector's `cnrm-controller-manager`, would be covered by Adopt and not by Strip. That reading follows from the specification and Config Connector's source, although neither project states it. Check the current Kustomization API for the exact field name and the release that introduced it, and remember that `driftDetection.ignore` on the HelmRelease and the per-object `ssa` annotation described below are separate mechanisms ([[decisions/force-conflicts-or-strip-or-adopt-when-two-controllers-co-own-a-field]]). There is also a per-object `kustomize.toolkit.fluxcd.io/ssa` annotation with values `Override`, `Merge`, `IfNotPresent` and `Ignore` ([[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]).

The price of ignoring is easy to forget. Git changes to an ignored field are no longer applied, so if a team later wants Git to set the replica count, nothing will do it ([[findings/ignoring-a-field-in-flux-or-argo-cd-means-git-changes-to-it-are-no-longer-applied]]). Ignore only fields that another controller rewrites on purpose.

Two more details from the specifications decide how safely you can use these rules. First, a Flux rule is scoped by its `target` selector, and the kustomize-controller specification says "Omitting the `target` selector causes the rule to match **all** objects managed by the Kustomization". A rule written for one Deployment's `/spec/replicas` that leaves the target out therefore exempts that path on every other object in the Kustomization too, and real drift there goes uncorrected without any signal. The safe reading is to put a target selector on every rule ([[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]]). Second, Argo CD's equivalent, `ignoreDifferences`, behaves differently by default. Its sync-options page says Argo CD uses the rules "just for computing the diff between the live and desired state", so an ignored field stops showing as OutOfSync but the next sync still applies the full manifest from Git and can overwrite the field, which looks like a revert loop even though the diff is clean. Setting the sync option `RespectIgnoreDifferences=true` makes the sync honor the rules, but the page adds that it is "only effective when the resource is already created in the cluster", so a first create still applies every field ([[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]], [[comparisons/flux-ignore-rules-versus-argo-cd-ignoredifferences-and-force-conflicts-for-drift-fights]]). Flux's rules act during drift detection and correction directly, which is the practical difference between the two. Config Connector adds a third variation worth knowing. Its `state-into-spec: Merge` mode copies live cloud state into unspecified spec fields, and because both Argo CD and Config Sync treat list fields as atomic they see those additions as drift from Git. The default is `Absent` for resources created from Config Connector 1.123.1 on, though objects created earlier may still carry `merge`, and Config Connector issue 837 reports Argo CD 2.7.6 repeatedly replacing `DNSRecordSet` objects until the default annotations were written out explicitly. That issue is a single user report ([[findings/config-connector-state-into-spec-merge-populates-unspecified-fields-that-argo-cd-and-config-sync-treat-as-drift-and-absent-is-the-default-from-1-123-1]], [[examples/config-connector-issue-837-argo-cd-2-7-6-kept-replacing-dnsrecordset-objects-until-the-default-annotations-were-added-explicitly]]).

Where does Flux sit among SSA conflict policies? Like Argo CD, it force-applies its own intent by default and then offers escape hatches. The Kubernetes maintainers argue that controllers should force conflicts on objects they own, while CD systems are "more like users" and should surface conflicts to humans. Kluctl takes a third route and decides per field: it overwrites changes from known interactive managers such as kubectl and k9s, leaves fields it lost to other managers alone, and exposes `kluctl.io/force-apply-field` for single fields ([[comparisons/ssa-conflict-policy-across-tools]], [[examples/kluctl-decides-field-level-conflicts-with-known-manager-heuristics]]). The wiki's decision page concludes that the sources do not settle the best default for platforms that run GitOps and in-cluster controllers on the same objects ([[decisions/force-conflicts-or-surface-them-to-humans]]). A second decision page lays out force against strip-or-adopt side by side and makes no recommendation, because no source or experiment compares them. It also notes the cost of the escape hatches: manager-scoped ignores depend on the other controller using server-side apply under a stable name, and a forced apply is not always enough, as a Kubernetes issue shows in which a forced apply could not revert an edited Service port ([[decisions/force-conflicts-or-strip-or-adopt-when-two-controllers-co-own-a-field]], [[examples/kubernetes-issue-130292-a-forced-server-side-apply-could-not-revert-an-edited-service-port]]).

## 8. Multi-tenancy, impersonation and security lockdown

Pull delivery changes the security picture. A push pipeline holds credentials for every environment it deploys to, so a breached build server exposes all targets. A pull agent needs only read access to the source and uses in-cluster identity to write ([[comparisons/push-versus-pull-delivery]]). But the agent becomes powerful itself. By default the kustomize controller applies with its own identity, which is cluster-admin, so anyone who can commit a manifest to a repository Flux watches can create anything the controller can ([[findings/without-lockdown-flags-a-flux-kustomization-applies-with-the-controllers-own-identity]]).

Flux's answer is impersonation. A Kustomization or HelmRelease can name a ServiceAccount in `spec.serviceAccountName`, and the controller performs every write as that account, so ordinary Kubernetes RBAC decides what the tenant's repository may create. Platform administrators then start the controllers with three flags: `--no-cross-namespace-refs=true`, which stops a tenant from pointing at sources in other namespaces; `--no-remote-bases=true`, which stops Kustomize from fetching remote bases that could smuggle in content; and `--default-service-account=default`, so objects with no `serviceAccountName` use the `default` account in the tenant's namespace. If that account has no RBAC, deployments simply fail until a Role and RoleBinding are added.

The `fluxcd/flux2-multi-tenancy` reference repository shows the pattern. A fleet repository has `clusters/` for per-cluster entry points, `policies/` for cluster-wide resources, and `tenants/` for the provisioning manifests the administrators own. Each tenant's repository carries a `base/` directory and `staging/` and `production/` overlays. The repository states that "Sharing namespaces between tenants is not supported, as it would break the isolation guarantees" ([[examples/flux-multi-tenancy-repository-isolates-tenants-with-service-account-impersonation]]). A manifest that tries to create a ClusterRole or write into another namespace is rejected by the API server, not by Flux.

Morgan Stanley's version adds a self-service onboarding platform. It checks the requester's entitlements, registers the service in a configuration management database, primes the new namespace with a GitRepository and a Kustomization, and scaffolds the team's repository. The firm relied on ServiceAccount impersonation with Kubernetes RBAC, so a team's Kustomization can only create what its ServiceAccount is allowed to create.

Secrets are the next security question, because a pull agent that reads a repository must somehow deliver values that should never sit in the repository in plain text. Flux's answer is built into the kustomize controller. The Kustomization specification says "The only supported encryption provider is SOPS", decryption runs inside kustomize-controller, and encrypted files must "leave `metadata`, `kind` or `apiVersion` in plain text" so the controller can still identify the object. The documented key types are age, OpenPGP, cloud KMS and OpenBao or Vault, plus a service-account mode described as secret-less authentication to cloud KMS services. The SOPS guide notes that the decryption key is needed even to verify a file, because of the SOPS message authentication code, and Flux also documents Sealed Secrets, which only the controller in your cluster can decrypt. Argo CD takes the opposite default. Its secret-management page says "We strongly recommend" populating secrets on the destination cluster with an operator, naming Sealed Secrets, External Secrets Operator, the Secrets Store CSI Driver and Vault Secrets Operator as examples. It cautions against plugins that inject secret values while Argo CD renders manifests, such as argocd-vault-plugin, for three stated reasons: "Argo CD stores generated manifests in plaintext in its Redis cache" (Redis is the in-memory store Argo CD uses for rendered manifests), secret updates become coupled to syncs, and the approach is "incompatible with the 'Rendered Manifests' pattern". The project says it will keep supporting generation-based secrets but will not prioritize new features for that style. The page does not mention SOPS or ksops at all, so it states no Argo CD position on them, and the sources describe no failure modes for either approach beyond the plaintext-field requirement. The decision page lays the three options side by side and makes no recommendation ([[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]], [[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]]).

Reach is a related question, because a pull model is only as pull-based as its layout. A central Argo CD instance targets remote clusters that are registered with it, so delivery to a fleet is a push from a hub even though each Application pulls from Git. A separate project, argocd-agent in the `argoproj-labs` organization, describes the inverse, "instead of your control plane reaching out to remote clusters, lightweight agents reach back to a central hub", with Managed and Autonomous modes, but the project publishes no maturity statement and no adopter write-up exists, so its maturity is undocumented. Flux can also reach a remote cluster, because a Kustomization accepts `.spec.kubeConfig`, whose `configMapRef` form the specification recommends as secret-less authentication, but the more common Flux layout runs a controller set in every cluster, as the D2 design does ([[findings/argo-cd-reaches-into-registered-clusters-from-a-hub-and-the-argocd-agent-pull-model-is-a-labs-project-of-unverified-maturity]], [[decisions/reach-spoke-clusters-from-a-central-argo-cd-hub-or-with-argocd-agent-pulling-from-the-spokes]]).

Two caveats are worth carrying forward. First, no incident report of tenant escalation appears in the sources, so the risk rests on documentation. Second, blast radius is a general property of control planes. [[findings/blast-radius-and-privilege-centralization]] observes that a controller concentrating authority is a target, whether it is Flux, a Cluster API management cluster, or a Crossplane provider with a shared cloud credential. The D2 design reduces the exposure further by removing cluster-to-Git connections altogether. A vendor blog about Argo CD says it isolates tenants with Projects, while Flux uses namespaces and RBAC, but that comparison is opinion and should be read as such ([[comparisons/flux-versus-argo-cd-isolation-ordering-and-interface-according-to-a-vendor-blog]]).

## 9. Use cases: fleet management, multi-cluster, image automation, replacing helm upgrade in CI

**Fleet management and multi-cluster delivery.** The strongest evidence is the Morgan Stanley case above: more than 500 clusters, per-tenant impersonation, intervals raised and concurrency tuned, a source of truth moved to S3, a central Grafana dashboard built from kube-state-metrics, and notification-controller events fed to developer tools so tenants can see the outcome of their own deployments. The company listed sharding, OCI artifacts and Flagger as roadmap items (the write-up names Flagger without describing it), so no production sharding numbers are published, and a targeted search found no organization that says it runs sharded Flux ([[sources/research-gap-g1-named-adopters]]). The same pattern generalizes. A fleet repository has a directory per cluster, each cluster's Flux instance points at its own directory, and shared bases carry what is common.

Flux also pairs well with Cluster API for fleet lifecycle. Cluster API is a SIG Cluster Lifecycle project where a management cluster reconciles Cluster, Machine, MachineDeployment and MachineHealthCheck objects into real clusters ([[examples/cluster-fleet-lifecycle-with-cluster-api]]). Flux can deliver those objects from Git and hold back dependent Kustomizations until the Cluster API objects report ready, which is exactly where kstatus and CEL checks mattered in section 6. The management cluster, as the wiki notes, concentrates authority and becomes a single point of failure.

**Image automation.** A team wants patch releases and CVE fixes to reach clusters without anyone editing a manifest, while keeping Git as the record. The image update guide describes the aim as to "automatically deploy application patches (CVEs and bug fixes), and keep a record of all deployments in Git history". Three objects split the job: an ImageRepository scans a registry for tags, an ImagePolicy picks one using semver (semantic versioning, where numbers like 1.4.2 encode major, minor and patch changes), calver (calendar versioning, where the version is a date such as 2026.11) or regex rules, and an ImageUpdateAutomation edits YAML at `$imagepolicy` marker comments, commits and pushes. The ordinary loop then fetches the new revision and applies it, so the cluster still changes only through Git. The multi-tenancy reference repository enables this only for the staging overlay ([[examples/flux-image-automation-commits-new-tags-to-git-and-the-reference-repo-limits-it-to-staging]]). The risk is that a loose regex or a wide semver range can promote a release nobody reviewed ([[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]]). The current specifications answer the API question: the spec pages for ImageRepository, ImagePolicy and ImageUpdateAutomation all use `image.toolkit.fluxcd.io/v1`, the ImagePolicy CRD lists `v1` as served and as the storage version, and the Go API directory still holds `v1beta1` and `v1beta2` packages. Both controllers' latest releases were v1.3.1, published 2026-11-20. The sources give no release notes saying when v1 graduated and do not state the storage version of the ImageUpdateAutomation CRD. The documentation described here is from the main branch, which may be ahead of the release a cluster runs, so check the installed version ([[findings/flux-image-automation-kinds-are-image-toolkit-fluxcd-io-v1-with-older-versions-still-in-the-api-directory]]).

The guide also names the promotion controls, and it stops at three. Production uses semver-selected release tags built by CI, while staging uses `branch-sha-timestamp` tags chosen by numerical or alphabetical policies. Setting `spec.git.push.branch` to a branch different from the checkout branch lets CI open a pull request, and the guide says "This way you can manually approve the image updates before they are applied on your clusters." A bad update is undone by narrowing the semver range, since "you can tell Flux to revert the image tag to a previous version". ImagePolicy also has a `digestReflectionPolicy` field whose documented default is `Never`. The guide prescribes nothing beyond those choices for keeping automatic updates out of production, and no third-party adopter write-up on staging-only or reviewed promotion exists in the sources, so the promotion policy adopters actually use is an open question ([[findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range]], [[decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation]]). One scale note belongs here as well: the documented sharding recipe deletes the image-reflector and image-automation Deployments from its shard sets, so image scanning stays on the default instance, as section 12 explains.

**Replacing `helm upgrade` in CI.** A Helm-heavy team runs `helm upgrade` from a CI job. A failed upgrade leaves the release in a bad state until someone notices, and nothing corrects the release if an operator edits a live object. The Flux guide for Helm users frames the alternative this way: "While the Helm client commands let you imperatively do things, Flux Helm Custom Resources let you declare what you want the Helm SDK to do automatically." A HelmRelease names a chart, supplies values inline or from ConfigMaps and Secrets, remediates failures by retrying, rolling back or uninstalling, optionally runs Helm tests, and can detect and correct drift ([[examples/teams-replace-helm-upgrade-in-ci-with-flux-helmrelease-objects]]). The deeper change is from a one-shot push to a continuous loop, which is the same difference the OpenGitOps principles draw.

**Delivering infrastructure custom resources.** Flux and Argo CD both deliver Config Connector, ACK and Crossplane objects from Git. This is the two-layer loop: the GitOps agent reconciles Git into the Kubernetes API, and a domain controller reconciles the API into reality ([[concepts/gitops-pull-based-delivery]]). On Google Cloud, Config Connector then acts with its own IAM service account, so developer permissions are decoupled from cloud rights, but anyone who can create a resource gains the controller's rights ([[examples/google-cloud-shops-deliver-config-connector-resources-from-git-while-the-controller-s-own-identity-makes-the-cloud-calls]]). Flux publishes no official document about Crossplane, kro, Config Connector, ACK or Cluster API beyond the generic mechanics, but individual reports are enough to describe how the combination behaves, and most of the reports are cautionary.

Start with what Flux does by default. It treats a Crossplane composite or a kro instance as any other custom resource: `healthChecks` and `wait` judge it through kstatus or CEL, and `dependsOn` waits on it. Resources that Crossplane or kro create from the composite are not applied by Flux, so they sit outside Flux's inventory. It follows that Flux needs no owner reference or tracking annotation on composites, in contrast to Argo CD, which needs owner references and tracking identifiers before it can track kro resources, but no Flux page states this, so treat it as an inference. No Flux or kro document describes using the two together ([[findings/flux-tracks-composite-resources-through-its-inventory-and-kstatus-or-cel-health-checks-and-documents-no-owner-reference-recipe-or-kro-guidance]], [[examples/kro-resources-need-owner-references-and-tracking-ids-to-be-tracked-by-argo-cd]]). A second writer is the usual trouble. kro issue 1290, open on 2026-11-26, reports external controllers changing fields on resources kro manages and kro resetting them on its next reconciliation. It is not a Flux report, but a Flux Kustomization that also sets fields on a kro-created resource would be one of those external writers, and that reading is an application of the issue rather than something a source describes ([[examples/kro-issue-1290-external-controllers-fight-kro-over-fields-and-kro-resets-their-changes]]).

ACK is the clearest case of delivery interacting with a provider controller, and the evidence is open issues from individual reporters, not maintainer-confirmed behavior. ACK issue 2361, opened on 2025-02-26, reports that ACK controllers resolve reference fields (the `*Ref` fields) and write the resolved value back into the custom resource, that Flux's server-side apply then restores the Git value, and that the controller's diff sees changed desired state, so at the 10-hour requeue the reporter saw unnecessary ECS redeploys. Setting `kustomize.toolkit.fluxcd.io/ssa: merge` did not help, and a maintainer suggested a fix modeled on a pull request in the eks-controller. ACK's runtime sends merge patches and records no server-side-apply field manager, which is consistent with the report ([[examples/ack-issue-2361-flux-server-side-apply-reverted-reference-fields-and-triggered-ecs-redeploys-at-the-ten-hour-resync]], [[findings/flux-server-side-apply-reverts-ack-reference-fields-that-the-controller-rewrote-according-to-issue-2361]]). The deletion side is sharper. ACK deletes the AWS resource when the Kubernetes object is deleted, and its documented lookup order for the deletion policy is the resource annotation `services.k8s.aws/deletion-policy`, then the namespace annotation, then the controller default, with the first match winning. ACK issue 3153, opened on 2026-11-09 against iam-controller v1.11.3 and open on 2026-11-26, reports that Argo CD prune, Flux Kustomization prune and a helm-controller upgrade each led to AWS deletion, with reproduction scripts, and that a controller-wide `retain` did not help because every chart-rendered resource carried `deletion-policy: delete`. Under the first-match rule that outcome is what the documentation predicts. The reproductions ran on kind with a mock AWS, and the account is a single reporter's, so treat it as a well-documented warning, not a postmortem. The practical reading is that a controller-wide `retain` is the weakest layer, so set `retain` on the resource itself or add an agent-side opt-out such as Flux's per-object `prune: disabled` annotation or Argo CD's `Prune=false` ([[examples/ack-issue-3153-pruning-a-custom-resource-from-git-deletes-the-aws-resource-irreversibly]], [[findings/ack-deletion-policy-resolves-from-the-resource-then-the-namespace-then-the-controller-default-and-one-reporter-says-chart-stamped-delete-defeats-a-controller-wide-retain]], [[decisions/protect-a-provider-managed-object-from-gitops-prune-with-a-provider-retain-policy-or-an-agent-side-prune-opt-out]]).

Config Connector adds installation-mode questions that matter before you automate delivery. Google's installation page recommends namespaced mode for most uses and says it provides better permission isolation, and the operator CRD defaults to it. In namespaced mode each enabled namespace needs its own `ConfigConnectorContext` naming that namespace's Google service account, while cluster mode takes exactly one credential for every resource, even across projects. A GitOps tenancy design that gives each team a namespace and a ServiceAccount, as section 8 describes, maps naturally onto namespaced mode, and an example page records how namespaces map to projects ([[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]], [[examples/config-connector-namespaced-mode-maps-namespaces-to-projects-and-service-accounts]]). Teardown is the weak point under either agent. A practitioner reports that Config Connector has no Terraform-style dependency graph and that Argo CD deletes children with no ordering, leaving objects in a failed delete after the parent goes, and a Config Connector design document describes a child whose parent was deleted first sticking on `DependencyNotFound`. The first is a single-author account and no documentation describes ordered teardown.

The Argo CD half of that claim is not corroborated. Argo CD's own documentation says that pruning reverses the wave order, so the practitioner may be describing a different kind of delete, such as removing a whole Application with a cascade, and no source says whether a cascade delete honors waves. The post does not say which delete it means and cites an Argo CD issue whose content the sources do not describe. The author's workaround is a CronJob that runs every five minutes and removes the finalizers from BigQuery tables stuck in `DeleteFailed` after their dataset object is gone, and he argues this is safe only because deleting a dataset in Google Cloud also deletes its tables. That argument holds only where the parent's deletion removes the child in the cloud, and it is the same forced-finalizer trade-off described in section 7 ([[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]], [[findings/a-config-connector-design-document-says-a-child-whose-parent-was-deleted-first-sticks-on-dependencynotfound-and-no-read-documentation-describes-ordered-teardown]]). Where a composition wraps these provider objects, the ACK documentation's kro guide is the one first-party worked example: it composes an S3 bucket, a DynamoDB table and a Deployment and deletes the Deployment before the AWS resources. No worked example of Crossplane composing ACK or Config Connector objects appears in the sources, and Crossplane's function auto-ready and kro's `readyWhen` both depend on the provider's `Ready` condition ([[examples/the-ack-docs-kro-guide-composes-an-s3-bucket-a-dynamodb-table-and-a-deployment-and-deletes-the-deployment-before-the-aws-resources]], [[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]]). If you must choose between those provider routes on Google Cloud, a decision page sets out using Config Connector directly, wrapping it in Crossplane through the Kubernetes provider, or using a Crossplane GCP provider, and records that a Crossplane maintainer said the wrapped route is not a replacement for a provider ([[decisions/use-config-connector-directly-wrap-it-in-crossplane-through-the-kubernetes-provider-or-use-a-crossplane-gcp-provider]]).

## 10. Design principles to take from Flux

Flux is useful to learn for its own sake, but its design is more valuable as a set of choices you can reuse. Each principle below states a reason, not only a preference.

**One controller per concern.** Flux separates fetching, rendering, Helm management, notification and image updates. The wiki cites it as the clearest example of the single-responsibility split, and compares it with ACK (split by AWS service) and Cluster API (core versus provider controllers). The three cut along different axes, function, external API and portability, and the wiki offers no performance comparison among them ([[comparisons/how-flux-ack-and-cluster-api-split-controllers]]). The reason to prefer small controllers is that each has a narrow API, a narrow failure mode and independent upgrade and scaling choices. Sharding in section 12 works only because the controllers are separable.

**Communicate through objects, not calls.** The controllers meet only in custom resources, so every handoff is visible in the API, inspectable with kubectl, and replaceable. When the source layer is separate from the delivery layer, changing from Git to OCI is a one-object edit.

**Level-triggered with events as hints.** The periodic pass guarantees correctness, and webhooks and revision changes only reduce latency. This is the design in [[decisions/events-as-hints-state-as-truth]], and it is the reason a lost webhook produces delay, not divergence.

**Pull, not push.** An agent inside the target holds its own credentials and needs only read access to the source. The reasoning is credential locality: compromising a build server should not hand over every environment. The principle has a price, which is that the agent becomes a powerful identity that must be constrained, and Flux supplies impersonation and lockdown flags for exactly that purpose.

**Inventory-based pruning.** Because Flux records what it applied, it can delete exactly that set when it disappears from the source. Owner references cannot do the job for objects a controller did not create through a parent, and labels alone are fragile. The inventory is an explicit ledger, and the cost is that you must decide what a missing entry means, which is what `prune`, the opt-out annotation and `deletionPolicy` are for.

**Explicit health and ordering.** Flux makes readiness and dependency visible in configuration (`wait`, `healthChecks`, `dependsOn`) instead of hoping retries sort things out. It admits that generic health is hard and provides CEL for kinds that do not follow kstatus.

**Separate detection from correction.** Helm drift detection offers `disabled`, `warn` and `enabled`. The wiki's decision page on staged adoption recommends exactly this ladder: observe first, correct selectively for well-understood workloads, then enforce broadly with documented ignore rules ([[decisions/staged-adoption-of-automated-drift-correction]]). Argo CD's manual sync, Crossplane's Observe policy and tofu-controller's detection-only mode follow the same idea. The principle is that a team should see drift before it lets software act on it.

**Make every dangerous action opt-in and every loop pausable.** Prune, force, drift correction and image automation are switches. `suspend` stops the loop, and the wiki's comparison page notes that every tool it covers ships an off-switch for the same reason: continuous loops override intentional changes ([[comparisons/reconcile-cadence-and-off-switches-across-tools]]). The corollary is that an off-switch needs monitoring, or a forgotten suspension becomes silent drift.

**Compensate for upstream limits, and say so.** Helm will not upgrade or delete CRDs "due to unintentional data loss dangers". Flux's `spec.install.crds` and `spec.upgrade.crds` offer Skip, Create (the default) and CreateReplace, and CreateReplace updates existing CRDs but deliberately does not delete removed ones, leaving cleanup to a human ([[examples/flux-helmrelease-crd-policies-createreplace-and-dependson]], [[findings/helm-does-not-upgrade-or-delete-crds]]). A good wrapper improves on the tool beneath it without hiding its safety choices.

## 11. Pitfalls: orphans, prune accidents, SSA migration, silent suspended failures, circular dependencies, HPA fights

The evidence on pitfalls comes from documentation, issue trackers and one practitioner blog. No independent Flux postmortem exists in those sources, so severity is inferred and each item below says what kind of evidence stands behind it.

**Orphans and prune accidents.** These are the two sides of the same switch, covered in section 7. Mitigations are to enable `prune` together with `healthChecks`, run `flux diff` or `kubectl diff` before merging risky changes, annotate objects that must never be pruned, and pick `Orphan` for critical resources. For managed cloud resources, a Git removal becomes a prune followed by a provider delete unless Delete is excluded from the provider's management policies ([[findings/unintended-deletion-through-prune]]). ACK issue 3153, described in section 9, is the freshest report of this path, and it shows that a controller-wide retain setting can be overridden by what a chart stamps on each resource. The Skyscanner outage from section 1 is the named, dated illustration of the worst case on the Argo CD side, where a reconciler enforced a corrupted configuration across every region. Its lessons transfer directly to Flux: a templated configuration file that looks like data needs tests and a staged regional rollout before a controller applies it globally, and the same pull model that spread the damage also made recovery routine once correct configuration was restored ([[findings/templated-configuration-that-looks-like-config-is-code-and-needs-tests-and-a-regional-rollout-before-a-gitops-controller-applies-it-globally]]). Two other incidents in the wiki are useful as contrasts and are not GitOps failures. Reddit's 314-minute outage on 14 March 2023 followed a Kubernetes 1.23 to 1.24 upgrade that removed a node label that its Calico route reflectors selected, and Spotify deleted one production GKE cluster through a console click in November 2018 and two more through Terraform about a month later, with no end-user impact. Both are described in primary write-ups, and neither involved a GitOps agent ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]], [[examples/spotify-deleted-one-production-gke-cluster-by-console-click-and-two-more-through-terraform-with-no-end-user-impact]]). Argo CD defaults to no prune and adds an allow-empty guard, and its own `Replace=true` and `Force=true` options can recreate resources and cause outages ([[findings/argo-cd-replace-and-force-sync-options-can-recreate-resources-and-cause-outages]]). Flux's `force` recreates objects on immutable-field changes and should be set only temporarily because it can cause downtime.

**Client-side to server-side apply migration.** Flux 0.17 applied through client-side apply, and 0.18 moved kustomize-controller to server-side apply. Users who upgraded, and users who adopted hand-applied resources, found that fields removed from Git stayed in the cluster. Issue 486 records the cause: the old manager still co-owned the fields, and force cannot take ownership of a field that no longer appears in the applied object, in the maintainer's phrase "you can't force ownerships for non existing fields". The workaround was to delete the offending `metadata.managedFields` entry, and an `--override-manager` flag later reclaimed named managers, but only after a successful dry run ([[examples/flux-migration-from-client-side-apply-strands-removed-fields]], [[findings/client-side-to-server-side-migration-leaves-stale-co-owners]]). A related case, issue 1722, shows a legacy controller co-owning a container entry's key, so that removing the container left a half-removed object and the dry run failed on every reconcile. The issue was opened on 2026-08-06 and closed through kustomize-controller PR 1747, merged on 2026-10-23, which added an opt-in flag that runs the takeover before the dry run. The flag is named `--override-manager-before-dry-run`, and it first shipped in kustomize-controller v1.10.0 on 2026-10-24 and in Flux v2.10.0 on 2026-10-26. A maintainer had called this kind of takeover dangerous, and the shipped documentation bears that out. The takeover transfers all fields owned by the managers you list, not only the field that wedged the dry run, it prunes fields missing from the source, and the `managedFields` change is not reverted if the apply then fails. Manager names are matched exactly rather than by prefix, and the default managers such as kubectl stay on the ordinary post-dry-run path. The documentation says to use the flag only to recover stuck objects and to remove it once they reconcile ([[examples/flux-issue-1722-a-stale-legacy-manager-wedges-the-dry-run-until-the-v1-10-0-pre-dry-run-flag]], [[findings/the-flux-pre-dry-run-takeover-transfers-all-fields-of-the-named-managers-and-is-not-reverted-if-the-apply-fails]], [[findings/a-stale-manager-owning-a-list-entry-key-breaks-the-dry-run-after-removal]]). Crossplane hit the same class of problem moving composed resources to composition functions, and Argo CD automates a migration to its `argocd-controller` manager.

**Field ownership blocks drift correction.** A community discussion shows a HelmRelease with drift detection enabled and a Service port edited by `kubectl edit`. `Service.spec.ports` is a list keyed by port and protocol, and the `kubectl-edit` manager still owns the entry, so the dry run fails with duplicate port names and helm-controller stops at "unable to determine cluster state". Ignore rules do not help because they apply after the dry run. The reported fix is `--override-manager=kubectl-edit`. The community member who suggested it said it was available since helm-controller v1.5.0, and the helm-controller CHANGELOG records both the flag and the version: its 1.5.0 section, dated 2026-02-20, says the flag "has been added for server-side apply drift detection and correction", and it adds that this drift correction is unrelated to Helm v4's own server-side apply support and was implemented long before Helm v4. The flag is repeatable, so you can list several managers, for example `--override-manager=kubectl-edit --override-manager=kubectl-patch`. Reading the helm-controller source shows how it works. When drift detection is on and the list is non-empty, the controller patches `managedFields` on each live object to remove the listed managers before its dry-run diff runs, and the error text if that cleanup fails is "failed to clean-up disallowed field managers". That is the reverse of kustomize-controller, whose `--override-manager` takes over only after a successful dry run, and which needed the separate `--override-manager-before-dry-run` flag from section 11 to recover an object whose dry run already fails. helm-controller therefore needed no separate recovery flag, and its flag can clear a stale `kubectl-edit` owner that wedges the diff. Two details deserve care. The sources do not describe how the function that rewrites `managedFields` works internally, and helm-controller's upgrade path always forces conflicts, so a dry-run failure caused by a validation error in the merged object, not by a conflict, is a different failure that force does not fix ([[findings/helm-controller-has-had-a-repeatable-override-manager-flag-since-v1-5-0-and-it-is-unrelated-to-helm-v4-server-side-apply]], [[findings/helm-controller-takes-over-override-manager-fields-before-its-dry-run-diff-the-reverse-of-kustomize-controller]], [[examples/flux-helmrelease-drift-correction-blocked-by-edited-service-port]]). The lesson is that self-healing depends on the diff succeeding, and the diff depends on clean field ownership. (Ignore rules fail here for a structural reason, not an oversight: they act on the diff's result, and the diff never gets to produce one.)

**Webhooks without dry-run support.** Because Flux dry-runs first, an admission webhook (a call the API server makes to an external service to validate or modify an object before storing it) that does not declare `sideEffects` of `None` or `NoneOnDryRun` makes the apply fail with "admission webhook does not support dry run". The fix belongs on the webhook configuration, not in Flux ([[examples/flux-dry-run-fails-against-webhooks-without-dry-run-support]]).

**Silent failures.** The practitioner blog lists three ways Flux looks healthy while not delivering: a suspended resource stops reconciling and drift builds up unnoticed; without webhook Receivers, a change waits for the next poll; and running `flux reconcile` without `--with-source` reconciles against the source's last fetched revision, so the command succeeds without picking up the new commit. It recommends alerting on `gotk_reconcile_error_total` and `gotk_suspend_status` ([[findings/suspended-resources-polling-lag-and-a-missing-with-source-flag-make-flux-failures-silent]]). This is a secondary source, but the failure modes follow directly from the design in section 2.

**Circular dependencies.** The HelmRelease reference says circular dependencies "must be avoided, otherwise the interdependent HelmRelease resources will never be reconciled". Each waits for the other to be Ready, so neither starts, and the failure is a stall, not an error. The sources do not say whether Flux detects the cycle at admission. kro, in contrast, rejects cycles at definition time ([[findings/circular-dependson-chains-between-flux-resources-never-reconcile]]).

**HPA fights.** Covered in section 7. The general diagnosis, from [[findings/controllers-fighting-over-fields-cause-revert-loops]], is that drift is often two writers disagreeing, and the first step is to find the second writer. Argo CD saw the same pattern when argocd-image-updater rewrote child Application specs ([[examples/argo-cd-app-of-apps-out-of-sync-from-image-updater]]).

**Failure and retry defaults differ across tools.** Flux keeps retrying on `retryInterval`. Argo CD does not retry a failed sync of the same commit and parameters unless retry is configured ("Automatic sync will not reattempt a sync if the previous sync attempt against the same commit-SHA and parameters had failed"), while controller-runtime retries forever with exponential backoff ([[examples/argo-cd-does-not-retry-a-failed-sync-of-the-same-commit-unless-retry-is-configured]], [[comparisons/retry-and-backoff-controls-across-tools]]). Retrying without limit risks amplification, and refusing to retry risks silent non-convergence.

**A cross-tool summary.** The table lists how each stack deals with the problems above.

| Problem | Flux | Argo CD | Other tools |
|---|---|---|---|
| Second writer on a field | `.spec.ignore` Strip and Adopt (documented in the kustomize-controller specification), `driftDetection.ignore` on HelmRelease, `ssa` annotation | `ignoreDifferences`, Server-Side Diff | Crossplane `initProvider` and `managementPolicies`; Kluctl per-field force |
| Removal from source | `prune` plus inventory, `deletionPolicy` | Prune off by default, resources finalizer on the Application | ACK retain policy; Config Connector `abandon` annotation |
| Ordering | `dependsOn`, `healthChecks`, `wait`, CEL | Phases and waves, Lua health | kro graph references; Crossplane function readiness |
| Readiness of custom kinds | kstatus plus CEL | Lua per CRD | Crossplane `Synced` and `Ready`; Cluster API moving to `Available` |
| Pause | `suspend` | Disable automated sync | Crossplane pause annotation; Config Connector interval "0" (documented as irreversible) |
| Secrets | Controller-side SOPS only; Sealed Secrets guide | Destination-cluster operators recommended; generation plugins cache plaintext in Redis | No source compared |
| Health of provider kinds | kstatus plus CEL; Crossplane examples in the cheatsheet | Built-in Lua for Config Connector, ACK, Crossplane, Upbound, kro and Cluster API kinds | ACK conditions lack `observedGeneration` |
| Signed OCI sources | Cosign and Notation verification in `.spec.verify` | OCI sources supported; no signature verification documented | No source compared |

Every cell comes from the pages cited in this section and in sections 4, 6, 7 and 8 ([[comparisons/exemption-and-ignore-controls-across-tools]], [[comparisons/deletion-policies-across-gitops-and-provider-tools]]). The Flux `.spec.ignore` entry is documented in the kustomize-controller specification, as section 7 explains. The entries in the last column, such as the Crossplane `initProvider` and pause annotation, the ACK retain policy and the Config Connector `abandon` annotation and interval "0", come from comparison pages that summarize their sources and do not quote every one in full.

The table is a quick reference, and the reasons behind it matter more than the cells. For a second writer on a field, Flux and Argo CD both start from a force-everything stance and then offer escape hatches. Flux lets you strip or adopt fields per object or per path, and the specification documents how each policy behaves, although no source compares forcing with strip-or-adopt, so the choice between them rests on reasoning and not on measurement. Argo CD's `ignoreDifferences` hides differences from its comparison and its Server-Side Diff makes the comparison use the server's own merge logic. The provisioning tools approach it from the other side, because they expect other writers (cloud defaults, other controllers) and so give each resource a policy for which fields to leave alone. The trade-off is between predictability and surprise. A tool that always reverts is simple to reason about but fights every legitimate co-owner, and a tool with per-field rules is flexible but needs a human to decide which fields are safe to ignore.

For removal from the source, Argo CD defaults to the non-destructive choice, since prune is off until you enable it, whereas Flux asks you to set `prune` and then offers explicit switches (the opt-out annotation and `deletionPolicy`) for the dangerous cases. Provider tools differ again, because deleting the Kubernetes object can delete real cloud infrastructure, so their policies (ACK retain, Config Connector `abandon`, Crossplane management policies) exist to separate the life of the object from the life of the cloud resource. Ordering and readiness follow the same logic. Flux and Argo CD order objects delivered from outside and need generic or scripted health checks to know when a custom kind is ready, while kro and Crossplane order resources inside one abstraction and can read readiness from their own graph. Pause is the simplest row, since every tool has an off switch, and the cost of each is that a forgotten pause quietly becomes drift.

## 12. Scaling Flux: intervals, concurrency, sharding and memory

Scale in a controller is several separate limits, not a single number. The wiki's scale page lists four constraints inside a client-go controller: the informer cache holds every watched object, so memory grows with what is watched; the workqueue never processes one key concurrently, so throughput depends on the worker count and the time per reconcile; the client rate limiter throttles requests before they reach the server; and leader election (replicas of a controller agree on one active instance via a lock object, and the rest wait as standbys) means only one replica reconciles ([[concepts/scale-and-sharding]], [[concepts/informers-reflectors-and-workqueues]]). The informer cache is an in-memory copy of everything watched, and the Kubernetes blog says it has no eviction ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]).

Flux's controllers use two cache-narrowing options that are worth knowing by name. The source, kustomize and helm controllers each build their own controller-runtime manager, which means each is a separate process with its own informer cache. No document says so explicitly, but each controller's `main.go` builds its own manager, so the cache is not shared between controllers. Each controller narrows the cache for its own custom kinds with a label selector taken from `--watch-label-selector`, and a `--watch-namespace` flag can limit the cache to one namespace. That same label selector is the sharding key described below, so one mechanism both shrinks memory and splits work. The second option concerns Secrets and ConfigMaps: each controller adds both kinds to the client's list of types that bypass the cache, so reading them goes to the API server every time, unless the `CacheSecretsAndConfigMaps` feature gate is switched on. The Flux runtime package warns that switching it on causes "increased memory usage and cluster-wide RBAC permissions (list and watch)", so the trade is API-server load against memory and privilege. The defaults in the source are `--concurrent` 4 for kustomize-controller and helm-controller and 2 for source-controller ([[findings/flux-controllers-keep-separate-caches-narrowed-by-a-watch-label-selector-and-leave-secrets-and-configmaps-uncached-by-default]], [[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]).

Flux's documented order of response is to tune before you split.

**Lengthen intervals.** Fewer scheduled reconciles mean less API load, at the cost of slower drift correction. Morgan Stanley did this.

**Raise concurrency and resources.** The `--concurrent` flags raise the number of parallel reconciles, which are the workqueue workers. The scale research source states a suggested 10 to 20, along with higher CPU and memory limits for the source, kustomize and helm controllers, a memory-backed `emptyDir` on `/tmp` to speed Kustomize builds, and persistent volumes so artifacts survive restarts. The source controller can cache Helm indexes with `--helm-cache-max-size` and `--helm-cache-ttl`. The vertical scaling page warns that "tmpfs will count against the controller's pod memory usage" ([[examples/flux-controllers-expose-worker-concurrency-and-helm-cache-size-as-tuning-knobs]]). Raising concurrency shifts load onto the API server or onto pod memory.

**Do not add replicas for capacity.** "Extra replicas of a Flux controller are failover standbys. Only the elected leader reconciles." Going from one replica to three buys availability, not throughput ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

**Shard when one instance cannot keep up.** Sharding runs several copies of a controller under unique names, such as `source-controller-shard1`. Each starts with `--watch-label-selector` set to its own value of the label `sharding.fluxcd.io/key` and reconciles only objects carrying that label, while the default controllers skip labeled objects so nothing is handled twice. Source, kustomize and helm controllers can be sharded, but the sharding page says of the notification controller and the source-watcher, a newer Flux component that this document does not otherwise cover, that "these controllers do not support sharding". The page's example also deletes the image-reflector and image-automation Deployments from the shard sets, so the documented recipe shards the source, kustomize and helm controllers and leaves image automation to the default instance. Whether the image controllers can be sharded at all is not stated in the sources, and they do not describe the Flux Operator's own sharding guide. The practical consequence is that a plan aimed at relieving notification or image-scanning load will not be helped by adding shards ([[findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded]], [[sources/research-scale-and-sharding]]). Each shard also elects its own leader. When a watch label selector is set, the leader election ID is derived from it, so a shard does not compete with the default instance for the same lease, and the source notes that the process is presumed to terminate when it loses leadership ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]]).

```yaml
# Illustrative: a HelmRelease placed on a shard by label
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: tenant-b-ingress
  namespace: tenant-b
  labels:
    sharding.fluxcd.io/key: shard1
spec:
  interval: 15m
  chart:
    spec:
      chart: ingress-nginx
      sourceRef:
        kind: HelmRepository
        name: tenant-b-charts
```

The label places the release on the controller instance watching `shard1`. The catch is that the HelmRepository it references, and the HelmChart generated from it, need matching labels too, otherwise the pieces land on different controllers. The sharding page states the rule: "Source object kinds which have a dependency on another kind (i.e. `HelmChart` on a `HelmRepository`) need to have the same labels." Because a HelmChart is generated from a HelmRelease and not written by hand, its label is set through the HelmRelease's `.spec.chart.metadata.labels`, which the page describes as setting "the sharding key on the generated Flux `HelmChart` object". The main controllers are told to ignore any keyed object with `--watch-label-selector=!sharding.fluxcd.io/key`, so a HelmRelease that carries the shard key while its chart does not would have its chart handled by a different controller than the one that needs the artifact. The documentation does not spell out the symptom a user would see, so the exact error is unknown ([[findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels]]). A parent Kustomization can bulk-label children through `commonMetadata` and patches, and the Flux Operator removes the manual work by declaring shards in the FluxInstance spec, though the labels still have to be applied ([[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]], [[examples/flux-sharding-splits-reconciliation-across-label-selected-controller-instances]]).

Is sharding needed yet? The Flux sharding page advises it when Flux is managing "tens of thousands of applications", though the decision page on this question notes that no source states a precise threshold. A targeted search for named adopters found no organization that says it runs sharded Flux with a shard count or object count. Morgan Stanley, the best-known large adopter, lists "Exploring sharding Flux controllers" under "Looking Ahead", so it is not a documented sharding user. The evidence that does exist is thinner and mostly anonymous: a hub-and-spoke user reported reconciliation storms during nightly deploy windows in flux2 issue 5470 (August 2025) and a maintainer suggested sharding among other options ([[examples/a-hub-and-spoke-flux-user-reported-nightly-reconciliation-storms-and-was-told-to-shard-or-tune]]), a cross-shard `dependsOn` failure was fixed in 2024 ([[findings/a-flux-dependson-across-shards-failed-with-dependency-not-found-until-a-2024-fix]]), and an unnamed reporter of source-controller issue 2150 said they hit stale artifacts after objects left a shard "in production" ([[findings/objects-that-leave-a-flux-shard-keep-stale-artifacts-on-the-old-source-controller]]). These show that people shard, but none is a named adopter with numbers.

One named project does automate it. Cozystack, which turns commodity servers into a Kubernetes-based cloud, ships a `flux-shard-operator` that creates helm-controller shards with `--watch-label-selector=sharding.fluxcd.io/key=shard<i>`, places tenants greedily by HelmRelease count, and sizes the shard count at roughly 100 HelmReleases per shard with a maximum of 16, using the formula `K = clamp(ceil(H/100), 1, min(16, T))` where H is the HelmRelease count and T the tenant count, and a default per-shard `--concurrent` of 5. Those numbers are the project's own documentation of design intent. No measured outcome or production use is published, so they are design targets and not adopter measurements, but the example does show the tenant-per-shard placement pattern ([[examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard]], [[entities/cozystack]]). The reasonable reading, which no source states as a rule, is to tune first and shard when one instance reaches its limits ([[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]], [[comparisons/flux-scaling-options-intervals-concurrency-sharding-and-source-choice]]).

Argo CD partitions by destination cluster instead of by label, with `legacy`, `round-robin` and `consistent-hashing` assignment, a legacy algorithm that can be uneven, and the other two still labelled experimental at Argo CD v3.6.3. Legacy is still the default in the code at that version, although the v3.6.3 high-availability page no longer marks it as the default, and no source explains the documentation change. Cluster sharding fits hub-and-spoke setups (one central cluster running the delivery tool and pushing to many smaller workload clusters) but cannot divide one very large cluster, whereas label sharding can separate tenants inside one cluster at the price of label discipline ([[comparisons/flux-label-sharding-versus-argo-cd-cluster-sharding]]).

A word on API Priority and Fairness (APF), the API server feature that queues and prioritizes incoming requests by flow so that no single client can starve the rest. Flux's June 2022 update says all its controllers conform to APF, and the change behind it turns off the controllers' own client-side throttling when the server has APF enabled, because client-go honors the `Retry-After` header the APF filter sets. A pull request closed in February 2026 (fluxcd/pkg PR 1118) fixed a path where a custom kubeconfig still used client-side rate limiting even when APF was available; the sources show the pull request as closed without saying it was merged, so the release that carries the fix is unknown. Until that fix, the two throttling layers can disagree inside one tool ([[findings/flux-turns-off-client-side-throttling-when-apf-is-enabled-but-a-custom-kubeconfig-path-kept-it-until-2026]]). No published incident or postmortem ties Flux, sharded or not, to APF throttling in the sources behind this document. Because the available evidence is limited, read this as an open question and not as proof that no such incident happened.

Finally, remember that constant reconciliation costs something. Level triggering means repeated work, and for controllers that manage external systems every cycle can be a quota-consuming API call. Flux and Argo CD read the Kubernetes API and Git, so seconds-to-minutes cadences are cheap, while ACK defaults to about ten hours between real re-reads of an AWS resource, and kro has a ten-hour resync as well.

Config Connector sits much closer to Flux than to ACK. Its three reconciler families, the direct controllers and the two older code paths that wrap Terraform and Google's Declarative Client Library, all end a successful pass through one shared jittered requeue function, so the kind of controller behind a resource does not change the cadence. The default mean is ten minutes, spread by jitter to somewhere between five and fifteen minutes, and the annotation `cnrm.cloud.google.com/reconcile-interval-in-seconds` overrides every built-in value. Per-kind overrides are rare: the Terraform service mappings set five of them, and no Declarative Client Library kind sets one. Drift detection is the reconcile itself and not a separate poll, so the worst-case detection delay is the interval. Setting the interval to 0 switches off periodic drift correction for that resource, and the reconciliation page states that doing so is irreversible, which makes it a very different off-switch from Flux's `suspend`. No measured drift latency from a live cluster appears in the sources ([[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]]).

The two ten-hour figures are not the same mechanism: ACK's is a requeue that triggers a fresh read from the cloud API, whereas kro's flag text says it will "re list" resources but the source suggests that it replays the informer's cached state to the handlers (an informer is the client-side cache a controller keeps of the objects it watches), so it does not by itself contact the cloud. The sources do not state whether the two figures describe comparable mechanisms ([[findings/the-word-resync-names-three-different-mechanisms-in-client-go-kro-and-ack]], [[findings/cost-of-constant-reconciliation]], [[decisions/choosing-a-drift-check-interval-for-external-resources]]).

## 13. How Flux compares with Argo CD, Kluctl and push-based CI, and its relationship to Crossplane and Cluster API

**Argo CD.** Both are CNCF GitOps delivery tools. Flux is "controllers all the way down": separate controllers with their own CRDs, a Kubernetes-API-and-custom-resource interface, and reconciliation on a schedule. Argo CD is more centralized, with an API server serving UI, CLI and CI, a repository server that caches Git and renders manifests, and an application controller that diffs live against target state ([[comparisons/flux-versus-argo-cd-architecture]]). Their defaults differ in a revealing way. Argo CD ships with destructive actions off: prune off, self-heal off, allow-empty protection, and manual sync as a middle stage. Flux exposes explicit switches and policies for each, such as `prune`, `deletionPolicy` and drift-detection modes ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). Argo CD's default repository polling interval depends on the version: a flat 180 seconds through v2.14, and from v3.0 a base of 120 seconds plus up to 60 seconds of random jitter, so a poll lands somewhere between two and three minutes. Some documentation still says three minutes, and no source explains why the default changed, so check the version you run, and Flux's interval is chosen per object, with no controller-side default, since the field is required, as section 5 explains. Argo CD blocks rollback while automated sync is on, so rollback becomes a Git revert ([[findings/rollback-is-blocked-while-automated-sync-is-on]]). One more caution about this comparison: much of the comparative claim-making comes from vendors. Akuity, which sells Argo CD, says Flux has a lower and more predictable footprint and suits air-gapped setups, and relies on the Flux Operator for its official UI. Devtron, a vendor built around Argo CD, says Flux lacks a native UI, which the wiki marks as dated. None of these were independently benchmarked ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]]). Treat the UI and scale claims as opinion. A side-by-side reading of the two projects' documentation turns up no neutral benchmark or CNCF comparison, so the head-to-head rests on each project's primary pages ([[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]).

**Argo CD ApplicationSets and fleets.** Argo CD's answer to "one definition, many clusters" is the ApplicationSet, a controller that generates Applications from generators, such as one per registered cluster, per Git directory or per pull request. The documented limits are worth knowing before you plan around it. The matrix generator "currently only supports combining the outputs of only two child generators", combination-type generators "can only be nested once", and the Pull Request generator polls every 30 minutes by default and makes anonymous requests, with a lower rate limit, when no token is set. The generator overview says there are nine generators and then lists ten, a stale count and not a missing generator. The Cluster generator works from the clusters Argo CD manages and targets both local and non-local clusters unless a selector excludes the local one. For staged rollout, the RollingSync strategy is marked Beta since v3.3.0, "will force all generated Applications to have autosync disabled", respects sync windows, and "only interacts with the health of managed Applications", so its safety depends on how well the health checks of section 6 judge the kinds involved. An Application that no step selects is excluded from the rolling sync and never syncs through that path. No quantified scale limit for ApplicationSets or hub-and-spoke Argo CD is published, which does not mean none exists, and one ApplicationSet incident is on record in which a generated Application was deleted together with its namespaces and Argo CD itself. Flux has no direct equivalent object. Fleet layouts are built from a directory per cluster and shared bases, and from the Flux Operator's ResourceSet templates in the D2 design ([[findings/applicationset-generators-have-documented-limits-matrix-takes-two-children-nesting-is-once-and-pull-request-polling-defaults-to-30-minutes]], [[findings/applicationset-rollingsync-is-beta-forces-autosync-off-and-watches-only-application-health]], [[examples/argo-cd-issue-20440-an-applicationset-generated-application-was-deleted-with-its-namespaces-and-argo-cd-itself]]).

**Kluctl.** Kluctl is a deployment tool whose author moved it from shelling out to kubectl with client-side apply to calling server-side apply directly, after hitting the annotation size limit on large CRDs. Its distinctive feature is per-field conflict decisions ([[entities/kluctl]]). Compared with Flux, which force-applies its intent and provides ignore rules, Kluctl is the one tool in the wiki that makes a field-level decision by default. The source is the tool's own maintainer writing on the Kubernetes blog.

**Push-based CI.** A push pipeline runs `kubectl apply` or `helm upgrade` once and stops. It holds credentials for every target, fails the "continuously reconciled" principle if it never re-checks, and tends to accumulate drift. The Morgan Stanley account describes exactly this experience. The comparison is not absolute: Flux itself supports push-style triggers through webhooks, and the pull agent is a powerful identity that needs constraining ([[comparisons/push-versus-pull-delivery]]). INNOQ argues that the pull pattern does not require Kubernetes, since an operator inside any target can read desired state from Git and reconcile, though no named production deployment of that idea appears in the sources ([[examples/gitops-agent-on-non-kubernetes-targets]]).

**Crossplane, Config Connector, ACK and kro.** These are provisioning or abstraction tools, so the relationship with Flux is layered, not competitive. Flux delivers their custom resources, and they reconcile the real world. Crossplane lets a platform team publish its own typed API through an XRD and Composition with a pipeline of functions. kro does something similar with a resource graph and CEL, the Common Expression Language used for small inline expressions. In kro, a ResourceGraphDefinition (RGD) is the object that declares a graph of Kubernetes resources behind a new custom API, so that creating one instance of that API creates and wires together the whole graph. Config Connector and ACK expose roughly one CRD per cloud resource. Because these tools reach into clouds, prune and deletion semantics propagate: ACK's default is to delete the AWS resource, Config Connector's `abandon` annotation keeps it, and Flux's `Orphan` and `prune: disabled` keep the Kubernetes objects ([[comparisons/deletion-policies-across-gitops-and-provider-tools]]). A render-time tool such as Helm or Kustomize produces manifests once and needs something like Flux for continuous correction, while Crossplane and kro are themselves live control loops ([[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]]). The Argo CD guide for Crossplane calls for custom Lua health checks, annotation-based tracking and a raised client QPS (the queries-per-second limit on how fast the controller may call the API server), because a generic GitOps agent cannot judge custom-resource health unaided ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]). At v3.6.3 the Argo CD tree ships built-in scripts for the Config Connector, ACK, Crossplane and Upbound groups, so a team on that release or a later one should look at the shipped script before writing its own, as section 6 describes. Flux faces the same issue and answers with kstatus plus CEL. No source compares Flux tool by tool with Crossplane, kro, Config Connector or ACK, so the relationship here is an inference from how each tool is documented.

**kro and the Crossplane function runner.** Two newer entrants sit one layer above delivery and are worth placing on the map, because teams weighing a platform abstraction will meet both. Governance and roadmap come first, since they decide how far a team can plan around kro. kro is governed as a subproject of Kubernetes SIG Cloud Provider (the Kubernetes special interest group that owns it), which four first-party sources state. Besides the ResourceGraphDefinition, the project is developing an alpha Graph API, a newer and lower-level way to declare a graph of resources directly instead of through an RGD, and its in-repo roadmap gives no promotion timeline for it. The roadmap file is marked last updated 2026-04-03 and said v0.10 would arrive in mid-May, while v0.10.0 was published on 2026-11-10. The design text says the Graph API "does not replace or deprecate the RGD Kind", and both ride one engine, so a team choosing between ResourceGraphDefinitions and the alpha Graph API cannot plan from the roadmap ([[findings/the-kro-in-repo-roadmap-predates-the-v0-10-0-release-and-gives-no-graph-promotion-timeline]], [[decisions/build-platform-apis-on-resourcegraphdefinitions-or-track-the-alpha-graph-api]]).

The evidence for how kro behaves at scale is thin, and it matters because a platform API that every team depends on needs known limits. The public evidence is two open issues, one about a single queue for all resource types and one asking for automated performance testing, and a pull request closed unmerged on 2026-08-11. No benchmark, measured limit or named production adopter appears, and one consultancy article listing failure patterns cites no customer and uses outdated names. The sources also disagree on the controller layout: the kro docs FAQ says there is a dedicated controller per ResourceGraphDefinition, while the tuning page and the source code describe one shared queue, so the documentation conflicts with itself.

Two vendor-side signals add context without filling that gap. The Amazon EKS documentation page on resource composition states that under EKS Capabilities kro is fully managed by AWS, so customers do not install or scale its controllers, and it names two integrations with other managed capabilities: ACK for AWS resources and Argo CD for deploying kro custom resources across multiple clusters. The page is vendor documentation, names no kro version or scale limit, uses the `kro.run/v1alpha1` API in its example, and says nothing about Flux. Separately, a company blog dated 2026-07-29 reports that the CNCF and SlashData Q1 2026 Platform Engineering Radar placed kro in its Adopt tier for application delivery, based on a Q4 2025 survey of more than 400 developers. The radar itself is not among the sources, the post names no company running kro in production, reports no scale figure or incident, and itself notes that the rating does not make a particular kro release battle-tested ([[findings/the-amazon-eks-kro-overview-lists-resourcegraphdefinition-as-the-only-primary-resource-type-and-names-no-kro-version]], [[findings/one-blog-reports-that-the-cncf-and-slashdata-q1-2026-radar-rated-kro-adopt-from-a-survey-of-more-than-400-developers]], [[findings/kro-scale-evidence-is-two-open-issues-and-a-closed-unmerged-pull-request-with-no-benchmark-and-no-named-production-adopter]], [[findings/the-kro-docs-faq-says-a-dedicated-controller-per-rgd-while-the-tuning-page-and-source-describe-one-shared-queue]]).

The two ecosystems meet in function-kro, which lets a Crossplane pipeline step run a kro graph. Its README claims full feature parity, but its own file of upstream differences lists gaps, such as a fatal result that makes Crossplane apply nothing and set `Synced=False` where kro would retry. Release v0.4.0 on 2026-11-26 moved it onto kro's own graph engine. It has one listed maintainer, and no independent production reports exist in the sources, so treat it as the same engine with documented gaps and not as a drop-in equivalent ([[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]], [[examples/function-kro-v0-4-0-moved-onto-the-kro-v0-10-0-graph-engine-on-2026-11-26-with-one-listed-maintainer]]).

The word "function" is also a trap, because two unrelated specifications use it. The KRM Functions specification, which kpt and Kustomize use, says "A function MUST be implemented as a container", reads a `ResourceList` on stdin and writes one to stdout, and treats a non-zero exit as failure. It is a client-side standard, "completely decoupled from Kubernetes API machinery". Crossplane composition functions share the name and the pipeline idea but speak a gRPC `RunFunction` contract, and Crossplane moved them from an `xfn` sidecar in v1.11 to package-manager Deployments in v1.14, with functions reaching v1 in v1.17. Kustomize runs a function without a container only through the opt-in `--enable-alpha-plugins --enable-exec` flags, and its guide says "Kustomize does not provide an execution sandbox of any kind" ([[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]], [[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]], [[findings/crossplane-moved-composition-functions-from-an-xfn-sidecar-in-v1-11-to-package-manager-deployments-in-v1-14]], [[examples/a-kustomize-exec-krm-function-runs-only-with-enable-alpha-plugins-and-enable-exec]]).

For Crossplane's own operations, no performance or sharding guide appears in the sources. Core strips CRD schemas from its cache, defaults a worker pool of 100, and the Pods guide gives a one-minute poll and a one-hour sync interval. Package dependencies are resolved by a controller that creates only the first missing dependency per pass, and version upgrades and downgrades are alpha ([[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]], [[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]], [[decisions/let-crossplane-resolve-package-dependencies-or-pin-versions-and-skip-resolution]]).

**Terraform in the cluster.** Teams with large Terraform estates often want those resources under GitOps without rewriting them. tofu-controller, a Flux-adjacent controller, reconciles a Terraform resource by running plan and apply in runner pods, keeping state as Kubernetes Secrets and expressing manual approval in Git through `.spec.approvePlan`. It lives at `flux-iac/tofu-controller` and is community maintained, with five active maintainers listed. Its v0.17.0 release on 2026-11-16 removed the `v1alpha1` API, so manifests still on it need migration, and the sources do not include the project's migration advice. Terraform Operator is the alternative, and its last release was v0.17.1 in May 2024 with essentially one maintainer, which supports calling it low-activity, not abandoned, since no deprecation notice appears in the sources. The costs are state in Secrets, Git-based approvals and coupling to particular controller and Flux versions, and the alternative is modeling resources natively in Crossplane.

One more difference decides many of these choices, which is the review step. Terraform and OpenTofu produce a reviewable plan before anything changes, and tofu-controller carries that into Git through `.spec.approvePlan`, while Crossplane has no built-in plan preview, and a 2022 evaluation by the consultancy Superorbital noted no Terraform-plan equivalent. The plan is a check and not a guarantee. One practitioner, in a 2025 opinion post that names no provider, resource or date, reports a plan that showed an update while the apply recreated the resource and lost data, and uses the story to argue for plan review before changing production databases. That is a single anecdote and not a measurement of how often plans and applies diverge ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]], [[findings/one-practitioner-reports-a-terraform-plan-that-showed-an-update-while-the-apply-recreated-the-resource-and-lost-data]], [[examples/superorbital-s-2022-evaluation-reported-no-terraform-plan-equivalent-for-crossplane]]). The project and decision pages behind the rest of this paragraph are ([[findings/tofu-controller-is-community-maintained-under-flux-iac-and-v0-17-0-removed-the-v1alpha1-api]], [[findings/terraform-operator-has-had-no-release-since-may-2024-and-is-effectively-single-maintainer]], [[decisions/run-existing-terraform-in-the-cluster-with-tofu-controller-or-terraform-operator-or-model-resources-natively-in-crossplane]], [[comparisons/tofu-controller-versus-terraform-operator-as-terraform-in-cluster-controllers]]).

**Portals and developer-facing layers.** Above delivery sit tools that give developers a simpler front end. Kratix lets a platform team publish a Promise, a self-service API, and schedules the resulting workloads across Destinations. A Destination does not apply anything. Kratix writes `dependencies` and `resources` directories to a Git or bucket state store, and an agent such as Flux or Argo CD on the Destination pulls them, which makes Flux a natural consumer. The Destination's filepath mode is immutable once created. Syntasso's example of scattering workloads across standard, PCI and Terraform destinations is a vendor illustration and not an independent case study ([[findings/a-kratix-destination-writes-dependencies-and-resources-directories-and-its-filepath-mode-is-immutable]], [[examples/kratix-promises-scatter-workloads-across-standard-pci-and-terraform-destinations]]). Backstage is a portal and not an operator. Its Kubernetes plugin matches catalog entities to cluster objects by the `backstage.io/kubernetes-id` label, its Scaffolder is a one-shot task runner, and the nearest operator-style integration is a third-party plugin that ingests Crossplane claims and kro instances into the catalog ([[findings/the-backstage-kubernetes-plugin-matches-entities-to-cluster-objects-by-label-and-no-backstage-document-describes-an-operator-pattern]], [[examples/the-terasky-kubernetes-ingestor-ingests-crossplane-claims-and-kro-instances-into-the-backstage-catalog]], [[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]). Radius and Score are workload abstractions. Both are CNCF Sandbox projects per the landscape file, which is the entry tier and says nothing about production readiness. All four Radius maintainers are Microsoft employees and only its newest minor channel is supported, with v0.62.0 on 2026-10-27 listing breaking changes. Score's maintainers span four employers, and its sandbox application names Humanitec as sponsoring company, though no document says in words that Humanitec created it ([[findings/radius-and-score-are-both-cncf-sandbox-projects-per-the-landscape-file-and-both-passed-sandbox-votes]], [[findings/all-four-radius-maintainers-are-microsoft-employees-and-only-the-newest-minor-channel-is-supported]], [[findings/score-maintainers-span-four-employers-and-the-sandbox-application-names-humanitec-as-sponsoring-company]], [[comparisons/score-versus-radius-as-developer-facing-workload-abstractions]]).

**Cluster API.** Cluster API is the clearest case of Kubernetes managing Kubernetes, and Flux's role is to deliver its objects and wait for them. The kstatus episode in section 6 is the concrete point of contact, and it shows how a change in a provider's condition vocabulary (`Ready` moving toward `Available`) forced Flux to add explicit CEL checks ([[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]).

## 14. Getting started checklist and remaining unknowns

If you are starting from zero, an order that follows the wiki's evidence is the following. Bootstrap Flux against a test cluster so that it commits its own manifests and manages itself. Create one GitRepository and one Kustomization, with an explicit `interval`, and watch the status conditions, then hand-edit a Deployment and watch it revert. Turn on `prune` with a deliberately throwaway manifest and confirm what disappears, and learn the `prune: disabled` annotation before you need it. Add `wait` or `healthChecks`, then a `dependsOn` edge for a CRD-and-operator pair. Move one `helm upgrade` job into a HelmRelease, leaving drift detection at `warn` until you have read the drift events. Add webhook Receivers and an Alert so that failures and new commits are not silent. Decide on tenancy before the second team arrives: set the three lockdown flags, create a ServiceAccount per tenant with namespace-scoped RBAC, and keep one tenant per namespace. Add alerts on `gotk_reconcile_error_total` and `gotk_suspend_status`. Only after that, consider ignore rules, image automation (staging only to begin with), and sharding.

Some questions have no answer in the available sources, and a few are answered differently by different sources, so they belong in your plan as caveats. The Flux concepts page still says five minutes by default, but the reference pages and the controller's type definition show `interval` is required with no default. The sentence replaced a one-minute statement in a 2022 documentation commit, and the reason for the change is unknown.

On the Flux mechanics, the Kustomization-level `.spec.ignore` list with Strip and Adopt modes is documented in the kustomize-controller specification, but no source compares forcing with strip-or-adopt, and only the blog says that `flux diff` honours the rules. The documentation excerpts behind this document are summaries, and the Kustomization and HelmRelease pages are only partly covered, so check quoted field names against the live pages. Flux's own finalizer is `finalizers.fluxcd.io`, and the controller removes it even after a WaitForTermination timeout, as documented for the v1 API on the main branch; the sources say nothing about older API versions. Whether Flux detects circular `dependsOn` chains at admission is not stated. The pre-dry-run takeover flag from issue 1722 is `--override-manager-before-dry-run`, shipped in kustomize-controller v1.10.0 and Flux v2.10.0. The helm-controller `--override-manager` flag dates from v1.5.0 according to its changelog, and its source takes over fields before the dry-run diff. No source describes how helm-controller surfaces a dry-run validation failure on a stuck release.

On health and readiness, whether kstatus treats a v1beta2 Cluster with `Available=False` as reconciled is an inference that no source tests. That each Flux controller keeps a separate cache follows from the controllers' `main.go` files and is not stated by any document. The image automation kinds are `image.toolkit.fluxcd.io/v1` on the main branch, but the sources do not state the release in which they graduated or the ImageUpdateAutomation storage version, and no adopter write-up of reviewed promotion exists. The HelmChart shard-labeling rule is documented on the sharding page, although the symptom of a mismatch is not. The source-controller artifact server starts only after leader election, according to its source, while the claim that artifacts vanish on restart because `/data` maps to an `emptyDir` is an inference, and no source states the lease durations.

On Argo CD and the wider landscape, Argo CD's lack of documented OCI signature verification and its silence on SOPS rest on the Argo CD documentation and not on a statement from the project, and the maturity of argocd-agent is undocumented. No source describes how Flux reads ACK's terminal condition, whether Flux needs owner references on composites, or any Flux guidance for kro instances. The ACK and Config Connector issue reports are single-reporter accounts, several still open without maintainer resolution. The Cozystack figure of about 100 HelmReleases per shard is design intent, not a measurement. The sources contain no neutral comparison of Config Connector with Crossplane, no kro benchmark or named kro adopter, and no Crossplane performance guide.

On evidence about adoption and scale, no independent Flux postmortem or neutral Argo CD benchmark exists in the sources, although Skyscanner's Argo CD postmortem is a primary account of a pull-based GitOps outage, and no organization is named as running Flux shards or as having had an APF incident with Flux. Finally, the sources do not settle the best default for platforms that run GitOps and other controllers on the same objects ([[decisions/force-conflicts-or-surface-them-to-humans]]). These items remain open questions.
