# Flux Ramp-Up: GitOps Toolkit Architecture, Operation and Design Principles

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) but have not yet worked with controllers, API machinery or GitOps agents in depth<br>
> **Purpose:** Teach how Flux works from first principles, where it fails in practice, how it compares with neighboring tools, and which of its design choices are worth copying<br>
> **Status:** Active<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-27<br>
> **Draws on:** [[entities/flux]], [[concepts/gitops-pull-based-delivery]], [[sources/research-flux-deep-dive]], [[concepts/scale-and-sharding]], [[comparisons/flux-versus-argo-cd-architecture]] and the other wiki pages listed under Further reading<br>

## 1. What Flux is and who uses it

Flux is a GitOps tool that runs inside a Kubernetes cluster. You tell it where a set of manifests lives, in a Git repository, an OCI registry (a registry that stores artifacts in the Open Container Initiative artifact format, the same registry format container images use), a Helm repository or an object-storage bucket, and it keeps the cluster matching what it finds there. It does this continuously. If someone edits a live object by hand, Flux notices on its next pass and puts the object back. If someone deletes a manifest from the source, Flux can remove the corresponding object from the cluster. The definition of the underlying idea, set out in [[concepts/gitops-pull-based-delivery]], is that the whole desired state is written down declaratively, stored in a versioned and immutable place, and applied by software agents instead of by people or pipelines running commands.

Two words in that definition carry most of the weight, so it is worth unpacking them now. "Declarative" means you describe the end state you want, such as "this Deployment has three replicas and runs this image", and you leave the steps to the system. The alternative, "imperative", means you issue actions, such as `kubectl scale` or a shell script that runs `helm upgrade`. [[concepts/declarative-vs-imperative]] covers the spectrum. "Pull" means the agent lives inside the target cluster and fetches desired state, instead of an outside CI server pushing changes in. The OpenGitOps working group states four principles: the desired state is declarative, it is stored versioned and immutable, agents pull it automatically, and agents continuously observe the real state and try to apply the desired one. The last two principles are what separate GitOps from a CI pipeline that happens to read YAML from Git. A pipeline that pushes once and never looks again does not qualify.

Who uses Flux? The Flux project's adopters page lists organizations that include Cisco, SAP, Kong, Grafana Labs, Sonatype, Maersk, Volvo Cars and Axel Springer, though it gives no per-entry detail. The page describes the list as a selection of organizations that self-identified as using any of the Flux projects in production, so read it as a self-reported roll of organizations that chose to add themselves, not as a measured market share ([[sources/research-flux-deep-dive]], [[entities/flux]]). The data file behind the page does let you name some entries, for example Xenit, Sortlist, Tietoevry, Nexxiot, SoulCycle and Luma Health, but it carries no migration story, incident report or measurement for any of them, so what those organizations do with Flux and how well it works is not documented ([[examples/the-flux-adopters-data-file-lists-xenit-sortlist-tietoevry-nexxiot-soulcycle-and-luma-health-among-others-with-no-write-ups]]). Argo CD keeps an equivalent self-reported file, `USERS.md`, naming Adobe, IBM, Intuit, Red Hat and Tesla among others. The two lists are the same kind of evidence, a roll call that organizations add themselves to, and neither gives outage information, so a longer list says something about visibility and nothing about reliability ([[examples/the-argo-cd-users-file-lists-452-self-reported-adopters]]).

The one adopter with a detailed public account in the sources is Morgan Stanley. A write-up by the Flux team, based on a FluxCon talk, reports "over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources", and says the firm moved to Flux from push pipelines that suffered from drift and made cluster rebuilds fragile ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]). Because that account was written about the adopter by the project and recounts the adopter's own talk, it is self-reported evidence, not an independent audit. No independent postmortem of a Flux outage and no neutral benchmark against Argo CD appear in the sources behind this document, and the caveat recurs wherever it matters. The public issue trackers of Flux, Argo CD, Config Connector and ACK contain individual reporter issues and reproductions, but no named organization with a date and an outage impact ([[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]). Web searches for such reports returned little, so the absence is weak evidence and does not prove that no such incident has happened.

The absence is specific to Flux, though, because a primary, organization-written postmortem exists for a pull-based GitOps outage on the neighboring tool. Skyscanner, a travel search company, published an account of a 2021 outage, when an engineer merged a templating change that was meant to alter no behavior, the change reached every region at once, and Argo CD reconciled each cluster against a configuration that listed no valid namespaces and deleted all of its services within about half an hour. Skyscanner first got its site serving from a single region and restored the rest over the next two days, and the post's own summary is that Argo CD did this "ultimately because we told it to" ([[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]]). Flux was not involved, and the post does not say which Argo CD sync options were set, so it is evidence about what a faithful pull-based reconciler does with a bad desired state, and not evidence about Flux's own behavior. Section 11 returns to it.

The thesis of this ramp-up is that Flux is a set of single-purpose, level-triggered Kubernetes controllers that pull desired state from Git, OCI or Helm sources and converge clusters with server-side apply, and that its design choices (composable controllers, pull delivery, inventory-based pruning, and explicit health and ordering) form a model worth borrowing when you design platforms of your own. The rest of the document earns that claim one layer at a time.

## 2. Mental model: Flux as Kubernetes controllers over KRM objects

To understand Flux you need three ideas that are not specific to Flux: the Kubernetes Resource Model, controllers, and the level-triggered reconcile loop.

The Kubernetes Resource Model, usually shortened to KRM, is the convention that everything in Kubernetes is an object with an identity, a `spec` and a `status`. The `spec` records what a user wants. The `status` records what a controller observed. The wiki's page on the [[concepts/spec-status-split]] explains that users and GitOps tools own `spec`, while controllers own `status`, and the API server enforces the split through a `/status` subresource. This sounds like bookkeeping, but it is the reason a GitOps tool can write a HelmRelease and then read back, from the same object, whether the release succeeded.

A controller is a program that watches objects through the API server and acts to make reality match their `spec`. The Kubernetes documentation calls controllers non-terminating control loops that move current state closer to desired state ([[concepts/reconciliation-loop]]). A Deployment controller makes ReplicaSets match a Deployment. Flux's controllers do the same trick on a higher level, except that the "reality" they converge is the contents of other objects in the cluster, and the "desired state" comes from outside the cluster. Because the cluster's API server, its storage (etcd) and its controller convention have no inherent tie to Pods, the same machinery can manage any declaratively described thing. [[concepts/universal-control-plane]] names this idea, and Flux is an example of using it for delivery.

The third idea is level-triggered reconciliation. An edge-triggered system reacts to an event, such as "a Pod was deleted". A level-triggered system reacts to the current state, such as "three replicas are desired, two exist". If a level-triggered controller misses an event, the next pass still converges, because it recomputes what to do from the state it can see ([[concepts/level-triggered-vs-edge-triggered]]). The wiki records the Kubernetes design stance as "Controllers are level-based to maximize fault tolerance", with watch events used as hints that make the loop faster, never as the source of correctness ([[decisions/events-as-hints-state-as-truth]]). Flux applies this literally. A Kustomization is re-checked on a timer, and events such as a new source revision are an optimization that skips the wait.

Level triggering has three consequences that recur through this document. First, reconcilers must be idempotent, meaning that running them twice leaves the system in the same state as running them once ([[concepts/idempotency]]). Second, the system is eventually consistent. Kubernetes does not promise that the gap between desired and actual state closes instantly, only that it keeps working toward the latest declared state ([[concepts/eventual-consistency-and-convergence]]). Third, the loop is relentless. It will revert intentional manual changes as readily as accidental ones, which [[findings/continuous-loops-override-intentional-changes]] calls the main operational lesson for platform teams.

Finally, Flux sits in the delivery layer of the tooling landscape. The wiki's landscape page ([[concepts/tooling-landscape]]) sorts tools into delivery (get manifests into a cluster and keep them there), provisioning (turn custom resources into cloud API calls) and platform or portal layers (what developers see). Flux and Argo CD are delivery tools. Crossplane, Config Connector, ACK and Cluster API are provisioning tools. Many comparisons go wrong by pitting a delivery tool against a provisioning tool, and section 13 returns to this.

## 3. The GitOps Toolkit: source, kustomize, helm, notification and image controllers

Flux is built from the GitOps Toolkit, which the Flux documentation describes as "a set of specialized tools and Flux Controllers; composable APIs; reusable Go packages for GitOps" ([[examples/flux-splits-gitops-into-single-purpose-controllers]]). Instead of one large operator, Flux ships several small controllers, each of which reconciles its own custom resource definitions (CRDs, the objects that extend the Kubernetes API with new kinds). The controllers communicate only through those custom resources.

The source controller fetches content from outside the cluster. It handles the kinds GitRepository, OCIRepository, HelmRepository, HelmChart and Bucket, fetches "on-demand and on-a-schedule", and packages the result as an archive (tar.gz or yaml) that other controllers read from inside the cluster. The consequence is that downstream controllers never talk to Git themselves. If you decide to move from Git to an OCI registry, you change the source object and leave the delivery objects alone ([[sources/research-flux-deep-dive]]).

The way the source controller serves those archives explains several behaviors that otherwise look odd. It runs a small file server inside its own process, and that server starts only after the controller has won leader election, so only the replica that holds the leader lease serves artifacts. Standby replicas deliberately report themselves as not ready, which the sharding page states directly: "Standby source-controller replicas stay not ready by design, because only the leader serves artifacts." The artifact store is local to that one process, and the stock installation declares only scratch volumes for it, which suggests that artifacts do not survive a pod restart and are rebuilt on the next reconcile. If that holds, a restart of the source controller leaves a window with no artifact server and probably an empty store, and a platform that restarts the controller often or runs it on evictable nodes should expect dependent controllers to wait. The GitRepository specification supports the general point by saying an artifact can "disappear from the storage due to e.g. the source-controller Pod being evicted". The sources consulted do not say how dependent controllers behave in that window. Flux's vertical-scaling guidance does recommend persistent volumes for artifact storage so that artifacts survive restarts, which is the documented way to avoid the empty store. The design lesson is that a separate fetching layer buys a clean handoff between controllers at the price of one stateful component whose availability the delivery controllers depend on ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]], [[decisions/single-replica-versus-leader-election]]).

The kustomize controller reads an artifact from a source, builds it with Kustomize (a template-free tool that customizes plain YAML with overlays and patches, described in [[entities/kustomize]]), and applies the result to the cluster. It also handles decryption of secrets with SOPS (a tool that encrypts the values in a file) using age, OpenPGP or cloud KMS keys, post-build variable substitution, health assessment, ordering, garbage collection and ServiceAccount impersonation. The helm controller does similar work for Helm releases. Helm, the Kubernetes package manager ([[entities/helm]]), normally runs as a command on a laptop or CI runner. Flux's helm controller instead uses the Helm SDK directly, so there is no in-cluster Helm server of the kind early Helm required (it was called Tiller), and a HelmRelease object declares what you want the SDK to do.

The notification controller works in two directions. Providers push events to chat systems and other endpoints, Alerts choose which events to send by severity and by involved object, and Receivers accept webhooks from Git hosts, registries and CI so that reconciliation starts at once instead of waiting for the next poll ([[examples/flux-notification-receivers-start-reconciliation-without-waiting-for-the-poll-interval]]). The image automation controllers scan registries for new tags and write the chosen tag back into Git, which section 9 covers.

The API types are published as Go packages, including `github.com/fluxcd/pkg/apis/meta`, and the controllers are ordinary controller-runtime programs, so anyone can read Flux objects with a standard client. That is a quiet but important property. A toolkit whose objects are plain Kubernetes objects can be observed with kubectl, queried by dashboards, composed by other controllers, and tested the way any other API is tested.

There is one more piece worth naming. The Flux Operator, a ControlPlane project, installs and manages Flux through a FluxInstance resource, so the Flux controllers themselves become declaratively managed objects, and it can also declare shards ([[entities/flux-operator]]). Separately, `flux bootstrap` installs Flux and commits its own manifests to the repository so that Flux manages itself from then on ([[concepts/gitops-pull-based-delivery]]).

## 4. Sources and artifacts: Git, OCI, Helm and Bucket, and choosing Git versus OCI

A source object tells the source controller where to fetch from and how often. Here is a minimal GitRepository, followed by the Kustomization that consumes it. The pair is the smallest useful Flux configuration.

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: platform-config
  namespace: flux-system
spec:
  interval: <how stale the fetched source may be>
  url: https://git.example.com/platform/config
  ref:
    branch: main
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: <how stale the cluster may be relative to the source>
  sourceRef:
    kind: GitRepository
    name: platform-config
  path: ./apps/production
  prune: true
```

The first object asks the source controller to check the repository on a schedule and publish an artifact whenever the branch tip changes. The second asks the kustomize controller to take the `./apps/production` directory from that artifact, build it, apply it, and re-check the result on its own schedule. The two objects are decoupled. The Kustomization does not know that the artifact came from Git, only that a source named `platform-config` produced one. This is what the Flux deep dive means when it says a team can change where manifests come from without changing how they are applied. The URL, names and intervals above are illustrative.

The four source kinds fit different situations. Git is the familiar choice: review happens in pull requests, history is the audit trail, and every engineer already knows the workflow. OCI registries store the same manifests as immutable, optionally signed artifacts. Helm repositories serve packaged charts. Buckets, meaning S3-style object storage, serve a directory of manifests. Morgan Stanley moved its source of truth from a self-hosted Git provider to S3 buckets, which the write-up gives as an availability and compliance choice, and it lists OCI artifacts as roadmap work ([[decisions/git-versus-oci-as-the-canonical-source]]).

The choice between Git and OCI is open in the wiki's sources, and the decision page frames it without resolving it. Pulling directly from Git gives the simplest mental model and a review workflow people already use. But each cluster then needs network access and credentials to the Git host, and branches and remote references are mutable. Pulling signed OCI artifacts decouples source control from deployment control. CI builds and signs the artifacts, pushes them to a registry, and clusters pull only what they can verify. The cost is an extra build step and registry infrastructure. ControlPlane's D2 reference architecture takes this path for regulated, multi-tenant fleets: three repositories (fleet, infrastructure and applications) are built and signed by CI, each cluster runs a FluxInstance, and ResourceSet templates generate per-tenant resources. ControlPlane summarizes the effect as having "decoupled source control from deployment control, while improving auditability and reducing risk" ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]). The claim is the vendor's own and no independent source corroborates it, so treat it as a design rationale, not a measured result.

The signature story is one place where the two main tools differ on documented features. The OCIRepository specification says a new artifact is archived "When the current OCIRepository digest differs from the latest fetched digest", and its `.spec.verify` field can "enable the verification of Cosign or Notation signatures". Cosign and Notation are two signing tools for OCI artifacts. Keyless verification, which proves who signed an artifact through a short-lived identity from an OpenID Connect provider and not through a long-lived key you must guard, is configured by stating which identities you trust and by pinning the Sigstore trust root they chain to. The Flux OCI cheatsheet adds a useful rule of thumb: "Using OCI instead of Git is particularly useful when the Git repository doesn't contain the final Kubernetes manifests." Argo CD also accepts OCI images as an application source. The Argo CD documentation, however, describes no signature verification for OCI sources. Its source-integrity page covers Git commit signatures made with GnuPG keys, and the OCI page contains no mention of signing, cosign or verification. That is a statement about the documentation, not proof the feature is absent from the code. No independent security review or measured benefit of signed OCI over Git exists for either tool in the sources, and neither project's documentation gives registry rate-limit guidance, so the case for OCI rests on the design argument above ([[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]]).

A related hazard applies whichever source you choose. If a manifest points at a moving remote reference, such as a Helm chart tag that can be re-pushed or a Kustomize remote base at `HEAD`, the same commit can render differently over time. The OpenGitOps requirement that desired state be versioned and immutable assumes that a revision identifies exactly one desired state, and a floating reference quietly breaks that assumption ([[findings/mutable-remote-references-change-what-a-commit-renders]]). Pin remote references to tags or digests, and change them through reviewed commits.

## 5. Kustomization and HelmRelease: the reconcile loop, intervals, retries and server-side apply

The Kustomization and the HelmRelease are where the work happens, so their timing and apply behavior deserve careful attention.

Every Kustomization carries an `interval`. On each interval the kustomize controller fetches the artifact, builds the manifests, applies them with server-side apply and detects drift. If a run fails, a separate retry interval sets the delay before the next attempt, and a timeout limits the time spent on build, apply and health checks in one run. Controllers add jitter, a small random offset to each timer, so that many Kustomizations do not all fire at the same instant and hit the API server together. Suspending an object pauses both reconciliation and drift correction, and an annotation can request a manual reconcile ([[examples/flux-kustomization-interval-and-retry-interval-set-the-loop-timing]]). Reconciliation also starts at once when the source revision or relevant metadata changes, so the interval is a safety net and a change is picked up sooner. How often a controller re-checks is a trade-off between how quickly drift is noticed and how many calls are spent on the API server and on external systems, and each tool and component chooses its own cadence.

Every Kustomization and HelmRelease declares its own interval, and the field is required, so there is no hidden controller-wide default to fall back on. A manifest that omits the interval is rejected instead of quietly adopting a cadence nobody chose. That interval is how often the controller re-checks the live objects against the source, which makes it the worst-case time before drift is noticed. A short interval notices drift quickly and spends more API calls, and a long one is cheaper and slower to react. Because Flux adds a small random offset to each timer, many objects with the same interval do not all fire at the same instant. The practical consequence is that the drift-correction latency you get is whatever you wrote in the manifest, give or take that offset, so set an interval deliberately on every object, which keeps the trade between drift latency and API cost visible in the repository ([[entities/flux]]).

Here is a fuller Kustomization showing the common operational fields.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: team-a-apps
  namespace: team-a
spec:
  interval: <how stale the cluster may be relative to the source>
  retryInterval: <delay before retrying a failed run>
  timeout: <limit for build, apply and health checks>
  sourceRef:
    kind: GitRepository
    name: team-a-repo
  path: ./production
  prune: true
  wait: true
  serviceAccountName: team-a-reconciler
```

Reading it from the top: re-check on a regular interval; after a failure, try again after a shorter retry interval instead of waiting for the full interval; put a time limit on each run; use the `production` directory from the team's repository; delete objects that have disappeared from the source; wait for the applied objects to become healthy before reporting Ready; and perform every write as the named ServiceAccount. The last line matters more than it looks, and section 8 explains why.

Why does Flux apply with server-side apply (SSA)? In the older client-side apply, the kubectl client computes a three-way merge using a `last-applied-configuration` annotation on the object. In server-side apply the API server merges a partial object into the live one and records, for each field, which manager owns it in `metadata.managedFields` ([[concepts/server-side-apply-and-field-ownership]]). The comparison page ([[comparisons/client-side-apply-versus-server-side-apply]]) lists the benefits: no annotation size cap that large CRDs exceed, conflicts that are detected instead of silently lost, and merge behavior defined by schema markers. For a GitOps agent the key benefit is that it can co-manage an object with other actors. Flux owns the fields it sets, an autoscaler can own `replicas`, and the API server knows who is who.

Flux uses SSA in two ways. It applies with SSA, and it runs an SSA dry run on each interval to detect drift: the server computes what would change if the manifest were applied, and a non-empty answer means the live object has diverged. This is elegant, because the diff is computed by the same server logic as a real apply, so server defaults are not mistaken for drift. [[findings/diff-is-not-apply-server-defaults-look-like-drift]] shows the contrary case in Argo CD, whose default diff compares inside its own process and therefore reports server-defaulted fields as differences until Server-Side Diff is enabled.

The HelmRelease adds Helm's own lifecycle. It covers `dependsOn`, install and upgrade remediation (retry, roll back or uninstall on failure), optional Helm tests, `valuesFrom` to pull values from ConfigMaps and Secrets, `chartRef` to an OCIRepository or HelmChart, CEL health checks, and a CRD policy ([[sources/research-flux-deep-dive]]). Its status records an audit trail alongside machine-readable health. The conditions are `Ready`, `Reconciling`, `Stalled`, `Released` and `TestSuccess`, and fields such as `observedGeneration`, failure counters, `lastAttemptedRevision` and `lastHandledReconcileAt` say what the controller tried ([[examples/flux-helmrelease-status-records-attempts-and-health]]). The reading rules are simple. `Ready` is the headline. `Reconciling=True` is normal progress. `Stalled` means the release will not advance without a change. And an `observedGeneration` lower than `metadata.generation` means a spec change is still waiting to be processed ([[concepts/conditions]]). Remember that a suspended resource keeps its last condition and can look healthy while doing nothing.

Helm drift detection is opt-in and staged. A HelmRelease can leave drift detection off, run it in a warning mode that only emits events, or run it in a mode that corrects the drift. This three-step ladder is a model for staged adoption, which section 10 returns to.

## 6. Ordering, health checks and dependsOn

Kubernetes applies objects concurrently and lets failures retry until dependencies appear. For many cases that is fine. But some orderings are not self-healing in a pleasant way: a custom resource applied before its CRD exists fails with "no matches for kind", and an application started before its database operator exists may log errors for minutes. The wiki treats CRD ordering as a recurring theme ([[findings/custom-resources-applied-before-their-crd-exists]], [[examples/servicemonitor-no-matches-for-kind-in-helm-and-argo-cd]]).

Flux handles ordering with three tools. `dependsOn` makes one Kustomization (or HelmRelease) wait until the objects it names are Ready. `wait` and `healthChecks` define what Ready means, so readiness covers the applied objects actually becoming healthy, and not only the apply call returning. Optional CEL expressions (a small expression language, the same one the API server uses for validation) allow custom readiness conditions. The documented pattern for CRDs is to put the CRD-providing controllers in one Kustomization and the custom resources in a second that depends on the first ([[examples/flux-dependson-and-health-checks-gate-rollout]]):

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: monitoring-config
  namespace: flux-system
spec:
  interval: <how stale the cluster may be relative to the source>
  sourceRef:
    kind: GitRepository
    name: platform-config
  path: ./monitoring/config
  dependsOn:
    - name: monitoring-operator
  prune: true
```

This Kustomization applies the monitoring custom resources, but only after the Kustomization named `monitoring-operator` reports Ready. If that first Kustomization uses `wait: true` or health checks, "Ready" means the operator Deployment is actually available, so the CRDs and their controller exist. The practitioner blog summarized in the wiki's example page on `dependsOn` and health checks recommends layering infrastructure, platform and applications this way. The important insight, stated in the wiki's example page, is that Flux does not abandon eventual consistency to get ordering. It adds health-checked dependencies so that the retry-until-ready behavior happens in a controlled sequence instead of as a burst of transient errors.

Health judgment is a harder problem than it looks, because Flux has to decide whether arbitrary custom resources are healthy. It relies on kstatus, a Go package in `sigs.k8s.io/cli-utils` that computes a generic status for any resource that follows the status conventions, using `observedGeneration` and the `Ready`, `Reconciling` and `Stalled` conditions ([[entities/kstatus]]). The weakness is that kstatus only works where conventions are followed. It evaluates a resource in a fixed order: deletion first, then a comparison of the top-level `status.observedGeneration` with `metadata.generation`, then the `Reconciling` and `Stalled` conditions, then type-specific rules for built-in kinds, then a fallback that looks for a `Ready` condition. A kind it has no rule for and that publishes no `Ready` condition falls to the unknown-resource strategy, which the kstatus README states as "assume they are always reconciled" ([[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]]). Notice also that `Reconciling` and `Stalled` are abnormal-true conditions, present and `True` only when something is in flight or wrong, so a controller that is not running at all looks the same as a healthy one, and the README says as much ([[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]).

The wider ecosystem has not settled which polarity condition authors should choose. Some conditions are positive and are true when things are well, such as `Ready`, while others are abnormal-true and appear only when something is in flight or wrong, such as `Reconciling` and `Stalled`. The Kubernetes API conventions do not recommend either polarity as a general rule, while kstatus's README still describes the abnormal-true pair. Flux sidesteps the argument by publishing `Ready` together with `Reconciling` and `Stalled` ([[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]]). The failure that follows is a race: a newly created object can carry an observed generation before its controller has published any conditions, and a generic readiness check may read that as ready, so Flux can start dependents too early. The reliable remedy is an explicit per-kind health expression, written in CEL, that waits for the condition the provider actually publishes ([[findings/premature-readiness-in-kstatus-based-tools]], [[examples/cluster-api-readiness-gates-flux-dependents]]).

The unknown-kind fallback raises a further worry that the sources leave open. A kind that publishes only an `Available`-style condition and no `Ready` condition can fall through to the fallback rule and be treated as reconciled even while `Available` is false. That conclusion follows from two documented facts, the missing `Ready` condition and the kstatus fallback rule, but no source states it or shows kstatus run against such a kind, and the result also depends on whether the provider's controller writes a top-level `observedGeneration`. The lesson is general: generic readiness depends on every provider following one convention, and when a project changes its condition vocabulary, consumers need explicit per-kind checks again.

Argo CD faces the same problem and answers it differently. It orders a sync by phase (PreSync, Sync, PostSync), then wave number, then kind and name, and advances only when the current wave is healthy, and for custom resources it runs Lua scripts (small programs in the Lua scripting language that Argo CD embeds) over `status`, noting that "CRDs do not follow a consistent or standardized status format" ([[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]], [[examples/argo-cd-rolls-up-child-health-with-lua-checks]]). kro derives ordering from references between resources inside one graph, and Crossplane lets composition functions withhold dependents until observed state allows them ([[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]). The distinction is that Flux and Argo CD order objects that a pipeline or Git delivers, while kro and Crossplane order resources inside one abstraction.

The two delivery tools differ visibly in how they judge kinds that cloud-provider controllers publish. Flux has no per-provider health logic at all. A Kustomization's `healthChecks` accept built-in kinds, Flux kinds and "custom resources that are compatible with kstatus", `wait: true` checks everything the Kustomization applied, and for kinds that do not follow the conventions `healthCheckExprs` supply CEL expressions named `current`, `inProgress` and `failed`, while `dependsOn[].readyExpr` can replace the readiness test for a dependency with a CEL expression. A provider's own `Ready` condition therefore reaches Flux through kstatus's generic handling. The Flux CEL cheatsheet carries examples for Crossplane kinds, but a search of the page for Config Connector's `cnrm` group and for ACK's `services.k8s.aws` group found nothing, so a team delivering those kinds writes its own expressions.

Argo CD went the other direction. It ships health scripts, written in Lua, for whole families of provider kinds, including Config Connector, ACK, Crossplane, Upbound, kro and Cluster API resources, so common provider objects are judged without extra configuration. Those scripts map each provider's own conditions, such as a terminal-error condition or a `Ready` condition, onto Healthy, Progressing and Degraded. Provider awareness has a cost, because Argo CD advances sync waves only when the current wave is healthy, so a provider object whose status a script mishandles blocks every later wave. There is also a structural limit: ACK conditions carry no `observedGeneration`, so a built-in script cannot tell whether the controller has seen the latest spec change and can report Healthy before it has noticed a change ([[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]]).

No source describes what Flux's kstatus does with ACK's abnormal-true `ACK.Terminal` condition, so whether a terminally failed ACK object looks failed or ready to Flux is open ([[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]], [[comparisons/health-and-readiness-models-across-tools]]). The same kstatus race appears with Crossplane resources: a resource that has no `Ready` condition yet reads as ready to a generic check, and a CEL expression that also compares the observed generation with the object's generation closes the gap.

## 7. Drift, pruning, ignore rules and deletion policies

Drift is the gap between what the source says and what the cluster holds. It arises when a human edits a live object, when another controller rewrites a field, or when the API server fills in defaults. Flux's detection mechanism is the SSA dry run on each interval, so, as [[findings/drift-detection-latency-is-the-interval]] puts it, the worst-case detection latency equals the interval. Webhook Receivers shorten the time to notice new commits but do not change how often live drift is checked.

Pruning is the other half of convergence. With `prune: true`, objects that were applied earlier but are missing from the current source revision are removed. Flux knows which objects it applied through an inventory recorded in the Kustomization's `.status.inventory`, not through Kubernetes owner references ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). The distinction matters. Owner references link a child object to a parent in the same namespace so that deleting the parent cascades ([[concepts/owner-references-and-garbage-collection]]). A GitOps agent applies objects it did not create through a parent object, so it needs its own inventory plus a finalizer (a token in `metadata.finalizers` that holds an object in a deleting state until a controller finishes cleanup, see [[concepts/finalizers]]) on its own top-level object. The wiki's comparison of garbage collection mechanisms makes the same point for Argo CD, Crossplane and Cluster API ([[comparisons/how-tools-garbage-collect-owner-references-inventory-and-finalizers]]).

Prune is a double-edged switch. Without it, "Git is the only source of truth. Without prune, deleted manifests leave orphaned resources", in the practitioner blog's words, which quietly breaks the claim that Git describes the cluster ([[findings/without-prune-flux-leaves-removed-manifests-running-as-orphans]]). With it, a bad edit to Git can delete real objects, and for provider-managed resources a prune followed by a provider delete can remove cloud infrastructure ([[findings/unintended-deletion-through-prune]]). Flux's controls are an annotation, `kustomize.toolkit.fluxcd.io/prune: disabled`, that exempts a single object, and a deletion policy for the case where the Kustomization itself is deleted.

The `spec.deletionPolicy` takes four values. MirrorPrune follows the `prune` setting. Delete removes the deployed objects. WaitForTermination removes them and waits for the children to leave etcd, so while it waits it is held up by any finalizer its children carry. Orphan leaves them running, the GitOps equivalent of `kubectl delete --cascade=orphan` ([[examples/flux-kustomization-deletion-policy-chooses-between-mirror-prune-delete-wait-and-orphan]]).

It helps to know the three propagation modes that Kubernetes itself offers for deleting an owner. In the background mode, which is the usual default, the owner is deleted at once and the garbage collector removes dependents afterward in no guaranteed order. In the foreground mode the owner stays visible with a deletion timestamp until every dependent that sets `blockOwnerDeletion=true` is gone, so an owner can hang if such a dependent cannot be deleted. In the orphan mode the dependents lose their owner references and keep running unmanaged until someone deletes them. Argo CD can prune with foreground deletion and accepts all three modes, so the two tools differ in what a prune waits for as well as in what they delete ([[comparisons/background-foreground-and-orphan-propagation-modes]]).

The mechanics behind these four values explain what each one waits for. Flux's reconciler adds its own finalizer before doing any other work, because a finalizer can only be added while the object has no deletion timestamp, so adding it first avoids a race with deletion. When the Kustomization is deleted, the controller prunes its inventory only if a decision function says to. A suspended Kustomization or one with an empty inventory never deletes anything. MirrorPrune follows `spec.prune`, Delete and WaitForTermination always prune, and Orphan never does. The wait in WaitForTermination polls the children and is limited by the Kustomization's own timeout. If the wait fails, the controller logs an error, emits an event and removes its finalizer anyway, so a stuck child cannot hold the Kustomization forever, although the child stays behind under its own finalizers.

What to do about such a child matters, because the quickest fix is also the riskiest. A finalizer is usually the only record that something outside the object still needs releasing, so patching `metadata.finalizers` to empty makes the object vanish without performing the cleanup the finalizer guarded. Practitioner write-ups list the results as cloud storage that keeps billing, StatefulSets on shared storage at risk of corruption, and pods that keep running after their API object is gone, and the Kubernetes documentation advises against manual removal unless you understand the finalizer's purpose and have met it another way. The Kubernetes finalizers blog adds that forcing a namespace through its `finalize` subresource can leave orphan objects in a namespace that no longer exists, and that re-creating the namespace may bring them back. The safer order is to find the blocking finalizer, read the owning controller's logs or source, and repair the condition that keeps it from finishing, and to clean up the external resource by hand if you must force removal ([[findings/forcing-a-finalizer-off-skips-cleanup-and-can-leak-billing-resources-or-corrupt-data]], [[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]).

The controller does the same if the impersonated ServiceAccount has already been deleted: it logs the stale objects and finishes finalization. Because the wait stops at the Kustomization's timeout, it does not hold the Kustomization for every child finalizer indefinitely ([[findings/flux-kustomization-uses-finalizers-fluxcd-io-and-removes-it-even-when-waitfortermination-times-out]], [[comparisons/finalizer-gated-teardown-across-argo-cd-flux-kro-and-cluster-api]]).

Ignore rules address the most common drift problem, which is a second writer that legitimately owns a field. A team runs Flux against workloads scaled by a HorizontalPodAutoscaler (HPA), and against CRDs whose `caBundle` is injected by cert-manager's cainjector (the cert-manager component that writes certificate authority bundles into CRDs). Flux reverts both. The Flux project's own blog tells of a SEV2 (a second-highest-severity production incident in the blog author's incident scale) in which Flux kept resetting replicas to a high value, the HPA kept lowering it, and the cluster autoscaler added and removed nodes in a loop, with "the two controllers ping-pong indefinitely" ([[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]]). Flux answers this with a Kustomization ignore list of JSON Pointer paths with an optional target selector, and the kustomize-controller specification documents its two policies, so the behavior does not rest on the blog post alone. If another server-side-apply manager of the Apply type owns the field, Flux strips it from its own apply payload ("Strip"), which the specification describes as relinquishing the controller's ownership and leaves the field with the other manager. If Flux is the sole Apply-type owner, it copies the live value ("Adopt"), which the specification says "preserves the current value without reverting changes made by Update-type operations", so edits made with `kubectl patch` or `kubectl edit` survive. The specification also says "Changes to ignored fields alone do not trigger a reconciliation". The blog also says `flux diff` honours the rules, a claim that only the blog makes. The distinction between Apply-type and Update-type managers matters for choosing a policy, because a controller that writes with plain updates, such as Config Connector's `cnrm-controller-manager`, would be covered by Adopt and not by Strip. That reading follows from the specification and Config Connector's source, although neither project states it. Remember that the HelmRelease's own drift-detection ignore list and the per-object `ssa` annotation described below are separate mechanisms ([[decisions/force-conflicts-or-strip-or-adopt-when-two-controllers-co-own-a-field]]). There is also a per-object `kustomize.toolkit.fluxcd.io/ssa` annotation with values `Override`, `Merge`, `IfNotPresent` and `Ignore` ([[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]).

The price of ignoring is easy to forget. Git changes to an ignored field are no longer applied, so if a team later wants Git to set the replica count, nothing will do it ([[findings/ignoring-a-field-in-flux-or-argo-cd-means-git-changes-to-it-are-no-longer-applied]]). Ignore only fields that another controller rewrites on purpose.

Two more details from the specifications decide how safely you can use these rules. First, a Flux rule is scoped by its `target` selector, and the kustomize-controller specification says "Omitting the `target` selector causes the rule to match **all** objects managed by the Kustomization". A rule written for one Deployment's `/spec/replicas` that leaves the target out therefore exempts that path on every other object in the Kustomization too, and real drift there goes uncorrected without any signal. The safe reading is to put a target selector on every rule ([[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]]). Second, Argo CD's equivalent, `ignoreDifferences`, behaves differently by default. Its sync-options page says Argo CD uses the rules "just for computing the diff between the live and desired state", so an ignored field stops showing as OutOfSync but the next sync still applies the full manifest from Git and can overwrite the field, which looks like a revert loop even though the diff is clean. A sync option can make the sync honor the rules, but the page adds that it is "only effective when the resource is already created in the cluster", so a first create still applies every field ([[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]], [[comparisons/flux-ignore-rules-versus-argo-cd-ignoredifferences-and-force-conflicts-for-drift-fights]]). Flux's rules act during drift detection and correction directly, which is the practical difference between the two. Config Connector adds a third variation worth knowing. One of its modes copies live cloud state into spec fields the author left unspecified. Because both Argo CD and Config Sync treat list fields as atomic, they see those additions as drift from Git and can keep rewriting the object. The remedy is to write the defaults out explicitly in Git, or to use the mode that does not copy state back ([[findings/config-connector-state-into-spec-merge-populates-unspecified-fields-that-argo-cd-and-config-sync-treat-as-drift-and-absent-is-the-default-from-1-123-1]]).

Where does Flux sit among SSA conflict policies? Like Argo CD, it force-applies its own intent by default and then offers escape hatches. The Kubernetes maintainers argue that controllers should force conflicts on objects they own, while CD systems are "more like users" and should surface conflicts to humans. Kluctl takes a third route and decides per field: it overwrites changes from known interactive managers such as kubectl and k9s, leaves fields it lost to other managers alone, and offers an annotation to force single fields ([[comparisons/ssa-conflict-policy-across-tools]], [[examples/kluctl-decides-field-level-conflicts-with-known-manager-heuristics]]). The wiki's decision page concludes that the sources do not settle the best default for platforms that run GitOps and in-cluster controllers on the same objects ([[decisions/force-conflicts-or-surface-them-to-humans]]). A second decision page lays out force against strip-or-adopt side by side and makes no recommendation, because no source or experiment compares them. It also notes the cost of the escape hatches: manager-scoped ignores depend on the other controller using server-side apply under a stable name, and a forced apply is not always enough when a stale manager still owns a list entry, as section 11 shows ([[decisions/force-conflicts-or-strip-or-adopt-when-two-controllers-co-own-a-field]]).

## 8. Multi-tenancy, impersonation and security lockdown

Pull delivery changes the security picture. A push pipeline holds credentials for every environment it deploys to, so a breached build server exposes all targets. A pull agent needs only read access to the source and uses in-cluster identity to write ([[comparisons/push-versus-pull-delivery]]). But the agent becomes powerful itself. By default the kustomize controller applies with its own identity, which is cluster-admin, so anyone who can commit a manifest to a repository Flux watches can create anything the controller can ([[findings/without-lockdown-flags-a-flux-kustomization-applies-with-the-controllers-own-identity]]).

Flux's answer is impersonation. A Kustomization or HelmRelease can name a ServiceAccount in `spec.serviceAccountName`, and the controller performs every write as that account, so ordinary Kubernetes RBAC decides what the tenant's repository may create. Platform administrators then lock the controllers down in three ways. They forbid references to sources in other namespaces, so a tenant cannot reach into another tenant's sources. They forbid remote Kustomize bases, which could smuggle in content that was never reviewed. And they set a default ServiceAccount, so that objects that name none run as an unprivileged account in the tenant's own namespace. If that account has no RBAC, deployments simply fail until a Role and RoleBinding are added.

The `fluxcd/flux2-multi-tenancy` reference repository shows the pattern. A fleet repository has `clusters/` for per-cluster entry points, `policies/` for cluster-wide resources, and `tenants/` for the provisioning manifests the administrators own. Each tenant's repository carries a `base/` directory and `staging/` and `production/` overlays. The repository states that "Sharing namespaces between tenants is not supported, as it would break the isolation guarantees" ([[examples/flux-multi-tenancy-repository-isolates-tenants-with-service-account-impersonation]]). A manifest that tries to create a ClusterRole or write into another namespace is rejected by the API server, not by Flux.

Morgan Stanley's version adds a self-service onboarding platform. It checks the requester's entitlements, registers the service in a configuration management database, primes the new namespace with a GitRepository and a Kustomization, and scaffolds the team's repository. The firm relied on ServiceAccount impersonation with Kubernetes RBAC, so a team's Kustomization can only create what its ServiceAccount is allowed to create.

Secrets are the next security question, because a pull agent that reads a repository must somehow deliver values that should never sit in the repository in plain text. Flux's answer is built into the kustomize controller. The Kustomization specification says "The only supported encryption provider is SOPS", decryption runs inside kustomize-controller, and encrypted files must "leave `metadata`, `kind` or `apiVersion` in plain text" so the controller can still identify the object. The documented key types are age, OpenPGP, cloud KMS and OpenBao or Vault, plus a service-account mode described as secret-less authentication to cloud KMS services. The SOPS guide notes that the decryption key is needed even to verify a file, because of the SOPS message authentication code, and Flux also documents Sealed Secrets, which only the controller in your cluster can decrypt. Argo CD takes the opposite default. Its secret-management page says "We strongly recommend" populating secrets on the destination cluster with an operator, naming Sealed Secrets, External Secrets Operator, the Secrets Store CSI Driver and Vault Secrets Operator as examples. It cautions against plugins that inject secret values while Argo CD renders manifests, such as argocd-vault-plugin, for three stated reasons: "Argo CD stores generated manifests in plaintext in its Redis cache" (Redis is the in-memory store Argo CD uses for rendered manifests), secret updates become coupled to syncs, and the approach is "incompatible with the 'Rendered Manifests' pattern". The project says it will keep supporting generation-based secrets but will not prioritize new features for that style. The page does not mention SOPS or ksops at all, so it states no Argo CD position on them, and the sources describe no failure modes for either approach beyond the plaintext-field requirement. The decision page lays the three options side by side and makes no recommendation ([[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]], [[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]]).

Reach is a related question, because a pull model is only as pull-based as its layout. A central Argo CD instance targets remote clusters that are registered with it, so delivery to a fleet is a push from a hub even though each Application pulls from Git. A separate project, argocd-agent in the `argoproj-labs` organization, describes the inverse, "instead of your control plane reaching out to remote clusters, lightweight agents reach back to a central hub", with Managed and Autonomous modes, but the project publishes no maturity statement and no adopter write-up exists, so its maturity is undocumented. Flux can also reach a remote cluster, because a Kustomization accepts `.spec.kubeConfig`, whose `configMapRef` form the specification recommends as secret-less authentication, but the more common Flux layout runs a controller set in every cluster, as the D2 design does ([[findings/argo-cd-reaches-into-registered-clusters-from-a-hub-and-the-argocd-agent-pull-model-is-a-labs-project-of-unverified-maturity]], [[decisions/reach-spoke-clusters-from-a-central-argo-cd-hub-or-with-argocd-agent-pulling-from-the-spokes]]).

Two caveats are worth carrying forward. First, no incident report of tenant escalation appears in the sources, so the risk rests on documentation. Second, blast radius is a general property of control planes. [[findings/blast-radius-and-privilege-centralization]] observes that a controller concentrating authority is a target, whether it is Flux, a Cluster API management cluster, or a Crossplane provider with a shared cloud credential. The D2 design reduces the exposure further by removing cluster-to-Git connections altogether. A vendor blog about Argo CD says it isolates tenants with Projects, while Flux uses namespaces and RBAC, but that comparison is opinion and should be read as such ([[comparisons/flux-versus-argo-cd-isolation-ordering-and-interface-according-to-a-vendor-blog]]).

## 9. Use cases: fleet management, multi-cluster, image automation, replacing helm upgrade in CI

**Fleet management and multi-cluster delivery.** The strongest evidence is the Morgan Stanley case above: more than 500 clusters, per-tenant impersonation, longer reconcile cadences and tuned concurrency, a source of truth moved to S3, a central Grafana dashboard built from kube-state-metrics, and notification-controller events fed to developer tools so tenants can see the outcome of their own deployments. The company listed sharding, OCI artifacts and Flagger as roadmap items (the write-up names Flagger without describing it), so no production sharding numbers are published, and a targeted search found no organization that says it runs sharded Flux ([[sources/research-gap-g1-named-adopters]]). The same pattern generalizes. A fleet repository has a directory per cluster, each cluster's Flux instance points at its own directory, and shared bases carry what is common.

Flux also pairs well with Cluster API for fleet lifecycle. Cluster API is a SIG Cluster Lifecycle project where a management cluster reconciles Cluster, Machine, MachineDeployment and MachineHealthCheck objects into real clusters ([[examples/cluster-fleet-lifecycle-with-cluster-api]]). Flux can deliver those objects from Git and hold back dependent Kustomizations until the Cluster API objects report ready, which is exactly where kstatus and CEL checks mattered in section 6. The management cluster, as the wiki notes, concentrates authority and becomes a single point of failure.

**Image automation.** A team wants patch releases and CVE fixes to reach clusters without anyone editing a manifest, while keeping Git as the record. The image update guide describes the aim as to "automatically deploy application patches (CVEs and bug fixes), and keep a record of all deployments in Git history". Three objects split the job: an ImageRepository scans a registry for tags, an ImagePolicy picks one using semver (semantic versioning, where numbers like 1.4.2 encode major, minor and patch changes), calver (calendar versioning, where the version number is built from a date) or regex rules, and an ImageUpdateAutomation edits YAML at `$imagepolicy` marker comments, commits and pushes. The ordinary loop then fetches the new revision and applies it, so the cluster still changes only through Git. The multi-tenancy reference repository enables this only for the staging overlay ([[examples/flux-image-automation-commits-new-tags-to-git-and-the-reference-repo-limits-it-to-staging]]). The risk is that a loose regex or a wide semver range can promote a release nobody reviewed ([[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]]).

The guide also names the promotion controls, and it stops at three. Production uses semver-selected release tags built by CI, while staging uses `branch-sha-timestamp` tags chosen by numerical or alphabetical policies. Pushing to a branch different from the checkout branch lets CI open a pull request, and the guide says "This way you can manually approve the image updates before they are applied on your clusters." A bad update is undone by narrowing the semver range, since "you can tell Flux to revert the image tag to a previous version". The guide prescribes nothing beyond those choices for keeping automatic updates out of production, and no third-party adopter write-up on staging-only or reviewed promotion exists in the sources, so the promotion policy adopters actually use is an open question ([[findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range]], [[decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation]]). One scale note belongs here as well: the documented sharding recipe deletes the image-reflector and image-automation Deployments from its shard sets, so image scanning stays on the default instance, as section 12 explains.

**Replacing `helm upgrade` in CI.** A Helm-heavy team runs `helm upgrade` from a CI job. A failed upgrade leaves the release in a bad state until someone notices, and nothing corrects the release if an operator edits a live object. The Flux guide for Helm users frames the alternative this way: "While the Helm client commands let you imperatively do things, Flux Helm Custom Resources let you declare what you want the Helm SDK to do automatically." A HelmRelease names a chart, supplies values inline or from ConfigMaps and Secrets, remediates failures by retrying, rolling back or uninstalling, optionally runs Helm tests, and can detect and correct drift ([[examples/teams-replace-helm-upgrade-in-ci-with-flux-helmrelease-objects]]). The deeper change is from a one-shot push to a continuous loop, which is the same difference the OpenGitOps principles draw.

**Delivering infrastructure custom resources.** Flux and Argo CD both deliver Config Connector, ACK and Crossplane objects from Git. This is the two-layer loop: the GitOps agent reconciles Git into the Kubernetes API, and a domain controller reconciles the API into reality ([[concepts/gitops-pull-based-delivery]]). On Google Cloud, Config Connector then acts with its own IAM service account, so developer permissions are decoupled from cloud rights, but anyone who can create a resource gains the controller's rights ([[examples/google-cloud-shops-deliver-config-connector-resources-from-git-while-the-controller-s-own-identity-makes-the-cloud-calls]]). Flux publishes no official document about Crossplane, kro, Config Connector, ACK or Cluster API beyond the generic mechanics, but individual reports are enough to describe how the combination behaves, and most of the reports are cautionary.

Start with what Flux does by default. It treats a Crossplane composite or a kro instance as any other custom resource: `healthChecks` and `wait` judge it through kstatus or CEL, and `dependsOn` waits on it. Resources that Crossplane or kro create from the composite are not applied by Flux, so they sit outside Flux's inventory. It follows that Flux needs no owner reference or tracking annotation on composites, in contrast to Argo CD, which needs owner references and tracking identifiers before it can track kro resources, but no Flux page states this, so treat it as an inference. No Flux or kro document describes using the two together ([[findings/flux-tracks-composite-resources-through-its-inventory-and-kstatus-or-cel-health-checks-and-documents-no-owner-reference-recipe-or-kro-guidance]], [[examples/kro-resources-need-owner-references-and-tracking-ids-to-be-tracked-by-argo-cd]]). A second writer is the usual trouble. A controller that enforces its own desired state, as kro does for the resources an instance creates, resets fields that another controller changes on its next reconciliation. A Flux Kustomization that also sets fields on a kro-created resource would be one of those outside writers, so the two would fight over the field. That reading is an application of the principle, not something a source describes.

ACK is the clearest case of delivery interacting with a provider controller, and the evidence comes from individual reporters, not from maintainer-confirmed behavior. ACK controllers resolve reference fields (the `*Ref` fields) and write the resolved value back into the custom resource. Flux's server-side apply then restores the Git value, the controller's diff sees changed desired state, and the result can be needless re-provisioning, such as a service being redeployed, at the next re-check of the cloud resource. ACK's runtime sends merge patches and records no server-side-apply field manager, so the two writers do not coordinate field ownership. The deletion side is sharper. ACK deletes the AWS resource when the Kubernetes object is deleted, and its documented lookup order for the deletion policy is the resource annotation first, then the namespace annotation, then the controller default, with the first match winning. One reporter showed, with reproduction scripts, that a prune by Argo CD or Flux, or a Helm upgrade that removed an object, led to AWS deletion, and that a controller-wide `retain` did not help because every chart-rendered resource carried an explicit delete policy. Under the first-match rule that outcome is what the documentation predicts. The reproductions ran against a mock AWS and the account is a single reporter's, so treat it as a well-documented warning, not a postmortem. The practical reading is that a controller-wide `retain` is the weakest layer, so set `retain` on the resource itself or add an agent-side opt-out such as Flux's per-object prune opt-out annotation or Argo CD's prune opt-out ([[findings/ack-deletion-policy-resolves-from-the-resource-then-the-namespace-then-the-controller-default-and-one-reporter-says-chart-stamped-delete-defeats-a-controller-wide-retain]], [[decisions/protect-a-provider-managed-object-from-gitops-prune-with-a-provider-retain-policy-or-an-agent-side-prune-opt-out]]).

Config Connector adds installation-mode questions that matter before you automate delivery. Google's installation page recommends namespaced mode for most uses and says it provides better permission isolation. In namespaced mode each enabled namespace needs its own `ConfigConnectorContext` naming that namespace's Google service account, while cluster mode takes exactly one credential for every resource, even across projects. A GitOps tenancy design that gives each team a namespace and a ServiceAccount, as section 8 describes, maps naturally onto namespaced mode, and an example page records how namespaces map to projects ([[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]], [[examples/config-connector-namespaced-mode-maps-namespaces-to-projects-and-service-accounts]]). Teardown is the weak point under either agent. A practitioner reports that Config Connector has no Terraform-style dependency graph and that Argo CD deletes children with no ordering, leaving objects in a failed delete after the parent goes, and a Config Connector design document describes a child whose parent was deleted first sticking on `DependencyNotFound`. The first is a single-author account and no documentation describes ordered teardown.

The Argo CD half of that claim is not corroborated. Argo CD's own documentation says that pruning reverses the wave order, so the practitioner may be describing a different kind of delete, such as removing a whole Application with a cascade, and no source says whether a cascade delete honors waves. The post does not say which delete it means. The author's workaround is a recurring job that removes the finalizers from BigQuery tables stuck in `DeleteFailed` after their dataset object is gone, and he argues this is safe only because deleting a dataset in Google Cloud also deletes its tables. That argument holds only where the parent's deletion removes the child in the cloud, and it is the same forced-finalizer trade-off described in section 7 ([[findings/config-connector-has-no-terraform-style-dependency-graph-and-argo-cd-deletes-children-without-ordering]], [[findings/a-config-connector-design-document-says-a-child-whose-parent-was-deleted-first-sticks-on-dependencynotfound-and-no-read-documentation-describes-ordered-teardown]]). Where a composition wraps these provider objects, the ACK documentation's kro guide is the one first-party worked example: it composes an S3 bucket, a DynamoDB table and a Deployment and deletes the Deployment before the AWS resources. No worked example of Crossplane composing ACK or Config Connector objects appears in the sources, and Crossplane's function auto-ready and kro's `readyWhen` both depend on the provider's `Ready` condition ([[examples/the-ack-docs-kro-guide-composes-an-s3-bucket-a-dynamodb-table-and-a-deployment-and-deletes-the-deployment-before-the-aws-resources]], [[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]]). If you must choose between those provider routes on Google Cloud, a decision page sets out using Config Connector directly, wrapping it in Crossplane through the Kubernetes provider, or using a Crossplane GCP provider, and records that a Crossplane maintainer said the wrapped route is not a replacement for a provider ([[decisions/use-config-connector-directly-wrap-it-in-crossplane-through-the-kubernetes-provider-or-use-a-crossplane-gcp-provider]]).

## 10. Design principles to take from Flux

Flux is useful to learn for its own sake, but its design is more valuable as a set of choices you can reuse. Each principle below states a reason, not only a preference.

**One controller per concern.** Flux separates fetching, rendering, Helm management, notification and image updates. The wiki cites it as the clearest example of the single-responsibility split, and compares it with ACK (split by AWS service) and Cluster API (core versus provider controllers). The three cut along different axes, function, external API and portability, and the wiki offers no performance comparison among them ([[comparisons/how-flux-ack-and-cluster-api-split-controllers]]). The reason to prefer small controllers is that each has a narrow API, a narrow failure mode and independent upgrade and scaling choices. Sharding in section 12 works only because the controllers are separable.

**Communicate through objects, not calls.** The controllers meet only in custom resources, so every handoff is visible in the API, inspectable with kubectl, and replaceable. When the source layer is separate from the delivery layer, changing from Git to OCI is a one-object edit.

**Level-triggered with events as hints.** The periodic pass guarantees correctness, and webhooks and revision changes only reduce latency. This is the design in [[decisions/events-as-hints-state-as-truth]], and it is the reason a lost webhook produces delay, not divergence.

**Pull, not push.** An agent inside the target holds its own credentials and needs only read access to the source. The reasoning is credential locality: compromising a build server should not hand over every environment. The principle has a price, which is that the agent becomes a powerful identity that must be constrained, and Flux supplies impersonation and lockdown settings for exactly that purpose.

**Inventory-based pruning.** Because Flux records what it applied, it can delete exactly that set when it disappears from the source. Owner references cannot do the job for objects a controller did not create through a parent, and labels alone are fragile. The inventory is an explicit ledger, and the cost is that you must decide what a missing entry means, which is what `prune`, the opt-out annotation and `deletionPolicy` are for.

**Explicit health and ordering.** Flux makes readiness and dependency visible in configuration (`wait`, `healthChecks`, `dependsOn`) instead of hoping retries sort things out. It admits that generic health is hard and provides CEL for kinds that do not follow kstatus.

**Separate detection from correction.** Helm drift detection offers `disabled`, `warn` and `enabled`. The wiki's decision page on staged adoption recommends exactly this ladder: observe first, correct selectively for well-understood workloads, then enforce broadly with documented ignore rules ([[decisions/staged-adoption-of-automated-drift-correction]]). Argo CD's manual sync, Crossplane's Observe policy and tofu-controller's detection-only mode follow the same idea. The principle is that a team should see drift before it lets software act on it.

**Make every dangerous action opt-in and every loop pausable.** Prune, force, drift correction and image automation are switches. `suspend` stops the loop, and the wiki's comparison page notes that every tool it covers ships an off-switch for the same reason: continuous loops override intentional changes ([[comparisons/reconcile-cadence-and-off-switches-across-tools]]). The corollary is that an off-switch needs monitoring, or a forgotten suspension becomes silent drift.

**Compensate for upstream limits, and say so.** Helm will not upgrade or delete CRDs "due to unintentional data loss dangers". Flux's HelmRelease offers CRD policies for install and upgrade: skip CRDs, create them, or create and replace them. Replacing updates existing CRDs but deliberately does not delete removed ones, leaving cleanup to a human ([[examples/flux-helmrelease-crd-policies-createreplace-and-dependson]], [[findings/helm-does-not-upgrade-or-delete-crds]]). A good wrapper improves on the tool beneath it without hiding its safety choices.

## 11. Pitfalls: orphans, prune accidents, SSA migration, silent suspended failures, circular dependencies, HPA fights

The evidence on pitfalls comes from documentation, issue trackers and one practitioner blog. No independent Flux postmortem exists in those sources, so severity is inferred and each item below says what kind of evidence stands behind it.

**Orphans and prune accidents.** These are the two sides of the same switch, covered in section 7. Mitigations are to enable `prune` together with `healthChecks`, run `flux diff` or `kubectl diff` before merging risky changes, annotate objects that must never be pruned, and pick `Orphan` for critical resources. For managed cloud resources, a Git removal becomes a prune followed by a provider delete unless Delete is excluded from the provider's management policies ([[findings/unintended-deletion-through-prune]]). As section 9 explains, a controller-wide retain setting can be overridden by what a chart stamps on each resource, so the protection belongs on the resource itself. The Skyscanner outage from section 1 is the named, dated illustration of the worst case on the Argo CD side, where a reconciler enforced a corrupted configuration across every region. Its lessons transfer directly to Flux: a templated configuration file that looks like data needs tests and a staged regional rollout before a controller applies it globally, and the same pull model that spread the damage also made recovery routine once correct configuration was restored ([[findings/templated-configuration-that-looks-like-config-is-code-and-needs-tests-and-a-regional-rollout-before-a-gitops-controller-applies-it-globally]]). Argo CD treats prune as an explicit opt-in and adds an allow-empty guard, and its replace and force sync options can recreate resources and cause outages ([[findings/argo-cd-replace-and-force-sync-options-can-recreate-resources-and-cause-outages]]). Flux's `force` recreates objects on immutable-field changes and should be set only temporarily because it can cause downtime.

**Client-side to server-side apply migration.** Moving a cluster from client-side to server-side apply, or adopting resources that were applied by hand, can strand fields. The older manager still co-owns the fields it set, and forcing cannot take ownership of a field that no longer appears in the applied object, in a maintainer's phrase "you can't force ownerships for non existing fields", so fields removed from Git stay in the cluster. The remedy is to clear the stale manager's entry from the object's `metadata.managedFields`, or to have the controller take ownership from named managers ([[examples/flux-migration-from-client-side-apply-strands-removed-fields]], [[findings/client-side-to-server-side-migration-leaves-stale-co-owners]]). A related case is a legacy manager co-owning a list entry's key. Removing the container then leaves a half-removed object, and the dry run fails on every reconcile, so the controller never gets far enough to fix the ownership. A takeover that happens only after a successful dry run can never help here, so the kustomize controller can instead take over field ownership from named managers before the dry run. A maintainer called this kind of takeover dangerous, and the documentation bears that out. It transfers all fields owned by the managers you name, not only the field that wedged the dry run, it prunes fields missing from the source, and the ownership change is not reverted if the apply then fails. Manager names are matched exactly rather than by prefix. It is a recovery tool, to be used only on stuck objects and removed once they reconcile ([[findings/the-flux-pre-dry-run-takeover-transfers-all-fields-of-the-named-managers-and-is-not-reverted-if-the-apply-fails]], [[findings/a-stale-manager-owning-a-list-entry-key-breaks-the-dry-run-after-removal]]). Crossplane hit the same class of problem moving composed resources to composition functions, and Argo CD automates a migration to its own field manager.

**Field ownership blocks drift correction.** A community discussion shows a HelmRelease with drift detection enabled and a Service port edited by `kubectl edit`. `Service.spec.ports` is a list keyed by port and protocol, and the `kubectl-edit` manager still owns the entry, so the dry run fails with duplicate port names and the helm controller stops at "unable to determine cluster state". Ignore rules do not help, because they act on the result of the diff and the diff never gets to produce one. The remedy is to tell the helm controller which stale managers to remove. Reading its source shows how this works: when drift detection is on and that list is non-empty, the controller patches `managedFields` on each live object to remove the listed managers before its dry-run diff runs. That is the reverse order from the kustomize controller's ordinary takeover, which happens only after a successful dry run, so a stale owner that wedges the diff can be cleared without a separate recovery step. Two details deserve care. The sources do not describe how the function that rewrites `managedFields` works internally, and the helm controller's upgrade path always forces conflicts, so a dry-run failure caused by a validation error in the merged object, not by a conflict, is a different failure that force does not fix ([[findings/helm-controller-takes-over-override-manager-fields-before-its-dry-run-diff-the-reverse-of-kustomize-controller]], [[examples/flux-helmrelease-drift-correction-blocked-by-edited-service-port]]). The lesson is that self-healing depends on the diff succeeding, and the diff depends on clean field ownership.

**Webhooks without dry-run support.** Because Flux dry-runs first, an admission webhook (a call the API server makes to an external service to validate or modify an object before storing it) that does not declare `sideEffects` of `None` or `NoneOnDryRun` makes the apply fail with "admission webhook does not support dry run". The fix belongs on the webhook configuration, not in Flux ([[examples/flux-dry-run-fails-against-webhooks-without-dry-run-support]]).

**Silent failures.** The practitioner blog lists three ways Flux looks healthy while not delivering: a suspended resource stops reconciling and drift builds up unnoticed; without webhook Receivers, a change waits for the next poll; and running a manual reconcile without asking it to refresh the source first reconciles against the source's last fetched revision, so the command succeeds without picking up the new commit. It recommends alerting on `gotk_reconcile_error_total` and `gotk_suspend_status` ([[findings/suspended-resources-polling-lag-and-a-missing-with-source-flag-make-flux-failures-silent]]). This is a secondary source, but the failure modes follow directly from the design in section 2.

**Circular dependencies.** The HelmRelease reference says circular dependencies "must be avoided, otherwise the interdependent HelmRelease resources will never be reconciled". Each waits for the other to be Ready, so neither starts, and the failure is a stall, not an error. The sources do not say whether Flux detects the cycle at admission. kro, in contrast, rejects cycles at definition time ([[findings/circular-dependson-chains-between-flux-resources-never-reconcile]]).

**HPA fights.** Covered in section 7. The general diagnosis, from [[findings/controllers-fighting-over-fields-cause-revert-loops]], is that drift is often two writers disagreeing, and the first step is to find the second writer. Argo CD saw the same pattern when argocd-image-updater rewrote child Application specs ([[examples/argo-cd-app-of-apps-out-of-sync-from-image-updater]]).

**Failure and retry behavior differs across tools.** Flux keeps retrying a failed reconcile on its retry interval until the object converges. Argo CD does not retry a failed sync of the same commit and parameters unless retry is configured, while controller-runtime retries forever with exponential backoff ([[examples/argo-cd-does-not-retry-a-failed-sync-of-the-same-commit-unless-retry-is-configured]], [[comparisons/retry-and-backoff-controls-across-tools]]). Retrying without limit risks amplification, and refusing to retry risks silent non-convergence.

**A cross-tool summary.** The table lists how each stack deals with the problems above.

| Problem | Flux | Argo CD | Other tools |
|---|---|---|---|
| Second writer on a field | `.spec.ignore` Strip and Adopt (documented in the kustomize-controller specification), `driftDetection.ignore` on HelmRelease, `ssa` annotation | `ignoreDifferences`, Server-Side Diff | Crossplane `initProvider` and `managementPolicies`; Kluctl per-field force |
| Removal from source | `prune` plus inventory, `deletionPolicy` | Prune as an explicit opt-in, resources finalizer on the Application | ACK retain policy; Config Connector `abandon` annotation |
| Ordering | `dependsOn`, `healthChecks`, `wait`, CEL | Phases and waves, Lua health | kro graph references; Crossplane function readiness |
| Readiness of custom kinds | kstatus plus CEL | Lua per CRD | Crossplane `Synced` and `Ready`; Cluster API conditions |
| Pause | `suspend` | Disable automated sync | Crossplane pause annotation; Config Connector reconcile-interval off-switch |
| Secrets | Controller-side SOPS only; Sealed Secrets guide | Destination-cluster operators recommended; generation plugins cache plaintext in Redis | No source compared |
| Health of provider kinds | kstatus plus CEL; Crossplane examples in the cheatsheet | Built-in Lua for Config Connector, ACK, Crossplane, Upbound, kro and Cluster API kinds | ACK conditions lack `observedGeneration` |
| Signed OCI sources | Cosign and Notation verification in `.spec.verify` | OCI sources supported; no signature verification documented | No source compared |

The table is a quick reference ([[comparisons/exemption-and-ignore-controls-across-tools]], [[comparisons/deletion-policies-across-gitops-and-provider-tools]]), and the reasons behind it matter more than the cells. For a second writer on a field, Flux and Argo CD both start from a force-everything stance and then offer escape hatches. Flux lets you strip or adopt fields per object or per path, and the specification documents how each policy behaves, although no source compares forcing with strip-or-adopt, so the choice between them rests on reasoning and not on measurement. Argo CD's `ignoreDifferences` hides differences from its comparison and its Server-Side Diff makes the comparison use the server's own merge logic. The provisioning tools approach it from the other side, because they expect other writers (cloud defaults, other controllers) and so give each resource a policy for which fields to leave alone. The trade-off is between predictability and surprise. A tool that always reverts is simple to reason about but fights every legitimate co-owner, and a tool with per-field rules is flexible but needs a human to decide which fields are safe to ignore.

For removal from the source, Argo CD pairs prune with extra guards such as allow-empty protection, whereas Flux asks you to set `prune` and then offers explicit switches (the opt-out annotation and `deletionPolicy`) for the dangerous cases. Provider tools differ again, because deleting the Kubernetes object can delete real cloud infrastructure, so their policies (ACK retain, Config Connector `abandon`, Crossplane management policies) exist to separate the life of the object from the life of the cloud resource. Ordering and readiness follow the same logic. Flux and Argo CD order objects delivered from outside and need generic or scripted health checks to know when a custom kind is ready, while kro and Crossplane order resources inside one abstraction and can read readiness from their own graph. Pause is the simplest row, since every tool has an off switch, and the cost of each is that a forgotten pause quietly becomes drift.

## 12. Scaling Flux: intervals, concurrency, sharding and memory

Scale in a controller is several separate limits, not a single number. The wiki's scale page lists four constraints inside a client-go controller: the informer cache holds every watched object, so memory grows with what is watched; the workqueue never processes one key concurrently, so throughput depends on the worker count and the time per reconcile; the client rate limiter throttles requests before they reach the server; and leader election (replicas of a controller agree on one active instance via a lock object, and the rest wait as standbys) means only one replica reconciles ([[concepts/scale-and-sharding]], [[concepts/informers-reflectors-and-workqueues]]). The informer cache is an in-memory copy of everything watched, and the Kubernetes blog says it has no eviction ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]).

Flux's controllers use two cache-narrowing options that are worth knowing. Each of the source, kustomize and helm controllers is its own process with its own informer cache, so the cache is not shared between them. No document says so explicitly, but each controller's `main.go` builds its own manager. Each controller can narrow its cache to the objects it should handle, selecting by label or by namespace. The same label selector is the sharding key described below, so one mechanism both shrinks memory and splits work. The second option concerns Secrets and ConfigMaps: by default controllers read them directly from the API server instead of caching them, which keeps memory and cluster-wide list and watch permissions low at the cost of more API-server load. Caching them reverses that trade, and the Flux runtime package warns that it causes "increased memory usage and cluster-wide RBAC permissions (list and watch)", so the choice is API-server load on one side and memory and privilege on the other ([[findings/flux-controllers-keep-separate-caches-narrowed-by-a-watch-label-selector-and-leave-secrets-and-configmaps-uncached-by-default]], [[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]).

Flux's documented order of response is to tune before you split.

**Lengthen intervals.** Fewer scheduled reconciles mean less API load, at the cost of slower drift correction. Morgan Stanley did this.

**Raise concurrency and resources.** A controller can be allowed more parallel reconciles, which are its workqueue workers, and given more CPU and memory. Kustomize builds can be sped up by giving them a memory-backed scratch directory, at the price that, in the vertical scaling page's words, "tmpfs will count against the controller's pod memory usage", and artifacts can be placed on persistent volumes so they survive restarts. The source controller can also cache Helm repository indexes. Raising concurrency shifts load onto the API server or onto pod memory, so it is a trade and not free capacity ([[examples/flux-controllers-expose-worker-concurrency-and-helm-cache-size-as-tuning-knobs]]).

**Do not add replicas for capacity.** "Extra replicas of a Flux controller are failover standbys. Only the elected leader reconciles." Adding replicas buys availability, not throughput ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

**Shard when one instance cannot keep up.** Sharding runs several copies of a controller under unique names, such as `source-controller-shard1`. Each shard reconciles only objects carrying its own shard label, while the default controllers skip labeled objects so nothing is handled twice. Source, kustomize and helm controllers can be sharded, but the sharding page says of the notification controller and the source-watcher, another Flux component that this document does not otherwise cover, that "these controllers do not support sharding". The page's example also deletes the image-reflector and image-automation Deployments from the shard sets, so the documented recipe shards the source, kustomize and helm controllers and leaves image automation to the default instance. Whether the image controllers can be sharded at all is not stated in the sources, and they do not describe the Flux Operator's own sharding guide. The practical consequence is that a plan aimed at relieving notification or image-scanning load will not be helped by adding shards ([[findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded]], [[sources/research-scale-and-sharding]]). Each shard also elects its own leader. When a shard label is set, the leader election identity is derived from it, so a shard does not compete with the default instance for the same lease, and the source notes that the process is presumed to terminate when it loses leadership ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]]).

```yaml
# Illustrative: a HelmRelease placed on a shard by label
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: tenant-b-ingress
  namespace: tenant-b
  labels:
    sharding.fluxcd.io/key: shard1
spec:
  interval: <how stale the cluster may be relative to the source>
  chart:
    spec:
      chart: ingress-nginx
      sourceRef:
        kind: HelmRepository
        name: tenant-b-charts
```

The label places the release on the controller instance watching `shard1`. The catch is that the HelmRepository it references, and the HelmChart generated from it, need matching labels too, otherwise the pieces land on different controllers. The sharding page states the rule: "Source object kinds which have a dependency on another kind (i.e. `HelmChart` on a `HelmRepository`) need to have the same labels." Because a HelmChart is generated from a HelmRelease and not written by hand, its label is set through the HelmRelease's `.spec.chart.metadata.labels`, which the page describes as setting "the sharding key on the generated Flux `HelmChart` object". The default controllers are told to ignore any object that carries a shard key, so a HelmRelease that carries the shard key while its chart does not would have its chart handled by a different controller than the one that needs the artifact. The documentation does not spell out the symptom a user would see, so the exact error is unknown ([[findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels]]). A parent Kustomization can bulk-label children through `commonMetadata` and patches, and the Flux Operator removes the manual work by declaring shards in the FluxInstance spec, though the labels still have to be applied ([[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]], [[examples/flux-sharding-splits-reconciliation-across-label-selected-controller-instances]]).

Is sharding needed yet? Flux's documentation advises sharding at the scale of "tens of thousands of applications", and the decision page on this question notes that no source states a precise threshold. A targeted search for named adopters found no organization that says it runs sharded Flux with a shard count or object count. Morgan Stanley, the best-known large adopter, lists "Exploring sharding Flux controllers" under "Looking Ahead", so it is not a documented sharding user. The evidence that does exist is thin and mostly anonymous. One hub-and-spoke operator reported reconciliation storms when many objects fired during nightly deploy windows and was advised to shard or tune ([[examples/a-hub-and-spoke-flux-user-reported-nightly-reconciliation-storms-and-was-told-to-shard-or-tune]]), and another reported stale artifacts that remained on the old source controller after objects moved to a different shard ([[findings/objects-that-leave-a-flux-shard-keep-stale-artifacts-on-the-old-source-controller]]). These show that people shard and that sharding has real operational edges, but none is a named adopter with numbers.

One named project automates sharding. Cozystack, which turns commodity servers into a Kubernetes-based cloud, runs an operator that creates helm-controller shards, places tenants onto them in proportion to how many HelmReleases each tenant has, and sizes the shard count from the total workload. It is a design pattern, not a measured result, and no production outcome is published, but it shows the tenant-per-shard placement idea ([[entities/cozystack]]). The reasonable reading, which no source states as a rule, is to tune first and shard when one instance reaches its limits ([[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]], [[comparisons/flux-scaling-options-intervals-concurrency-sharding-and-source-choice]]).

Argo CD partitions by destination cluster instead of by label, and offers several assignment algorithms that differ in how evenly they spread clusters across controller replicas. Cluster sharding fits hub-and-spoke setups (one central cluster running the delivery tool and pushing to many smaller workload clusters) but cannot divide one very large cluster, whereas label sharding can separate tenants inside one cluster at the price of label discipline ([[comparisons/flux-label-sharding-versus-argo-cd-cluster-sharding]]).

A word on API Priority and Fairness (APF), the API server feature that queues and prioritizes incoming requests by flow so that no single client can starve the rest. When the server has APF enabled, a well-behaved controller can turn off its own client-side throttling and honor the server's retry signals instead, because two independent throttling layers can disagree and slow each other down. Flux's controllers are built to do this. No published incident or postmortem ties Flux, sharded or not, to APF throttling in the sources behind this document, so read this as an open question and not as proof that no such incident happened.

Finally, remember that constant reconciliation costs something. Level triggering means repeated work, and for controllers that manage external systems every cycle can be a quota-consuming API call. Flux and Argo CD read the Kubernetes API and Git, so frequent checks are cheap, whereas controllers that manage external systems pay an API call, and sometimes a quota cost, for every real re-read of the cloud resource, and so tend to re-check far less often. How often a controller re-checks the outside world is a trade-off between how quickly drift is noticed and how many calls are spent on the external API, and each tool and provider picks its own cadence.

Config Connector sits much closer to Flux than to ACK in cadence. Its three reconciler families, the direct controllers and the two older code paths that wrap Terraform and Google's Declarative Client Library, all end a successful pass through one shared jittered requeue function, so the kind of controller behind a resource does not change how often it is re-checked, and the cadence can be overridden per resource. Drift detection is the reconcile itself and not a separate poll, so the worst-case detection delay is the interval. Config Connector can also switch periodic drift correction off for a resource, and the reconciliation page states that doing so is irreversible, which makes it a very different off-switch from Flux's `suspend`. No measured drift latency from a live cluster appears in the sources ([[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]]).

The word resync names three different mechanisms across these tools. In client-go it replays the informer's cached state to the event handlers without contacting any outside system (an informer is the client-side cache a controller keeps of the objects it watches), in ACK a requeue triggers a fresh read from the cloud API, and kro's equivalent setting appears, from its source, to behave like the client-go one, although its own description of the setting suggests a full re-list, so the sources disagree on what it does. When you compare cadences across tools, first ask whether a cycle touches the external system at all, and note that the sources do not state whether the tools' settings describe comparable mechanisms ([[findings/the-word-resync-names-three-different-mechanisms-in-client-go-kro-and-ack]], [[findings/cost-of-constant-reconciliation]], [[decisions/choosing-a-drift-check-interval-for-external-resources]]).

## 13. How Flux compares with Argo CD, Kluctl and push-based CI, and its relationship to Crossplane and Cluster API

**Argo CD.** Both are CNCF GitOps delivery tools. Flux is "controllers all the way down": separate controllers with their own CRDs, a Kubernetes-API-and-custom-resource interface, and reconciliation on a schedule. Argo CD is more centralized, with an API server serving UI, CLI and CI, a repository server that caches Git and renders manifests, and an application controller that diffs live against target state ([[comparisons/flux-versus-argo-cd-architecture]]). Their stances toward destructive actions differ in a revealing way. Argo CD makes prune and self-heal explicit opt-ins, adds allow-empty protection, and offers manual sync as a middle stage. Flux exposes explicit switches and policies for each, such as `prune`, `deletionPolicy` and drift-detection modes ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). Argo CD polls repositories on a controller-wide cadence, while Flux's interval is chosen per object with no controller-side default, since the field is required, as section 5 explains. In both tools polling trades how quickly new commits are noticed against load on the Git host, and webhooks remove the wait for new commits in either one. Argo CD blocks rollback while automated sync is on, so rollback becomes a Git revert ([[findings/rollback-is-blocked-while-automated-sync-is-on]]). One more caution about this comparison: much of the comparative claim-making comes from vendors. Akuity, which sells Argo CD, says Flux has a lower and more predictable footprint and suits air-gapped setups, and relies on the Flux Operator for its official UI. Devtron, a vendor built around Argo CD, says Flux lacks a native UI, a claim that is out of date. None of these were independently benchmarked ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]]). Treat the UI and scale claims as opinion. A side-by-side reading of the two projects' documentation turns up no neutral benchmark or CNCF comparison, so the head-to-head rests on each project's primary pages ([[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]).

**Argo CD ApplicationSets and fleets.** Argo CD's answer to "one definition, many clusters" is the ApplicationSet, a controller that generates Applications from generators, such as one per registered cluster, per Git directory or per pull request. Generators have composition limits worth knowing before you plan around them: combining generators is restricted, so deeply layered fleet definitions do not compose freely, and the Pull Request generator polls the Git host, which is a rate-limit consideration. The Cluster generator works from the clusters Argo CD manages and targets both local and non-local clusters unless a selector excludes the local one. For staged rollout, the ApplicationSet controller offers a rolling-sync strategy that steps through generated Applications in groups. It forces all generated Applications to have autosync disabled, respects sync windows, and judges progress only by the health of the managed Applications, so its safety depends on how well the health checks of section 6 judge the kinds involved. An Application that no step selects is excluded from the rolling sync and never syncs through that path. No quantified scale limit for ApplicationSets or hub-and-spoke Argo CD is published, which does not mean none exists. One ApplicationSet incident is on record in which a generated Application was deleted together with its namespaces and Argo CD itself, which illustrates that when a generator stops producing an Application the controller deletes it with everything it owns, and that a delivery tool can be managed by itself. Flux has no direct equivalent object. Fleet layouts are built from a directory per cluster and shared bases, and from the Flux Operator's ResourceSet templates in the D2 design.

**Kluctl.** Kluctl is a deployment tool whose author moved it from shelling out to kubectl with client-side apply to calling server-side apply directly, after hitting the annotation size limit on large CRDs. Its distinctive feature is per-field conflict decisions ([[entities/kluctl]]). Compared with Flux, which force-applies its intent and provides ignore rules, Kluctl is the one tool in the wiki that makes a field-level decision by default. The source is the tool's own maintainer writing on the Kubernetes blog.

**Push-based CI.** A push pipeline runs `kubectl apply` or `helm upgrade` once and stops. It holds credentials for every target, fails the "continuously reconciled" principle if it never re-checks, and tends to accumulate drift. The Morgan Stanley account describes exactly this experience. The comparison is not absolute: Flux itself supports push-style triggers through webhooks, and the pull agent is a powerful identity that needs constraining ([[comparisons/push-versus-pull-delivery]]). INNOQ argues that the pull pattern does not require Kubernetes, since an operator inside any target can read desired state from Git and reconcile, though no named production deployment of that idea appears in the sources ([[examples/gitops-agent-on-non-kubernetes-targets]]).

**Crossplane, Config Connector, ACK and kro.** These are provisioning or abstraction tools, so the relationship with Flux is layered, not competitive. Flux delivers their custom resources, and they reconcile the real world. Crossplane lets a platform team publish its own typed API through an XRD and Composition with a pipeline of functions. kro does something similar with a resource graph and CEL, the Common Expression Language used for small inline expressions. In kro, a ResourceGraphDefinition (RGD) is the object that declares a graph of Kubernetes resources behind a new custom API, so that creating one instance of that API creates and wires together the whole graph. Config Connector and ACK expose roughly one CRD per cloud resource. Because these tools reach into clouds, prune and deletion semantics propagate: ACK's default is to delete the AWS resource, Config Connector's `abandon` annotation keeps it, and Flux's `Orphan` and `prune: disabled` keep the Kubernetes objects ([[comparisons/deletion-policies-across-gitops-and-provider-tools]]). A render-time tool such as Helm or Kustomize produces manifests once and needs something like Flux for continuous correction, while Crossplane and kro are themselves live control loops ([[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]]). The Argo CD guide for Crossplane calls for custom health scripts and annotation-based tracking, because a generic GitOps agent cannot judge custom-resource health unaided, and notes that these controllers generate considerable API traffic ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]). Argo CD ships built-in health scripts for the major provider families, so a team should look at the shipped script before writing its own, as section 6 describes. Flux faces the same issue and answers with kstatus plus CEL. No source compares Flux tool by tool with Crossplane, kro, Config Connector or ACK, so the relationship here is an inference from how each tool is documented.

**kro and the Crossplane function runner.** Two newer entrants sit one layer above delivery and are worth placing on the map, because teams weighing a platform abstraction will meet both. kro is governed as a subproject of Kubernetes SIG Cloud Provider (the Kubernetes special interest group that owns it), which several first-party sources state. Besides the ResourceGraphDefinition, the project is developing a lower-level Graph API, a way to declare a graph of resources directly instead of through an RGD. The design text says the Graph API "does not replace or deprecate the RGD Kind", and both ride one engine, so the practical choice is between a higher-level, opinionated abstraction and a lower-level building block over the same machinery ([[decisions/build-platform-apis-on-resourcegraphdefinitions-or-track-the-alpha-graph-api]]).

How kro behaves at scale is not well documented, and it matters because a platform API that every team depends on needs known limits. No benchmark, measured limit or named production adopter appears in the sources. The design question is whether each ResourceGraphDefinition gets its own controller or all of them share a single work queue: a shared queue means one noisy graph type can delay the others, while per-definition controllers isolate them at the price of more moving parts. The sources describe both layouts, because the kro docs FAQ says there is a dedicated controller per ResourceGraphDefinition while the tuning page and the source code describe one shared queue, so the documentation conflicts with itself ([[findings/the-kro-docs-faq-says-a-dedicated-controller-per-rgd-while-the-tuning-page-and-source-describe-one-shared-queue]]).

Cloud vendors have started to offer kro as a managed capability. Amazon EKS documents it as a fully managed component, so customers do not install or scale its controllers, and describes integrations with ACK for AWS resources and with Argo CD for deploying kro custom resources across multiple clusters. That is vendor documentation, it names no scale limit, and it says nothing about Flux ([[findings/the-amazon-eks-kro-overview-lists-resourcegraphdefinition-as-the-only-primary-resource-type-and-names-no-kro-version]]).

The two ecosystems meet in function-kro, which lets a Crossplane pipeline step run a kro graph. Its README claims full feature parity, but its own file of upstream differences lists gaps. For example, a fatal result makes Crossplane apply nothing and mark the composite not synced, where kro itself would retry. No independent production reports exist in the sources, so treat it as the same engine with documented gaps and not as a drop-in equivalent ([[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]]).

The word "function" is also a trap, because two unrelated specifications use it. The KRM Functions specification, which kpt and Kustomize use, says "A function MUST be implemented as a container", reads a `ResourceList` on stdin and writes one to stdout, and treats a non-zero exit as failure. It is a client-side standard, "completely decoupled from Kubernetes API machinery". Crossplane composition functions share the name and the pipeline idea but speak a gRPC contract: a function is a long-running server that Crossplane's package manager deploys as an ordinary workload behind a Service, and Crossplane calls it with the composite and its observed state and receives the desired state back. That differs from the KRM Functions model, where a function is a container started for each invocation. Kustomize can run a function without a container only through an explicit opt-in, and its guide says "Kustomize does not provide an execution sandbox of any kind" ([[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]], [[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]]).

For Crossplane's own operations, no performance or sharding guide appears in the sources. Its core process reduces memory by stripping CRD schemas it does not need from its cache, and its package dependency resolver creates only the first missing dependency on each pass instead of resolving the whole tree at once, which is a conservative design. Whether to let Crossplane resolve package dependencies or to pin versions and skip resolution is a trade between convenience and predictability ([[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]], [[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]], [[decisions/let-crossplane-resolve-package-dependencies-or-pin-versions-and-skip-resolution]]).

**Terraform in the cluster.** Teams with large Terraform estates often want those resources under GitOps without rewriting them. tofu-controller, a Flux-adjacent controller that lives at `flux-iac/tofu-controller` and is community maintained, reconciles a Terraform resource by running plan and apply in runner pods, keeping state as Kubernetes Secrets and expressing manual approval in Git through `.spec.approvePlan`. Terraform Operator is the alternative, with lower project activity. The costs are state in Secrets, Git-based approvals and coupling between the controller and Flux. The alternative is modeling resources natively in Crossplane, which trades Git-based plan approval for continuous reconciliation ([[decisions/run-existing-terraform-in-the-cluster-with-tofu-controller-or-terraform-operator-or-model-resources-natively-in-crossplane]], [[comparisons/tofu-controller-versus-terraform-operator-as-terraform-in-cluster-controllers]]).

One more difference decides many of these choices, which is the review step. Terraform and OpenTofu produce a reviewable plan before anything changes, and tofu-controller carries that into Git through `.spec.approvePlan`, while Crossplane has no built-in plan preview, and a 2022 evaluation by the consultancy Superorbital noted no Terraform-plan equivalent. The plan is a check and not a guarantee. One practitioner, in a 2025 opinion post that names no provider, resource or date, reports a plan that showed an update while the apply recreated the resource and lost data, and uses the story to argue for plan review before changing production databases. That is a single anecdote and not a measurement of how often plans and applies diverge ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]], [[findings/one-practitioner-reports-a-terraform-plan-that-showed-an-update-while-the-apply-recreated-the-resource-and-lost-data]], [[examples/superorbital-s-2022-evaluation-reported-no-terraform-plan-equivalent-for-crossplane]]).
**Portals and developer-facing layers.** Above delivery sit tools that give developers a simpler front end. Kratix lets a platform team publish a Promise, a self-service API, and schedules the resulting workloads across Destinations. A Destination does not apply anything. Kratix writes `dependencies` and `resources` directories to a Git or bucket state store, and an agent such as Flux or Argo CD on the Destination pulls them, which makes Flux a natural consumer. Syntasso's example of scattering workloads across standard, PCI and Terraform destinations is a vendor illustration and not an independent case study ([[findings/a-kratix-destination-writes-dependencies-and-resources-directories-and-its-filepath-mode-is-immutable]], [[examples/kratix-promises-scatter-workloads-across-standard-pci-and-terraform-destinations]]). Backstage is a portal and not an operator. Its Kubernetes plugin matches catalog entities to cluster objects by the `backstage.io/kubernetes-id` label, its Scaffolder is a one-shot task runner, and the nearest operator-style integration is a third-party plugin that ingests Crossplane claims and kro instances into the catalog ([[findings/the-backstage-kubernetes-plugin-matches-entities-to-cluster-objects-by-label-and-no-backstage-document-describes-an-operator-pattern]], [[examples/the-terasky-kubernetes-ingestor-ingests-crossplane-claims-and-kro-instances-into-the-backstage-catalog]], [[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]). Radius and Score are developer-facing workload abstractions that sit above delivery tools, letting a developer describe a workload while the platform decides how to realize it ([[comparisons/score-versus-radius-as-developer-facing-workload-abstractions]]).

**Cluster API.** Cluster API is the clearest case of Kubernetes managing Kubernetes, and Flux's role is to deliver its objects and wait for them. The kstatus episode in section 6 is the concrete point of contact, and it shows how a provider whose condition vocabulary departs from the common convention forces explicit CEL checks ([[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]).

## 14. Getting started checklist and remaining unknowns

If you are starting from zero, an order that follows the wiki's evidence is the following. Bootstrap Flux against a test cluster so that it commits its own manifests and manages itself. Create one GitRepository and one Kustomization, with an explicit `interval`, and watch the status conditions, then hand-edit a Deployment and watch it revert. Turn on `prune` with a deliberately throwaway manifest and confirm what disappears, and learn the `prune: disabled` annotation before you need it. Add `wait` or `healthChecks`, then a `dependsOn` edge for a CRD-and-operator pair. Move one `helm upgrade` job into a HelmRelease, leaving drift detection at `warn` until you have read the drift events. Add webhook Receivers and an Alert so that failures and new commits are not silent. Decide on tenancy before the second team arrives: apply the three lockdown settings from section 8, create a ServiceAccount per tenant with namespace-scoped RBAC, and keep one tenant per namespace. Add alerts on `gotk_reconcile_error_total` and `gotk_suspend_status`. Only after that, consider ignore rules, image automation (staging only to begin with), and sharding.

Some questions have no answer in the available sources, and a few are answered differently by different sources, so they belong in your plan as caveats. Flux's reference pages require an interval on every Kustomization and HelmRelease and give no default, so the drift latency of an installation is whatever its manifests say.

On the Flux mechanics, the Kustomization-level ignore list with Strip and Adopt modes is documented in the kustomize-controller specification, but no source compares forcing with strip-or-adopt, and only the blog says that `flux diff` honours the rules. The documentation excerpts behind this document are summaries, and the Kustomization and HelmRelease pages are only partly covered, so check quoted field names against the live pages. Whether Flux detects circular `dependsOn` chains at admission is not stated. No source describes how the helm controller surfaces a dry-run validation failure on a stuck release, and no source says which field-ownership policy (forcing, stripping or adopting) is best when two controllers co-own a field.

On health and readiness, whether kstatus treats a kind that publishes only an `Available` condition as reconciled is an inference that no source tests. That each Flux controller keeps a separate cache follows from the controllers' `main.go` files and is not stated by any document. No adopter write-up of reviewed image promotion exists. The HelmChart shard-labeling rule is documented on the sharding page, although the symptom of a mismatch is not. The source-controller artifact server starts only after leader election, according to its source, while the claim that artifacts vanish on restart is an inference from its storage layout.

On Argo CD and the wider landscape, Argo CD's lack of documented OCI signature verification and its silence on SOPS rest on the Argo CD documentation and not on a statement from the project, and the maturity of argocd-agent is undocumented. No source describes how Flux reads ACK's terminal condition, whether Flux needs owner references on composites, or any Flux guidance for kro instances. The ACK and Config Connector reports are single-reporter accounts. Cozystack's shard placement is a design pattern, not a measurement. The sources contain no neutral comparison of Config Connector with Crossplane, no kro benchmark or named kro adopter, and no Crossplane performance guide.

On evidence about adoption and scale, no independent Flux postmortem or neutral Argo CD benchmark exists in the sources, although Skyscanner's Argo CD postmortem is a primary account of a pull-based GitOps outage, and no organization is named as running Flux shards or as having had an APF incident with Flux. Finally, the sources do not settle the best default for platforms that run GitOps and other controllers on the same objects ([[decisions/force-conflicts-or-surface-them-to-humans]]). These items remain open questions.
