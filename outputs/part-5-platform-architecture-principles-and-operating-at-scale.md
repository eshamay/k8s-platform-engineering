# Part 5: Principles of Good Platform Architecture and Operating at Scale

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) and are finishing the tutorial series on controllers, API machinery and platform abstractions.<br>
> **Purpose:** Trace one Flux commit through server-side apply, finalizers and conditions to a Ready status, show that good platform architecture is the disciplined composition of the earlier mechanics, and describe what operating that architecture at scale requires.<br>
> **Status:** Draft. The end-to-end trace is assembled from documented pieces, because the wiki holds no single sourced trace (see section 12).<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** [[concepts/universal-control-plane]], [[concepts/gitops-pull-based-delivery]], [[concepts/reconciliation-loop]], [[concepts/server-side-apply-and-field-ownership]], [[concepts/finalizers]], [[concepts/conditions]], [[concepts/scale-and-sharding]], [[concepts/pitfalls-and-case-studies]], [[concepts/tooling-landscape]], and the examples, findings, comparisons and decisions linked inline

## 1. Recap: the layered stack from Parts 1 to 4

The earlier parts of this series built one idea in layers, and this final part puts the layers to work together. It helps to restate them in plain terms before we trace anything.

The foundation is the observation that Kubernetes ships two products in one box. One is a container scheduler. The other is a generic, extensible API machine: an API server that provides authentication, RBAC, admission, validation and watch, backed by etcd, plus a convention that controllers reconcile an object's `spec` (what you want) toward its `status` (what is observed). The second product has no inherent tie to pods, so anything that can be described declaratively and reconciled by a loop can become a custom resource, whether it is a cloud database, a DNS record or a whole cluster. That is the idea behind the [[concepts/universal-control-plane]], and every tool in this part depends on it. Once an outside thing is represented as a Kubernetes object, it inherits authentication, RBAC, audit and a shared tooling ecosystem.

The second layer is the controller itself. A controller runs a [[concepts/reconciliation-loop]]: a function that receives only the namespace and name of an object, never the event that woke it, reads the current state, performs API calls to close the gap, and writes status. Because the function can run many times in any order, it must be [[concepts/idempotency]] safe, and because it works from current state and not from a stream of events, it is level-triggered, meaning a missed event cannot leave the system permanently wrong. Under the loop sits the machinery from [[concepts/informers-reflectors-and-workqueues]]: a reflector lists and then watches the API server, an informer keeps an in-memory cache, and a rate-limited workqueue deduplicates object keys so that one object is never reconciled by two workers at once.

The third layer is the set of API conventions that let many writers share one object. [[concepts/server-side-apply-and-field-ownership]] records which manager owns each field in `metadata.managedFields`. [[concepts/finalizers]] hold an object in the API until its controller has cleaned up whatever lives outside the cluster. [[concepts/owner-references-and-garbage-collection]] let the cluster remove children when a parent goes away. [[concepts/conditions]] give every kind a common, machine-readable way to say whether it is ready.

The fourth layer is the set of abstractions that platform tools build on top. A [[concepts/provider]] teaches the control plane to speak to an external API and exposes [[concepts/managed-resource]] objects, each standing for exactly one outside resource. A [[concepts/composite-resource]] bundles several of those behind a simple API, and a [[concepts/composition]] defines how the bundle expands. On the delivery side, [[concepts/gitops-pull-based-delivery]] uses an in-cluster agent such as Flux to pull desired state from Git and apply it.

The thesis of this part is that none of these pieces is new when you meet it in a platform. A good platform is the disciplined composition of the same mechanics, and a failing platform is nearly always one of those mechanics used carelessly. The fastest way to see this is to follow one commit all the way down and then all the way back out.

## 2. End-to-end lifecycle trace: a Git commit to a Flux Kustomization to server-side apply

A note on evidence before we start. The wiki records, as an open gap, that no single source traces a Flux commit step by step through to a Ready object. What follows is therefore an assembly of documented behaviors from the Flux documentation, the Flux deep dive and the concept pages, and we will mark the places where the documentation is silent. The composition is the point of the exercise, and it is the best test of whether the earlier concepts fit together.

Imagine a platform team that keeps a Git repository describing what should run in a cluster. A developer merges a commit that changes the image tag of a Deployment. Flux is a set of single-purpose controllers that communicate through custom resources, so the first thing to understand is who does what. A source controller watches a `GitRepository` object, fetches the repository on its interval and packages the content as an artifact. A kustomize controller watches a `Kustomization` object that points at that source, builds the manifests and applies them. The notification controller can accept a webhook from the Git host that tells the source to refresh immediately, which is described in [[examples/flux-notification-receivers-start-reconciliation-without-waiting-for-the-poll-interval]]. Without a webhook, the commit waits until the next interval fires, which is a quiet failure mode, because the system looks healthy while changes arrive late.

Here is a minimal Kustomization of the kind a platform team would write. It is illustrative, and the field names follow the Kustomization API as the wiki describes it.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: team-a
spec:
  interval: 10m
  retryInterval: 2m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: team-a-repo
  path: ./deploy/production
  prune: true
  wait: true
  serviceAccountName: team-a-deployer
  dependsOn:
    - name: infrastructure
```

Read it as a policy wrapped around the bare reconcile primitive. The `interval` says how often the controller re-fetches, builds, applies and checks for drift; the Kustomization reference recommends a minimum of 60 seconds, phrased as "should", and nothing in the API type enforces it. The `retryInterval` is the delay before the next attempt after a failure, and it defaults to the interval. The `timeout` caps the build, apply and health-check work of a single run. The `prune` field turns on garbage collection, `wait` holds the object until what it applied is healthy, and `dependsOn` makes this Kustomization wait for another one to be Ready. This is exactly the structure described in [[examples/flux-kustomization-interval-and-retry-interval-set-the-loop-timing]]: a cadence, a failure delay, a time budget and a set of switches. One point from the wiki is worth repeating because it corrects a common belief. The Flux concepts page says reconciliation runs every five minutes by default, but the Kustomization and HelmRelease references both call `.spec.interval` a required field, and the Kustomization Go type marks it as required with no default value. A manifest without an interval is therefore rejected and never quietly falls back to five minutes. The only default the wiki found is the one-minute `--interval` flag of the `flux create` command, which applies when the command-line tool generates a manifest for you. This is not a difference between versions: Flux's own pages disagree, and the origin of the five-minute wording on the concepts page was not traced. The practical consequence is that drift-correction latency in Flux is whatever the author wrote in the manifest, so set the interval explicitly on every object. Changes to the source itself are picked up outside the interval window when a webhook fires, so the interval governs mainly drift detection and periodic re-checks.

Now the apply. The kustomize controller does not use the old client-side approach of stamping a `last-applied-configuration` annotation. It uses server-side apply. The controller sends the set of fields it has an opinion about together with a field manager name, and the API server merges that into the live object and updates `managedFields`. In Part 3 we saw that if another manager owns a field with a different value, the API server answers with a conflict instead of silently overwriting. Flux's posture, as the wiki records it in [[comparisons/ssa-conflict-policy-across-tools]], is to force-apply its own intent by default and then offer escape hatches. The Kubernetes documentation recommends that controllers force conflicts on objects they own, while the same maintainers argue that CI/CD systems behave like users and should surface conflicts to humans. The wiki frames this unresolved tension in [[decisions/force-conflicts-or-surface-them-to-humans]].

Flux runs a server-side apply dry run on every interval to detect drift, which is why a hand edit gets reverted. [[examples/gitops-reverts-a-hand-edited-deployment]] describes the outcome: the revert is not a bug, it is a level-triggered controller doing what it was built to do, and teams that need an emergency change must set `suspend` first, which stops both applying and drift detection.

The same field-ownership machinery explains the most famous way this goes wrong. In [[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]], Flux kept resetting a replica count, a horizontal autoscaler kept lowering it, and the cluster autoscaler added and removed nodes in a loop that a Flux blog describes as two controllers ping-ponging indefinitely. Flux's answer was a `.spec.ignore` list of JSON Pointer paths. A "strip" rule removes the field from Flux's payload when another server-side apply manager owns it, and an "adopt" rule keeps the live value when Flux is the sole owner. The price, recorded in [[findings/ignoring-a-field-in-flux-or-argo-cd-means-git-changes-to-it-are-no-longer-applied]], is that Git changes to an ignored field are no longer applied. Per-object annotations such as `kustomize.toolkit.fluxcd.io/ssa` choose between Override, Merge, IfNotPresent and Ignore, as shown in [[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]. There is one limit that surprises people: lists in custom resources whose CRDs carry no merge markers are treated as atomic, so only one manager can own such a list ([[findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership]]).

Identity is the last piece of the apply step. Unless the platform team locks it down, a Kustomization applies with the controller's own identity, which is powerful. The reference multi-tenancy repository, described in [[examples/flux-multi-tenancy-repository-isolates-tenants-with-service-account-impersonation]], starts the controllers with `--no-cross-namespace-refs=true`, `--no-remote-bases=true` and `--default-service-account=default`. A Kustomization then reconciles as a ServiceAccount in the tenant's namespace, and ordinary Kubernetes RBAC decides what that tenant's repository may create. A manifest that tries to create a ClusterRole is rejected by the API server. Without those flags the trade-off is stated bluntly in [[findings/without-lockdown-flags-a-flux-kustomization-applies-with-the-controllers-own-identity]].

At this point the Deployment's new image tag is in the API server. The Deployment controller, a built-in reconcile loop, creates a new ReplicaSet, which creates pods. Notice that Flux did not roll anything out. It declared intent, and a chain of other controllers carried it forward through owner references. That handoff, intent written once and realized by several loops, is the first architectural principle we will name later.

## 3. Continuing the trace: composite, composition function and managed resources reaching the cloud API

Suppose the same commit also adds a request for a database. The repository does not contain a cloud-specific resource. It contains a small custom object that the platform team designed, for example a composite resource of a kind the platform team calls a PostgreSQL instance. This is the layer where the platform team's opinions live.

In Crossplane, which the wiki treats in depth, the schema of that small API is declared by a CompositeResourceDefinition, which becomes a CRD. A Composition says how an instance of that API becomes lower-level objects. In current Crossplane, a Composition is a pipeline of composition functions. A function is installed as a package and runs as a pod. On each reconcile, Crossplane calls the steps in order over gRPC, giving each the composite's observed state and the desired state accumulated so far, and each function returns what should exist ([[concepts/composition]]). The wiki records a hazard here that every author should memorize: a function that omits a resource from its desired state causes that resource to be deleted ([[findings/a-composition-function-that-omits-a-resource-from-its-desired-state-deletes-it]]).

The composite spec carries operational controls as well as user-facing fields. It selects a Composition with `compositionRef` or `compositionSelector`, can pin a composition revision, can be paused with the `crossplane.io/paused` annotation, and can be forced to reconcile with `crossplane.io/reconcile-requested-at` ([[examples/crossplane-xr-spec-pins-composition-and-status-reports-synced-and-ready]]). Version history matters: in Crossplane v1 a namespaced claim fronted a cluster-scoped composite, while in v2 the composite is namespaced and claims are gone for new-style definitions. The wiki flags that older tutorials describing claims and patch-and-transform may no longer match current behavior (see [[entities/crossplane]]).

The functions produce managed resources. A managed resource is a Kubernetes object that represents exactly one external thing, and the Crossplane documentation calls the thing in the cloud the external resource. It has `spec.forProvider`, which is the authoritative desired state, `status.atProvider`, which is what the provider last observed, and an external-name annotation that ties the object to the cloud identifier. A provider controller then runs a Connect, Observe, Create, Update, Delete cycle against the cloud API ([[concepts/managed-resource]], [[concepts/provider]]).

This is where idempotency stops being a theoretical virtue. Creating a cloud resource is not naturally idempotent. If a controller calls a create API and crashes before it records the returned identifier, the next reconcile cannot tell whether the resource exists, and a blind retry could leak the first one. [[concepts/idempotency]] lists four answers that the tools use: deterministic names (Config Connector acquires a same-named resource, ACK adopts by identifier), a persisted external identity (Crossplane's external-name annotation), recording intent before acting (Crossplane writes create-pending annotations and halts for a human if the outcome is unknown), and a server-side client token that lets the cloud recognize a retried request. Which of these is safest at scale is still open in the wiki.

The delete verb needs the same care on this side, and we will return to it in section 5. For now note one more arrow in the trace. The GitOps agent reconciles Git into the Kubernetes API, and the Crossplane controllers reconcile the API into reality. That is the two-loop structure described in [[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]. A green sync in the GitOps agent says only that the custom resource matches Git. It does not say the database exists, and drift in a composed resource may be corrected by the lower loop without the GitOps agent ever seeing a difference.

## 4. Status flowing back: conditions, observedGeneration, readiness and health rollups

Everything so far flowed downward from intent to reality. A platform is only usable if the answer flows back up, and the vehicle is status. The spec-status split from Part 2 reserves `spec` for the user and `status` for the controller, and the standard way to say something useful in status is the condition.

A condition is one entry in `.status.conditions`. It has a `type` such as `Ready`, a `status` of `True`, `False` or `Unknown`, a machine-readable `reason`, a human-readable `message`, a `lastTransitionTime` and an optional `observedGeneration`. Here is how a Flux Kustomization might look partway through a rollout, again as an illustration of the documented fields.

```yaml
status:
  observedGeneration: 7
  conditions:
    - type: Ready
      status: "False"
      reason: DependencyNotReady
      message: dependency 'team-a/infrastructure' is not ready
      observedGeneration: 7
    - type: Reconciling
      status: "True"
      reason: Progressing
      observedGeneration: 7
```

The most important field to read is `observedGeneration`. The API server increments `metadata.generation` whenever the spec changes, and a controller copies the generation it has processed into status. If `generation` is greater than `observedGeneration`, the status describes an older spec and should not be trusted. [[concepts/conditions]] makes the point that under the "abnormal-true" polarity that kstatus describes (kstatus is a library from the Kubernetes SIGs `cli-utils` project that computes whether an object is ready by reading standard status fields such as conditions and `observedGeneration`, so tools can judge readiness without knowing each kind), the absence of problem conditions looks healthy, so a stopped controller looks identical to a healthy one unless you compare generations. The sources agree that omitting `observedGeneration` is the most common mistake ([[findings/missing-observedgeneration-hides-stale-status]]).

Flux gives its own objects a clear reading guide, summarized in [[examples/flux-helmrelease-status-records-attempts-and-health]]. `Ready` is the headline, `Reconciling=True` is normal progress, `Stalled` means the release will not advance without a change, and a chain of `DependencyNotReady` conditions points at an upstream problem. The status never restates what the user wanted; it records what happened to that intent, including the last attempted revision and release action. The wiki adds a trap: a suspended resource keeps its last condition and can look healthy.

Crossplane splits the idea differently, and understanding the split is worth the effort. A managed resource reports `Synced`, which says whether the last reconcile succeeded, and `Ready`, which says the external resource is usable. A composite reports `Ready` only when the function pipeline says every composed resource is ready. While a cloud provisions a database, a user sees `Synced=True` and `Ready=False`, which means the controller is working and the thing is not usable yet ([[examples/crossplane-database-claim-reports-synced-and-ready]]). The platform's two failure stories are the mirror images. `Synced=False` with `Ready=True` is a silent failure: the thing exists and apps keep running, but Crossplane can no longer manage it, so drift is no longer corrected ([[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]]). And a summary condition can stay true while long work runs. In one reported case, an AWS MSK cluster update that took over an hour left `Synced=True` the whole time, and only an `AsyncOperation` condition said `Ongoing` ([[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]]). A later check found no fix: the provider-aws issue about this behavior was closed as stale, and the shared Upjet and crossplane-runtime source on its main branch still reports a successful reconcile while the asynchronous operation runs. The wiki did not read the body of one open pull request that might change this, so treat the behavior as current but not guaranteed to stay that way.

Other stacks use different vocabularies for the same job, compared in [[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]. ACK adds `ACK.ResourceSynced`, `ACK.Terminal` and `ACK.Recoverable` and keeps `Ready` as a roll-up. Config Connector uses a single `Ready` whose reasons move through `Updating`, `UpToDate` and `UpdateFailure`. kro lets the author of a ResourceGraphDefinition (kro's single object that declares both the new API's schema and the graph of resources behind it) define instance conditions with CEL, the Common Expression Language, a small expression syntax that Kubernetes and its ecosystem use to write conditions over an object's fields. Cluster API moved to the standard condition type and split `Available` from `Ready`. KEP-1623 produced the shared `metav1.Condition` type, but adoption is voluntary, so older APIs keep their own forms.

Why does this vocabulary matter so much to a platform? Because conditions are what ordering depends on. In Flux, a Kustomization marks itself Ready only after health checks pass, and that unblocks the Kustomizations that `dependsOn` it. Flux judges compatible custom resources with kstatus and others with CEL health expressions, which are short expressions the user writes to say what "healthy" means for a kind that does not follow the conventions. Argo CD aggregates the worst health among an application's immediate children and needs Lua checks for custom kinds, meaning small scripts in the Lua language that the user supplies to teach Argo CD what ready means for that kind ([[comparisons/health-and-readiness-models-across-tools]]). When a provider's conditions do not follow the convention, the rollup lies. The best-documented case is Cluster API: an object that had `observedGeneration` set but no conditions yet could look ready to kstatus, so Flux might start dependents too early ([[findings/premature-readiness-in-kstatus-based-tools]], [[entities/cluster-api]]). The proposed fix was closed as not planned, because Cluster API is moving from `Ready` to `Available` and Flux added CEL-based custom health checks instead. Likewise, Crossplane's guide for running resources under Argo CD prescribes custom Lua health checks, since a generic agent has no idea what "ready" means for a custom kind ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]).

The lesson of this section is that a rolled-up status is only as honest as its definition of ready. The platform author chooses what the composite promises, and the platform is only trustworthy if that promise is true.

## 5. Deletion trace: prune, finalizers, propagation modes and ordered teardown

Creation is the easy half. Deletion is where platforms lose data and money, so we trace it with equal care.

Start with the commit that removes the database request from Git. With `prune: true`, Flux deletes objects that were applied earlier but are missing from the current source, using the inventory recorded in `.status.inventory` ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). Notice that this is not Kubernetes garbage collection. Flux and Argo CD apply objects they do not own through owner references, so each keeps its own record of what it applied. An object can opt out with the annotation `kustomize.toolkit.fluxcd.io/prune: disabled`. The wiki's warning in [[findings/unintended-deletion-through-prune]] is that the boundary of "the desired configuration" is easy to misjudge, and a level-based loop deletes whatever it no longer sees in desired state. Argo CD ships with prune off and an allow-empty guard so that an empty source cannot prune everything; Flux exposes explicit switches ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). That table is assembled from separate documentation pages and is not a head-to-head test.

The delete now reaches the composite, and this is where finalizers enter. When a client deletes an object that carries finalizers, the API server does not remove it. It sets `metadata.deletionTimestamp`, returns HTTP 202, and leaves the object visible as Terminating. The controller that owns each finalizer sees the timestamp, performs cleanup, and removes its own entry; when the list is empty, the object is deleted ([[concepts/finalizers]]). Here is the pattern in an object, illustrative of a managed resource under deletion.

```yaml
metadata:
  name: orders-db
  deletionTimestamp: "2026-11-25T10:15:00Z"
  finalizers:
    - example.com/external-cleanup
```

The finalizer line is the promise that the cloud database will be removed before the Kubernetes record disappears. The API server enforces rules around that promise: after the deletion timestamp is set, nobody can add a new finalizer, and the only permitted edit is removal. Custom finalizer names must be qualified with a domain. A well-written controller adds its finalizer on the first pass, before creating anything outside, and its cleanup must be idempotent and treat an already-deleted external resource as success.

The three deletion mechanisms divide the work. Owner references handle in-cluster, same-namespace cleanup. Finalizers handle external resources, cross-namespace cleanup and ordered shutdown. Propagation modes decide timing ([[comparisons/background-foreground-and-orphan-propagation-modes]]): background, the default, removes the owner at once and cleans dependents later; foreground puts a finalizer on the owner and waits for dependents that carry `blockOwnerDeletion=true`; orphan leaves the dependents behind.

Ordering is the hard part, because the default is no ordering at all. Crossplane composed resources carry owner references to their composite, and under the default Background policy the garbage collector marks all children deleted at once. [[examples/crossplane-foreground-and-pipeline-deletion-policies-order-composed-resource-teardown]] describes the options: `Foreground` keeps the parent until the children are gone, and `Pipeline` lets a function remove resources from desired state step by step. A Usage object can additionally block deletion of a used resource, such as a subnet, until its users are gone ([[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]]). The Crossplane deletion policy is alpha, and the wiki records an interaction between tools that is easy to miss: Argo CD deletes with foreground propagation by default, and in that case Crossplane ignores the composite deletion policy and emits a warning event, so the ordered-teardown guarantee depends on settings in two tools ([[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]]).

kro takes a different route. It keeps an instance finalizer until every managed resource is gone, finds them through a persisted inventory, and deletes in reverse dependency order in waves, each fully gone before the next begins ([[examples/kro-deletes-instance-resources-in-reverse-dependency-waves]]). The wiki contrasts this with a Crossplane gap: a credentials secret without its own finalizer can vanish before managed resources finish cleanup ([[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]]).

The tools also answer a different question, which is whether deleting the Kubernetes object should delete the real thing. Crossplane, ACK and Config Connector default to deleting the external resource and offer an opt-out (Orphan, retain, abandon). Argo CD cascades an Application delete only if the Application carries the `resources-finalizer.argocd.argoproj.io` finalizer, and `preserveResourcesOnDeletion` on an ApplicationSet prevents it being added. Flux has `deletionPolicy` with MirrorPrune (the default), Delete, WaitForTermination and Orphan, where WaitForTermination means Flux's own deletion waits on every finalizer its children carry. Cluster API orders teardown with a drain, volume detachment, hooks and then infrastructure deletion. These are compared in [[comparisons/deletion-policies-across-gitops-and-provider-tools]]; the decision itself is framed in [[decisions/delete-or-retain-the-external-resource-when-the-kubernetes-object-is-deleted]]. One unconfirmed detail: the wiki did not establish from a primary source what Flux names its own finalizer.

The failure modes follow directly. A finalizer only works while its controller runs, so deleting the cluster first, or removing a Crossplane provider before its managed resources, strands the cloud resources, still billing ([[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]], [[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]]). The first of those rests on a single consultancy blog and the second on Crossplane's documentation. Forcing a finalizer off to unstick an object skips the cleanup it guarded ([[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]). The practical rule is to uninstall controllers only after their custom resources are deleted.

The newer research pass added three dated, public reports that show these mechanisms in practice. All are issue reports from individual users, not organization-authored postmortems, and their authors are anonymous or identified only by a handle, so read them as reproductions and not as audited incidents. In ACK issue 2911, opened in June 2026, a reporter running the ACK WAFv2 controller had Argo CD prune a WebACL custom resource. The controller deleted the AWS resource but did not map the "not found" error it received on a later pass, so the custom resource sat in Terminating until someone patched the finalizer off by hand. A maintainer confirmed the cause. In this instance the manual patch was safe because the cloud resource was already gone, but the same patch would leak a billing resource if the cloud object still existed ([[examples/an-argo-cd-prune-left-an-ack-wafv2-webacl-terminating-on-its-finalizer-after-the-aws-resource-was-already-gone]]). In Config Connector issue 16444, filed on 2026-11-25 and still open a day later, a reporter describes a multi-cluster setup with leader election: objects deleted on a standby cluster stay in Terminating because the standby does not process them, and when that cluster becomes leader again it runs the stale deletion against Google Cloud, possibly after another cluster has re-created a resource of the same name. There was no maintainer response yet, so this is one reporter's account of a scenario ([[findings/config-connector-leader-election-across-clusters-can-run-a-stale-deletion-against-live-google-cloud-resources]]). Finally, ACK community issue 3177 (November 2026) contains the author's own audit, not an observed production count, claiming that in 22 controllers a lost create response either duplicates 28 resources or wedges 20 more because the name already exists. A runtime change merged on 2026-11-20 moves the status write to immediately after the create call, which narrows the window but cannot close it, because a crash between the cloud call and the write can still lose the identifier ([[findings/an-ack-audit-found-48-resources-in-22-controllers-where-a-lost-create-response-duplicates-the-resource-or-wedges-the-custom-resource]]). The wiki still found no source that quantifies how often forced finalizer removal orphans resources, so the frequency of that mistake remains unknown.

## 6. Principles of good platform architecture, drawn from the traced lifecycle

The trace above is long, but a handful of principles recur at every step. Each is a reason the design works, and each has a documented way of failing when ignored.

The first principle is that intent is written once, declaratively, and realized by many small loops. Flux declares a Deployment and lets the built-in controllers produce pods. The platform declares a composite and lets functions and providers produce cloud resources. Each controller owns one aspect, which is the design the Kubernetes documentation favors. This works because the loops are level-triggered and idempotent, so a crash, a missed event or a duplicate run changes nothing about the end state. When the principle is violated, as with logic keyed to specific events, resources get stuck ([[findings/event-specific-logic-in-reconcilers]]).

The second principle is that events are hints and state is truth. Webhooks, watches and notification receivers lower latency, but the interval and the full reread of state are the safety net. Flux's notification receiver speeds a commit along, while the poll interval guarantees it eventually arrives. See [[decisions/events-as-hints-state-as-truth]]. The consequence is that detection latency equals the interval, so you choose intervals per resource class ([[findings/drift-detection-latency-is-the-interval]]).

The third principle is that every writer must be identified, and shared objects must have explicit ownership. Server-side apply makes ownership visible and turns a clash into a conflict. A platform that lets Flux, an autoscaler and cert-manager touch one object without an ownership decision will fight indefinitely. The wiki's open question is which conflict policy is the best default, since forcing hides real disagreement ([[findings/forcing-conflicts-hides-disagreements-between-writers]]).

The fourth principle is that deletion deserves as much design as creation. The delete verb is destructive for external resources, so good platforms make the outcome explicit through finalizers, deletion policies, management policies and ordering controls, and they make the default safe for the data that matters. The wiki records that Argo CD ships with destructive actions off while Flux exposes explicit switches for each; neither is "right," but both are explicit.

The fifth principle is honest status. A readiness signal is a contract with other automation. If it says ready too early, dependents start against nothing. If it stays true while work is ongoing, alerts stay silent. Good platforms set conditions on first visit (even as `Unknown`), track `observedGeneration`, separate "controller can reconcile" from "thing is usable," and teach generic agents the health meaning of custom kinds.

The sixth principle is that every loop has a budget, and the budget should be explicit. A workqueue limiter normally protects the API server, but for a provider the same queue is also the budget for someone else's API. Crossplane's `--max-reconcile-rate` exists because, in the issue's words, reconcile rate is a good proxy for average external API call rate ([[examples/crossplane-max-reconcile-rate-turns-reconcile-rate-into-an-api-call-budget]]). ACK's roughly ten-hour default resync after a resource is synced makes the same trade of freshness for API cost ([[examples/ack-resync-period-tuning-for-stateful-resources]]). Self-healing also needs a brake: Cluster API's `maxUnhealthy` stops automatic remediation when too many machines look unhealthy at once ([[findings/remediation-can-amplify-an-outage]]).

The seventh principle is that blast radius should be a design decision. A control plane that manages everything concentrates authority. ACK runs one controller per AWS service with scoped IAM; a single management cluster or shared provider credential enlarges the blast radius; and whoever can create a custom resource inherits the controller's cloud rights ([[findings/blast-radius-and-privilege-centralization]]). RBAC on the platform API is the security boundary, and Flux's per-tenant impersonation is one way to apply that principle.

The eighth principle is to keep abstractions small and honest. A platform API is a contract that users depend on. The wiki cites practitioner advice, from a single blog, against mega-Compositions and against APIs that mirror a cloud's own resource names, and it records Crossplane's own cost admission: it needs a hosting cluster, Kubernetes skills and platform-team-owned abstractions ([[findings/crossplane-adoption-needs-a-hosting-cluster-kubernetes-skills-and-platform-team-owned-abstractions]]). The expressiveness question, functions versus CEL graphs, is compared in [[comparisons/helm-versus-kro-versus-crossplane-as-platform-abstraction-layers]].

The ninth principle is to stage risky automation. Drift correction, pruning and cluster-wide defaults all amplify a mistake through a loop. Grafana's 2019 outage came from a new cluster-wide default PriorityClass that a ReplicaSet kept reapplying to every recreated pod, preempting every production ingester and causing about 26 minutes of outage, with no data lost ([[findings/a-new-cluster-wide-default-must-wait-until-existing-workloads-carry-explicit-values]]). The pattern is to add the explicit value first and change the default second, and to adopt automatic correction in stages ([[decisions/staged-adoption-of-automated-drift-correction]]).

## 7. Scale: informer memory, workqueue rates, API priority and fairness, etcd limits

Scale in this world is a set of separate limits, and the practical method the sources describe is to find which resource saturates first and then either raise it or split the work ([[concepts/scale-and-sharding]]).

At the cluster level, SIG Scalability publishes a tested envelope of about 5,000 nodes, 150,000 pods, 10,000 namespaces, 10,000 services and a 1.5 MB object size cap, along with 150,000 non-event objects per type and about 3 GB total. The page says explicitly that these thresholds are not hard limits and that crossing one results in degraded performance. A recheck against the raw page also found that the thresholds are scoped to built-in resource types and tied to a particular test setup. The envelope is not a cube, because the dimensions interact. CRD count is not one of the tested dimensions, which is exactly where platform tools fell in. Operators of many clusters give tighter advice: Gardener says most clusters should stay below about 500 nodes, that etcd has a practical space limit of 8 GB with a healthy database under 3 GB, that object counts should not exceed about 100,000 for most use cases, and that webhooks and object counts need control (its page is undated, and its node advice assumes machines of at least 8 vCPU and 32 GB) ([[examples/gardener-advises-keeping-most-clusters-under-about-500-nodes-and-controlling-webhooks-and-object-counts]]). The wiki does not reconcile the order-of-magnitude gap between the 5,000 and 500 figures, because they answer different questions: a tested maximum versus working advice. Treat the envelope as an upper limit and operator advice as a conservative target ([[findings/tested-scalability-maximums-and-operator-advice-differ-by-an-order-of-magnitude]]).

Underneath is the shared store. Every custom resource lives in etcd, which has a single Raft write leader, an 8 GB default cap and revision growth that needs compaction. Mitigations include moving Events to a separate etcd, alternative backends and watch-cache improvements ([[findings/etcd-scale-limits-of-the-shared-store]]). Ant Group's more-than-10,000-node cluster cut apiserver memory from roughly 400 GB to 100 GB by serving list requests from the watch cache, among other changes ([[examples/ant-group-large-cluster-tuning-of-apiserver-watch-cache-and-etcd]]). A vCluster claim of degradation around 30,000 to 40,000 objects is a vendor figure that depends on workload.

Inside a controller there are four limits, and they are worth understanding separately. First, the informer cache holds every watched object with no eviction, so memory grows with what you watch ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]). Second, the workqueue never processes one key concurrently, so throughput is set by worker count and reconcile duration and not by the object count; a slow reconcile hogs a worker and deepens the queue. Third, the client-side rate limiter, set by QPS and burst, throttles requests before they leave the process. Fourth, leader election means only one replica reconciles, so extra replicas add failover and not capacity ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

Two throttling layers are easy to confuse. Client-side throttling delays requests inside the process. Server-side API Priority and Fairness classifies requests by FlowSchema into priority levels with their own concurrency shares, queues with shuffle sharding, and rejects with HTTP 429 when a level saturates, so one badly behaved controller need not starve others. Upbound's log line "Waited for 1.033772408s due to client-side throttling, not priority and fairness" shows why the distinction matters: raising server capacity would not have helped ([[findings/client-side-throttling-and-server-side-apf-are-separate-layers]]).

Watches have their own failure. When a resource version is too old, the server answers 410 Gone and the client must relist. If many clients lose their watch together they relist together, a storm ([[findings/an-expired-resourceversion-forces-a-relist-and-synchronized-relists-can-storm]]). Bookmarks, the server watch cache and jittered backoff are the mitigations. The default workqueue limiter combines two ideas, and it helps to see them in plain terms. Exponential backoff means that each time the same object fails, the wait before retrying it roughly doubles, so a persistently broken object backs off quickly instead of hammering the API server. A token bucket works like a jar that refills at a steady rate: every reconcile must take a token, so the queue can burst briefly when the jar is full but cannot sustain more than the refill rate over time. Together they keep one failing object and one busy burst from crowding out everything else. The values were checked against controller-runtime v0.25.3 (published 2026-11-16): the per-object backoff starts at 5 ms and caps at 1000 s. The token bucket of 10 per second with room for 100 belongs to client-go's default limiter, and controller-runtime does not apply it when its priority queue is on, which is the default. With the priority queue on, only the per-object backoff applies, so the overall bucket is present only if you turn the priority queue off. The bucket figures were read from client-go's main branch and not a pinned release.

The failure that ties this together is described in [[examples/an-openai-outage-shows-many-api-clients-can-overload-the-control-plane]], and the wiki has now read OpenAI's own postmortem for it, not just a commentary. On 2024-12-11 OpenAI merged a change at 2:23 pm Pacific, rolled it out to its clusters between 2:51 and 3:20 pm, and deployed a new telemetry service at 3:12 pm. The postmortem says the service's configuration caused every node in each cluster to run resource-intensive Kubernetes API operations whose cost scaled with the size of the cluster, and the API servers were overwhelmed in most large clusters. All services were significantly degraded from 3:16 to 7:38 pm, with the first cluster recovering at 4:36 pm. The data plane could mostly run on its own, but DNS-based service discovery relied on the control plane, so cached records hid the failure for about twenty minutes and then, as they expired, services began failing and the expiring caches added load ([[findings/dns-caching-hid-the-control-plane-failure-for-about-twenty-minutes-before-expiring-records-added-load]]). Remediation was slow because removing the telemetry service required control-plane access that the overload had taken away, so teams scaled down clusters, blocked network access to the admin APIs and scaled up the API servers in parallel. Staging did not catch it because the pre-rollout checks looked at CPU and memory and not at API server load. All of these figures are self-reported by OpenAI. One earlier detail is withdrawn: the primary text does not say the calls were list or watch calls or that the service was a DaemonSet, so any such claim is this wiki's inference, and the link to informers is indirect. Use the incident as an illustration that [[findings/control-plane-overload-blocks-the-remediation-that-would-fix-it]]. Neon's postmortem of 2025-05-21 is a second, different example from a platform built on Kubernetes: a changed query plan made a control-plane database query 10 to 100 times slower, idle compute pods were not suspended, the count rose to about 8,000 against 6,000 planned, and pods exhausted IP addresses in two of three subnets, with 5.5 hours of impact across 2025-05-16 and 2025-05-19 ([[examples/neon-s-may-2025-delayed-start-incidents-exhausted-subnet-ips-after-a-slow-control-plane-database-query]]). A related, widely known principle follows: keep the means of repair off the path that can fail. Fail-closed admission webhooks are the same trap, because an unreachable backend with `failurePolicy: Fail` blocks the writes needed to repair it ([[findings/fail-closed-webhooks-can-block-the-writes-needed-to-repair-them]]); the webhook guidance is now backed by one primary postmortem, Jetstack's, described in section 10. The wiki still found no primary postmortem of a CRD deletion cascade or an etcd quota alarm, though its search tool returned empty results for many queries, so that absence is weak evidence ([[findings/no-primary-postmortem-was-found-for-a-crd-deletion-cascade-or-an-etcd-quota-alarm]]).

Finally, CRD count is itself a scale dimension. Upbound's test of a control plane of about 2,000 managed resources found client discovery needing around 300 HTTP requests, server OpenAPI computation burning CPU, and memory use of a little over 4 MiB of resident memory per CRD causing out-of-memory kills on hosted control planes; fixes included lazy OpenAPI computation in Kubernetes 1.23, backported to 1.20.13, 1.21.7 and 1.22.4, and garbage-collection tuning that cut peak resident memory by about 25 percent on an idle API server with roughly 2,000 CRDs ([[examples/upbound-tested-a-multi-cloud-control-plane-of-about-2000-managed-resources-and-upstreamed-kubernetes-fixes]]). The Upbound post is dated August 2022 and self-reported. The wiki originally took these figures from model-generated digests, so it re-read the raw pages on 2026-11-26. Every quoted figure matched, and three wordings were tightened: the Upbound memory figure above, the Argo CD processor numbers in section 8, and the Crossplane memory figures in section 8, which are design targets and not measurements. The Kubernetes API Priority and Fairness page was read in full, while the KEP-1040 text was read closely only in part, so claims about the rest of that KEP remain unverified ([[findings/the-scale-dossier-relies-on-model-digests-for-most-numbers-so-limits-need-rechecking]]).

## 8. Sharding and tuning: Flux label sharding, Argo CD cluster sharding, Crossplane provider families, domain-scoped control planes

There are two levers: raise capacity vertically, or split the work along a stable key.

For Flux, the first lever is documented. Flux exposes `--concurrent` (a range of 10 to 20 is mentioned), Helm repository cache size and TTL flags, and warns that tmpfs counts against the pod's memory ([[examples/flux-controllers-expose-worker-concurrency-and-helm-cache-size-as-tuning-knobs]]). The wiki's own reading of the sources is to tune first and shard when one instance reaches its limits, though no source states a threshold ([[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]]). Morgan Stanley did exactly the tuning route, as we will see.

When tuning is not enough, Flux shards by label. Additional controller deployments run under unique names, for instance `source-controller-shard1`, each started with `--watch-label-selector` set to its own value of the label `sharding.fluxcd.io/key`, so it reconciles only objects with that label, while the default controllers skip labeled objects so nothing is handled twice ([[examples/flux-sharding-splits-reconciliation-across-label-selected-controller-instances]]). The sharp edge is consistency: a HelmRepository, the HelmChart generated from it, and the HelmRelease that uses the chart all need matching labels, or the pieces land on different controllers ([[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]]). A parent Kustomization can bulk-label children, and the Flux Operator can declare shards in a `FluxInstance` spec. The wiki notes Flux shards only three controllers and leaves the notification controller as a singleton.

Argo CD shards by destination cluster. Application-controller replicas are told the replica total (`ARGOCD_CONTROLLER_REPLICAS`) and clusters are assigned with the `legacy`, `round-robin` or `consistent-hashing` algorithm, or pinned through the cluster secret. The worker counts are set with `--status-processors` and `--operation-processors` (defaults of 20 status processors and 10 operation processors, confirmed against the raw documentation, with 50 and 25 suggested for about 1,000 applications), and `GOMEMLIMIT` is set to 80 to 90 percent of the container limit ([[examples/argo-cd-application-controller-shards-clusters-and-tunes-processor-counts]]). The legacy algorithm distributes clusters by UID in a non-uniform way, so it can be uneven. The other two algorithms are still labelled experimental (Alpha) on the v3.6.3 high-availability page (released 2026-11-24), with wording unchanged since v2.14.0 ([[findings/argo-cd-legacy-sharding-can-be-uneven-and-the-other-algorithms-were-labelled-experimental]]). Which method is the default today is not confirmed. The v2.8.0, v2.14.0 and v3.0.0 pages marked `legacy` as the default, while the v3.6.3 page lists all three methods without any "(default)" marker; nothing the wiki read says the default changed, but it did not read the parameters config map reference or the v3 upgrade notes. If it matters to you, check the controller's `--sharding-method` setting or the `argocd-cmd-params-cm` config map instead of the documentation ([[findings/the-argo-cd-v3-6-3-high-availability-page-no-longer-marks-legacy-as-the-default-sharding-method]]). Compare the two ideas in [[comparisons/flux-label-sharding-versus-argo-cd-cluster-sharding]]: Flux's key is a label on each object, which is flexible and requires discipline, while Argo CD's key is the destination cluster, which fits hub-and-spoke setups naturally.

The same split-by-key idea appears outside GitOps. kro funnels the events for all of its instances through one shared, rate-limited queue. Because every ResourceGraphDefinition feeds the same queue, a rate limit on that queue works as a fairness device: a definition with thousands of busy instances, or one stuck in a failure loop, can only consume its share of the worker time and API calls, and cannot starve the others. The caps matter because without them a single misbehaving definition would be limited only by how fast the cluster could answer. The same backoff-and-token-bucket ideas described in section 7 apply, and a retry cap adds a final stop so that an object that never succeeds is eventually left alone instead of being retried forever ([[examples/kro-shared-queue-tunes-throughput]]). The released kro v0.10.0 (published 2026-11-10) documents the same defaults that the earlier unreleased documentation showed, so the earlier caveat no longer applies to them: a default of 20 retries before an item is dropped, a single worker, a 200 ms to 1000 s backoff range combined with a token bucket of 10 items per second and a burst of 100, client-side QPS (queries per second) of 100 with a burst of 150, and a 10-hour full resync. The v0.10.0 page adds a 30-second watch sync timeout, a collection limit of 1,000 items, and an instance requeue interval of 3 seconds that now backs off exponentially up to five minutes. The older v0.9.4 page reads as a fixed delay, so the exponential behavior looks new, though that is an inference from two pages, and the v0.9.4 rate-limiter table was not read in full. The docs also say per-definition queues may replace the shared queue in a future version, and there is no measured throughput data, only an open request for performance testing and a maintainer proposal for weighted queues ([[findings/kro-s-single-shared-queue-can-starve-resources-and-a-maintainer-proposed-weighted-queues]]). Crossplane composite load is arithmetic: composites poll every 60 seconds by default in core (Upjet-based providers poll managed resources every 10 minutes, a different layer with a different default) and each function step is a gRPC call, so 100 composites with one function step produce about 100 calls per minute, and large composites can exhaust function memory according to a third-party article whose log excerpts are labelled simulated ([[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]).

For Crossplane the dominant scale problem is CRD count, and the remedy is packaging. The original provider-aws registered a CRD for every AWS service and passed 900 CRDs, which could leave the API server unresponsive for up to an hour during scale-up. Provider families split the monolith so an operator installs only the member providers for the services in use, sharing a common configuration provider ([[examples/crossplane-provider-families-let-operators-install-only-the-cloud-services-they-use]]). The design document's estimate was a typical user dropping from more than 900 CRDs to about 176, at the cost of about nine provider pods instead of two ([[findings/splitting-a-provider-into-a-family-trades-fewer-crds-for-more-pods-and-memory]]); the figures reproduced against the raw design document, which also says problems start "very approximately" above 500 CRDs, a rough threshold and not a tested limit. The memory figures in that document (about 600 MB for the Crossplane provider process and about 300 MB for each Terraform provider process) are targets the authors hoped to reach, not measurements, and the document is still marked Draft ([[findings/crossplane-provider-memory-figures-are-design-doc-targets-not-measurements]]). Crossplane v2 adds a second control: ManagedResourceActivationPolicies list exact names or prefix patterns, and only matching ManagedResourceDefinitions become served CRDs ([[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]]). Two cautions apply. First, the documentation labels activation policies and definitions alpha, although the source code lists the definition conversion under beta features, so the stage is disputed between the docs and the code. Second, a stock install does not save you anything: the default Crossplane Helm chart creates a `default` activation policy that activates every resource (`provider.defaultActivations: ["*"]`), so you must turn that default off, for example with `--set provider.defaultActivations={}`, and then list the groups you need. Activation is also one-way, so a definition that has become Active cannot be deactivated, and providers that declare the `safe-start` capability start their definitions Inactive while others start Active ([[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]]). The Crossplane docs estimate about 3 MiB of API server memory per CRD, which is an estimate, and no with-versus-without measurement was found. Current scaling guidance is scattered across pages (a one-minute polling default with an hourly full re-check, API Priority and Fairness in place of custom client-side rate limiting since v2.1.0, a circuit breaker on composites, and a configurable concurrency setting), and the wiki found no documented numeric limits for composites or composed resources. ACK avoided the problem by shipping one controller per service from the start ([[comparisons/provider-families-versus-per-service-controllers]]), and the choice among families, filtering and lazy loading is framed in [[decisions/split-a-large-provider-into-families-or-filter-or-lazy-load-its-crds]].

Domain-scoped control planes are the architectural version of the same idea. Two practitioner blogs argue that teams no longer need one monolithic Crossplane instance and propose several small control planes scoped to domains such as networking or data. The wiki marks this as advice and not evidence: neither post names an organization running it or gives numbers ([[examples/domain-scoped-crossplane-control-planes-are-proposed-in-place-of-one-monolithic-instance]], [[decisions/run-one-crossplane-control-plane-or-several-domain-scoped-ones]]). It fits the blast-radius principle, but it also multiplies the clusters you must operate.

The tooling comparison across stacks is in [[comparisons/concurrency-and-cache-memory-controls-across-flux-argo-cd-and-crossplane]] and [[comparisons/load-and-fairness-controls-across-controller-runtime-flux-argo-cd-and-kro]]. For retry behavior, [[comparisons/retry-and-backoff-controls-across-tools]] shows that kro caps retries at 20, Argo CD refuses to retry a failed sync of the same commit unless retry is configured, and Flux separates `retryInterval` from `interval`; uncapped retries are the cause of the retry storms described in section 10.

## 9. Industry scale stories: Morgan Stanley, Upbound, Ant Group, Gardener, Cozystack

Real organizations show how these principles bend under load, but the evidence quality varies, and it is worth reading each story with its caveat.

Morgan Stanley described its Flux adoption at FluxCon North America 2025, written up by the Flux team in March 2026, with a reported footprint of "over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources." Before Flux it used push pipelines, which suffered drift and made cluster rebuilds fragile. Multi-tenancy rested on service account impersonation, and a self-service onboarding platform checked entitlements, registered the service in a configuration management database, primed the namespace with a `GitRepository` and a `Kustomization`, and scaffolded the team's repository. At scale the team raised reconciliation intervals, tuned `--concurrent` and resource limits, and moved the source of truth from a self-hosted Git provider to S3 buckets, which the write-up gives as an availability and compliance choice ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]). Sharding, OCI artifacts and Flagger were roadmap items, so there are no production sharding numbers. It is a self-reported conference account, not an independent audit, but it is the clearest evidence that vertical tuning plus per-tenant impersonation holds at several hundred clusters.

Upbound's test, covered in section 7, is the story of what happens when a platform meets API machinery that was never tested for thousands of CRDs, and it ended with upstream Kubernetes fixes and then Crossplane's own packaging answer. Crossplane's ADOPTERS list adds self-reported counts from thousands of managed resources (Nike, Deutsche Kreditbank, SAP at 100-plus control planes as of February 2024) up to Akamai's provider-ceph orchestrating up to 200,000 managed resources; the wiki treats these as pointers and not as verified case studies ([[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]]). The targeted pass added a little more named detail. The Crossplane adopters file has 87 entries, but only about eight give any number. Built Technologies says that at times it has exceeded 10,000 AWS resources managed by Crossplane, in a developer environment and not production, undated and self-reported ([[examples/built-technologies-reports-peaks-above-10000-aws-resources-managed-by-crossplane-in-a-developer-environment]]). On the ACK side, Adobe is listed for global Kubernetes cluster provisioning and for stateful service infrastructure using multiple ACK controllers, with no object count and no date ([[examples/adobe-lists-ack-for-global-kubernetes-cluster-provisioning-and-stateful-service-infrastructure]]). Argo CD's users file lists 452 self-reported adopters, but the GitOps outages the wiki found are anonymous GitHub issues. No organization says it runs sharded Flux, since Morgan Stanley lists sharding as future work, and there is no adopters file for kro, Cluster API or Config Connector, so named adopters and measured scale for those remain absent ([[findings/no-named-organization-postmortem-was-found-for-a-gitops-revert-loop-a-gitops-outage-or-controller-retry-amplification]]).

Ant Group's more-than-10,000-node cluster is a reminder that custom resources share storage and watch paths with built-in objects, so general apiserver and etcd tuning applies to them too, though the write-up is not about CRDs. Gardener, an operator of many clusters for many tenants, supplies the conservative numbers from section 7 and the warning that conversion webhooks are especially risky because an outage blocks garbage collection ([[findings/a-down-conversion-webhook-can-stall-garbage-collection]]).

Cozystack is a different kind of story. It packages Talos Linux, Kubernetes, KubeVirt, LINSTOR with DRBD, and Kube-OVN into a PaaS framework for turning commodity servers into a cloud offering Kubernetes clusters, databases and VMs through an API ([[examples/cozystack-turns-commodity-servers-into-a-cloud-with-kubernetes-databases-and-vms]]). The wiki has no adopter names or measurements for it, so it illustrates the architecture's direction and not its scale.

Several other stories show platform composition in practice. JFrog delivers self-service cloud environments through Jenkins, Git, Argo CD and Crossplane ([[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]). VSHN's AppCat sells self-service databases, queues and object storage through composition functions ([[examples/vshn-appcat-sells-self-service-databases-queues-and-object-storage-through-composition-functions]]). A Google Cloud style stack that delivers Config Connector resources from Git with Argo CD or Flux is described in [[concepts/tooling-landscape]]. The control-plane-as-a-platform idea at its far end is kcp hosting node-less API workspaces for multi-tenant SaaS ([[examples/multi-tenant-api-hosting-with-kcp]]) and Cluster API managing fleets of clusters ([[examples/cluster-fleet-lifecycle-with-cluster-api]]). The wiki repeatedly notes that named production adopters, scale numbers and postmortems remain thin.

## 10. Pitfalls catalog and operational guardrails

The postmortems in the wiki agree that serious incidents are cascades in which a small change meets a loop, a default or a shared dependency. [[concepts/pitfalls-and-case-studies]] names three mechanisms that recur: finalizers, field ownership and deletion propagation. We have already met all three. This section adds the rest and pairs each pitfall with the guardrail the tools provide.

Retry storms come first. Zalando's January 2019 outage began with a timed-out downstream call. Clients retried, which spiked DNS queries; the CoreDNS pods had a 100Mi memory limit and were OOM-killed together; the `ndots:5` default meant about ten DNS queries per external lookup; and monitoring that depended on DNS and ran inside the cluster went blind. Zalando raised the memory limits to 2000Mi, adopted a node-local design, and moved alerting outside the cluster ([[examples/zalando-s-2019-coredns-outage-turned-a-retry-storm-into-a-total-dns-failure]], [[findings/monitoring-that-runs-inside-the-cluster-and-depends-on-cluster-dns-goes-blind-in-the-outage-it-should-report]]). The postmortem states the principle: it should not be possible for a single application to take down DNS infrastructure. Within the tools, retries are capped differently, as described in section 8.

Webhook outages are a recurring class in the k8s.af index ([[findings/admission-webhook-outages-are-a-recurring-failure-class]]), and the wiki has now read one of those postmortems in full: Jetstack's post of 2019-09-05, read through a Wayback Machine copy because the original page returned empty. A regional GKE cluster in europe-west1, shared by many teams, was upgrading its master through a Terraform pipeline. During the second master's upgrade the API server tried to update the `extension-apiserver-authentication` ConfigMap in `kube-system` as part of a post-start hook, and that write was subject to an OPA validating webhook whose backend was not responding, so it timed out. The post says the operation must complete for a master to pass its health check, so the master crash-looped and the upgrade halted. Intermittent API downtime then stopped kubelets from reporting node health, and GKE node auto-repair began recreating nodes in an endless loop, which caused loss of service for every tenant. Jetstack fixed it by deleting the validating webhook, which worked only because the API server answered intermittently. Its follow-ups were scoping the webhook to the namespaces where policy applies, enabling it only for Ingress and Service resources, adding a liveness probe to OPA, and alerting on API server response times for create and update calls, and it deliberately kept node auto-repair on. The post never mentions `failurePolicy`, so its fixes were not a change of failure policy. The account is self-reported ([[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]]). The second k8s.af webhook entry, an Airbnb KubeCon talk, was video-only and unread, so only these two webhook entries exist in the index and just one has been verified. The OpenAI incident in section 7 shows the same lesson from the control-plane side, since the tools needed to repair the cluster sat on the path that failed. The official guidance is to scope matches narrowly, exclude system namespaces, keep timeouts short, run multiple replicas and use `Fail` only for security-critical checks ([[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]]).

Ordering and CRDs are the next group. Applying a custom resource before its CRD is established fails with "no matches for kind", reported in Helm, Argo CD and Flux alike ([[findings/custom-resources-applied-before-their-crd-exists]]). Flux's remedy is separate Kustomizations linked by `dependsOn` with health checks; Argo CD users reach for sync waves, where the order is phase, then wave, then kind, then name, and each wave must be Healthy before the next ([[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]]); the wiki marks some Argo CD details as unverified, and compares the two in [[comparisons/missing-crd-handling-flux-versus-argo-cd]]. Helm has no native support for upgrading or deleting CRDs, which Flux works around with `install.crds` and `upgrade.crds` policies ([[findings/helm-does-not-upgrade-or-delete-crds]]). Circular `dependsOn` chains never reconcile ([[findings/circular-dependson-chains-between-flux-resources-never-reconcile]]). The deeper principle, from [[concepts/eventual-consistency-and-convergence]], is that Kubernetes does not promise instant convergence; Flux's `dependsOn` keeps the retry-until-ready behavior but in a controlled order, so transient errors do not arrive as a burst ([[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]).

Automation hazards come from the fact that GitOps tools do exactly what they are told, quickly and repeatedly, so any ambiguity in what they are told becomes an outage. The first hazard is image automation, where a controller watches a container registry and writes new image tags back into Git. If the rule that selects tags is looser than the team realizes, an unintended version is committed and then rolled out by the same loop that normally protects you, and nothing in the pipeline treats it as unusual ([[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]]). Flux's reference repository limits image automation to staging for that reason, so production changes still pass through a human decision.

A related hazard is the mutable remote reference. A Kustomization or Helm release can pull a base or a chart from somewhere other than your repository, and if that reference points at a branch or a floating tag, the same commit of your own repository can render different manifests tomorrow than it did today. The deployment looks unchanged in Git while the cluster changes, which defeats the audit trail that made GitOps attractive. Pinning remote Helm and Kustomize references to tags or commit SHAs restores the property that a commit determines what runs ([[findings/mutable-remote-references-change-what-a-commit-renders]]). Rollback has a similar trap in Argo CD. Its rollback action works by deploying an older revision directly, but while automated sync is on, the next sync immediately re-applies whatever Git says, so the rollback is undone or refused. The tool blocks it to protect the principle that Git is the source of truth, which means the working path is a Git revert that the automation then follows ([[findings/rollback-is-blocked-while-automated-sync-is-on]]).

The remaining hazards concern how objects are written. Argo CD's `Replace` and force sync options delete and recreate a resource instead of patching it, which is sometimes needed for immutable fields but briefly removes the object, so a Deployment or a stateful resource can take an outage ([[findings/argo-cd-replace-and-force-sync-options-can-recreate-resources-and-cause-outages]]). Flux's `force` option does the same when an update touches an immutable field, and it should be a temporary measure and not a standing setting. Migrating from client-side apply to server-side apply can leave behind fields that nobody now wants. The old `kubectl apply` ownership is recorded under a manager that no longer runs, and a stale co-owner cannot be forced off a field by the new manager through an ordinary apply, so removing the field from Git does not remove it from the live object ([[examples/flux-migration-from-client-side-apply-strands-removed-fields]]). Finally, an Argo CD app-of-apps, which is an Application whose job is to create other Applications, can show perpetually out of sync when an image updater edits the same fields that the parent also declares. That is the same two-writers field fight from section 2, and the fix is likewise an explicit ownership decision ([[examples/argo-cd-app-of-apps-out-of-sync-from-image-updater]]).

Silent failures are the most dangerous class because nothing alerts. Flux failures can be silent when resources are suspended, when polling lag hides a missing webhook, or when the `--with-source` flag is missing ([[findings/suspended-resources-polling-lag-and-a-missing-with-source-flag-make-flux-failures-silent]]); the evidence there is documentation plus one practitioner blog. The `Synced=False` with `Ready=True` case from section 4 belongs here too.

A short set of operational guardrails follows from all of this, stated as sentences and not a checklist. Keep prune off until the source of truth is trusted, and annotate objects that must never be pruned. Choose an orphan or retain policy for critical external resources before deleting anything, and apply the policy before the delete. Set explicit propagation options when a GitOps tool hosts composites. Alert from outside the cluster on saturation signals. Read both the GitOps tool's sync status and the custom resource's conditions. Keep test environments identical to production and read release notes before upgrades. Review cluster-scoped configuration with the rigor of code. The wiki is careful to say that its pitfall evidence rests mostly on 2017 to 2021 incidents, documentation and blogs, and that it read no pitfalls specific to kro, Config Connector, ACK or Cluster API ([[findings/the-pitfalls-dossier-rests-on-index-summaries-an-older-crossplane-version-and-few-primary-incident-reports]]).

## 11. The tooling landscape: delivery, provisioning, platform and portal layers

The landscape is easiest to learn as three layers that solve different problems and are routinely combined, and confusing them is the most common source of bad comparisons ([[concepts/tooling-landscape]], [[comparisons/delivery-versus-provisioning-versus-platform-layers-in-the-kubernetes-tooling-landscape]]). Asking whether Argo CD or Crossplane is better is like asking whether a package manager beats a database, because one moves manifests and the other reconciles cloud resources.

The delivery layer gets desired state from Git, OCI or Helm into a cluster and keeps it there. Flux and Argo CD are the two CNCF projects. Argo CD ships as an integrated application with an API server, a repository server that renders manifests and an application controller that diffs live against target state, polling on a 120-second cadence with up to 60 seconds of jitter in v3.x. That is a version-specific fact: through v2.14 the default was a flat 180 seconds, and some newer documentation still repeats the three-minute figure. The wiki did not find the reason for the change ([[findings/argo-cd-changed-its-default-polling-from-a-flat-180-seconds-to-120-seconds-plus-60-seconds-of-jitter-in-v3-0-and-some-docs-still-say-three-minutes]]). Flux ships as a toolkit of small controllers that each own their own CRDs, so its parts can be used by other automation ([[comparisons/flux-versus-argo-cd-architecture]], [[comparisons/reconcile-cadence-and-off-switches-across-tools]]). The vendor caution applies here: comparisons often come from vendors such as Akuity (which sells Argo CD), Port and Syntasso (which sells Kratix), with no independent benchmarks ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]], [[comparisons/flux-versus-argo-cd-isolation-ordering-and-interface-according-to-a-vendor-blog]]). The pull-versus-push comparison in [[comparisons/push-versus-pull-delivery]] explains why pull limits credential exposure: a push pipeline holds credentials for every environment, while a pull agent needs only read access to the source but becomes a powerful identity itself. Flux's D2 reference architecture goes further, with clusters pulling signed OCI artifacts so they never connect to a Git host ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]); the wiki notes this is a vendor write-up, and whether Git or OCI should be the source of truth is unresolved (see [[concepts/gitops-pull-based-delivery]]).

The provisioning layer turns custom resources into calls against an infrastructure API. Config Connector, ACK and Azure Service Operator are single-vendor controllers that expose roughly one CRD per cloud resource ([[comparisons/crossplane-versus-cloud-vendor-add-ons-ack-config-connector-and-aso]]). Crossplane is multi-cloud and adds Compositions so a platform team can publish its own API without writing a controller. The Terraform wrappers, tofu-controller and terraform-operator, run plan and apply in pods ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]]). Cluster API applies the pattern to Kubernetes clusters themselves. The per-resource controllers do not build a dependency graph, so ordering falls to the delivery tool or a composition layer, and the controller holds the cloud identity, so whoever can create the custom resource inherits its rights.

The platform and portal layer defines what application teams see. Backstage and Port are catalogs and portals with self-service actions, Kratix is an orchestration framework behind a portal where a Promise, Kratix's unit of packaging, bundles a platform API together with the workflows that fulfill requests for it and the rules for scheduling the result onto a fleet of clusters, and Cozystack ships its own substrate ([[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]). The wiki records that a portal supplies visibility and not provisioning, a claim attributed to a Kratix vendor.

Abstraction tools overlap with each other. kro merges schema and implementation into one ResourceGraphDefinition, generates the CRD, infers dependency order from CEL references, and deletes in reverse; the Crossplane project's `function-kro` runs kro-style graphs inside a pipeline. Helm and Kustomize are render-time abstractions that produce manifests once and leave correction to a GitOps tool, while composites are live control loops ([[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]], [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]]). Both tools reach the same outcome in the wiki's StorageApp comparison, with kro inferring order and Crossplane's Go-template route needing hand-written ordering and deletion guards ([[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]). A worked end-to-end example is [[examples/platform-team-self-service-apis-with-crossplane-and-kro]], and kro is `v1alpha1`, which the wiki flags as immaturity ([[findings/immature-abstractions-in-the-control-plane-ecosystem]]).

For plain controllers, the contrast is the cost of writing one per platform API, which composition and resource graphs exist to avoid ([[comparisons/hand-written-operator-versus-crossplane-composition-versus-kro]]). Tenancy at the cluster level is compared in [[comparisons/tenancy-models-namespaces-vcluster-kcp]].

## 12. Remaining gaps and what is not yet known

This part would be dishonest if it ended with a tidy conclusion, because the wiki records many open questions, and several touch the heart of the thesis.

The first is the trace itself. The wiki's open gap on the full Git-commit-to-Ready lifecycle remains open: no source traces the handoff from the source controller to the kustomize controller in detail, finalizer registration, and status updates, and the dossiers cover Flux at the component and API level. What you read in section 2 is a faithful composition of documented behaviors, but it is a composition and not an observation. A worked example on a live cluster would close it.

The second is scale evidence. Named production adopters and object counts are mostly self-reported. The scale dossier relies on digests for most numbers, so limits need rechecking. There is no sourced data on how cloud provider API limits constrain Crossplane, Config Connector or ACK, no scaling data for kro, ACK, Cluster API or Config Connector controllers, and no documented numeric limits in the current Crossplane v2 scaling guidance, which exists only as scattered advice. The scale figures that came from digests were rechecked against raw text on 2026-11-26 and held up. No source states a threshold at which Flux sharding becomes necessary, and Morgan Stanley lists sharding as future work. Authoritative CRD scale limits are open ([[findings/the-scale-dossier-relies-on-model-digests-for-most-numbers-so-limits-need-rechecking]]).

The third is controller mechanics. Informer resync semantics are unresolved: no source explains whether resync replays cached state to handlers or refetches from the API server, and sources disagree on whether it should be on ([[decisions/keep-informer-resync-disabled-or-set-a-periodic-resync]]). The reconcile result `Requeue: true` is deprecated, and its behavior is now settled at controller-runtime v0.25.3: it is a rate-limited requeue with per-object exponential backoff, and the failure history is kept, so a reconciler that returns it on every pass waits longer each time. Only `RequeueAfter` clears the history and schedules the next run after exactly that duration. The earlier suggestion in one issue summary that it requeues immediately could not be traced to a source, because only the issue body was read and not its comment thread ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]]). Reconcile defaults are now mostly established: Crossplane polls at one minute in core and ten minutes in Upjet providers, ACK resyncs at about ten hours, Config Connector averages ten minutes with jitter, and Cluster API's ten-minute sync period is a cache resync and not a poll of the cloud infrastructure, though Cluster API drift handling beyond that flag was not found ([[findings/crossplane-poll-interval-defaults-differ-by-layer-with-one-minute-in-core-and-runtime-and-ten-minutes-in-upjet-providers]], [[findings/the-cluster-api-sync-period-flag-is-a-cache-resync-and-not-a-poll-of-the-cloud-infrastructure]]). Server-side apply behavior in kro, ACK, Config Connector and Helm 4 still could not be read.

The fourth is the evidence for failure modes. The pitfalls evidence is mostly older, documentation-based and vendor-influenced. The wiki still found no organization-authored postmortem of a runaway reconcile loop, an accidental prune, an operator failure or a kro, Config Connector, ACK or Cluster API pitfall, and only five named-project issues with two recurring causes (a status write on every pass, and volatile text in a condition message that defeats the equality check) stand in for them. The control-plane-as-platform class now has two primary reports, OpenAI (December 2024) and Neon (May 2025), plus Jetstack's 2019 webhook outage, but nothing from 2024 to 2026 on Argo CD, Flux, Crossplane, Karpenter or cert-manager surfaced, and the Skyscanner, Reddit and Spotify primaries were unreadable with the available tools, so they remain index-level evidence. How Flux, ACK, Config Connector and kro name and remove their own finalizers was not established. The Flux default interval conflict is explained in section 2: the concepts page says five minutes, and the API types require an explicit interval.

The fifth is design direction. Where `observedGeneration` should live, the right polarity for new condition types, the best default conflict policy for teams running GitOps beside in-cluster controllers, and whether to place external names in an annotation or a spec field are all framed as open decisions. Crossplane versus kro is still a live debate, and the abstractions themselves are young.

None of these gaps contradicts the thesis, and each sharpens it. The mechanics compose, the principles follow from the composition, and the places where the evidence is thin are the places where a careful platform team should measure its own system instead of trusting a number from a blog.
