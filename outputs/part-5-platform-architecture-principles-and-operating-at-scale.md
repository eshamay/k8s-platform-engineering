# Part 5: Principles of Good Platform Architecture and Operating at Scale

> [!NOTE]
> **Audience:** Engineers who operate Kubernetes (pods, deployments, services, RBAC, kubectl) and are finishing the tutorial series on controllers, API machinery and platform abstractions.<br>
> **Purpose:** Trace one Flux commit through server-side apply, finalizers and conditions to a Ready status, show that good platform architecture is the disciplined composition of the earlier mechanics, and describe what operating that architecture at scale requires.<br>
> **Status:** Active. The end-to-end trace is assembled from documented pieces, because the wiki holds no single sourced trace (see section 12).<br>
> **Created:** 2026-11-25<br>
> **As of:** 2026-11-26<br>
> **Draws on:** [[concepts/universal-control-plane]], [[concepts/gitops-pull-based-delivery]], [[concepts/reconciliation-loop]], [[concepts/server-side-apply-and-field-ownership]], [[concepts/finalizers]], [[concepts/conditions]], [[concepts/scale-and-sharding]], [[concepts/pitfalls-and-case-studies]], [[concepts/tooling-landscape]], and the examples, findings, comparisons and decisions linked inline

## 1. Recap: the layered stack from Parts 1 to 4

The earlier parts of this series built one idea in layers, and this final part puts the layers to work together. It helps to restate them in plain terms before we trace anything.

The foundation is the observation that Kubernetes ships two products in one box. One is a container scheduler. The other is a generic, extensible API machine: an API server that provides authentication, RBAC, admission, validation and watch, backed by etcd, plus a convention that controllers reconcile an object's `spec` (what you want) toward its `status` (what is observed). The second product has no inherent tie to pods, so anything that can be described declaratively and reconciled by a loop can become a custom resource, whether it is a cloud database, a DNS record or a whole cluster. That is the idea behind the [[concepts/universal-control-plane]], and every tool in this part depends on it. Once an outside thing is represented as a Kubernetes object, it inherits authentication, RBAC, audit and a shared tooling ecosystem.

The second layer is the controller itself. A controller runs a [[concepts/reconciliation-loop]]: a function that receives only the namespace and name of an object, never the event that woke it, reads the current state, performs API calls to close the gap, and writes status. Because the function can run many times in any order, it must be [[concepts/idempotency]] safe, and because it works from current state and not from a stream of events, it is level-triggered, meaning a missed event cannot leave the system permanently wrong. Under the loop sits the machinery from [[concepts/informers-reflectors-and-workqueues]]: a reflector lists and then watches the API server, an informer keeps an in-memory cache, and a rate-limited workqueue deduplicates object keys so that one object is never reconciled by two workers at once.

The third layer is the set of API conventions that let many writers share one object. [[concepts/server-side-apply-and-field-ownership]] records which manager owns each field in `metadata.managedFields`. [[concepts/finalizers]] hold an object in the API until its controller has cleaned up whatever lives outside the cluster. [[concepts/owner-references-and-garbage-collection]] let the cluster remove children when a parent goes away. [[concepts/conditions]] give every kind a common, machine-readable way to say whether it is ready.

The fourth layer is the set of abstractions that platform tools build on top. A [[concepts/provider]] teaches the control plane to speak to an external API and exposes [[concepts/managed-resource]] objects, each standing for exactly one outside resource. A [[concepts/composite-resource]] bundles several of those behind a simple API, and a [[concepts/composition]] defines how the bundle expands. On the delivery side, [[concepts/gitops-pull-based-delivery]] uses an in-cluster agent such as Flux to pull desired state from Git and apply it.

The thesis of this part is that none of these pieces is new when you meet it in a platform. A good platform is the disciplined composition of the same mechanics, and a failing platform is nearly always one of those mechanics used carelessly. The fastest way to see this is to follow one commit all the way down and then all the way back out.

## 2. End-to-end lifecycle trace: a Git commit to a Flux Kustomization to server-side apply

A note on evidence before we start. The wiki records, as an open gap, that no single source traces a Flux commit step by step through to a Ready object. What follows is therefore an assembly of documented behaviors from the Flux documentation, the Flux deep dive and the concept pages, and we will mark the places where the documentation is silent. The composition is the point of the exercise, and it is the best test of whether the earlier concepts fit together.

Imagine a platform team that keeps a Git repository describing what should run in a cluster. A developer merges a commit that changes the image tag of a Deployment. Flux is a set of single-purpose controllers that communicate through custom resources, so the first thing to understand is who does what. A source controller watches a `GitRepository` object, fetches the repository on its interval and packages the content as an artifact. A kustomize controller watches a `Kustomization` object that points at that source, builds the manifests and applies them. The notification controller can accept a webhook from the Git host that tells the source to refresh immediately, which is described in [[examples/flux-notification-receivers-start-reconciliation-without-waiting-for-the-poll-interval]]. Without a webhook, the commit waits until the next interval fires, which is a quiet failure mode, because the system looks healthy while changes arrive late.

The handoff between the source controller and the kustomize controller has a few operational details that the 2026-11-26 Flux internals research read from source. The source controller serves the artifacts it builds through a small in-process HTTP file server, and it starts that server only after it has won leader election. Leader election means that several replicas of a controller may run but only one holds a lease and does the work. A standby replica reports itself not ready by design, so adding replicas of the source controller buys failover and not extra capacity, as the Flux sharding page itself says. The stock manifest runs a single replica with a Recreate rollout strategy and two `emptyDir` volumes (scratch storage that disappears when the pod does), and the artifact flags default to a storage path of `/data` with a retention of one minute. The research inferred, but did not verify, that `/data` maps to one of those scratch volumes, so a restart most likely empties the artifact store and every dependent waits while the next reconcile rebuilds it. In practice that means a source controller that is rolled often, or scheduled on nodes that get evicted, produces short windows in which Kustomizations cannot fetch their sources. The wiki did not read the lease durations or how dependent controllers behave in that window, and it found no documentation of a persistent-volume alternative ([[findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness]], [[findings/the-stock-flux-source-controller-keeps-artifacts-in-an-emptydir-with-one-minute-retention-so-a-restart-rebuilds-them]]).

Here is a minimal Kustomization of the kind a platform team would write. It is illustrative, and the field names follow the Kustomization API as the wiki describes it.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: team-a
spec:
  interval: 10m
  retryInterval: 2m
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: team-a-repo
  path: ./deploy/production
  prune: true
  wait: true
  serviceAccountName: team-a-deployer
  dependsOn:
    - name: infrastructure
```

Read it as a policy wrapped around the bare reconcile primitive. The `interval` says how often the controller re-fetches, builds, applies and checks for drift; the Kustomization reference recommends a minimum of 60 seconds, phrased as "should", and nothing in the API type enforces it. The `retryInterval` is the delay before the next attempt after a failure, and it defaults to the interval. The `timeout` caps the build, apply and health-check work of a single run. The `prune` field turns on garbage collection, `wait` holds the object until what it applied is healthy, and `dependsOn` makes this Kustomization wait for another one to be Ready. This is exactly the structure described in [[examples/flux-kustomization-interval-and-retry-interval-set-the-loop-timing]]: a cadence, a failure delay, a time budget and a set of switches. One point from the wiki is worth repeating because it corrects a common belief. The Flux concepts page says reconciliation runs every five minutes by default, but the Kustomization and HelmRelease references both call `.spec.interval` a required field, and the Kustomization Go type marks it as required with no default value. A manifest without an interval is therefore rejected and never quietly falls back to five minutes. The only default the wiki found is the one-minute `--interval` flag of the `flux create` command, which applies when the command-line tool generates a manifest for you. This is not a difference between versions: Flux's own pages disagree. The wiki traced the five-minute wording to a documentation commit on 2022-08-10 that replaced an earlier "every one minute by default" with no stated reason and no accompanying controller change, so why the sentence says five minutes is unknown. The practical consequence is that drift-correction latency in Flux is whatever the author wrote in the manifest, so set the interval explicitly on every object. Changes to the source itself are picked up outside the interval window when a webhook fires, so the interval governs mainly drift detection and periodic re-checks.

Now the apply. The kustomize controller does not use the old client-side approach of stamping a `last-applied-configuration` annotation. It uses server-side apply. The controller sends the set of fields it has an opinion about together with a field manager name, and the API server merges that into the live object and updates `managedFields`. In Part 3 we saw that if another manager owns a field with a different value, the API server answers with a conflict instead of silently overwriting. Flux's posture, as the wiki records it in [[comparisons/ssa-conflict-policy-across-tools]], is to force-apply its own intent by default and then offer escape hatches. The Kubernetes documentation recommends that controllers force conflicts on objects they own, while the same maintainers argue that CI/CD systems behave like users and should surface conflicts to humans. The wiki frames this unresolved tension in [[decisions/force-conflicts-or-surface-them-to-humans]]. Other tools in this part sit at different points on that spectrum, as the wiki read from source on 2026-11-26. kro applies the resources it templates with server-side apply and forces ownership when its force flag is set, but a patch node that contributes fields to an object kro does not own is applied under its own manager without force, so it claims only the fields it sets ([[findings/kro-applies-template-resources-with-server-side-apply-and-force-and-applies-patch-contributions-without-force]]). The Cluster API topology controller forces ownership under the manager name `capi-topology` while letting provider controllers co-author the generated objects, although co-authored list slices can reconcile forever when apply cannot remove list items ([[findings/cluster-api-co-authored-list-slices-can-reconcile-forever-and-server-side-apply-can-fail-to-remove-list-items]]). The ACK runtime does not use server-side apply at all: it sends merge patches and sets no field manager ([[findings/the-ack-runtime-sends-merge-patches-and-sets-no-server-side-apply-field-manager]]). Helm 4 defaults to server-side apply for new releases, but an upgrade or rollback follows the method of the previous release, so releases created by Helm 3 stay on client-side apply until reinstalled ([[findings/helm-4-defaults-to-server-side-apply-for-new-releases-and-helm-controller-keeps-the-previous-method-on-upgrade]]).

Flux runs a server-side apply dry run on every interval to detect drift, which is why a hand edit gets reverted. [[examples/gitops-reverts-a-hand-edited-deployment]] describes the outcome: the revert is not a bug, it is a level-triggered controller doing what it was built to do, and teams that need an emergency change must set `suspend` first, which stops both applying and drift detection.

The same field-ownership machinery explains the most famous way this goes wrong. In [[examples/flux-resetting-hpa-replicas-caused-a-sev2-scaling-loop-until-ignore-rules-existed]], Flux kept resetting a replica count, a horizontal autoscaler kept lowering it, and the cluster autoscaler added and removed nodes in a loop that a Flux blog describes as two controllers ping-ponging indefinitely. Flux's answer was a `.spec.ignore` list of JSON Pointer paths. A "strip" rule removes the field from Flux's payload when another server-side apply manager owns it, and an "adopt" rule keeps the live value when Flux is the sole owner. The price, recorded in [[findings/ignoring-a-field-in-flux-or-argo-cd-means-git-changes-to-it-are-no-longer-applied]], is that Git changes to an ignored field are no longer applied. Per-object annotations such as `kustomize.toolkit.fluxcd.io/ssa` choose between Override, Merge, IfNotPresent and Ignore, as shown in [[examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers]]. There is one limit that surprises people: lists in custom resources whose CRDs carry no merge markers are treated as atomic, so only one manager can own such a list ([[findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership]]).

The two big GitOps tools word their versions of this escape hatch differently, and each has a trap that the 2026-11-26 primary-documentation pass documented. A Flux ignore rule can carry an optional `target` selector, and the Kustomization specification says that omitting it makes the rule match every object the Kustomization manages. A rule written with one Deployment's `/spec/replicas` in mind therefore also exempts that path on every other object, and real drift there goes uncorrected without any signal, so the safe habit is to give every rule a target ([[findings/a-flux-ignore-rule-without-a-target-selector-matches-every-object-the-kustomization-manages]]). Argo CD's `ignoreDifferences` is narrower than its name suggests. By default Argo CD uses it only when computing the diff that drives the sync status, so an ignored field stops showing as OutOfSync, yet the next sync still applies the full manifest from Git and can overwrite the field, which looks exactly like a revert loop with a clean diff. Setting the sync option `RespectIgnoreDifferences=true` makes the sync honor the rules, but the documentation says it is effective only for resources that already exist, so a first create still applies every field ([[findings/argo-cd-ignoredifferences-only-affects-the-diff-unless-respectignoredifferences-is-set-and-then-only-for-resources-that-already-exist]], [[comparisons/exemption-and-ignore-controls-across-tools]]). Neither tool documents an observe-only mode in the pages the wiki read, though that is a negative from the pages read and not a statement from the projects.

Secrets are the other writer problem that GitOps meets early, because a repository is a poor place for plaintext. The two projects take opposite stances. Flux decrypts inside the kustomize controller and supports SOPS as its only encryption provider, with the requirement that `metadata`, `kind` and `apiVersion` stay in plaintext so the controller can read the object before decrypting it ([[findings/flux-kustomize-controller-decrypts-only-sops-and-requires-metadata-kind-and-apiversion-to-stay-in-plaintext]]). Argo CD's secret-management page strongly recommends the opposite design, in which an operator on the destination cluster (Sealed Secrets, External Secrets Operator, the Secrets Store CSI Driver or Vault Secrets Operator) populates the secret and Git never holds the value. It cautions against plugins that inject secrets while rendering manifests, because Argo CD stores generated manifests in plaintext in its Redis cache, secret updates become coupled to syncs, and the approach conflicts with the rendered-manifests pattern. The page is silent on SOPS and ksops, which the wiki records as unverified and not as a stated position, and no failure modes for either approach were collected ([[findings/argo-cd-recommends-destination-cluster-secret-operators-and-warns-that-generation-plugins-cache-plaintext-manifests-in-redis]], [[decisions/supply-gitops-secrets-from-a-destination-cluster-operator-a-generation-plugin-or-controller-side-sops]]).

Identity is the last piece of the apply step. Unless the platform team locks it down, a Kustomization applies with the controller's own identity, which is powerful. The reference multi-tenancy repository, described in [[examples/flux-multi-tenancy-repository-isolates-tenants-with-service-account-impersonation]], starts the controllers with `--no-cross-namespace-refs=true`, `--no-remote-bases=true` and `--default-service-account=default`. A Kustomization then reconciles as a ServiceAccount in the tenant's namespace, and ordinary Kubernetes RBAC decides what that tenant's repository may create. A manifest that tries to create a ClusterRole is rejected by the API server. Without those flags the trade-off is stated bluntly in [[findings/without-lockdown-flags-a-flux-kustomization-applies-with-the-controllers-own-identity]].

At this point the Deployment's new image tag is in the API server. The Deployment controller, a built-in reconcile loop, creates a new ReplicaSet, which creates pods. Notice that Flux did not roll anything out. It declared intent, and a chain of other controllers carried it forward through owner references. That handoff, intent written once and realized by several loops, is the first architectural principle we will name later.

## 3. Continuing the trace: composite, composition function and managed resources reaching the cloud API

Suppose the same commit also adds a request for a database. The repository does not contain a cloud-specific resource. It contains a small custom object that the platform team designed, for example a composite resource of a kind the platform team calls a PostgreSQL instance. This is the layer where the platform team's opinions live.

In Crossplane, which the wiki treats in depth, the schema of that small API is declared by a CompositeResourceDefinition, which becomes a CRD. A Composition says how an instance of that API becomes lower-level objects. In current Crossplane, a Composition is a pipeline of composition functions. A function is installed as a package and runs as a pod. On each reconcile, Crossplane calls the steps in order over gRPC, giving each the composite's observed state and the desired state accumulated so far, and each function returns what should exist ([[concepts/composition]]). The wiki records a hazard here that every author should memorize: a function that omits a resource from its desired state causes that resource to be deleted ([[findings/a-composition-function-that-omits-a-resource-from-its-desired-state-deletes-it]]).

Two pieces of function history help when you read older tutorials and posts. The name comes from the KRM Functions Specification (KRM, the Kubernetes Resource Model, is the convention that every object is a structured document with `apiVersion`, `kind`, `metadata`, `spec` and `status`). That specification is a client-side standard used by tools such as kpt and Kustomize: a function must be a container that reads a `ResourceList` document on standard input, writes one on standard output and exits non-zero on failure, and the spec is explicitly decoupled from the cluster. kpt and Kustomize can run functions without containers only through opt-in exec extensions that both projects' documentation discourages ([[findings/the-krm-functions-spec-requires-a-container-with-a-resourcelist-on-stdin-and-stdout-and-a-non-zero-exit-on-failure]], [[findings/kpt-and-kustomize-run-functions-without-containers-only-through-opt-in-exec-extensions-that-both-docs-discourage]]). Crossplane borrowed the idea and the name but speaks a different contract, a gRPC `RunFunction` call, so the two are not interchangeable ([[findings/crossplane-functions-speak-a-grpc-runfunction-contract-that-differs-from-the-krm-resourcelist-over-stdio]]). Crossplane's own runner also changed. In the alpha of v1.11.0 (2023-01-31) functions were run-to-completion containers started by an `xfn` sidecar in the Crossplane pod. Version v1.14.0 (2023-11-01) shipped beta functions as long-running gRPC servers that the package manager deploys as ordinary Deployments behind a headless Service, and it broke compatibility with the alpha functions. Functions reached v1 in v1.17.0 (2024-08-29) ([[findings/crossplane-moved-composition-functions-from-an-xfn-sidecar-in-v1-11-to-package-manager-deployments-in-v1-14]]). The second piece concerns pinning. Pinning a composite to a Composition revision with the `Manual` update policy freezes the pipeline definition but not the function code behind a `functionRef` step, because every such step follows the active revision of the Function package, so upgrading a Function reaches pinned composites as well. Only an alpha feature (`--enable-pipeline-oci-references`) that references a function by digest keeps old and new revisions running side by side ([[findings/upgrading-a-crossplane-function-changes-every-composition-revision-that-uses-functionref-including-manual-pins]]).

The composite spec carries operational controls as well as user-facing fields. It selects a Composition with `compositionRef` or `compositionSelector`, can pin a composition revision, can be paused with the `crossplane.io/paused` annotation, and can be forced to reconcile with `crossplane.io/reconcile-requested-at` ([[examples/crossplane-xr-spec-pins-composition-and-status-reports-synced-and-ready]]). Version history matters: in Crossplane v1 a namespaced claim fronted a cluster-scoped composite, while in v2 the composite is namespaced and claims are gone for new-style definitions. The wiki flags that older tutorials describing claims and patch-and-transform may no longer match current behavior (see [[entities/crossplane]]).

The functions produce managed resources. A managed resource is a Kubernetes object that represents exactly one external thing, and the Crossplane documentation calls the thing in the cloud the external resource. It has `spec.forProvider`, which is the authoritative desired state, `status.atProvider`, which is what the provider last observed, and an external-name annotation that ties the object to the cloud identifier. A provider controller then runs a Connect, Observe, Create, Update, Delete cycle against the cloud API ([[concepts/managed-resource]], [[concepts/provider]]).

This is where idempotency stops being a theoretical virtue. Creating a cloud resource is not naturally idempotent. If a controller calls a create API and crashes before it records the returned identifier, the next reconcile cannot tell whether the resource exists, and a blind retry could leak the first one. [[concepts/idempotency]] lists four answers that the tools use: deterministic names (Config Connector acquires a same-named resource, ACK adopts by identifier), a persisted external identity (Crossplane's external-name annotation), recording intent before acting (Crossplane writes create-pending annotations and halts for a human if the outcome is unknown), and a server-side client token that lets the cloud recognize a retried request. Two more tools add mechanisms worth knowing. kro records the resources it is about to create in `status.managedResources` before it applies them, so if the controller restarts between applying a child and recording the result, the next reconcile still knows the child exists, and it applies with server-side apply and no force, so a clash with another writer is rejected as a conflict instead of overwriting ([[findings/kro-records-the-resources-it-is-about-to-create-in-status-before-applying-them-and-applies-without-force]]). That protects Kubernetes children and not an external cloud call, and the pages the wiki read give no naming rule for children, so names are deterministic only as far as the graph author templates them. The comparison with Crossplane's create-pending annotation is this wiki's reading and no source makes it. Cluster API takes a different approach, which is guidance for provider authors and not an algorithm: its best-practices page says not to use a derived infrastructure name as the sole lookup key, and asks for provider-owned tags or labels, plus a deterministic name shortening that keeps a readable prefix and adds a hash. It states no recovery algorithm for a create whose response was lost, so how a given infrastructure provider recovers is left to that provider ([[findings/cluster-api-tells-providers-not-to-use-a-derived-name-as-the-only-lookup-key-and-states-no-lost-create-algorithm]]). Which of these is safest at scale is still open in the wiki.

The delete verb needs the same care on this side, and we will return to it in section 5. For now note one more arrow in the trace. The GitOps agent reconciles Git into the Kubernetes API, and the Crossplane controllers reconcile the API into reality. That is the two-loop structure described in [[findings/two-reconcile-loops-hide-status-and-drift-at-two-layers]]. A green sync in the GitOps agent says only that the custom resource matches Git. It does not say the database exists, and drift in a composed resource may be corrected by the lower loop without the GitOps agent ever seeing a difference.

## 4. Status flowing back: conditions, observedGeneration, readiness and health rollups

Everything so far flowed downward from intent to reality. A platform is only usable if the answer flows back up, and the vehicle is status. The spec-status split from Part 2 reserves `spec` for the user and `status` for the controller, and the standard way to say something useful in status is the condition.

A condition is one entry in `.status.conditions`. It has a `type` such as `Ready`, a `status` of `True`, `False` or `Unknown`, a machine-readable `reason`, a human-readable `message`, a `lastTransitionTime` and an optional `observedGeneration`. Here is how a Flux Kustomization might look partway through a rollout, again as an illustration of the documented fields.

```yaml
status:
  observedGeneration: 7
  conditions:
    - type: Ready
      status: "False"
      reason: DependencyNotReady
      message: dependency 'team-a/infrastructure' is not ready
      observedGeneration: 7
    - type: Reconciling
      status: "True"
      reason: Progressing
      observedGeneration: 7
```

The most important field to read is `observedGeneration`. The API server increments `metadata.generation` whenever the spec changes, and a controller copies the generation it has processed into status. If `generation` is greater than `observedGeneration`, the status describes an older spec and should not be trusted. [[concepts/conditions]] makes the point that under the "abnormal-true" polarity that kstatus describes (kstatus is a library from the Kubernetes SIGs `cli-utils` project that computes whether an object is ready by reading standard status fields such as conditions and `observedGeneration`, so tools can judge readiness without knowing each kind), the absence of problem conditions looks healthy, so a stopped controller looks identical to a healthy one unless you compare generations ([[findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy]]). The sources agree that omitting `observedGeneration` is the most common mistake ([[findings/missing-observedgeneration-hides-stale-status]]).

It helps to know exactly how kstatus reads these fields, because a great deal of GitOps tooling inherits its behavior. Reading the library's source, it evaluates an object in a fixed order. It first checks for a deletion timestamp, which reads as Terminating. It then compares `metadata.generation` with the top-level `status.observedGeneration`, and a mismatch reads as in progress. Next it scans the conditions in array order, where `Reconciling=True` means in progress and `Stalled=True` means failed, and the first match wins. Only then does it apply rules for built-in kinds and, for other kinds, fall back to `Ready`, where `True` reads as current and both `False` and `Unknown` read as in progress. Two consequences follow. A `Ready=False` condition on its own never reads as failed, because the library cannot tell a slow object from a doomed one. And a kind with no `Ready` condition at all is assumed to be always reconciled, which is the mechanism behind the premature-readiness problem described below ([[findings/kstatus-checks-deletion-then-generation-then-reconciling-and-stalled-then-ready-so-a-stale-top-level-observedgeneration-overrides-ready-true]], [[findings/kstatus-treats-an-unknown-kind-without-a-ready-condition-as-always-reconciled]]). kstatus also reads only the top-level `observedGeneration`, because its condition struct has no per-condition field, so a per-condition value written under the newer `metav1.Condition` convention is never consulted by it ([[findings/kstatus-reads-only-the-top-level-observedgeneration-because-its-condition-struct-has-no-per-condition-field]]). Which polarity condition authors should choose is itself unsettled: kstatus favors the abnormal-true style, while the Kubernetes API conventions recommended abnormal-true, reversed to positive in February 2020, and since June 2020 say neither can be recommended as a general rule ([[findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions]]).

Flux gives its own objects a clear reading guide, summarized in [[examples/flux-helmrelease-status-records-attempts-and-health]]. `Ready` is the headline, `Reconciling=True` is normal progress, `Stalled` means the release will not advance without a change, and a chain of `DependencyNotReady` conditions points at an upstream problem. The status never restates what the user wanted; it records what happened to that intent, including the last attempted revision and release action. The wiki adds a trap: a suspended resource keeps its last condition and can look healthy.

Crossplane splits the idea differently, and understanding the split is worth the effort. A managed resource reports `Synced`, which says whether the last reconcile succeeded, and `Ready`, which says the external resource is usable. A composite reports `Ready` only when the function pipeline says every composed resource is ready. While a cloud provisions a database, a user sees `Synced=True` and `Ready=False`, which means the controller is working and the thing is not usable yet ([[examples/crossplane-database-claim-reports-synced-and-ready]]). The platform's two failure stories are the mirror images. `Synced=False` with `Ready=True` is a silent failure: the thing exists and apps keep running, but Crossplane can no longer manage it, so drift is no longer corrected ([[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]]). And a summary condition can stay true while long work runs. In one reported case, an AWS MSK cluster update that took over an hour left `Synced=True` the whole time, and only an `AsyncOperation` condition said `Ongoing` ([[examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update]]). A later check found no fix: the provider-aws issue about this behavior was closed as stale, and the shared source of Upjet (the code generator and shared runtime that builds Crossplane providers from Terraform providers) and crossplane-runtime on its main branch still reports a successful reconcile while the asynchronous operation runs. The wiki did not read the body of one open pull request that might change this, so treat the behavior as current but not guaranteed to stay that way.

Other stacks use different vocabularies for the same job, compared in [[comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api]]. ACK adds `ACK.ResourceSynced`, `ACK.Terminal` and `ACK.Recoverable` and keeps `Ready` as a roll-up. Config Connector uses a single `Ready` condition whose reasons move through `Updating`, `UpToDate` and, on failure, `UpdateFailed`. The spelling matters, because Config Connector's design document proposes `UpdateFailure`, while the code at release v1.162.0 (2026-11-23) ships `UpdateFailed`, and Argo CD's own health script for these resources matches the shipped name. The same design document also proposes a failure message that names the first failing field path and a reason that carries a long-running operation ID, and a search of the code found neither, so a consumer should match on the shipped reasons and not on the design text. Because `Ready=False` covers both an update in flight and an update that failed, the reason is the only way to tell them apart ([[findings/config-connector-shipped-updatefailed-with-a-single-ready-condition-and-the-first-field-path-message-and-operation-id-reason-are-not-in-code]]). kro lets the author of a ResourceGraphDefinition (kro's single object that declares both the new API's schema and the graph of resources behind it) define instance conditions with CEL, the Common Expression Language, a small expression syntax that Kubernetes and its ecosystem use to write conditions over an object's fields. Cluster API moved to the standard condition type and split `Available` from `Ready`. KEP-1623 produced the shared `metav1.Condition` type, but adoption is voluntary, so older APIs keep their own forms.

Why does this vocabulary matter so much to a platform? Because conditions are what ordering depends on. In Flux, a Kustomization marks itself Ready only after health checks pass, and that unblocks the Kustomizations that `dependsOn` it. Flux judges compatible custom resources with kstatus and others with CEL health expressions, which are short expressions the user writes to say what "healthy" means for a kind that does not follow the conventions. Argo CD aggregates the worst health among an application's immediate children and needs Lua checks for custom kinds, meaning small scripts in the Lua language that the user supplies to teach Argo CD what ready means for that kind ([[comparisons/health-and-readiness-models-across-tools]]). When a provider's conditions do not follow the convention, the rollup lies. The best-documented case is Cluster API: an object that had `observedGeneration` set but no conditions yet could look ready to kstatus, so Flux might start dependents too early ([[findings/premature-readiness-in-kstatus-based-tools]], [[entities/cluster-api]]). The proposed fix was closed as not planned, because Cluster API is moving from `Ready` to `Available` and Flux added CEL-based custom health checks instead. Likewise, Crossplane's guide for running resources under Argo CD prescribes custom Lua health checks, since a generic agent has no idea what "ready" means for a custom kind ([[findings/generic-gitops-agents-cannot-judge-custom-resource-health]]).

The 2026-11-26 coverage pass narrowed that last claim, because the two agents diverge here. Reading the Argo CD v3.6.3 source tree, the project now ships built-in Lua scripts for whole provider groups: `cnrm.cloud.google.com` (Config Connector), `services.k8s.aws` (ACK), `crossplane.io`, `upbound.io`, `kro.run`, and five `cluster.x-k8s.io` kinds. The scripts show exactly how each condition maps to a health state. The ACK script treats `ACK.Terminal=True` as Degraded, `Ready=False` as Progressing and `Ready=True` as Healthy. The Config Connector script returns Progressing while `observedGeneration` is stale, Healthy on the reason `UpToDate`, and Degraded on `UpdateFailed`. The Crossplane script marks `Synced=False` Degraded and treats a list of kinds that never carry conditions as Healthy, so they do not sit at Progressing forever. The cost of matching a whole group by wildcard is that a script that mishandles one kind blocks sync waves: Argo CD advances a wave only when the current one is synced and healthy, so an unhealthy provider object in an early wave stops everything after it ([[findings/argo-cd-ships-built-in-lua-health-checks-for-config-connector-ack-crossplane-upbound-kro-and-cluster-api-kinds-and-an-unhealthy-provider-object-blocks-later-sync-waves]]). Flux has no per-provider logic at all. A Kustomization's `healthChecks` accept built-in kinds, Flux kinds and custom resources that are compatible with kstatus, and for the rest the author supplies CEL `healthCheckExprs`, so a provider's own `Ready` condition reaches Flux only through kstatus's generic handling. Flux's CEL cheatsheet lists a Crossplane library but, in the page as scraped, nothing for Config Connector or ACK, and the wiki did not read how kstatus treats ACK's abnormal-true `ACK.Terminal` condition, so whether a terminal ACK error reads as failed under Flux is open ([[findings/flux-judges-provider-managed-resources-through-kstatus-or-cel-health-check-expressions-and-its-cel-cheatsheet-lists-crossplane-but-not-config-connector-or-ack]]). The premature-readiness race for kinds that start without a `Ready` condition is visible in a Flux issue about Crossplane resources, where maintainers recommended an `observedGeneration` CEL expression ([[examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression]]). For a composite that wraps these objects the same logic applies one level up: Crossplane's `function-auto-ready` treats a non-built-in composed resource as ready only when it carries `Ready=True`, and kro's `readyWhen` expressions make dependents wait, so on paper both ACK and Config Connector objects satisfy them, but no worked example of Crossplane composing ACK or Config Connector objects was found, and that conclusion is the wiki's inference ([[findings/crossplane-function-auto-ready-and-kro-readywhen-gate-on-the-provider-ready-condition-and-no-worked-example-of-crossplane-composing-ack-or-config-connector-was-found]]).

The lesson of this section is that a rolled-up status is only as honest as its definition of ready. The platform author chooses what the composite promises, and the platform is only trustworthy if that promise is true.

## 5. Deletion trace: prune, finalizers, propagation modes and ordered teardown

Creation is the easy half. Deletion is where platforms lose data and money, so we trace it with equal care.

Start with the commit that removes the database request from Git. With `prune: true`, Flux deletes objects that were applied earlier but are missing from the current source, using the inventory recorded in `.status.inventory` ([[examples/gitops-tools-garbage-collect-through-inventory-and-finalizers-not-owner-references]]). Notice that this is not Kubernetes garbage collection. Flux and Argo CD apply objects they do not own through owner references, so each keeps its own record of what it applied. An object can opt out with the annotation `kustomize.toolkit.fluxcd.io/prune: disabled`. The wiki's warning in [[findings/unintended-deletion-through-prune]] is that the boundary of "the desired configuration" is easy to misjudge, and a level-based loop deletes whatever it no longer sees in desired state. Argo CD ships with prune off and an allow-empty guard so that an empty source cannot prune everything; Flux exposes explicit switches ([[comparisons/flux-versus-argo-cd-drift-and-prune-defaults]]). That table is assembled from separate documentation pages and is not a head-to-head test.

The delete now reaches the composite, and this is where finalizers enter. When a client deletes an object that carries finalizers, the API server does not remove it. It sets `metadata.deletionTimestamp`, returns HTTP 202, and leaves the object visible as Terminating. The controller that owns each finalizer sees the timestamp, performs cleanup, and removes its own entry; when the list is empty, the object is deleted ([[concepts/finalizers]]). Here is the pattern in an object, illustrative of a managed resource under deletion.

```yaml
metadata:
  name: orders-db
  deletionTimestamp: "2026-11-25T10:15:00Z"
  finalizers:
    - example.com/external-cleanup
```

The finalizer line is the promise that the cloud database will be removed before the Kubernetes record disappears. The API server enforces rules around that promise: after the deletion timestamp is set, nobody can add a new finalizer, and the only permitted edit is removal. Custom finalizer names must be qualified with a domain. A well-written controller adds its finalizer on the first pass, before creating anything outside, and its cleanup must be idempotent and treat an already-deleted external resource as success.

The three deletion mechanisms divide the work. Owner references handle in-cluster, same-namespace cleanup. Finalizers handle external resources, cross-namespace cleanup and ordered shutdown. Propagation modes decide timing ([[comparisons/background-foreground-and-orphan-propagation-modes]]): background, the default, removes the owner at once and cleans dependents later; foreground puts a finalizer on the owner and waits for dependents that carry `blockOwnerDeletion=true`; orphan leaves the dependents behind.

Ordering is the hard part, because the default is no ordering at all. Crossplane composed resources carry owner references to their composite, and under the default Background policy the garbage collector marks all children deleted at once. [[examples/crossplane-foreground-and-pipeline-deletion-policies-order-composed-resource-teardown]] describes the options: `Foreground` keeps the parent until the children are gone, and `Pipeline` lets a function remove resources from desired state step by step. A Usage object can additionally block deletion of a used resource, such as a subnet, until its users are gone ([[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]]). The Crossplane deletion policy is alpha, and the wiki records an interaction between tools that is easy to miss: Argo CD deletes with foreground propagation by default, and in that case Crossplane ignores the composite deletion policy and emits a warning event, so the ordered-teardown guarantee depends on settings in two tools ([[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]]).

kro takes a different route. It keeps an instance finalizer until every managed resource is gone, finds them through a persisted inventory, and deletes in reverse dependency order in waves, each fully gone before the next begins ([[examples/kro-deletes-instance-resources-in-reverse-dependency-waves]]). The wiki contrasts this with a Crossplane gap: a credentials secret without its own finalizer can vanish before managed resources finish cleanup ([[findings/a-credentials-secret-without-a-finalizer-can-vanish-before-managed-resources-finish-cleanup]]).

The tools also answer a different question, which is whether deleting the Kubernetes object should delete the real thing. Crossplane, ACK and Config Connector default to deleting the external resource and offer an opt-out (Orphan, retain, abandon), and the details of each opt-out decide whether it protects you under a GitOps agent. ACK resolves its deletion policy from the resource annotation `services.k8s.aws/deletion-policy` first, then the namespace annotation, then the controller-wide default, and the first match wins. A controller-wide `retain` is therefore the weakest layer: any chart or manifest that stamps `delete` on each resource overrides it. That is the account in ACK issue 3153 (opened 2026-11-09, iam-controller v1.11.3), whose reporter says an Argo CD prune, a Flux Kustomization prune and a helm-controller upgrade each led to AWS deletion, and that a controller-wide retain did not help because every chart-rendered custom resource carried `delete`. The same reporter's issue 3154 says the namespace annotation is ignored in single-namespace installs. Both are single-reporter claims, open when read, with no maintainer confirmation, and the reporter's own reproductions ran on a local kind cluster against a mock AWS service, so treat them as strong warnings and not as audited incidents ([[findings/ack-deletion-policy-resolves-from-the-resource-then-the-namespace-then-the-controller-default-and-one-reporter-says-chart-stamped-delete-defeats-a-controller-wide-retain]], [[examples/ack-issue-3153-pruning-a-custom-resource-from-git-deletes-the-aws-resource-irreversibly]], [[findings/pruning-an-ack-custom-resource-deletes-the-aws-resource-and-the-namespace-retain-annotation-is-ignored-in-single-namespace-installs]]). Config Connector's switch is the annotation `cnrm.cloud.google.com/deletion-policy: abandon`, and in source only that one value changes the delete path; any other value leaves the default delete in place. It must be present before the delete happens, and an open report says abandon does not release some stuck resources ([[findings/config-connector-deletion-policy-has-two-source-values-and-only-abandon-changes-the-delete-path-and-the-terraform-based-controller-path-is-unverified]]). The agents have their own per-object opt-outs, which live in the manifests that GitOps manages: Flux's annotation `kustomize.toolkit.fluxcd.io/prune: disabled` and Argo CD's `Prune=false` or `Prune=confirm` sync options, plus whole-group protections such as the Flux Kustomization `deletionPolicy: Orphan`, Argo CD's `Delete=false`, and `preserveResourcesOnDeletion` on an ApplicationSet. Provider-side retention survives any client that deletes the object, including kubectl, but a retained cloud resource keeps costing money, while agent-side opt-outs protect only against that agent. The wiki records the choice without a recommendation, and it found no test of Argo CD's `Prune=false` against ACK finalizers ([[decisions/protect-a-provider-managed-object-from-gitops-prune-with-a-provider-retain-policy-or-an-agent-side-prune-opt-out]]). Argo CD cascades an Application delete only if the Application carries a cascade finalizer, and it recognizes three spellings: the bare `resources-finalizer.argocd.argoproj.io`, the explicit `resources-finalizer.argocd.argoproj.io/foreground` and `resources-finalizer.argocd.argoproj.io/background`. The documentation says the default cascading delete is foreground, and in the code the wiki read the controller chooses background propagation only for the exact `/background` spelling, so the bare name and the `/foreground` name behave alike. Two further Argo CD finalizers, `pre-delete-finalizer.argocd.argoproj.io` and `post-delete-finalizer.argocd.argoproj.io`, are unrelated to cascading and only track the execution of PreDelete and PostDelete hooks. A non-cascading delete removes the finalizer or never adds it: `argocd app delete APPNAME --cascade=false`, patching `finalizers` to null before a `kubectl delete`, or the Non-Cascading (Orphan) choice in the UI, and `preserveResourcesOnDeletion` on an ApplicationSet stops the finalizer being added in the first place. Do not confuse these with the `PrunePropagationPolicy` sync option, which governs pruning during a sync and not how an Application delete is propagated ([[findings/argo-cd-applications-use-three-cascade-finalizer-names-and-a-non-cascading-delete-removes-the-finalizer]]).

Flux has `deletionPolicy` with MirrorPrune (the default), Delete, WaitForTermination and Orphan. The Kustomization finalizer is named `finalizers.fluxcd.io`, and the controller adds it before any other work so that a deletion cannot race its registration. With WaitForTermination the controller polls every two seconds for the deleted objects to terminate, which covers the finalizers their children carry, but only up to the Kustomization's own `.spec.timeout`. If that wait fails, Flux logs an error, emits an event and removes its finalizer anyway, so a stuck child finalizer does not hold the Kustomization forever; the children are then left to their own finalizers. The wiki read only the v1 API type and the controller on the main branch, not the older beta versions ([[findings/flux-kustomization-uses-finalizers-fluxcd-io-and-removes-it-even-when-waitfortermination-times-out]]).

Other tools name theirs differently, and none of the three projects below explains the choice in its documentation, so the names come from code. ACK renders `finalizers.<apiGroup>/<Kind>` per generated controller and removes it only after the AWS resource is cleaned up. Config Connector uses `cnrm.cloud.google.com/finalizer` plus a second `cnrm.cloud.google.com/deletion-defender`, and when a resource's CRD is being uninstalled it removes both and sets the resource to abandon, so uninstalling a CRD keeps the Google Cloud resources. kro uses `kro.run/finalizer` on instances and removes it only when no deletion candidates remain ([[findings/ack-config-connector-and-kro-each-name-their-finalizers-differently-and-remove-them-only-after-cleanup]], [[findings/config-connector-has-a-second-deletion-defender-finalizer-and-removes-both-finalizers-with-an-abandon-setting-when-its-crd-is-uninstalled]]). Cluster API orders teardown with a drain, volume detachment, hooks and then infrastructure deletion. These are compared in [[comparisons/deletion-policies-across-gitops-and-provider-tools]]; the decision itself is framed in [[decisions/delete-or-retain-the-external-resource-when-the-kubernetes-object-is-deleted]]. Cluster API deliberately chose annotation hooks over finalizers for blocking machine deletion, because a misbehaving controller could remove a finalizer ([[findings/cluster-api-chose-annotation-hooks-over-finalizers-for-machine-deletion-because-a-misbehaving-controller-could-remove-finalizers]]). Two details are still not settled: whether Argo CD's `/foreground` spelling differs from the bare name in any other code path, and the literal ACK string for a specific service controller, since only the template form was read.

The failure modes follow directly. A finalizer only works while its controller runs, so deleting the cluster first, or removing a Crossplane provider before its managed resources, strands the cloud resources, still billing ([[findings/deleting-the-cluster-first-orphans-cloud-resources-because-the-controller-is-gone]], [[findings/removing-a-crossplane-provider-before-its-managed-resources-abandons-the-cloud-resources]]). The first of those rests on a single consultancy blog and the second on Crossplane's documentation. Forcing a finalizer off to unstick an object skips the cleanup it guarded ([[decisions/remove-a-stuck-finalizer-by-force-or-repair-the-owning-controller]]). The practical rule is to uninstall controllers only after their custom resources are deleted.

The newer research pass added three dated, public reports that show these mechanisms in practice. All are issue reports from individual users, not organization-authored postmortems, and their authors are anonymous or identified only by a handle, so read them as reproductions and not as audited incidents. In ACK issue 2911, opened in June 2026, a reporter running the ACK WAFv2 controller had Argo CD prune a WebACL custom resource. The controller deleted the AWS resource but did not map the "not found" error it received on a later pass, so the custom resource sat in Terminating until someone patched the finalizer off by hand. A maintainer confirmed the cause. In this instance the manual patch was safe because the cloud resource was already gone, but the same patch would leak a billing resource if the cloud object still existed ([[examples/an-argo-cd-prune-left-an-ack-wafv2-webacl-terminating-on-its-finalizer-after-the-aws-resource-was-already-gone]]). In Config Connector issue 16444, filed on 2026-11-25 and still open a day later, a reporter describes a multi-cluster setup with leader election: objects deleted on a standby cluster stay in Terminating because the standby does not process them, and when that cluster becomes leader again it runs the stale deletion against Google Cloud, possibly after another cluster has re-created a resource of the same name. There was no maintainer response yet, so this is one reporter's account of a scenario ([[findings/config-connector-leader-election-across-clusters-can-run-a-stale-deletion-against-live-google-cloud-resources]]). Finally, ACK community issue 3177 (November 2026) contains the author's own audit, not an observed production count, claiming that in 22 controllers a lost create response either duplicates 28 resources or wedges 20 more because the name already exists. A runtime change merged on 2026-11-20 moves the status write to immediately after the create call, which narrows the window but cannot close it, because a crash between the cloud call and the write can still lose the identifier ([[findings/an-ack-audit-found-48-resources-in-22-controllers-where-a-lost-create-response-duplicates-the-resource-or-wedges-the-custom-resource]]). The wiki searched the Kubernetes finalizers page and the issues of Kubernetes, Cluster API, Crossplane and ACK and found no source that quantifies how often forced finalizer removal orphans resources, so the frequency of that mistake remains unknown and should not be stated as a number ([[findings/no-source-quantifies-how-often-forced-finalizer-removal-orphans-guarded-resources]]).

Three Argo CD reports show the same destructive path from the delivery side, and all three are anonymous reporter accounts. In Argo CD issue 6046 (2021-04-15, v1.8.1 then v1.8.7 on EKS) a reporter wiped the `argocd` namespace and reinstalled Argo CD, after which it "started deleting all the apps under it's management"; a maintainer asked whether the Application objects carried the resources finalizer, and the root cause was not confirmed ([[examples/argo-cd-issue-6046-reinstalling-argo-cd-into-a-wiped-namespace-started-deleting-every-app-it-managed]]). In issue 20440 (v2.6.6, still open with comments through 2024-11-10) one deleted ApplicationSet-generated Application removed the workloads it managed, including namespaces and Argo CD itself, and no mechanism was established ([[examples/argo-cd-issue-20440-an-applicationset-generated-application-was-deleted-with-its-namespaces-and-argo-cd-itself]]). In issue 15441 (2023-09-11) a reporter replaced an explicit Namespace manifest with the `CreateNamespace=true` sync option and found the sync deleted and recreated the namespace, which deletes everything inside it ([[examples/argo-cd-issue-15441-removing-a-namespace-manifest-under-createnamespace-deleted-and-recreated-the-namespace]], [[findings/deleting-or-recreating-an-argo-cd-parent-can-cascade-to-everything-it-managed]]). Taken together with the Skyscanner outage in section 10, they give reporter-level and one named-organization example of an accidental delete, but no named organization has published a postmortem of an accidental prune of provider-managed cloud resources.

## 6. Principles of good platform architecture, drawn from the traced lifecycle

The trace above is long, but a handful of principles recur at every step. Each is a reason the design works, and each has a documented way of failing when ignored.

The first principle is that intent is written once, declaratively, and realized by many small loops. Flux declares a Deployment and lets the built-in controllers produce pods. The platform declares a composite and lets functions and providers produce cloud resources. Each controller owns one aspect, which is the design the Kubernetes documentation favors. This works because the loops are level-triggered and idempotent, so a crash, a missed event or a duplicate run changes nothing about the end state. When the principle is violated, as with logic keyed to specific events, resources get stuck ([[findings/event-specific-logic-in-reconcilers]]).

The second principle is that events are hints and state is truth. Webhooks, watches and notification receivers lower latency, but the interval and the full reread of state are the safety net. Flux's notification receiver speeds a commit along, while the poll interval guarantees it eventually arrives. See [[decisions/events-as-hints-state-as-truth]]. The consequence is that detection latency equals the interval, so you choose intervals per resource class ([[findings/drift-detection-latency-is-the-interval]]).

The third principle is that every writer must be identified, and shared objects must have explicit ownership. Server-side apply makes ownership visible and turns a clash into a conflict. A platform that lets Flux, an autoscaler and cert-manager touch one object without an ownership decision will fight indefinitely. The wiki's open question is which conflict policy is the best default, since forcing hides real disagreement ([[findings/forcing-conflicts-hides-disagreements-between-writers]]).

The fourth principle is that deletion deserves as much design as creation. The delete verb is destructive for external resources, so good platforms make the outcome explicit through finalizers, deletion policies, management policies and ordering controls, and they make the default safe for the data that matters. The wiki records that Argo CD ships with destructive actions off while Flux exposes explicit switches for each; neither is "right," but both are explicit.

The fifth principle is honest status. A readiness signal is a contract with other automation. If it says ready too early, dependents start against nothing. If it stays true while work is ongoing, alerts stay silent. Good platforms set conditions on first visit (even as `Unknown`), track `observedGeneration`, separate "controller can reconcile" from "thing is usable," and teach generic agents the health meaning of custom kinds.

The sixth principle is that every loop has a budget, and the budget should be explicit. A workqueue limiter normally protects the API server, but for a provider the same queue is also the budget for someone else's API. Crossplane's `--max-reconcile-rate` was introduced because, in the issue's words, reconcile rate is a good proxy for average external API call rate ([[examples/crossplane-max-reconcile-rate-turns-reconcile-rate-into-an-api-call-budget]]). That description has aged, and it is easy to be misled by it. The v2.1.0 release notes say the flag was renamed `--max-concurrent-reconciles`, and in the v2.5.0 source it is a worker pool size with a default of 100 and the old name kept as an alias, even though the v2.5 pods guide still describes it as a rate in times per second. A pool of 100 workers is therefore a ceiling on parallel reconciles and not on calls per second, and how many calls per second it produces depends on how long each reconcile takes, so the flag no longer states a call budget on its own. The runaway guard in v2 is the circuit breaker on composites (burst 100), and providers define their own flags, which should be checked separately ([[findings/the-crossplane-v2-5-docs-describe-max-reconcile-rate-as-a-rate-but-source-treats-it-as-a-worker-pool-size-alias]]). ACK's roughly ten-hour default resync after a resource is synced makes the same trade of freshness for API cost ([[examples/ack-resync-period-tuning-for-stateful-resources]]). Self-healing also needs a brake: Cluster API's `maxUnhealthy` stops automatic remediation when too many machines look unhealthy at once ([[findings/remediation-can-amplify-an-outage]]).

The seventh principle is that blast radius should be a design decision. A control plane that manages everything concentrates authority. ACK runs one controller per AWS service with scoped IAM; a single management cluster or shared provider credential enlarges the blast radius; and whoever can create a custom resource inherits the controller's cloud rights ([[findings/blast-radius-and-privilege-centralization]]). RBAC on the platform API is the security boundary, and Flux's per-tenant impersonation is one way to apply that principle.

The eighth principle is to keep abstractions small and honest. A platform API is a contract that users depend on. The wiki cites practitioner advice, from a single blog, against mega-Compositions and against APIs that mirror a cloud's own resource names, and it records Crossplane's own cost admission: it needs a hosting cluster, Kubernetes skills and platform-team-owned abstractions ([[findings/crossplane-adoption-needs-a-hosting-cluster-kubernetes-skills-and-platform-team-owned-abstractions]]). The expressiveness question, functions versus CEL graphs, is compared in [[comparisons/helm-versus-kro-versus-crossplane-as-platform-abstraction-layers]].

The ninth principle is to stage risky automation. Drift correction, pruning and cluster-wide defaults all amplify a mistake through a loop. Grafana's 2019 outage came from a new cluster-wide default PriorityClass that a ReplicaSet kept reapplying to every recreated pod, preempting every production ingester and causing about 26 minutes of outage, with no data lost ([[findings/a-new-cluster-wide-default-must-wait-until-existing-workloads-carry-explicit-values]]). The pattern is to add the explicit value first and change the default second, and to adopt automatic correction in stages ([[decisions/staged-adoption-of-automated-drift-correction]]).

## 7. Scale: informer memory, workqueue rates, API priority and fairness, etcd limits

Scale in this world is a set of separate limits, and the practical method the sources describe is to find which resource saturates first and then either raise it or split the work ([[concepts/scale-and-sharding]]).

At the cluster level, SIG Scalability publishes a tested envelope of about 5,000 nodes, 150,000 pods, 10,000 namespaces, 10,000 services and a 1.5 MB object size cap, along with 150,000 non-event objects per type and about 3 GB total. The page says explicitly that these thresholds are not hard limits and that crossing one results in degraded performance. A recheck against the raw page also found that the thresholds are scoped to built-in resource types and tied to a particular test setup. The envelope is not a cube, because the dimensions interact. CRD count is not one of the tested dimensions, which is exactly where platform tools fell in. Operators of many clusters give tighter advice: Gardener says most clusters should stay below about 500 nodes, that etcd has a practical space limit of 8 GB with a healthy database under 3 GB, that object counts should not exceed about 100,000 for most use cases, and that webhooks and object counts need control (its page is undated, and its node advice assumes machines of at least 8 vCPU and 32 GB) ([[examples/gardener-advises-keeping-most-clusters-under-about-500-nodes-and-controlling-webhooks-and-object-counts]]). The wiki does not reconcile the order-of-magnitude gap between the 5,000 and 500 figures, because they answer different questions: a tested maximum versus working advice. Treat the envelope as an upper limit and operator advice as a conservative target ([[findings/tested-scalability-maximums-and-operator-advice-differ-by-an-order-of-magnitude]]).

Underneath is the shared store. Every custom resource lives in etcd, which has a single Raft write leader, a default storage limit of 2 GiB and revision growth that needs compaction. The 8 GB figure that circulates (one secondary explainer calls it a default cap) is the etcd documentation's suggested maximum for normal environments, not the default, and the same page limits a single request to 1.5 MiB by default, which is below the kube-apiserver's own 3 MiB request body default, so the etcd limit binds first and matches the roughly 1.5 MB object cap in the SIG Scalability envelope ([[findings/etcd-limits-requests-to-1-5-mib-and-storage-to-2-gib-by-default-and-8-gib-is-a-suggested-maximum-not-the-default]]). Mitigations include moving Events to a separate etcd, alternative backends and watch-cache improvements ([[findings/etcd-scale-limits-of-the-shared-store]]). Ant Group's more-than-10,000-node cluster cut apiserver memory from roughly 400 GB to 100 GB by serving list requests from the watch cache, among other changes ([[examples/ant-group-large-cluster-tuning-of-apiserver-watch-cache-and-etcd]]). A vCluster claim of degradation around 30,000 to 40,000 objects is a vendor figure that depends on workload.

Inside a controller there are four limits, and they are worth understanding separately. First, the informer cache holds every watched object with no eviction, so memory grows with what you watch ([[findings/informer-caches-hold-every-watched-object-and-memory-grows-with-cluster-size]]). Since nothing is evicted, the only way to shrink the cache is to watch less or keep less, and controller-runtime's cache package offers several options, each with a cost its source names ([[findings/controller-runtime-narrows-its-cache-with-selectors-transforms-metadata-only-informers-and-disable-for-and-each-option-has-a-cost]]). Per-type options (`ByObject`), namespace lists and label or field selectors restrict what the list-and-watch fetches, at the cost that anything outside them is invisible to the cache, so the selector must match everything the reconciler reads. A transform rewrites each object as it is stored, and the documented `TransformStripManagedFields` can, in the project's words, lead to a significant reduction in memory, though that is a vendor statement and not a measurement; a related option asks the server to omit managed fields, and its comment warns not to enable it if you read `managedFields` from cached objects. A metadata-only informer (the builder's `OnlyMetadata`) caches just the object's metadata, so the full object is unavailable from the cache. `DisableFor` sends every read of a type straight to the API server as a live lookup, which saves cache memory and costs an API call per read, and unstructured reads already bypass the cache unless asked otherwise. Skipping the deep copy on cache reads saves CPU but lets a careless caller mutate a shared cached object, and `ReaderFailOnMissingInformer` turns a read of an unplanned type into an error instead of silently starting a new informer. No source gave memory measurements for any of these, so the size of the savings is unquantified. Second, the workqueue never processes one key concurrently, so throughput is set by worker count and reconcile duration and not by the object count; a slow reconcile hogs a worker and deepens the queue. Third, the client-side rate limiter, set by QPS and burst, throttles requests before they leave the process. Fourth, leader election means only one replica reconciles, so extra replicas add failover and not capacity ([[findings/extra-replicas-of-a-flux-controller-add-failover-not-capacity]]).

Two throttling layers are easy to confuse. Client-side throttling delays requests inside the process. Server-side API Priority and Fairness classifies requests by FlowSchema into priority levels with their own concurrency shares, queues with shuffle sharding, and rejects with HTTP 429 when a level saturates, so one badly behaved controller need not starve others. The design is more approximate than that summary suggests. The KEP-1040 README itself calls its fair queuing dissatisfying in two ways: it allocates seats equally among non-empty queues and not by max-min fairness, so it sometimes pretends a queue uses more seats than it can, and it runs one request per queue at a time in its virtual-time model. A LIST costs more than one seat, with a width that grows with the number of objects returned (the README estimates memory cost dominates only around 400,000 objects, and its text still carries a to-do about how the object count is estimated). The README also names a failure mode in which a client that requests big responses and does not finish reading them within a minute can hold hand size times 10 seats for a long time, so one slow reader can still tie up capacity that other flows need ([[findings/apf-fair-queuing-allocates-seats-equally-and-a-slow-reader-can-hold-hand-size-times-ten-seats]]). Upbound's log line "Waited for 1.033772408s due to client-side throttling, not priority and fairness" shows why the distinction matters: raising server capacity would not have helped ([[findings/client-side-throttling-and-server-side-apf-are-separate-layers]]).

Watches have their own failure. When a resource version is too old, the server answers 410 Gone and the client must relist. If many clients lose their watch together they relist together, a storm ([[findings/an-expired-resourceversion-forces-a-relist-and-synchronized-relists-can-storm]]). Bookmarks, the server watch cache and jittered backoff are the mitigations. The default workqueue limiter combines two ideas, and it helps to see them in plain terms. Exponential backoff means that each time the same object fails, the wait before retrying it roughly doubles, so a persistently broken object backs off quickly instead of hammering the API server. A token bucket works like a jar that refills at a steady rate: every reconcile must take a token, so the queue can burst briefly when the jar is full but cannot sustain more than the refill rate over time. Together they keep one failing object and one busy burst from crowding out everything else. The values were checked against controller-runtime v0.25.3 (published 2026-11-16): the per-object backoff starts at 5 ms and caps at 1000 s. The token bucket of 10 per second with room for 100 belongs to client-go's default limiter, and controller-runtime does not apply it when its priority queue is on, which is the default. With the priority queue on, only the per-object backoff applies, so the overall bucket is present only if you turn the priority queue off. The bucket figures were read from client-go's main branch and not a pinned release.

The failure that ties this together is described in [[examples/an-openai-outage-shows-many-api-clients-can-overload-the-control-plane]], and the wiki has now read OpenAI's own postmortem for it, not just a commentary. On 2024-12-11 OpenAI merged a change at 2:23 pm Pacific, rolled it out to its clusters between 2:51 and 3:20 pm, and deployed a new telemetry service at 3:12 pm. The postmortem says the service's configuration caused every node in each cluster to run resource-intensive Kubernetes API operations whose cost scaled with the size of the cluster, and the API servers were overwhelmed in most large clusters. All services were significantly degraded from 3:16 to 7:38 pm, with the first cluster recovering at 4:36 pm. The data plane could mostly run on its own, but DNS-based service discovery relied on the control plane, so cached records hid the failure for about twenty minutes and then, as they expired, services began failing and the expiring caches added load ([[findings/dns-caching-hid-the-control-plane-failure-for-about-twenty-minutes-before-expiring-records-added-load]]). Remediation was slow because removing the telemetry service required control-plane access that the overload had taken away, so teams scaled down clusters, blocked network access to the admin APIs and scaled up the API servers in parallel. Staging did not catch it because the pre-rollout checks looked at CPU and memory and not at API server load. All of these figures are self-reported by OpenAI. One earlier detail is withdrawn: the primary text does not say the calls were list or watch calls or that the service was a DaemonSet, so any such claim is this wiki's inference, and the link to informers is indirect. Use the incident as an illustration that [[findings/control-plane-overload-blocks-the-remediation-that-would-fix-it]]. Neon's postmortem of 2025-05-21 is a second, different example from a platform built on Kubernetes: a changed query plan made a control-plane database query 10 to 100 times slower, idle compute pods were not suspended, the count rose to about 8,000 against 6,000 planned, and pods exhausted IP addresses in two of three subnets, with 5.5 hours of impact across 2025-05-16 and 2025-05-19 ([[examples/neon-s-may-2025-delayed-start-incidents-exhausted-subnet-ips-after-a-slow-control-plane-database-query]]). A related, widely known principle follows: keep the means of repair off the path that can fail. Fail-closed admission webhooks are the same trap, because an unreachable backend with `failurePolicy: Fail` blocks the writes needed to repair it ([[findings/fail-closed-webhooks-can-block-the-writes-needed-to-repair-them]]); the webhook guidance is now backed by one primary postmortem, Jetstack's, described in section 10. The wiki still found no primary postmortem of a CRD deletion cascade or an etcd quota alarm, though its search tool returned empty results for many queries, so that absence is weak evidence ([[findings/no-primary-postmortem-was-found-for-a-crd-deletion-cascade-or-an-etcd-quota-alarm]]).

Finally, CRD count is itself a scale dimension. Upbound's test of a control plane of about 2,000 managed resources found client discovery needing around 300 HTTP requests, server OpenAPI computation burning CPU, and memory use of a little over 4 MiB of resident memory per CRD causing out-of-memory kills on hosted control planes; fixes included lazy OpenAPI computation in Kubernetes 1.23, backported to 1.20.13, 1.21.7 and 1.22.4, and garbage-collection tuning that cut peak resident memory by about 25 percent on an idle API server with roughly 2,000 CRDs ([[examples/upbound-tested-a-multi-cloud-control-plane-of-about-2000-managed-resources-and-upstreamed-kubernetes-fixes]]). The Upbound post is dated August 2022 and self-reported. The wiki originally took these figures from model-generated digests, so it re-read the raw pages on 2026-11-26. Every quoted figure matched, and three wordings were tightened: the Upbound memory figure above, the Argo CD processor numbers in section 8, and the Crossplane memory figures in section 8, which are design targets and not measurements. The Kubernetes API Priority and Fairness page was read in full, while the KEP-1040 text was read closely only in part, so claims about the rest of that KEP remain unverified ([[findings/the-scale-dossier-relies-on-model-digests-for-most-numbers-so-limits-need-rechecking]]).

## 8. Sharding and tuning: Flux label sharding, Argo CD cluster sharding, Crossplane provider families, domain-scoped control planes

There are two levers: raise capacity vertically, or split the work along a stable key.

For Flux, the first lever is documented. Flux exposes `--concurrent` (a range of 10 to 20 is mentioned), Helm repository cache size and TTL flags, and warns that tmpfs counts against the pod's memory ([[examples/flux-controllers-expose-worker-concurrency-and-helm-cache-size-as-tuning-knobs]]). The wiki's own reading of the sources is to tune first and shard when one instance reaches its limits. The sharding page gives the only figure the wiki found, advising sharding when Flux is "managing tens of thousands of applications", and the project's own benchmark gives a reference point for a single unsharded instance: with a kustomize controller of 2 CPU and 1 GiB at concurrency 20 on a three-node kind cluster in a CI runner, 1,000 Kustomizations reconcile in 4 minutes 13 seconds using at most 297 MiB (Flux v2.10.0; the v2.9.0 table shows the same time at 223 MiB). That is a project-run benchmark on a small cluster and not a production report, and a maintainer once cited about three minutes per thousand Kustomizations in a user thread, which is in the same range ([[decisions/shard-flux-controllers-or-tune-intervals-and-concurrency-first]], [[examples/the-flux-benchmark-reconciles-1000-kustomizations-in-4-minutes-13-seconds-on-flux-v2-10-0]]). The same research found that Flux has turned off its own client-side throttling when the API server has Priority and Fairness enabled since 2022, although a custom-kubeconfig code path kept the client-side limiter until a fix closed in February 2026, and that no published incident ties Flux to API Priority and Fairness throttling ([[findings/flux-turns-off-client-side-throttling-when-apf-is-enabled-but-a-custom-kubeconfig-path-kept-it-until-2026]]). Morgan Stanley did exactly the tuning route, as we will see.

When tuning is not enough, Flux shards by label. Additional controller deployments run under unique names, for instance `source-controller-shard1`, each started with `--watch-label-selector` set to its own value of the label `sharding.fluxcd.io/key`, so it reconciles only objects with that label, while the default controllers skip labeled objects so nothing is handled twice ([[examples/flux-sharding-splits-reconciliation-across-label-selected-controller-instances]]). The sharp edge is consistency: a HelmRepository, the HelmChart generated from it, and the HelmRelease that uses the chart all need matching labels, or the pieces land on different controllers ([[findings/sharded-flux-dependents-must-carry-the-same-shard-label-as-their-parents]]). A parent Kustomization can bulk-label children, and the Flux Operator can declare shards in a `FluxInstance` spec. The labeling rule for charts is now verified: a HelmChart is generated from a HelmRelease and not written by hand, so its shard label is set through the HelmRelease's `.spec.chart.metadata.labels`, and the main controllers are told to ignore any keyed object with `--watch-label-selector=!sharding.fluxcd.io/key`. If a HelmRelease carries the key but its chart does not, a different controller ends up handling the chart than the one that needs its artifact, though the documentation does not spell out the symptom a user would see ([[findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels]]). The sharding page says the notification controller and the source-watcher do not support sharding, and its example recipe deletes the image reflector and image automation Deployments from the shard sets, so the recipe shards the source, kustomize and Helm controllers and leaves image automation to the default instance. Whether the image controllers can be sharded is not stated, so a plan that targets load from notifications or image scanning will not be relieved by adding shards ([[findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded]]). Each shard also elects its own leader, because the leader election ID is derived from the label selector, so a shard does not compete with the default instance for a lease. The one named project that automates this is Cozystack, whose `flux-shard-operator` creates Helm controller shards at roughly 100 HelmReleases per shard (a formula clamped between 1 and 16 shards, with a per-shard concurrency of 5), placing tenants greedily by HelmRelease count. Those numbers are the project's documented design intent, with no measured outcome and no independent confirmation of production use ([[examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard]]).

Argo CD shards by destination cluster. Application-controller replicas are told the replica total (`ARGOCD_CONTROLLER_REPLICAS`) and clusters are assigned with the `legacy`, `round-robin` or `consistent-hashing` algorithm, or pinned through the cluster secret. The worker counts are set with `--status-processors` and `--operation-processors` (defaults of 20 status processors and 10 operation processors, confirmed against the raw documentation, with 50 and 25 suggested for about 1,000 applications), and `GOMEMLIMIT` is set to 80 to 90 percent of the container limit ([[examples/argo-cd-application-controller-shards-clusters-and-tunes-processor-counts]]). The legacy algorithm distributes clusters by UID in a non-uniform way, so it can be uneven. The other two algorithms are still labelled experimental (Alpha) on the v3.6.3 high-availability page (released 2026-11-24), with wording unchanged since v2.14.0 ([[findings/argo-cd-legacy-sharding-can-be-uneven-and-the-other-algorithms-were-labelled-experimental]]). The default today is `legacy`. The v2.8.0, v2.14.0 and v3.0.0 documentation pages marked it as the default, while the v3.6.3 page lists all three methods without any "(default)" marker, which at first left the question open. The source settles it: `common/common.go` sets `DefaultShardingAlgorithm = LegacyShardingAlgorithm` at both v3.0.0 and v3.6.3, and the application controller's `--sharding-method` flag takes its default from that constant, a result a second reading on 2026-11-26 confirmed independently. Only the documentation changed, so a default install shows the uneven distribution described above. A CNOE blog dated 2023-11-21, which the v3.6.3 page cites, reports that the newer algorithms improve CPU utilization by a factor of 3 and cut rebalancing by a factor of 5, but those are the authors' own benchmarks and do not change the Alpha label. To pick a different algorithm, set `--sharding-method` or the `argocd-cmd-params-cm` config map yourself ([[findings/argo-cd-v3-6-3-still-defaults-to-legacy-sharding-because-the-source-says-so-even-though-the-docs-page-dropped-the-marker]]; this supersedes [[findings/the-argo-cd-v3-6-3-high-availability-page-no-longer-marks-legacy-as-the-default-sharding-method]]). Compare the two ideas in [[comparisons/flux-label-sharding-versus-argo-cd-cluster-sharding]]: Flux's key is a label on each object, which is flexible and requires discipline, while Argo CD's key is the destination cluster, which fits hub-and-spoke setups naturally.

Hub-and-spoke deserves one clarification, because "pull-based" is easy to over-read. A central Argo CD instance targets remote clusters that are registered with it, so delivery to a fleet is a push from the hub into each spoke even though every Application pulls its source from Git. A separate project, `argocd-agent` in the `argoproj-labs` organization (a Labs project, not core Argo CD), describes the inverse model in which lightweight agents reach back to a central hub, with Managed and Autonomous agent modes. Its README states no maturity level, so the wiki records its maturity as unverified. Flux can also target a remote cluster through `.spec.kubeConfig`, whose documentation recommends the secret-less `configMapRef` form, although the more common Flux layout runs a controller set in each cluster ([[findings/argo-cd-reaches-into-registered-clusters-from-a-hub-and-the-argocd-agent-pull-model-is-a-labs-project-of-unverified-maturity]], [[decisions/reach-spoke-clusters-from-a-central-argo-cd-hub-or-with-argocd-agent-pulling-from-the-spokes]]). On the Argo CD side the fleet is usually generated by an ApplicationSet, which stamps out Applications from generators, and the documentation lists limits worth knowing: the matrix generator combines only two child generators, combination generators (matrix or merge) can be nested only once, the Pull Request generator polls every 30 minutes by default and makes anonymous, lower-rate-limit requests when no token is configured, and the OCI generator polls every 3 minutes. The generator overview says there are nine generators and then lists ten, a stale count and not a missing one. The wiki found no quantified scale limit for ApplicationSets or for hub-and-spoke Argo CD, which means unverified and not nonexistent ([[findings/applicationset-generators-have-documented-limits-matrix-takes-two-children-nesting-is-once-and-pull-request-polling-defaults-to-30-minutes]]). The RollingSync strategy for staged rollout across a fleet has costs of its own. It is Beta since v3.3.0, it forces autosync off on every generated Application (which also turns off the self-heal and automated prune a team may rely on), it watches only Application health and so depends on how honest that health is, and an Application that no step selects is silently left out of the rollout ([[findings/applicationset-rollingsync-is-beta-forces-autosync-off-and-watches-only-application-health]]). Finally, a head-to-head comparison of Argo CD and Flux behavior is still assembled from each project's own documentation, because no neutral benchmark or CNCF comparison was found ([[findings/no-neutral-benchmark-or-cncf-comparison-of-argo-cd-and-flux-was-found-so-the-comparison-rests-on-each-project-s-own-documentation]]).

The same split-by-key idea appears outside GitOps. kro funnels the events for all of its instances through one shared, rate-limited queue. Because every ResourceGraphDefinition feeds the same queue, a rate limit on that queue works as a fairness device: a definition with thousands of busy instances, or one stuck in a failure loop, can only consume its share of the worker time and API calls, and cannot starve the others. The caps matter because without them a single misbehaving definition would be limited only by how fast the cluster could answer. The same backoff-and-token-bucket ideas described in section 7 apply, and a retry cap adds a final stop so that an object that never succeeds is eventually left alone instead of being retried forever ([[examples/kro-shared-queue-tunes-throughput]]). The released kro v0.10.0 (published 2026-11-10) documents the same defaults that the earlier unreleased documentation showed, so the earlier caveat no longer applies to them: a default of 20 retries before an item is dropped, a single worker, a 200 ms to 1000 s backoff range combined with a token bucket of 10 items per second and a burst of 100, client-side QPS (queries per second) of 100 with a burst of 150, and a 10-hour full resync. The v0.10.0 page adds a 30-second watch sync timeout, a collection limit of 1,000 items, and an instance requeue interval of 3 seconds that now backs off exponentially up to five minutes. The older v0.9.4 page reads as a fixed delay, so the exponential behavior looks new, though that is an inference from two pages, and the v0.9.4 rate-limiter table was not read in full. The docs also say per-definition queues may replace the shared queue in a future version, and there is no measured throughput data, only an open request for performance testing and a maintainer proposal for weighted queues ([[findings/kro-s-single-shared-queue-can-starve-resources-and-a-maintainer-proposed-weighted-queues]]). Crossplane composite load is arithmetic: composites poll every 60 seconds by default in core (Upjet-based providers poll managed resources every 10 minutes, a different layer with a different default) and each function step is a gRPC call, so 100 composites with one function step produce about 100 calls per minute, and large composites can exhaust function memory according to a third-party article whose log excerpts are labelled simulated ([[findings/function-calls-scale-with-composite-count-and-large-composites-can-exhaust-function-memory]]).

A word on how much to trust kro's scale story, because the sources disagree with each other. The kro documentation FAQ says kro "deploys a dedicated controller" for each ResourceGraphDefinition, while the tuning page and the v0.10.0 source describe one dynamic controller with one shared queue (named "dynamic-controller-queue") and one parent watch per definition. The code and the tuning page agree, so the FAQ wording is the outlier, and a reader who sizes kro as many controllers with separate queues will look for isolation that does not exist ([[findings/the-kro-docs-faq-says-a-dedicated-controller-per-rgd-while-the-tuning-page-and-source-describe-one-shared-queue]]). The scale evidence itself is thin: the wiki found no benchmark, no measured limit, no adopters file and no named production adopter. The closest primary items are an open issue proposing weighted queues (opened 2025-01-11), an open issue asking for automated performance testing (2025-07-23), and a pull request about deletion latency at large scale that was closed unmerged on 2026-08-11, so it shows no shipped fix. The tuning page warns that a resource with tens of thousands of objects can exceed the default 30-second watch sync timeout, and the roadmap items for level-based and wavefront controllers were still Draft in an April 2026 snapshot ([[findings/kro-scale-evidence-is-two-open-issues-and-a-closed-unmerged-pull-request-with-no-benchmark-and-no-named-production-adopter]]). On governance, kro is a Kubernetes SIG Cloud Provider subproject, the in-repo roadmap lags the v0.10.0 release it was meant to describe, and no source gives a promotion timeline for the alpha Graph API, so a team choosing between ResourceGraphDefinitions and Graphs should treat Graph as additive and unstable while both ride one engine ([[findings/the-kro-in-repo-roadmap-predates-the-v0-10-0-release-and-gives-no-graph-promotion-timeline]], [[decisions/build-platform-apis-on-resourcegraphdefinitions-or-track-the-alpha-graph-api]]).

For Crossplane the dominant scale problem is CRD count, and the remedy is packaging. The original provider-aws registered a CRD for every AWS service and passed 900 CRDs, which could leave the API server unresponsive for up to an hour during scale-up. Provider families split the monolith so an operator installs only the member providers for the services in use, sharing a common configuration provider ([[examples/crossplane-provider-families-let-operators-install-only-the-cloud-services-they-use]]). The design document's estimate was a typical user dropping from more than 900 CRDs to about 176, at the cost of about nine provider pods instead of two ([[findings/splitting-a-provider-into-a-family-trades-fewer-crds-for-more-pods-and-memory]]); the figures reproduced against the raw design document, which also says problems start "very approximately" above 500 CRDs, a rough threshold and not a tested limit. The memory figures in that document (about 600 MB for the Crossplane provider process and about 300 MB for each Terraform provider process) are targets the authors hoped to reach, not measurements, and the document is still marked Draft ([[findings/crossplane-provider-memory-figures-are-design-doc-targets-not-measurements]]). Crossplane v2 adds a second control: ManagedResourceActivationPolicies list exact names or prefix patterns, and only matching ManagedResourceDefinitions become served CRDs ([[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]]). Two cautions apply. First, the documentation labels activation policies and definitions alpha, although the source code lists the definition conversion under beta features, so the stage is disputed between the docs and the code. Second, a stock install does not save you anything: the default Crossplane Helm chart creates a `default` activation policy that activates every resource (`provider.defaultActivations: ["*"]`), so you must turn that default off, for example with `--set provider.defaultActivations={}`, and then list the groups you need. Activation is also one-way, so a definition that has become Active cannot be deactivated, and providers that declare the `safe-start` capability start their definitions Inactive while others start Active ([[findings/the-default-crossplane-helm-install-activates-every-managed-resource-so-activation-policies-need-the-default-turned-off]]). The Crossplane docs estimate about 3 MiB of API server memory per CRD, which is an estimate, and no with-versus-without measurement was found. Current scaling guidance is scattered across pages (a one-minute polling default with an hourly full re-check, API Priority and Fairness in place of custom client-side rate limiting since v2.1.0, a circuit breaker on composites, and a configurable concurrency setting), and the wiki found no documented numeric limits for composites or composed resources. ACK avoided the problem by shipping one controller per service from the start ([[comparisons/provider-families-versus-per-service-controllers]]), and the choice among families, filtering and lazy loading is framed in [[decisions/split-a-large-provider-into-families-or-filter-or-lazy-load-its-crds]].

Several newer pieces of Crossplane evidence explain where the cost moved after the CRD problem was attacked. Crossplane core strips the OpenAPI schemas, which are most of a CRD's size, from the CRDs it caches, excludes Secrets from its client cache, and defaults its worker pool to 100. The v2.5.0 release notes (2026-11-24) report that this change cut heap use from 338 MiB to 190 MiB and resident memory from 415 MiB to 250 MiB on a cluster with 791 CRDs, and a Crossplane blog post of 2026-10-08 reports provider memory dropping by roughly 80 to 95 percent depending on the provider on a cluster of about 2,000 CRDs, using crossplane-runtime v2.4. All of these are self-reported by the project and not independent benchmarks, and the wiki found no measurement of API server memory with and without activation policies ([[findings/crossplane-core-strips-crd-schemas-from-its-cache-and-no-crossplane-performance-or-sharding-guide-was-found]], [[examples/crossplane-v2-4-and-v2-5-cut-memory-on-clusters-with-hundreds-to-two-thousand-crds]]). The Upjet runtime that produces most large providers has no single execution model: it supports three Terraform execution modes chosen per resource configuration, a traditional fork-based mode that spawns the Terraform CLI and provider process (sharing a forked provider process and keeping a workspace per resource until an invocation timeout), and two no-fork modes that call the provider as a Go library, one for the Terraform Plugin SDK v2 and one for the Plugin Framework over protocol v6. Which official providers use which mode was not established, and no official memory or CPU figures exist; the one first-party memory-footprint issue was closed as outdated once provider families arrived, with a collaborator noting that the large monolithic packages are discouraged ([[findings/upjet-supports-three-terraform-execution-modes-selected-per-resource-configuration]], [[findings/no-official-upjet-memory-or-cpu-figures-exist-and-the-memory-footprint-issue-was-closed-as-outdated-by-provider-families]]). Package installs have their own scaling behavior. Crossplane's resolver builds a dependency graph from the Lock object (the cluster-scoped `Lock`, named `lock`, is the "lock file"), never modifies it, and creates only the first missing dependency on each pass, so a chain of unmet dependencies fills in over several reconciles and a Configuration can briefly report unmet dependencies during an install. Dependency version upgrades and downgrades are alpha, and downgrades need two feature flags ([[findings/the-crossplane-lock-resolver-never-modifies-the-lock-and-creates-only-the-first-missing-dependency]], [[findings/crossplane-dependency-version-upgrades-and-downgrades-are-alpha-and-downgrades-need-both-feature-flags]]). The activation-policy and history-limit defaults are documented for providers and Configurations but were not found for Functions ([[findings/crossplane-activation-policy-and-history-defaults-are-documented-for-providers-and-configurations-and-were-not-found-for-functions]]).

Config Connector and ACK are worth stating next to Crossplane because their cadence and controller choice are now documented from source. Config Connector routes each kind to a controller through a static table that, at master commit 5cce7c7e (the latest release then being v1.162.0, 2026-11-23), has 814 entries: direct is the default controller for 539 of them, Terraform-based for 206, DCL-based for 65, and four IAM kinds have their own (these counts are the research author's own tally). All three reconcilers end a successful pass with the same jittered requeue, with a mean of 10 minutes and a jitter that makes the actual delay between 5 and 15 minutes, so the controller kind alone does not change the success cadence. There is no separate drift poll: each reconcile reads live state and compares, so drift detection runs at that cadence. Only five Terraform service-mapping entries override it (two at 0 and three at 3600 seconds), and of 267 generated reference pages the value 600 appears on 262 of them. Failed reconciles back off exponentially from 250 ms up to a 120-second ceiling, and tuning that ceiling with an annotation works only for direct controllers from v1.160.0 ([[findings/config-connector-s-static-config-table-lists-814-kinds-and-sets-direct-as-the-default-for-539-of-them]], [[findings/config-connector-direct-terraform-and-dcl-reconcilers-share-one-jittered-requeue-so-the-controller-kind-alone-does-not-change-the-cadence]], [[findings/config-connector-per-kind-reconcile-intervals-exist-only-as-five-terraform-service-mapping-overrides-and-262-of-267-reference-pages-show-600-seconds]], [[findings/config-connector-has-no-separate-drift-poll-and-the-failure-backoff-annotation-works-only-for-direct-controllers-from-1-160-0]]). Config Connector is installed in namespaced mode by default (the recommended mode, with one `ConfigConnectorContext` per namespace naming that namespace's Google service account) or in cluster mode, which takes exactly one credential for every resource, and by default two objects can manage one cloud resource unless a lease policy is set ([[findings/config-connector-namespaced-mode-is-the-crd-default-and-needs-one-configconnectorcontext-per-namespace-while-cluster-mode-takes-exactly-one-credential]], [[findings/config-connector-conflict-prevention-defaults-to-none-so-two-objects-can-manage-one-cloud-resource-unless-a-lease-policy-is-set]]). ACK's drift check runs about every 10 hours by default. ACK also keeps two documentation sites that disagree: the older one calls annotation-based adoption alpha and disabled by default, while the newer one calls it Beta and enabled by default, and an ACK contributor called the older site deprecated. For controllers released on or after 2026-10-08, cross-namespace references default to blocked, which is a reference-resolution setting and not a tenant-isolation boundary ([[findings/the-ack-old-and-new-documentation-sites-disagree-on-adoption-maturity-and-cross-namespace-references-default-to-blocked-from-2026-10-08-releases]], [[findings/disabling-ack-cross-namespace-references-is-not-tenant-isolation]]). When these tools are wrapped by a composition, the only first-party example is the ACK documentation's kro guide, which composes an S3 bucket, a DynamoDB table and a Deployment, waits for the ACK resources to become ready before creating dependents, and on deletion removes the Deployment first and then the AWS resources following ACK's deletion policy. The guide does not say how kro's alpha deletion-policy annotation combines with ACK's, and it was read and not run ([[examples/the-ack-docs-kro-guide-composes-an-s3-bucket-a-dynamodb-table-and-a-deployment-and-deletes-the-deployment-before-the-aws-resources]]).

Domain-scoped control planes are the architectural version of the same idea. Two practitioner blogs argue that teams no longer need one monolithic Crossplane instance and propose several small control planes scoped to domains such as networking or data. The wiki marks this as advice and not evidence: neither post names an organization running it or gives numbers ([[examples/domain-scoped-crossplane-control-planes-are-proposed-in-place-of-one-monolithic-instance]], [[decisions/run-one-crossplane-control-plane-or-several-domain-scoped-ones]]). It fits the blast-radius principle, but it also multiplies the clusters you must operate.

The tooling comparison across stacks is in [[comparisons/concurrency-and-cache-memory-controls-across-flux-argo-cd-and-crossplane]] and [[comparisons/load-and-fairness-controls-across-controller-runtime-flux-argo-cd-and-kro]]. For retry behavior, [[comparisons/retry-and-backoff-controls-across-tools]] shows that kro caps retries at 20, Argo CD refuses to retry a failed sync of the same commit unless retry is configured, and Flux separates `retryInterval` from `interval`; uncapped retries are the cause of the retry storms described in section 10.

## 9. Industry scale stories: Morgan Stanley, Upbound, Ant Group, Gardener, Cozystack

Real organizations show how these principles bend under load, but the evidence quality varies, and it is worth reading each story with its caveat.

Morgan Stanley described its Flux adoption at FluxCon North America 2025, written up by the Flux team in March 2026, with a reported footprint of "over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources." Before Flux it used push pipelines, which suffered drift and made cluster rebuilds fragile. Multi-tenancy rested on service account impersonation, and a self-service onboarding platform checked entitlements, registered the service in a configuration management database, primed the namespace with a `GitRepository` and a `Kustomization`, and scaffolded the team's repository. At scale the team raised reconciliation intervals, tuned `--concurrent` and resource limits, and moved the source of truth from a self-hosted Git provider to S3 buckets, which the write-up gives as an availability and compliance choice ([[examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding]]). Sharding, OCI artifacts and Flagger were roadmap items, so there are no production sharding numbers. It is a self-reported conference account, not an independent audit, but it is the clearest evidence that vertical tuning plus per-tenant impersonation holds at several hundred clusters.

Upbound's test, covered in section 7, is the story of what happens when a platform meets API machinery that was never tested for thousands of CRDs, and it ended with upstream Kubernetes fixes and then Crossplane's own packaging answer. Crossplane's ADOPTERS list adds self-reported counts from thousands of managed resources (Nike, Deutsche Kreditbank, SAP at 100-plus control planes as of February 2024) up to Akamai's provider-ceph orchestrating up to 200,000 managed resources; the wiki treats these as pointers and not as verified case studies ([[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]]). The targeted pass added a little more named detail. The Crossplane adopters file has 87 entries, but only about eight give any number. Built Technologies says that at times it has exceeded 10,000 AWS resources managed by Crossplane, in a developer environment and not production, undated and self-reported ([[examples/built-technologies-reports-peaks-above-10000-aws-resources-managed-by-crossplane-in-a-developer-environment]]). On the ACK side, Adobe is listed for global Kubernetes cluster provisioning and for stateful service infrastructure using multiple ACK controllers, with no object count and no date ([[examples/adobe-lists-ack-for-global-kubernetes-cluster-provisioning-and-stateful-service-infrastructure]]). Argo CD's users file lists 452 self-reported adopters, and Flux's adopters data file names organizations such as Xenit, SortList, Tietoevry, Nexxiot, SoulCycle and Luma Health, again with no write-ups attached ([[examples/the-flux-adopters-data-file-lists-xenit-sortlist-tietoevry-nexxiot-soulcycle-and-luma-health-among-others-with-no-write-ups]]). The web search that was meant to find more adopter accounts returned nothing, so the absence of further named adopters is an unverified negative. For GitOps outages, the wiki now holds one named-organization postmortem, Skyscanner's, described in section 10, alongside reporter-level GitHub issues from individuals whose employers are not named. No organization says it runs sharded Flux, since Morgan Stanley lists sharding as future work, and there is no adopters file for kro, Cluster API or Config Connector, so named adopters and measured scale for those remain absent ([[findings/no-named-organization-postmortem-was-found-for-a-gitops-revert-loop-a-gitops-outage-or-controller-retry-amplification]]).

Ant Group's more-than-10,000-node cluster is a reminder that custom resources share storage and watch paths with built-in objects, so general apiserver and etcd tuning applies to them too, though the write-up is not about CRDs. Gardener, an operator of many clusters for many tenants, supplies the conservative numbers from section 7 and the warning that conversion webhooks are especially risky because an outage blocks garbage collection ([[findings/a-down-conversion-webhook-can-stall-garbage-collection]]).

Cozystack is a different kind of story. It packages Talos Linux, Kubernetes, KubeVirt, LINSTOR with DRBD, and Kube-OVN into a PaaS framework for turning commodity servers into a cloud offering Kubernetes clusters, databases and VMs through an API ([[examples/cozystack-turns-commodity-servers-into-a-cloud-with-kubernetes-databases-and-vms]]). The wiki has no adopter names or measurements for it, so it illustrates the architecture's direction and not its scale. Its repository does contain a Flux shard operator, described in section 8, which is the only automated Flux sharding the wiki found, with design targets and no measured result. A related direction is the Kubernetes-as-a-kernel distribution model that Aenix, the company behind Cozystack, describes: the wiki found no SIG charter, KEP or conference talk adopting that model, and the one direct source is Aenix's own post, so it is a vendor position and not a community direction ([[findings/no-sig-charter-or-kep-adopts-a-kubernetes-distribution-model-and-the-only-direct-source-is-aenix-s-own-post]]).

Several other stories show platform composition in practice. JFrog delivers self-service cloud environments through Jenkins, Git, Argo CD and Crossplane ([[examples/jfrog-delivers-self-service-cloud-environments-through-jenkins-git-argo-cd-and-crossplane]]). VSHN's AppCat sells self-service databases, queues and object storage through composition functions ([[examples/vshn-appcat-sells-self-service-databases-queues-and-object-storage-through-composition-functions]]). A Google Cloud style stack that delivers Config Connector resources from Git with Argo CD or Flux is described in [[concepts/tooling-landscape]]. The control-plane-as-a-platform idea at its far end is kcp hosting node-less API workspaces for multi-tenant SaaS ([[examples/multi-tenant-api-hosting-with-kcp]]) and Cluster API managing fleets of clusters ([[examples/cluster-fleet-lifecycle-with-cluster-api]]). The wiki repeatedly notes that named production adopters, scale numbers and postmortems remain thin.

## 10. Pitfalls catalog and operational guardrails

The postmortems in the wiki agree that serious incidents are cascades in which a small change meets a loop, a default or a shared dependency. [[concepts/pitfalls-and-case-studies]] names three mechanisms that recur: finalizers, field ownership and deletion propagation. We have already met all three. This section adds the rest and pairs each pitfall with the guardrail the tools provide.

Retry storms come first. Zalando's January 2019 outage began with a timed-out downstream call. Clients retried, which spiked DNS queries; the CoreDNS pods had a 100Mi memory limit and were OOM-killed together; the `ndots:5` default meant about ten DNS queries per external lookup; and monitoring that depended on DNS and ran inside the cluster went blind. Zalando raised the memory limits to 2000Mi, adopted a node-local design, and moved alerting outside the cluster ([[examples/zalando-s-2019-coredns-outage-turned-a-retry-storm-into-a-total-dns-failure]], [[findings/monitoring-that-runs-inside-the-cluster-and-depends-on-cluster-dns-goes-blind-in-the-outage-it-should-report]]). The postmortem states the principle: it should not be possible for a single application to take down DNS infrastructure. Within the tools, retries are capped differently, as described in section 8.

Webhook outages are a recurring class in the k8s.af index ([[findings/admission-webhook-outages-are-a-recurring-failure-class]]), and the wiki has now read one of those postmortems in full: Jetstack's post of 2019-09-05, read through a Wayback Machine copy because the original page returned empty. A regional GKE cluster in europe-west1, shared by many teams, was upgrading its master through a Terraform pipeline. During the second master's upgrade the API server tried to update the `extension-apiserver-authentication` ConfigMap in `kube-system` as part of a post-start hook, and that write was subject to an Open Policy Agent (OPA, a policy engine that Kubernetes admission webhooks can call) validating webhook whose backend was not responding, so it timed out. The post says the operation must complete for a master to pass its health check, so the master crash-looped and the upgrade halted. Intermittent API downtime then stopped kubelets from reporting node health, and GKE node auto-repair began recreating nodes in an endless loop, which caused loss of service for every tenant. Jetstack fixed it by deleting the validating webhook, which worked only because the API server answered intermittently. Its follow-ups were scoping the webhook to the namespaces where policy applies, enabling it only for Ingress and Service resources, adding a liveness probe to OPA, and alerting on API server response times for create and update calls, and it deliberately kept node auto-repair on. The post never mentions `failurePolicy`, so its fixes were not a change of failure policy. The account is self-reported ([[examples/jetstack-s-2019-gke-master-upgrade-stalled-on-an-unresponsive-opa-validating-webhook]]). The second k8s.af webhook entry, an Airbnb KubeCon talk, was video-only and unread, so only these two webhook entries exist in the index and just one has been verified. The OpenAI incident in section 7 shows the same lesson from the control-plane side, since the tools needed to repair the cluster sat on the path that failed.

Reddit's Pi-Day postmortem (March 2023) shows the webhook as a symptom and not the cause. During a 1.23 to 1.24 upgrade the API server began timing out on writes because of calls to its OPA webhook, and removing the webhook configurations ended the timeouts without recovering the cluster, since the real fault was that Kubernetes 1.24 removed the `node-role.kubernetes.io/master` label that Calico route reflectors selected on ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]]). The official guidance is to scope matches narrowly, exclude system namespaces, keep timeouts short, run multiple replicas and use `Fail` only for security-critical checks ([[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]]).

Policy engines make that choice for you unless you override it: Kyverno, another policy engine that runs as an admission webhook, defaults to `failurePolicy: Fail` with a 10-second timeout (range 1 to 30 seconds), excludes its own and `kube-system` namespaces by default, and documents three admission replicas as the minimum for high availability, while its troubleshooting page warns that wildcard-matching policies can double or triple its resource needs ([[findings/kyverno-defaults-to-failure-policy-fail-with-a-10-second-timeout-and-needs-three-admission-replicas-for-high-availability]]). Not every tool has a webhook to fail. kro and ACK ship no admission webhook and rely on CRD schema and CEL validation instead (for Argo CD the wiki found no admission webhook, but only by searching the repository tree, which is weaker evidence than reading the manifests) ([[findings/kro-and-ack-ship-no-admission-webhook-and-rely-on-crd-schema-and-cel-validation-and-no-argo-cd-webhook-was-found-in-a-tree-search-only]]). CEL validation has its own limits that bite platform authors: the API server estimates each rule's cost statically and rejects a CRD whose rule exceeds 10 million for one expression or 100 million for all rules in one CRD, an unbounded list or string makes the estimate too high until `maxItems` and `maxLength` are set, and at runtime there is a per-call limit of 1 million and a budget of 10 million per request ([[findings/cel-cost-limits-are-10-million-per-expression-and-100-million-per-crd-statically-and-1-million-per-call-and-10-million-per-request-at-runtime]], [[findings/an-unbounded-list-or-string-makes-the-cel-cost-estimate-reject-a-crd-rule-until-maxitems-and-maxlength-are-set]]).

Three named postmortems now show what happens when a faithful automation applies the wrong intent, and they are worth reading as a set. Skyscanner's outage of 25 August 2021 is the clearest GitOps case. An engineer merged a change to the templating system that was meant to change no behavior, but it left out the `{{ }}` template markers, so templating stopped applying and the rarely changed root file that rolled out regional configuration reached every region at once. At about 1600 GMT Argo CD reconciled the clusters against a configuration that listed no valid namespaces and began deleting every service, 478 in all, across every availability zone and region. Because clusters pull their state, recovery meant restoring correct configuration and letting each cluster reconcile itself, and skyscanner.net was serving from a single region by about 2030 GMT, with the rest returning over two days. The post does not say which Argo CD sync options were set, whether pruning was automated, or why no guard stopped the deletion, and it gives two outage durations (four and four and a half hours), so the wiki does not claim a specific misconfiguration ([[examples/skyscanner-s-2021-global-outage-an-incorrect-template-change-was-reconciled-by-argo-cd-into-deleting-478-services]]). Reddit's outage of 14 March 2023 ran 314 minutes. A Kubernetes 1.23 to 1.24 upgrade removed a master node label that its hand-edited Calico route reflector selectors relied on, routing collapsed, rolling back required restoring an etcd backup because Kubernetes has no supported downgrade, and the restore procedure was old and untested ([[examples/reddit-s-march-2023-pi-day-outage-a-kubernetes-1-24-upgrade-removed-the-master-node-label-that-calico-route-reflectors-selected]], [[findings/kubernetes-has-no-supported-downgrade-so-a-failed-control-plane-upgrade-forces-a-backup-restore-and-an-untested-restore-procedure-is-the-risk]]). The primary post supersedes an earlier secondary retelling whose reconstructed command output and user figure were not in Reddit's own account. Spotify's talk covers a November 2018 console deletion of a 50-node production GKE cluster, restored in 3 hours 15 minutes, and a second incident about a month later in which a Terraform review build wrote to a state file shared with production builds, an out-of-order merge deleted the Asia cluster, and widening a service account's permissions while recreating it led Terraform to delete a second cluster. Two of three production clusters were gone for roughly nine hours, yet the team reports no end-user impact, which it credits to partial migration, service discovery that registered pod IPs, hourly backups and rehearsed restores ([[examples/spotify-deleted-one-production-gke-cluster-by-console-click-and-two-more-through-terraform-with-no-end-user-impact]]). The Spotify dates are the speaker's and the end-user claim means no reports reached the team. All three accounts are self-reported by the organizations involved. Skyscanner and Spotify share the lesson that destructive operations need guards separate from the tool doing the reconciling.

Ordering and CRDs are the next group. Applying a custom resource before its CRD is established fails with "no matches for kind", reported in Helm, Argo CD and Flux alike ([[findings/custom-resources-applied-before-their-crd-exists]]). Flux's remedy is separate Kustomizations linked by `dependsOn` with health checks; Argo CD users reach for sync waves, where the order is phase, then wave, then kind, then name, and each wave must be Healthy before the next ([[examples/argo-cd-sync-waves-order-crds-operators-and-workloads]]); the wiki marks some Argo CD details as unverified, and compares the two in [[comparisons/missing-crd-handling-flux-versus-argo-cd]]. Helm has no native support for upgrading or deleting CRDs, which Flux works around with `install.crds` and `upgrade.crds` policies ([[findings/helm-does-not-upgrade-or-delete-crds]]). Circular `dependsOn` chains never reconcile ([[findings/circular-dependson-chains-between-flux-resources-never-reconcile]]). The deeper principle, from [[concepts/eventual-consistency-and-convergence]], is that Kubernetes does not promise instant convergence; Flux's `dependsOn` keeps the retry-until-ready behavior but in a controlled order, so transient errors do not arrive as a burst ([[comparisons/ordering-models-flux-argo-cd-kro-crossplane]]).

Automation hazards come from the fact that GitOps tools do exactly what they are told, quickly and repeatedly, so any ambiguity in what they are told becomes an outage. The first hazard is image automation, where a controller watches a container registry and writes new image tags back into Git. If the rule that selects tags is looser than the team realizes, an unintended version is committed and then rolled out by the same loop that normally protects you, and nothing in the pipeline treats it as unusual ([[findings/automatic-image-tag-updates-can-roll-unintended-versions-into-production]]). Flux's reference repository limits image automation to staging for that reason, so production changes still pass through a human decision. The current image automation kinds (ImageRepository, ImagePolicy and ImageUpdateAutomation) are served at `image.toolkit.fluxcd.io/v1`, with the older `v1beta1` and `v1beta2` packages still present in the API directory; the wiki did not find the release at which they graduated to v1 or the ImageUpdateAutomation storage version ([[findings/flux-image-automation-kinds-are-image-toolkit-fluxcd-io-v1-with-older-versions-still-in-the-api-directory]]). The official image update guide offers three controls and stops there. Production uses semver-selected release tags built by CI while staging uses tags chosen by numerical or alphabetical policies. Setting `spec.git.push.branch` to a branch different from the checkout branch lets CI open a pull request, so that, in the guide's words, you can manually approve the image updates before they are applied. A bad update is undone by narrowing the semver range. No adopter write-up on staging-only or reviewed promotion was found, so the promotion policy that teams actually use remains an open question ([[findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range]], [[decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation]]).

A related hazard is the mutable remote reference. A Kustomization or Helm release can pull a base or a chart from somewhere other than your repository, and if that reference points at a branch or a floating tag, the same commit of your own repository can render different manifests tomorrow than it did today. The deployment looks unchanged in Git while the cluster changes, which defeats the audit trail that made GitOps attractive. Pinning remote Helm and Kustomize references to tags or commit SHAs restores the property that a commit determines what runs ([[findings/mutable-remote-references-change-what-a-commit-renders]]). Rollback has a similar trap in Argo CD. Its rollback action works by deploying an older revision directly, but while automated sync is on, the next sync immediately re-applies whatever Git says, so the rollback is undone or refused. The tool blocks it to protect the principle that Git is the source of truth, which means the working path is a Git revert that the automation then follows ([[findings/rollback-is-blocked-while-automated-sync-is-on]]).

The remaining hazards concern how objects are written. Argo CD's `Replace` and force sync options delete and recreate a resource instead of patching it, which is sometimes needed for immutable fields but briefly removes the object, so a Deployment or a stateful resource can take an outage ([[findings/argo-cd-replace-and-force-sync-options-can-recreate-resources-and-cause-outages]]). Flux's `force` option does the same when an update touches an immutable field, and it should be a temporary measure and not a standing setting. Migrating from client-side apply to server-side apply can leave behind fields that nobody now wants. The old `kubectl apply` ownership is recorded under a manager that no longer runs, and a stale co-owner cannot be forced off a field by the new manager through an ordinary apply, so removing the field from Git does not remove it from the live object ([[examples/flux-migration-from-client-side-apply-strands-removed-fields]]). Finally, an Argo CD app-of-apps, which is an Application whose job is to create other Applications, can show perpetually out of sync when an image updater edits the same fields that the parent also declares. That is the same two-writers field fight from section 2, and the fix is likewise an explicit ownership decision ([[examples/argo-cd-app-of-apps-out-of-sync-from-image-updater]]).

Silent failures are the most dangerous class because nothing alerts. Flux failures can be silent when resources are suspended, when polling lag hides a missing webhook, or when the `--with-source` flag is missing ([[findings/suspended-resources-polling-lag-and-a-missing-with-source-flag-make-flux-failures-silent]]); the evidence there is documentation plus one practitioner blog. The `Synced=False` with `Ready=True` case from section 4 belongs here too.

A short set of operational guardrails follows from all of this, stated as sentences and not a checklist. Keep prune off until the source of truth is trusted, and annotate objects that must never be pruned. Choose an orphan or retain policy for critical external resources before deleting anything, and apply the policy before the delete. Set explicit propagation options when a GitOps tool hosts composites. Alert from outside the cluster on saturation signals. Read both the GitOps tool's sync status and the custom resource's conditions. Keep test environments identical to production and read release notes before upgrades. Review cluster-scoped configuration with the rigor of code. The wiki is careful to say that its older pitfall evidence rests mostly on 2017 to 2021 incidents, documentation and blogs, although the postmortems above add 2023 (Reddit), 2024 (OpenAI) and 2025 (Neon) accounts, and that it found no named-organization postmortem specific to kro, Config Connector, ACK or Cluster API. What exists for those tools is first-party known-issue lists and release notes, plus individual reporter issues, almost all open without maintainer root-cause confirmation. Google's Config Connector known-issues page (last updated 2026-11-10) records a race in webhook TLS setup before version 1.134.1 that could leave the API server rejecting creates while existing resources kept reconciling, a stricter validation in 1.134.0 that wedged `SQLInstance` in Updating until 1.134.2, and regressions in direct reconcilers in 1.132.0. That is useful evidence of upgrade-ordering risk, but it names no organization and gives no incident timeline, so it is a known-issue list and not a postmortem ([[findings/config-connector-known-issues-record-a-webhook-tls-race-before-1-134-1-and-direct-reconciler-regressions-in-1-132-0-and-1-134-0]], [[findings/no-named-organization-postmortem-was-found-for-kro-config-connector-ack-or-cluster-api]]). kro's v0.10.0 release notes record fixes for partial-apply cleanup and duplicate definition identities, and an alpha deletion policy behind an off-by-default feature flag, though whether any kro fix followed a production incident is undetermined ([[findings/kro-v0-10-0-fixes-partial-apply-cleanup-and-duplicate-rgd-identities-and-pull-request-1445-adds-an-alpha-deletion-policy-behind-an-off-by-default-gate]]). A Flux Kustomization with `WaitForTermination` also gives up at its own timeout and lets the Kustomization be deleted while a provider resource may still be finalizing ([[findings/a-flux-waitfortermination-deletion-policy-gives-up-at-spec-timeout-and-lets-the-kustomization-be-deleted-while-a-provider-resource-may-still-be-finalizing]]) ([[findings/the-pitfalls-dossier-rests-on-index-summaries-an-older-crossplane-version-and-few-primary-incident-reports]]).

## 11. The tooling landscape: delivery, provisioning, platform and portal layers

The landscape is easiest to learn as three layers that solve different problems and are routinely combined, and confusing them is the most common source of bad comparisons ([[concepts/tooling-landscape]], [[comparisons/delivery-versus-provisioning-versus-platform-layers-in-the-kubernetes-tooling-landscape]]). Asking whether Argo CD or Crossplane is better is like asking whether a package manager beats a database, because one moves manifests and the other reconciles cloud resources.

The delivery layer gets desired state from Git, OCI or Helm into a cluster and keeps it there. Flux and Argo CD are the two CNCF projects. Argo CD ships as an integrated application with an API server, a repository server that renders manifests and an application controller that diffs live against target state, polling on a 120-second cadence with up to 60 seconds of jitter in v3.x. That is a version-specific fact: through v2.14 the default was a flat 180 seconds, and some newer documentation still repeats the three-minute figure. The wiki did not find the reason for the change ([[findings/argo-cd-changed-its-default-polling-from-a-flat-180-seconds-to-120-seconds-plus-60-seconds-of-jitter-in-v3-0-and-some-docs-still-say-three-minutes]]). Flux ships as a toolkit of small controllers that each own their own CRDs, so its parts can be used by other automation ([[comparisons/flux-versus-argo-cd-architecture]], [[comparisons/reconcile-cadence-and-off-switches-across-tools]]). The vendor caution applies here: comparisons often come from vendors such as Akuity (which sells Argo CD), Port and Syntasso (which sells Kratix), with no independent benchmarks ([[findings/landscape-comparisons-of-argo-cd-flux-port-and-kratix-come-from-vendors-with-no-independent-benchmarks]], [[comparisons/flux-versus-argo-cd-isolation-ordering-and-interface-according-to-a-vendor-blog]]). The pull-versus-push comparison in [[comparisons/push-versus-pull-delivery]] explains why pull limits credential exposure: a push pipeline holds credentials for every environment, while a pull agent needs only read access to the source but becomes a powerful identity itself. Flux's D2 reference architecture goes further, with clusters pulling signed OCI artifacts so they never connect to a Git host ([[examples/flux-d2-gitless-gitops-fleet-with-signed-oci-artifacts]]); the wiki notes this is a vendor write-up, and whether Git or OCI should be the source of truth is unresolved (see [[concepts/gitops-pull-based-delivery]]). The signature evidence is lopsided. Flux's OCIRepository can verify Cosign or Notation signatures, supports keyless verification by matching OIDC identities, and can pin a Sigstore trust root, while the Argo CD pages the wiki read document OCI sources (an image with a single layer) and Git commit signature checks with GnuPG keys, and describe no OCI signature verification. That is a statement about the pages read and not proof that the feature is absent from the code, and no independent evidence that signed OCI beats Git, nor any registry rate-limit documentation, was found for either tool ([[findings/flux-verifies-cosign-and-notation-signatures-on-oci-artifacts-while-the-argo-cd-pages-read-document-no-oci-signature-verification]], [[decisions/git-versus-oci-as-the-canonical-source]]).

The provisioning layer turns custom resources into calls against an infrastructure API. Config Connector, ACK and Azure Service Operator are single-vendor controllers that expose roughly one CRD per cloud resource ([[comparisons/crossplane-versus-cloud-vendor-add-ons-ack-config-connector-and-aso]]). Crossplane is multi-cloud and adds Compositions so a platform team can publish its own API without writing a controller. The Terraform wrappers, tofu-controller and terraform-operator, run plan and apply in pods ([[comparisons/crossplane-versus-terraform-reconciliation-versus-plan-and-apply]]). Their maintenance status was checked on 2026-11-26. tofu-controller lives under the community `flux-iac` organization (it was previously the Weave TF-Controller), has five active maintainers and a roughly monthly to bimonthly release cadence, and its v0.17.0 release of 2026-11-16 removed the v1alpha1 API so only v1alpha2 remains. The Terraform Operator, now at `GalleyBytes/terraform-operator`, had no release after v0.17.1 on 2024-05-17 and one person wrote nearly all of its commits, though the wiki found no deprecation notice and so describes it as low-activity and not as abandoned ([[findings/tofu-controller-is-community-maintained-under-flux-iac-and-v0-17-0-removed-the-v1alpha1-api]], [[findings/terraform-operator-has-had-no-release-since-may-2024-and-is-effectively-single-maintainer]], [[comparisons/tofu-controller-versus-terraform-operator-as-terraform-in-cluster-controllers]]). Be cautious with the comparisons you will find: no neutral comparison of Crossplane with Terraform or with the single-cloud operators turned up, only vendor, consultancy and lab write-ups, the most independent item is a 2022 post that predates Crossplane v2, and a search for a neutral Config Connector versus Crossplane study found two vendor positions and nothing else ([[findings/no-neutral-comparison-of-crossplane-with-terraform-or-single-cloud-operators-was-found-and-the-independent-material-is-dated]], [[findings/no-neutral-comparison-of-config-connector-and-crossplane-was-found-so-the-evidence-is-two-vendor-positions]]). Cluster API applies the pattern to Kubernetes clusters themselves. The per-resource controllers do not build a dependency graph, so ordering falls to the delivery tool or a composition layer, and the controller holds the cloud identity, so whoever can create the custom resource inherits its rights.

The platform and portal layer defines what application teams see. Backstage and Port are catalogs and portals with self-service actions, Kratix is an orchestration framework behind a portal where a Promise, Kratix's unit of packaging, bundles a platform API together with the workflows that fulfill requests for it and the rules for scheduling the result onto a fleet of clusters, and Cozystack ships its own substrate ([[comparisons/backstage-versus-port-versus-kratix-as-portal-and-orchestration-layers]]). The wiki records that a portal supplies visibility and not provisioning, a claim attributed to a Kratix vendor. Backstage's own documentation fits that reading. Its Kubernetes feature is described as designed for service owners and not cluster admins, and its backend reads standard objects plus the custom resources an operator configures by group, version and plural, matching them to catalog entities through the label `backstage.io/kubernetes-id` or a label selector annotation. A custom resource whose CRD is not installed is silently skipped and only logged at debug level, so a typo shows up as an empty panel and not an error. No Backstage document the wiki read describes an operator pattern, and Software Templates were not read, so the idea that templates and the catalog form a platform layer above operators remains unverified ([[findings/the-backstage-kubernetes-plugin-matches-entities-to-cluster-objects-by-label-and-no-backstage-document-describes-an-operator-pattern]]). A later pass read the Software Templates documentation and settled that question in part: the Scaffolder loads code skeletons, fills in variables and publishes the result to a location such as GitHub or GitLab, and each run is treated as a unique task, which makes it an imperative run-once tool and not a reconcile loop. The nearest operator-style integration is a community plugin, the TeraSky Kubernetes Ingestor, which acts as a sync loop in the Backstage backend from cluster to catalog and ingests Crossplane claims and kro instances, while the upstream community-plugins repository has workspaces for Argo CD and Flux but none for Crossplane or kro. The built-in Scaffolder actions page was not read, so a built-in action that creates custom resources is not ruled out ([[findings/the-backstage-scaffolder-is-a-one-shot-task-runner-and-the-nearest-operator-style-integration-is-a-third-party-plugin]]).

Kratix's mechanics are now documented in more detail. It schedules in two stages by label matching. In the first stage a Promise's dependencies go to every Destination by default, or only to Destinations whose labels satisfy the Promise's `destinationSelectors`, and a Destination with `strictMatchLabels: true` accepts only Promises whose selectors match its labels. In the second stage a resource request triggers the `resource.configure` workflow and its output goes to a matching Destination, and when several match, Kratix by default picks one at random. A workflow can add selectors of its own, and on conflict the order of precedence is the Promise selectors, then the Promise workflow file, then the Resource workflow file. Kratix does not apply what it produces. It writes documents to a state store (a Git repository through a GitStateStore, or an S3-compatible bucket through a BucketStateStore) under a `dependencies` directory and a `resources` directory, and the agent on the Destination, typically Flux or Argo CD, reads them from there. The Destination's filepath mode is immutable once created, so changing the layout means creating a new Destination. Only the documentation and the Go types were read, not the scheduler or the work-creator source, so how matching is implemented is unverified ([[findings/kratix-schedules-in-two-stages-by-label-matching-and-picks-a-destination-at-random-when-several-match]], [[findings/a-kratix-destination-writes-dependencies-and-resources-directories-and-its-filepath-mode-is-immutable]]).

Radius and Score, the two developer-facing workload abstractions, now have primary status evidence. The CNCF landscape file lists both as Sandbox projects (Radius accepted 2024-04-16, Score 2024-07-08), and the matching sandbox issues passed their votes. Sandbox is the entry tier, so it confirms presence in the foundation and says nothing about production readiness. All four Radius maintainers listed in its community repository are Microsoft employees, only the newest minor release channel (0.62 when read) is supported with the four before it deprecated, and its changelog still lists breaking changes. Score's maintainers span four employers, and its sandbox application names Humanitec as the sponsoring company, though no primary text says Humanitec created it ([[findings/radius-and-score-are-both-cncf-sandbox-projects-per-the-landscape-file-and-both-passed-sandbox-votes]], [[findings/all-four-radius-maintainers-are-microsoft-employees-and-only-the-newest-minor-channel-is-supported]], [[findings/score-maintainers-span-four-employers-and-the-sandbox-application-names-humanitec-as-sponsoring-company]]). The earlier single-blog finding about Radius was marked contradicted by these listings, and only its Bicep-dependency claim still rests on one blog.

Abstraction tools overlap with each other. kro merges schema and implementation into one ResourceGraphDefinition, generates the CRD, infers dependency order from CEL references, and deletes in reverse; the Crossplane project's `function-kro` runs kro-style graphs inside a pipeline. Its README claims "full feature parity", but the repository's own `UPSTREAM_DIFFERENCES.md` lists where a graph behaves differently from the same definition in kro: a resource that cannot be rendered makes the function return a fatal result so that Crossplane applies nothing and the composite goes `Synced=False` (upstream keeps the resource and retries), a hard error in one resource fails the whole run, dependents see rendered values one function pass before server-set values, the composite's status is not checked against its definition, Crossplane-owned condition types cannot be set by authors, and conditions such as `GraphResolved` are approximations. Release v0.4.0 (2026-11-26) moved onto the kro v0.10.0 graph engine, with one listed maintainer, so the fair reading is the same engine with documented gaps. Independent production reports were not found, and how a standalone kro controller would feed a Crossplane composite is undocumented ([[findings/function-kro-lists-documented-behavioral-differences-from-upstream-kro-so-its-full-parity-claim-reads-as-same-engine-with-gaps]], [[examples/function-kro-v0-4-0-moved-onto-the-kro-v0-10-0-graph-engine-on-2026-11-26-with-one-listed-maintainer]], [[findings/function-kro-approximates-kro-built-in-conditions-from-one-run-and-writes-only-declared-status-paths-to-the-desired-xr]]). Helm and Kustomize are render-time abstractions that produce manifests once and leave correction to a GitOps tool, while composites are live control loops ([[comparisons/render-time-versus-controller-driven-abstraction-helm-kustomize-kpt-score-crossplane-kro-and-radius]], [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]]). Both tools reach the same outcome in the wiki's StorageApp comparison, with kro inferring order and Crossplane's Go-template route needing hand-written ordering and deletion guards ([[findings/go-template-compositions-need-hand-written-ordering-and-deletion-guards]]). A worked end-to-end example is [[examples/platform-team-self-service-apis-with-crossplane-and-kro]], and kro is `v1alpha1`, which the wiki flags as immaturity ([[findings/immature-abstractions-in-the-control-plane-ecosystem]]).

For plain controllers, the contrast is the cost of writing one per platform API, which composition and resource graphs exist to avoid ([[comparisons/hand-written-operator-versus-crossplane-composition-versus-kro]]). Tenancy at the cluster level is compared in [[comparisons/tenancy-models-namespaces-vcluster-kcp]]. If you want a yardstick for how mature a hand-written operator is, the Operator SDK defines five capability levels from Level 1, Basic Install, to Level 5, Auto Pilot, framed around an operator managing a workload. It says operators that do not manage a workload, or that delegate to off-cluster orchestration services, remain at Level 1, and its page never mentions Crossplane, kro or composition, so it offers no rating for those tools ([[findings/operator-sdk-capability-levels-keep-delegating-operators-at-level-1-and-say-nothing-about-composition-tools]]).

## 12. Remaining gaps and what is not yet known

This part would be dishonest if it ended with a tidy conclusion, because the wiki records many open questions, and several touch the heart of the thesis.

The first is the trace itself. The wiki's open gap on the full Git-commit-to-Ready lifecycle remains open: no source traces the handoff from the source controller to the kustomize controller in detail, finalizer registration, and status updates, and the dossiers cover Flux at the component and API level. What you read in section 2 is a faithful composition of documented behaviors, but it is a composition and not an observation. A worked example on a live cluster would close it.

The second is scale evidence. Named production adopters and object counts are mostly self-reported. The scale dossier relies on digests for most numbers, so limits need rechecking. There is no sourced data on how cloud provider API limits constrain Crossplane, Config Connector or ACK, no scaling data for kro, ACK, Cluster API or Config Connector controllers, and no documented numeric limits in the current Crossplane v2 scaling guidance, which exists only as scattered advice. The scale figures that came from digests were rechecked against raw text on 2026-11-26 and held up. The only threshold the wiki found for Flux sharding is the documentation's advice to shard at "tens of thousands of applications", and the project benchmark is a single small kind cluster, while Morgan Stanley lists sharding as future work and Cozystack's roughly 100 HelmReleases per shard is a design target. kro has no benchmark, measured limit or named production adopter, Crossplane's v2 scaling guidance is still scattered across pages with no numeric capacity limits, Upjet has no official memory or CPU figures, Config Connector's drift latency was never measured on a live cluster, and no neutral Argo CD versus Flux benchmark exists. Authoritative CRD scale limits are open ([[findings/the-scale-dossier-relies-on-model-digests-for-most-numbers-so-limits-need-rechecking]]).

The third is controller mechanics. What an informer resync does is now settled from the client-go source: it is a local replay of the informer's cached objects to the handlers and never contacts the API server, as Part 3 explains. What remains unresolved is whether it should be switched on, because sources disagree on whether a periodic resync is a useful defense against reconciler bugs or a common misunderstanding ([[decisions/keep-informer-resync-disabled-or-set-a-periodic-resync]]). The reconcile result `Requeue: true` is deprecated, and its behavior is now settled at controller-runtime v0.25.3: it is a rate-limited requeue with per-object exponential backoff, and the failure history is kept, so a reconciler that returns it on every pass waits longer each time. Only `RequeueAfter` clears the history and schedules the next run after exactly that duration. The earlier suggestion in one issue summary that it requeues immediately could not be traced to a source, because only the issue body was read and not its comment thread ([[findings/a-requeue-true-result-backs-off-exponentially-because-only-requeueafter-forgets-the-failure-history]]). Reconcile defaults are now mostly established: Crossplane polls at one minute in core and ten minutes in Upjet providers, ACK resyncs at about ten hours, Config Connector averages ten minutes with jitter, and Cluster API's ten-minute sync period is a cache resync and not a poll of the cloud infrastructure, though Cluster API drift handling beyond that flag was not found ([[findings/crossplane-poll-interval-defaults-differ-by-layer-with-one-minute-in-core-and-runtime-and-ten-minutes-in-upjet-providers]], [[findings/the-cluster-api-sync-period-flag-is-a-cache-resync-and-not-a-poll-of-the-cloud-infrastructure]]). Server-side apply behavior is now read for kro (force for templates, no force for patches), ACK (merge patches, no field manager), Cluster API (forced ownership under `capi-topology`) and Helm 4 (server-side by default for new releases), as section 2 describes. Config Connector's apply behavior was not found, and the helm-controller's handling of Helm 4 server-side apply was not settled.

The fourth is the evidence for failure modes. The pitfalls evidence is mostly older, documentation-based and vendor-influenced. The wiki still found no named-company postmortem of a runaway reconcile loop, of an accidental prune that a company reported as its own, or of a kro, Config Connector, ACK or Cluster API pitfall. What exists are named issue-level incidents with reporter-measured rates, in three projects: Cluster API provider RKE2 reached about 10 reconciles per second because it patched status on every pass and the loop outlived its trigger ([[examples/cluster-api-provider-rke2-issue-905-an-unconditional-status-patch-held-the-controller-at-about-ten-reconciles-per-second]]); Longhorn v1.10.1 copied a raw backup-store error, with S3 request IDs and timestamps, into a condition message, so its equality check never matched and it ran about 6 reconciles per second ([[examples/longhorn-issue-13831-volatile-text-in-a-condition-message-drove-about-six-reconciles-per-second]]); and the Konflux kube-shard operator server-side-applied one ConfigMap twice per pass with different labels while owning ConfigMaps with no predicate, which looped at about 13 reconciles per second ([[examples/konflux-kube-shard-issue-121-two-server-side-applies-of-one-configmap-looped-at-about-13-reconciles-per-second]]). A Crossplane issue shows the same unconditional status update keeping reconcile-ordering tests from converging, though its fix was not read ([[examples/crossplane-issue-7221-an-unconditional-status-update-kept-reconcile-ordering-tests-from-converging]]). The three mechanisms are a status write on every pass, volatile text in a condition message, and an apply that changes the object each time with no predicate to ignore the controller's own writes ([[findings/a-status-patch-or-update-on-every-pass-keeps-a-controller-in-a-self-sustaining-reconcile-loop]], [[findings/volatile-text-in-a-condition-message-defeats-the-equality-check-and-causes-a-reconcile-storm]], [[findings/applying-one-object-twice-in-a-reconcile-with-owns-and-no-predicate-loops-on-its-own-resource-version]]). The rates are the reporters' own. The control-plane-as-platform class has two primary reports, OpenAI (December 2024) and Neon (May 2025), plus Jetstack's 2019 webhook outage, and the section 10 postmortems from Skyscanner, Reddit and Spotify are now read in primary form, so they are no longer index-level evidence; but nothing from 2024 to 2026 on Argo CD, Flux, Crossplane, Karpenter or cert-manager surfaced as an organization postmortem, and the Airbnb webhook talk remains unread. Finalizer naming is now established from source for Flux, Argo CD, ACK, Config Connector and kro (section 5), with the caveats noted there. The Flux default interval conflict is explained in section 2: the concepts page says five minutes, and the API types require an explicit interval. The other-tool coverage pass closed some questions and left others. It settled Config Connector's per-kind controller routing and cadence, the Radius and Score status, the Kratix Destination mechanics, the tofu-controller and Terraform Operator maintenance state, the KRM function specification and Crossplane's function-runner history. It left open the Argo CD and Flux comparison that rests on each project's own documentation, any named kro, Config Connector or Cluster API adopter, argocd-agent's maturity, how Flux treats Cluster API objects and ACK terminal conditions, whether the Terraform-based Config Connector controller honors `abandon`, and the Kubernetes staleness-mitigation work. For that last item, the metric and feature-flag names are now pinned to tagged source: the staleness check for the horizontal pod autoscaler is already in v1.37.0, while `MonitorInformerStaleness` and the handler `BookmarkFunc` described by KEP 5647 are absent from v1.36.0, v1.37.0 and master, so a later release cannot be ruled out ([[findings/monitorinformerstaleness-and-the-handler-bookmarkfunc-are-absent-from-kubernetes-v1-36-0-v1-37-0-and-master-source]], [[findings/kubernetes-v1-37-0-already-carries-the-horizontal-pod-autoscaler-staleness-gate-and-every-per-controller-gate-depends-on-atomicfifo]]). Several of these answers rest on documentation or source read on the main branch and not on pinned release tags, and the web search tool returned nothing for several queries, so each absence is weak evidence and a different access path might change it.

The fifth is design direction. Where `observedGeneration` should live, the right polarity for new condition types, the best default conflict policy for teams running GitOps beside in-cluster controllers, and whether to place external names in an annotation or a spec field are all framed as open decisions. Crossplane versus kro is still a live debate, and the abstractions themselves are young.

None of these gaps contradicts the thesis, and each sharpens it. The mechanics compose, the principles follow from the composition, and the places where the evidence is thin are the places where a careful platform team should measure its own system instead of trusting a number from a blog.
