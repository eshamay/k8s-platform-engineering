## Summary

The dossier explains that a CustomResourceDefinition (CRD) is an API object that registers a new resource type with the built-in kube-apiserver at runtime. The server then serves a REST endpoint for the new kind with the same machinery as built-in types: list and watch, RBAC, audit logging, schema validation, and storage in etcd. The official documentation frames this as the low-effort extension path, with the aggregated API server as the more flexible but more expensive alternative.

The dossier organizes the topic into four themes. The first is that a CRD only stores data, so the usual pattern is a custom resource plus a custom controller, which is the operator pattern, governed by the API conventions for `spec`, `status`, conditions, `resourceVersion`, and `generation`. The second is schema and version mechanics: structural OpenAPI v3 schemas drive validation, pruning, and defaulting, CEL rules reduce the need for validating webhooks, exactly one version is the storage version, and conversion is either `None` or a webhook. The third is that platform tools treat CRDs as a product surface, because Crossplane XRDs and kro ResourceGraphDefinitions generate CRDs, while Flux and Argo CD must cope with the CRD lifecycle. The fourth is operational weight: every CRD adds API surface, etcd data, webhook dependencies, and upgrade-ordering concerns.

See [[concepts/custom-resource-definition]] for the synthesized concept.

## Key claims

### What a CRD gives and costs

- Custom resources can appear and disappear in a running cluster through dynamic registration, and cluster admins can update them independently of the cluster itself. The concept page compares CRDs, which need no new server, with aggregated APIs, which allow custom business logic but must be run separately. It lists when to use a custom resource (a declarative API, kubectl and dashboard integration, RBAC and audit for free) and when not to (a non-declarative API, unusual REST paths), and it warns that third-party CRD code adds failure points, that data lives in etcd and needs backup, and that authentication, authorization, and audit must be considered. URL: https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/. Quote: "Custom resources can appear and disappear in a running cluster through dynamic registration, and cluster admins can update custom resources independently of the cluster itself." The dossier read about 100,000 of 119,000 characters. See [[decisions/crd-versus-aggregated-api]].
- An internals explainer says the apiserver turns a schema into a typed REST surface, and that custom resources sit in the same etcd keyspace as built-ins under `/registry/<group>/<resource>/...`. It cites a limit of about 1.5 MB per object, a conversion webhook evaluation budget, and per-rule CEL cost budgets, but it is a secondary source and the numbers need confirming against official documentation. URL: https://semicolony.dev/codex/kubernetes/internals/crd-operators/. Quote: "Hand the api-server an OpenAPI schema, it gives you back a typed REST surface: listed, watched, validated, RBAC'd, audit-logged, and stored in etcd." See [[examples/postgrescluster-custom-resource-reconciled-into-child-objects]] and [[findings/etcd-scale-limits-of-the-shared-store]].
- The API conventions document sets the contract that well-built CRDs follow: `spec` is desired state and `status` is observation, status is written through the `/status` subresource, conditions have a standard structure (type, status, reason, message, observedGeneration), `resourceVersion` conflicts return HTTP 409, and `generation` and `observedGeneration` show whether a controller has seen the latest spec. It also describes three kinds of defaulting (static, admission, and controller-assigned), ownerReferences for garbage collection, and avoiding cross-namespace references. URL: https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md. Quote (approximate, supplied by the fetch tool): "By convention, the Kubernetes API distinguishes between the specification of desired state (`spec`) and the status of objects at current time (`status`)." See [[concepts/spec-status-split]], [[concepts/conditions]], and [[concepts/operator-pattern]].

### Schema, pruning, and validation

- A structural schema is a constrained subset of OpenAPI v3 that enables validation, pruning, and defaulting. Plain OpenAPI describes what must be present but not what is forbidden, so unknown fields previously leaked into storage, and structural schemas bring CRDs closer to the rigor of built-in types. URL: https://kubernetes.io/blog/2019/06/20/crd-structural-schema/. Quote: "By the nature of OpenAPI specifications though—only describing what must be there, not what shouldn't, and by being potentially incomplete spec". See [[findings/unknown-fields-are-silently-pruned-under-structural-schemas]].
- The task page for writing a CRD covers a minimal manifest (group, scope, names, versions, `openAPIV3Schema`), pruning with the `x-kubernetes-preserve-unknown-fields` escape hatch, CEL validation rules, defaulting, validation ratcheting, the `/status` and `/scale` subresources, finalizers, and additional printer columns. The dossier read about 100,000 of 170,000 characters, so categories, short names, and deeper CEL details were not reviewed. URL: https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/. See [[examples/hpa-scales-any-workload-through-the-scale-subresource]] and [[concepts/finalizers]].
- CEL rules in `x-kubernetes-validations`, such as `self.minReplicas <= self.maxReplicas`, express cross-field validation inside the schema. The announced benefits are no webhook to run, less operational risk, and per-rule cost limits that protect the apiserver. The dossier did not read the feature-gate history or transition rules. URL: https://kubernetes.io/blog/2022/09/23/crd-validation-rules-beta/. Quote: "Validation rules make it possible to declare how custom resources are validated using the Common Expression Language (CEL)." See [[examples/cel-rule-replaces-a-validating-webhook-for-cross-field-checks]], [[comparisons/cel-validation-rules-versus-validating-webhooks]], and [[concepts/admission-webhooks-and-cel]].

### Versions, conversion, and migration

- `served` and `storage` are separate flags, and only one version is the storage version. The documented lifecycle is to add a version, migrate data, deprecate the old version, and remove it, and the page tells readers to check `status.storedVersions` before dropping an old version from the spec. Conversion is `None`, which changes only `apiVersion`, or `Webhook`, which calls a service using `conversionReviewVersions` and a `caBundle`. The dossier read about 100,000 of 139,000 characters, and the fetch returned a paraphrase with no verbatim quote. URL: https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning/. See [[concepts/crd-versioning-and-storage-migration]] and [[comparisons/crd-conversion-strategies-none-webhook-and-hub-and-spoke]].
- The Kubebuilder book describes the hub-and-spoke pattern, in which one version is the hub and every other version converts only to and from it, so N versions need roughly 2(N-1) conversion functions instead of pairwise conversions. This is the practical way controller-runtime projects implement conversion webhooks. A multi-version tutorial follows in the same book but was not read. URL: https://book.kubebuilder.io/multiversion-tutorial/conversion-concepts.html. Quote (paraphrased by the fetch tool): "Mark one version as the 'hub', and all other versions just define conversion to and from the hub". See [[examples/kubebuilder-hub-and-spoke-conversion-for-multi-version-crds]] and [[entities/kubebuilder]].
- The built-in StorageVersionMigration API and controller graduated to GA and are on by default in Kubernetes v1.37. A user creates a `StorageVersionMigration` object naming a resource, and the controller rewrites stored objects to the current storage version, which closes a gap that operators previously filled with their own migrators. The dossier did not verify the exact fields or whether migration triggers automatically, and it advises checking the release notes before relying on the details. URL: https://kubernetes.io/blog/2026/08/31/kubernetes-v1-37-storage-version-migration-ga/. Quote: "Storage version migration has graduated to General Availability (GA) in Kubernetes v1.37". See [[concepts/crd-versioning-and-storage-migration]].

### Platform tools that generate or deliver CRDs

- A Crossplane XRD is a schema from which Crossplane generates a CRD for a composite resource and, in older modes, a claim CRD. Scope can be Namespaced (the default in v2), Cluster, or LegacyCluster, multiple API versions are allowed, and breaking schema changes need conversion webhooks. Documented pitfalls are that schema changes may need a Crossplane pod restart and that group or names cannot change after creation. The v1.14 URL returned 404, so the "latest" documentation was read and details may differ by version. URL: https://docs.crossplane.io/latest/composition/composite-resource-definitions/. Quote: "XRDs define the names, data types, and required parameters for a custom API schema following OpenAPIv3 standards." See [[comparisons/crossplane-xrds-versus-kro-resourcegraphdefinitions-as-crd-generators]] and [[entities/crossplane]].
- In kro, applying a ResourceGraphDefinition makes kro validate it, generate and register a CRD, and run a dynamic controller for instances. Dependencies are inferred from CEL expressions, resources are created in topological order, and errors are caught at definition time, with no separate composition language. URL: https://kro.run/docs/concepts/rgd/overview/. Quote: "kro generates a CustomResourceDefinition for your API and registers it with the Kubernetes API server." See [[entities/kro]].
- Flux documents `spec.install.crds` and `spec.upgrade.crds` on a HelmRelease with the policies Skip, Create (the default), and CreateReplace. CreateReplace updates existing CRDs but does not delete removed ones, and Flux recommends `dependsOn` so that CRDs and their controllers exist before dependent releases. The dossier read about 100,000 of 130,000 characters. URL: https://fluxcd.io/flux/components/helm/helmreleases/. Quote: "Helm has no native support for upgrading or deleting CRDs using Helm due to unintentional data loss dangers." See [[examples/flux-helmrelease-crd-policies-createreplace-and-dependson]] and [[findings/helm-does-not-upgrade-or-delete-crds]].
- An Argo CD helm chart issue reports that the ApplicationSets CRD grew so large that the `last-applied-configuration` annotation exceeded the 262,144-byte annotation limit, so client-side apply failed. The workarounds are the `ServerSideApply=true` sync option and, for Kustomize, `ClientSideApplyMigration=false`. URL: https://github.com/argoproj/argo-helm/issues/3704. Quote: "The ApplicationSets CRD is invalid: metadata.annotations may not be more than 262144 bytes". See [[examples/argo-cd-applicationsets-crd-too-large-for-client-side-apply]] and [[findings/large-crds-exceed-the-client-side-apply-annotation-limit]].
- Deleting a CRD deletes all of its custom resources, which is why tools are cautious about CRD removal. The dossier calls this standard Kubernetes behavior but did not see it stated verbatim in the pages read, so the wiki records it as unverified by this source. See [[findings/deleting-a-crd-deletes-every-custom-resource-of-that-kind]].

### Failure modes and scale

- When a CRD's conversion webhook service is unavailable, the garbage collector in kube-controller-manager can fail to sync its cache, and cascading deletes then stop, for example a Deployment is deleted while its ReplicaSets and Pods remain. The issue was closed as a duplicate of #101078, with the proposed direction being to let the garbage collector work with partial informer sync. URL: https://github.com/kubernetes/kubernetes/issues/110720. Quote (as returned, likely a typo for "not working"): "When the webhook service is down, the GC of controller-manager to be still working." See [[findings/a-down-conversion-webhook-can-stall-garbage-collection]].
- The k8s.af failure-story index lists admission webhook outages as a recurring failure class, including a 2019 Jetstack post and an Airbnb KubeCon NA 2020 talk citing a mutating admission webhook in outages. The dossier did not open the linked posts, so these are index-level claims only and are not CRD-specific. URL: https://k8s.af/. Quote (index entry text): "ValidatingWebhookConfiguration caused prolonged downtime, nodes lost, and failed master upgrades". See [[findings/admission-webhook-outages-are-a-recurring-failure-class]].
- Ant Group's write-up on a 10,000-plus node cluster describes serving lists from the apiserver watch cache (memory from roughly 400 GB to 100 GB), dynamic watch cache sizing, label indexing, retry tuning, and etcd splitting. It is not about CRDs specifically, but custom resources share the same storage and watch paths, so the bottlenecks it addresses are the ones that large custom resource counts hit. URL: https://segmentfault.com/a/1190000040750768/en. Quote: "All problems in computer science can be solved by another level of indirection, except for too many layers of indirection and performance problems." See [[examples/ant-group-large-cluster-tuning-of-apiserver-watch-cache-and-etcd]].
