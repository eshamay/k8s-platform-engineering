## Summary

The dossier explains that a status condition is one entry in a resource's `.status.conditions` list: a record with a `type`, a `True`, `False`, or `Unknown` status, a machine-readable `reason`, a human-readable `message`, a `lastTransitionTime`, and an optional `observedGeneration`. The list behaves like a map keyed by `type`, and conditions complement the detailed status fields without replacing them. KEP-1623 produced the shared `metav1.Condition` type because earlier APIs each invented their own shape, but adoption is voluntary, so older APIs keep theirs.

The dossier argues that `observedGeneration` is what makes a condition trustworthy, and that most real failures come from the gap between a partly standardized contract and the generic tools that consume it. It surveys how six stacks use conditions differently: Crossplane (`Synced` and `Ready`), ACK (`ResourceSynced`, `Terminal`, `Recoverable`), Config Connector (a single `Ready`), Flux (`Ready`, `Reconciling`, `Stalled`), kro (author-defined conditions in CEL), and Cluster API (`Available` beside `Ready`). Its pitfalls are stale or missing `observedGeneration`, premature readiness on new objects, abnormal-true polarity that hides a dead controller, summary conditions that mask in-flight work, an all-powerful `Ready`, and heartbeat writes to `lastTransitionTime`.

See [concepts/conditions](../concepts/conditions.md) for the synthesized concept and [concepts/spec-status-split](../concepts/spec-status-split.md) for the surrounding status model.

## Key claims

### Conventions and shared types

- Condition type names should be short PascalCase adjectives or past-tense verbs that describe observed state, the list is treated as a map keyed by `type`, and no condition is equivalent to `Unknown`. Controllers should report conditions on first visit, even as `Unknown`, to show they have started work. URL: https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md. Quote: "A negative condition like 'MemoryExhausted' may be easier for humans to understand than 'SufficientMemory.'" Only the first 100 KB was read. See [concepts/conditions](../concepts/conditions.md).
- Polarity is left to authors, with advice that humans should find the name easy to read, so `Ready` or `Succeeded` is preferred over `Failed`, and a top-level summary condition is recommended for long-running objects. Same URL. See [findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions](../findings/condition-polarity-guidance-conflicts-between-kstatus-and-the-api-conventions.md).
- KEP-1623 created `metav1.Condition` because existing APIs had inconsistent schemas and serialization. It makes `lastTransitionTime` and `reason` required, ships helpers such as `SetStatusCondition` and `FindStatusCondition`, and makes `observedGeneration` a non-pointer integer because `metadata.generation` is never zero. URL: https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/1623-standardize-conditions/README.md. Quote: "LastTransitionTime is required. Some current implementations allow this to be missing, but this makes it difficult for consumers." Adoption is voluntary. See [comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api](../comparisons/condition-vocabularies-across-crossplane-ack-config-connector-flux-kro-and-cluster-api.md).
- A Medium explainer says generation is a monotonically increasing number bumped on every spec update, that status can lag or go stale after a controller restart because spec and status are written by different actors, and that StatefulSet and `kubectl rollout status` are the model to copy. URL: https://alenkacz.medium.com/kubernetes-operator-best-practices-implementing-observedgeneration-250728868792. Quote: "Generation is a monotonically increasing number that gets bumped every time you update your resource." The scraper returned empty content, so the page was fetched with WebFetch. See [findings/missing-observedgeneration-hides-stale-status](../findings/missing-observedgeneration-hides-stale-status.md).
- A tutorial for controller authors says to evaluate conditions on every reconcile, use `meta.SetStatusCondition`, set `observedGeneration`, and pair `Ready` with `Available` and `Progressing`. It lists vague messages, too many conditions, inconsistent types across CRDs, a missing `observedGeneration`, and bumping `lastTransitionTime` on every loop as pitfalls. URL: https://oneuptime.com/blog/post/2026-02-09-crd-status-conditions-conventions/view. This is a secondary vendor blog, explanatory and not authoritative. See [findings/updating-lasttransitiontime-on-every-reconcile-turns-a-condition-into-a-heartbeat](../findings/updating-lasttransitiontime-on-every-reconcile-turns-a-condition-into-a-heartbeat.md).

### Generic consumers

- kstatus computes InProgress, Failed, Current, Terminating, NotFound, and Unknown, and defines the standard `Reconciling` and `Stalled` conditions under the abnormal-true pattern. It names the pattern's weakness and fixes it with `observedGeneration`, falls back to `Ready` for types without those conditions, and lists corner cases: a `Ready` condition that only appears once `True` is invisible, and a controller that has not yet written conditions is treated as reconciled. URL: https://github.com/kubernetes-sigs/cli-utils/blob/master/pkg/kstatus/README.md. Quote: "If the controller is not running... it will look like it is in a good state when that is not true." See [findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy](../findings/abnormal-true-polarity-makes-a-stopped-controller-look-healthy.md) and [entities/kstatus](../entities/kstatus.md).
- A brand-new Cluster API resource with no `status.conditions` and `observedGeneration` equal to `generation` is judged ready by kstatus before the controller acts, so Flux can start dependents too early. A suggested workaround defaulted `observedGeneration` to -1 with a kubebuilder default marker, and the issue became moot when Cluster API changed its conditions, because Flux uses CEL health checks for Cluster API resources. URL: https://github.com/kubernetes-sigs/cluster-api/issues/9299. Quote: "Custom resources without status are considered ready by kstatus, while Kubernetes built-in resources handle this differently." See [findings/premature-readiness-in-kstatus-based-tools](../findings/premature-readiness-in-kstatus-based-tools.md) and [examples/cluster-api-readiness-gates-flux-dependents](../examples/cluster-api-readiness-gates-flux-dependents.md).
- Flux's kustomize-controller reports `Ready`, `Reconciling`, and `Stalled` plus `observedGeneration`, waits for applied resources to become healthy using kstatus for compatible custom resources, and accepts `healthCheckExprs` CEL expressions for those that do not follow kstatus. Health gating drives `dependsOn` ordering. URL: https://fluxcd.io/flux/components/kustomize/kustomizations/. Quote: "CEL expressions define custom logic for performing health checks on custom resources." Only the first 100 KB was read. See [entities/flux](../entities/flux.md) and [examples/flux-dependson-and-health-checks-gate-rollout](../examples/flux-dependson-and-health-checks-gate-rollout.md).
- Argo CD assigns each resource Healthy, Progressing, Degraded, Suspended, Missing, or Unknown, takes the worst health among an application's immediate children, and needs custom Lua checks (`resource.customizations.health.<group>_<kind>`) for CRDs because status formats are not standardized. URL: https://argo-cd.readthedocs.io/en/stable/operator-manual/health/. Quote: "The App health will be the worst health of its immediate child resources." See [examples/argo-cd-rolls-up-child-health-with-lua-checks](../examples/argo-cd-rolls-up-child-health-with-lua-checks.md) and [findings/generic-gitops-agents-cannot-judge-custom-resource-health](../findings/generic-gitops-agents-cannot-judge-custom-resource-health.md).
- Deployments publish `Progressing`, `Available`, and `ReplicaFailure` conditions plus `observedGeneration`, and `progressDeadlineSeconds` (default 600) leads to `Progressing=False` with reason `ProgressDeadlineExceeded` when a rollout stalls, which is how `kubectl rollout status` knows to fail. URL: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/. Only the first 100 KB was read. See [examples/deployment-progress-deadline-sets-progressing-false-for-a-stalled-rollout](../examples/deployment-progress-deadline-sets-progressing-false-for-a-stalled-rollout.md).

### Platform and cloud controllers

- Crossplane managed resources use `Ready` (reasons `Available`, `Creating`, `Unavailable`, `Deleting`) for whether the external resource is operational and `Synced` (reasons `ReconcileSuccess`, `ReconcileError`, `ReconcilePaused`) for whether the provider's reconcile succeeded. `Synced=False` points to credentials, configuration, or provider problems, while `Ready=False` with `Synced=True` points to the cloud-side resource, and Upjet-based providers add an `AsyncOperation` condition. URL: https://docs.crossplane.io/v1.20/concepts/managed-resources/. Quote: "Provider created and is monitoring the managed resource" (the description of `ReconcileSuccess`). The dossier read only a summary of the v1.20 page. See [entities/crossplane](../entities/crossplane.md) and [examples/crossplane-database-claim-reports-synced-and-ready](../examples/crossplane-database-claim-reports-synced-and-ready.md).
- During a 60-plus-minute MSK cluster update the Upjet-based provider reported "up to date", and crossplane-runtime overwrote the pending state with `ReconcileSuccess`, so alerts on `Synced=False` never fired and automation polling `Synced` saw false convergence. An `AsyncOperation=False/Ongoing` condition exists but is outside normal alert conventions, and the fix needs changes in both upjet and crossplane-runtime. URL: https://github.com/crossplane-contrib/provider-aws/issues/2287. See [findings/a-summary-condition-can-stay-true-while-a-long-async-operation-is-running](../findings/a-summary-condition-can-stay-true-while-a-long-async-operation-is-running.md) and [examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update](../examples/crossplane-synced-stays-true-through-a-sixty-minute-async-msk-update.md).
- ACK uses `ACK.Recoverable` for transient errors such as throttling, `ACK.Terminal` for errors that need a spec change, `ACK.ResourceSynced` for whether the AWS resource matches the spec, `ACK.Adopted` for adopted resources, `ACK.ReferencesResolved` for resolved cross-resource references, and `Ready` as the top-level indicator. URL: https://aws-controllers-k8s.github.io/docs/concepts/. Quote: "Unrecoverable error - spec must be updated before sync can continue." See [examples/ack-splits-terminal-and-recoverable-errors-into-separate-conditions](../examples/ack-splits-terminal-and-recoverable-errors-into-separate-conditions.md) and [entities/ack](../entities/ack.md).
- Config Connector uses one `Ready` condition: `Ready=False` with reason `Updating` while it calls Google APIs (the message names the first changed field), `Ready=True` with reason `UpToDate`, and `Ready=False` with reason `UpdateFailure` carrying the error. Only one `Ready` entry exists at a time, `observedGeneration` is set on status update, and the design document floats putting long-running operation IDs in the reason so work can resume after a controller restart. URL: https://github.com/GoogleCloudPlatform/k8s-config-connector/blob/master/docs/designs/reconcile-status.md. Quote: "Resource is up to date" (the message for `Ready=True`, reason `UpToDate`). This is a design document, so the dossier does not say which parts shipped. See [examples/config-connector-ready-condition-moves-through-updating-uptodate-and-updatefailure](../examples/config-connector-ready-condition-moves-through-updating-uptodate-and-updatefailure.md) and [entities/config-connector](../entities/config-connector.md).
- kro's ResourceGraphDefinition reference (v0.10.0) documents `readyWhen` (CEL expressions that decide when a child counts as ready, defaulting to "exists"), `includeWhen`, and the RGD's own conditions such as `Ready`, `GraphAccepted`, `KindReady`, and `ControllerReady`, and it says each condition's `observedGeneration` is the generation the condition was based on, so generation 12 against 9 means the condition is stale. URL: https://kro.run/api/crds/resourcegraphdefinition/. Quote: "If not specified, the resource is considered ready when it exists." See [examples/kro-rgd-authors-define-instance-conditions-with-cel-and-readywhen](../examples/kro-rgd-authors-define-instance-conditions-with-cel-and-readywhen.md) and [entities/kro](../entities/kro.md).
- When an RGD author declares custom conditions with CEL (`runtime.newCondition()`), kro hides its four built-in conditions and the author owns the whole surface, including composing a `Ready` from kro's `ResourcesReady` plus domain signals. Expression errors set `state: Error` and keep the previous conditions. URL: https://kro.run/docs/concepts/rgd/status-conditions/. Quote: "only the author's conditions appear on `.status.conditions[]`." The kro Instances page returned no usable content, so instance built-in condition names are inferred. See [comparisons/provider-fixed-versus-author-defined-condition-semantics-crossplane-versus-kro](../comparisons/provider-fixed-versus-author-defined-condition-semantics-crossplane-versus-kro.md).
- Cluster API abandoned its custom condition model (a mandatory `Ready` that summarized everything, a custom `Severity` field, divergence from the API conventions) for `metav1.Condition`, added `Available` as a separate signal, and added operation conditions such as `ScalingUp` and `Remediating`. URL: https://github.com/kubernetes-sigs/cluster-api/blob/main/docs/proposals/20240916-improve-status-in-CAPI-resources.md. Quote: "higher level abstractions in Cluster API are designed to remain operational during lifecycle operations." About 95 percent of the page was read. See [examples/cluster-api-adds-available-and-operation-conditions-beside-ready](../examples/cluster-api-adds-available-and-operation-conditions-beside-ready.md) and [findings/one-mandatory-ready-condition-that-summarizes-everything-is-too-rigid](../findings/one-mandatory-ready-condition-that-summarizes-everything-is-too-rigid.md).

### Open points the dossier records

- The Crossplane page read was v1.20, so condition behavior in Crossplane v2 and the fix status of the upjet and crossplane-runtime signaling problem were not confirmed.
- kstatus favors abnormal-true (`Reconciling` and `Stalled`) while the Cluster API proposal and the Kubernetes conventions lean toward positive `Ready` and `Available`, and the sources leave the choice to authors. See [decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types](../decisions/choose-abnormal-true-or-positive-polarity-for-new-condition-types.md).
- Whether `observedGeneration` belongs at the top level, per condition, or both is not settled: the conventions allow either, KEP-1623 puts it on each condition, and kstatus checks the top-level field. See [comparisons/observedgeneration-top-level-versus-per-condition](../comparisons/observedgeneration-top-level-versus-per-condition.md).

## Correction note (2026-11-26)

Two claims in this summary were corrected by [sources/research-gap-m3-status-conditions](research-gap-m3-status-conditions.md). Config Connector's shipped failure reason is `UpdateFailed`, not the design document's `UpdateFailure`, and its first-field-path message was not found in code. The original summary above is left as written for provenance.
