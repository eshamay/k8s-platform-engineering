## Summary

The dossier explains that a Crossplane managed resource is a Kubernetes object that stands for exactly one external thing, such as an S3 bucket or a Cloud SQL instance. The object lives in the Kubernetes API, the real thing lives in a provider's system, and a provider controller reconciles the two. Every managed resource has the same skeleton: `spec.forProvider` is the authoritative desired state, `spec.initProvider` holds values applied only at creation, `status.atProvider` records what the provider last observed, and the `crossplane.io/external-name` annotation says which external resource the object maps to. Two independent conditions, `Synced` and `Ready`, diagnose different failures.

The central safety and import lever is `spec.managementPolicies`, a list of the verbs Crossplane may perform (Observe, Create, Update, Delete, LateInitialize, or `*` for all). An Observe-only list gives read-only import, a list without Delete gives "manage but orphan on delete", and an empty list pauses reconciliation. The dossier compares this explicit list with Config Connector's acquire-by-name behavior and `abandon` annotation, with ACK's read-only annotation, and with Flux prune controls. It also records two costs of the model: deleting the Kubernetes object deletes the cloud resource by default, and one CRD per external resource type pushes API server discovery and OpenAPI computation to their limits, which Crossplane v2 answers with managed resource definitions and activation policies.

See [[concepts/managed-resource]] for the synthesized concept and [[entities/crossplane]] for the tool.

## Key claims

### Anatomy and management policies

- A managed resource is the in-cluster object and the external resource is the real object in the provider. `spec.forProvider` is authoritative, `spec.initProvider` applies only at creation (useful for fields that something else later changes, such as autoscaled counts), and `status.atProvider` is the last observation. Crossplane writes create-pending, succeeded, and failed annotations so an interrupted create does not leak a resource. URL: https://docs.crossplane.io/latest/managed-resources/managed-resources/. Quote: "Crossplane calls the object inside Kubernetes a managed resource and the external object inside the Provider an external resource." Read through a summarizing fetch. See [[concepts/managed-resource]] and [[examples/crossplane-initprovider-lets-an-autoscaler-own-node-group-size]].
- The management policy table lists `*`, Create, Delete, Observe, Update, and LateInitialize, and an empty array pauses reconciliation. The `Ready` reasons are Creating, Available, Deleting, and Unavailable, and the `Synced` reasons are ReconcileSuccess, ReconcileError, and ReconcilePaused. The `crossplane.io/paused: "true"` annotation also pauses, and `ClusterProviderConfig` is the cluster-wide counterpart of the namespaced `ProviderConfig`. Same URL. See [[comparisons/observe-only-and-keep-controls-across-crossplane-config-connector-and-ack]].
- Crossplane keeps immutable fields unchanged and does not delete and recreate the resource as Terraform does, so a change to such a field may simply not apply. Same URL. See [[findings/crossplane-does-not-delete-and-recreate-to-change-immutable-fields]].
- The provider-development guide describes the `managed.Reconciler` phases (Connect, Observe, Create, Update, Delete) and the five-method `managed.ExternalClient` interface. It stresses idempotency, late initialization of output-only fields, and publishing connection details. The page lacks the Disconnect step and newer features, so specifics need verification. URL: https://github.com/crossplane/crossplane/blob/main/contributing/guide-provider-development.md. Quote: "Delete implementations must not return an error when asked to delete a non-existent external resource." See [[examples/provider-authors-implement-an-external-client-behind-the-shared-managed-reconciler]].

### Import and observe-only

- The import guide uses a GCP DatabaseInstance: set `managementPolicies: ["Observe"]`, add the external-name annotation matching the provider-side name, pick a Kubernetes object name, and add a `forProvider` field such as region if names collide. After apply `status.atProvider` fills in, and taking control means changing policies to `["*"]` after manually copying needed values from `atProvider` into `forProvider`. The page labels management policies a beta feature that providers must support. URL: https://docs.crossplane.io/latest/guides/import-existing-resources/. Quote: "Crossplane imports observe only resources but never changes or deletes the resources." See [[examples/crossplane-import-of-an-existing-gcp-database-observes-first-then-takes-control]] and [[findings/observe-based-import-has-manual-copy-steps-ambiguous-names-and-relaxed-validation]].
- The observe-only design document says the motivation was to reference and monitor existing cloud resources owned by other tools, which earlier needed workarounds such as provider-terraform or provider-kubernetes. The original proposal had FullControl, OrphanOnDelete, and ObserveOnly modes, and the shipped feature generalized them into a list. Risks it lists are conflicts between deletionPolicy and managementPolicy, required-field validation that must be relaxed for observation (through CEL), and disabled late initialization. A separate data-source-style type was rejected because it would double CRD counts. URL: https://github.com/crossplane/crossplane/blob/main/design/design-doc-observe-only-resources.md. Quote: "Crossplane will only observe the external resource and will not make any changes or deletions." See [[decisions/choose-management-policies-for-an-imported-resource]] and [[examples/an-observe-only-managed-resource-lets-a-composition-read-a-database-owned-by-another-team]].
- A consultancy blog recommends a three-part safety recipe for adopting AWS resources (external-name, deletionPolicy Orphan, ObserveOnly) and lists pitfalls: drift correction of accidental manual changes, importing before a resource is fully provisioned, deletion of production infrastructure if YAML is removed without orphan protection, and IAM or ProviderConfig gaps. It uses v1-era terms, is vendor-authored, and names no customers. URL: https://www.cloudkeeper.com/insights/blog/onboarding-aws-crossplane-importing-rds-s3-and-eks-safely. Quote: "Always start with ObserveOnly when adopting existing infrastructure". See [[findings/older-observeonly-and-deletionpolicy-advice-needs-translation-to-managementpolicies]].

### Operating managed resources

- The OnCallReady lesson is the clearest ramp-up read in the dossier. It tabulates `Synced` and `Ready` combinations, documents error prefixes (connect, observe, create, update, delete failed), notes asynchronous upjet operations and the finalizer `finalizer.managedresource.crossplane.io`, and says namespaced v2 managed resources have no `deletionPolicy`, so "everything except Delete" is the v2 orphan idiom. It also says deletion hangs if the provider is gone and that removing the finalizer by hand orphans the real resource. URL: https://oncallready.dev/learn/platform-engineering-backstage-and-crossplane/managed-resources-synced-ready-external-names-and-policies/. Quote: "Synced False with Ready True means the thing exists but Crossplane can no longer manage it." See [[findings/synced-false-with-ready-true-is-a-silent-failure-where-drift-correction-stops]] and [[findings/forcing-a-finalizer-off-skips-cleanup-and-can-leak-billing-resources-or-corrupt-data]].
- A Usage object marks one resource as in use, optionally by another, and blocks deletion of the used resource until its users are gone. Its fields are `of`, `by`, `reason`, and `replayDeletion`. It gives deletion ordering (do not delete a database subnet before the database) and accidental-deletion protection, and complements `managementPolicies` as a second guardrail. URL: https://docs.crossplane.io/latest/managed-resources/usages/. Quote: "Deletion ordering by ensuring that a resource isn't deleted before the deletion of its dependent resources." See [[examples/crossplane-usages-order-deletion-and-guard-against-accidental-removal]].

### Other tools' answers to the same ownership question

- Config Connector acquires an existing Google Cloud resource when the manifest name or ID matches it, so import is implicit. Deleting the Kubernetes object deletes the cloud resource by default, and the annotation `cnrm.cloud.google.com/deletion-policy: abandon` must be set before deletion to keep it. URL: https://docs.cloud.google.com/config-connector/docs/how-to/managing-deleting-resources. Quote: "To keep the Google Cloud resource, add the following to the Config Connector resource YAML before deleting". Read through a summarized fetch. See [[entities/config-connector]].
- ACK offers the annotation `services.k8s.aws/read-only: "true"`: the controller syncs status from AWS, ignores spec, never creates, updates, or deletes, and shows an error if the AWS resource is missing. ACK's separate adoption feature gives full management, which mirrors the observe-versus-adopt split in Crossplane. URL: https://aws-controllers-k8s.github.io/docs/guides/readonly/. Quote: "ACK will sync the resource status from AWS but will never create, update, or delete the underlying AWS resource." See [[entities/ack]] and [[examples/ack-adopt-or-create-brings-existing-aws-resources-under-management]].
- Flux Kustomization with `spec.prune: true` deletes objects that disappeared from Git, tracked through `.status.inventory`. The annotation `kustomize.toolkit.fluxcd.io/prune: disabled` exempts an object, and `spec.deletionPolicy` (MirrorPrune, Delete, WaitForTermination, Orphan) governs what happens when the Kustomization itself is deleted. For managed resources, a Git removal becomes a prune of the object followed by a provider delete of the cloud resource, unless Delete is excluded from `managementPolicies`. Only the first 100,000 of about 121,000 characters were read. URL: https://fluxcd.io/flux/components/kustomize/kustomizations/. Quote: "Garbage collection means that the Kubernetes objects that were previously applied on the cluster but are missing from the current source revision, are removed from the cluster automatically." See [[entities/flux]] and [[findings/unintended-deletion-through-prune]].
- Crossplane's Argo CD guide says to use annotation-based resource tracking because label tracking conflicts with Crossplane's own labels on composed resources, to add custom Lua health checks that read `Ready` and `Synced`, to hide ProviderConfigUsage objects, and to raise `ARGOCD_K8S_CLIENT_QPS` (to 300) as CRDs multiply. URL: https://docs.crossplane.io/latest/guides/crossplane-with-argo-cd/. Quote: "Argo CD synchronizes Kubernetes resource manifests stored in a Git repository with those running in a Kubernetes cluster (GitOps)." See [[examples/crossplane-resources-hosted-by-argo-cd]] and [[entities/argo-cd]].

### Scale cost of one CRD per external resource type

- A GitHub issue reports that installing 100-plus CRD Terrajet-based providers made API servers slow: OpenAPI recomputation on each CRD registration and client discovery limits (about 20 requests per second with a 30 burst) were the root causes. Reported outcomes include GKE control planes unresponsive at about 680 CRDs, `kubectl` taking more than 14 seconds, Rancher slowness, and a second large provider taking about 70 minutes to install against 20 for the first. URL: https://github.com/crossplane/crossplane/issues/2649. See [[findings/one-crd-per-external-resource-type-overloads-api-server-discovery-and-openapi-computation]].
- Upbound's engineering blog estimates roughly 2,000 CRDs for AWS, Azure, and GCP together, with more than 4 MiB of API server memory per CRD and about 300 API group-versions needing discovery requests. It lists upstream fixes: discovery rate limit increases (Kubernetes 1.22 and later), a checksum-based client cache in place of fsync, lazy OpenAPI computation (1.23 and later), and consolidated etcd client logging (1.25 and later). URL: https://www.upbound.io/blog/scaling-kubernetes-to-thousands-of-crds. Quote: "Each time a CRD was added or updated the API server was doing serialization work that became more expensive." See [[concepts/custom-resource-definition]].
- Crossplane v2 represents each managed resource type as a ManagedResourceDefinition and uses ManagedResourceActivationPolicies with exact or prefix-wildcard patterns to activate only the types a cluster needs. Providers that implement "safe-start" can activate definitions on demand. This is the official answer to the scale problem above. URL: https://docs.crossplane.io/latest/managed-resources/managed-resource-activation-policies/. See [[examples/crossplane-managed-resource-activation-policies-install-only-the-resource-types-a-cluster-needs]].

### Adopters and use cases

- The Crossplane adopters list is self-reported: Nike (internal developer platform managing thousands of resources), Autodesk (unified control plane), SAP (100-plus KRM control planes and thousands of managed resources as of February 2024), Deutsche Kreditbank (10-plus EKS clusters), IBM, Elastic, UiPath, VMware Tanzu, DB Systel (Deutsche Bahn, fully GitOps self-service), Nokia, and Akamai (provider-ceph orchestrating up to 200,000 managed resources). Entries are one-line claims and not verified case studies. URL: https://github.com/crossplane/crossplane/blob/main/ADOPTERS.md. Quote: "Crossplane powers the internal developer platform managing thousands of resources from development to production." See [[examples/crossplane-adopters-report-managed-resource-counts-from-thousands-to-two-hundred-thousand]].
- The dossier names three dominant scenarios: internal developer platforms with managed resources as the lowest layer under compositions, brownfield adoption of existing RDS, S3, or Cloud SQL resources, and multi-tenant, multi-cluster operation with namespaced v2 managed resources paired with per-team ProviderConfigs.

### Open points the dossier records

- The import guide calls management policies beta while the managed resources page presents them as standard, and the current feature-lifecycle status was not read. See [[open-knowledge-gaps]].
- The mapping from the old `ObserveOnly` and `deletionPolicy` terms to the policy list is not spelled out in any page read.
- The default external name differs between sources (the object name for S3 in one, the Kubernetes object name in general in another), and per-provider variation is not documented in one place.
- Adoption and orphaning behavior in Cluster API, kro, and plain controller-runtime operators was not covered, and neither was the behavior of v2 namespaced managed resources when a namespace is deleted while the provider is down.
- Config Connector's conflict handling when two objects target one cloud resource is not documented in the pages read.
