## Summary

The dossier explains a composite resource as a platform-defined Kubernetes API that stands for a bundle of other resources. A user creates one small object, such as a `Database` or `WebApplication`, and a controller expands it into Deployments, Services, cloud buckets, IAM roles, or VPCs, keeps them reconciled, wires values from one child into another, reports aggregate readiness, and tears everything down in a sensible order. It is the ordinary controller pattern applied one level up, where the world being reconciled is a set of other API objects.

Crossplane and kro implement the idea differently. Crossplane splits it across objects: a CompositeResourceDefinition (XRD) declares the schema and becomes a CRD, and a Composition maps an instance of that API (the composite resource, or XR) onto composed resources through a pipeline of gRPC composition functions. In v1 a namespaced claim fronted a cluster-scoped XR, and in v2 XRs are namespaced and claims are gone for new-style XRDs. kro merges schema and implementation into one ResourceGraphDefinition (RGD), generates the CRD, registers a dynamic controller, infers a dependency graph from CEL expressions, and creates children in topological order. In March 2026 the Crossplane project shipped `function-kro`, which runs kro-style YAML and CEL inside a Crossplane pipeline step, so the two models now overlap.

The dossier frames the problem from the platform-team side: custom controllers are costly, client-side templating cannot use CRD benefits, and a stable versioned platform API protects users from provider features that could break compliance. Its pitfall catalog covers schema evolution, rolling out changes to live instances, late versus early error detection, template-language sprawl, ordering versus readiness, deletion semantics under GitOps, and version churn. See [[concepts/composite-resource]] and [[concepts/composition]] for the synthesized concepts, and [[entities/crossplane]], [[entities/kro]], and [[entities/function-kro]] for the tools.

## Key claims

### Crossplane composite resources and compositions

- An XR "represents a set of Kubernetes resources as a single Kubernetes object." It is created through a custom API that an XRD defines and a Composition configures, and the Composition is chosen by matching `compositeTypeRef` to the XRD's group and kind. Per-XR controls are `compositionRef`, `compositionSelector`, `compositionUpdatePolicy` (Automatic by default, or Manual), `compositionRevisionRef` and `compositionRevisionSelector` for pinning, the `crossplane.io/paused` annotation, a per-XR poll interval, and `crossplane.io/reconcile-requested-at` to force a reconcile. URL: https://docs.crossplane.io/latest/composition/composite-resources/. See [[concepts/composite-resource]] and [[decisions/choose-automatic-or-manual-composition-update-policy]].
- The same page documents an alpha deletion policy (Background, Foreground, Pipeline) and warns that Argo CD's default foreground deletion makes Crossplane ignore the policy and emit a warning event. The fix is the `PrunePropagationPolicy=background` sync option with a background finalizer, and a stuck Foreground or Pipeline deletion leaves the XR in Deleting until the finalizer is removed by hand. See [[findings/argo-cd-foreground-deletion-makes-crossplane-ignore-the-composite-deletion-policy]].
- An XRD is "like a Kubernetes custom resource definition" with fewer required fields plus Crossplane options (claims, connection secrets, defaults). Applying one makes Crossplane create a matching CRD. The XRD name must be `<plural>.<group>`, the convention is an `X` prefix on the kind, versions follow alpha, beta, and stable conventions, `group` and `names` cannot change without deleting the XRD, and at v1.20 a schema change needed a restart of the Crossplane pod. Defaults include `defaultCompositionRef`, `enforcedCompositionRef`, and `defaultCompositionUpdatePolicy`. URL: https://docs.crossplane.io/v1.20/concepts/composite-resource-definitions/ (older version, still the clearest walk-through). See [[findings/platform-api-schemas-are-contracts-and-breaking-changes-are-blocked-or-need-conversion]].
- "A Composition is a pipeline of composition functions." A Function is installed as a package and runs as a pod. Crossplane calls each step in order with the XR's current state and the state of the resources it owns, and the function returns what should exist. Named options are function-patch-and-transform, Go templating, CUE, KCL, Python, and custom functions in Go or Python. Functions do not run on deletion, so Crossplane deletes composed resources itself. URL: https://docs.crossplane.io/latest/composition/compositions/. See [[examples/a-composition-function-pipeline-turns-observed-state-into-desired-state]] and [[findings/composition-functions-add-moving-parts-that-must-be-healthy]].
- The composition functions design document says maintainers wanted to "Avoid organically growing a new configuration Domain Specific Language (DSL)," citing Brian Grant's writing on configuration complexity and noting that patch-and-transform was starting down that path. The proposal adds `mode: Pipeline` with an ordered array of steps, each calling a function over gRPC with a `RunFunctionRequest` that carries observed state and returns desired state. URL: https://github.com/crossplane/crossplane/blob/main/design/design-doc-composition-functions.md. See [[comparisons/crossplane-composition-functions-versus-kro-resource-graph-execution-models]].
- In v1, "Claims represents a set of managed resources as a single Kubernetes object, inside a namespace." A claim is a namespaced stand-in for a cluster-scoped XR, enabled through `claimNames` in the XRD, linked through `spec.resourceRef` on the claim and `spec.claimRef` on the XR, able to bind to pre-provisioned XRs, and delivering connection secrets to the claim's namespace through `writeConnectionSecretToRef`. The page says claims are unnecessary if you do not use namespaces. URL: https://docs.crossplane.io/v1.20/concepts/claims/. See [[examples/a-v1-crossplane-claim-fronts-a-cluster-scoped-composite-resource]] and [[comparisons/crossplane-v1-claims-versus-v2-namespaced-composite-resources]].
- The v2 upgrade guide removes native patch-and-transform (`mode: Resources`), ControllerConfig, external secret stores, XR-level connection details, and the default registry flag. It requires being on v1.20 and upgrading one minor version at a time, offers `crossplane beta upgrade check` and `crossplane beta convert pipeline-composition`, and introduces namespaced managed resources under `.m.` API groups and namespaced XRs. Quote: "There's no automated tooling yet to migrate existing v1 cluster-scoped XRs and MRs to v2 namespaced style." It warns against editing a live Composition that existing XRs use. URL: https://docs.crossplane.io/latest/guides/upgrade-to-crossplane-v2/. See [[findings/crossplane-v2-removed-features-and-offers-no-automated-migration-for-v1-composites]] and [[findings/editing-a-live-composition-can-disrupt-or-replace-existing-composed-resources]].
- The Crossplane blog by Markus Schweig (Upbound, 2023-10-06) argues that platform teams should expose well understood features behind their own versioned APIs instead of passing provider features straight through, and lists automated tagging, multi-tenant segregation for claims, external secret stores, GitOps, and short feedback loops as design principles. It describes a test-driven workflow with kind, Kuttl, and Skaffold in which each Kuttl run takes 2 to 5 minutes. The post predates v2 and is vendor-authored. URL: https://blog.crossplane.io/design-compositions-for-your-organizational-needs-with-crossplane/. See [[examples/a-platform-api-hides-provider-features-to-enforce-tagging-and-tenant-segregation]].

### kro resource graphs

- An RGD defines a new API and the resources behind it in one object, with `spec.schema` in SimpleSchema and `spec.resources` as templates with CEL expressions. kro validates it, generates and registers a CRD, and starts a dynamic controller. Static analysis at creation covers schema, existence of referenced kinds, CEL type checking, and dependency inference including cycle rejection. Quote: "kro performs extensive static analysis to catch errors before deployment." The computed order is in `status.topologicalOrder`, creation follows topological order and deletion follows the reverse, and the RGD conditions are Ready, GraphRevisionsResolved, GraphAccepted, KindReady, and ControllerReady. URL: https://kro.run/docs/concepts/rgd/overview/ (v0.10.0). See [[entities/kro]] and [[concepts/composite-resource]].
- Each spec change becomes an immutable GraphRevision. If the latest revision fails compilation, instances stop progressing and there is no fallback to an older revision. Breaking schema changes (field removal, type change, a new required field without a default, enum or pattern changes) are blocked unless the `kro.run/allow-breaking-changes` annotation is set. Same URL. See [[findings/a-kro-graph-revision-that-fails-compilation-stops-all-instances-with-no-fallback]] and [[comparisons/composition-revisions-versus-graph-revisions-for-rolling-out-platform-api-changes]].
- The FAQ says the controller verifies an RGD, creates a CRD, and deploys a dedicated micro-controller for instance events, and states "kro's API is currently at `v1alpha1`." It distinguishes an RGD from the newer alpha `Graph` (a namespaced object whose nodes are reconciled directly, disabled by default), gives the Argo CD recipe of an ownerReference plus an `argocd.argoproj.io/tracking-id` annotation on every templated resource, and shows a Helm-style checksum trick for restarting Deployments when a ConfigMap changes. URL: https://kro.run/docs/faq. See [[examples/kro-resources-need-owner-references-and-tracking-ids-to-be-tracked-by-argo-cd]].
- `readyWhen` is a list of CEL boolean expressions that define when one resource counts as ready: "`readyWhen` determines when **this specific resource** is ready." In an RGD, dependents wait until all dependencies are ready, which prevents using status values that do not exist yet. In the alpha Graph API it only reports health and a dependent is applied as soon as the fields it references exist. Expressions can reference only the resource itself, and the page teaches the optional `?` operator with `orValue`. URL: https://kro.run/docs/concepts/reconciliation/readiness. See [[findings/kro-readywhen-gates-dependents-in-a-resource-graph-definition-but-only-reports-health-in-the-alpha-graph-api]].
- The Amazon EKS user guide documents kro as a managed EKS capability. Its example composes ACK S3 Buckets with ConfigMaps and Deployments and passes ARNs from `status.ackResourceMetadata`. It explains SimpleSchema, the `${...}` CEL forms, optional access, ternaries, `includeWhen` (which can reference only `schema.spec`), and parallel creation of independent resources, and it stresses that "kro validates ResourceGraphDefinitions at creation time, not at runtime." URL: https://docs.aws.amazon.com/eks/latest/userguide/kro-concepts.html. See [[examples/the-eks-kro-capability-composes-ack-s3-buckets-with-deployments-and-config-maps]].
- The Google Cloud announcement by Abdel Sghiouar and Nic Slattery (2025-01-30) presents kro as a joint effort of Google Cloud, AWS, and Azure, says custom controllers or Helm-style templating are the alternatives, gives a GKE cluster API backed by Config Connector resources and a WebApp API as examples, says kro works with ACK, Config Connector, and Azure Service Operator, and states: "As an early-stage project, kro is not yet ready for production use". URL: https://cloud.google.com/blog/products/containers-kubernetes/introducing-kube-resource-orchestrator. See [[examples/self-service-gke-cluster-with-kro]].

### Convergence of the two models

- The function-kro announcement by Jared Watts (Upbound, 2026-03-19) says the function embeds kro's graph builder, CEL evaluator, and runtime so kro-style `resources` blocks drop into a Crossplane pipeline step unchanged. The example is a NetworkingStack API with a VPC, Subnet, and SecurityGroup wired by CEL, followed by a `function-auto-ready` step. The post lists what Crossplane adds: CompositionRevisions to pin and roll back, extra pipeline steps for policy or tagging, multiple Compositions behind one API, pause annotations, `crossplane render` for local testing, and `crossplane xrd generate --from simpleschema`. Quote: "One schema, many implementations." The claim of full feature parity is the project's own. URL: https://blog.crossplane.io/function-kro-yaml-cel/. See [[entities/function-kro]] and [[examples/function-kro-runs-a-kro-resource-graph-as-a-crossplane-pipeline-step]].
- A consultancy comparison by Ajeet Yadav (published 2026-06-26, updated 2026-09-19) places Helm (packaging, no reconciliation), kro ("kro is a CRD factory" over existing Kubernetes resources), and Crossplane (a control plane that owns external infrastructure) at different altitudes, and says to use kro when building blocks are already Kubernetes resources and Crossplane when you need to drive cloud APIs directly. It mentions a `LegacyCluster` fallback for v1-style XRDs, says IDPs often combine the tools, and cites kro v0.9.x where the kro docs show 0.10.0. URL: https://codingprotocols.com/blog/kro-vs-crossplane-vs-helm. Secondary evidence. See [[comparisons/helm-versus-kro-versus-crossplane-as-platform-abstraction-layers]] and [[decisions/choose-kro-crossplane-or-both-for-a-platform-abstraction-layer]].

### Other tools and adopters

- Cluster API's ClusterClass is "a powerful abstraction implemented on top of existing interfaces" that creates clusters with less boilerplate. A reusable class plus a small topology object expands into machine and infrastructure objects, gated by the `ClusterTopology` feature gate. The page read labels it experimental, which may be stale, and the linked CAEP was not read. URL: https://cluster-api.sigs.k8s.io/tasks/experimental-features/cluster-class/. See [[examples/cluster-api-clusterclass-expands-a-small-topology-into-many-machine-and-infrastructure-objects]] and [[entities/cluster-api]].
- The Crossplane adopters list names Renault (XRDs and compositions as an abstraction layer), Wellhub and Wildlife Studios (self-service platforms), Deutsche Kreditbank (more than 10 EKS clusters), Consensys (internal developer platform, a truncated row mentioning more than 1,000 resources), Autodesk (declarative API abstractions for a unified control plane), Grafana Labs (internal developer platform control plane), VSHN (the AppCat service catalog), Millennium bcp (self-service application lifecycle), Continental (self-service ephemeral vclusters), and Syntasso (Crossplane as a component of Kratix). Entries are brief, self-reported, and unaudited. URL: https://github.com/crossplane/crossplane/blob/main/ADOPTERS.md. See [[examples/crossplane-adopters-build-self-service-platforms-and-service-catalogs-on-composite-resources]].

### Open points the dossier records

- Claim support in v2 is not stated precisely by any primary page read, and the `LegacyCluster` detail comes from the third-party post. See [[open-knowledge-gaps]].
- The kro docs show 0.10.0 while the comparison blog says v0.9.x, and the status of the alpha `Graph` API versus RGD is still moving.
- No source covers Flux with XRs or RGD instances, no source covers Config Connector or ACK readiness or deletion semantics beyond their role as leaf providers, and the CAEP for ClusterClass was not read.
- The dossier found no public postmortem about a composite-resource outage, no KubeCon talk write-up, and no scale or performance numbers. A DeepWiki page on the RGD was skipped because of a rate-limit error, and Kubernetes core documentation was not fetched.
