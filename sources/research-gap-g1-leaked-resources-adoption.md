## Summary

The dossier asked two questions. The first is what happens when a controller loses the result of a cloud create call, so that a resource is leaked or duplicated. The second is what production teams see when a controller adopts an existing resource instead of requiring an explicit import.

On the first question the evidence is maintainer analysis plus user-reported incidents. Crossplane maintainer Nic Cope explains in issue 3037 why the `external-create-pending` annotation exists and which three leak scenarios it guards against. An ACK issue (3122) gives a timestamped CI reproduction of a duplicate VPC endpoint during a controller rollout, and an ACK audit (3177) counts 48 resources in 22 controllers where a lost create response duplicates the resource or wedges the custom resource. A provider-upjet-aws issue (2199) reports a stuck retry loop that cost about $155 over 15 days. The Crossplane opt-out for deterministic identifiers did ship in crossplane-runtime, but an open upjet issue says the upjet controllers do not set it.

On the second question the evidence is a catalog of reproduced failure modes, not a measured comparison. ACK `adopt-or-create` disables the only "already exists" guard, so two custom resources can overwrite one IAM role and deleting either deletes it. Config Connector acquisition of an existing bucket removed its encryption-enforcement configuration. No production comparison of the two policies was found, so the safer default remains a judgment, and the failure catalog supports caution about `adopt-or-create` as a default.

## Key claims

### Leaked and duplicated resources from ambiguous creates

- Crossplane writes `external-create-pending` before the create call, and an interrupted reconcile leaves the managed resource stuck so a human decides, in order to avoid creating a second VPC and leaking the first. VERIFIED. Crossplane issue 3037, opened 2022-04-08, maintainer negz: the guard "ensures that if creation was ambiguous that we stop and ask a human to intervene rather than potentially creating more infrastructure". https://github.com/crossplane/crossplane/issues/3037
- The maintainer lists three leak causes the annotations address: cloud-generated names that cannot be stored, eventually consistent APIs reporting that a resource does not exist, and stale cache reads of the managed resource. VERIFIED. Same issue, referencing docs PR 688 (merged 2024-02-01).
- The maintainer proposed letting resources with deterministic identifiers opt out, and said providers had no graceful shutdown handling for in-flight creates at the time. VERIFIED. https://github.com/crossplane/crossplane/issues/3037
- Reported triggers in the same thread are a normal Deployment rollout of the provider after a create that was failing on IAM errors, and a cluster upgrade that replaced all nodes (the second report was partly struck through by its author). VERIFIED as reporters' accounts.
- provider-terraform: if the pod is terminated during a multi-minute `terraform apply`, the update that writes the failed annotation fails on a cancelled context, so the pending annotation stays stuck. VERIFIED. crossplane-runtime issue 340, 2022-07-14. https://github.com/crossplane/crossplane-runtime/issues/340
- crossplane-runtime main contains `WithDeterministicExternalName(b bool)`. When the option is false the reconciler stops with "cannot determine creation result" instead of re-queuing, and when true the safeguard is skipped because "it is safe to re-queue a deterministically named resource." VERIFIED. https://github.com/crossplane/crossplane-runtime/blob/main/pkg/reconciler/managed/reconciler.go, read on 2026-11-26, with v2.4.4 the latest release listed (2026-11-24).
- provider-upjet-aws issue 2251 (2026-09-25, open) reports "Controllers don't set WithDeterministicExternalName", so S3 bucket sub-resources and IAM Policy, which have deterministic names, still wedge. The trigger was a dropped HTTP/2 connection to the API server under load, with about 500 S3 and IAM managed resources across 10 environments created in parallel. VERIFIED as the reporter's claim in an open issue, and the upjet template itself was not read. https://github.com/crossplane-contrib/provider-upjet-aws/issues/2251
- provider-upjet-aws issue 2199 (2026-08-18, open): a provider-aws-eks restart during the 30 to 60 second asynchronous create of a PodIdentityAssociation lost the external name, the next create got `409 ResourceInUseException`, and the provider retried about 3 to 4 times per minute. The reporter says each stuck resource cost about $12 per day in GuardDuty analysis of CloudTrail management events, "a 15-day, $155 anomaly across 7 stuck PIAs on two clusters". The report exists (VERIFIED) and the figures are SECONDARY-ONLY because they are the reporter's own estimate. A commenter reported the same for Kafka VPCConnection. The 409 prevented a duplicate, so this is a stuck retry loop and not a duplicate resource. https://github.com/crossplane-contrib/provider-upjet-aws/issues/2199
- ACK community issue 3122 (opened 2026-10-31 by sapphirew), about ec2-controller PR 398 and a CI build dated 2026-10-30: a controller restart during a Deployment rollout (RollingUpdate, leader election disabled) coincided with a second `CreateVpcEndpoint`. EC2 made two endpoints and only one was recorded, and the orphan blocked subnet deletion, so bootstrap teardown spent about 2 hours retrying `DeleteSubnet` with `DependencyViolation`. VERIFIED as the author's CI observation. The overlapping-pod cause is inferred, because Prow keeps only the surviving pod's logs, and an SDK retry of the token-less call would leave the same evidence. The stated root cause is no stable `ClientToken`. https://github.com/aws-controllers-k8s/community/issues/3122
- In the same issue maintainer knottnt cautioned that a stable token can break re-creation after out-of-band deletion, and suggested "Turn leader election on by default" and the Recreate deployment strategy (comment 2026-11-03). VERIFIED.
- ACK issue 3177 (2026-11-13, gecube) states that when a Create response is lost, "48 resources in 22 controllers either create a second AWS resource (28) or fail on every following reconcile" because the name is taken (20), with 12 more depending on undocumented behavior. VERIFIED as the audit's stated result. It is an author's code and documentation audit at main on 2026-11-13, not an observed incident count and not independently re-run. https://github.com/aws-controllers-k8s/community/issues/3177
- ACK runtime PR 292 (opened 2026-11-13, merged 2026-11-20) moves the status patch to immediately after Create. Its text says a controller stopped before that patch "left a resource in AWS whose identifier the CR did not have", a duplicate for server-generated IDs. VERIFIED. https://github.com/aws-controllers-k8s/runtime/pull/292
- ACK issue 3067 (2026-10-01, shrinedogg): Route 53 allows two public hosted zones with the same name, so a GitOps bootstrap that ran the controller on a throwaway cluster and then on the durable management cluster, with empty status on the second, "leaving one duplicate zone per name in the account". Maintainer knottnt said "we do want to allow creation of ACK resources to match what the service itself allows" and pointed to tag-based adoption work in runtime PR 261. VERIFIED as the reporter's account. https://github.com/aws-controllers-k8s/community/issues/3067
- Config Connector issue 648 (2022-04-05, v1.76.0): a MonitoringAlertPolicy with an invalid query returned HTTP 400 yet created a policy on each reconcile. A Config Connector engineer said "a policy resource will still be created nonetheless", attributing it to the GCP API. VERIFIED. https://github.com/GoogleCloudPlatform/k8s-config-connector/issues/648
- Crossplane issue 6260 (2025-02-01, closed, bobh66): in 1.17 cached unstructured reads let the composite reconciler "leak resources when it runs multiple reconciliations in a row", creating extra composed resources. VERIFIED as the reporter's analysis. These are Kubernetes objects and not cloud resources, but the mechanism is the same: a stale read followed by a second create. https://github.com/crossplane/crossplane/issues/6260

### Adopt-or-create versus explicit import

- ACK issue 3149 (2026-11-09; iam-controller v1.11.3, runtime v0.67.0, reproduced against moto and not real AWS): with `adopt-or-create`, a found resource is adopted without checking whether another custom resource manages it. A second CR with the same role name rewrote the role (seven mutating calls), each resync flips the trust policy between the two CRs, and "Both CRs report `ACK.ResourceSynced=True` and `Ready=True` with the same ARN". Deleting either CR deleted the role in 4 ms, and the surviving CR's next resync created a new role with a new role ID. The same CR without the annotation stops with a terminal "Resource already exists", so "the annotation turns off the only guard there is." VERIFIED as the author's reproduction. https://github.com/aws-controllers-k8s/community/issues/3149
- In the same reproduction a role created outside ACK and tagged `team=terraform` was adopted and "`UntagRole` removes `team=terraform`." The author notes this is the intended use but indistinguishable to the runtime from the bad cases, and that no misconfiguration is needed beyond one cluster and default settings. VERIFIED.
- ACK issue 3103 (2026-10-22): for the same "name already exists" case, Role gives a terminal error while Policy retries `EntityAlreadyExists` forever as recoverable, and `adopt-or-create` does not adopt a Policy unless the ARN is passed in `adoption-fields`. "The same situation produces a terminal error for one kind and an endless retry for the other." Argo CD custom checks then show Degraded versus Progressing forever. VERIFIED. https://github.com/aws-controllers-k8s/community/issues/3103
- ACK issue 3123 (2026-10-31): an EKS Cluster adopted over an existing cluster loops on a no-op update, with 17 identical failed calls in 11 minutes in CloudTrail per the reporter. VERIFIED as the reporter's observation. https://github.com/aws-controllers-k8s/community/issues/3123
- ACK issue 2728 (2025-12-24): an RDS DBCluster created through kro with `adopt-or-create` reconcile-loops because the controller rewrites a KMS alias to an ARN, so "certain fields (for example, kmsKeyID) trigger a continuous reconcile loop." VERIFIED as the reporter's account. https://github.com/aws-controllers-k8s/community/issues/2728
- Config Connector issue 14236 (2026-10-21, v1.117.0, open, not confirmed by maintainers in what was read): acquiring an existing StorageBucket removed its CSEK `FullyRestricted` enforcement config because the CRD has no field for it, though undeclared fields should stay externally managed. "The encryption enforcement config is removed during acquisition." The author notes bulk-export does not show the setting, so a KRM diff would not reveal the change. VERIFIED as the reporter's reproduction. https://github.com/GoogleCloudPlatform/k8s-config-connector/issues/14236
- Config Connector issue 13840 (2026-10-08, closed, resolution not read): a user who did not set the server-generated resourceID got "`HTTP 409 (CONTACT_ALREADY_EXISTS)`", the opposite failure of not acquiring by natural key. VERIFIED as the request text. https://github.com/GoogleCloudPlatform/k8s-config-connector/issues/13840
- Config Connector issue 12740 (2026-09-03, open) proposes that for server-generated-ID resources the controller refuse to re-create a vanished resource ("Do **not** call `adapter.Create()`") and fail terminally, which is the explicit-intent posture. VERIFIED as an open proposal. https://github.com/GoogleCloudPlatform/k8s-config-connector/issues/12740
- ACK issue 3143 (2026-11-09) proposes recording ownership in AWS tags, "on the resource itself, at the moment it is created", to refuse foreign resources and recover lost IDs. VERIFIED as an open proposal. https://github.com/aws-controllers-k8s/community/issues/3143
- Verdict stated by the dossier: `adopt-or-create` removes the foreign-owner guard and can cause silent overwrite and deletion, adoption can mutate undeclared settings, and no production frequencies exist. Explicit adopt or import fails closed and loud, `adopt-or-create` fails open and quiet, and strict create-only has its own failure of duplicates when the create result is lost. The ACK evidence comes mostly from one prolific reporter (gecube) in late 2026 and so is not independent corroboration. Crossplane's Observe-then-manage import flow produced no accidental-adoption reports in the searches.

## Corrections made during the dossier's verification

The dossier's own verification corrected three points: ACK runtime PR 292 is merged (2026-11-20) and not only closed, the overlapping-pod cause of ACK 3122 is inferred because the old pod's logs are unavailable, and the graceful-shutdown exchange belongs to Crossplane issue 3037 and not runtime issue 340. No VERIFIED claim was downgraded.
