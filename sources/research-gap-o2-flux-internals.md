## Summary

The dossier reads the Flux source code and documentation to settle how source-controller stores and serves artifacts, what the sharding labeling rule is, which API version the image automation kinds use, and how Flux judges the health of composite resources. Source-controller starts its in-process artifact server only after it wins leader election, and standby replicas fail readiness by design, so extra replicas add failover and no capacity. The stock manifest runs one replica with a Recreate strategy and emptyDir volumes. A HelmChart generated by a HelmRelease takes its shard label from the HelmRelease's `.spec.chart.metadata.labels`. The image automation kinds are `image.toolkit.fluxcd.io/v1` in the current specs. Flux has no documented ownerReference recipe or kro guidance for composites, and an issue on Crossplane resources shows the kstatus race that a CEL expression on `observedGeneration` avoids.

The dossier's own verification pass found no corrections, and nothing in it contradicts an existing wiki page, so no page was marked contradicted. Two existing pages that said a detail was unverified received one-line correction notes.

## Key claims

- The artifact server starts only after leader election. Quote from main.go: "Start the artifact server if running as leader." URL: https://github.com/fluxcd/source-controller/blob/main/main.go. See [findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness](../findings/flux-source-controller-starts-its-artifact-server-only-after-winning-leader-election-and-standbys-fail-readiness.md).
- Non-leaders fail the `leader-election` readiness check with "manager is not the leader" (https://github.com/fluxcd/pkg/blob/main/runtime/probes/probes.go), and the sharding page says "Standby source-controller replicas stay not ready by design, because only the leader serves artifacts."
- The leader election ID is derived from the watch label selector, so shard instances elect independently.
- Artifact defaults are path `/data`, address `:9090`, retention TTL of one minute, two records kept, and sha256. The stock manifest runs `replicas: 1` with `type: Recreate`, passes `--enable-leader-election`, and shows two `emptyDir: {}` volumes. See [findings/the-stock-flux-source-controller-keeps-artifacts-in-an-emptydir-with-one-minute-retention-so-a-restart-rebuilds-them](../findings/the-stock-flux-source-controller-keeps-artifacts-in-an-emptydir-with-one-minute-retention-so-a-restart-rebuilds-them.md).
- The GitRepository spec says an Artifact can "disappear from the storage due to e.g. the source-controller Pod being evicted", and a suspended object does not reflect that until resumed.
- The sharding rule is that "Source object kinds which have a dependency on another kind (i.e. `HelmChart` on a `HelmRepository`) need to have the same labels", and the generated chart is labeled through the HelmRelease. See [findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels](../findings/a-flux-helmchart-generated-from-a-helmrelease-takes-its-shard-label-from-spec-chart-metadata-labels.md).
- Main controllers exclude keyed objects with `--watch-label-selector=!sharding.fluxcd.io/key`, and "these controllers do not support sharding" for notification-controller and source-watcher. See [findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded](../findings/flux-notification-controller-and-source-watcher-do-not-support-sharding-and-the-documented-recipe-leaves-image-automation-unsharded.md).
- Cozystack ships a flux-shard-operator that sizes shards at about 100 HelmReleases each, per its own README ("K = clamp(ceil(H/100), 1, min(16, T))"). See [examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard](../examples/cozystack-s-flux-shard-operator-creates-helm-controller-shards-at-about-100-helmreleases-per-shard.md).
- Morgan Stanley lists sharding only as exploration: "Exploring sharding Flux controllers to distribute load across multiple instances within a cluster." URL: https://github.com/fluxcd/website/blob/main/content/en/blog/2026-03-15-stairway-to-gitops-morgan-stanley/index.md. See [examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding](../examples/morgan-stanley-runs-flux-across-more-than-500-clusters-with-self-service-onboarding.md).
- The image automation spec pages use `image.toolkit.fluxcd.io/v1`, and the ImagePolicy CRD shows `v1` as served and storage. See [findings/flux-image-automation-kinds-are-image-toolkit-fluxcd-io-v1-with-older-versions-still-in-the-api-directory](../findings/flux-image-automation-kinds-are-image-toolkit-fluxcd-io-v1-with-older-versions-still-in-the-api-directory.md).
- The image update guide describes semver tags for production, `branch-sha-timestamp` tags for staging, a separate push branch for manual approval, and revert by narrowing the semver range. See [findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range](../findings/the-flux-image-update-guide-offers-semver-for-production-a-separate-push-branch-for-review-and-revert-by-narrowing-the-range.md) and [decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation](../decisions/gate-flux-image-automation-with-semver-ranges-a-separate-push-branch-or-staging-only-automation.md).
- Kustomization `healthChecks` accept "Custom resources that are compatible with kstatus", `dependsOn` waits on health checks when `wait` or `healthChecks` is set, and `readyExpr` replaces the built-in readiness check. See [findings/flux-tracks-composite-resources-through-its-inventory-and-kstatus-or-cel-health-checks-and-documents-no-owner-reference-recipe-or-kro-guidance](../findings/flux-tracks-composite-resources-through-its-inventory-and-kstatus-or-cel-health-checks-and-documents-no-owner-reference-recipe-or-kro-guidance.md).
- Flux issue 5855 (closed 2026-04-21) reports Crossplane resources without an initial Ready condition seen as ready. See [examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression](../examples/flux2-issue-5855-kstatus-saw-crossplane-resources-without-a-ready-condition-as-ready-and-maintainers-recommended-an-observedgeneration-cel-expression.md).
- kro issue 1290 (open) says "kro resets those changes on the next reconciliation" when external controllers change fields. See [examples/kro-issue-1290-external-controllers-fight-kro-over-fields-and-kro-resets-their-changes](../examples/kro-issue-1290-external-controllers-fight-kro-over-fields-and-kro-resets-their-changes.md).
