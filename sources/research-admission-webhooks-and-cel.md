## Summary

The dossier describes admission control as the stage of the kube-apiserver request path that runs after authentication and authorization and before an object is persisted to etcd. Operators extend it in two ways. Admission webhooks are HTTPS callouts, split into mutating webhooks that may return patches and validating webhooks that may only allow or deny. The newer in-process option uses CEL, the Common Expression Language, in ValidatingAdmissionPolicy, MutatingAdmissionPolicy, and CRD validation rules.

The operational theme is blast radius. Because the API server blocks on webhook calls, a slow or unreachable webhook becomes a control-plane availability problem, and most guidance in the sources is about containing it through narrow matching, short timeouts, high availability, and careful use of `failurePolicy`. CEL mechanisms remove the external server for common cases, while webhooks stay the escape hatch for external data, complex code, and side effects. GitOps tools are not admission systems, but their server-side dry-runs run into webhook configuration.

See [[concepts/admission-webhooks-and-cel]] for the synthesized concept and [[comparisons/admission-mechanisms-webhooks-vap-map-and-crd-rules]] for the mechanism comparison.

## Key claims

### Webhook mechanics

- The Kubernetes reference describes the order of execution as mutating webhooks, then schema validation, then validating webhooks, with an AdmissionReview request and response. Matching uses `rules`, `namespaceSelector`, `objectSelector`, `matchPolicy`, and CEL `matchConditions`. `failurePolicy` defaults to `Fail` for `v1`, `timeoutSeconds` defaults to 10 seconds, `sideEffects` takes `None`, `NoneOnDryRun`, or `Some`, and `reinvocationPolicy` takes `Never` or `IfNeeded`. The API server authenticates to a webhook with kubeconfig-based credentials and mutual TLS. Only the first 100,000 of about 154,000 characters were covered. URL: https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/. Quote: "Admission webhooks that need to guarantee they see the final state of the object in order to enforce policy should use a validating admission webhook". See [[comparisons/admission-mechanisms-webhooks-vap-map-and-crd-rules]].
- The Kubernetes good-practices page is a checklist for webhook authors and operators: low latency and short timeouts, tight match scoping, high availability behind a load balancer, patching only needed fields, idempotent mutation, avoiding self-triggering and dependency loops, excluding system namespaces, testing across minor upgrades, and listing existing webhook configurations with kubectl. It also recommends CEL-based admission policies where they suffice. Only the first 100,000 of about 127,000 characters were covered. URL: https://kubernetes.io/docs/concepts/cluster-administration/admission-webhooks-good-practices/. Quote: "Ensure that the mutating webhooks in your cluster are idempotent". See [[findings/mutating-webhooks-can-run-repeatedly-and-in-no-guaranteed-order]] and [[findings/api-evolution-breaks-webhooks-that-drop-unknown-fields]].
- A source-code walkthrough of the kube-apiserver traces a request through the filter chain, aggregator, decoding and conversion, the admission plugin chain, and storage. It says mutating webhooks are called serially while validating webhooks run in parallel, and places ValidatingAdmissionPolicy evaluation (v1.26 alpha era) in the plugin chain. URL: https://www.zeng.dev/post/2023-k8s-api-admission/. Quote: "Matching webhooks are called in serial; each one may modify the object if it desires." See [[concepts/admission-webhooks-and-cel]].
- A vendor blog advises choosing `Fail` or `Ignore` by how critical a policy is, and making backends resilient with multiple replicas, pod anti-affinity, circuit breakers, namespace exemptions, sensible timeouts, and monitoring. It is secondary advice that agrees with the official page. URL: https://oneuptime.com/blog/post/2026-02-09-webhook-failurepolicy-ha/view. Quote: "Security-critical validations should use Fail, while nice-to-have mutations can use Ignore." See [[decisions/failure-policy-fail-or-ignore-for-an-admission-webhook]] and [[findings/fail-closed-webhooks-can-block-the-writes-needed-to-repair-them]].

### CEL-based admission

- The ValidatingAdmissionPolicy reference describes a policy with `matchConstraints`, `matchConditions`, `validations` (CEL over `object`, `oldObject`, `request`, and `params`), `variables`, `auditAnnotations`, and `failurePolicy`, plus a binding that selects scope, supplies parameters through `paramKind` and `paramRef`, and sets `validationActions` (`Deny`, `Warn`, `Audit`). Type checking is informational and the feature is stable since v1.30. Only the first 100,000 of about 137,000 characters were covered. URL: https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/. Quote: "Deny and Warn may not be used together since this combination needlessly duplicates the validation failure." See [[examples/vap-minimum-replicas-policy-with-per-environment-parameters]].
- The 1.30 GA announcement states the motivation as a declarative, built-in mechanism that avoids running and securing a webhook service, and names Kubescape as an ecosystem user. URL: https://kubernetes.io/blog/2024/04/24/validating-admission-policy-ga/. Quote: "Validating Admission Policy provides a declarative alternative to validating admission webhooks" (digest wording; verify). See [[concepts/admission-webhooks-and-cel]].
- The hands-on tutorial creates a policy requiring at least two Deployment replicas, binds it, and tries `Audit`, `Warn`, and `Deny`. A second part builds a MutatingAdmissionPolicy using `ApplyConfiguration` or JSON Patch. New policies do not retroactively affect existing objects. URL: https://kubernetes.io/docs/tutorials/cluster-management/admission-policies/. See [[examples/vap-minimum-replicas-policy-with-per-environment-parameters]].
- KEP-3488 proposes an in-process alternative because webhooks add infrastructure, latency, and reliability burden. Goals include covering most validating use cases and robust type checking under version skew. Non-goals include mutation, full webhook parity, and a whole policy framework. It describes the policy, binding, and parameter model, and prevents policies from matching admission-control resources themselves. URL: https://www.kubernetes.dev/resources/keps/3488/. Quote: "CEL expressions have comparatively small impact on latency and are in-process" (digest wording; verify). See [[findings/cel-policies-cannot-reach-external-data-and-have-bounded-cost]].
- The Mutating Admission Policy reference describes a policy, an optional parameter resource, and a binding, with mutations of `patchType` `ApplyConfiguration` or `JSONPatch`, plus `matchConstraints`, `matchConditions`, `failurePolicy`, and `reinvocationPolicy`. The digest reports the feature as stable from v1.36 and enabled by default, which the dossier could not cross-check and which earlier knowledge places at beta. Sidecar injection and default labels are the target use cases. URL: https://kubernetes.io/docs/reference/access-authn-authz/mutating-admission-policy/. See [[comparisons/admission-mechanisms-webhooks-vap-map-and-crd-rules]] and [[open-knowledge-gaps]].
- The CRD validation rules beta announcement introduces `x-kubernetes-validations` with `self` and `oldSelf`, presents it as a webhook replacement for most CRD validation with no network hop and no extra deployment, and notes that rule cost is bounded so a schema with unbounded lists or strings can be rejected at CRD creation. Only part of the page was covered. URL: https://kubernetes.io/blog/2022/09/23/crd-validation-rules-beta/. See [[examples/cel-rule-replaces-a-validating-webhook-for-cross-field-checks]] and [[findings/cel-policies-cannot-reach-external-data-and-have-bounded-cost]].
- The immutability post shows `self == oldSelf` for immutable fields, `self.all(x, x in oldSelf)` for append-only lists, and key-immutable maps, and explains that transition rules run only on updates where an old value exists. URL: https://kubernetes.io/blog/2022/09/29/enforce-immutability-using-cel/. See [[examples/cel-transition-rules-enforce-crd-immutability]].

### Tools and operators

- Kyverno's ValidatingPolicy is described as a superset of ValidatingAdmissionPolicy that adds background scanning, policy exceptions, extended CEL libraries, PolicyReports, `messageExpressions`, and an evaluation mode for non-Kubernetes JSON such as Terraform plans. It can generate native ValidatingAdmissionPolicy objects so enforcement runs in the API server instead of Kyverno's webhook. URL: https://kyverno.io/docs/policy-types/validating-policy/. See [[entities/kyverno]], [[examples/kyverno-validatingpolicy-generates-native-vap-objects]], and [[comparisons/kyverno-versus-native-validating-admission-policy]].
- Flux applies manifests with a server-side dry-run first, so webhooks that do not declare `sideEffects` of `None` or `NoneOnDryRun` cause reconciliation failures. The cheatsheet says to find the offending webhook configuration and fix `sideEffects`, and it covers the five-minute health-check timeout and the `disableWait` option. URL: https://fluxcd.io/flux/cheatsheets/troubleshooting/. Quote: "admission webhook does not support dry run". See [[examples/flux-dry-run-fails-against-webhooks-without-dry-run-support]], [[findings/webhooks-without-sideeffects-declared-break-dry-run-clients]], and [[entities/flux]].
- The Kubebuilder book shows `kubebuilder create webhook`, implementing `Default()` and `ValidateCreate`, `ValidateUpdate`, and `ValidateDelete`, and markers that generate webhook manifests. Webhooks ship in the same binary as the controller. URL: https://book.kubebuilder.io/cronjob-tutorial/webhook-implementation. See [[examples/kubebuilder-operator-scaffolds-defaulting-and-validating-webhooks]] and [[entities/kubebuilder]].
- cert-manager uses validation, defaulting, and conversion webhooks on its own CRDs. Its page lists connectivity failures between the API server and the webhook on GKE private clusters and EKS with custom CNIs, an initial unavailability window while the webhook waits for leader election, certificate generation, and CA bundle injection, and a self-signed CA with automatic serving-certificate renewal. URL: https://cert-manager.io/docs/concepts/webhook/. Quote: "The webhook automatically renews its serving certificate before it expires." See [[examples/cert-manager-runs-validation-defaulting-and-conversion-webhooks]], [[findings/webhook-tls-and-network-bootstrap-leaves-an-unready-window]], and [[entities/cert-manager]].
