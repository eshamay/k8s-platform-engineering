# Research dossier: Server-Side Apply and Field Ownership

The Cluster API pull request was read only as a description, the Crossplane SSA page is the v1.20 alpha documentation, and two items (Crossplane issue 7453 and the Helm 4 default) are unconfirmed. Two of the sources are personal blogs, one of which discloses AI assistance in drafting.

## Summary

The dossier explains that server-side apply (SSA) moves the merge half of `kubectl apply` into the API server. A client sends only the fields it has an opinion about, names itself with a `fieldManager`, and the server records which manager owns which field in `metadata.managedFields`. This replaces client-side apply, which computed a three-way merge in the client from the new manifest, the `last-applied-configuration` annotation, and the live object. SSA reached GA in Kubernetes 1.22.

The central mechanic is the conflict. When two managers set a field to different values, the later apply fails instead of overwriting, and the applier can force the write, drop the field, or set the same value and share ownership. Because ownership is tracked, removing a field from a manifest deletes it from the live object only when nobody else owns it. The dossier then follows the mechanic to its boundaries: controllers are told to force conflicts, CD tools are told to surface them, GitOps tools mostly force and then add escape hatches, and most real failures come from migrations from client-side apply, from atomic lists and unmarked CRDs, from stale co-owners, and from diffing that does not understand server defaults.

See [concepts/server-side-apply-and-field-ownership](../concepts/server-side-apply-and-field-ownership.md) for the synthesized concept and [comparisons/ssa-conflict-policy-across-tools](../comparisons/ssa-conflict-policy-across-tools.md) for the tool comparison.

## Key claims

### Mechanics and design

- The Kubernetes reference defines fully specified intent, `managedFields`, the `Apply` and `Update` operation values, the three conflict resolutions, shared ownership, and the merge markers `listType`, `listMapKey`, `mapType`, and `structType`. A field manager is required for apply and is inferred from the User-Agent otherwise, so `kubectl` is the default name. Custom resources without markers are treated as unstructured with atomic lists. URL: https://kubernetes.io/docs/reference/using-api/server-side-apply/. Quote: "It is strongly recommended for controllers to always force conflicts on objects that they own and manage". See [concepts/server-side-apply-and-field-ownership](../concepts/server-side-apply-and-field-ownership.md).
- KEP-555 lists the surprises of client-side apply, including applying after a `kubectl edit` and two users applying in turn. It replaces the last-applied annotation with per-field manager tracking, formalizes the schema in structured-merge-diff, adds server-side dry-run, and defines "status wiping". Parts of the document are marked TODO. URL: https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/555-server-side-apply/README.md. Quote: "Instead of using a `kubectl.kubernetes.io/last-applied-configuration` annotation, the control plane will track a \"manager\" for every field." See [comparisons/client-side-apply-versus-server-side-apply](../comparisons/client-side-apply-versus-server-side-apply.md).
- The 1.22 GA announcement adds subresource support for `status` and `scale`, first-class support in client-go and Kubebuilder, and generated apply configuration types in which every field is a pointer so a request can name exactly the fields a controller cares about. URL: https://kubernetes.io/blog/2021/08/06/server-side-apply-ga/. Quote: "Server-side Apply is a new merging algorithm, as well as tracking of field ownership, running on the Kubernetes api-server." See [examples/kubebuilder-controller-applies-status-with-a-field-owner](../examples/kubebuilder-controller-applies-status-with-a-field-owner.md).
- A core maintainer compares SSA with client-side apply, hand-rolled patches, shelling out to kubectl, and GET-modify-PUT with its optimistic-concurrency retry cost. The post splits controllers into "extract and re-apply" and "reconstructive" and recommends the second for new controllers. It argues that CD systems must surface conflicts to humans and lists the possible human responses. URL: https://kubernetes.io/blog/2022/10/20/advanced-server-side-apply/. Quote: "CI/CD systems are literally controllers, but for the purpose of apply, they are more like users". See [decisions/force-conflicts-or-surface-them-to-humans](../decisions/force-conflicts-or-surface-them-to-humans.md) and [examples/hpa-and-git-both-set-replicas-surface-an-ssa-conflict](../examples/hpa-and-git-both-set-replicas-surface-an-ssa-conflict.md).
- A personal-blog walkthrough of KEP-555 explains the three-way merge of client-side apply and why it is fragile, and gives an adoption timeline including Argo CD v2.5.0 support in October 2022. It also claims that Helm 4.0.0 (November 2025) enables SSA by default, which the dossier could not confirm. URL: https://blog.yangjerry.tw/en/posts/k8s-ssa-design/. Quote: "CSA performs a Three-Way Merge Patch on the client side, then produces a Strategic Merge Patch to send to the apiserver." See [entities/helm](../entities/helm.md).

### Tool behavior

- Kluctl moved from shelling out to kubectl to calling SSA directly. Because `kubectl --server-side` can only force everything or nothing, Kluctl decides per field, overwrites changes from known interactive managers such as kubectl and k9s, and offers `--force-apply`, `kluctl.io/force-apply`, and `kluctl.io/force-apply-field`. An admin can run `kubectl --field-manager=admin-override` to make a change Kluctl respects. URL: https://kubernetes.io/blog/2022/11/04/live-and-let-live-with-kluctl-and-ssa/. Quote: "Kluctl will not overwrite any fields that it lost ownership of, unless you explicitly tell it to do so." See [examples/kluctl-decides-field-level-conflicts-with-known-manager-heuristics](../examples/kluctl-decides-field-level-conflicts-with-known-manager-heuristics.md) and [entities/kluctl](../entities/kluctl.md).
- Flux kustomize-controller applies with SSA and runs a server-side dry-run each interval. The per-resource annotation `kustomize.toolkit.fluxcd.io/ssa` takes Override, Merge, IfNotPresent, or Ignore, the `force` annotation recreates on immutable-field changes, and `.spec.ignore` rules use JSON Pointer paths with "Strip" and "Adopt" semantics. The `flux-client-side-apply` manager name preserves kubectl edits, and atomic lists such as `.spec.tolerations` cannot be shared under `Merge`. URL: https://fluxcd.io/flux/components/kustomize/kustomizations/. Quote: "The `IfNotPresent` policy instructs the controller to only apply the Kubernetes resources if they are not present on the cluster." See [examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers](../examples/flux-ssa-annotations-and-ignore-rules-share-fields-with-other-controllers.md) and [entities/flux](../entities/flux.md).
- Flux kustomize-controller issue 486 records that moving from client-side apply (Flux 0.17) to SSA (0.18) left fields removed from Git in the cluster, because the old manager still co-owned them and force cannot take ownership of a field that no longer appears in the applied object. The maintainer workaround was to delete the offending `managedFields` entry, and one commenter instead recreated the Deployment with `--cascade=orphan`. URL: https://github.com/fluxcd/kustomize-controller/issues/486. Quote: "you can't force ownerships for non existing fields." See [findings/client-side-to-server-side-migration-leaves-stale-co-owners](../findings/client-side-to-server-side-migration-leaves-stale-co-owners.md) and [examples/flux-migration-from-client-side-apply-strands-removed-fields](../examples/flux-migration-from-client-side-apply-strands-removed-fields.md).
- Flux kustomize-controller issue 1722 describes a stale Update-type manager that co-owns a container entry's key but not its required `image` field. A later commit that removes the container makes SSA drop the field Flux solely owned and leave an invalid half-removed container, so the dry-run fails every reconcile before the post-dry-run manager cleanup (`--override-manager`) can run. The proposed opt-in flag `--override-manager-before-dry-run=<manager>` was closed as completed through PR 1747, and the dossier did not read the shipped documentation. URL: https://github.com/fluxcd/kustomize-controller/issues/1722. Quote: "doing operations before dry-run is dangerous and can have unintended consequences." See [findings/a-stale-manager-owning-a-list-entry-key-breaks-the-dry-run-after-removal](../findings/a-stale-manager-owning-a-list-entry-key-breaks-the-dry-run-after-removal.md).
- Argo CD defaults to client-side `kubectl apply`. Setting `ServerSideApply=true` (per Application or per resource) runs `kubectl apply --server-side --force-conflicts`. The page lists large CRDs, patching resources not fully managed by Argo CD, and a field-management model as reasons. `Replace=true` takes precedence over SSA, `Force=true` is ignored under SSA, and a client-side apply migration feature moves ownership to the `argocd-controller` manager. Adopting a namespace with `managedNamespaceMetadata` needs a prior upgrade to server-side apply or labels may be removed. URL: https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/. Quote: "Argo CD will use the `kubectl apply --server-side --force-conflicts` command to apply changes." See [entities/argo-cd](../entities/argo-cd.md) and [examples/argo-cd-applicationsets-crd-too-large-for-client-side-apply](../examples/argo-cd-applicationsets-crd-too-large-for-client-side-apply.md).
- The Argo CD SSA proposal gives the motivations as interoperability with admission controllers (the server always runs them), conflict identification through `managedFields`, and no annotation size limit. It requires a fixed manager name, a version check that falls back to client-side apply below Kubernetes 1.18, and notes the risk of alternating client-side and server-side syncs. URL: https://argo-cd.readthedocs.io/en/stable/proposals/server-side-apply/. Quote: "ArgoCD must register itself with a pre-defined manager".
- A practitioner article (October 2026, written with disclosed AI assistance) separates applying from comparing. With `ServerSideApply=true` Argo CD's default diff still compares Git-rendered manifests with live state in-process, so API-server defaults such as `volumeMode` and `status.phase` in StatefulSet `volumeClaimTemplates` look like drift. It recommends confirming with `kubectl diff --server-side` and enabling `ServerSideDiff=true`, noting that mutating-webhook changes are excluded unless `IncludeMutationWebhook=true` and that resources being created fall back to the normal diff. It also states that Server-Side Diff is stable since Argo CD 3.1.0, which the dossier did not verify. URL: https://blog.danielepetrollo.com/en/argocd-outofsync-server-side-diff. Quote: "Server-Side Diff hides nothing." See [examples/argo-cd-server-side-diff-ends-false-out-of-sync-from-server-defaults](../examples/argo-cd-server-side-diff-ends-false-out-of-sync-from-server-defaults.md) and [findings/diff-is-not-apply-server-defaults-look-like-drift](../findings/diff-is-not-apply-server-defaults-look-like-drift.md).
- Crossplane (v1.20 documentation, alpha behind `--enable-ssa-claims`) uses SSA to sync claims to composite resources and, with composition functions, composite resources to composed resources. Spec and metadata flow forward and status flows back. Deleted fields and labels propagate downstream, and merging of complex fields only works where the CRD schema carries merge markers, otherwise users should ask the provider maintainer to add them. URL: https://docs.crossplane.io/v1.20/concepts/server-side-apply/. Quote: "When Crossplane uses server-side apply, the Kubernetes API server helps sync resources." See [entities/crossplane](../entities/crossplane.md) and [findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership](../findings/atomic-lists-and-unmarked-crds-block-shared-field-ownership.md).
- Crossplane issue 5639 describes a four-step managed-fields migration for moving to composition functions. Fields start under manager `crossplane` with operation `Update`, all managers are deleted, the controller server-side applies under a manager with the prefix `apiextensions.crossplane.io/composed/`, and the leftover `before-first-apply` entry is deleted. URL: https://github.com/crossplane/crossplane/issues/5639. Quote: "Without this managedFields upgrade, the composed resources ends up having shared ownership of fields and field removals won't sync properly." See [examples/crossplane-clears-managed-fields-when-migrating-to-composition-functions](../examples/crossplane-clears-managed-fields-when-migrating-to-composition-functions.md).
- Crossplane issue 7453 (reported May 2026 against v2.3.1, stale and unresolved) claims that a field applied to a composite resource by an external controller with `ForceOwnership` disappears within one reconcile and that `managedFields` looks empty. A maintainer could not reproduce and suggested that `kubectl get -o yaml` hides `managedFields`. The claim is unconfirmed. URL: https://github.com/crossplane/crossplane/issues/7453. Quote: "`kubectl get -o yaml` hides `managedFields` unless you pass `--show-managed-fields`". See [findings/managedfields-are-hidden-from-kubectl-output-by-default](../findings/managedfields-are-hidden-from-kubectl-output-by-default.md).
- The Kubebuilder book shows scaffolding with `--ssa` to generate apply configuration types and applying status with `client.FieldOwner("controller-name")` and `client.ForceOwnership`. It recommends SSA when several controllers or users manage one resource and plain `Update()` for a sole owner, and its best practices are to always set a field owner, force fields the controller manages, and specify only fields you manage. The page is marked alpha. URL: https://master.book.kubebuilder.io/reference/server-side-apply.html. Quote: "For controllers that are the sole owner of a resource and manage the entire object, traditional `Update()` is simpler and sufficient." See [entities/kubebuilder](../entities/kubebuilder.md) and [findings/applying-a-whole-read-back-object-claims-every-field](../findings/applying-a-whole-read-back-object-claims-every-field.md).
- Cluster API pull request 6495 (merged June 2022) makes the ClusterClass topology controller use SSA through a structured-merge dry-run and patch helper. Only the stated motivation was read. URL: https://github.com/kubernetes-sigs/cluster-api/pull/6495. Quote: "leverage on the API server for handling controllers co-authoring the same object". See [examples/cluster-api-topology-controller-uses-ssa-for-co-authored-objects](../examples/cluster-api-topology-controller-uses-ssa-for-co-authored-objects.md) and [entities/cluster-api](../entities/cluster-api.md).

### Synthesis claims made by the dossier

- Large CRDs that exceed the 262,144-byte annotation limit are a primary reason Argo CD users enable SSA, and Kluctl reports the same driver. See [findings/large-crds-exceed-the-client-side-apply-annotation-limit](../findings/large-crds-exceed-the-client-side-apply-annotation-limit.md).
- Kubernetes maintainers say controllers should force conflicts and CD tools should surface them, yet Argo CD and Flux both force by default, and the sources do not settle the best default for platform teams that run GitOps and in-cluster controllers on the same objects. See [decisions/force-conflicts-or-surface-them-to-humans](../decisions/force-conflicts-or-surface-them-to-humans.md).
- Argo CD guidance keeps `ignoreDifferences` for fields a controller rewrites on purpose, such as `replicas` under an autoscaler, and prefers Server-Side Diff for server defaults because `ignoreDifferences` also hides real drift. See [comparisons/ssa-conflict-policy-across-tools](../comparisons/ssa-conflict-policy-across-tools.md).
- The maintainers hope to make server-side apply the `kubectl` default, and the dossier did not verify whether that happened.
