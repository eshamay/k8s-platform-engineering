# Research dossier: gap cluster g1-gitops-drift-incidents

Research date: 2026-11-26

## Overview

This pass looked for named GitOps adopters, incidents caused by drift correction or prune, evidence on how often forced finalizer removal orphans guarded resources, and a named end-user convergence case study. The web_search tool returned results for only a few queries (most returned empty), so most evidence came from GitHub issues read through the gh CLI and from a handful of pages read with web_scrape. Medium-hosted postmortems could not be read (the scrape returned empty content), so the Skyscanner GitOps outage is recorded from an index entry only.

What was found: a primary, dated (2026-11-20) CNCF blog post describing an Argo CD self-heal race at an anonymous customer (five regional Applications, two skipped a migration hook, 36 to 44 minutes of schema mismatch); several Argo CD and Flux GitHub issues in which prune, app-of-apps deletion or HPA ownership handoff removed or reset live resources; a 2026 ACK issue where an Argo CD prune left a CR stuck on its finalizer; and the official Kubernetes finalizers page, which warns against manual finalizer removal but gives no frequency data. Named adopters exist as lists (Argo CD USERS.md, 452 entries on 2026-11-26; CNCF case study for Subaru), all self-reported and none tied to an outage.

What was not found: any quantified rate of orphaning after forced finalizer removal, any named organization's postmortem for a GitOps revert loop, and any named end-user postmortem for controller retry amplification in Kubernetes. Issue reporters are anonymous, so the incidents are real but unattributed. All adopter and incident claims below are self-reported unless noted.

## Gap: Named GitOps adopters and GitOps-caused outages

Argo CD's own USERS.md is the largest primary adopter list; counting lines that start with a numbered link gave 452 organizations (adopters self-submit by PR). CNCF's Subaru case study documents an Argo CD plus Helmfile move from manual deployment procedures; it reports no outage. A press-release repost of the CNCF 2025 Argo CD end-user survey says nearly 60 percent of respondents' clusters use Argo CD (secondary, not read at cncf.io).

For outages, the evidence is user-filed GitHub issues without organization names. Argo CD issue 6046 (April 2021) reports that after wiping and reinstalling the argocd namespace, Argo CD began deleting all apps it managed; a maintainer asked whether the Application CRs carried the resources-finalizer. Issue 20440 (still open when read; v2.6.6) reports an ApplicationSet-generated Application and all its managed resources, including namespaces and Argo CD itself, being deleted, and a second reporter saw it with app-of-apps. Issue 15441 (2023) shows a namespace deleted and recreated when its explicit Namespace manifest was removed in favor of CreateNamespace. The k8s.af index lists a 2021 Skyscanner post, "involved: Gitops, templating, namespace deletion; impact: global outage", but the primary post could not be read, so its mechanism is unverified.

## Gap: Production incidents from drift correction

The strongest find is the CNCF blog post of 2026-11-20 by a CNCF Ambassador, retelling a customer incident: a release pushed during a deny sync window; at window close five regional Applications (automated sync, prune, self-heal) rolled out the same commit, three ran the database migration hook and two did not. Mechanism per the author, from reading Argo CD source and a lab repro: a level-1 refresh mistook the last compared revision for the last synced one, so self-heal ran a partial sync of out-of-sync resources, which skips hooks. The customer is unnamed, the Argo CD version was not stated in the portions I read (I skipped part of the lab section), and the source-code reading is the author's. Mitigations offered: make the migration a managed resource with a sync wave and release-specific name, or turn self-heal off for those apps (losing drift correction).

Flux issue 2514 (2022) shows the HPA conflict class: replicas reset to 1 on the first reconciliation of Flux over an HPA-managed Deployment, then recovered. A maintainer's first reply said a replicas field in Git conflicts with the HPA; the reporter reproduced it without it, attributing it to field-ownership handoff. This is a transient scale-down, not an outage report. The ACK issue 2911 (2026-06) shows prune interacting with a controller finalizer: Argo CD prune deleted a WAFv2 WebACL CR, AWS WAF was removed, and the CR stuck Terminating because the controller did not map the AWS not-found error; a maintainer confirmed the cause and fix in generator config.

## Gap: How often forced finalizer removal orphans guarded resources

No source quantifies the rate. The official Kubernetes finalizers page says to avoid manually removing finalizers and that this is safe only when the finalizer's purpose is accomplished another way. It gives no frequency. Related primary issues show the orphaning mechanism but not forced removal specifically: Kubernetes issue 53451 (2017) says the service controller can leave orphaned load balancers if it restarts while a delete is pending, because the Service is already gone from etcd; the issue proposed a finalizer on all Services as the fix, and PR 54569 was opened to add one [corrected in verification: PR 54569 was closed unmerged on 2019-06-04; the issue itself is closed as completed, and the PR merge outcome of the finalizer work is not established here]. Issue 43730 (2017, Azure) reports public IP and LB frontend leaks after service deletion filling a 10-entry pool. Cluster API issue 8172 (2023) shows orphaning when objects are deleted before the controller adds its finalizer. ACK 2911 (above) shows an operator needing a manual finalizer patch, which is the setup where removal would skip cleanup, though there the AWS resource was already gone. No survey or incident count was found.
