## Overview

This pass settled four version-sensitive questions by reading primary sources at stated versions: the Kubernetes v1.36 and v1.37 CHANGELOG files, `kube_features.go` at tags v1.36.0 and v1.37.0, KEP 4192 and its `kep.yaml`, the official kubernetes.io blog and docs pages, and the controller-runtime source at tag v0.25.3 (published 2026-11-16, the newest release listed by the GitHub releases API on the research date). Latest Kubernetes releases on the research date were v1.37.3, v1.36.7 and v1.35.11 (all published 2026-11-25); v1.38.0-beta.0 was published 2026-11-06.

Three of the four gaps are answered by primary text. MutatingAdmissionPolicy is GA and enabled by default since v1.36; the "beta" belief in the gap is out of date. StorageVersionMigration is GA in v1.37 and is user-triggered, not automatic. In controller-runtime v0.25.3, `Result{Requeue: true}` is a rate-limited requeue with per-item exponential backoff, which matches the package comment and contradicts the "immediate" reading. The staleness gap is largely answered, with some naming discrepancies between the v1.36 blog and the code and CHANGELOG that the wiki should record.

Two cautions for wiki authors. First, the v1.36 staleness blog names metrics that differ from the names in the CHANGELOG and source (see the staleness section). Second, the kubernetes.io SVM task page scraped in this run shows a header "Beta since Kubernetes v1.35; disabled by default" but a body saying the gate and API are "enabled by default in all clusters", so the page header is stale or inconsistent and should not be cited for stage. Large pages were saved to files by the scrape tool and read via jq and rg; all relevant article sections were read in full, navigation chrome was skipped.

## Gap: Kubernetes v1.36 staleness mitigation mechanisms and metrics

The mechanism, KEP 5647 (owner michaelasp), has three layers. In client-go, the `AtomicFIFO` feature gate (Beta, default on since 1.36) makes the informer FIFO handle list/relist batches atomically and lets a Store report `LastStoreSyncResourceVersion()`, the latest resource version the cache has seen. In kube-controller-manager, four controllers (DaemonSet, StatefulSet, ReplicaSet, Job) record the resource version of their own writes and, before syncing an object, skip the sync if the cache has not caught up. Each has its own gate `StaleControllerConsistency<Type>` (Beta, default true in 1.36), and each depends on `AtomicFIFO`. A client-go helper, `ConsistencyStore` (`WroteAt`, `EnsureReady`, `Clear`), is described for informer authors.

Observability: the blog names `stale_sync_skips_total` (per controller subsystem) and `store_resource_version`. The CHANGELOG and source give the precise names: `daemonset_controller_stale_sync_skips_total` and `job_controller_stale_sync_skips_total` (CHANGELOG-1.36), and the client-go gauge `informer_store_resource_version` with labels name, group, version, resource (alpha stability, "15 least significant digits of the resource version"). I did not find CHANGELOG names for the ReplicaSet and StatefulSet skip metrics.

Later developments: v1.37 extends the mitigation to the HorizontalPodAutoscaler controller (`StaleControllerConsistencyHPA`, Beta 1.37), adds a `BookmarkFunc` callback, a circuit-breaking variant for node lifecycle (`NodeControllerLeaseCircuitBreaker`, Beta 1.37), and an observation-only gate `MonitorInformerStaleness` that polls the apiserver every 5 seconds. For controller-runtime, a design PR (3473, "Read your own write client design") merged 2026-10-05; the tracking issue 3320 "Feature: ReadYourWritesConsistency" was still open when read. I did not confirm that any controller-runtime release ships the feature.

Effect on guidance: upstream treats "my cache has not yet seen my own write" as a skip-and-requeue condition keyed on resource version, and exposes lag through the informer resource-version gauge and per-controller skip counters. This supports the wiki finding on stale cache and double action, with the added fact that the built-in fix is resource-version gating, not sleeping or time-based waits.

## Gap: StorageVersionMigration GA details in Kubernetes v1.37

Verified: the API `storagemigration.k8s.io/v1` and the built-in `StorageVersionMigrator` controller (in kube-controller-manager) graduated to GA and enabled by default in v1.37. KEP 4192 `kep.yaml` gives alpha v1.30, beta v1.35, stable v1.37; the gate table at v1.36.0 shows Beta default false, and at v1.37.0 shows GA default true. v1.37 has been released (v1.37.0 release blog dated 2026-08-26; patch v1.37.3 on 2026-11-25).

Fields at v1.37.0: `spec.resource` (a `GroupResource`, immutable); `status.conditions` (types Running, Succeeded, Failed) and `status.resourceVersion` (the resource version compared against the garbage-collector cache, set when KCM first observes the object). The kind is cluster-scoped with a status subresource. Migration is not triggered automatically: the KEP states that creation of the migration object is deferred to the user, and the release blog says users create a declarative object. The controller then rewrites all stored objects of that resource. The out-of-tree trigger controller (discovery every 10 minutes) was not moved in-tree. The task docs state the requirement of an integer resource version, so aggregated APIs may fail. After a CRD migration, `.status.storedVersions` should shrink to the preferred version; if not, the CRD changed mid-migration and the migration should be retried.

Post-beta changes recorded in CHANGELOG-1.37: progress reporting in conditions (PR 138875), merge patch instead of server-side apply (PR 138874), a kube-controller-manager panic fix when the target resource is missing from the RESTMapper (PR 140586). KEP metrics: `storage_migrator_core_migrator_migrated_objects_total`, `..._remaining_objects_total`, `..._migrations_total`. Exact field shape of the progress reporting was not read.

## Gap: Requeue true backoff behavior in current controller-runtime

Answer at v0.25.3: `Result{Requeue: true}` with a nil error is a rate-limited requeue, not an immediate one. The handler calls `Queue.AddWithOpts(... RateLimited: true ...)`, which asks the controller's rate limiter for a delay. The per-item failure counter is not reset on this path, so repeated `Requeue: true` returns back off exponentially. By contrast, `RequeueAfter > 0` calls `Queue.Forget(req)` first (clearing backoff history) and then adds after exactly that duration. A non-nil error requeues rate-limited and ignores both fields (a warning is logged if either was set), except `TerminalError`, which is not requeued. The package comment, the `TypedReconciler` doc and the handler code agree. The `Requeue` field is marked `Deprecated: Use RequeueAfter instead`, with advice to use a duration or poll interval instead of a rate-limiter delay.

Defaults: `UsePriorityQueue` defaults to true when unset. With the priority queue, the default rate limiter is `NewTypedItemExponentialFailureRateLimiter(5ms, 1000s)` only, per item, no overall bucket. When the priority queue is disabled, the default is client-go's `DefaultTypedControllerRateLimiter`: max of that same per-item exponential limiter and a 10 qps, 100 burst bucket (read from client-go master, not a pinned tag). In the priority queue, if a rate-limited add also has an `After` value, the smaller delay wins.

Issue 808 ("Document ways to trigger/not trigger exponential backoff") is still open; its body does not say that `Requeue: true` is immediate. I read only the issue body, not the comment thread, so the origin of the "immediate" claim is not located. Metrics: the controller counts `reconcile_total` with result labels `error`, `requeue_after`, `requeue`, `success`.
