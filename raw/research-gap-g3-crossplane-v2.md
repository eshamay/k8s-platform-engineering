# Research dossier: gap cluster g3-crossplane-v2

Research date: 2026-11-26

## Overview

This pass settles most of the Crossplane v2 questions from primary sources. The current release is v2.5.0 (published 2026-11-24 per the GitHub releases API) and v1.20 reached end of life with it (v1.20.15 is the final v1.20 release). Documentation was read as markdown source in `crossplane/docs` (`content/v2.5/...`, which is what docs.crossplane.io/latest renders), plus the v2.0.0, v2.1.0, v2.4.0 and v2.5.0 release notes, CRD manifests shipped with the v2.5 docs, and `main`-branch source in `crossplane/crossplane`, `crossplane/crossplane-runtime` and `crossplane/upjet`. "main" claims describe the branch as read on 2026-11-26, not a tagged release.

The main structural findings. (1) Claims survive only for legacy XRDs: the v2 XRD API has `scope` of `Namespaced` (default) or `Cluster`, rejects `claimNames` by a CEL rule, and `LegacyCluster` is a v1 XRD scope that keeps claims. The v2.5 docs have no claims page at all; the v1.20 docs did. (2) `deletionPolicy` was removed from namespaced managed resources in v2.0.0 and survives only on legacy cluster-scoped MRs, where runtime code combines it with `managementPolicies`; `managementPolicies` is still labeled beta in v2.5 docs, and the issue to deprecate `deletionPolicy` (5283) is still open. (3) Operations, managed resource definitions (MRDs) and activation policies (MRAPs) are all alpha in the v2.5 docs, with `v1alpha1` APIs. (4) The async `Synced` problem (provider-aws 2287) was closed by the stale bot on 2026-06-25 with no fix; the current upjet and crossplane-runtime source still reports `ReconcileSuccess` while an async operation runs. (5) Issue 7453 (external SSA writers losing a field on an XR) is still open, a maintainer could not reproduce it, and two community PRs that assume a real bug are open and unmerged.

Scaling guidance did not change the provider-family decision outright. The MRD design doc says families "helped alleviate" the problem; MRDs plus MRAPs (alpha) are the v2 mechanism, and v2.4 and v2.5 add provider scale-to-zero and lower memory. Deprecated-API scanners (pluto, kubent) ship rule sets for core Kubernetes, cert-manager and istio only; neither covers Crossplane GVKs out of the box, though both accept custom entries. Crossplane has its own `crossplane beta upgrade check` (v1.20 CLI) for removed v1 features.

Gaps still open: whether `managementPolicies` interacts with owner-reference cascade is not documented (only derivable from source); no source quantifies cluster memory with and without MRAPs beyond the docs' ~3 MiB per CRD figure and project-reported blog numbers; no promotion plan for Operations to beta was found.

## Gap: Claim support and scope in Crossplane v2 XRDs

The v2.5 "What's New" page and the XRD page agree: new-style XRs are `Namespaced` (default for the v2 XRD API) or `Cluster`, and neither supports claims. A v1 XRD (`apiextensions.crossplane.io/v1`) defaults to `LegacyCluster`, which supports claims and does not use `spec.crossplane`. The shipped CRD for XRDs confirms this at the schema level: the v2 version's scope enum has only `Namespaced` and `Cluster` with a validation rule that rejects `claimNames`; the v1 version's enum includes `LegacyCluster` and a rule that only `LegacyCluster` XRs can offer claims. The XRD docs page lists all three values in one table, which blurs the fact that `LegacyCluster` exists only on the v1 API. XRD v1 is marked deprecated in the CRD but is still served and is still the storage version in the v2.5 manifest. Claims remain supported and maintained (v2.4 and v2.5 contain claim fixes); I found no removal date. This replaces the third-party-blog basis for `LegacyCluster` in the comparison page.

## Gap: Crossplane v2 condition behavior and the fix for async Synced signaling

Not fixed. Issue crossplane-contrib/provider-aws#2287 (opened 2026-03-11, `bug` label) reported `Synced=True/ReconcileSuccess` being rewritten on every reconcile during a 60+ minute MSK update while `AsyncOperation=False (Reason: Ongoing)` was set. The stale bot marked it stale on 2026-06-10 and closed it on 2026-06-25 with no maintainer comment and no linked fix. A doc/code discrepancy: the docs show `AsyncOperation` with `Status: True` for `Ongoing`, while upjet's `AsyncOperationOngoingCondition` sets `Status: False` (and the issue reporter observed False). Related v2 condition changes: v2.0.0 made XR and claim conditions persist `observedGeneration`; an open PR (8080, "stop stale XR condition replay", 2026-11-20) exists but I read only its title.

## Gap: Crossplane v2 server-side apply behavior and external writers

The v2.5 docs no longer carry the v1.20 "server-side apply" concept page; the only SSA text is in Operations ("server-side apply with force ownership"). Behavior has to be read from source. On `main`, the composite reconciler persists `spec.crossplane.resourceRefs` with an SSA `Apply` patch using `ForceOwnership` and field owner `apiextensions.crossplane.io/composite`, then applies the XR's status the same way; composed resources use field owners prefixed `apiextensions.crossplane.io/composed` plus a hash. A comment in the code says to stop using `client.Apply` "after the v2.2 release". The composite reconciler's other status writes use `Status().Update`. Claim-to-XR sync uses SSA behind a beta flag defaulting on.

Issue 7453 (opened 2026-05-31, Crossplane v2.3.1, function-go-templating) claims the XR controller clears `metadata.managedFields` on every reconcile and wipes a spec field an external controller applied with `--force-conflicts`. The reporter did not reply in the thread. Two community PRs (7783 and 7787, opened 2026-08-27 and 08-28, both open) assert a root cause (`FromStruct()` replaces the whole XR object, dropping `managedFields`) and propose preserving them; neither is merged and I found no maintainer review of the claim. Verdict: unresolved, not confirmed as a bug, and the wiki should say "reported, not reproduced by a maintainer, open".

## Gap: Crossplane v2 namespaced composites and managementPolicies versus garbage collection

Documented pieces: a namespaced XR can only compose resources in its own namespace; cluster-scoped XRs can compose anything; legacy XRs cannot compose namespaced resources. Composed resources carry a controller `ownerReference` to the XR with `blockOwnerDeletion: true` (docs example). XR deletion defaults to Background (Crossplane drops the XR and Kubernetes garbage-collects children); the alpha Composition `deletionPolicy` (Foreground, Pipeline; `--enable-function-controlled-deletion`, introduced in v2.5.0) changes this, and `kubectl delete --cascade=orphan|foreground` and Argo CD foreground deletion bypass it.

The interaction with `managementPolicies` is not documented in the pages read. The managed-resource reconciler source gives the answer: on deletion, the external resource is deleted only if it exists and the policy allows `Delete`; otherwise the reconciler unpublishes connection details and removes the finalizer. So a cascade that deletes an MR object whose `managementPolicies` lack `Delete` leaves the external resource in place and removes the Kubernetes object. The docs' policy table says the same for policy sets without Delete ("doesn't delete the external resource when deleting the managed resource"). v2.4.0 also restricted the XR garbage collector to resources whose controller reference points to the XR. Not covered: deletion of a namespace while the provider is down, and any special handling of `Observe`-only MRs inside compositions.

## Gap: Current Crossplane v2 status of deletionPolicy and managementPolicies

Both still exist, but on different resource kinds. v2.0.0 release notes: namespaced MRs (the new `.m.` groups) have no `deletionPolicy`; recreate Orphan with a `managementPolicies` list lacking `Delete`. Legacy cluster-scoped MRs keep `deletionPolicy`. The v2.5 managed resources docs page never mentions `deletionPolicy`. In crossplane-runtime `main`, a `LegacyManagementPoliciesResolver` (marked Deprecated, "for LegacyManaged types, that had deletion policy") merges the two fields, while `ManagementPoliciesResolver` serves modern MRs. Issue 5283 ("Deprecate DeletionPolicy") was opened 2024-01-25, is OPEN (state reason REOPENED), last activity 2024-08-14 (stale bot then `/fresh` by a maintainer), labels `exempt-from-stale`, `feature-lifecycle`, `release/breaking-api-change`. A contributor comment there says the field was never officially deprecated, only noted as planned. So: no formal deprecation of `deletionPolicy` on legacy MRs as of 2026-11-26.

## Gap: Managed resource activation policy mechanism and defaults

MRAPs work on ManagedResourceDefinitions. Since v2.0, installing a provider converts its CRDs to MRDs (flag `--enable-custom-to-managed-resource-conversion`, default true). An MRD has `state: Active|Inactive`; an Inactive MRD means no CRD exists. An MRAP (`apiextensions.crossplane.io/v1alpha1`) lists `spec.activate` patterns; the controller lists MRDs, matches names against exact names or prefix-only `*` wildcards (not regex, `*` only at the start), sets matching MRDs `Active`, and records `status.activated`. MRAPs are additive. Transition is one way (Inactive to Active). Default: the Helm chart creates a `default` MRAP activating `"*"` (chart value `provider.defaultActivations: ["*"]`), so a stock install activates everything; set it to `{}` or a list to go selective. A provider declaring the `safe-start` capability yields MRDs that start Inactive; a provider without it gets MRDs that start Active. Failure modes in docs: pattern does not match, MRDs not yet created because the provider is not installed, provider lacks `safe-start`, and `Healthy: Unknown / EncounteredErrors` when some activations fail. Maturity: docs mark MRAP and MRD alpha (`alphaVersion: 2.0`), yet `core.go` groups the MRD conversion flag under "Beta Features" (default true), a docs/code mismatch. v2.4.0 scales a safe-start provider's runtime Deployment to zero until its first MRD is active. Doc inconsistency: MRAP page examples use `*.m.crossplane.io` suffixes, the upgrade guide uses `.m.upbound.io`; the latter matches the Upbound AWS provider's group names.

Measurements: the docs' own figure is about 3 MiB of API server memory per CRD (so 200 CRDs is 600 MiB), an estimate, not a benchmark. v2.5.0 notes report Crossplane core heap 338 to 190 MiB and RSS 415 to 250 MiB on a 791-CRD cluster after it stopped caching all CRD OpenAPI schemas (project self-reported). A Crossplane blog (2026-10-08, project-authored) reports 80 to 95 percent provider memory reduction on a 2,000-CRD cluster from crossplane-runtime v2.4 (CRD schema stripping and optional Secret cache). I found no with-versus-without-MRAP API server measurement.
