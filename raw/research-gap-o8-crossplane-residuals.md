# Research dossier: gap cluster o8-crossplane-residuals

Research date: 2026-11-26

## Overview

This pass read primary sources for the four residual Crossplane gaps: the crossplane/docs repository (the `content/master` tree, plus a few `v2.5` paths), the crossplane/crossplane v2.5.0, v2.4.0, v2.3.0 and v2.1.0 release notes, the Lock resolver and package API source, the crossplane/upjet repository (README, CLAUDE.md, `docs/monitoring.md`, `pkg/terraform` source, issues), and the crossplane-contrib/function-kro source. All material was fetched with the gh CLI as raw text. The docs repo `master` tree is unversioned, so doc quotes are labelled "docs master, read 2026-11-26". The latest tagged Crossplane release seen was v2.5.0, published 2026-11-24.

Scaling: nothing new contradicts the existing wiki position that there is no single v2 scaling page and no published numeric limit for XRs or composed resources per controller. The new material is a memory measurement in the v2.5.0 notes (heap 338 MiB to 190 MiB and RSS 415 MiB to 250 MiB on a cluster with 791 CRDs), a docs-guide estimate of about 3 MiB of API server memory per CRD, and a v2.4.0 note about a provider-side memory fix for safe-start providers. The v2.5.0 notes also add GC for unused CompositionRevisions (alpha). The v2.1.0 circuit-breaker numbers (50 burst, 1 per 2s) are re-confirmed from the release notes.

Upjet: the runtime model is settled from first-party source. Upjet supports three execution modes selected per resource: a fork-based Terraform CLI mode, a no-fork Terraform Plugin SDK v2 mode, and a no-fork Plugin Framework mode. In CLI mode a shared Terraform provider gRPC server process is forked and reused across reconciles, with a TTL counted in invocations, while each resource has its own workspace directory with a state file. No official memory or CPU numbers exist in the docs read. The only cost-related first-party material is the Upjet metrics (process counts, CLI duration, time-to-readiness) and an old issue closed as outdated by the provider-family change. Which official providers use which mode was not established.

Packages: the docs and source give the revision activation policy (`Automatic` default, `Manual`), the revision history limit (default one inactive revision), `skipDependencyResolution`, and alpha dependency upgrade and downgrade flags. The Lock resolver is a controller that never modifies the Lock itself and creates one missing dependency at a time. The Function page in docs master did not show an activation policy or history limit in a keyword scan, so the Function case is unconfirmed.

kro to Crossplane status: the question is answered through `function-kro` (a crossplane-contrib project that embeds kro's engine as a composition function). Its source shows the function does not use kro's controller. It approximates three kro built-in conditions from a single run, sets author conditions as XR conditions, and sets only declared status paths on the desired XR. A kro controller feeding a Crossplane composite as a composed resource was not documented anywhere I found.

## Gap: Current Crossplane v2 scaling guidance

Findings. The Pods guide documents the poll interval (default one minute, `--poll-interval`) and sync interval (hourly default, `--sync-interval`), and still describes `--max-reconcile-rate` as a rate in times per second, which the v2.1.0 notes say was renamed to `--max-concurrent-reconciles` (a worker pool size). The v2.1.0 notes say Crossplane relies on API Priority and Fairness, the XR circuit breaker, and worker pool configuration to manage reconcile load. v2.3.0 added per-resource `crossplane.io/poll-interval` and `crossplane.io/reconcile-requested-at` annotations and an XR `scale` subresource (this is for scaling XR-defined workloads, not Crossplane capacity). v2.4.0 added watch-driven reconcile on required resources and zero-replica runtimes for safe-start providers. v2.5.0 reports a measured memory cut and an alpha GC for unused CompositionRevisions (default `unusedRevisionHistoryLimit` of 1).

The MRD guide gives a docs-level estimate: about 3 MiB of API server memory per CRD, so 200 CRDs is about 600 MiB. This is an illustrative calculation in the guide, not a benchmark. No numeric limit for XRs or composed resources per Crossplane controller, no recommended CPU or memory sizing for the Crossplane pod, and no independent benchmark were found (searched docs repo for "memory" and "max-reconcile-rate", release notes v2.1.0 to v2.5.0, `guides/` listing). The 2023 provider-family decision is not retired by anything read here; the MRD and activation-policy path is an additional mechanism.

## Gap: Upjet runtime execution model and cost

Findings. Upjet's README lists "Multiple Terraform Execution Modes": Terraform CLI (fork-based), Plugin SDK v2 (no-fork, direct Go library), and Plugin Framework (no-fork, protocol-based over protov6). The repository CLAUDE.md says the mode is selected per resource configuration and names the controller files for each (`external.go` for CLI, `external_tfpluginsdk.go`, `external_tfpluginfw.go`). In CLI mode the runtime keeps a per-resource `Workspace` directory with a `terraform.tfstate` file and runs `terraform` subcommands (apply, destroy, plan, import, refresh) in sync or async mode. `SharedProvider.Start` forks one native Terraform provider process and reuses it through a gRPC reattach configuration (the controller sets the `TF_REATTACH_PROVIDERS`-style JSON with a unix socket). `SharedProviderScheduler` shares one provider process across reconciles whose resource blocks are configuration-wise identical, and replaces a runner when its invocation count reaches a TTL and no invocation is in use. Open issue #754 says the no-fork framework connector re-runs the provider's `Configure` on every reconcile, building and discarding a provider server each time, whereas the SDK v2 path reuses a configured handle.

Cost: the Upjet monitoring doc exposes `upjet_terraform_cli_duration`, `upjet_terraform_active_cli_invocations`, `upjet_terraform_running_processes` (labelled `cli` or `provider`), and `upjet_resource_ttr`, so operators can measure process counts and time-to-readiness. No memory or CPU figures, requests, or limits appear in the docs read. Issue #151 ("Capture Provider memory footprint with releases") was closed, and a maintainer comment says it is outdated after the provider family architecture (introduced in Upjet v0.9.0) and that monolithic provider packages are discouraged because the API server handles many CRDs inefficiently. Which of the official AWS, Azure and GCP providers run in which mode was not determined.

## Gap: Crossplane package dependency resolution, revision activation, and upgrade policy

Findings. Installing a new version of a Provider or Configuration creates a new revision. Only one revision is Active at a time. `revisionActivationPolicy` is `Automatic` (default, the most recently installed revision becomes Active) or `Manual`. `revisionHistoryLimit` defaults to keeping one Inactive revision, `0` disables storing. `skipDependencyResolution: true` makes Crossplane ignore a package's dependencies (providers then must be installed manually). Dependencies are declared in the package's `crossplane.yaml` with an optional version constraint (example `">=v0.36.0"`), and a Configuration with unmet dependencies reports `HEALTHY: False`. The Provider doc's Upgrade section says the new `ProviderRevision` lets Crossplane retain deprecated CRDs "until you decide".

The resolver is the Lock controller (`internal/controller/pkg/resolver`). It watches ConfigurationRevision, ProviderRevision, FunctionRevision and ImageConfig, builds a DAG from the Lock's packages, refuses on cycles, and if dependencies are implied but missing it creates only the first implied node ("The resolver never modifies the Lock"). Failures set `ResolutionFailed`, success `ResolutionSucceeded`. Alpha features: `EnableAlphaDependencyVersionUpgrades` (docs flag `--enable-dependency-version-upgrades`) picks the minimum version satisfying all constraints, and `EnableAlphaDependencyVersionDowngrades` (Helm `packageManager.enableAutomaticDependencyDowngrade=true`) additionally lets it downgrade; downgrades need both flags and the docs warn about orphaned MRs, data loss, and storage-version changes. Without downgrades, the error says manual intervention is required when a valid version needs a downgrade. v2.5.0 fixes a new revision taking ownership of objects during upgrades. The docs Function page did not mention `revisionActivationPolicy` or history limit in a keyword scan (UNVERIFIED for Functions; Function revisions exist per the Lock watch). The "lock file" is the cluster-scoped `Lock` object named `lock`, not a file.

## Gap: kro status schema and Crossplane v2 status propagation

Findings. The wiki already settled standalone kro status and Crossplane's ready derivation (see the gap entry). The residual question is how a kro-style resource graph feeds a Crossplane composite. The concrete route is `function-kro` (crossplane-contrib), which says it "natively embeds KRO's graph builder, CEL evaluator, and runtime engine". Its README says the `resources` and `status` blocks are identical to a kro ResourceGraphDefinition. In `fn.go`, a hard graph error becomes a fatal result (except while waiting on external-ref fetches), a not-ready error from the executor only sets `allReady` to false, desired composed resources are written into the response, and the desired XR contains only the status paths declared in the graph, to keep server-side apply ownership narrow. `setAuthorConditions` approximates kro's built-ins from one run: `GraphResolved` always True, `ResourcesReady` and `Ready` equal to `allReady`, `InstanceManaged` omitted. Author conditions from `runtime.newCondition` are returned as XR conditions through the function SDK, with Crossplane-reserved condition types rejected with a warning, and conditions that are waiting for data are left out, so Crossplane keeps their last value. How composed resources' Ready values reach the XR `Ready` condition remains the Crossplane v2.5.0 behavior already recorded in the wiki (function sets READY_TRUE; function-auto-ready). I did not find where function-kro sets per-resource readiness (grep for READY_TRUE in `fn.go` found nothing; `engine.go` path returned 404), so that link is UNVERIFIED. A standalone kro controller instance whose output feeds a Crossplane composite was not documented; only a third-party lab repo (suzuki0430/kro-crossplane-eks-idp-lab) turned up by search and was not read. v2.5.0 also reserves `status.crossplane` on XRs.
