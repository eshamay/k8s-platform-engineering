# Research dossier: gap cluster g1-leaked-resources-adoption

Research date: 2026-11-26

## Overview

This pass looked for incident-grade evidence on two questions: what happens when a controller loses the result of a cloud "create" call (leaked or duplicated resources), and what production teams see when a controller adopts an existing resource instead of requiring an explicit import. Every source below was read as raw text through the gh CLI (issue bodies, comments, and one source file in crossplane-runtime). No source is a named, dated, organization-authored postmortem or a conference talk. The evidence is GitHub issues from users and maintainers. Where an issue gives cost or scale, it is self-reported by the issue author and labeled that way.

On leaked and duplicated resources, the strongest material is: (a) Crossplane maintainer Nic Cope (negz) explaining in issue 3037 why the `external-create-pending` annotation exists and which three leak scenarios it guards against; (b) an ACK issue (3122) with a timestamped CI reproduction of a duplicate VPC endpoint during a controller rollout, and a follow-up audit (3177) that counts 48 resources in 22 ACK controllers where a lost Create response either duplicates the resource or wedges the CR; (c) a self-reported cost incident in provider-upjet-aws (2199) where a lost external-name led to a 409 retry loop costing about $155 over 15 days in GuardDuty analysis of CloudTrail events; (d) a Route 53 report (ACK 3067) where a GitOps bootstrap across two clusters left one duplicate hosted zone per name; and (e) a Config Connector report (648, 2022) where a failed create still produced an alert policy on every reconcile, which a Config Connector engineer attributed to the GCP API.

On adopt-or-create versus explicit import, the evidence is about failure modes of adoption, not about measured outcomes across many adopters. ACK issue 3149 reproduces, with moto as IAM, that `adopt-or-create` bypasses the "already exists" guard so two CRs overwrite one role and deleting either deletes it. ACK 3103 documents Role and Policy diverging in the same situation. Config Connector 14236 reports that acquiring an existing bucket removed its encryption-enforcement config. No source compared the two policies in production over time, so the safer default cannot be settled from this evidence alone, but the failure catalog supports caution about `adopt-or-create` as a default.

Also answered: whether the Crossplane opt-out for deterministic identifiers shipped. The crossplane-runtime source on main contains `WithDeterministicExternalName`, and an open upjet issue (2251) says upjet controllers do not yet set it.

## Gap: Postmortems of leaked or duplicated cloud resources from ambiguous creates

No formal postmortem from a named organization and no conference talk was found. What exists is maintainer analysis plus user-reported incidents in issues. Incidents below are labeled with reporter and what is self-reported.

**Crossplane design rationale (maintainer).** In crossplane/crossplane issue 3037 (opened 2022-04-08, closed), reporter on AWS provider with Crossplane 1.6.4 saw SQS queues stuck with "cannot determine creation result". Negz explained that the provider writes `external-create-pending` before the create call and `succeeded` or `failed` after, all inside one reconcile, so an interrupted reconcile (for example a provider restart) leaves the MR needing human intervention. He gave the VPC example: if the returned ID is not recorded, the next reconcile cannot tell whether the VPC was created, and could create a second one and leak the first. He later listed three leak scenarios the annotations cover: cloud-generated names that cannot be stored, eventually consistent APIs reporting that a resource does not exist, and stale cache reads of the MR. He proposed documenting the behavior and letting resources with deterministic identifiers opt out.

**Triggers reported in the same thread.** A user (Jell) reported a normal Deployment rollout of the provider after a create that was failing on IAM issues. Another (iAnomaly) reported MRs 209 days old failing after a cluster upgrade replaced all nodes (this text was struck through in the comment, so treat it as the reporter's partly retracted claim). crossplane-runtime issue 340 (2022-07-14) reports provider-terraform: if the pod is terminated during a multi-minute `terraform apply`, the failed-annotation update fails because the context is cancelled, leaving the pending annotation stuck. Negz agreed graceful shutdown handling would be a good idea and said providers had none at that time [corrected in verification: that exchange is in issue 3037 (comment dated 2022-04-29), not in runtime issue 340].

**Did the opt-out ship?** Searched crossplane-runtime main source: `WithDeterministicExternalName(b bool)` exists, and when false the reconciler stops with "cannot determine creation result" instead of re-queuing; when true the safeguard is skipped. So the opt-out exists in the runtime. However provider-upjet-aws issue 2251 (2026-09-25, open) reports that upjet controller templates do not pass it, so resources with deterministic names (S3 bucket sub-resources, IAM Policy) still wedge. The trigger there was a dropped HTTP/2 connection to the Kubernetes API server under load (about 500 S3 and IAM MRs across 10 environments created in parallel, self-reported) which lost the response of the pending-annotation update. Provider-level adoption of the flag is therefore not complete as of the issue date.

**Cost incident (self-reported).** provider-upjet-aws issue 2199 (2026-08-18, open): a provider-aws-eks restart during the 30 to 60 second async create window of a PodIdentityAssociation lost the external-name; the next create got `409 ResourceInUseException`, and the provider retried about 3 to 4 times per minute. The reporter says each stuck resource cost about $12 per day in GuardDuty analysis of the CloudTrail management events and that they saw a "15-day, $155 anomaly across 7 stuck PIAs on two clusters". A commenter reported the same for Kafka VPCConnection. These figures are the reporter's, not independently confirmed. Note this is a stuck-retry loop, not a duplicate resource: the 409 prevented the duplicate.

**Duplicate resources (reproduced, ACK).** ACK community issue 3122 (opened 2026-10-31 by sapphirew) documents a CI run (ec2-controller PR 398, build dated 2026-10-30) where a controller restart during a Deployment rollout (RollingUpdate, leader election disabled) coincided with a second `CreateVpcEndpoint`; EC2 made two endpoints, only one was recorded, and the orphan [corrected in verification: the issue says the old pod's create cannot be seen directly because Prow keeps only the surviving pod's logs; the overlapping-pod cause is inferred, and an SDK retry of the token-less call would leave the same evidence] blocked subnet deletion so bootstrap teardown retried `DeleteSubnet` for about 2 hours until it was deleted by hand. Root cause given: no stable `ClientToken`. Maintainer knottnt cautioned that a stable token can break re-creation after out-of-band deletion and suggested leader election by default and the Recreate deployment strategy. The follow-up audit, ACK issue 3177 (2026-11-13, gecube), states that when a Create response is lost, 48 resources in 22 controllers either create a second AWS resource (28) or fail on every reconcile because the name is taken (20), with 12 more depending on undocumented behavior. This is an author's code and documentation audit, not an observed production incident count. The fix in ACK runtime PR 292 (opened 2026-11-13, merged 2026-11-20 [corrected in verification: was "closed"]) moves the status patch to immediately after Create; the PR text states a controller stopped before that patch leaves a resource in AWS whose ID the CR lacks, a duplicate for server-generated IDs.

**Duplicate hosted zones.** ACK issue 3067 (2026-10-01, shrinedogg): Route 53 allows two public hosted zones with the same name, so a GitOps bootstrap that ran the controller on a throwaway cluster and then on the durable management cluster, with empty status on the second, created one duplicate zone per name. Maintainer knottnt asked whether ACK should enforce a constraint the service does not, and pointed to a WIP tag-based adoption PR (runtime PR 261).

**Other.** Config Connector issue 648 (2022-04-05, v1.76.0): MonitoringAlertPolicy with an invalid query returned HTTP 400 yet created a policy each reconcile; a Config Connector engineer said the GCP API itself still creates the policy when create returns 400. Crossplane issue 6260 (2025-02-01, closed, bobh66) shows leaked composed Objects when 1.17's cached unstructured reads let the composite reconciler create extra composed resources; this is a leak in Kubernetes objects, not cloud resources, but the same mechanism (stale read leading to a second create).

## Gap: Production outcomes of adopt-or-create versus explicit import

No production comparison of the two policies was found, and no adopter write-up or talk. The evidence is a set of reproduced failure modes of ACK `adopt-or-create` and one Config Connector acquisition side effect, most from late 2026 and mostly from a single prolific reporter (gecube) in ACK, so it should not be read as independent corroboration. Crossplane's Observe-then-manage import flow produced no accidental-adoption reports in the searches.

**ACK takeover of a managed resource (3149).** Reproduced with iam-controller v1.11.3 and runtime v0.67.0 against moto. A CR with `adopt-or-create` and the same role name as an existing CR's role is adopted with no ownership check; the controller rewrote the role (seven mutating calls) and each resync flips the trust policy between the two CRs; both stay Synced=True with no warning. Deleting either CR deleted the role in 4 ms, and the surviving CR's next resync created a new role with a new role ID. The same CR without the annotation stops with a terminal "Resource already exists", so the annotation disables the only guard. A role created outside ACK and tagged `team=terraform` was adopted and the tag was removed, which the author notes is the intended use but indistinguishable to the runtime. The author says this needs no misconfiguration: one cluster, default settings.

**Inconsistent semantics (3103).** For the same "name already exists" case, Role gives a terminal error while Policy retries `EntityAlreadyExists` forever as recoverable; `adopt-or-create` does not adopt a Policy unless the ARN is passed in `adoption-fields`. Health tools (Argo CD custom checks) show Degraded versus Progressing forever.

**Adoption not converging.** 3123 (EKS Cluster adopted over an existing cluster loops on a no-op update, 17 identical failed calls in 11 minutes in CloudTrail per the reporter); 2728 (RDS DBCluster created through kro with `adopt-or-create` reconcile-loops because the controller rewrites a KMS alias to an ARN).

**Config Connector acquisition.** Issue 14236 (2026-10-21, v1.117.0, still reproducible against the report's claim about v1.159.0 CRD) says acquiring an existing StorageBucket removed its CSEK `FullyRestricted` enforcement config because the CRD has no field for it, though undeclared fields should stay externally managed. The author notes bulk-export does not show the setting, so a KRM diff would not reveal the change. Issue 13840 (2026-10-08, closed) shows the opposite failure of not acquiring by natural key: a 409 CONTACT_ALREADY_EXISTS when the user did not set the server-generated resourceID, with the author citing existing acquire-by-natural-key precedents for other kinds. Issue 12740 (2026-09-03, open) proposes that for server-generated-ID resources Config Connector refuse to re-create and instead fail terminally, which is the explicit-intent posture.

**Proposed mitigations.** ACK 3143 (proposal, 2026-11-09) records ownership in AWS tags to refuse foreign resources and recover lost IDs; ACK maintainers pointed to an earlier WIP tag-check adoption PR (runtime 261). These are open proposals, not shipped results.

**Verdict on the decision question.** The evidence supports the claim that `adopt-or-create` removes the foreign-owner guard and can cause silent overwrite and deletion, and that adoption can mutate undeclared settings (Config Connector). It does not give production frequencies, so "which default is safer" remains a judgment: explicit adopt/import fails closed and loud, `adopt-or-create` fails open and quiet, while the duplicate-resource evidence in the first gap shows that strict create-only has its own failure (duplicates when the create result is lost).
