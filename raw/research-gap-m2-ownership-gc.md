# Research dossier: gap cluster m2-ownership-gc

Research date: 2026-11-26

## Overview

This pass targeted seven open gaps about ownership and garbage collection. The main result is that kro, the one tool the earlier dossier could not read, is now documented from its v0.10.0 source tree and website docs. kro deliberately does not set owner references on the resources an instance creates. It stamps labels (including an ApplySet part-of label), tracks children in an ApplySet inventory, and deletes them itself in reverse dependency waves. It does set owner references on its own RGD-level objects (the generated CRD and GraphRevisions). An alpha annotation, `kro.run/deletion-policy: Orphaned`, releases a resource by stripping kro's labels and annotations, and the docs say a later instance can adopt it.

The blockOwnerDeletion dispute can be settled from the admission plugin source. When `OwnerReferencesPermissionEnforcement` is enabled, a write that adds `blockOwnerDeletion: true` without `update` on the owner's `finalizers` subresource is rejected with a Forbidden error. No code in the plugin drops the flag. The plugin is not in the default-on list of upstream kube-apiserver, so on a cluster that has not enabled it the flag is stored with no permission check at all. The "silently not honored" claim from the earlier blog source could not be reproduced from source and its page was not re-read in this run.

Argo CD's tracking methods and prune propagation are now read from its docs and source. The default propagation for pruning is foreground, and `PrunePropagationPolicy` accepts background, foreground and orphan. For Kubernetes enhancement proposals, no KEP was found that is dedicated to cross-namespace ownership or garbage collector performance. What exists is the documented v1.20 behavior (a warning event for invalid cross-namespace owner references), two closed issues, KEP-5080 (ordered namespace deletion, which states the GC still handles owner references), and KEP-2336 (a `resource` field on owner references, aimed at removing discovery calls).

Controller-runtime and Cluster API adoption are read from source: controller-runtime refuses cross-namespace owners and refuses to take over an object already controlled by another controller, and Cluster API's MachineSet controller adopts matching Machines that have no controller reference. For Crossplane v2, the docs do not describe the namespace-deleted-while-provider-down case, but an open Crossplane issue describes the closely related race where the namespace controller deletes the credentials Secret before managed resources finish deleting. Findings on `managementPolicies` versus the owner-reference cascade rest on the docs plus a prior wiki dossier that read the managed reconciler source; that source was not re-read here.

## Gap: How kro sets ownership and labels on child resources

Findings. kro v0.10.0 (latest release, published 2026-11-10 per the GitHub releases API) documents that it does not set owner references on managed resources by default, giving two reasons: ordered deletion and the fact that namespaced owners cannot own cluster-scoped children. Ownership is expressed through labels and the Kubernetes ApplySet specification. The labels stamped on each child are `kro.run/owned`, `kro.run/kro-version`, `kro.run/instance-id`, `kro.run/instance-name`, `kro.run/instance-namespace` (namespaced instances only), `kro.run/instance-group`, `kro.run/instance-version`, `kro.run/instance-kind`, `app.kubernetes.io/managed-by: kro`, `kro.run/node-id`, and `applyset.kubernetes.io/part-of`. Collection (forEach) items also get `kro.run/collection-index` and `kro.run/collection-size`. Long instance names or groups are hashed into label values (`h-` prefix) and the full value is kept in an `internal.kro.run/...` annotation. The source (`pkg/metadata/labels.go`) confirms the label constants; the docs say child resources do not carry `resource-graph-definition-*` labels.

Deletion order: kro stores each child's dependency wave in the `internal.kro.run/apply-order` annotation and deletes in reverse order, one wave at a time, waiting for each wave to disappear completely. Children are discovered from the instance's persisted ApplySet inventory, not by re-evaluating the graph, so cleanup can proceed when an external reference is gone. Children with no valid annotation (for example created before an upgrade) go in a final unordered wave.

Where kro does use owner references: `pkg/metadata/owner_reference.go` builds a `ResourceGraphDefinition` owner reference, with the comment "stamped on the CRD and RGIs"; GraphRevisions carry an owner reference to their RGD, and the controller re-adopts orphaned revisions by stamping the reference again. For users who need owner references on children (for Argo CD), the docs say to add them manually in the template and warn of out-of-order GC, validation failures for cross-namespace or cluster-scoped children, and timing conflicts with kro's reconciliation. The FAQ example uses `controller: false` and `blockOwnerDeletion: true`, plus an `argocd.argoproj.io/tracking-id` annotation. The deletion-policy page adds that releasing a resource does not touch `metadata.ownerReferences`, so if the template sets one, Kubernetes GC deletes the resource anyway.

Not settled: the docs name KREP-014 (a broader lifecycle field, under design) and the v1 roadmap lists KREP-004 (owner references and deletion policy for RGD/CRD lifecycle) as draft. Neither was read in full.

## Gap: Argo CD PrunePropagationPolicy and resource tracking methods

Findings. Argo CD has three tracking methods set by `application.resourceTrackingMethod` in `argocd-cm`: `annotation` (default, `argocd.argoproj.io/tracking-id`), `annotation+label` (the `app.kubernetes.io/instance` label is informational only and truncated at 63 characters; the annotation does the tracking), and `label` (the instance label is the tracking key). Changing the method requires a re-sync. The docs list label-mode limitations: 63-character truncation, other tools writing the same label, and awkwardness with multiple Argo CD instances. With annotation methods, a tracking annotation that does not reference the resource it is on (name, namespace, group, kind) makes the resource neither affect sync status nor get pruned; HNC-copied resources are the cited case. `installationID` adds an `argocd.argoproj.io/installation-id` annotation to separate multiple Argo CD instances on one cluster. In source (`util/argo/resource_tracking.go`) label-only mode does not truncate the label value, to avoid breaking resource-to-app matching, and leaves Kubernetes to report a validation error.

PrunePropagationPolicy: the sync-options page says pruned resources use foreground deletion by default, and the option accepts background, foreground and orphan. The controller source maps `PrunePropagationPolicy=background|foreground|orphan` to the Kubernetes `DeletePropagation` values and falls back to foreground; the gitops-engine sync context passes it in `DeleteOptions.PropagationPolicy`. For Application deletion (separate from prune), the default is foreground cascading deletion through the `resources-finalizer.argocd.argoproj.io` finalizer, and background is used when `resources-finalizer.argocd.argoproj.io/background` is set. The Crossplane docs warn that Argo CD's foreground default causes Crossplane to ignore its composite deletion policy (see the Crossplane gap below). The kro FAQ says its sample uses the default annotation tracking and must be adapted for label or annotation+label.

Caveat: the docs were read from the `master` branch of the argo-cd repository, not a stated release; the latest release at read time was v3.6.3. Nothing was found on how the three tracking methods interact with an owner-reference-based discovery of child resources (searched the tracking page and sync options page; no statement).

## Gap: What happens when blockOwnerDeletion is set without finalizers permission

Findings. The admission plugin source (`plugin/pkg/admission/gc/gc_admission.go`, master) settles the mechanism for clusters where the plugin is enabled. It validates creates and updates. Edits that do not change owner references pass. For non-create operations the caller needs `delete` on the dependent. Then, only if the change adds `blockOwnerDeletion: true`, the caller needs `update` on the `finalizers` subresource of every referenced owner (all RESTMappings if the kind maps to several resources). A shortcut allows the write if the caller can `update` `finalizers` on `*`. When the check fails, the plugin returns `admission.NewForbidden` with the message "cannot set blockOwnerDeletion if an ownerReference refers to a resource you can't set finalizers on". That is a rejected request, not a silent drop. Creates are exempt from the delete check but not from the blocking check, per the code comment. `pods/status` is whitelisted.

The plugin is not in the default-on list: `DefaultOffAdmissionPlugins()` in `pkg/kubeapiserver/options/plugins.go` subtracts a list that does not include `OwnerReferencesPermissionEnforcement`, so upstream it is off unless enabled with `--enable-admission-plugins`. The official admission controller reference and the owners-and-dependents page both describe the control. I did not read the platform-specific defaults of managed distributions. When the plugin is off, the owner-reference write is accepted, and the flag is stored. I searched the code-search hits for `BlockOwnerDeletion` in kubernetes/kubernetes and found no code path that strips the flag on write (hits were the plugin, the garbage collector graph and patch code, controller utilities and bootstrap RBAC policy); this is a negative search result and not proof.

The blog claim that the flag is "silently not honored" was not located again (web search returned no results), so it stays UNVERIFIED. A possible reading that fits the source: if a controller sets the flag where the plugin is off, GC will honor it, since the GC graph treats `BlockOwnerDeletion` true dependents as blocking in foreground deletion. Whether the blog describes some other behavior is not established.

## Gap: Adoption and orphaning behavior in Cluster API, kro, and controller-runtime operators

Findings. Cluster API (latest release v1.14.4, published 2026-11-03; docs and source read from the `main` branch): the MachineSet controller lists Machines in its namespace by the selector, skips ones controlled by something else, and adopts those with no controller reference by patching a controller owner reference, emitting `SuccessfulAdopt` or `FailedAdopt` events. The book lists adoption duties for MachineSet (unowned Machines, unmanaged Machines with no Cluster) and MachineDeployment (matching MachineSets). The owner-reference guidelines say objects should always be created with an owner reference, references should be re-reconciled if lost (Velero is named as a tool that can remove them), and references should use the most recent apiVersion so GC still works after an old version stops being served. An ownership table maps each kind to its owner and whether it is a controller reference. `clusterctl move` pauses the Cluster before moving. KubeadmControlPlane adoption of existing control-plane Machines has an e2e test (`kcp_adoption.go`). No CAPI source in the search used an explicit orphan delete propagation (searched for `PropagationPolicy`, `DeletePropagation`, `OrphanDependents` in non-test Go code; found nothing), so deletion relies on default GC through owner references; that is an inference from the book's statement that owner references "are used for Kubernetes garbage collection, which is also used for Cluster deletion".

kro: see the first gap. The deletion-policy annotation (alpha, behind the `DeletionPolicy` feature gate, default off per `pkg/features/features.go`) lets an RGD author mark a template `Orphaned`; kro then strips its labels and annotations from the object (including the ApplySet ID) and leaves it. The docs describe moving a resource between graphs: orphan it in the old RGD, delete the old instance, then declare it in the new RGD and "kro adopts the existing object rather than creating a new one". The RGD-level CRD apply compares ownership labels and names adoption (same RGD name, different ID) versus conflict (different RGD or not kro-owned) in `CompareRGDOwnership`. For instance children, the v0.10.0 upgrade notes say the new engine adopts existing resources in place via the unchanged `kro.run/applyset` field manager. For the Graph API, a field already managed by another Graph causes a conflict and the node is not ready.

controller-runtime: `SetControllerReference` sets `controller: true` and `blockOwnerDeletion: true`, errors with `AlreadyOwnedError` if another controller already controls the object, and rejects owner/dependent pairs in different namespaces and cluster-scoped dependents with namespaced owners. So a plain controller-runtime operator does not take over a controlled object; adoption of orphans is something the operator must write itself (the original Kubernetes design makes controllers responsible for adoption via selectors). Orphaning on delete is a client option: the delete propagation policy in the request, or a finalizer in the operator. No controller-runtime documentation on a standard adoption helper was read. Note that the in-tree `ControllerRefManager` in kubernetes/kubernetes handles adopt and release but was not read in this run.

## Gap: Behavior of namespaced v2 managed resources when a namespace is deleted while the provider is down

Findings. No Crossplane documentation was found that states this case. The v2.5 docs say a managed resource carries a finalizer, that the object stays until the external resource is fully deleted, and that deleting Crossplane resources out of order can leave cloud resources running (the ordered uninstall is composite definitions, then managed resources, then providers). The Kubernetes side is generic: the namespace controller deletes the namespace's contents, and an object with a finalizer stays Terminating until its finalizer controller removes it. From these two facts, a namespaced managed resource whose provider is not running would stay Terminating and hold the namespace open; this is an inference from documented general behavior, and I found no Crossplane page or issue testing it with the provider absent. The earlier wiki finding (hand-removing the finalizer orphans the external resource) is consistent with the open issue below.

What does exist is evidence for the neighboring failure with the provider running. crossplane/crossplane issue #7801 (open, created 2026-09-02) states that the namespace controller deletes objects in no particular order, the credentials Secret has no finalizer, so it can go first while managed resources, `ProviderConfigUsage` objects and the `ProviderConfig` are held by finalizers. The provider then cannot authenticate, "the namespace all stay `Terminating`", and "the only way out today is to remove finalizers by hand, which orphans the external resources." A comment (2026-10-14) from the provider-gitlab maintainers' tests reports finalization success counts per build: with a namespaced `ProviderConfig` and Secret in the namespace, 0/5 on provider-gitlab master with crossplane-runtime v2.4.2, and 1/5 with the runtime fix for ProviderConfigUsage protection merged; with `ClusterProviderConfig`, 3/3 to 5/5 depending on build. Options listed there: protect the Secret, cache credentials in the provider (finalized 9/9 but failed after restart, 0/2), or document deleting managed resources before the namespace. The linked design one-pager (#7594, merged) says the `Secret` case is an explicit limitation. Separate issue crossplane-runtime #1150 (open) reports `Connect()` running before the deleted-check and a rejected `ProviderConfigUsage` create (403 `NamespaceTerminating`) blocking managed resource deletion for hours on v2.3.3; I read only its first part. Those results are anecdotal test data inside an issue thread, not release-note facts, and the merge state of the fixes in a given release was not checked.

KEP-5080 (stable in v1.34) adds ordered namespace deletion, but its text was not read for the credentials Secret case; whether it changes the ordering for CRD-defined objects was not verified.

## Gap: Crossplane v2 namespaced composites and managementPolicies versus garbage collection

Findings. From the v2.5 docs: composition functions do not run when a composite is deleted, and Crossplane handles composed resource deletion itself. The alpha deletion policy (behind `--enable-function-controlled-deletion`) has three values: Background (default; Crossplane stops managing the parent at once, and Kubernetes deletes children by owner-reference GC), Foreground (Crossplane deletes the children and keeps the parent until they are gone), and Pipeline (functions decide when each child is deleted). Composed resources carry an owner reference to the composite with `controller: true` and `blockOwnerDeletion: true`, shown in the `crossplane composition render` example output. The deletion policy is not used for legacy cluster-scoped composites (always Background) or when `kubectl delete --cascade=orphan` or `--cascade=foreground` is used, because Kubernetes then decides. When Argo CD deletes with foreground propagation, Crossplane ignores the policy and emits a warning event; the docs say to set `PrunePropagationPolicy=background` and use the `/background` Application finalizer.

managementPolicies: a beta field, on by default, whose support depends on the provider. `Delete` lets Crossplane delete the external resource when the managed resource is deleted; without it Crossplane does not delete the external resource when deleting the managed resource (several rows of the combination table say so), and an empty list pauses the resource. The v2.5 docs do not connect the policies to the owner-reference cascade. The previous wiki dossier (research-gap-g3-crossplane-v2) already reports from source that the managed reconciler removes the Kubernetes object but leaves the cloud resource when `Delete` is missing; that was not re-read in this run. Not found in the docs: namespaced composite scope rules (searched the composite resources page for "namespaced" and "scope"; only the legacy cluster-scoped note appeared), and special handling of Observe-only managed resources in compositions.
