# Research dossier: gap cluster g3-scale-recheck

Research date: 2026-11-26

## Overview

This pass rechecked the scale figures in the wiki's scale dossier against raw text. Raw text came from two routes: `web_scrape` full-page text (SIG Scalability thresholds, Gardener scalability guide, the Upbound CRD post, the Argo CD high-availability page, the Crossplane provider-families blog) and `gh api` raw file contents (KEP-1040 README and kep.yaml, the Kubernetes website APF page, the Crossplane smaller-providers design doc, client-go workqueue source, controller-runtime source, Argo CD docs at tag v3.6.3). No digest was used for any claim below.

Every figure the wiki quotes from these sources was confirmed. No numeric value needed correction. Three claims need tightening in wording. First, the Upbound memory figure is "a little over 4MiB" of RSS per CRD, which is more precise than "several MiB". Second, the Argo CD processor guidance is concrete: defaults are 20 status and 10 operation processors, and the docs say they use 50 and 25 for 1,000 applications. Third, SIG Scalability's "no CRD count" is true of the table, which is explicitly scoped to "builtin resource types", and the Crossplane blog independently says CRD count was never an official threshold. The wiki's KEP-1040 "crowding out" claim, which the dossier marked as paraphrase, is supported by close wording in the KEP's Motivation section, which can now be quoted verbatim.

Two version-sensitivity points matter. The SIG thresholds page is stated for Kubernetes head and says the release-blocking scale tests have run on kops since Dec 2025, so the figures are tied to that setup. The Argo CD docs at v3.6.3 (latest release when read) and master still label both `round-robin` and `consistent-hashing` as experimental, so the wiki's "labelled experimental" is current, not just a historical digest reading. Also worth recording: the workqueue defaults differ by path. client-go's `DefaultTypedControllerRateLimiter` is the max of a 5 ms to 1000 s per-item exponential limiter and a 10 qps, burst 100 bucket, but controller-runtime in the version read uses only the exponential limiter (same 5 ms and 1000 s) when its priority queue is on, which is the default.

Gaps: the wiki also asked for full reads of the APF page and KEP-1040. The APF page was read in full as raw markdown. The KEP-1040 README was fetched in full (3,337 lines) but only the Summary, Motivation and Goals sections, the seat and shuffle-sharding sections by keyword, and kep.yaml were examined line by line; the rest was searched by keyword, not read end to end.

## Gap: Scale numbers from model digests need rechecking

Outcome: all wiki-quoted figures from the SIG Scalability thresholds, Gardener, Upbound, Argo CD, Crossplane, APF and KEP-1040 sources match the raw text. Details and the few wording refinements follow.

SIG Scalability thresholds (read via web_scrape of the raw markdown on master; last commit to the file per the GitHub API was 2026-11-24). The cluster-scope table gives 5000 nodes, 10000 namespaces, 150000 pods, 10000 services; the per-resource-type object table gives 150'000 non-event objects, 1'000'000 events, 1.5MB per object, 3GB total. The wiki's "5,000 nodes, 150,000 pods, 10,000 namespaces, 10,000 services, 1.5 MB" is correct. The wiki's quoted sentence is verbatim. The page adds namespace-scope thresholds (3000 pods, 5000 services, 2000 deployments, 250 endpoints per service) and "#Pods per node: min(110, 10*#cores)". Thresholds are "NOT hard limits".

Gardener (read via web_scrape, full page, undated; the page is the current site version). Verified: etcd practical limit 8 GB; healthy DB under 3 GB; more than 16GB etcd memory is a red flag; object count under 100k excluding events; kube-apiserver pod continuous 3 cores and 16 GB considered safe; most clusters under 500 nodes; conversion webhooks can block garbage collection. Two precisions: the etcd and apiserver numbers are conditioned on nodes with "at least 8 vCPU and 32GB memory", and the 100k figure is "for most use cases". The wiki's digest line is accurate.

Upbound CRD post (web_scrape full text, dated Aug 9, 2022). Verified: about 300 API groups/versions so about 300 HTTP requests for discovery; client-side throttling log line "Waited for 1.033772408s"; the lazy OpenAPI fix landed in v1.23.0 and was backported to v1.20.13, v1.21.7, v1.22.4; memory "a little over 4MiB" RSS per CRD (measured with 780 CRDs in the screenshot caption). The OOM point: managed services "won't begin scaling until the API server is repeatedly OOM killed". The post does not present a formal OOM test; it describes the observation and cites a GKE repair-mode quote. A zap logger fix claimed about 20% memory reduction for Kubernetes 1.25 and a GC tuning experiment gave 25% lower peak RSS on an idle API server with about 2,000 CRDs. The wiki should say "a little over 4 MiB per CRD" and not "several MiB".

Argo CD (web_scrape of master docs, and gh raw at tag v3.6.3). Verified: `--status-processors` default 20, `--operation-processors` default 10; "For 1000 applications, we use 50 for --status-processors and 25 for --operation-processors"; sharding methods legacy (uid based, non-uniform), round-robin, consistent-hashing; both of the latter two carry an "experimental feature" admonition in v3.6.3. The round-robin note adds that rank-0 cluster removal reshuffles all clusters.

Crossplane: the smaller-providers design doc (status Draft in its header, last committed 2023-04-25 per GitHub API) lists provider-aws v0.30.0 at 872 CRDs, provider-azure v0.28.0 at 692, provider-gcp v0.28.0 at 325, says problems start "very approximately" over 500 CRDs, and a survey of about 40 community members estimates about 176 CRDs and about 9 provider pods versus over 900 CRDs and about 2 pods. The memory numbers (about 600MB base, about 300MB per Terraform provider process) are expectations stated as "we suspect we can get providers down to at least", so they are targets, not measurements; the wiki says "need about", which overstates. The provider-families blog (13 Jun 2023, Jared Watts, full text) confirms "tens of CRDs", "more than 900", and an unresponsive API "up to an hour".

APF page (raw markdown, feature-state stable for v1.29) and KEP-1040 (kep.yaml: status implemented, alpha v1.18, beta v1.20, stable v1.29). The "poorly-behaved controller" sentence is verbatim in the page's intro. HTTP 429 for `Reject` type levels and `Queue` with shuffle sharding and fair queuing both verified. Concurrency shares are expressed as "nominal concurrency shares" converted to seats; the page also describes lendable and borrowable percentages. Note the wiki says classification "with concurrency share measured in seats" - more exactly, the setting is shares and the derived limit is in seats.

Workqueue defaults (client-go master `util/workqueue/default_rate_limiters.go`): `DefaultTypedControllerRateLimiter` is a MaxOf of an item exponential failure limiter (5ms base, 1000s max) and a bucket limiter at 10 qps with burst 100, with the source comment "only for retry speed and its only the overall factor (not per item)". controller-runtime `pkg/controller/controller.go` (main) [corrected in verification: path was given as `pkg/internal/controller`] uses only the exponential limiter when the priority queue is on (default true), otherwise the client-go default. The wiki currently states no numbers here, so these are additions.
