# Research dossier: gap cluster m3-status-conditions

Research date: 2026-11-26

## Overview

This pass read the kstatus Go source in kubernetes-sigs/cli-utils directly (latest release v0.37.2, published 2024-07-08; the files read are on the default branch), the Kubernetes API conventions and KEP-1623 as they stand on the default branch, the Flux, Cluster API and Config Connector sources, and Argo CD's docs, types and Config Connector health script. All GitHub material was fetched as raw text through the gh CLI. Config Connector's public docs were read through web_scrape and curl. Versions: Config Connector latest release v1.162.0 (2026-11-23), Argo CD latest release v3.6.3 (2026-11-24), Cluster API latest release v1.14.4.

The kstatus gap is settled from source. `Compute` runs a fixed sequence: deletion timestamp, then a top-level `metadata.generation` versus `status.observedGeneration` check, then `Reconciling` and `Stalled` conditions, then per-type rules for built-ins, then a `Ready` fallback, then "Current" by default. The conditions' own `observedGeneration` is never read, because kstatus's condition struct has no such field. This matters for the other gaps: the Kubernetes conventions put `observedGeneration` on each condition (via `metav1.Condition`) and also describe a status-level field, Flux writes both, kstatus reads only the top-level one, and Config Connector writes only the top-level one and has a commented-out TODO for the per-condition one. The conventions do not tell authors to pick one location.

On polarity, the primary record is a history rather than a rule. The conventions once recommended abnormal-true, then in February 2020 reversed to positive, then in June 2020 removed the preference and now say neither polarity can be recommended as a general rule. kstatus's README still describes abnormal-true for `Reconciling` and `Stalled` while treating `Ready` as a legacy positive fallback, and a kstatus maintainer said in May 2020 that the then-pending conventions PR would move naming away from abnormal-true. Flux mixes both (positive `Ready`, abnormal-true `Stalled` and `Reconciling`). No published incident write-up about polarity misreadings was found. Per the evidence rules, this dossier presents options and does not recommend.

For Config Connector, the design document (committed 2026-01-30) differs from shipped code in several specifics. The shipped lifecycle handler uses reasons `Updating`, `UpToDate` and `UpdateFailed` (not `UpdateFailure`), different message text, a single replaced `Ready` condition, and a top-level `status.observedGeneration`. The "first field path" message and the long-running-operation ID in the reason were not found in code. Argo CD ships a Lua health check for `cnrm.cloud.google.com` resources that keys on the `UpToDate`, `UpdateFailed`, `DependencyNotFound` and `DependencyNotReady` reasons and gates on top-level `observedGeneration`. Argo CD's own status beyond health (sync status, application conditions, resource tracking) was read from types and docs, but its operation-state docs and controller aggregation code were not.

## Gap: kstatus rules for combining observedGeneration and conditions

Findings. Order of evaluation in `status.Compute` (cli-utils pkg/kstatus/status, read at default branch; `generic.go` last changed 2021-07-02, `status.go` last changed 2025-07-05): (1) `metadata.deletionTimestamp` set gives Terminating. (2) `checkGeneration`: if both `metadata.generation` and `status.observedGeneration` exist and differ, the result is InProgress with a synthetic `Reconciling` condition with reason `LatestGenerationNotObserved`; if `status.observedGeneration` is absent the check is skipped. (3) The condition list is scanned in array order: `Reconciling=True` gives InProgress using the condition's reason and message, `Stalled=True` gives Failed; the first match in array order wins (this is read from the loop, not stated in docs). (4) If undecided, type-specific "legacy" rules apply to built-in kinds. (5) Otherwise a `Ready` condition decides: True gives Current, False gives InProgress, Unknown gives InProgress. `Ready=False` never produces Failed. (6) If nothing decided, the result is Current.

Consequences read from the code order (inference, not documented): a `Ready=True` condition with a stale top-level `observedGeneration` yields InProgress because step 2 precedes step 5. A resource whose controller has never written `status.observedGeneration` skips step 2 and can read Current before the controller acts, which is the premature-readiness window. Conditions' own `observedGeneration` is ignored: `BasicCondition` carries only type, status, reason and message. For built-in kinds, `core.go` has a stricter helper that returns InProgress when `status.observedGeneration` is missing, but the generic path does not.

## Gap: Where observedGeneration should live

Findings. The sources describe three coexisting placements and none says to choose one.

Status level. The API conventions say "Some resources report the `observedGeneration`" at status level for checking that reported status reflects the latest desired state. Per condition. The same conventions document the `metav1.Condition` struct with an optional `observedGeneration` ("the condition is out of date with respect to the current state of the instance"). KEP-1623 (status implemented, stage stable, created 2020-03-23) makes it a non-pointer integer and explains that absent and zero mean the same thing. apimachinery's `SetStatusCondition` copies a changed `ObservedGeneration` into the existing condition. On the default branch, `metav1.Condition.ObservedGeneration` carries new declarative-validation markers tagged `+k8s:beta(since: "1.38")` for optional and minimum 0; this was read from `types.go` only, not from release notes.

Consumers. kstatus reads only the top-level field. Argo CD's docs tell health-check authors to use `status.observedGeneration` and its Config Connector script gates on it. Flux writes both: its condition setter always stamps `condition.ObservedGeneration = to.GetGeneration()` and its Kustomization status also has a top-level `observedGeneration`. Cluster API's 2020 conditions proposal had no `observedGeneration` ("In K8s there is an ObservedGeneration field, while in this proposal not."); its 2024 proposal moves to `metav1.Conditions`, and the provider contract for InfraMachine accepts a per-condition `observedGeneration`, defaulting to the resource's generation when omitted. Config Connector sets top-level `status.observedGeneration` in both code paths and has a commented-out per-condition line with a TODO.

Options for the wiki decision (no recommendation): (a) top-level only, which is what kstatus and Argo CD consume; (b) per-condition only, which is what `metav1.Condition` supports and which lets each condition go stale independently; (c) both, which is what Flux does and what the conventions permit. Trade-offs recorded in sources: kstatus cannot see per-condition values; the conventions' per-condition comment defines staleness per condition.

## Gap: How a platform should choose condition polarity

Findings. Sources on each side, no recommendation.

Neither-recommended. The current conventions (default branch, last changed 2026-11-05) say positive and negative polarity cannot be recommended as a general rule and that without knowing the conditions "it is not possible to compute a generic summary". Cluster API's 2024 proposal says it will adopt this. History from commit diffs in kubernetes/community (PR 4521): the commit of 2020-02-14 recommended positive polarity as an "explicit reversal from earlier recommendations of abnormal-true"; the commit of 2020-06-26 removed that preference and added the current "neither" text.

Abnormal-true side. kstatus's `Reconciling` and `Stalled` are abnormal-true by design; the README states the weakness (a stopped controller looks healthy) and relies on `observedGeneration` to cover it. Flux's constants say `Stalled` and `Reconciling` "MUST only be present on the resource if the Condition is True" and recommend implementing them so kstatus observers can stop waiting without a timeout. Argo CD's Application conditions are error, warning and info typed entries with no status field, which behaves like abnormal-true.

Positive side. The Cluster API 2020 proposal recommends type suffixes `Ready` and `Succeeded` and "other suffix with positive meaning" and records that Pod conditions are consistently positive while Node conditions mix polarities. The conventions note that `Failed=False` can cause double-negative confusion. Config Connector uses a single positive `Ready`. kstatus's own `Ready` fallback treats False as InProgress and cannot distinguish doomed from slow.

Generic-tool misreadings. The only documented failure mode found is the README's. A kstatus maintainer said on issue 167 (2020-05-12) that `Stalled` is not named Failed because "it is hard in most cases to distinguish slow from doomed", and that the pending conventions change would move naming away from abnormal-true. Correction to wiki text: the wiki's gap entry says the Cluster API proposal leans positive. The 2020 proposal's suffix guidance leans positive, but its text and the 2024 proposal both say neither polarity can be recommended.

## Gap: Config Connector and Argo CD status semantics beyond health checks

Findings, Config Connector. Docs (page last updated 2026-11-10): `status` is read-only; the `Ready` condition conveys readiness and extra error or information through reason and message; important status changes also appear as Kubernetes events. The monitoring page lists event types (Updating, UpToDate, UpdateFailed, DependencyNotReady, DependencyNotFound, DependencyInvalid, Deleting, Deleted, DeleteFailed, ManagementConflict, PreActuationTransformFailed, PostActuationTransformFailed, Unmanaged). The docs label these as event types, but the same strings are used as `Ready` condition reasons in code. In `pkg/controller/lifecyclehandler/handler.go`, `setCondition` replaces the entire conditions list with one `Ready` entry, preserves `lastTransitionTime` when status is unchanged, and `setObservedGeneration` writes a top-level `status.observedGeneration`. A test golden file for a direct controller shows `Ready=False`, reason `UpdateFailed`, message "Update call failed: error updating: ..." and `observedGeneration: 1`. Generated types document `observedGeneration` as "If this is equal to metadata.generation, then ... the current reported status reflects the most recent desired state". Release 1.138 notes mention updating `status.observedGeneration` on the ConfigConnector object.

Findings, Argo CD. Argo CD's Config Connector health script (last changed 2026-10-30) handles three shapes: `ConfigConnector` and `ConfigConnectorContext` kinds via `status.healthy` gated on `observedGeneration`; `customize.core.cnrm.cloud.google.com` kinds that treat `observedGeneration` 0 as unset; and ordinary resources via `Ready`-condition reasons. Reason mapping: `UpToDate` with status True gives Healthy; `UpdateFailed` gives Degraded; `DependencyNotFound` gives Degraded; `DependencyNotReady` gives Suspended; everything else, including `Updating`, falls through to the default Progressing "Update in progress". Beyond health: an Application has a sync status of Synced, OutOfSync or Unknown; an Application condition list of error, warning and info entries (DeletionError, InvalidSpecError, ComparisonError, SyncError, UnknownError, SharedResourceWarning, RepeatedResourceWarning, ExcludedResourceWarning, OrphanedResourceWarning); `reconciledAt` and a deprecated `observedAt`. Resource tracking defaults to the `argocd.argoproj.io/tracking-id` annotation, and a tracking annotation that does not reference the resource it sits on does not affect sync status or pruning. Not read: the operation-state and sync-phase docs, and the controller code that aggregates per-resource sync status (the `sync-status.md` file is a 152-byte stub).

## Gap: Which parts of the Config Connector reconcile-status design shipped

Findings. The design document `docs/designs/reconcile-status.md` has one commit, 2026-01-30 ("Add design document for setting status during GCP updates"). It targets "direct" controllers only (non-goal: legacy Terraform and DCL controllers). Comparison with code on the default branch (release v1.162.0, 2026-11-23):

Shipped as designed: a single `Ready` condition type with at most one entry (the legacy handler replaces the list; the direct-controller `SetStatusCondition` finds and updates by type); `Ready=False` with reason `Updating` while an update is in progress (`HandleUpdating`, and direct controllers such as Bigtable memory layer pass `k8s.Updating`); `Ready=True` with reason `UpToDate`; top-level `status.observedGeneration` written on every `UpdateStatus` (the design's claim that `UpdateStatus` "already sets" it is accurate); and Kubernetes events with the same reason strings.

Shipped differently: the failure reason is `UpdateFailed`, not the design's `UpdateFailure`; the failure message is "Update call failed: ..." not "Failed to update resource (first field path: ...)"; the Updating message is "Update in progress"; the UpToDate message is "The resource is up to date" (design: "Resource is up to date").

Not found in code: the "first field path" message, a field-path extraction helper, the `Updating:<operation-id>` reason, and a per-condition `observedGeneration`. The LRO idea is in the design's "Future Considerations" and its non-goals, so absence is consistent with its stated scope. The direct-controller `RecordUpdatingEvent` emits an event, not a condition. Argo CD's shipped health script keys on `UpdateFailed`, which corroborates that name. Caveat: the code searches used GitHub's code search, which may lag; whether any open PR implements the design was not checked. The wiki example page's `UpdateFailure` wording therefore describes the design, not shipped behavior.
