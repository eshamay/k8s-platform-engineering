# Research dossier: gap cluster o4-config-connector-ack

Research date: 2026-11-26

## Overview

This pass read primary sources for four open gaps: Config Connector (KCC) installation modes and deletion policy, a direct Config Connector versus Crossplane comparison, direct reads of the Argo CD, Flux, ACK and Config Connector failure modes, and first-party pitfall evidence for kro, Config Connector, ACK and Cluster API. Sources were Google's installation and deletion docs, the KCC Go source and design docs read through the gh CLI, the Argo CD and Flux docs repositories, the ACK old and new documentation, the ACK and KCC issue trackers, and release notes for kro and Cluster API. Every version and date below came from a page read in this run. The date of the underlying file is given where the gh API exposes it.

The strongest new material is on Config Connector deletion. The documented `deletion-policy` annotation has exactly two named values in source, `delete` and `abandon`, and the controllers branch only on `abandon`. Namespaced mode is the CRD default and the documented recommendation, and it is implemented as a `ConfigConnectorContext` object per namespace. A first-party KCC design document describes the stuck-deletion case under missing dependencies, which is the mechanism behind the practitioner report of `DeleteFailed` children. No KCC document or source file read here gives ordered deletion. Open issues from 2021 and 2024 report the ordering problem and name annotation workarounds.

The Config Connector versus Crossplane comparison remains thin. The only direct treatments found are a Crossplane maintainer's 2021 blog post and 2020 issue comments, and a Google 2023 blog post that compares Config Connector with Terraform and never mentions Crossplane. No neutral side-by-side or cost-of-ownership study was found. The dossier records both vendors' positions with their sources and does not pick between them.

For failure modes, the Argo CD and Flux docs are specific about defaults, and ACK has two documentation sites that now disagree on some points (the old site is flagged deprecated by an ACK maintainer in an issue thread). First-party incident evidence for kro, ACK and Cluster API is mostly issue reports and release notes. The ACK items are one contributor's audit and are not independent corroboration. No named-organization postmortem was found for any of the four tools.

## Gap: Config Connector namespaced versus cluster mode and deletion policies

Namespaced mode is the default in the operator's `ConfigConnector` CRD and Google's installation page recommends it for most uses. In cluster mode a single Google service account (supplied through `googleServiceAccount` or `credentialSecretName`, never both) is used for every resource, even across several projects. In namespaced mode each enabled namespace needs its own `ConfigConnectorContext` that names its own Google service account, which gives per-namespace permission isolation. `ConfigConnectorContext` also carries per-namespace `requestProjectPolicy`, `billingProject`, `stateIntoSpec`, `actuationMode`, an immutable `managerNamespace` (controller managers are deployed there instead of `cnrm-system`), and experimental per-kind controller overrides. Namespace annotations such as `cnrm.cloud.google.com/project-id` select the target project, folder or organization when the resource itself does not say. The docs read do not state whether that annotation behavior differs between modes. The page that would settle it, the manual-install page, was not read.

For deletion, the documented default is that deleting the Kubernetes object deletes the Google Cloud resource. The annotation `cnrm.cloud.google.com/deletion-policy: abandon` keeps the cloud resource. Source defines the constants `delete` and `abandon`, and the helper `HasAbandonAnnotation` returns true only for `abandon`. The DCL controller and the direct controller both check it during finalization. I did not locate an equivalent branch in `pkg/controller/tf/tfcontroller.go` by pattern search, so the Terraform-based path is UNVERIFIED here. A separate deletion-defender controller puts a `cnrm.cloud.google.com/deletion-defender` finalizer on resources. If the CRD itself is being deleted (an uninstall), it removes both KCC finalizers and sets `abandon`, so uninstalling KCC does not delete cloud resources. A plain deletion of the Kubernetes object only removes the defender finalizer and lets the controller delete the cloud resource.

On ordering: no read doc or source describes a dependency-ordered teardown. A KCC design document (`graceful-orphan-deletion.md`, last commit 2026-02-09) describes a child whose parent was deleted first. The child's `DependencyNotFound` error blocks finalization indefinitely. The document is a proposal, and whether and when it shipped was not checked. Issue 534 (opened 2021-08-19, still open) reports the dataset-before-table case and gives two annotation workarounds. Issue 2894 (2024-10-10, open) says KCC lacks Terraform's dependency graph. Issue 13335 reports that `abandon` leaves `managed-by-cnrm` labels on the cloud resource. In that issue the reporter says they have not reproduced it on a current release, and the earlier report (#146) is cited only secondhand. Argo CD's own documentation says that during pruning the sync-wave order is reversed so higher waves go first, but the Argo CD app-deletion page (first 90 lines read) does not say cascade deletion honors waves. Neither the wiki's practitioner report nor the Argo CD docs are therefore contradicted, and the question of whether Argo CD deletes children unordered is left open here.

## Gap: Direct comparison of Config Connector and Crossplane

Options and sources, without a recommendation. The Crossplane side is argued by Crossplane's lead maintainer in a 2021 blog post and in 2020 comments on a provider-gcp issue. The positions are that Crossplane exposes a more opinionated resource model (consistent credentials, conditions, deletion policies and references across providers), adds composition to hide low-level APIs, packages providers and configurations, and makes managed resources cluster scoped, with namespaced claims offered on top. The same maintainer says that using Config Connector through the Kubernetes provider is acceptable but not "sufficient as a replacement" for a Crossplane provider. The Google side on that thread, a commenter whose issue metadata shows no association, notes that Config Connector is open source, has many resource types, can be wrapped in Crossplane compositions, and is being made kstatus-compatible. A Google Cloud blog post from 2023 describes Config Connector as a reconciling operator and compares it with Terraform and Cloud Build, not Crossplane. It also discourages the GKE add-on in production because of version lag, and it says Config Controller may bring Anthos fees.

Architecture and scope as read from first-party material. Config Connector covers Google Cloud only and has a namespaced or cluster install; Google's own docs make namespaced mode the default. Its resources are namespaced and carry a project, folder or organization through namespace annotations. Crossplane's managed resources were cluster scoped in the 2021 post. The current docs show an `.m.` namespaced API group example (`rds.aws.m.upbound.io`), so the 2021 statement is dated for v2. Whether any given Crossplane GCP provider reproduces Config Connector's resource coverage was not checked. Resource model: Crossplane providers follow the Crossplane resource model with `forProvider`, `atProvider` and `crossplane.io/external-name`, and Config Connector uses a spec and status with `resourceID` and the `state-into-spec` annotation. The structural difference visible in the sources is that Crossplane adds Composition, XRDs and packages, and Config Connector adds none of these (no composition layer was found in the docs read). Drift behavior: Crossplane's managed reconciler constant is a 1 minute poll with a per-resource `crossplane.io/poll-interval` annotation, and the runtime also accepts `managementPolicies` (beta) and `crossplane.io/paused`. Config Connector's mean re-enqueue is 10 minutes with a per-kind or per-resource override. A provider may set a different Crossplane default through its own flag, and that was not read. Cost of ownership: Config Connector charges nothing itself ("You will incur costs for these resources"), the manual install carries operational cost, and the add-on can lag the latest release by 12 months or more. No Crossplane cost-of-ownership statement or neutral measurement was found.

## Gap: Direct reads of Argo CD, Flux, ACK, and Config Connector failure modes

Argo CD. The automated-sync page documents defaults that explain common failures. Self-heal and prune are both off unless set. Automated sync tries once per commit and parameter combination and does not retry a previously failed attempt for the same commit. When self-heal is on the retry delay is 5 seconds, and the Git polling interval is 120 seconds with up to 60 seconds of jitter. Manual syncs do not prune unless `manualDefaults` is set, and once `manualDefaults` is present with any field, prune defaults to true, which the page flags with a warning. Safer controls are `Prune=false`, `Prune=confirm`, `Delete=false`, `Delete=confirm` and `PruneLast`. The prune propagation policy defaults to foreground. Application deletion cascades only with the resources finalizer, whose default is foreground deletion, and a non-cascading delete requires removing the finalizer first.

Flux. The kustomize-controller spec documents `prune` as required, and garbage collection also runs when the Kustomization is deleted. `deletionPolicy` takes `MirrorPrune` (default), `Delete`, `WaitForTermination` and `Orphan`. `WaitForTermination` is bounded by `.spec.timeout`, after which the controller logs an error and lets the Kustomization be deleted anyway. This is relevant to provider-managed resources with their own finalizers, because a timeout leaves the Kustomization gone while the cloud resource may still be deleting. Server-side apply field ownership is controlled by `kustomize.toolkit.fluxcd.io/ssa` (`Override`, `Merge`, `IfNotPresent`, `Ignore`). `Merge` cannot help with atomic list fields, and Flux cites the server-side apply KEP for that. `force` replaces resources on immutable-field failures, and the docs warn that forcing a StatefulSet may lose data. The troubleshooting cheatsheet lists `webhook does not support dry run` and repeated "configured" events caused by empty or null fields.

ACK. The deletion policy docs give the order resource annotation, namespace annotation, then controller flag, with values `delete` (default) and `retain`. The old docs site says drift is checked every 10 hours after `ResourceSynced` is true, and that all controllers default to that. The ACK 10 hour constant in runtime source was already verified in the wiki and not re-read here. Adoption has two documented generations. The old page marks `AdoptedResource` as no longer recommended and says the annotation-based feature is alpha with gates disabled by default. The new site describes the annotation-based adoption as a Beta feature enabled by default. A maintainer comment on ACK issue 3152 confirms the old site is deprecated. The new breaking-changes page records that from controller versions released on or after 2026-10-08, `--enable-cross-namespace` defaults to false.

Config Connector. Known-issues documents a webhook TLS race before 1.134.1 that blocked creating new resources while existing ones kept reconciling, a stricter `state-into-spec` validation in 1.134.0 that wedged `SQLInstance` in Updating until 1.134.2, and direct-reconciler regressions in 1.132.0 (duplicate controller name, a bad label value for `SecretManagerSecret`).
