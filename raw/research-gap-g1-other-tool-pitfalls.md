# Research dossier: gap cluster g1-other-tool-pitfalls

Research date: 2026-11-26

## Overview

This pass looked for first-party evidence (project GitHub issues, release notes, maintainer-authored docs) of pitfalls in kro, Config Connector (KCC), ACK, and Cluster API (CAPI). All material was read through the gh CLI as raw issue bodies and release notes on 2026-11-26. Tool versions and dates below come from those reads, not from memory. The kro repo has moved: issue and release URLs resolve under kubernetes-sigs/kro (formerly kro-run/kro).

The strongest evidence is for ACK and Config Connector. Both trackers hold detailed, reproduction-backed issues filed in September to November 2026. Several ACK issues share one reporter (gecube) and were filed in a batch on 2026-11-09, so they are one person's audit, not independent reports; all are still open and no maintainer fix is confirmed. The KCC issues come from several different reporters and cover deletion hangs, a stuck-Terminating state that `deletion-policy: abandon` cannot release, and silent drift on an immutable field. kro evidence is thinner: a crash-during-deletion issue found by a fault-injection tool (not a production incident), and a breaking-schema-change gate introduced in v0.8.0 with a user report on a long-lived cluster. CAPI produced release-note breaking changes and a webhook-availability issue during clusterctl upgrades, but no deletion or data-loss incident of the kind found for ACK and KCC.

None of these are named-organization production postmortems. Reporters are individuals or vendor staff (for example a reporter whose GitHub handle suggests Splunk affiliation on kro [corrected in verification: affiliation is inferred from the handle `dmarquez-splunk` only; the issue does not state it]), and the incidents are reproductions or near-misses rather than outage reports. Self-reported claims are labeled as such. Where an issue says "reproduced live," that is the reporter's statement; I did not reproduce anything.

## Gap: First-party pitfall and incident evidence for kro, Config Connector, ACK, and Cluster API

### kro

kro v0.8.0 added schema diffing that blocks breaking CRD changes by default, overridable with the `kro.run/allow-breaking-changes` annotation. A user report (#1395, 2026-09-04) says the block error did not name the annotation, so operators on a live cluster were led toward deleting and recreating the RGD; the reporter said the RGD drove per-AZ ENIConfig, so recreation was unsafe. Issue #1391 (2026-09-03, reporter dmarquez-splunk) says adding an `enum=` or CEL `validation=` marker to an existing field is accepted as Ready but never patched into the live CRD, so the CRD keeps accepting values the RGD now forbids. Issue #886 (2025-12-05) says one misconfigured RGD blocked updates to all other RGDs until the bad RGD was deleted and the controller pod restarted. It was open when read.

Issue #1171 (2026-03-19, kro v0.8.4) came from a fault-injection tool (kamera), not production. It reports that a controller crash mid-deletion can leave the instance with its finalizer, leave children alive, and, per the reporter, delete the CRD despite `allowCRDDeletion=false`. It was open and had only triage-bot comments plus one reporter `/remove-lifecycle stale` [corrected in verification: the reporter also commented once, 2026-06-23]. The v0.10.0 release (2026-11-10) lists later cleanup fixes ("Fix Graph cleanup after partial apply failures", "Fix Graph cleanup when child UIDs are missing"), but I did not tie them to #1171 and make no claim that they close it. v0.10.0 also adds per-resource deletion policy and unifies the engine on "Graph"; both are large changes to read before upgrading.

### Config Connector

KCC v1.162.0 was the latest release read (2026-11-23). Issue #16444 (2026-11-25) describes multi-cluster leader election: deleting objects on a standby that previously led leaves them Terminating, and when that cluster leads again it executes the stale deletion against GCP. The issue states the GitOps delete, re-create, failover sequence deletes live GCP resources with no error. Issue #15930 (2026-11-17, reproduced on v1.161.0 per the reporter) says Direct-controller resources stick in Terminating when a referenced or parent object is deleted first, and `deletion-policy: abandon` cannot release them, because reference resolution and the GCP read run before the deletion check. Issue #13335 (2026-09-20) says abandon leaves `managed-by-cnrm` and lease labels on the GCP resource [corrected in verification: the reporter says they did not reproduce this on a current release and took it from older issue #146, which was closed as not planned]. Issue #12944 (2026-09-15) says StorageBucket `spec.location` edits reconcile to Ready/UpToDate while the bucket stays put, since the immutability check was removed in 1.132.0; the reporter says they now reject such edits in their own validation layer.

### ACK

All of these ACK issues are open; all but #3122 were filed on 2026-11-09 [corrected in verification: #3122 was filed 2026-10-31]. Issue #3142 says ACK records ownership only in the CR status; nothing in AWS names an owner, so a restored cluster copy, two controller installs, or a rollout overlap can give one AWS resource two owners, and deleting a CR in one deletes the other's resource. Issue #3152 says adoption under Argo CD or Flux overwrites the adopted AWS resource with whatever spec is in git. Issue #3153 says a CR that drops out of git (prune) deletes the AWS resource and the DELETE cannot be undone once accepted. Issue #3154 says the namespace deletion-policy annotation is ignored in single `--watch-namespace` installs, so a namespace set to retain still has resources deleted. Issue #3136 says a failed spec patch during adoption lets the next reconcile write the CR's stub spec to AWS. #3122 reports duplicate orphaned EC2 resources from missing stable ClientTokens. All are by gecube except #3122 (sapphirew) [corrected in verification]; treat them as a single audit, not independent corroboration. No ACK release-note breaking changes were retrieved (see Not found).

### Cluster API

CAPI v1.14.0 release notes list 4 breaking changes, including a controller-runtime v0.24 bump and "Fix version validation in webhooks" (PR #13874, 2026-07-02), which the PR says tightens validation that allowed invalid pre-release or build tags. The same notes warn that v1beta1 is on track to be unserved in v1.16 and that Docker* resources are removed in v1.15. Issue #10522 (2024-04-26, by a maintainer) reports that cert-manager certificate rotation can make conversion and validating webhooks unreachable for up to 90 seconds, and says a clusterctl upgrade test (v0.4 to v1.6) failed from x509 errors on a validating webhook. It was open when read. Issue #11387 reports the `random` MachineSet delete policy ignored the `cluster.x-k8s.io/delete-machine` annotation. This is a minor behavioral inconsistency, not an incident. The latest stable releases read were v1.14.4 and v1.13.8 (2026-11-03); v1.15.0-rc.0 is a pre-release.

### Claims

1. Claim: kro v0.8.0 blocks breaking CRD schema changes by default and uses the `kro.run/allow-breaking-changes` annotation to override. Status: VERIFIED. URL: https://github.com/kubernetes-sigs/kro/releases/tag/v0.8.0. Version: v0.8.0. Quote: "blocks incompatible changes (like removing fields, changing types, or adding required properties) by default".
2. Claim: the block error did not name the override annotation, and recreating the RGD was risky on a live cluster. Status: VERIFIED (as the reporter's claim, JacobGabrielson, 2026-09-04). URL: https://github.com/kubernetes-sigs/kro/issues/1395. Version: open issue. Quote: "Operators reasonably conclude the only way forward is to delete and recreate the RGD".
3. Claim: adding enum or CEL validation to an existing RGD field is not detected as a CRD change, so the live CRD is not updated. Status: VERIFIED (reporter claim, with code reference). URL: https://github.com/kubernetes-sigs/kro/issues/1391. Version: 2026-09-03, open. Quote: "never patches the live CRD's `openAPIV3Schema` to add the constraint".
4. Claim: one unhealthy RGD blocks updates to all other RGDs until deleted and the controller restarted. Status: VERIFIED (reporter claim, toweroy, 2025-12-05). URL: https://github.com/kubernetes-sigs/kro/issues/886. Version: open. Quote: "all new changes to every `ResourceGraphDefinition` will be blocked".

6. Claim: kro v0.10.0 (2026-11-10) includes graph-cleanup fixes and a per-resource deletion policy. Status: VERIFIED (release notes list only). URL: https://github.com/kubernetes-sigs/kro/releases/tag/v0.10.0. Version: v0.10.0. Quote: "Fix Graph cleanup after partial apply failures".
