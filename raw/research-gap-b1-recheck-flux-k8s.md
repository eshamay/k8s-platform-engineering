## Gap: Flux default reconcile interval and drift-detection wording

Findings. The jitter is applied by the shared package `github.com/fluxcd/pkg/runtime/jitter`. The flag `--interval-jitter-percentage` has a default of 5 (uint8), documented on the kustomize-controller options page as "(default 5)". The jitter is symmetric: `Percent(p)` draws a random factor between -p and +p, so 5 means plus or minus 5 percent of the interval. Both kustomize-controller and helm-controller bind the flag and call `SetGlobalJitter`. kustomize-controller wraps its requeue in `jitter.JitteredIntervalDuration(obj.GetRequeueAfter())`. The default was set to plus or minus 5 percent by commit b73ba327 on 2023-08-07 ("runtime/jitter: change default to +/-5%"). Jitter is not applied when p is 0 or 100 or more. A code comment in the package uses "requeue every 5 minutes" as a worked example (1000 resources, concurrency 50), which is a plausible secondary source of five-minute folklore but is an example, not a default; that attribution is my inference and is UNVERIFIED.

Origin of the five-minute wording. In fluxcd/website, content/en/docs/concepts.md read "The reconciliation runs every one minute by default" at commit f691a9a0 (2022-02-01). Commit 962bf6f9 on 2022-08-10 by Stefan Prodan, titled "Add OCIRepository docs", changed that line to "every five minutes by default". The commit message body carries only a sign-off, so the reason is not stated. The file moved to content/en/flux/concepts.md on 2022-08-30 and the sentence is unchanged on the current main branch (last edits to the file 2026-04-21 touched other text). Only a diff of the commit shows the change; no issue or PR discussion was located (searched the commit, the website repo code search for "every five minutes", and the controller docs).

Reference wording that conflicts. The Kustomization reference says `.spec.interval` "is a required field" and "The minimum value should be 60 seconds", and notes that a generation change or source revision change "is handled instantly outside the interval window". It also says the controller can apply jitter, linking to the options page.

## Gap: Flux pre-dry-run manager takeover flag and current SSA documentation

Findings. The earlier dossier settled the kustomize-controller flag. The options page (read here) lists both flags: `--override-manager` ("Field manager disallowed to perform changes on managed resources") and `--override-manager-before-dry-run` ("Field manager taken over before the server-side apply dry-run"). It explains that `--override-manager` "takes over the named field managers only after a successful server-side apply dry-run", and the before-dry-run flag is for recovering stuck objects and should be removed after.

The remaining items were the helm-controller side. helm-controller main.go defines `--override-manager` as a string-array flag, help text "List of field managers to override during drift detection." The changelog for helm-controller 1.5.0 (release date 2026-02-20, matching the GitHub release timestamp 2026-02-20T11:21:16Z) says the flag was added in that release (PR 1365) and states that helm-controller drift detection and correction "is completely unrelated to Helm v4's server-side apply support, and was implemented long before Helm v4 was released." That release also moved helm-controller to Helm v4 and defaulted new HelmReleases to server-side apply.

HelmRelease driftDetection: the Go type says the mode "defaults to DiffModeDisabled" with enum `enabled`, `warn`, `disabled`. With `warn` or `enabled`, and when the desired state matches the Helm storage release, the controller compares the stored manifest against the cluster with a server-side dry-run apply, emits an event and logs a JSON Patch at debug level; with `enabled` it corrects by creating and patching resources based on the dry-run result. Ignore rules are JSON Pointers with optional target selectors, and the annotation `helm.toolkit.fluxcd.io/driftDetection: disabled` excludes a resource.

Helm 4 server-side apply: the helm.sh overview says Helm 4 defaults to SSA for new releases and follows the previous release's method on upgrade and rollback, so Helm 3 releases stay client-side after upgrading to Helm 4. The helm CLI has `--server-side` taking true, false, or auto (auto follows the previous release) and `--force-conflicts`, which is mutually exclusive with `--force-replace` [corrected in verification: upgrade.go marks it mutually exclusive with both `force-replace` and the deprecated `force`]. helm-controller exposes this as `.spec.install.serverSideApply` (boolean, default true, or false under the `UseHelm3Defaults` gate) and `.spec.upgrade.serverSideApply` / rollback equivalents (`enabled`, `disabled`, `auto`, default `auto`); `force` is "ignored for server-side apply (which always forces conflicts with other field managers)". The controller go.mod pins helm.sh/helm/v4 v4.3.1.

## Gap: StorageVersionMigration GA details in Kubernetes v1.37

Findings. The progress-condition layout at v1.37.0 is now read from source. The v1 type (`storagemigration.k8s.io/v1`, `prerelease-lifecycle-gen:introduced=1.37`) has `spec.resource` (immutable GroupResource) and `status` with `conditions` (a map list keyed by `type`, standard `metav1.Condition`) and `resourceVersion`. Condition types are `Running`, `Succeeded`, `Failed`. There is no numeric progress field. Progress is carried in the `message` of the `Running` condition, built by `migrationRunningMessage`: "The migration is running", then either ", N/M objects not yet migrated" while objects remain, or ", M objects verified migrated" when none remain, and "; transient error: <err>" if a transient error occurred. The controller sets Reason `MigrationRunning`, and on success sets `Succeeded` true with Reason `StorageVersionMigrationSucceeded` and Message "Migration completed"; on failure `Failed` true with Reason `StorageVersionMigrationFailed`. When migration completes, the controller flips `Running` to False with Reason `MigrationCompleted`, Message "Migration completed". The Running message is only written when its content changes (SetStatusCondition) and an update call is made at the end of each pass. Also for CRDs, the controller sets a `StorageMigrating` condition on the CRD and, per PR 135297 (merged 2026-03-11, "Remove CRD stored versions from status upon SVM migration"), removes old stored versions from the CRD status after migration.

Whether this is user-triggered: the earlier dossier already settled that the user creates the object; not re-checked here. GA via PR 138560 (merged 2026-07-08, "Promote SVM to GA") was seen in the PR list.

Fair queuing. The README says the current solution is "dissatisfying" in two ways: it allocates seats equally rather than max-min fairly, and it executes one request per queue at a time in the virtual world, cutting corners that a fully accurate version would need to revise. The equations: `rho(i,t)` is the sum of widths of arrived-but-unfinished requests, `mu_equal(t) = min(C, Sum rho) / NEQ(t)` for non-empty queues, `rate(i,t) = mu_equal(t) / NOS(i,t)`, and a request's virtual finish solves an integral of rate equal to its estimated length `len`, with an initial guess `G` for unfinished requests.

LIST width: `width_cpu(N) = min(A, B*N)`, `width_ram(N) = D*N`, combined `width(n) = max(min(A, B*N), D*N)`, approximated as `width_approx(n) = min(A, ceil(N/E))`, E = 1/B; the text says a back-of-envelope estimate (4 GB per CPU, 10 kB objects) puts the memory-dominates point at about 400,000 objects, and "[TODO: describe how `N` is estimated.]" remains in the text. Widths are capped at the priority level's seats rather than rejected (the text says borrowing was not yet done at that point). Shuffle sharding example: numQueues=128, handSize=6.
