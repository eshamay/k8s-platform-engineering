# Research dossier: gap cluster m6-admission-crds

Research date: 2026-11-26

## Overview

This pass read primary sources for six open gaps about admission and CRDs: GitHub source files and Helm values at the default branch (read through the gh CLI on 2026-11-26), upstream issues and pull requests, and the official etcd, Kyverno, Gatekeeper, Backstage and Kubernetes pages. The gh API reports the following as latest releases on the read date: Kubernetes v1.37.3, Crossplane v2.5.0, kro v0.10.0, Argo CD v3.6.3, Config Connector v1.162.0, ACK s3-controller v1.16.0, Cluster API v1.14.4, Gatekeeper v3.23.1, Kyverno v1.20.0, Backstage v1.57.3. File contents quoted below are from the default branch at read time, which can be ahead of those tags.

Admission differs sharply by tool. Config Connector and Cluster API ship many webhooks, all with failurePolicy Fail. Crossplane core ships exactly one (a delete-protection webhook for Usages, Fail by default, overridable) and has replaced its older XRD and Composition webhooks with CEL. Gatekeeper ships fail-open (Ignore) webhooks by default with a documented fail-closed path. kro, Argo CD and the ACK service controller chart ship no admission webhook in what was read; kro leans on CRD-level CEL, ACK's runtime has only a conversion-webhook framework. Kyverno defaults the failure policy of policy-driven webhooks to Fail, excludes only its own namespace and kube-system by default, and documents three admission replicas as the minimum for HA.

The CEL cost limits are now settled from source: a per-expression static estimate of 10,000,000, a per-CRD estimated total of 100,000,000, a runtime per-call limit of 1,000,000 and a runtime budget of 10,000,000 per custom resource or policy binding. The garbage-collector problem is fixed upstream: pull request 125796 merged 2024-09-25, milestone v1.32, and its release note appears in the 1.32 changelog. The remaining caveat is that owner references with blockOwnerDeletion on an unsynced resource type are not seen by the collector. CRD scale has no official count limit in the SIG Scalability thresholds, which cover built-in types only; the evidence is a set of issues with measured behavior (CPU spike near 700 CRDs, about 8 GiB apiserver RSS near 1,900 CRDs) and a still-open one-etcd-client-per-CRD issue.

CRD handling for Cluster API, Config Connector, ACK and Backstage is partly answered: CAPI has a contract label scheme, a CRD migrator and conversion webhooks; Config Connector ships 883 CRD files, the largest about 579 KB; ACK ships one Helm chart per service with CRDs in the chart; Backstage consumes CRDs only through an explicit customResources list. ACK API-version policy and Backstage behavior beyond its documented config were not found.

## Gap: Admission behavior of Crossplane, kro, Argo CD, Config Connector, ACK, Cluster API, and Gatekeeper

Crossplane core (v2.5.0 read via its latest release tag; files read on main) installs a ValidatingWebhookConfiguration named crossplane-no-usages that fires on DELETE for any resource carrying the label crossplane.io/in-use=true, with failurePolicy Fail. The failure policy can be set to Ignore through a flag and Helm value, and the chart comment says this is for managed-Kubernetes operations that reject Fail-policy webhooks with wildcard rules (AKS cluster stop is named). The init code also removes the former validating webhooks for compositeresourcedefinitions and compositions with a code comment that Crossplane now uses CEL validation. The chart value webhooks.enabled covers Crossplane and installed provider packages.

kro (v0.10.0) has no webhook templates in its Helm chart. Its docs say instance validation is done by Kubernetes against the generated CRD, and SimpleSchema has a validation marker whose CEL rule is evaluated by the API server. An integration test shows kro reporting a third-party webhook denial in instance status, so kro is a client of other people's admission.

Argo CD (v3.6.3 tree): no webhook configuration under manifests or charts paths (searched tree paths for "webhook"; found nothing in those paths). The relevant admission-adjacent fact is the sync-options doc on the 262144-byte annotation limit for client-side apply.

Config Connector (v1.162.0) ships a separate webhook-manager Deployment (HPA minReplicas 2, maxReplicas 20) and registers handlers in pkg/webhook/register.go, each with FailurePolicy Fail: immutable-field denial, unknown-field denial, IAM validation, IAM defaulting, container-annotation handling, management-conflict annotation defaulting, generic defaulter, resource validation, state-into-spec validation, and abandon-on-uninstall. Selection is by rules and objectSelector; no namespaceSelector field is set in the generated config (manifests.go sets Rules, ObjectSelector, FailurePolicy, SideEffects). Timeout is left at the Kubernetes default, per a code comment.

ACK: the shared runtime package defines only a conversion webhook type (validating and defaulting types are a TODO). The s3-controller chart (v1.16.0) has no webhook template and its deployment has no webhook reference. ACK therefore relies on CRD schema validation plus controller-side checks.

Cluster API (v1.14.4 tag; core/config/webhook/manifests.yaml on main) ships mutating (defaulting) and validating webhooks for Cluster, ClusterClass, ClusterResourceSet, ExtensionConfig, Machine, MachineDeployment, MachineHealthCheck, MachinePool, MachineSet, IPAddress and more, every one failurePolicy Fail, plus CRD conversion webhooks (strategy Webhook, path /convert). Namespace exclusion was not found in those manifests.

Gatekeeper (v3.23.1) defaults validatingWebhookFailurePolicy and mutatingWebhookFailurePolicy to Ignore (timeouts 3 s and 1 s, 3 replicas), keeps a separate check-ignore webhook at Fail, excludes namespaces labeled admission.gatekeeper.sh/ignore, supports a Config resource with excludedNamespaces per process, and integrates with ValidatingAdmissionPolicy (stable v3.18, VAP management beta v3.20 per its doc).

## Gap: Kyverno webhook failure modes and availability

Kyverno's website docs (main, read 2026-11-26; Kyverno latest release v1.20.0, published 2026-11-12) say the failure policy controls what happens when a request times out or errors: the default Fail rejects, Ignore allows. It is set per policy (spec.failurePolicy) with webhook timeout per policy (spec.webhookConfiguration.timeoutSeconds, default 10, range 1 to 30). The chart/config option forceFailurePolicyIgnore defaults to false. Webhooks are generated dynamically from installed policies. If auto-update is disabled, Kyverno creates catch-all webhooks with failurePolicy Ignore. By default the Kyverno and kube-system namespaces are excluded through a namespaceSelector in the ConfigMap.

The troubleshooting page names the failure mode: if all Kyverno pods are down and policies are fail-closed on Pods, API requests time out; this is "usually only the case when the Kyverno Namespace has not been excluded". Recovery is deleting the resource validating and mutating webhook configurations (kyverno-resource-validating-webhook-cfg and kyverno-resource-mutating-webhook-cfg); Kyverno recreates them. The HA guide says the admission controller does not use leader election for requests, and "the minimum supported replica count for a highly-available admission controller deployment is three". Wildcard-matching policies send every request to Kyverno and can double or triple resource needs.

Not found: any measured availability numbers, and any page read comparing Kyverno-generated native ValidatingAdmissionPolicy resilience to webhook mode (the wiki comparison page's resilience claim stays unquantified).

## Gap: CEL cost limits and per-request budgets

The numbers are in Kubernetes source (master at read time; latest release v1.37.3). In staging/src/k8s.io/apiserver/pkg/apis/cel/config.go: PerCallLimit 1,000,000 ("roughly 0.1 second for each expression validation call"), RuntimeCELCostBudget 10,000,000 (overall per ValidatingAdmissionPolicyBinding or custom resource, "roughly 1 seconds"), RuntimeCELCostBudgetMatchConditions 2,500,000 (about a quarter second, per webhook or per binding), MaxRequestSizeBytes 3 MiB (used as a worst-case size), MaxEvaluatedMessageExpressionSizeBytes 5 KiB. In apiextensions validation.go: StaticEstimatedCostLimit 10,000,000 per expression and StaticEstimatedCRDCostLimit 100,000,000 for the total of all x-kubernetes-validations rules of a CRD. The per-expression check is suppressed when the schema is unchanged (suppressPerExpressionCost), so older CRDs are not broken by tightened estimates.

How authors hit them: the official CRD docs say the estimator assumes the worst case when a list, map or string has no bound, so rules that iterate need maxItems, maxProperties and maxLength. The doc example `self.all(x, x.contains('a string'))` on an unbounded array of strings is rejected on budget grounds; with maxItems 25 and maxLength 10 it is accepted. The estimate multiplies by how many times a rule runs (nested lists multiply).

## Gap: CRD scale limits

No official CRD-count or per-type custom-resource limit was found. The SIG Scalability thresholds document says its thresholds are for built-in types: 150,000 objects per resource type (non-Event), 1.5 MB per object, 3 GB total per type, 5,000 nodes, 10,000 namespaces. It was last edited after December 2025 (mentions kops tests since Dec 2025). A search for "custom" and "CRD" in it found nothing beyond the license. So the answer to "authoritative limits" is: not documented for CRDs.

Per-object size: etcd's docs state a default maximum request size of 1.5 MiB (flag --max-request-bytes) and a default storage limit of 2 GiB with 8 GiB suggested maximum. The apiserver's own default MaxRequestBodyBytes is 3 MiB (config.go), above the etcd default, so the etcd limit is the binding one unless etcd is reconfigured. The 1.5 MB figure from the secondary source is therefore consistent with both the etcd doc (1.5 MiB) and the scalability doc (1.5MB).

Measured behavior (issue reports, not benchmarks): Crossplane reported a kube-apiserver CPU spike when posting just over 700 CRDs at once, from the background OpenAPI publishing job, and instability on GKE at 685 CRDs (issue 105932, closed 2021-11-10; commenters said kube-openapi PR 251 would likely fix or alleviate it). Crossplane also reported about 8 GiB apiserver RSS with about 1,900 CRDs, with about 1.5 GiB from the etcd client logger (issue 111476, closed 2022-08-01). Issue 111622 (open) records that the API server creates one etcd client per CRD, costing memory and TCP connections. Issue 82292 (open) records CRD size trouble: the 262144-byte last-applied annotation, a 700 KB single-version CRD, a size distribution over 5,519 CRDs (99th percentile 27,617 B, max 171,823 B), and Strimzi's Kafka CRD at 1,231,093 bytes.

## Gap: Status of the conversion webhook and garbage collection problem

Fixed upstream for the stall, with a stated remaining limitation. Issue 110720 was closed 2022-06-24 as a duplicate of 101078 by a maintainer (liggitt), whose recommendation was that the collector stop blocking on discovery or informer sync, since the block exists only for blockOwnerDeletion, which is already advisory and racy. Issue 101078 ("Creating a CRD with broken converter webhook prevents GC controller from initialization") stayed open through several abandoned attempts: PR 110858 (closed unmerged 2024-02-04), PR 120164 (closed unmerged 2024-08-28). PR 125796 "garbagecollector: controller should not be blocking on failed cache sync" merged 2024-09-25 with milestone v1.32, and 101078 was closed as completed at the same moment. A follow-up report (issue 127105, opened 2024-09-04, closed 2024-10-08) described the same stall in an HA kind cluster.

The release note, present in the Kubernetes 1.32 changelog, says the collector can continue when a resource cannot be listed or watched, and that "Any objects in the unsynced resource type with owner references with `blockOwnerDeletion: true` will not be known to the garbage collector." Current source (master) logs "not all resource monitors could be synced, proceeding anyways", and in the periodic sync it no longer waits for sync before workers run: "gc worker no longer waits for cache to be synced". Not settled: a down webhook still leaves that resource type unwatched by the collector (errors, metric GarbageCollectorResourcesSyncError), so cascading deletes for owners and dependents of that type are not handled until the webhook recovers; no source read measures how long dependents linger or whether partial-informer-sync work beyond this PR exists. The workaround comment in 101078 (delete the converter webhook while the controller is down, or run multiple replicas) predates the fix.

## Gap: CRD handling in Cluster API, Config Connector, ACK, and Backstage

Cluster API: providers must label their CRDs with cluster.x-k8s.io/<version> mapping the CAPI contract version to the provider CRD versions (underscore-delimited list), which lets controllers convert object references automatically. The release-versus-contract rules say breaking changes within a contract version are not allowed. CAPI also runs a CRD migrator (controllers/crdmigrator) that performs storage-version migration (no-op patches to all custom resources, then sets status.storedVersions) and cleans managedFields for apiVersions no longer served. It has an option to migrate via the status endpoint because mutating and validating webhooks usually are not configured on status, and webhook errors would otherwise block the no-op updates.
