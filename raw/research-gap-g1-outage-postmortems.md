## Overview

This pass tried to settle four gaps with primary-source outage write-ups. Two succeeded fully in the sense of reading the original text: OpenAI's own December 11, 2024 post-mortem (published on its status page) and Jetstack's 2019 admission-webhook outage post (read through a Wayback Machine capture of the Venafi-hosted copy, because the original blog.jetstack.io URL returned an empty page to the scraper). A third, Neon's May 2025 delayed-start postmortem, is a real 2025 incident on Kubernetes (AWS CNI IP exhaustion triggered by a control-plane database slowdown), but I could only read it on a Vercel preview mirror, not neon.com, so it is marked SECONDARY-ONLY. [corrected in verification: https://neon.com/blog/postmortem-delayed-start-compute-operations is fetchable and has identical text (author line Em Sharnoff, Mihai Bojin; dated May 21, 2025), so the Neon claims below are upgraded to VERIFIED (self-reported by Neon, primary host).]

The two incidents read in full share one shape: a component that sits on the critical path of the Kubernetes API (an OPA validating webhook on writes; a fleet-wide telemetry agent making expensive API calls) degraded the control plane, and the fix then required control-plane access that the failure had removed. OpenAI states this explicitly as being "locked out"; Jetstack's fix was possible only because the API server answered intermittently, letting them delete the webhook configuration. In both cases a delayed-visibility mechanism (DNS cache; staged master upgrade) let the damage spread before it was understood.

The research tooling was weak in this run: web_search returned no results for many queries and returned mostly SEO or aggregator pages for others. I did not find primary write-ups for CRD-deletion cascades or etcd quota alarms in 2024 to 2026, did not read the Airbnb KubeCon NA 2020 talk (video only), and found no 2024 to 2026 GitOps-tool (Argo CD, Flux) or Crossplane incident postmortems. These are listed under "Not found". The k8s.af index (read via its Codeberg repository README) has 78 entries; by the year tags in the entry titles, the newest is 2023 (Reddit Pi-Day), so it contains no 2024 to 2026 material.

## Gap: Contents of the k8s.af admission webhook postmortems

The k8s.af index entry for the 2019 Jetstack post lists "involved: ValidatingWebhookConfiguration, GKE node auto-repair" and the impact as "prolonged downtime of non-prod environment, nodes lost, failed master upgrade". I read the post itself (via Wayback). Setting: regional GKE cluster in europe-west1, dev cluster shared by many teams, master upgrade through a Terraform pipeline with a 20 minute timeout. Mechanism, as established with Google Support: during the second master's upgrade the API server could not complete the ca-registration PostStartHook, which updates the ConfigMap extension-apiserver-authentication in kube-system; that write was subject to the OPA validating webhook, whose backend was not responding, so the write timed out, the master failed its health check and crash-looped, and the upgrade halted. Intermittent API downtime stopped kubelets reporting node health, so GKE node auto-repair recreated nodes in an endless loop, causing loss of service for all tenants.

Mitigation: delete the ValidatingAdmissionWebhook resource (possible because the API was intermittently reachable). Follow-ups: scope the webhook to namespaces where policy applies and teams have access, enable it only for Ingress and Service, add a livenessProbe to OPA, update OPA docs (PRs 1435 and 1605). They kept node auto-repair on. Their takeaways: alert on API server response times for CREATE and UPDATE; use a Helm chart that encodes probes. Self-reported by Jetstack/Venafi; the upstream issue kubernetes/kubernetes#54522 was cited as open at capture time (not read here).

The Airbnb KubeCon NA 2020 talk "10 More Weird Ways to Blow Up Your Kubernetes" is a YouTube video; k8s.af tags it with MutatingAdmissionWebhook, CPU Limits, OOMKill, kube2iam, HPA and "impact: outages". I could not obtain a transcript, so the contents remain unread.

## Gap: Primary OpenAI Kubernetes outage postmortem

Primary source located and read in full: OpenAI's status page incident of 2024-12-11, which embeds the post-mortem. Answers to the gap's questions: telemetry service: a new service deployed at 3:12 PM PST to collect detailed Kubernetes control plane metrics; its configuration made every node execute expensive API operations scaling with cluster size. API server load: with thousands of nodes doing this at once the API servers were overwhelmed in most large clusters. DNS dependency: the data plane can run mostly independently, but DNS relies on the control plane; DNS caching hid the failure for about 20 minutes while the rollout continued, then expiring caches multiplied DNS load. List and watch clients: the write-up does not use the words list or watch; it says only "resource-intensive Kubernetes API operations". Any claim that these were list/watch calls is therefore not supported by the primary text (secondary commentary may infer it).

Impact window: 3:16 PM to 7:38 PM PST; all services degraded. Remediation was slow because the fix (remove the telemetry service) required control-plane access that the load had removed. Workstreams run in parallel: scale down cluster size, block network access to Kubernetes admin APIs, scale up API servers. Prevention list: phased rollouts with cluster-health monitoring, fault injection, break-glass control-plane access, decouple data plane from control plane (DNS), faster recovery with caching and dynamic rate limiters. All figures are self-reported by OpenAI. Staging testing missed it because impact was specific to larger clusters.
