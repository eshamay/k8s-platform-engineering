# Research dossier: gap cluster m5-informers-caches

Research date: 2026-11-26

## Overview

This pass read primary sources for all eight gaps: client-go and controller-runtime Go source, the kubernetes/community Controller Writing Guide, the archived Kubernetes architecture design proposals, KEP-3352, controller-runtime release notes and PRs, Flux, Crossplane, kro, Config Connector, ACK, Cluster API and Argo CD source or docs. Source files were read on the default branch (main or master) on 2026-11-26 through the gh CLI; where a release tag was read, the tag is named. Branch reads are not pinned to a release, so field names and defaults may differ in older tagged releases.

The main results: resync in client-go replays objects from the informer's local store as update events and does not contact the API server (source comment, quoted below). controller-runtime's SyncPeriod is built on that and its own godoc says it "does not sync between the local cache and the server". The "Level driven, not edge driven" quote is point 3 of the "Guidelines" list in contributors/devel/sig-api-machinery/controllers.md in kubernetes/community; the earlier design principle ("Functionality must be level-based") is in the archived architecture principles doc, and Tim Hockin's 2017 deck and a 2018 Hacker Noon post (quoting Joe Beda via Cloud Native Infrastructure) are the popular explanations. The Beda quote's original wording in the O'Reilly book was NOT read.

For the cache and tool-comparison gaps, the source shows a clear spread of choices. controller-runtime offers per-type selectors, transforms, namespace scoping, metadata-only informers and a client-side DisableFor list. Flux controllers each run their own manager, narrow caches with a watch label selector, and keep Secrets and ConfigMaps out of the cache unless a feature gate is on. Crossplane core strips CRD schemas via a transform and disables caching for Secrets; its docs describe poll-interval, sync-interval and max-reconcile-rate but do not describe informer sharding. kro keeps one metadata-only informer per GVR. Config Connector caches only its own config kinds by default. ACK scopes by namespace and label selector. Cluster API caches only cluster-labelled Secrets and a separate per-workload-cluster cache.

On keying: controller-runtime keys informers by GVK (and maps to a GVR at creation through the RESTMapper), client-go's typed factory keys by Go type, and its dynamic and metadata factories key by GVR. Argo CD, ACK and Config Connector key by group and kind with no version; Cluster API resolves the version from CRD contract labels. The v0.3.0 release notes list "DynamicRESTMapper that reloads on REST cache miss (#554)" and the v0.3.0 manager source shows it as the default MapperProvider. KEP-3352 gives the aggregated discovery rationale. Behavior on CRD removal or scope change in controller-runtime is only partly documented by closed issues.

## Gap: Informer resync semantics

Findings. client-go's SharedInformer interface comment states the resync operation delivers an update notification for every object in the local cache and adds no interaction with the authoritative storage. The Reflector calls store.Resync() on a timer, and DeltaFIFO.Resync re-queues keys from knownObjects (the local store) as Sync deltas. A zero period means no resync. The comment also says HasSynced is "unrelated to resync", so resync is distinct from the initial LIST or any relist after a watch failure. controller-runtime documents SyncPeriod (default 10 hours, with jitter) as an artificial Update event with ObjectOld equal to ObjectNew, and says predicates such as GenerationChangedPredicate filter it out; it recommends RequeueAfter instead of changing SyncPeriod to guard against missed watch events. Related finding: kro's flag help text calls its resync "re list", and ACK's "resync" is a RequeueAfter on a successful reconcile, not an informer resync, so the word is used for different mechanisms.

## Gap: Cache narrowing options in controller-runtime

Findings. cache.Options (main) provides: ByObject (per-GVK overrides), DefaultNamespaces and per-ByObject Namespaces, DefaultLabelSelector and DefaultFieldSelector (with ByObject Label and Field), DefaultTransform and ByObject Transform, DefaultDropManagedFields and ByObject DropManagedFields, DefaultUnsafeDisableDeepCopy, ReaderFailOnMissingInformer, and SyncPeriod. TransformStripManagedFields is shipped for the common memory saving. Precedence is ByObject, then DefaultNamespaces[ns], then Default*. On the client side, client.Options.Cache.DisableFor sends reads for listed types to the API server, and Unstructured defaults to false so unstructured reads bypass the cache. The builder offers OnlyMetadata, which uses PartialObjectMetadata informers (a separate Metadata map in the informer tracker). Costs documented in source: DropManagedFields should not be enabled if you read managedFields from cached objects; unsafe disable-deep-copy risks mutation of shared cache objects (field exists, risk text not quoted here); DisableFor means every read is a live API call. The unread blog cited by the gap was not re-read; the package source answers the question directly. Cost numbers (memory savings) were NOT measured here.

## Gap: Flux shared caches and Crossplane performance guidance

Findings. Flux: the source-, kustomize- and helm-controllers each build their own controller-runtime manager (separate processes), so informer caches are per controller and not shared across controllers. Each narrows the cache for its own custom kinds with ByObject Label watchSelector (from --watch-label-selector), optionally limits to a --watch-namespace, and appends Secret and ConfigMap to client DisableFor unless the CacheSecretsAndConfigMaps feature gate is on (flux pkg comment: "resulting in increased memory usage and cluster-wide RBAC permissions"). The sharding docs say extra replicas are failover standbys that add no capacity and horizontal scaling is by running extra controller instances with a label selector on sharding.fluxcd.io/key. The vertical-scaling docs recommend more workers and limits, in-memory kustomize builds, and a Helm index cache in source-controller. Defaults read from source: kustomize-controller --concurrent 4, helm-controller 4, source-controller 2.

Crossplane: the guessed performance URL (docs.crossplane.io/latest/guides/performance/) scraped as empty. The docs repo has no performance guide file; the closest official guidance is the "Crossplane Pods" guide (poll-interval default one minute, sync-interval default one hour, max-reconcile-rate, providers have their own rate) and an Upbound KB article on provider reconcile rates (poll interval 30m or 1h cuts drift checks 3x or 6x; cache rebuilt on restart causing a burst). Core source (main) sets default max reconcile 100, SyncPeriod from sync-interval, DisableFor Secret, and a transform that strips OpenAPI schemas from typed CRDs in the API-extensions cache. No sharding guidance was found in the Crossplane docs. Doc default and source default for poll-interval agree (1m); the docs say "sync-interval" default one hour, which was not cross-checked against the source flag default.

## Gap: Informer and cache behavior keyed by GVR

Findings. Three keying schemes coexist. (1) client-go's generated typed factory keys informers by Go type (map[reflect.Type]SharedIndexInformer). (2) client-go's dynamic and metadata factories key by GroupVersionResource. (3) controller-runtime's informer tracker keys by GroupVersionKind, in three maps (Structured, Unstructured, Metadata); when an informer is created it calls mapper.RESTMapping(gvk.GroupKind(), gvk.Version) to get the GVR for the ListWatch. cache.RemoveInformer deletes the GVK entry; the code comment says the informer is deactivated and removed. Another closed issue (2589) reports a controller started before its CRD existed did not recover until a cache sync timeout (about two minutes) restarted it; it was closed by the stale bot without a fix. Behavior of a running informer when its CRD is deleted, or served versions change, was NOT read from source or docs in this pass.

## Gap: controller-runtime v0.3.0 dynamic mapper claim and aggregated discovery rationale

Findings. The v0.3.0 release notes (published 2019-10-10) list under New Features "DynamicRESTMapper that reloads on REST cache miss (#554)". ## Gap: How Argo CD, Config Connector, ACK, and Cluster API key resources by GVK

Findings. Argo CD: the tracking annotation encodes group, kind, namespace and name, with no version (example: my-app:apps/Deployment:default/my-deployment). The gitops-engine ResourceKey struct has exactly Group, Kind, Namespace and Name, built from the object's GVK by dropping the version; the cluster cache indexes API metadata by GroupKind and watches the preferred versions of API resources. Managed live objects are converted to the target manifest's version for comparison (ConvertToVersion call at gitops-engine cluster.go). Consequence in source: a manifest using a different version of the same group and kind maps to the same resource key, so an API version change does not by itself orphan or mis-prune; a group or kind change would. Removal of a served version that the live preferred-version listing depends on was not tested. Config Connector: a registration controller watches CRDs and registers one controller per group and kind, taking the version from the CRD (k8s.GetVersionFromCRD), and re-registered kinds update the schema in place. ACK: resource manager factories are stored in a map keyed by GroupKind string; each controller is built For(rd.EmptyRuntimeObject()) of one version. Cluster API: references in v1beta2 (ContractVersionedObjectReference) carry apiGroup and kind but no version; the version is resolved from the referenced CRD's contract labels, choosing the latest compatible, and errors if labels are missing. Official docs on how each tool behaves across a CRD version removal were not found.
