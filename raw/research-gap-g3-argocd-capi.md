# Research dossier: gap cluster g3-argocd-capi

Research date: 2026-11-26

## Overview

This pass settled four version-sensitive gaps by reading raw files from the upstream GitHub repositories at named tags (via `gh api`), because the docs sites are built from those files. Argo CD docs were read at v3.6.3 (released 2026-11-24, the newest stable line seen), v3.0.0, v2.14.0, v2.8.0. Cluster API docs, Go API types, proposals and release notes were read at tag v1.15.0-rc.0 (published 2026-11-24), plus v1.14.4 and v1.11.0 for comparison. The rendered sites argo-cd.readthedocs.io and cluster-api.sigs.k8s.io were not scraped; their source files were read instead, which is raw text rather than a digest.

Argo CD result: in the newest docs read (v3.6.3) both `round-robin` and `consistent-hashing` are still described as "an experimental feature", and the feature-maturity page lists both as Alpha (round-robin introduced v2.8.0, consistent-hashing v2.12.0). The wording is essentially unchanged since v2.14.0 and v3.0.0. So the label in the wiki finding is not stale. The legacy algorithm remains the uid-based, non-uniform one. The linked CNOE benchmark blog was not read.

Cluster API result: the project is at v1.15.0-rc.0 (v1.14.4 is the latest stable patch seen, v1.13.8 also current). The v1beta2 API (introduced in v1.11.0, 2025-08-19) replaced MachineHealthCheck `maxUnhealthy` and `unhealthyRange` with `remediation.triggerIf.unhealthyLessThanOrEqualTo` and `unhealthyInRange`, moved the checks under `spec.checks`, renamed the external remediation reference to `remediation.templateRef`, and v1.15 adds CEL `unhealthyExpressions`. The default short-circuit threshold is 100 percent, meaning the guard is off unless set. The "Ready to Available" change is real but narrower than the gap title implies: the "Improving status in CAPI resources" proposal drops `Ready` from higher-level objects such as Cluster, MachineDeployment and control planes and adds `Available`, while Machine keeps `Ready` with a new meaning. No generic rule for kstatus-style tools was found in Cluster API material.

ClusterClass result: the `ClusterTopology` feature gate is Beta and enabled by default as of v1.15 (rc.0 docs and release notes); the v1.14.4 docs still carry an "Experimental Feature: ClusterClass (alpha)" heading. The original CAEP file still says `status: provisional` in its frontmatter, while its implementation history shows later additions (MachineHealthChecks 2022, upgrade plans 2025). The v1.15 line is not final: only rc.0 existed on the research date.

## Gap: Current Cluster API MachineHealthCheck behavior

Findings: current behavior is defined by the v1beta2 API (source `api/core/v1beta2/machinehealthcheck_types.go` and the user guide `docs/book/src/user/guide/lifecycle/healthchecking.md` at v1.15.0-rc.0). The v1.11.0 guide still used v1beta1 `maxUnhealthy: 40%`. In v1beta2 the equivalent is `spec.remediation.triggerIf.unhealthyLessThanOrEqualTo`; the old `maxUnhealthy` and `unhealthyRange` remain in v1beta1 but are marked deprecated. Semantics: remediation is skipped when the count of unhealthy Machines exceeds the limit; absolute numbers or percentages (rounded down); `unhealthyInRange` such as `[3-5]` takes precedence. The default is 100 percent, so the guard is disabled by default. This matters for the wiki finding that remediation can amplify an outage: the safety valve is opt-in. External remediation is configured through `remediation.templateRef` (apiVersion, kind, name), where the controller creates an object from the template and hands the Machine to an outside controller. v1.15 adds `checks.unhealthyExpressions` (CEL, OR-combined, max 10). MHCs only cover Machines owned by a MachineSet, MachineDeployment or KubeadmControlPlane. KCP remediation has extra preconditions (preserve etcd quorum, at least two control plane machines once initialized, no machines being deleted) and its own retry controls (`maxRetry`, `retryPeriodSeconds`, `minHealthyPeriodSeconds` default 3600). With ClusterClass, MHCs are defined by the class and can be overridden or disabled per Cluster topology; hand edits to those MHC objects get overridden. v1.15.0 final was not released on the research date (latest tag rc.0).

## Gap: Generic readiness when Cluster API moves from Ready to Available

Findings: the design source is the proposal "Improving status in CAPI resources" (`docs/proposals/20240916-improve-status-in-CAPI-resources.md`, status implementable, last-updated 2025-01-30). It states that the `Ready` condition no longer has to exist on all resources and drops it from higher-level abstractions, adding `Available` modelled on Kubernetes Deployments; Machine `Ready` is redefined to mean the machine can host workloads. The v1beta2 Go constants confirm: Cluster defines `ClusterAvailableCondition` and I found no Cluster ready-condition constant in `cluster_types.go` at v1.15.0-rc.0, while Machine defines both `MachineAvailableCondition` and `MachineReadyCondition`. v1beta2 shipped in v1.11.0 (2025-08-19); v1beta1 removal is tentatively April 2027 per the v1.14-to-v1.15 migration notes.

For generic tools: kstatus falls back to a `Ready` condition on custom resources, and treats resources with no `Ready` condition as always reconciled, so a Cluster API Cluster in v1beta2 that lacks `Ready` would look reconciled to naive kstatus-based tools. That inference is mine; the kstatus README documents the fallback and the corner case, and the CAPI proposal documents the removal, but no source states the combination. Flux's community CEL cheatsheet (last commit touching it 2026-04-21) still shows a `cluster.x-k8s.io/v1beta1` Cluster using the `Ready` condition; a v1beta2 variant keyed on `Available` was not found. No Cluster API or Flux page gives a general rule. Practical rule supported by the evidence: per-kind CEL expressions that check `Available` (and for control planes and Machines the type-specific conditions) for v1beta2 objects, and `availabilityGates` to extend Cluster `Available`. Outcome: partial.

## Gap: ClusterClass maturity and the managed topologies proposal

Findings: maturity moved. The v1.15.0-rc.0 ClusterClass docs state the `ClusterTopology` feature gate is Beta and enabled by default since v1.15; the feature-gates table lists it as Beta, and the rc.0 release notes list "ClusterTopology to beta and enabled per default (#14398)". The v1.14.4 docs still had the "Experimental Feature: ClusterClass (alpha)" heading, so the wiki's alpha label reflects older docs. Beta is not GA, and v1.15.0 final was unreleased on the research date, so anything here should be rechecked at release. Related v1.15 items: ClusterClass without template objects (inline templates, gate `ClusterClassInlineTemplates` still Alpha), and worker version pinning (gate Alpha, proposal dated 2026-07-06).

The CAEP (`docs/proposals/20210526-cluster-class-and-managed-topologies.md`) introduces a ClusterClass object as a collection of template references, and extends Cluster with a `topology` so the Cluster becomes a single control point for Kubernetes version, replicas, worker pools and labels, with continuous reconciliation of the managed objects. Goals include cluster-specific customization of a class. Implementation detail was moved into the book in 2022. Its frontmatter still says `status: provisional` despite later amendments; its history records MachineHealthCheck support (2022-01-10) and upgrade plans (2025-05-13), and it describes the initial rollout behind a feature flag unset by default. Outcome: answered, with the caveat about the pre-release version.
