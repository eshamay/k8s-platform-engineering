# Research dossier: gap cluster o9-cadence-and-staleness

Research date: 2026-11-26

## Overview

This pass targeted the residuals left after earlier dossiers on Config Connector cadence and on the Kubernetes v1.36 staleness work. For Config Connector, the earlier work had the global default (10 minutes mean, jittered 0.5x to 1.5x, annotation override, zero is irreversible) but not the per-kind picture. This pass read the Config Connector repository at master (commit 5cce7c7e, committed 2026-11-26; latest release tag v1.162.0 published 2026-11-23) and the current Google Cloud docs. The central finding is that `pkg/controller/resourceconfig/static_config.go` is a complete per-kind table: 814 entries, each with a default controller and a list of supported controllers. That answers "which kind uses which controller" in a checkable, machine-readable form, with counts below.

On cadence, the direct, Terraform-based and DCL-based reconcilers all obtain their post-success requeue delay from the same `JitteredReenqueue` function. The delay is the annotation value if present, else the per-kind value from Terraform service mapping or DCL metadata, else the IAM constants, else 10 minutes, then jittered. So the controller kind does not itself change the default cadence. Per-kind exceptions exist only in Terraform service mappings (ComputeSSLCertificate 0, ServiceUsage Service 3600, ServiceIdentity 0, BigtableInstance 3600, BigtableTable 3600). The DCL metadata struct has the field, but no DCL entry in the repository sets it. The drift check itself is not a separate poll: each reconcile reads live state and compares, so the cadence of drift detection is the reconcile requeue cadence. Failure backoff is a separate mechanism, and the annotation that tunes its ceiling is documented as direct-controller only.

On Kubernetes staleness, source at v1.36.0, v1.37.0 and master settles the metric names and gate shapes. All four controllers named in the blog (DaemonSet, Job, ReplicaSet, StatefulSet) define a counter `stale_sync_skips_total` under their own subsystem, and master adds the HPA gate. The informer gauge is `informer_store_resource_version`. KEP 5647 is in `implementable` status, with `kep.yaml` targeting beta in v1.37, and the tracking issue is open and carries the `lifecycle/stale` label. `MonitorInformerStaleness` appears in the KEP README and `kep.yaml` but in no `kube_features.go` read here at v1.36.0, v1.37.0 or master, and a GitHub code search of kubernetes/kubernetes returned zero hits. The KEP's `BookmarkFunc` on `ResourceEventHandlerFuncs` is also absent from shipped `controller.go` at v1.36.0 and master, although a different `Bookmark(rv)` method exists on the client-go Store interface.

Caveat on method: GitHub code search and tree reads reflect the repository at read time, not necessarily the release branches for every claim. Where a claim was read at a specific tag, the tag is stated.

## Gap: Config Connector controller kind per resource

Findings. The authoritative mapping is the Go table `ControllerConfigStatic` in `pkg/controller/resourceconfig/static_config.go` (master, commit 5cce7c7e). I counted entries with ripgrep on that file: 814 entries have a `DefaultController`. By default controller: Direct 539, Terraform 206, DCL 65, and 4 IAM-specific (IAMAuditConfig, IAMPartialPolicy, IAMPolicy, IAMPolicyMember). By supported-controller list: 510 kinds support only Direct, 140 only Terraform, 50 only DCL. Overlap exists: 66 kinds default to Terraform but also support Direct, 15 default to DCL but also support Direct, and 29 default to Direct but also support Terraform. None default to Direct and also list DCL. Counts are from line-pattern matching and could miss entries that wrap across lines; the totals sum to 814, which matches.

The direction of travel is toward direct. The official controller-types page says "New resources use the direct controller by default. Existing resources are migrated regularly." The same page says direct controllers avoid Terraform/DCL translation overhead, report structured diffs in logs, and populate `status.observedState`. Parent-controller routing precedence per the page is: namespace override in ConfigConnectorContext (`experiments.controllerOverrides`), then the build-time static default. The page also documents a per-resource annotation `alpha.cnrm.cloud.google.com/reconciler` with values `direct`, `tf`, `dcl`, and says you can tell a live CRD's controller by labels: `cnrm.cloud.google.com/tf2crd: "true"` means Terraform, `cnrm.cloud.google.com/dcl2crd: "true"` means DCL, and absence of both means direct. Example from the page: AlloyDBCluster defaults to Terraform and supports Direct and Terraform. This is a snapshot of master, not of v1.162.0; the table changes with each release, so a wiki page should cite the commit or tag and not hard-code the counts as permanent.

Not settled: a per-resource list as a published doc (the table lives only in source), and the release in which any specific kind switched default. Release notes were not read for per-kind migration dates.

## Gap: Config Connector reconcile interval and drift cadence

Findings. Documented default: the reconciliation concept page says resources are reconciled "with every update or after a jitter period with an average based on the preconfigured default interval", and points to a per-resource reference row "Config Connector Default Average Reconcile Interval In Seconds". The page does not state a number in the prose I read. The generated reference docs in the repository (scripts/generate-google3-docs/.../resource-docs) carry that row on 267 pages; across them the value 600 appears 262 times, 3600 three times, and 0 twice. The source constant `MeanReconcileReenqueuePeriod = 10 * time.Minute` is in `pkg/k8s/constants.go`, and the four IAM kinds also use 10 minutes.

Per controller kind. Direct, Terraform and DCL reconcilers all end a successful reconcile with `RequeueAfter: jitteredPeriod` from the same `JitteredReenqueue` (read in tf/controller.go, dcl/controller.go, and directbase_controller.go). The jitter call is `wait.Jitter(mean/2, JitterFactor)` with `JitterFactor = 2.0`, which the code's own comment describes for the sibling `WatchJitteredTimeout` as "between 1/2 * MeanReconcileReenqueuePeriod and 3/2 * MeanReconcileReenqueuePeriod". Resolution order in `MeanReconcileReenqueuePeriod`: Terraform service-mapping `reconciliationIntervalInSeconds`, then DCL metadata, then the IAM kind constants, then the 10-minute default; the annotation `cnrm.cloud.google.com/reconcile-interval-in-seconds` overrides all of them and takes the same jitter. A direct-controller kind has no service-mapping or metadata entry of its own in this lookup, so it gets the 10-minute default unless annotated (the lookup is by GVK, so a kind that has a Terraform mapping and also a direct controller would pick up the Terraform mapping value; I did not test that overlap case). Per-kind overrides found in `config/servicemappings/*.yaml`: ComputeSSLCertificate 0 (two entries), ServiceUsage `Service` 3600, `ServiceIdentity` 0, BigtableInstance 3600, BigtableTable 3600. For DCL, the metadata struct has `ReconciliationIntervalInSeconds` but a repository-wide search found no assignment, so DCL kinds use 10 minutes. The servicemapping type comment says an unreadable resource should set 0 "to avoid repeated creation of the resource".

Drift check: no separate poll was found. Each reconcile re-reads and diffs, and docs frame the interval as drift correction: setting 0 "disable[s] drift correction for a resource, but it does not disable resource actuation", and that 0 is irreversible. Failure retries are separate: exponential backoff from 250 ms doubling to a 120-second default ceiling; the annotation `cnrm.cloud.google.com/backoff-max-delay-in-seconds` is documented as supported only for direct controllers and needs Config Connector 1.160.0 or later.

Not settled: any measured cadence on a live cluster, and whether the Terraform/direct overlap kinds use the Terraform mapping value when running direct.

## Gap: Kubernetes v1.36 staleness mitigation mechanisms and metrics

Findings. Metrics read from source. The counter is `stale_sync_skips_total` (ALPHA, labels `group`, `resource`) defined in each controller's metrics package with these subsystem constants: `replicaset_controller`, `statefulset_controller`, `daemonset_controller`, `job_controller`. Full names are therefore `replicaset_controller_stale_sync_skips_total`, `statefulset_controller_stale_sync_skips_total`, `daemonset_controller_stale_sync_skips_total`, `job_controller_stale_sync_skips_total`, with help text of the form "Total number of ReplicaSet syncs skipped due to a stale watch cache." The ReplicaSet counter is registered in `Register()` at v1.36.0 and v1.37.0. DaemonSet and Job `Register()` list their counters at both tags. In the StatefulSet metrics file, the `Register()` body at v1.36.0 listed MaxUnavailable and UnavailableReplicas but my pattern did not show `StatefulSetRequeueSkips` registered, while at v1.37.0 it does, consistent with the earlier wiki finding that the StatefulSet counter was registered only from v1.37. The informer gauge is `informer_store_resource_version` (subsystem `informer`, name `store_resource_version`, labels `name`, `group`, `version`, `resource`, ALPHA, help "The 15 least significant digits of the resource version of the store."), defined in `component-base/metrics/prometheus/clientgo/fifo/metrics.go` at v1.36.0 beside `informer_queued_items` and `informer_processing_latency_seconds`. A 1.38 changelog entry says a fix made the metric stop reporting 0 before a store records a resource version (PR 143314).

Gates. At v1.36.0 `kube_features.go` defines per-controller gates `StaleControllerConsistencyDaemonSet`, `...Job`, `...ReplicaSet`, `...StatefulSet`, each Beta and default true from 1.36, and each depends on client-go `AtomicFIFO`. Client-go `AtomicFIFO` and `UnlockWhileProcessingFIFO` are both Beta, default true from 1.36. At master a `StaleControllerConsistencyHPA` gate is added, and `NodeControllerLeaseCircuitBreaker` depends on AtomicFIFO. [corrected in verification: the HPA gate is not master-only. It is already in v1.37.0 `kube_features.go` as Beta, default true, from version 1.37, and depends on AtomicFIFO; it is absent at v1.36.0. `NodeControllerLeaseCircuitBreaker` depending on AtomicFIFO is also present at v1.37.0.] The shape differs from the KEP, which names one `StaleControllerConsistency` gate.

KEP 5647 status. `kep.yaml` (blob sha b0ba8b0c, last committed 2026-05-27): `status: implementable`, `stage: beta`, `latest-milestone: "v1.37"`, `milestone: beta: "v1.37"`, with four gates listed: StaleControllerConsistency, MonitorInformerStaleness, AtomicFIFO, UnlockWhileProcessingFIFO. The tracking issue kubernetes/enhancements#5647 is open, labeled sig/api-machinery, stage/beta, lifecycle/stale, with no milestone set. The README says of MonitorInformerStaleness: "Components depending on the feature gate: None, but requires a direct get to the apiserver to determine staleness every 5 seconds." Its metrics section says "We are planning on adding staleness metrics", so the KEP names none.

MonitorInformerStaleness in released source: absent. `kube_features.go` at v1.36.0 and v1.37.0 returned 0 matches (v1.36.0 grep over the gate list, and a count at both tags), the client-go `known_features.go` at v1.36.0, v1.37.0 and master lists only AtomicFIFO and UnlockWhileProcessingFIFO among these, and GitHub code search for the string in kubernetes/kubernetes returned 0 results (it did find the KEP files in kubernetes/enhancements). Caveat: the master `kube_features.go` check was by grep for the name and showed none; the code search index may lag. BookmarkFunc: the KEP proposes adding it to `ResourceEventHandlerFuncs`. At v1.36.0 and master `ResourceEventHandlerFuncs` has only AddFunc, UpdateFunc, DeleteFunc. A different `Bookmark(rv string)` exists on the client-go `Store` interface at v1.36.0 and v1.37.0, plus `FakeCustomStore.BookmarkFunc`, so "BookmarkFunc exists" is true only for the test fake, not the handler API.

Not settled: the text of the v1.36 blog post was not re-read in this pass (earlier dossiers did); whether MonitorInformerStaleness is planned for a later release (the KEP still lists it); and the exact release in which `BookmarkFunc` on handlers might land.
