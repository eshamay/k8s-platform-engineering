# Research dossier: gap cluster o3-gitops-provider-managed

Research date: 2026-11-26

## Overview

This pass looked at what happens when a GitOps agent (Argo CD or Flux) meets objects that a provider controller turns into cloud resources: Config Connector (KCC), AWS Controllers for Kubernetes (ACK), Crossplane managed resources, and Cluster API (CAPI) objects. The strongest evidence came from source files and project issue trackers rather than from prose documentation. The web_search tool returned empty results for most long queries (short queries worked), so outage and adopter searches were thin.

The main findings are these. First, deletion is the sharp edge: both KCC and ACK delete the cloud resource by default when the Kubernetes object is deleted, and each offers an opt-out annotation (KCC `abandon`, ACK `retain`). Argo CD prune and Flux prune are ordinary Kubernetes DELETEs, so they trigger that default. An open ACK issue from November 2026 (#3153) argues that, once the API server has accepted the DELETE, nothing can undo it, and that a controller-wide `retain` does not protect charts that stamp `deletion-policy: delete` on every CR. That is one user's reproduction; no maintainer response was present when read. Second, health assessment differs by agent. Argo CD ships built-in Lua health checks for the `cnrm.cloud.google.com`, `services.k8s.aws`, `crossplane.io`, `upbound.io`, `kro.run` and several `cluster.x-k8s.io` kinds, and the files show exactly which condition maps to which health state. Flux has no built-in per-provider logic: it relies on kstatus compatibility, with optional CEL `healthCheckExprs`; the Flux CEL cheatsheet library lists Crossplane and CAPI-style entries but, on the page read, nothing for Config Connector or ACK. Third, spec defaulting and references cause drift fights: Config Connector's `state-into-spec: merge` mode populates unspecified list subfields, which Argo CD and Config Sync treat as drift; ACK reference fields (`*Ref`) are rewritten by the controller, and Flux server-side apply reverts them (ACK #2361).

For compositions, the evidence is thinner. kro's ACK guide documents a ResourceGraphDefinition wrapping ACK Bucket and Table objects with dependency ordering and deletion through ACK's policy, and kro's readiness page documents `readyWhen` CEL against `status.conditions`. Crossplane's `function-auto-ready` treats any non-built-in composed resource as ready when it has `Ready=True`, which ACK defines (equivalent to ResourceSynced per the runtime source) and KCC reports. No worked example of Crossplane composing Config Connector or ACK objects was found, and no first-party test of the interplay was found.

On named adopters and outages, this pass added no new named first-party outage write-up beyond what the wiki already holds (Skyscanner 2021, already ingested). It found anonymous, in-tracker evidence of GitOps-driven deletion paths for provider objects (ACK #3153, #3152; Argo CD and KCC issues) and one generic blog (not an incident report). No Flux outage postmortem was found.

## Gap: Config Connector and ACK behavior under a GitOps agent

Deletion: KCC deletes the Google Cloud resource when the Kubernetes object is deleted unless `cnrm.cloud.google.com/deletion-policy: abandon` is present before the delete. ACK deletes the AWS resource first, then the CR, unless `services.k8s.aws/deletion-policy: retain` resolves from resource annotation, then namespace annotation (`{service}.services.k8s.aws/deletion-policy`), then the controller flag or Helm value `deletionPolicy`. Flux prune and Argo CD prune issue ordinary deletes, so these defaults apply. Flux offers `kustomize.toolkit.fluxcd.io/prune: disabled` on an object and `.spec.deletionPolicy` (MirrorPrune, Delete, WaitForTermination, Orphan) for Kustomization deletion. Argo CD offers `Prune=false`, `Prune=confirm`, `Delete=false`, `Delete=confirm`, and for ApplicationSet-created Applications `preserveResourcesOnDeletion`. None of the pages read tests a prune of a KCC or ACK object end to end; the connection is by composition of documented behaviors, except for ACK #3153, where the reporter says Argo CD prune, Flux prune and helm-controller all led to cloud deletion and supplies repro scripts.

Drift and defaults: ACK's drift detection is a 10-hour resync by default (docs and runtime source agree). KCC's `state-into-spec` default is `Absent` from 1.123.1; `Merge` populates unspecified fields, which the KCC page says can conflict with Config Sync and Argo CD because both treat lists as atomic. ACK reference fields are rewritten into the CR by the controller (issue #2361, Flux SSA reverts them; ACK's controller diff then sees changed desired state). ACK adoption under GitOps (issue #3152) reports that spec fields kept in git overwrite the adopted resource on the next sync, and the maintainer reply points to newer docs that say to omit `spec`.

Not settled: no maintainer-confirmed resolution of #3153, #3152 or #2361; no read of KCC's own GitOps deletion guidance beyond the deletion page; no test of Argo CD `Prune=false` interplay with ACK finalizers; ACK's finalizer behavior was not read in this pass (existing wiki page covers finalizers).

## Gap: Flux and Argo CD handling of provider-managed resources

Argo CD health: Argo CD relies on CRD-provided status; for provider kinds it ships Lua. The ACK script maps `ACK.Terminal=True` to Degraded, `Ready=False` to Progressing, `Ready=True` to Healthy, and no conditions to Progressing ("Waiting for resource to be ready"). The KCC script returns Progressing while `observedGeneration` is stale, Healthy on reason `UpToDate`, Degraded on `UpdateFailed` or `DependencyNotFound`, and Suspended on `DependencyNotReady`. The Crossplane script treats `Synced=False` or `LastAsyncOperation=False` as Degraded and `Ready`/`Healthy` and similar True conditions as Healthy, with a list of kinds that never carry conditions treated as Healthy. Argo CD issue #30164 (closed; opened 2026-10-13) shows the cost of wildcard-by-group matching: KCC `customize.core.cnrm.cloud.google.com` kinds stayed Progressing because they use `status.healthy` and a default `observedGeneration: 0`; the current script has a branch for them. Consequence for sync waves: Argo CD advances waves only when the current wave is synced and healthy, and prunes in reverse wave order, so a provider object that never reaches Healthy blocks later waves ("the app can never get to healthy").

Flux health: Kustomization `healthChecks` accept built-ins, Flux kinds, and "custom resources that are compatible with kstatus"; `wait: true` checks everything applied; `healthCheckExprs` supply CEL `current`, `inProgress`, `failed` for kinds that are not kstatus-compatible; `dependsOn[].readyExpr` gates dependencies. A provider's own Ready condition therefore feeds Flux through kstatus (generic Ready condition handling) rather than any provider-specific code. The Flux CEL cheatsheet lists a library including `Crossplane`; searching the page text for cnrm, ACK and services.k8s.aws found nothing.

Other agents/objects: Argo CD ships Lua for CAPI `Cluster`, `Machine`, `MachineDeployment`, `MachineHealthCheck`, `MachinePool`, and `kro.run` `ResourceGraphDefinition`. Not read: those Lua files' contents, Flux's treatment of CAPI objects, and Flux kstatus handling of ACK's `ACK.Terminal` (kstatus semantics for Ready/Stalled conditions were not read in this pass).

## Gap: Config Connector and ACK behavior when wrapped by compositions

kro with ACK: AWS's ACK docs include a "Using ACK with kro" guide with a ResourceGraphDefinition that composes an S3 Bucket, a DynamoDB Table and a Deployment, with outputs read from `status.ackResourceMetadata.arn`. It states kro waits for ACK resources to be ready before creating dependents, does not create dependents if an ACK resource fails, and on instance deletion removes the Deployment first then the AWS resources "following ACK's deletion policy". kro's readiness page says `readyWhen` is a list of CEL expressions; without it a resource is ready once created and references resolve; in an RGD dependents wait. kro has its own alpha, feature-gated `kro.run/deletion-policy` annotation (Delete or Orphaned) that applies whenever kro would remove the resource, and it warns that owner references defeat Orphaned. How the kro annotation and ACK's annotation compose (for example kro Orphaned plus ACK delete) is not documented in the pages read; the pages imply they are independent because kro orphaning leaves the CR in place.

Crossplane: `function-auto-ready` considers a composed resource ready if it appears in observed state and, for non-built-in kinds, has `Ready=True`. ACK exposes `Ready` (runtime source) and KCC documents UpToDate (Argo's script keys on reason `UpToDate`); neither claim was tested in a composition. No Crossplane documentation or example composing ACK or KCC objects was found; Crossplane's own provider-kubernetes Object wrapper and its readiness policy were not read (only found via search listing).

Not settled: whether composition-level deletion (Crossplane composite deletion, foreground vs background) honors ACK or KCC deletion policy ordering; whether ACK `ACK.ReferencesResolved` waits interact with kro dependency ordering. Related: ACK issue #3131 says referencing CRs are not re-reconciled when the referenced CR becomes Synced and may wait up to about 16m40s on backoff, which would add latency to any graph that relies on `*Ref` fields.
