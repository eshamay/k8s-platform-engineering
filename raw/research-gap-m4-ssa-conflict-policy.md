# Research dossier: gap cluster m4-ssa-conflict-policy

Research date: 2026-11-26

## Overview

This pass read source code and primary documentation for the five open gaps. Source trees were shallow-cloned and read at the commits named in each claim (kro main a2ac57b, Helm main 3b82b52, ACK runtime main b1f8861, Config Connector main 793f18c, Cluster API main f11b064, helm-controller main 072b907, kustomize-controller main 9ed68b7). Docs were read from Argo CD (latest docs site), the Cluster API book (in-repo), the Kubernetes website source, and Flux (in-repo spec files). All version numbers below come from GitHub release API calls or files read in this run.

The four tools in the first gap behave very differently. kro applies template resources with server-side apply and force, applies "patch" contributions without force under a per-node manager, and has an opt-in mode that refuses to steal a field from another kro Graph. ACK's runtime does not use server-side apply at all (it sends merge patches). Config Connector does not apply either; it uses Update calls under a named manager and reads other managers' `managedFields` to decide which spec fields a user owns. Helm 4 uses server-side apply by default for new installs, with `--force-conflicts` as an opt-in on the CLI, while helm-controller always forces. The Config Connector public docs page could not be read, so Config Connector behavior rests on source and GitHub issues.

On Cluster API, the topology controller applies with the manager `capi-topology` and force ownership, and the book says this lets other controllers co-author the objects, but it also documents that co-authored list slices can loop forever. Argo CD's docs call Server-Side Diff stable since v3.1.0; the issue tracker still has many open Server-Side Diff bugs (some filed in 2026), so "stable" is a docs label, not a statement that the issues are closed. Kubernetes issue 130292 shows a case where forced SSA still fails (Service ports keyed by port and protocol).

For helm-controller, source shows the `--override-manager` takeover runs inside the drift-detection diff before the server-side dry-run diff, which is the opposite order from kustomize-controller's default flag. kustomize-controller has a second flag, `--override-manager-before-dry-run`, documented as recovery for objects that fail the dry-run. No helm-controller equivalent of that recovery flag was found. For the two evidence-only gaps (default conflict policy; force versus strip-or-adopt), the dossier lists the sources on each side and does not recommend. No named adopter policy and no head-to-head experiment was found.

## Gap: Server-side apply behavior in kro, ACK, Config Connector, and Helm 4

kro. In the executor, template nodes are applied through `ssaApply(..., force)` using `client.Apply` and, when force is true, `client.ForceOwnership`. Patch nodes (contributions to objects kro does not own) are applied under a per-node manager without force. A `ConflictDetection` option, enabled only for the standalone Graph controller, uses a per-Graph manager (prefix `kro-graphengine.tmpl.`) and refuses to force-steal a field owned by another Graph's template manager, surfacing a soft not-ready; external drift is still reclaimed by a forced re-apply. The shared manager on the RGD/instance path is `kro.run/applyset`; instance status uses `kro-instance-status`. Latest release read: v0.10.0, published 2026-11-10.

ACK. The aws-controllers-k8s runtime reconciler writes with controller-runtime `MergeFrom` patches (`client.MergeFrom(desiredCleaned.RuntimeObject())`) and `StrategicMergeFrom` for Secrets and ConfigMaps. A search of non-test, non-mock Go files for `ForceOwnership`, `FieldOwner`, and `client.Apply` found nothing outside a mock. So ACK does not set a server-side-apply manager in the runtime. Conclusion is from absence in the runtime repo at commit b1f8861; individual service controllers were not read. Latest runtime release: v0.68.0, 2026-11-09.

Config Connector. The lifecycle handler writes with `Update` and `Status().Update` under the field owner `cnrm-controller-manager`. The managed-fields helper builds a set of spec fields owned by other managers and skips entries whose manager is `cnrm-controller-manager`, so fields set by a GitOps tool are treated as user intent. A helper performs a tiny SSA patch under the manager `supports-ssa` just to create `managedFields` metadata. GitHub issue 11689 (a proposal by a repo collaborator; closed 2026-10-04 [corrected in verification: dossier said open]) says SSA is mandatory in an Argo CD Application because Config Connector's CRD bundle exceeds the 262144-byte annotation limit. Latest release: v1.162.0, 2026-11-23. The public docs page could not be read (empty scrape).

Helm 4. Release notes for v4.0.0 (2025-11-12) list "Server side apply is now supported" and warn that SSA "may impact the experience". Source on main: `helm install` has `--server-side` as a bool defaulting to true; `helm upgrade` takes "true", "false" or "auto" with default "auto" (value from the previous release's method); install, upgrade, and rollback all have `--force-conflicts`, default false. The field manager is `ManagedFieldsManager` if set, otherwise the base name of `os.Args[0]` (so `helm`). When upgrading a release created with client-side apply to SSA, Helm upgrades the client-side field manager (csaupgrade). helm-controller sets `ForceConflicts = ServerSideApply` ("We always force conflicts on server-side apply"). Open Helm issue 32706 is titled "Helm 4: install fails on an existing CRD previously installed client-side ("conflict with "helm"")"; only the title was read. The question "does Helm 4.0.0 enable SSA by default for new releases" is now answered from source on main (default true on install) but the v4.0.0 tag source was not read for that flag; the release notes alone do not say "default".

## Gap: Cluster API field ownership rules and Argo CD Server-Side Diff stability

Cluster API. The topology controller applies with `client.FieldOwner("capi-topology")` and `client.ForceOwnership`. The book (change-clusterclass page) says the controller uses SSA "to write/patch topology owned objects" so that other controllers can co-author, for example CAPA adding subnet info, and advises against ad-hoc edits to generated objects. It does not publish a per-field ownership table. The troubleshooting page says a slice co-authored by templates and an infrastructure controller can cause "infinite reconcile" (issue 6320), with no fix yet and advice to avoid co-authored slices. A second troubleshooting entry says SSA patches can fail to remove list items after atomic-to-map list transitions (for example `cluster.spec.topology.variables`) and says client-side apply or "continuous" SSA with GitOps tools works. The code also has a `MitigateManagedFieldsIssue` step applied to the topology-owned objects (function body not read). Latest release read: v1.14.4, 2026-11-03.

Argo CD. The diff-strategies page says Server-Side Diff is "Stable (Since v3.1.0)", runs a dry-run SSA per resource, is used automatically with the SSA sync option, can be turned off with `ServerSideDiff=false`, and is skipped for resources that do not yet exist. The jm-dev blog repeats the "stable since 3.1" claim and adds that mutating webhooks need `IncludeMutationWebhook=true`; it is SECONDARY-ONLY and is now backed by the primary docs. Stability is mixed: a search of the Argo CD tracker found 20 or more open issues containing "ServerSideDiff", including 28861 (stale managedFields cause permanent phantom OutOfSync, 2026-07-22), 27625 (reverts target changes for CRDs with `x-kubernetes-preserve-unknown-fields`, 2026-04-30), 27237 (hides manual changes, 2026-04-08), 25533 (misses CR spec changes, 2025-12-05), and 17717 (duplicate port error, 2024-04-03). Only titles of most were read. Latest Argo CD release: v3.6.3, 2026-11-24. The `kubectl` default-SSA question was not answered.

## Gap: Flux helm-controller override-manager and dry-run failure recovery

Confirmed. `--override-manager` is a repeatable string-array flag in helm-controller `main.go` with help text "List of field managers to override during drift detection." It entered the 1.5.0 changelog section (the release date 2026-02-20 was read from the release API), with the sentence that drift detection and correction "is completely unrelated to Helm v4's server-side apply support". The flag appears in helm-controller's `docs/README.md` flags table with the example `--override-manager=kubectl-edit --override-manager=kubectl-patch`. The HelmRelease spec docs do not describe it; the search of the docs tree found it only in the flags table and a contributor-facing AGENTS.md.

Order of operations (newly settled by source). In `DetermineReleaseState`, when drift detection is enabled, `action.Diff` is called with the disallowed managers. Inside `Diff`, if the list is non-empty, a non-dry-run client runs `replaceDisallowedFieldManagers` on each live object, patching `managedFields` (a JSON patch with the controller as field owner) before the dry-run client computes the diff. So helm-controller's takeover happens before its SSA dry-run diff. That is the reverse of kustomize-controller, whose docs say `--override-manager` "takes over the named field managers only after a successful server-side apply dry-run", and which added `--override-manager-before-dry-run` for objects whose dry-run fails every reconcile. Caveats: the `ssa.PatchReplaceFieldsManagers` body was not read, and `Diff` runs `Graceful(true)`, so how an error in the dry-run diff surfaces for a stuck HelmRelease was not traced. The helm-controller's upgrade path always forces conflicts, so a dry-run failure caused by a merged-object validation error (rather than a conflict) is a separate failure that force does not fix.

Recovery. For kustomize-controller the documented recovery is the before-dry-run flag, with two stated risks: it transfers all fields owned by the listed managers and prunes fields missing from source, and the managedFields change is not reverted if the apply fails. For helm-controller no documented recovery for a stuck dry-run was found; the Argo CD issue 17717 and Kubernetes issue 130292 were read (see previous gap) and describe a Service-port validation case that is not specific to Flux.

## Gap: Best default conflict policy for teams running GitOps and in-cluster controllers

This gap asks for evidence, not a decision. Sources are grouped by the position each supports.

Force by default (the GitOps tool wins). Kubernetes docs: "It is strongly recommended for controllers to always force conflicts on objects that they own and manage". Argo CD runs `kubectl apply --server-side --force-conflicts` when `ServerSideApply=true` and ignores `Force=true`. helm-controller always forces. Cluster API's topology controller forces under `capi-topology`. kro forces template applies. A practitioner blog (jm-dev, 2026-09-16) draws the consequence: "the conflict mechanism protects nobody from Argo CD", and the boundary is drawn in the repository by not declaring the field.

Surface or yield (the controller or a human decides). The Kubernetes docs list three resolution options and the HPA handover (both set the same value, then one drops the field). Flux's ignore rules strip a field from the payload when another Apply-type manager owns it, and adopt the live value when Flux is the sole Apply-type owner. kro's patch nodes apply without force, and kro's conflict-detection mode refuses to steal from another Graph. Config Connector reads other managers' `managedFields` to treat their values as user intent. Argo CD's `managedFieldsManagers` ignore rule keys off a named manager. The kube-green case study (christianhuth.de) says the `managedFieldsManagers` approach "holds today, but it's not a documented contract between the two projects" and requires the other controller to apply via SSA under a stable manager name.

Limits of forcing. Kubernetes issue 130292 shows forced SSA failing to correct a Service whose port entry was edited (open, still reported 2026-09-14). Cluster API documents infinite reconcile for co-authored list slices. Neither is solved by choosing force or yield.

Not found. A named adopter's written policy for mixed GitOps and controller ownership, and SIG API Machinery discussion of parsing `managedFields` to ignore conflicts, were not found (searched GitHub issues and the web for these; the closest implementations are Argo CD `managedFieldsManagers` and Flux Strip/Adopt).

## Gap: Force-conflicts versus strip-or-adopt when two controllers co-own a field

Evidence-only. The two policies differ in who loses writes. Argo CD (force) sets the Git value every sync and resets the other manager's ownership, so the other controller's write is overwritten on the next sync unless the field is omitted from Git or the diff ignores it (and `RespectIgnoreDifferences=true` is needed for the sync to honor ignores, per the jm-dev blog, SECONDARY-ONLY). Flux's strip rule drops the field from its payload when another Apply-type manager owns it, so the other controller keeps the field; its adopt rule copies the live value when Flux is the sole Apply-type owner, which preserves Update-type edits such as `kubectl patch`. The Flux docs also say changes to ignored fields alone do not trigger a reconcile. The Kubernetes docs give a third route (share ownership by setting the same value, then one party drops the field).

Side-by-side points with sources: (1) The strip rule only applies when the other manager is an Apply-type manager, so a controller that writes with Update (for example Config Connector's `cnrm-controller-manager`, which uses Update) is covered by adopt, not strip. This follows from the Flux spec text and the Config Connector source and is an inference, not a statement from either project. (2) The kube-green write-up reports that manager-scoped ignores depend on the other controller using SSA under a stable name. (3) kro does something comparable for its own Graphs (refuse to steal between Graphs) and forces for external drift.
