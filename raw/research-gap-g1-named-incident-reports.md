# Research dossier: gap cluster g1-named-incident-reports

Research date: 2026-11-26

## Overview

The gap asks for the primary reports behind four incidents that the wiki had only seen as one-line k8s.af summaries: the Skyscanner namespace-deletion outage, the Reddit Pi-Day outage, the Jetstack admission webhook outage, and the Spotify cluster deletion. This pass reached one of the four primary reports in full text: the Jetstack webhook post. It came through a Wayback Machine capture of the Venafi-hosted copy of the post (Venafi acquired Jetstack), not through the original blog.jetstack.io URL.

The other three primary sources could not be read. The scraper returned empty content for the Reddit (r/RedditEng) post, the Skyscanner Medium post, and the Spotify KubeCon talk page and YouTube page. WebFetch refused reddit.com, medium.com and blog.jetstack.io with "Unable to verify if domain ... is safe to fetch". A direct curl attempt and two further Wayback attempts were blocked by the permission classifier. I did not try to get around those blocks. Reading those three primaries therefore needs either a permission change or a different access path chosen by the user.

For Reddit, the only body text I read was a third-party retelling (Kubezilla). It matches the k8s.af summary on the main mechanism (Kubernetes 1.24 label change plus a Calico route-reflector selector), but it contains reconstructed command output and a minute-by-minute timeline that cannot be traced to the Reddit post. Treat it as SECONDARY-ONLY and do not copy its timeline into wiki pages. For Skyscanner and Spotify, nothing beyond the k8s.af index entries was obtained.

## Gap: Primary incident reports for Skyscanner, Reddit, Jetstack, and Spotify

Jetstack (answered from a primary source). Organization: Jetstack (now part of Venafi), self-reported. Posted 5 September 2019. Trigger: a GKE master upgrade of a regional development cluster in europe-west1, run through a Terraform pipeline with a 20-minute timeout. Mechanism: during the second master upgrade, the API server's `ca-registration` PostStartHook tried to update the `extension-apiserver-authentication` ConfigMap in `kube-system`. That write timed out because the backend of the validating OPA admission webhook was not responding. The master could not pass its health check, entered a crash loop, and halted the upgrade. Intermittent API downtime stopped kubelets from reporting node health, so GKE node auto-repair recreated nodes in a loop and all tenants lost service. Mitigation: deleting the `ValidatingAdmissionWebhook` resource restored the cluster. Follow-up: restrict the webhook to namespaces where policy applies and to `Ingress` and `Service` only, add a liveness probe to OPA, and keep node auto-repair enabled. Takeaways in the post: alert on API server latency for CREATE and UPDATE, and use probes on all workloads. The post links an upstream Kubernetes issue (#54522) that was still open in the captured copy. Note for [[findings/admission-webhook-outages-are-a-recurring-failure-class]]: the post does not mention `failurePolicy`; the stated fixes are scoping, a liveness probe and alerting. Do not attribute a `failurePolicy` recommendation to Jetstack.
