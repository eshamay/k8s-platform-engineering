## Gap: kro status schema and Crossplane v2 status propagation

Status of entry: open; the kro half was already settled. The open half was the mechanism by which a function's per-resource ready signal becomes the XR Ready condition. It is now read from v2.5.0 source.

Mechanism: the proto enum `Ready` (`READY_UNSPECIFIED`, `READY_TRUE`, `READY_FALSE`) is attached to each desired resource and to the desired composite. In `composition_functions.go`, each composed resource gets `Ready: dr.GetReady() == fnv1.Ready_READY_TRUE`, so both FALSE and UNSPECIFIED count as not ready; a TODO comment asks whether UNSPECIFIED should derive readiness from the resource's own Ready condition. That is why a pipeline needs `function-auto-ready` (or a function that sets READY_TRUE). The composer returns `Ready` as a nil-able bool from the desired composite's own ready field. In `reconciler.go`, after composing, every composed resource that is not Ready is added to an unready list; the XR Ready condition is `Available()` if the list is empty and `Creating()` with message "Unready resources: ..." otherwise. If the composer returned an explicit XR-level ready value it supersedes the derived value. If deleting, Ready is `Deleting()`. Synced is `ReconcileSuccess()` unless a composed resource is not synced, in which case it is `ReconcileError` with "Unsynced resources: ...". The function-auto-ready source checks explicit readiness first, then the observed resource's `Ready` condition equals True.

## Gap: Crossplane v2 condition behavior and the fix for async Synced signaling

The author reports local kind reproductions on 2.4.2, 2.4.3, and 2.5.0-rc.1, and says the issue exists back to 2.1.x so backports are wanted.

So PR 8080 addresses stale XR condition replay (a cache-staleness bug) and not the long-running async managed-resource case of provider-aws 2287 where the MR keeps ReconcileSuccess.
