# Research dossier: gap cluster g1-operator-loop-failures

Research date: 2026-11-26

## Overview

This pass looked for named, published evidence of operator and controller failures: formal postmortems, hot or self-triggered reconcile loops, incidents from lost events, and status bugs (missing observedGeneration, early Ready). The honest headline is that I found no formal, organization-authored postmortem written about a Kubernetes operator. The public record that does exist is GitHub issues with root-cause analysis, filed mostly by users or contributors rather than by the vendor's incident process. I treat those as VERIFIED primary sources for the mechanism, but they are not named-company postmortems, and every impact figure in them is self-reported by the issue author.

The strongest material is on runaway reconcile loops. Four independent issues (all re-fetched via the GitHub API in verification) show the same mechanism: a controller writes status (or re-applies an object) on every pass even when nothing changed, the write bumps resourceVersion, the watch fires, and the object is re-enqueued. Examples are Cluster API provider RKE2 (about 10 reconciles per second), Longhorn's BackupTarget controller (about 6 per second, caused by volatile timestamps and request IDs in a condition message defeating an equality check), Konflux kube-shard (about 13 per second, caused by two server-side applies of one ConfigMap with different label sets), and Crossplane's CompositionRevision reconciler (unconditional Status().Update(), found by a reconcile-ordering test tool). A fifth, Longhorn issue 14121, shows the resource cost of a retry loop with no backoff: memory growth on every node during an S3 outage, followed by OOM kills and node flaps.

For lost events, the best primary evidence is a client-go bug: an informer could miss a DELETE event when a relist happened while a CREATE was still queued, leaking the object in the consumer's own state. It was reported in kubernetes/kubernetes issue 115658 and fixed by merged PR 115620 plus PR 116623 for 1.27. The reporter noticed it as informers drifting out of sync in production. A second case, NVIDIA NVSentinel, shows the restart-gap variant (a delete that happens while the controller is down is never delivered). Two projects (Argo Rollouts, KubeFleet) document periodic resync as a deliberate safeguard against missed events. I could not read the Render informer post or the ondemandenv article.

For status problems, three open 2026 issues give concrete cases of Ready or Healthy being reported for a spec generation the controller has not yet seen: CloudNativePG, restate-operator, and an Argo CD ACK health check. None is a postmortem, and all are open at the time of reading. No conference talk on status handling specifically was found.

## Gap: Named operator failure postmortems

Finding: partial at best, and mostly negative. The k8s.af failure-stories index (read in full via scrape) lists about 60 public stories. Almost all concern DNS, CNI, etcd, ingress, CPU throttling, or cluster upgrades. None is titled as an operator or custom-controller failure. Two entries touch controllers or admission: Jetstack's admission webhook outage and Xing's "stuck controllers" talk, which I saw only as index summaries and did not read. The nearest evidence of operator-caused incidents is the Longhorn issue below, where the operator's own reconcile retry behavior took nodes down. The reporter wrote it up with a measured timeline, but it is a user bug report, not a vendor postmortem, and it is still open.

## Gap: Named postmortems of runaway reconcile loops

Finding: answered at the level of named projects with root-cause issues, not at the level of formal postmortems. Five distinct, well-documented cases, with two recurring causes. Cause A: unconditional status write each pass (CAPRKE2, Crossplane). Cause B: a write that is not idempotent in bytes even though it is in meaning (Longhorn volatile message text; kube-shard double SSA with differing label sets and no predicate on Owns). Argo CD issue 18151 is a sixth case of unexplained high PATCH rate after an upgrade; its root cause was not established in the comments I read, so I record it as symptom only.

## Gap: Incidents caused by lost events or edge-triggered design

Finding: partial. There is no named-company outage postmortem, but there are two primary-source cases of lost events with concrete mechanisms, plus evidence that real projects add periodic resync because of missed events. The client-go case is the best: it comes from production controllers at a company (reporter odinuge, whose employer is not stated in the issue), was triaged by api-machinery, and fixed upstream. The Render informer post could not be retrieved (web_scrape returned empty content; WebFetch was blocked for the domain), so it remains unread.

Claims:
- Claim: client-go informer bug: if a watch ends and a relist runs while a CREATE for a short-lived object is still queued in DeltaFIFO, no DELETED event is generated, so the consumer leaks the object. The reporter saw controllers drift out of sync with the cluster, with queues over 1000 elements and resync disabled; recovery occurs only after a later relist. | Status: VERIFIED (issue); impact figures self-reported | URL: https://github.com/kubernetes/kubernetes/issues/115658 | Date: opened 2023-02-09, closed 2023-03-20 | Quote: "informer having a queue of events while a relist occur, and for some objects, we never see the `DELETED` event"
- Claim: Fix: PR 115620 "client-go/cache: fix missing delete event on replace" was merged 2023-02-17. ## Gap: Named case studies and postmortems for status problems

Finding: partial. No postmortem or conference talk on status handling was found. Three open 2026 issues give named, reproducible cases where Ready or Healthy is reported for a stale generation. All three also show the missing-observedGeneration cause explicitly. They were filed as bugs, not incident reports, and all were open when read, so fixes are unknown. The loop-causing status writes above (CAPRKE2, Crossplane, Longhorn) also belong here as the opposite failure: status written too often.
