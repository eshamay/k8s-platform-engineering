# Research dossier: gap cluster g1-named-adopters

Research date: 2026-11-26

## Overview

This pass looked for named organizations and reported figures behind three open gaps: adopters of control-plane tools (Crossplane, ACK, kcp and others), named Flux sharding adopters and API Priority and Fairness (APF) incidents, and kro scaling limits and production adopters. Sources were read in this run: the raw ADOPTERS files on GitHub (Crossplane, ACK, kcp), the Flux adopters data file, the Flux sharding docs page, the Flux blog post on Morgan Stanley, GitHub issues and PRs fetched through gh, and kro's own docs and README. The built-in search tool returned few usable hits, so most evidence came from repository files and issues.

Crossplane has by far the richest adopter record, but every entry is a self-reported one-liner in a community-maintained table, with no audit. Only a handful carry numbers (SAP, Consensys, Built Technologies, Akamai, SpareBank 1, Nike, DKB). ACK and kcp have short adopter files. kcp's file marks most entries "Development" and only Upbound as "Production". No ADOPTERS file was found for kro, Cluster API or Config Connector.

For Flux sharding, no organization was found that publicly says it runs sharded Flux at a stated scale. The best-known large adopter, Morgan Stanley, reports over 500 clusters but lists sharding as a future exploration, not something it runs. The only named sharding users are anonymous GitHub issue reporters (a 300-namespace cluster, a hub-and-spoke setup, and a user who reports a production hit on a sharding bug). No postmortem was found that ties APF throttling to Flux. What exists is the 2022 change making Flux controllers APF-aware, plus a 2026 fix for a remaining client-side rate limiting path.

For kro, the premise of the gap needs correcting. The released-docs page on controller tuning describes one shared dynamic controller with a single queue, not a dedicated controller per ResourceGraphDefinition, and says per-RGD queues are a possible future change. No named production kro adopter and no benchmark was found. The only adoption evidence is secondary (survey rating, AWS docs, CNCF blog). The kro project has an open issue asking for continuous performance testing.

## Gap: Named production adopters of control-plane tools

Crossplane's ADOPTERS.md (commit blob c6b1ba1d at read time, last commit 2026-10-27) lists 87 organizations in table rows by my count of rows starting with a linked name. The file describes itself as an adopters list that organizations add themselves to. All figures below are self-reported by the listed organization through the contact handles in the file, and the date of each figure is not stated except SAP ("As of February 2024"). Entries with numbers: SAP (100+ KRM-based control planes, thousands of managed resources), Consensys (more than 1,000 resources, with a KubeCon talk link), Built Technologies (at times over 10,000 AWS resources, in a developer environment), DKB (more than 10 EKS clusters, thousands of resources), Nike (thousands of resources), Akamai (provider-ceph can orchestrate up to 200k managed resources, a capability statement rather than a measured production count), SpareBank 1 Utvikling (migration of over a thousand production microservices, databases and caches), and Jellysmack (hundreds of AWS IAM roles). Several others describe use without any number (Renault, Elastic, DB Systel, Grafana Labs, Autodesk, Nokia, UiPath, Xata, monday.com, Baloise, Stone Payments).

ACK's ADOPTERS.md calls itself "a self-reported list of users" and names Adobe (global Kubernetes cluster provisioning and stateful service infrastructure using multiple ACK controllers), BT, and Continuum Industries among others (I only read the first three rows in this run, so the full list is not captured). No object counts are given. kcp's ADOPTERS.md lists 8 table rows (my count of lines starting with a pipe, including header lines), with maturity labels: Upbound is "Production" (multi-tenant access to the host cluster in Cloud Managed Control Planes), while SAP (ApeiroRA Platform Mesh), SNCF Group, Kubermatic, Faros.sh and KubeStellar are marked "Development". No object counts are given. Cluster API: a search of the repo for an adopters page found only docs/book/src/reference/providers.md, which lists providers, not users. Config Connector: no ADOPTERS file at the repo root of GoogleCloudPlatform/k8s-config-connector (root listing contained no adopters file). Neither was checked beyond that.

The Flux adopters page front matter says the list is "a selection of organisations who self-identified as using any of the Flux projects in production". The data file lists 127 `name:` lines (a few may be non-company lines) with logos only and no use-case text. Morgan Stanley's figure comes from a FluxCon NA 2025 talk summarized on the official Flux blog.

Net: named adopters are easy to find for Crossplane, ACK and kcp, but each is an unaudited self-listing, and numeric evidence exists for only about eight Crossplane entries.

## Gap: Named Flux sharding adopters and API Priority and Fairness incidents

Sharding. The official sharding page (shown as v2.10 in the page's version picker) advises sharding "when Flux is managing tens of thousands of applications", explains the `sharding.fluxcd.io/key` label, and states that extra replicas are failover standbys that add no capacity. The feature itself was proposed by Stefan Prodan in flux2 issue #3731 (opened 2023-03-29) as a `--watch-label-selector` flag. A later website PR (#1528, 2023-06-23) recommends sharding for resource isolation.

Named adopters: the Morgan Stanley post on the Flux blog (2026-03-15, from a FluxCon NA 2025 talk by Tiffany Wang and Simon Bourassa) reports over 500 clusters, over 2,000 nodes, over 100,000 containers, and tens of thousands of Flux resources. It lists "Flux Sharding" under "Looking Ahead" as something the team is exploring, so Morgan Stanley is not a documented sharding user. They tuned reconciliation intervals, `--concurrent` flags and resource limits instead. These figures are self-reported by Morgan Stanley and relayed by the Flux maintainers. No other organization was found that says it runs sharded Flux. Anonymous GitHub reporters do exist: an unnamed user with 300+ namespaces and one Kustomization per namespace reported 5-minute delays in issue kustomize-controller #1174 (2024-05-29) and was told by a maintainer that "a single kustomize-controller instance can do 1K reconciliation in about 3m" (citing the flux-benchmark repo). An unnamed user (jordiclariana) ran sharding with a mutating webhook that assigns shard labels, and hit a cross-shard `dependsOn` failure (kustomize-controller #1175, 2024-05-30, closed 2024-09-26 via PR #1248). Issue flux2 #5470 (2025-08-05) describes a hub-and-spoke setup with reconciliation storms during nightly deploy windows, and the maintainer suggests sharding as one option. Source-controller issue #2150 (2026-09-07) reports that objects leaving a shard keep their artifacts on the old shard, and the reporter states they "also hit it in production". None of these name the employer.

The benchmark file in fluxcd/flux-benchmark (Flux v2.10.0 table) gives a scale reference without sharding: 1000 Kustomizations reconcile in 4m13s with a 2 CPU, 1Gi kustomize-controller at concurrency 20, using 297Mi max memory, on a 3-node Kind cluster in a GitHub runner. This is a project-run benchmark, not a production report.

APF. Flux's June 2022 update says "all Flux controllers conform to the Kubernetes API Priority and Fairness", and fluxcd/pkg PR #270 (merged around 2022-05-11) disables client-side throttling when the server has the APF filter enabled, relying on `Retry-After`. fluxcd/pkg PR #1118 (2026-02-16) fixed a path where a custom kubeconfig still used client-side rate limiting even if APF is supported. No incident or postmortem linking Flux sharding to APF throttling (for example 429 responses from the API server against sharded controllers) was found in GitHub issues or the web search. An org-wide GitHub issue search for "429", "apiserver overload" and "flowcontrol APF throttl" returned nothing relevant.

## Gap: Scaling limits of per-RGD kro controllers and named production kro adopters

Architecture correction. kro's controller tuning page on the main branch describes three loops: an RGD reconciler, a dynamic controller that "manages multiple resource types at runtime", and a Graph controller. The dynamic controller uses a "single shared queue" with lazy informers started per registered RGD and metadata-only watches. A note says the shared queue "could be replaced with per-RGD queues in future versions". So the gap's wording about a dedicated controller per RGD does not match the current docs: informers are per kind, the queue and workers are shared. Defaults on that page: `dynamicControllerConcurrentReconciles` 1 worker, `resourceGraphDefinitionConcurrentReconciles` 1, rate limiter 10 events per second with burst 100, resync 36000 seconds, retries 20, `watchSyncTimeout` 30s (raise it if a kind has tens of thousands of objects), `rgd.maxCollectionSize` 1000, `applyConcurrency` 20. A design proposal (docs/design/proposals/graph.md) also states that a standalone Graph keeps only an in-memory compiled-program cache.

Measured scaling: none found. kro issue #610 (2025-07-23) asks for continuous performance testing, with no results. Issue #198 (2025-01-11, by maintainer a-hilaly) proposes weighted queues because a single queue "can lead to resource starvation". Issue #1464 (2026-09-30, closed) reports that a hard apply failure on a Graph discarded the watches and hot-looped without backoff, and "on a large collection each rebuild re-issues a full WatchList, which drives apiserver memory up" (reported on kro main and v0.10.0-rc0, Kubernetes 1.35). This is a reporter observation, not a measurement. PR #1129 (CEL compilation caching) and #1449 (cycle detection optimization) are performance work items. Latest release at read time: v0.10.0 (2026-11-10).

Adopters: kro has no ADOPTERS.md at the repo root (404 on the raw path; root listing has none). Adoption evidence found is secondary: a bex.co blog (2026-07-29) says the CNCF and SlashData Q1 2026 Platform Engineering Radar placed kro in "Adopt", from a Q4 2025 survey of 400+ developers, and notes the API is still alpha. That blog is a third-party summary; the radar itself was not read. The same blog says AWS's EKS docs ship a kro concepts page (not opened in this run). A CNCF blog post from 2025-12-15 on platforms using kro for composition was read in part and names no production adopters in the lines I searched (matches were generic). Whether the Google Cloud, AWS or Microsoft offerings count as "production adopters" is a judgment call the sources do not settle.
