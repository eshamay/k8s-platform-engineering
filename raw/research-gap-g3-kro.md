# Research dossier: gap cluster g3-kro

Research date: 2026-11-26

## Overview

All kro documentation facts below were read as raw text from the kubernetes-sigs/kro repository at git tag v0.10.0 (fetched with `gh api ... contents/<path>?ref=v0.10.0`), which is the source of the versioned docs on kro.run. The GitHub releases API lists v0.10.0 as the latest non-prerelease, published 2026-11-10. The previous stable is v0.9.4 (2026-09-04). A v0.10.0-rc.0 prerelease went out 2026-09-22. This settles the version discrepancy noted in the wiki: a September 2026 blog citing v0.9.x was describing the stable release at that time, since v0.10.0 did not ship until November.

The headline change in v0.10.0 is the alpha `Graph` API (`kro.run/v1alpha1`, kind `Graph`), disabled by default behind the `GraphKind` feature gate. The release notes' first item is "RGD on Graph - unifying the composition engine (KREP-024)". The KREP-024 design text in the repo says the RGD controller now routes through the graph engine unconditionally and issues `GraphRevision` objects, so RGD is internally a graph while remaining a separate user-facing Kind. Readiness semantics differ by API: in an RGD, dependents wait for upstream `readyWhen`; in a Graph, `readyWhen` only feeds status and does not gate downstream nodes. Graph nodes are applied as soon as the referenced fields exist.

For tuning, the released v0.10.0 page confirms the numbers the wiki previously took from the unreleased "next" docs (1 worker, 200 ms to 1000 s backoff, 10 events per second with burst 100, 36000 s resync, 20 retries, QPS 100 and burst 150). v0.10.0 adds new settings: a 30 s `watchSyncTimeout`, a `3s` instance requeue interval with exponential backoff capped at five minutes, a Graph controller with its own concurrency, and composition-engine limits. The v0.9.4 page differs in one respect: it describes the requeue interval as a fixed delay. Instance conditions for RGD instances are `InstanceManaged`, `GraphResolved`, `ResourcesReady`, and `Ready`, which the Instances page now documents (the earlier dossier saw it empty).

Governance is plain: the repo README and kro.run say kro is a subproject of Kubernetes SIG Cloud Provider, and the SIG's own README lists it. No page read says kro is, or is applying to be, a CNCF project in its own right. The kro.run footer only says Kubernetes is a CNCF graduated project. On the Graph API's future, the repo roadmap (last updated 2026-04-03, stale relative to the release) and the KREP-024 text say Graph is additive and does not replace or deprecate RGD. No separate stability or promotion timeline for Graph was found.

## Gap: kro dependency graph and readiness mechanics

Dependencies are inferred from CEL references, and every reference is an edge, including references written with the optional operator `?.`. The graph is acyclic (cycles rejected at creation), creation follows topological order, deletion follows the reverse, and the order is published in `status.topologicalOrder` on the RGD. Resources whose references depend only on `schema` are created in parallel (diamond and parallel-branch patterns in the docs). In the v0.10.0 RGD flow, the RGD controller validates before any instance exists.

`readyWhen`: a list of boolean CEL expressions that may reference only the resource itself (by id) or `each` for collections, not other resources or `schema`. Without `readyWhen`, a resource is ready once created and its references resolve. In an RGD, dependents wait until upstream `readyWhen` holds. In a Graph, a node is applied as soon as the fields it references exist, so `readyWhen` only drives Graph status, and the docs show gating by referencing a field that appears only when healthy. `readyWhen` is accepted on `template`, `ref`, `def` nodes and rejected on `patch` and `graph` nodes.

`includeWhen`: boolean CEL list controlling whether a resource exists at all. It may reference `schema.spec` and, since the v0.9 KREP-008 work, upstream resources. Skipped resources skip all their dependents. The docs warn against volatile status fields because the resource and its dependents flip-flop. `forEach`: an array of single-entry iterators producing a cartesian product, an empty iterator yields zero resources, and iterators cannot depend on each other. Collections are capped at 1000 items by default (and 10 dimensions), and the docs warn that over-limit collections get stuck during deletion. Within a Graph, nodes apply serially in topological order and collection items apply in parallel. For RGD collections, any reference to a collection waits for it to be fully reconciled and ready.

## Gap: kro status schema and Crossplane v2 status propagation

kro side. An RGD's `spec.schema.status` maps field names to CEL expressions over managed resources. The generated CRD types those fields from the expression output, so status has "strongly-typed schemas", with scalar, object, array and string-template forms allowed. kro adds `conditions` and `state` to every instance status, and `state` is reserved (kro overwrites any user definition). An author `conditions:` list built with `runtime.newCondition({type,status,reason,message})` replaces the built-ins on the wire, can return a list to produce one condition per collection item, and can read child resource conditions with `runtime.condition(resource, 'X')`. RGD-level status (not instance status) has five conditions in v0.10.0: Ready, GraphRevisionsResolved, GraphAccepted, KindReady, ControllerReady. That differs from the four-condition set (`Ready`, `GraphAccepted`, `KindReady`, `ControllerReady`) the wiki recorded, and adds `GraphRevisionsResolved`. Instance and RGD `status.state` are different enums: for an RGD it is Active or Inactive. Graph objects have a third condition model (Accepted, ResourcesConverged, Ready) with reasons such as WaitingForReadiness, DataPending, FieldManagerConflict, ApplyFailed, and a `managedResources` inventory (cap 5000).

Crossplane side (limited). The Crossplane docs say a composite resource has two conditions, Synced and Ready, and that Ready becomes True when "the composite resource's composition function pipeline reports that all its composed resources are ready". The v2.5 guide uses `function-auto-ready` to mark composed resources ready when healthy. A draft Crossplane design one-pager (Status: Draft) records that a fatal function result sets Synced false, and that today the only path for custom user-facing messages is defining your own status field. I did not read function-SDK source, `RunFunctionResponse` readiness fields, or the v2 propagation code, so the mechanism by which a function's per-resource ready signal becomes the XR Ready condition is documented at the level of the docs sentence only. Crossplane latest release read from the GitHub API: v2.5.0, published 2026-11-24.
