# Research dossier: gap cluster o6-platform-landscape

Research date: 2026-11-26

## Overview

This pass covered five gaps in the wider platform-orchestration landscape. Four of them could be settled mostly from primary sources read in this run: the Radius and Score repositories and the CNCF landscape file and sandbox issues, the Kratix reference documentation and Go API types, the Backstage Kubernetes configuration page and Software Templates overview, and the GitHub release, commit and maintainer files for tofu-controller and the Terraform Operator. The fifth gap, neutral comparisons of Crossplane with Terraform and the single-cloud operators, is only partly answered. Nearly every comparison article that a search surfaces is written by a vendor with a stake in the answer, and the independent material found is thin and dated.

Radius is a CNCF Sandbox project (accepted 2024-04-16 per the CNCF landscape file), its four listed maintainers are all Microsoft employees, and it is releasing roughly monthly (v0.62.0 on 2026-10-27) with only the newest minor channel supported. Score is also CNCF Sandbox (accepted 2024-07-08), its maintainers list is spread across four employers, and the spec repository releases slowly (0.4.1 on 2026-05-25) while the reference implementations score-k8s and score-compose release frequently. Neither Radius nor Score is an operator-style reconciler for arbitrary resources; Radius is a platform with its own control plane and Score is a specification consumed by CLIs.

Kratix Destinations are cluster-scoped records of "a system Kratix can write documents to", paired with a GitStateStore or BucketStateStore that holds the credentials and location. Scheduling is label matching, in two stages (Promise dependencies to Destinations, then workload outputs to Destinations), with a documented precedence order. Backstage documentation describes a catalog-entity-driven, label-matched Kubernetes view with a configurable list of custom resources and a proxy; the Scaffolder is a template-to-repository tool. No Backstage document read describes an operator pattern, and the only operator-style integrations found are community plugins (TeraSky) that ingest Crossplane claims and kro instances into the catalog. tofu-controller is actively maintained under the flux-iac organization (v0.17.0 on 2026-11-16), while the GalleyBytes Terraform Operator has had no release since v0.17.1 on 2024-05-17 and no commit since 2025-12-09.

Note on vendor marks: where a source sells a competing or adjacent product, its claims carry a VENDOR tag. A claim whose status is VERIFIED means the quoted text was read at the URL in this run; it does not mean the underlying opinion is true.

## Gap: Kratix Destination and GitStateStore mechanics

Per the Kratix reference docs (docs.kratix.io, "main" version, copyright 2026), a Destination is a cluster-scoped record "of a system that Kratix can write documents to", which an external tool then reconciles. Examples given are Kubernetes clusters (Flux or Argo CD pulling manifests), Terraform, Ansible, and a Backstage catalog fed from Git. Key spec fields: `path` (required, relative to the state store path), `strictMatchLabels` (default false), `filepath.mode` (`nestedByMetadata` default, `aggregatedYAML`, `none`; immutable after creation), `cleanup` (`none` or `all`), `stateStoreRef` (name and kind, GitStateStore or BucketStateStore) and `initWorkloads`. Under `<statestore.path>/<destination.path>/` Kratix writes two top-level directories, `dependencies/` (Promise-level items such as CRDs) and `resources/` (per Resource request). In `none` mode Kratix writes `.kratix/<workplacement>.yaml` tracking files so it can clean up.

A GitStateStore holds the repository connection: `url`, `branch` (default main), `path`, `authMethod` (`basicAuth` default, `ssh`, `githubApp`), `secretRef`, `gitAuthor` (name defaults to `kratix`) and `insecure` (TLS verification skip; defaults to true when unset per the Go type comment, which is a notable default). The Go type in `api/v1alpha1/gitstatestore_types.go` confirms the enum and defaults and that the resource is cluster-scoped with a Ready condition. GitStateStore is a write target for Kratix; the GitOps agent on the Destination (Flux or Argo CD) is what reads from it.

Scheduling happens in two stages. First, Promise dependencies go to all Destinations by default, or only to Destinations whose labels satisfy the Promise's `spec.destinationSelectors` (equality-based `matchLabels`, all pairs must match). A Destination with `strictMatchLabels: true` only accepts Promises whose selectors match its labels. Second, when a Resource request triggers the `resource.configure` workflow, outputs go to a matching Destination; "when multiple Destinations match, Kratix will by default randomly select a registered Destination". Workflows can add `/kratix/metadata/destination-selectors.yaml`; with a `directory` key it targets that output subdirectory and ignores Promise selectors for it, without one it is added to the Promise selectors. Precedence on conflict: Promise `spec.destinationSelectors`, then Promise workflow file, then Resource workflow file. This is enough to explain how a PCI-style cluster example would route work by labels; the wiki's example page should be checked against these rules (not re-read in this pass).

## Gap: Backstage and the operator pattern

The Backstage Kubernetes configuration page (stable docs, Backstage v1.57.0 shown in site header) shows a portal that reads from clusters rather than reconciling anything. An entity is tied to cluster objects through the `backstage.io/kubernetes-id` annotation on the entity and a matching label on the objects, or a `backstage.io/kubernetes-label-selector` annotation; "the label selector takes precedence over the annotation/service id". Custom resources are not shown unless configured: `customResources` (group, apiVersion, plural) "Defaults to empty array", settable globally or per cluster. There is a `proxy` option for the Kubernetes API proxy (`/api/kubernetes/proxy`). This matches what the wiki already holds (portal over operator-produced resources, not an operator).

The Software Templates (Scaffolder) overview describes it as a tool to "create Components inside Backstage" by loading code skeletons, templating variables and publishing to locations such as GitHub or GitLab; each run is a "task" with a task list and "Start Over". That is an imperative, one-shot task runner, not a reconcile loop. Only the overview page was read, not the writing-templates or custom-actions pages, so whether any built-in action creates Kubernetes custom resources is not verified.

Operator-style integrations exist in community plugins. The TeraSky `backstage-plugins` repository (53 plugins, built against Backstage 1.56.0, last push 2026-11-20) includes a Kubernetes Ingestor, described as "a catalog entity provider which creates catalog entities directly from kubernetes resources", with the ability to "auto-ingest all crossplane claims and KRO instances automatically as components" and to generate Backstage templates for every XRD's claim type. Crossplane and kro resource plugins also exist. This is a controller-like sync loop in the Backstage backend, from cluster to catalog; it is the nearest thing to an operator pattern found, and it is a third-party plugin. The upstream `backstage/community-plugins` repo has workspaces for argocd, flux, tekton, argo-workflows and topology but none named crossplane or kro. The README states Backstage is a CNCF incubating project per the landscape file (project: incubating). Kratix's Destination docs mention a Backstage catalog filled from a Git repository as a use case, a second integration shape (Git as the hand-off).

## Gap: Neutral comparisons of Crossplane with Terraform and single-cloud operators

Truly neutral material was scarce. Searches for Crossplane versus Terraform returned mostly vendor pages: Spacelift (sells Terraform and multi-IaC orchestration), Loft/vCluster, Stategraph, Encore, the Crossplane project blog, plus smaller sites. The pages actually read were the Spacelift article (updated 2026-06-30), a SuperOrbital consultancy post (2022-09-08), a VSHN post (2021-04-29, VSHN is a Crossplane-using managed-services firm and enthusiastic about it), a personal migration walkthrough (2023-05-27), and the Crossplane blog post on cloud add-ons (Nic Cope, Upbound, 2021-02-02; VENDOR/project).

The most independent substantive source is SuperOrbital's 2022 post. It reports that Crossplane has no equivalent of `terraform plan`, that changes to fields that would force recreation in Terraform may be ignored, with the native AWS provider continuing to report in sync, and concludes adoption is "similar to adopting Docker in 2013". It is four years old, predates Crossplane v2 and function-based composition, and the wiki should not treat it as current. The Spacelift article (VENDOR) lists Terraform's larger ecosystem and gentler learning curve and says Crossplane's provider coverage claim is unachievable in full; it also notes Crossplane's CNCF graduation, which the CNCF landscape file confirms. The VSHN post argues Terraform is a CLI run on demand versus Crossplane as an always-on control plane, and says cloud-specific operators (Config Connector, Azure Service Operator, ACK) are "specific to the cloud they are engineered for" while Crossplane gives a cross-cloud abstraction; this echoes the Crossplane project's own framing and is not independent in substance. The migration walkthrough shows a staged path (Terraform provider inside Crossplane, then native providers), which is a procedure, not a comparative assessment.

No independent comparison with Config Connector, ACK, or Azure Service Operator primary documentation was read. Two Medium posts (a Terraform/OpenTofu/Crossplane choice post and a Config Connector pitfalls post) returned empty scrapes. The search tool returned zero results for several adopter-migration and operator-comparison queries. For this evidence-only gap, the options are: rely on dated practitioner posts (SuperOrbital 2022), accept vendor material with explicit tags, or run a fresh primary-doc read of ACK, Config Connector and ASO; the user decides.
